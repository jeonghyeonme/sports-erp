# 12. 원본 요구사항 추적표 및 구현 현황 차이 분석

> 이 문서는 두 가지를 다룹니다.
> 1. **요구사항 추적(Traceability)**: `제안요청서 원본.pdf`(㈜유니비즈컨설팅, 2022.06)에 적힌 원문 요구사항 항목을 하나씩, 이 프로젝트의 어느 설계 문서(1-1~1-9)가 어떻게 받아서 어떤 조정을 거쳤는지 표로 연결합니다. 각 조정의 상세 근거는 이미 [2-1_기술결정사항.md](2-1_기술결정사항.md)에 ADR 형식으로 정리되어 있으므로, 이 문서는 "원본 → 설계 문서 → 결정 근거"를 잇는 인덱스 역할을 합니다.
> 2. **설계 vs 실제 코드 차이(마이그레이션 갭)**: 1-1~1-9 설계 문서는 Prisma/PostgreSQL 실DB를 전제로 쓰여 있지만, **현재 `main` 브랜치에 실제로 병합되어 동작하는 코드는 `MockDataService` 기반 인메모리 스캐폴딩**입니다(2026-09-07 머지 결정, 아래 §2-1). 설계 문서만 읽으면 "이미 다 된 것"처럼 보일 수 있는 항목들을 실측 기준으로 다시 확인합니다.
>
> 원본 PDF는 한글 텍스트에 ToUnicode 매핑이 없는 폰트로 저장되어 있어 `pdftotext`(poppler)로는 추출이 안 되고, PyMuPDF로 재추출했습니다(추출 스크립트 결과는 이 세션 스크래치패드에만 존재, 저장소에는 포함하지 않음).

## 2. 설계 문서 vs 실제 코드 — 마이그레이션 갭

### 2-1. 오늘(2026-09-07) 발견된 것: 인증 모듈이 두 갈래로 각각 구현됨

`git pull` 충돌 해결 과정에서 드러난 사실입니다 — 같은 저장소에서 **로컬(이 세션 이전 커밋)과 원격(origin/main)이 서로 모르는 채로 인증/도메인 모듈을 독립적으로 각자 구현**했습니다.

| | 로컬(폐기, 보존됨) | origin/main(채택, 현재 `main`) |
|---|---|---|
| 데이터 소스 | 실제 Prisma + PostgreSQL | `MockDataService`(인메모리) |
| 인증 기능 | 로그인 + refresh + logout + 비밀번호 변경, bcrypt 계정 잠금(5회/15분), `AppException` 공통 에러 포맷 | 로그인 + `/auth/me`만. refresh/logout/비밀번호변경/계정잠금 **없음** |
| 회원/계정 관리 | `AccountModule`(계정 CRUD), `member/`(회원 CRUD 풀세트) | `members.controller.ts`는 목록 조회(`GET`)만 |
| 현재 위치 | 커밋 `eb79377`(main의 병합 조상 커밋으로 계속 보존됨, 브랜치 포인터는 2026-09-08 삭제) | `main`에 병합되어 동작 중 |

**채택 이유**: origin의 mock 구현 위에 admin-web 프론트엔드 전체(대시보드, 지점 드릴다운, 권한관리 화면)가 이미 만들어져 있어, 이걸 살리는 쪽이 손실이 적다고 판단했습니다(로컬의 실DB 인증은 아직 어떤 프론트엔드도 연결되어 있지 않았음). 로컬 구현은 커밋 `eb79377`에 그대로 남아있으므로, **실DB 전환 시점에 `git show eb79377:apps/api/src/modules/<파일경로>`로 꺼내와 `MockDataService` 호출부를 `PrismaService` 호출로 교체**하는 것이 다음 단계의 실제 작업 내용이 됩니다.

**2026-09-08 정리 완료**: 위 표의 "로컬(폐기)" 코드(`apps/api/src/modules/account/`, `apps/api/src/modules/member/`)는 `main`의 `app.module.ts` 어디에서도 import되지 않는 완전한 죽은 코드였음을 확인하고(참조 0건, `tsc --noEmit` 정상 통과 확인 후) **`main`에서 삭제했습니다.** 이 코드를 담고 있던 `wip/real-db-auth-phase1` 브랜치도 같은 날 정리 차원에서 삭제했습니다 — 단, 그 브랜치는 애초에 `eb79377`이라는 이름표에 불과했고, `eb79377` 자체는 `main`의 병합 커밋(`1ac50ea`)의 부모 커밋이라 **`main` 히스토리에서 여전히 도달 가능**합니다(삭제 전 `git merge-base --is-ancestor`로 확인). 즉 브랜치 이름은 사라졌지만 코드는 git 히스토리에 안전하게 남아있고, `git show eb79377:<경로>`로 언제든 다시 꺼낼 수 있습니다.

### 2-3. 설계 문서가 "당연히 될 것"처럼 서술하지만 실제로는 빠진 세부 항목

설계 문서 본문과 실제 mock 구현을 줄 단위로 대조해 발견한, 위 표보다 더 미세한 차이들입니다.

- **`AuditLog`**: 1-1문서 §2·§5가 "모든 주요 엔티티 변경을 기록"한다고 명시하지만, `mock-data.types.ts`에는 AuditLog 관련 타입 자체가 없습니다. 원본 요구사항 3번(데이터관리방안)의 핵심 대응 장치인데 미구현 상태입니다.
- **민감정보 마스킹(`@Exclude`, 전화번호 마스킹)**: 1-1문서 §5, 1-3문서 §7, 1-6문서 §7이 여러 차례 강조하지만, mock 컨트롤러들은 `MockMember`/`MockStaff` 객체를 가공 없이 그대로 반환합니다(마스킹 로직 없음).
- **계정 잠금/퇴사 즉시 차단**: 1-2문서 §3.2·§6의 핵심 보안 요건("퇴사처리 이후 시스템 접근 통제" — 원본 요구사항 1번의 명시적 문구)인데, `MockAccount`에는 `isActive`/`lockedUntil`/`failedLoginCount` 필드 자체가 없어 **현재 mock 로그인은 비활성화·잠금 개념이 없습니다**. 실DB 버전(커밋 `eb79377`, §2-1 참고)에는 이미 구현되어 있었습니다.
- **Program.status 라이프사이클**: 1-8문서·2-1문서(D7)가 설계·완료로 표시하고 있고 `MockProgram.status`도 실제로 존재하지만, **상태 전이 API(`PATCH /programs/:id/status`)는 없어** 현재는 조회만 가능하고 전이 규칙(허용되지 않은 전이 409 처리 등)은 검증할 방법이 없습니다.
