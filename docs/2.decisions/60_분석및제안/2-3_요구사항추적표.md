# 12. 원본 요구사항 추적표 및 구현 현황 차이 분석

> 이 문서는 두 가지를 다룹니다.
> 1. **요구사항 추적(Traceability)**: `제안요청서 원본.pdf`(㈜유니비즈컨설팅, 2022.06)에 적힌 원문 요구사항 항목을 하나씩, 이 프로젝트의 어느 설계 문서(1-1~1-9)가 어떻게 받아서 어떤 조정을 거쳤는지 표로 연결합니다. 각 조정의 상세 근거는 이미 [2-1_기술결정사항.md](../50_결정및이슈기록/2-1_기술결정사항.md)에 ADR 형식으로 정리되어 있으므로, 이 문서는 "원본 → 설계 문서 → 결정 근거"를 잇는 인덱스 역할을 합니다.
> 2. **설계 vs 실제 코드 차이(마이그레이션 갭)**: 1-1~1-9 설계 문서는 Prisma/PostgreSQL 실DB를 전제로 쓰여 있지만, **현재 `main` 브랜치에 실제로 병합되어 동작하는 코드는 `MockDataService` 기반 인메모리 스캐폴딩**입니다(2026-09-07 머지 결정, 아래 §2-1). 설계 문서만 읽으면 "이미 다 된 것"처럼 보일 수 있는 항목들을 실측 기준으로 다시 확인합니다.
>
> 원본 PDF는 한글 텍스트에 ToUnicode 매핑이 없는 폰트로 저장되어 있어 `pdftotext`(poppler)로는 추출이 안 되고, PyMuPDF로 재추출했습니다(추출 스크립트 결과는 이 세션 스크래치패드에만 존재, 저장소에는 포함하지 않음).

## 2. 설계 문서 vs 실제 코드 — 마이그레이션 갭

### 2-1. 오늘(2026-09-07) 발견된 것: 인증 모듈이 두 갈래로 각각 구현됨

`git pull` 충돌 해결 과정에서 드러난 사실입니다 — 같은 저장소에서 **로컬(이 세션 이전 커밋)과 원격(origin/main)이 서로 모르는 채로 인증/도메인 모듈을 독립적으로 각자 구현**했습니다.

| | 로컬(폐기, 보존됨) | origin/main(채택, 현재 `main`) |
|---|---|---|

### 2-3. 설계 문서가 "당연히 될 것"처럼 서술하지만 실제로는 빠진 세부 항목

설계 문서 본문과 실제 mock 구현을 줄 단위로 대조해 발견한, 위 표보다 더 미세한 차이들입니다.

- **`AuditLog`**: 1-1문서 §2·§5가 "모든 주요 엔티티 변경을 기록"한다고 명시하지만, `mock-data.types.ts`에는 AuditLog 관련 타입 자체가 없습니다. 원본 요구사항 3번(데이터관리방안)의 핵심 대응 장치인데 미구현 상태입니다.
- **민감정보 마스킹(`@Exclude`, 전화번호 마스킹)**: 1-1문서 §5, 1-3문서 §7, 1-6문서 §7이 여러 차례 강조하지만, mock 컨트롤러들은 `MockMember`/`MockStaff` 객체를 가공 없이 그대로 반환합니다(마스킹 로직 없음).
- **계정 잠금/퇴사 즉시 차단**: 1-2문서 §3.2·§6의 핵심 보안 요건("퇴사처리 이후 시스템 접근 통제" — 원본 요구사항 1번의 명시적 문구)인데, `MockAccount`에는 `isActive`는 있지만 `lockedUntil`/`failedLoginCount` 필드는 여전히 없어 **로그인 잠금(5회 실패) 기능은 없습니다.** 퇴사·탈퇴 즉시 차단(`isActive=false`) 자체는 이미 동작하며, 2026-09-18에 "JWT가 매 요청 최신 상태를 재조회하지 않고 로그인 시점 값을 돌려주던" 실제 버그까지 고쳐 문서가 명시한 "즉시" 반영을 실제로 만족시켰습니다.
- **TERMINATED 지점의 파견 직원 처리 (2026-09-20 확인, 미구현)**: 1-1문서 §2-1은 지점이 `TERMINATED`가 되면 그 지점에 현재 파견 중(`StaffAssignment.endDate=null`)인 직원의 파견을 종료 처리하고, 본사가 재배치할 대상 목록에 올려야 한다고 명시한다. 그러나 코드에는 이 로직이 없고, 지점의 `contractStatus`를 바꾸는 API 자체도 없다(mock 데이터에 값이 고정으로 들어 있음). 같은 절이 요구한 나머지 차단(신규 회원 등록·예약·게시글 작성 → 409 `BRANCH_TERMINATED`)은 구현되어 있고 통합 테스트로 검증된다(`apps/api/test/contract-termination.spec.ts`). 파견 종료 항목만 테스트에 `it.todo`로 남겨 두었다. 계정 처리 정책은 설계 자체가 "별개 정책"으로 미정이다. 범위 제외로 확정된 것이 아니라 **설계에는 있으나 아직 안 한 것**이며, 계약 상태 전이 API와 함께 구현하는 것이 자연스럽다.
- **Program.status 라이프사이클**: `PATCH /programs/:id/status` API가 이미 구현되어 전이표 위반 시 409를 반환합니다(2026-09-07 시점엔 없었으나 이후 커밋에서 추가됨 — 이 문서가 갱신을 못 따라갔던 부분). 다만 admin-web ProgramsPage에는 상태 변경 UI가 아직 없어 API 호출은 curl/Postman 수준에서만 검증 가능합니다.
