# 13. 차별화 전략 (RFP 재해석 기반 기능 제안)

> [1-1문서 §1-1](../1.spec/1-1_공통설계서.md#1-1-사업-맥락-원본-rfp-재해석)에서 정리했듯, 스포이즘은 헬스장 체인 본사가 아니라 **아파트·오피스텔 커뮤니티 시설 위탁운영사**이고, 이 ERP는 내부 운영툴이면서 동시에 신규 위탁계약 수주를 위한 영업 도구이기도 합니다. 이 문서는 그 재해석에서 나온 **차별화 기능 후보**를 정리합니다.
>
> 이 문서의 항목들은 원본 RFP의 8개 기능 요구사항([2-3문서](2-3_요구사항추적표.md) §1-1 참고)에 명시적으로 나열되어 있지 않습니다 — 즉 "필수 요구사항"이 아니라 **"이 사업 구조를 제대로 이해했을 때 자연스럽게 따라나오는 제안"**입니다. 2-1문서와 같은 자기비판적 태도를 유지해, 각 항목마다 "정말 필요한가, 오버엔지니어링은 아닌가"를 함께 평가합니다. **모두 Phase 1(필수) 범위 밖입니다** — README 로드맵의 Phase 2 이후, 시간이 남을 때 순서대로 검토할 스트레치 목표로 다룹니다.
>
> **2026-09-08 갱신**: 원래 이 문서 §3에 있던 "본사 파견 인력 관리"는 원본 RFP를 다시 확인한 결과 "확인 전 보류"가 아니라 **원본이 명시한 기본 고용구조**임이 드러나 [1-1문서 §2-2](../1.spec/1-1_공통설계서.md#2-2-staff직원-파견assignment-모델)·[02_인사정보관리](../1.spec/1-3_인사정보관리.md)의 핵심 데이터 모델로 이관했습니다 — "필수 요구사항이 아닌 제안"을 다루는 이 문서의 성격과 맞지 않아졌기 때문입니다. 아래 목록은 그 항목을 뺀 3가지입니다.

## 1. 위탁계약 라이프사이클 관리

**배경**: RFP는 "시스템 불안 → 민원 발생 → 위탁 업장 계약해지"를 기존 시스템의 실패 사례로 명시합니다. 즉 스포이즘에게 "지점"이란 계약이 걸린 자산이고, 계약 만료를 놓치는 것 자체가 사업 리스크입니다. 지금까지 설계는 이 계약 관계를 데이터로 전혀 다루지 않았습니다.

**제안 기능**: [1-1문서 §2-1](../1.spec/1-1_공통설계서.md#2-1-branch지점-데이터-모델--위탁계약-필드)에서 추가한 `Branch.contractStartAt/contractEndAt/contractStatus` 필드를 기반으로,
- SUPER_ADMIN 대시보드에 "갱신 임박 지점" 알림 카드(계약 종료 60일 이내 `RENEWAL_DUE` 지점 목록)
- 지점 상세 화면에 계약 정보 탭(계약 상대방, 계약 기간, 남은 일수)
- 매일 자정 배치로 `contractEndAt` 임박 지점을 `ACTIVE → RENEWAL_DUE`로 자동 전이

**API 초안**: `GET /api/v1/branches?contractStatus=RENEWAL_DUE`(SUPER_ADMIN), `PATCH /api/v1/branches/:id/contract`(계약 갱신 시 새 `contractEndAt` 입력)

**우선순위**: Phase 2 선택. 데이터 모델(1-1문서 §2-1)은 이미 이번 재설계에 포함했으므로, 화면·배치는 Phase 1 핵심 기능(회원관리 등)이 끝난 뒤 추가.

**리스크 자체 평가**: 계약 갱신은 실제로는 영업팀이 별도 계약관리 문서(엑셀/전자결재)로 다룰 가능성이 높고, 이 시스템에 억지로 넣는 것이 오버엔지니어링일 수 있습니다. 다만 **필드 몇 개 추가하는 비용 대비, "우리 시스템은 위탁계약 관리까지 고려했다"는 설계 완성도 어필 효과가 크다**고 판단해 데이터 모델만 먼저 반영하고, 화면·배치 로직은 시간이 남을 때로 미룹니다(즉 "설계는 해두되 구현은 스트레치"라는 절충).

### 1-1. 계약서 OCR·AI 분석 (2026-09-08 추가, 스코프를 계약서 1종으로 한정)

**배경**: 위 위탁계약 필드(`contractPartner`/`contractStartAt`/`contractEndAt` 등)는 지금 설계상 관리자가 수기로 입력하는 것을 전제로 합니다. 그런데 실제로는 종이(또는 스캔된) 계약서 원본이 존재할 것이므로, 이걸 매번 옮겨 적는 대신 **스캔·업로드하면 OCR+AI가 필드를 자동 추출**하게 하면 데이터 입력 부담을 줄이면서 "AI/OCR 역량을 보여주는 시그니처 기능"도 확보할 수 있습니다.

**스코프(중요 — 의도적으로 좁힘)**: 이 기능은 **계약서 1종에만 적용**합니다. 대화 중 프로그램 신청서·직원 자격증까지 같은 파이프라인으로 확장하는 안을 검토했지만, 문서 유형이 늘어날수록 유형별 필드 스키마·검증 로직이 늘어나 범위가 무한정 커지는 걸 막기 위해 **지금은 계약서 하나만 완성도 있게 만들고 나머지는 보류**합니다. 프로그램 신청서·자격증 OCR은 이 기능이 실제로 잘 동작하는 걸 확인한 뒤, 여유가 있을 때 재검토합니다(지금은 착수하지 않음).

**제안 기능**:
- `ContractDocument` 엔티티: `id, branchId(FK), fileUrl, ocrText, extractedFields(JSON: contractPartner/contractStartAt/contractEndAt 등), summary, status(업로드됨→OCR완료→AI분석완료→검토완료), uploadedBy, reviewedBy, reviewedAt`
- 처리 흐름: 관리자가 계약서 스캔본(PDF/이미지) 업로드 → **OCR**(로컬, 예: Tesseract/PaddleOCR)로 텍스트 추출 → **AI**(로컬 소형 모델)로 텍스트에서 계약상대방/계약기간 등 필드 추출 + 3줄 요약 생성 → 관리자가 검토 화면에서 추출값을 확인/수정 → **검토 승인 시에만** `Branch.contractPartner/contractStartAt/contractEndAt`(1-1문서 §2-1)에 반영
- **자동 반영이 아니라 검토 후 반영**인 이유: OCR/AI 추출은 틀릴 수 있고, 계약 필드는 위탁계약 상태 전이(§1 본문)의 근거 데이터라 오류가 그대로 들어가면 파급 효과가 큽니다 — 1-7문서의 "결제 금액은 서버에서 재조회해 검증, 클라이언트를 신뢰하지 않는다"는 원칙과 같은 태도입니다.

**API 초안**: `POST /api/v1/branches/:id/contract-documents`(업로드), `GET /api/v1/branches/:id/contract-documents/:docId`(OCR·AI 결과 조회), `PATCH /api/v1/branches/:id/contract-documents/:docId/review`(검토 확정 → Branch 필드 반영)

**우선순위**: Phase 2~3 스트레치, §1 본문(계약 필드·화면)이 먼저 있어야 의미가 있으므로 그 다음 순서.

**리스크 자체 평가**: 로컬 OCR·AI 모델의 실제 인식률은 스캔 품질에 크게 좌우되어 데모에서 100% 정확도를 보장하기 어렵습니다 — 그래서 "완전 자동화"가 아니라 "관리자 검토를 거치는 보조 도구"로 설계했고, 발표에서도 이 한계를 정직하게 밝히는 게 2-1문서의 태도와 일치합니다. 문서 유형을 계약서 1종으로 제한한 것도 같은 맥락 — 여러 유형을 어중간하게 지원하는 것보다 하나를 확실히 보여주는 쪽이 낫다고 판단했습니다.

## 2. 신규 수주 영업지원 리포트

**배경**: RFP의 "산출물" 항목(Ⅳ.3, p.7)은 "어플 도입 후 기대효과 분석"과 "경영개선 기대효과: 향후 3년간 어플리케이션 도입 후 기대되는 매출액 증가율, 경쟁력 강화로 인한 신규 계약 업장 수 증가율 예측치"를 명시적으로 요구합니다. 그리고 자체 개발의 동기 자체가 "현장발표(PT)에서 최첨단 회원관리 시스템을 어필"하는 것입니다. 즉 이 시스템이 만들어내는 **데이터 자체가 다음 수주 영업의 증거자료**가 되어야 합니다.

**제안 기능**: 특정 지점의 "도입 전/후" 또는 "기간 대비" 핵심 지표(회원 수 추이, 진행중 프로그램 수, 매출 — 1-7문서 Payment 도메인 완성 후)를 뽑아 발표자료 형태로 export하는 기능. 이미 있는 `branchSummary`(회원/직원/진행중 프로그램 카운트, mock-data.service.ts)를 시계열로 확장하는 개념입니다.

**API 초안**: `GET /api/v1/branches/:id/performance-report?from=&to=` — 기간별 회원 증가율, 프로그램 운영 현황 요약 JSON(우선 화면에서 렌더링, PDF export는 더 나중 단계)

**우선순위**: Phase 5(통합·발표 준비) 근처의 스트레치 목표. 1-7(예약및결제)·1-4(근태관리)이 아직 구현되지 않아 매출 등 핵심 지표 자체가 없는 상태이므로, 그 전 단계에서는 의미가 제한적입니다.

**리스크 자체 평가**: 지금 당장은 데이터 기반이 부족해(매출·근태 미구현) 만들어도 빈 리포트에 가깝습니다. **선구현보다 "이런 리포트가 나올 수 있도록 지금부터 시계열 데이터(어떤 시점에 회원이 몇 명이었는지)를 남기는 설계"를 해두는 것이 먼저**입니다 — 즉 `AuditLog`(1-1문서 §5, 2-3문서 §2-3에서 미연동으로 지적된 항목)를 실제로 연결하는 작업이 이 기능의 실질적 선행 조건입니다.

## 3. 본사 파견 인력 관리 — [1-1문서 §2-2](../1.spec/1-1_공통설계서.md#2-2-staff직원-파견assignment-모델)로 이관됨

이 항목은 원래 "RFP 배경 문장에서 추론한, 발주자 확인 전엔 보류할 아이디어"로 여기 있었습니다. 그런데 2026-09-08 원본 PDF를 다시 확인한 결과, "행정 및 트레이너들 역시 해당 지역 또는 본사 파견 형태로 직원이 투입"이라는 문장은 **추론이 아니라 원본이 직접 명시한 기본 고용구조**임이 확인됐습니다(관리자급인 "행정"과 "트레이너"를 나란히 언급 — BRANCH_ADMIN·STAFF 모두 대상). "확인 없이는 구현하지 않는다"던 전제가 확인으로 해소된 셈입니다.

**필수 요구사항이 아닌 제안**을 다루는 이 문서의 성격과 더 이상 맞지 않으므로, `StaffAssignment` 데이터 모델과 API·화면 설계는 [1-1문서 §2-2](../1.spec/1-1_공통설계서.md#2-2-staff직원-파견assignment-모델)와 [02_인사정보관리](../1.spec/1-3_인사정보관리.md)로 옮겨 Phase 1 핵심 설계에 포함했습니다.

## 4. 데이터 주권을 "보이는" 기능으로

**배경**: [2-1문서 D18](2-1_기술결정사항.md#d18-자체개발데이터-주권-원칙-saas-벤더-미사용)에서 "왜 자체 개발인가"의 근거(벤더 데이터유출·도산 리스크)를 정리했습니다. 하지만 이건 지금 **문서로만 존재하는 원칙**이라, 심사·발표 자리에서 "그래서 실제로 뭐가 다른가"를 보여줄 화면이 없습니다.

**제안 기능**: 새 기능을 만들기보다, 이미 설계되어 있지만 미연동 상태인 `AuditLog`(1-1문서 §5)를 실제로 연결하고, SUPER_ADMIN 전용 "접근 이력" 화면을 노출합니다 — "회원 개인정보를 누가 언제 조회/수정했는지"를 스포이즘 관리자 본인이 직접 열람할 수 있다는 것 자체가, "데이터가 외부로 새지 않고 우리가 직접 통제한다"는 D18의 주장을 말이 아니라 화면으로 증명하는 방법입니다. 개인정보보호법 26조 준수([2-3문서](2-3_요구사항추적표.md) §1-2, 8번 항목)의 실질적 이행이기도 합니다.

**API 초안**: `GET /api/v1/audit-logs?entityType=&entityId=&from=&to=`(SUPER_ADMIN 전용)

**우선순위**: 새 도메인이 아니라 기존 설계(AuditLog)의 완성이므로, 다른 Write API들과 함께 Phase 2~3에서 자연스럽게 챙길 항목. 별도 신규 기능이 아니라 **"이미 하기로 했던 것을 실제로 하기"**에 가깝습니다.

**리스크 자체 평가**: 오버엔지니어링 우려가 가장 적은 항목입니다 — AuditLog는 이미 1-1문서 §5에 설계되어 있었고, 단지 아직 어떤 쓰기 경로에도 연결되지 않았을 뿐입니다([2-3문서](2-3_요구사항추적표.md) §2-3). 새로 설계할 것 없이 "이미 있는 설계를 실제로 연결"하면 되므로 비용 대비 효과(발표 설득력)가 가장 큽니다.
