# 09. 기술적 결정사항 분석 (Technical Decision Log)

> 1.spec(1-1~1-9) 설계 문서와 실제 구현(Prisma 스키마, 커밋 이력)에 이미 녹아 있는 기술적 결정들을 한데 모아, **결정 내용 / 근거·타당성 / 장단점 / 대안**을 정리한 문서입니다. 새로운 결정을 내리는 문서가 아니라, 지금까지의 결정을 사후 검토(retrospective)한 기록입니다.
>
> 각 항목은 ADR(Architecture Decision Record)과 유사한 형식을 따르되, 1인 개발·포트폴리오 프로젝트라는 맥락을 항상 "타당성" 판단의 기준으로 둡니다 — 즉 "엔터프라이즈 정답인가"가 아니라 "이 프로젝트의 목표(졸업작품 심사 + 시연 가능한 완성도)에 맞는 선택인가"로 평가합니다.
>
> 관련: [트러블슈팅 문서](2-2_트러블슈팅.md)에서는 이 문서의 결정들을 구현하는 과정에서 실제로 부딪힌 문제와 해결 과정을 다룹니다.

## 전체 구조를 쉽게 이해하기 (비유로 보는 시스템)

기술 용어 없이 비유로 먼저 전체 그림을 그려봅니다. 아래 각 결정 항목을 읽기 전에 이 부분만 훑어도 시스템의 뼈대가 잡힙니다.

**이 시스템은 "여러 지점을 가진 헬스장 체인의 본사 시스템"이라고 생각하면 됩니다.**

- **지점(Branch)**: 서초점·강남점처럼 물리적으로 분리된 매장. 각 지점은 자기 지점의 회원·직원·프로그램만 봐야 하고, 다른 지점 것을 몰래 보면 안 됩니다 — 편의점 본사 시스템에서 A매장 점주가 B매장 매출을 못 보는 것과 같은 이치입니다. (→ D2)
- **출입증(Account)과 직급(Role)**: 로그인하는 모든 사람(본사 직원, 지점장, 트레이너, 회원)은 "출입증" 하나씩을 갖고, 그 출입증에 "직급"이 찍혀 있습니다. 직급은 딱 4가지뿐입니다 — 본사 관리자 / 지점 관리자 / 일반 직원(트레이너) / 회원. 직급에 따라 볼 수 있는 화면과 누를 수 있는 버튼이 달라집니다. (→ D1, D3, D12)
- **로그인 유지 방식**: 한 번 로그인하면 30분짜리 "임시 출입증"을 받고, 만료되면 뒤에 있는 14일짜리 "재발급 카드"로 조용히 새 임시 출입증을 받습니다. 임시 출입증을 도둑맞아도 30분 안에만 위험하도록 일부러 짧게 잡은 것입니다. (→ D4)
- **프로그램(Program)과 이용 방식**: 지점이 파는 상품(요가 클래스, 헬스장 자유이용권, PT 등)은 세 가지 팔리는 방식 중 하나입니다 — "그냥 와서 쓰는 것"(자유이용), "시간을 정해 예약하고 돈 내는 것"(회차 예약), "미리 회수권을 사고 하나씩 까먹는 것"(PT 패키지). 서로 완전히 다른 흐름이라 시스템도 다르게 처리합니다. (→ D8)
- **프로그램 상태**: 프로그램은 "준비중 → 진행중 → (일시중단) → 종료"라는 신호등 같은 상태를 가집니다. 이래야 "지금 우리 지점이 뭘 운영하고 있는지"를 한눈에 볼 수 있습니다. (→ D7)
- **예약 정원 다툼**: 마지막 한 자리를 두 사람이 동시에 예약하려 하면, 시스템이 한 명씩 순서대로 확인하도록 강제해서 정원 초과 사고를 막습니다 — 좁은 문에 한 번에 한 명씩만 들어가게 하는 것과 같습니다. (→ D6)
- **결제**: 실제 카드사와 연결하지 않고 "가짜 결제 승인" 화면으로 결제가 성공한 것처럼 흉내만 냅니다(진짜 카드사 연결에는 사업자 등록이 필요하기 때문). 대신 결제 상태가 "대기 → 승인 → 환불"로 바뀌는 흐름 자체는 진짜처럼 정교하게 만듭니다. (→ D5)
- **혼잡도**: 사람을 세는 카메라·센서가 없으니, "지금 체크인하고 아직 체크아웃 안 한 사람 수"를 세어 혼잡도를 자동 계산합니다. 이상하면 관리자가 손으로 고칠 수도 있습니다. (→ D10)
- **삭제 대신 "비활성화"**: 회원이 탈퇴해도 DB에서 그 사람 정보를 실제로 지우지 않고 "탈퇴함" 표시만 남깁니다 — 과거 결제·예약 기록이 깨지지 않게 하기 위해서입니다. 퇴사한 직원의 인사기록을 파쇄하지 않고 캐비닛에 보관하는 것과 비슷합니다. (→ D9)

이 비유들을 기억해두면 아래 각 결정 항목의 기술적 설명(근거·장단점)이 "왜 이런 선택을 했는지" 훨씬 쉽게 읽힙니다.

## D1. RBAC 4-Role 고정 (개별 권한 커스터마이징 미지원)

**결정**: 원본 요구사항의 "사용자별·프로그램별 세부 권한(입력/수정/삭제/조회/출력)"을 개별 ACL로 구현하지 않고, `SUPER_ADMIN / BRANCH_ADMIN / STAFF / MEMBER` 4개 고정 Role 기반 RBAC로 단순화했다. ([1-2문서](../../1.spec/10_인사조직/1-2_권한관리.md) §1)

**쉽게 말하면**: 직원 개개인한테 맞춤 권한을 하나하나 설정해주는 대신, "본사 관리자/지점 관리자/일반 직원/회원" 4개짜리 완성된 직급표를 만들어두고 그중 하나를 배정하는 방식입니다.

**근거**: 세밀한 개별 권한 부여(ACL) 시스템은 권한 관리 UI, 권한-리소스 매트릭스 저장 구조, 권한 변경 이력까지 요구하는 별도의 서브시스템이다. 1인 개발 리소스로는 이걸 만드는 데 들이는 공수가 실제 심사/시연 가치에 비해 과도하다. 반면 원본 요구사항의 실질적 핵심(요구사항 5번 "타현장 정보 조회 불가능")은 지점 간 격리이지, 개인별 세부 CRUD 권한이 아니다.

**타당성**: 높음. 대부분의 실서비스 ERP도 초기 단계에서는 Role 기반으로 시작해 필요할 때 ACL로 확장한다. 요구사항의 "본질"과 "표면 형태"를 구분해 본질(지점 격리, 퇴사 즉시 차단, 관리자/일반직원 분리)에 공수를 집중한 것은 합리적인 스코프 조정이다.

**장점**
- 구현·테스트가 단순해 Phase 1 내에 완성 가능(4개 Role × Guard 데코레이터 조합만 검증하면 됨)
- 문서화가 쉬워 심사 발표에서 권한 매트릭스 표 하나로 전체를 설명 가능
- Guard 로직이 예측 가능해 보안 버그 표면적이 작음

**단점·리스크**
- 실제 조직에는 "이 지점 관리자에게는 결제 조회만 주고 회원 수정은 막고 싶다" 같은 요구가 생길 수 있는데, 이 구조로는 Role을 새로 만들거나 예외 로직을 하드코딩해야 함
- Role이 늘어날수록(이미 4→ 늘리기 어려운 게 아니라, STAFF 추가 사례(D12)처럼 실제로 한 번 늘어났음) 권한 매트릭스 표가 커지고 Guard 조건 분기가 늘어남

**대안 및 미채택 사유**: 리소스별 Permission 테이블 + Role-Permission 매핑(RBAC2)은 이론적으로 더 유연하지만, 이 프로젝트 규모에서는 오버엔지니어링이라고 판단해 채택하지 않음.

## D2. 멀티테넌시를 `branchId` 컬럼 격리로 구현

**결정**: 지점별 데이터 격리를 별도 DB/스키마 분리(schema-per-tenant) 없이, 공유 테이블에 `branchId` 컬럼을 두고 `BranchScopeGuard` + 서비스 레이어의 이중 `WHERE branchId = ?` 강제로 구현한다. ([1-1문서](../../1.spec/00_공통/1-1_공통설계서.md) §3.3, [1-2문서](../../1.spec/10_인사조직/1-2_권한관리.md) §6)

**쉽게 말하면**: 지점마다 별도의 시스템을 새로 만드는 대신, 하나의 시스템 안에서 모든 데이터에 "어느 지점 것인지" 표시(branchId)만 해두고, 지점 관리자가 로그인하면 자기 지점 표시가 붙은 것만 보이도록 걸러줍니다.

**근거**: schema-per-tenant나 DB-per-tenant는 지점 수가 매우 많거나(수백~수천), 지점 간 완전한 물리적 격리가 컴플라이언스상 필요할 때(예: 금융권 개별 법인)만 정당화되는 복잡도다. 아파트 커뮤니티 시설 위탁운영사의 지점 수는 현실적으로 수십 단위이고, 격리 요구도 "관리자 화면에서 실수로/의도적으로 다른 지점을 못 보게"이지 물리적 분리가 아니다.

**타당성**: 높음. Row-level 격리는 업계 표준 패턴(예: Salesforce의 org_id 방식)이며, 이 규모에서는 정답에 가깝다. 다만 **가드를 우회하면 전체 데이터가 뚫린다**는 것이 이 패턴의 본질적 트레이드오프이므로, 문서에서 이미 "가드 + 서비스 레이어 이중 적용"으로 우회 방지 안전장치를 뒀다는 점(1-2문서 §3.3)이 이 리스크를 인지하고 있다는 근거다. 참고로 이 격리가 지키는 것은 "지점 간" 데이터 경계일 뿐이고, "스포이즘 대 외부 ERP 벤더" 경계(왜 애초에 이 시스템을 자체 개발하는가)는 별개의 결정이다 — 그 근거는 [D18](#d18-자체개발데이터-주권-원칙-saas-벤더-미사용)을 참고.

**장점**
- 마이그레이션/백업/모니터링이 단일 DB 인스턴스로 단순화됨
- 지점 간 통계 집계(SUPER_ADMIN의 전체 조회)가 JOIN 하나로 가능 — schema-per-tenant였다면 UNION ALL 등 훨씬 복잡해짐
- 로컬 개발 환경(Docker Compose 단일 PostgreSQL)과 정확히 일치해 개발 난이도가 낮음

**단점·리스크**
- 코드베이스 전역에서 "이 쿼리에 branchId 필터를 빼먹었는가"를 매번 신경 써야 함 — 필터 누락은 곧 정보 유출 취약점이 됨(가장 위험한 실수 유형)
- Prisma 미들웨어나 Row-Level Security(PostgreSQL RLS) 같은 DB 레벨 강제 장치 없이 애플리케이션 레벨(Guard+Service)에만 의존 → 새 API를 추가할 때마다 실수로 가드를 안 붙이면 뚫림
- 실제 심사/포트폴리오 시연에서 "타 지점 접근 차단"을 테스트 체크리스트(1-2문서 §9)로 명시한 것은 좋지만, 이게 유일한 안전망이라 테스트 커버리지가 곧 보안 커버리지임

**대안 및 미채택 사유**: PostgreSQL Row-Level Security(RLS)로 DB 레벨에서 branchId를 강제하는 방법도 있었으나, Prisma의 RLS 지원이 제한적이고(세션 컨텍스트 설정이 번거로움) 설정 복잡도 대비 이득이 크지 않다고 판단. **다만 이는 재고할 만한 지점**이다 — Phase 1 구현 시 애플리케이션 레벨 필터 누락 버그가 실제로 나온다면 RLS 도입을 고려할 가치가 있다.

## D3. Account 단일 테이블 + Staff/Member 1:1 프로필 분리

**결정**: 로그인 주체(`Account`: email/passwordHash/role/isActive)를 하나의 테이블로 통합하고, `Staff`(BRANCH_ADMIN·STAFF용)와 `Member`(MEMBER용)를 각각 Account에 1:1 연결되는 "역할별 상세 프로필" 테이블로 분리했다. ([1-1문서](../../1.spec/00_공통/1-1_공통설계서.md) §3.1)

**쉽게 말하면**: 로그인 정보(아이디/비밀번호)는 모든 사람이 공통으로 한 곳에 저장하고, 그 사람이 직원인지 회원인지에 따라 필요한 상세 정보(직급, 회원번호 등)는 따로 연결된 서류철에 저장합니다.

**근거**: 인증 로직(로그인/토큰/잠금)은 Role에 무관하게 동일해야 하므로 한 곳에 모으는 게 자연스럽고, 반면 "직원"과 "회원"은 완전히 다른 도메인 속성(직급/입사일 vs 회원번호/PT세션)을 가지므로 억지로 한 테이블에 넣으면 nullable 컬럼이 남발된다.

**타당성**: 높음. 이는 검증된 패턴(사용자 인증과 프로필을 분리하는 것)이며, `Member.accountId`가 nullable이라는 설계(1-6문서 §3 — 오프라인 등록 시 앱 미가입 상태로 먼저 생성)와도 잘 맞아떨어진다. Account 없이 Member만 존재할 수 있다는 요구사항을 이 구조가 정확히 표현한다.

**장점**
- 오프라인 회원 등록(Account 없이 Member만 생성) 같은 실제 운영 시나리오를 스키마가 자연스럽게 지원
- 인증 관련 보안 로직(bcrypt, 잠금, RefreshToken)이 Account 하나에 집중되어 감사·점검 포인트가 명확

**단점·리스크**
- BRANCH_ADMIN과 STAFF가 "둘 다 Staff 레코드를 가지며 Account.role로만 구분"(1-2문서 §3.1)되는 구조라, 쿼리 시 "이 Staff가 관리자인지 일반직원인지"를 판단하려면 항상 Account를 조인해야 함 — Staff 테이블 자체만 봐서는 알 수 없음
- Account.role이 바뀌면(예: STAFF → BRANCH_ADMIN 승진) Staff 레코드는 그대로 두고 권한만 바뀌는 게 맞는 설계인지 문서에 명시되어 있지 않음 — 향후 애매한 케이스가 될 수 있음

## D4. JWT Access(30분)/Refresh(14일, rotate) + 저장소 분리

**결정**: Access Token은 30분 수명으로 클라이언트 메모리/헤더에, Refresh Token은 14일 수명으로 admin-web은 httpOnly Cookie, member-app은 SecureStore에 저장한다. Refresh는 1회용(rotate) 방식을 권장한다. ([1-2문서](../../1.spec/10_인사조직/1-2_권한관리.md) §3.2, §6)

**쉽게 말하면**: 한 번 로그인하면 30분짜리 "임시 출입증"을 주고, 만료되면 뒤에 있는 14일짜리 "재발급 카드"로 조용히 새 임시 출입증을 받게 합니다. 임시 출입증을 도둑맞아도 피해가 30분 안에서 끝나도록 일부러 짧게 잡은 것입니다.

**근거**: Access Token을 길게 잡으면 탈취 시 피해 window가 커지고, 너무 짧으면 갱신 요청이 잦아져 UX와 서버 부하 모두 손해다. 30분/14일은 업계에서 흔히 쓰이는 중간값이다. httpOnly Cookie는 admin-web(브라우저)에서 XSS로 인한 토큰 탈취를 막는 표준 방어이고, SecureStore는 React Native의 표준 안전 저장소다.

**타당성**: 높음, 업계 표준을 그대로 따른 선택. 클라이언트 유형별로 적절한 저장소를 다르게 지정한 것도 정확하다.

**장점**
- httpOnly Cookie + SecureStore 조합은 각 플랫폼에서 검증된 최선의 선택지에 가까움
- Refresh Token을 원문이 아닌 해시로 저장(1-2문서 §3)해 DB 유출 시에도 토큰 자체는 즉시 악용 불가

**단점·리스크**
- httpOnly Cookie 사용 시 CSRF 방어(SameSite 속성, CSRF 토큰 등)가 별도로 필요한데, 문서에 명시적으로 다뤄지지 않음 — 실제 구현 시 반드시 챙겨야 할 항목
- Refresh Token rotate가 "권장"으로만 적혀 있고 Phase 1 필수 항목이 아님(1-2문서 §8 Phase 2로 분류) → Phase 1까지만 구현하고 멈추면 탈취된 Refresh Token이 만료 전까지 계속 유효한 상태로 남음

**How to apply (구현 시 주의)**: admin-web의 Cookie 발급 시 `SameSite=Strict` 또는 `Lax` + `Secure` 플래그를 반드시 설정할 것. CSRF 방어를 Phase 1 체크리스트에 암묵적으로라도 포함시키는 것을 권장.

## D5. Mock Payment 모듈 (실 PG 미연동)

**쉽게 말하면**: 진짜 카드사와 연결하는 대신, 결제가 성공한 것처럼 화면과 데이터만 그럴듯하게 흉내 내는 "가짜 결제" 기능을 만들었습니다.

**타당성**: 높음. 불가능한 것(실 PG 가입)을 억지로 하지 않으면서도, 평가받고자 하는 것(결제 상태 전이 설계 능력)은 정확히 겨냥했다. 토스페이먼츠 테스트 키 옵션을 스트레치로 남긴 것도 시간이 남을 때의 확장 경로를 미리 설계해둔 좋은 판단이다.

**장점**
- 결제 상태 전이 로직(대기→승인→환불)을 PG 응답 지연/실패 같은 외부 변수 없이 안정적으로 테스트·시연 가능
- `mockApprovalNo`(모의 승인번호) 필드로 "실제 결제인 것처럼" 시연 완성도를 챙김

**단점·리스크**
- 실 PG 웹훅(비동기 결제 승인 통지) 처리 경험은 이 구조로는 얻을 수 없음 — 만약 토스페이먼츠 테스트 연동까지 간다면 이 부분이 새로운 학습 포인트가 될 것
- 서버에서 Program 가격을 재조회해 검증(1-7문서 §7)한다는 원칙은 명시했으나, "결제 금액 위변조 방지"라는 보안 관점의 테스트 케이스가 2-1문서(현 문서) 이전엔 테스트 체크리스트에 없었음(1-7문서 §9 참고) — 실제 구현 시 추가 권장

## D6. 예약 동시성 제어: 트랜잭션 내 `SELECT ... FOR UPDATE`

**결정**: `ScheduleSlot.bookedCount`를 캐시 필드로 별도 관리하지 않고, 예약 생성 시 트랜잭션 내에서 락을 건 뒤 `capacity`와 비교해 정원 초과를 막는다. ([1-7문서](../../1.spec/20_이용자서비스/1-7_예약및결제.md) §6)

**쉽게 말하면**: 마지막 한 자리를 두 사람이 동시에 예약하려 하면, 한 명씩 차례로 확인하게 만들어서 정원이 초과되는 사고를 막습니다 — 좁은 문에 한 번에 한 명씩만 들어가게 하는 것과 같습니다.

**근거**: 캐시 카운터(`bookedCount` 컬럼을 두고 예약/취소마다 증감) 방식은 갱신 순서가 꼬이면(예: 동시 취소+예약) 실제 예약 건수와 캐시 값이 어긋날 위험이 있다. 실제 테이블을 매번 세는 방식이 정합성 면에서 더 안전하다.

**타당성 — 2026-09-15 정정**: 원래 여기 "실제로 정합성이 보장되는 올바른 구현이라 어필이 과장이 아니다"라고 적었는데, **이 자평 자체가 틀렸었습니다.** 원래 설계인 `SELECT COUNT(*) FROM Reservation ... FOR UPDATE`는 **기존에 존재하는 Reservation 행에만** 락을 겁니다 — 정원에 여유가 있어 기존 예약이 적거나 0건일 때는 잠글 대상이 없어, 두 트랜잭션이 동시에 통과해 정원을 초과하는 팬텀 삽입이 그대로 발생할 수 있었습니다. `FOR UPDATE`라는 키워드를 썼다는 사실과 "실제로 동시성이 안전하다"는 것은 다른 문제인데, 이 둘을 구분하지 못하고 "키워드가 있으니 안전하다"고 self-assess한 것이 이 항목의 실수였습니다. 수정된 설계는 `ScheduleSlot` 행 자체를 먼저 `SELECT ... FOR UPDATE`로 잠급니다(회차 행은 예약 건수와 무관하게 항상 존재하므로 반드시 잠금 대상이 있음) — 이렇게 "카운트할 대상"이 아니라 "정원이 걸려있는 리소스 자체"를 잠가야 동시성이 실제로 안전해집니다. 지금은 이 정정된 설계 기준으로 타당성이 높다고 평가합니다.

**장점**
- 캐시 필드를 두지 않아 "캐시와 실제 값의 불일치"라는 클래스의 버그가 원천적으로 발생하지 않음
- Postgres의 행 락 메커니즘을 그대로 활용해 애플리케이션 레벨의 분산 락(Redis 등) 같은 추가 인프라 없이 구현 가능

**단점·리스크**
- 트랜잭션이 길어지거나(예: 결제 승인까지 한 트랜잭션에 묶으면) 락 보유 시간이 늘어나 데드락/타임아웃 위험이 커짐 — 1-7문서의 흐름(예약 생성 → 별도 API로 결제 승인)처럼 트랜잭션을 짧게 끊어가는 설계가 유지되어야 함
- 트래픽이 실제로 매우 커지는 상황(다지점 대규모 서비스)에서는 특정 인기 슬롯에 요청이 몰릴 때 락 대기열이 병목이 될 수 있음 — 다만 이는 이 프로젝트의 스코프를 벗어나는 가정임

**대안 및 미채택 사유**: 낙관적 락(버전 컬럼 + 재시도)도 검토 가능했으나, 재시도 로직이 클라이언트/서버 양쪽에 필요해 구현 복잡도가 늘고, 예약처럼 "실패 시 즉시 사용자에게 정원마감을 알려도 되는" 도메인에서는 비관적 락(FOR UPDATE)이 더 단순하고 적합하다고 판단.

**구현 메모(2026-09-18)**: 현재 `MockDataService`는 Postgres가 아니라 단일 Node 프로세스에서 동기적으로 실행되는 인메모리 배열이다. `createReservation` 메서드 안에는 정원 체크(`bookedCount` 계산)와 `INSERT`(배열 push) 사이에 `await`가 전혀 없으므로, 자바스크립트 이벤트 루프의 단일 스레드 특성이 사실상 `ScheduleSlot` 행 락과 동일한 효과를 낸다 — 두 요청이 동시에 도착해도 한쪽이 메서드 전체를 끝마칠 때까지 다른 쪽은 실행될 수 없다. 그래서 위에서 설명한 팬텀 삽입 시나리오가 지금 구조에서는 원천적으로 발생하지 않는다. 다만 이는 "우연히 안전한" 것이 아니라 "동기 코드라 안전한"것이므로, 실DB(Prisma/PostgreSQL) 전환 시에는 이 가정이 깨진다 — 그때는 위에서 정정한 대로 `ScheduleSlot` 행에 `SELECT ... FOR UPDATE`를 실제로 걸어야 한다.

## D7. `Program.status` 4단계 라이프사이클 (isActive 불리언 대체)

**결정**: 커밋 `f90d8ed`에서 `Program.isActive` 불리언을 `status` enum(`PREPARING/RUNNING/PAUSED/ENDED`) + `startDate`/`endDate`로 교체했다. ([1-8문서](../../1.spec/20_이용자서비스/1-8_강사프로그램게시.md) §3-2)

**쉽게 말하면**: 프로그램이 "운영중이다/아니다" 두 가지로만 표시되던 것을, "준비중/진행중/일시중단/종료" 네 단계 신호등으로 바꿔서 지금 상태를 더 정확히 알 수 있게 했습니다.

**근거**: 불리언 하나로는 "아직 시작 전"과 "끝난 것"을 구분할 수 없다. 지점 관리자가 "지금 우리 지점이 뭘 운영 중인가"를 즉답해야 한다는 실사용 요구(원본 요구사항엔 없었으나 실무 관점에서 추가)가 있어, 상태를 명시적으로 확장했다.

**타당성**: 매우 높음 — 이 프로젝트에서 가장 잘 짚은 리팩터링 판단 중 하나. 불리언 플래그가 실제로는 다차원 상태를 표현하지 못해 나중에 조건문이 누더기가 되는 전형적인 패턴을 초기에 미리 방지했다. `Program(branchId, status)` 인덱스 하나로 지점 대시보드 쿼리가 해결된다는 것도 설계-구현 정합성이 좋다.

**장점**
- 상태 전이표(§3-2)가 "허용되는 다음 상태"까지 명시해, `PATCH /programs/:id/status`에서 잘못된 전이(ENDED→RUNNING)를 409로 거부하는 견고한 상태 머신이 됨
- 지점 현황판(준비중 N·진행중 N·휴강 N) 기능이 이 필드 하나로 자연스럽게 파생됨

**단점·리스크**
- Phase 2로 미룬 "startDate/endDate 도달 시 자동 상태 전이 배치"가 구현되지 않으면, 관리자가 수동으로 상태를 안 바꾼 프로그램은 날짜가 지나도 계속 `RUNNING`으로 남아 데이터 신뢰도가 떨어짐 — 이 배치와 "관리자가 수동으로 PAUSED로 바꿔둔 경우 자동 전이가 덮어쓰지 않아야 한다"는 예외 처리(1-8문서 §3-2 마지막 문단)는 함께 구현되어야 의미가 있음. 자동 전이만 있고 이 예외 처리가 빠지면 "휴강 처리해뒀는데 자동으로 RUNNING으로 되돌아간다"는 실사용 버그가 됨
- 기존에 `isActive`를 참조하던 코드/시드가 있었다면(실제로 seed.ts가 이 커밋에서 함께 수정됨) 마이그레이션 시 기존 데이터의 `isActive=true`를 어떤 status로 매핑할지 규칙이 필요 — 이번엔 아직 프로덕션 데이터가 없는 시점이라 문제가 없었지만, 이후 유사한 스키마 변경 시엔 데이터 마이그레이션 스크립트가 필요함을 유념

## D8. `pricingType` 3분류 명시적 enum

**결정**: 프로그램의 이용 방식을 `price===0`이라는 암묵적 규칙 대신 `FREE_ACCESS`(자유이용) / `PAID_SESSION`(회차 예약형, 무료 회차 포함) / `PT_PACKAGE`(세션 차감형) 3개의 명시적 enum으로 분리했다. ([1-8문서](../../1.spec/20_이용자서비스/1-8_강사프로그램게시.md) §3-1)

**쉽게 말하면**: "가격이 0원이면 무료"라고 대충 판단하는 대신, 프로그램을 등록할 때부터 "자유이용/예약형/PT패키지" 중 어떤 방식으로 파는지를 명확하게 표시해둡니다.

**근거**: "가격이 0이면 무료 프로그램"이라는 암묵적 규칙은 "정원 관리는 필요한데 무료인 체험 클래스"(PAID_SESSION, price=0)와 "예약 개념 자체가 없는 자유이용"(FREE_ACCESS)을 구분하지 못한다. 이 둘은 완전히 다른 트랙(Reservation 생성 여부 자체가 다름)으로 이어지므로, 가격이 아니라 "이용 방식"을 1급 필드로 승격시킨 것이다.

**타당성**: 높음. 이는 "암묵적 규칙을 명시적 상태로 승격"하는 좋은 도메인 모델링 사례로, D7과 같은 계열의 판단이다. 1-7/1-9문서 전반에서 이 enum 하나로 Reservation/Payment/FacilityCheckIn 중 어느 트랙을 탈지 깔끔하게 분기된다(1-7문서 §6).

**장점**
- 세 트랙(예약+결제 / 세션 차감 / QR체크인)이 서로 겹치지 않고 배타적으로 분리되어, 코드 분기(`switch(pricingType)`)가 도메인 규칙을 그대로 반영함
- 프로그램 등록 화면에서 `FREE_ACCESS`면 가격/정원 입력 자체를 비활성화(1-8문서 §6)하는 UX 규칙도 이 enum에서 자연스럽게 파생됨

**단점·리스크**
- 세 트랙이 겹치지 않는다는 전제가 깨지는 새 요구(예: "이 프로그램은 자유이용이면서 동시에 PT 세션도 차감하고 싶다")가 생기면 enum을 늘리는 대신 구조 자체를 재검토해야 함 — 다만 원본 요구사항 범위에서는 이런 케이스가 없어 현재로선 과도한 우려

## D9. 소프트 삭제 원칙 전반

**결정**: 회원/직원 등 핵심 엔티티는 물리 삭제 대신 상태값(`isActive=false`, `status=탈퇴/퇴사`, `deletedAt`)으로 처리해 결제/예약 등 참조 무결성을 보존한다. ([1-1문서](../../1.spec/00_공통/1-1_공통설계서.md) §4)

**쉽게 말하면**: 회원이 탈퇴해도 DB에서 그 사람 정보를 실제로 지우지 않고 "탈퇴함" 표시만 남깁니다 — 퇴사한 직원의 인사기록을 파쇄하지 않고 캐비닛에 보관해두는 것과 비슷합니다.

**근거**: 회원이 탈퇴해도 과거 결제/예약 기록(Payment, Reservation)은 회계/이력 관리상 남아있어야 하고, FK로 참조된 레코드를 물리 삭제하면 그 이력 자체가 깨지거나 CASCADE 삭제로 의도치 않게 함께 사라진다.

**타당성**: 매우 높음. 결제·인사 이력을 다루는 시스템에서 소프트 삭제는 사실상 필수 원칙이며, 이 프로젝트 전역에 일관되게 적용된 것(Member/Staff/Program/Post 모두 동일 원칙)이 설계 일관성 측면에서 좋은 점이다.

**장점**
- AuditLog(1-1문서 §5)와 결합해 "누가 언제 무엇을 비활성화했는가"까지 추적 가능
- 퇴사 처리(Staff.status=퇴사 + Account.isActive=false)처럼 여러 테이블에 걸친 상태 전이를 하나의 트랜잭션으로 원자적으로 처리하는 패턴(1-3문서 §6)과 자연스럽게 맞물림

**단점·리스크**
- 소프트 삭제된 레코드를 매 쿼리에서 걸러내야 하므로(`WHERE status != '탈퇴'`), D2의 branchId 필터와 마찬가지로 "필터 누락"이 새로운 버그 클래스가 됨 — 특히 Prisma는 기본적으로 소프트 삭제를 네이티브 지원하지 않으므로, 매 쿼리마다 수동으로 조건을 넣거나 Prisma 미들웨어로 전역 처리해야 함(문서에 이 구현 방식은 명시되어 있지 않음)
- 데이터가 영구히 쌓이므로 장기적으로는 아카이빙 전략이 필요하나, 포트폴리오 규모/기간에서는 해당 없음

**How to apply (구현 시 주의)**: Prisma 미들웨어(`$use`)로 소프트 삭제 필터를 전역 적용하는 것을 검토할 것 — 매 서비스 메서드에서 수동으로 조건을 넣는 방식은 D2의 branchId 필터 누락과 동일한 실수 패턴을 반복할 위험이 있음.

## D10. 혼잡도: 체크인 기반 자동계산 + 수동 보정 하이브리드

> **2026-09-20 범위 조정**: 이 결정의 "자동 계산" 절반(QR 체크인·5분 크론)은 구현하지 않기로 했다 — 수동 보정만으로 RFP 요건이 충족되고(1-9문서 §9), 회원 앱·스케줄러가 없어서다. 아래 결정 내용은 향후 확장 방향으로 남겨둔다.

**결정**: IoT 센서/CCTV 기반 실측 대신 예약·QR체크인 데이터로 5분 주기 자동 계산하고, 관리자가 필요 시 수동으로 덮어쓸 수 있는 하이브리드 방식을 채택했다. ([1-9문서](../../1.spec/30_운영지원/1-9_혼잡도관리.md) §1, §4)

**쉽게 말하면**: 사람을 직접 세는 장비가 없으니, 회원들이 QR로 체크인/체크아웃한 기록을 세어서 지금 몇 명 있는지 자동으로 추정하고, 이상하면 관리자가 손으로 고칠 수 있게 했습니다.

**근거**: IoT 하드웨어는 개인 포트폴리오로 확보 불가능하다. 대신 이미 시스템에 존재하는 데이터(예약, 체크인)로 근사치를 계산하는 것은 실제 중소 피트니스 업계에서도 쓰이는 현실적 대안이라고 문서 스스로 밝히고 있다(1-9문서 §1).

**타당성**: 높음. "왜 이렇게 설계했는지"를 발표에서 논리적으로 방어할 수 있는 지점이라고 문서가 미리 언급한 것 자체가, 이 결정이 타협이 아니라 의도된 설계임을 보여준다. 5분 주기는 원본 요구사항의 "최대 30분 이내 반영"을 상회 달성하는 수치로, 목표 대비 충분한 여유를 뒀다.

**장점**
- 하드웨어 의존성 없이 소프트웨어만으로 실사용 가능한 근사치를 제공
- 자동/수동 값이 충돌할 때의 동작(수동 보정 후 다음 tick에 자동이 override)까지 명시해 "의도한 동작"과 "버그"를 구분해뒀음

**단점·리스크**
- 체크아웃을 깜빡하는 회원이 많으면(문서도 "실무에서 매우 흔함"이라 인정) 혼잡도가 실제보다 부풀어 보이는 근본적 한계가 있음 — 23:00 강제 마감 배치(1-9문서 §7)로 완화하지만 당일 중 누적 오차는 남음
- QR 체크인이라는 행동 자체를 회원이 안 하면(스캔을 안 하고 그냥 이용) 자동계산의 원천 데이터가 애초에 없음 — 관리자 대리 체크인(1-9문서 §4)으로 보완하지만 결국 사람이 챙겨야 하는 운영 부담으로 이전됨

## D11. 인사정보 변경 신청 1단계 승인 (다단계 결재 미구현)

**결정**: 원본 요구사항의 "권한/승인 시 수정 가능"을 다단계 결재라인 대신 "본인 신청 → 관리자 승인(1단계)" 구조로 단순화했다. ([1-3문서](../../1.spec/10_인사조직/1-3_인사정보관리.md) §1)

**쉽게 말하면**: 정보 변경은 "직원이 신청하면 지점 관리자가 한 번에 승인/거절"하는 단순한 결재로 처리하고, 여러 단계를 거치는 복잡한 결재라인은 만들지 않았습니다.

**근거**: 다단계 결재(기안→1차승인→2차승인→반영)는 결재선 설정, 위임, 반려 시 재상신 등 부가 상태 관리가 크게 늘어나는 영역이라 1인 개발 범위를 넘는다.

**타당성**: 높음, D1과 같은 계열의 스코프 조정. 다만 D2/D9와 달리 이건 "요구사항의 표면 형태를 그대로 축소"한 것이라, 원본 요구사항 문서에 다단계 결재가 명시적으로 요구되어 있었다면 심사에서 "왜 단순화했는가"를 설명할 준비가 필요하다(문서에 근거가 이미 적혀 있어 이 자체는 문제 없음).

**장점**
- `StaffProfileChangeRequest`가 필드 단위 diff(oldValue/newValue)로 저장되어, 승인자가 "무엇이 바뀌는지"를 명확히 확인 가능(1-3문서 §6) — 단순화된 구조 안에서도 감사 가능성은 챙김

**단점·리스크**
- 향후 결재선이 필요해지면 `StaffProfileChangeRequest`에 결재 단계 개념이 아예 없어 테이블 구조부터 다시 설계해야 함(현재 스키마는 확장을 고려한 설계가 아니라 단순 2단계 상태 머신)

## D12. STAFF Role 분리 (BRANCH_ADMIN과 구분)

**결정**: 커밋 `ec30b90`에서 Role enum에 `STAFF`를 추가해, 지점 소속 일반 직원(트레이너 등)이 관리 권한 없이 본인 근태/휴가/업무일지만 셀프서비스하도록 `BRANCH_ADMIN`과 분리했다. ([1-2문서](../../1.spec/10_인사조직/1-2_권한관리.md) §1, §7)

**쉽게 말하면**: "지점 직원"이라고 다 관리자 권한을 주면 안 되기 때문에, 트레이너 같은 일반 직원은 "내 근태만 관리할 수 있는" 별도의 낮은 직급(STAFF)으로 새로 만들어 분리했습니다.

**근거**: 애초 설계에서는 "직원"이 곧 `BRANCH_ADMIN` 권한을 갖는 것으로 오인될 여지가 있었다(seed.ts에서 트레이너 계정을 BRANCH_ADMIN으로 임시 처리했던 것이 이 커밋에서 STAFF로 정정된 이력이 이를 보여줌). 실제로는 "직원이라고 다 지점 관리자는 아니다"가 원칙이어야 한다.

**타당성**: 매우 높음 — 최소 권한 원칙(principle of least privilege)을 정확히 적용한 수정이다. 트레이너가 실수로든 악의적으로든 다른 직원 정보나 회원 관리 기능에 접근할 수 없어야 한다는 문제의식(1-2문서 §1)이 명확하고, 이를 놓쳤다면 보안 심사에서 바로 지적받았을 결함이다.

**장점**
- `staffId`까지 본인 값으로 강제(1-2문서 §7 인용 — "동료 직원의 근태를 열람하는 것도 차단")하는 세밀함까지 챙겨, Role 분리가 형식적이지 않고 실질적임
- STAFF가 게시판의 "교육자료" 카테고리는 조회할 수 있어야 한다는 것(1-5문서 §7)까지 함께 정리되어, 한 번의 Role 추가가 여러 문서에 걸쳐 일관되게 반영됨

**단점·리스크**
- 이 수정이 초기 설계가 아니라 나중에 발견되어 추가된 사례라는 점 자체가, "Role/권한 설계는 초기에 최대한 완결적으로 검토해야 한다"는 교훈으로 남을 만함 — 유사한 누락이 아직 남아있을 가능성을 배제할 수 없으므로, Phase 1 구현 착수 전 1-2문서의 권한 매트릭스를 재검토하는 것을 권장
- 관리 권한 없는 STAFF 계정도 로그인/토큰 발급 대상이라 Account 테이블 부하나 계정 관리 UI(계정 목록 등)에 STAFF까지 포함해서 설계해야 하는데, 1-2문서 §4 화면 목록에는 "계정 목록/발급"이 SUPER_ADMIN 전용으로만 있어 STAFF 계정을 누가/어떻게 발급하는지(추정: BRANCH_ADMIN이 /staff 등록 시 함께 생성) 명시가 약간 암묵적임

## D13. 모노레포 + 기술 스택 선택 (NestJS/Prisma/PostgreSQL/React+Vite/Expo)

**결정**: npm workspaces 기반 모노레포(`apps/*`, `packages/*`)로 admin-web/api/member-app/types를 한 저장소에서 관리하고, 백엔드는 NestJS+Prisma+PostgreSQL, 관리자 웹은 React+Vite, 회원 앱은 React Native(Expo)를 사용한다. (README, [1-1문서](../../1.spec/00_공통/1-1_공통설계서.md) §6)

**쉽게 말하면**: 관리자 웹, 회원 앱, 백엔드 서버, 공용 타입 정의를 각각 따로 관리하지 않고 한 저장소(모노레포) 안에 모아서, 서로 같은 타입을 공유하며 개발합니다.

**근거**: `packages/types`로 클라이언트-서버 간 DTO 타입을 공유하려면 모노레포가 사실상 필수 전제 조건이다(별도 리포로 쪼개면 타입 동기화를 위해 npm 패키지 배포/버전관리가 추가로 필요해짐). NestJS는 데코레이터 기반 구조(Guard/Interceptor)가 이 프로젝트의 RBAC·BranchScope 요구사항과 잘 맞고, Prisma는 스키마 우선 설계와 타입 안전 쿼리를 제공해 1인 개발의 생산성을 높인다.

**타당성**: 높음. 모든 선택이 서로 시너지를 내도록 구성되어 있다 — 모노레포(공유 타입) + NestJS(데코레이터 기반 인가) + Prisma(스키마=단일 진실 공급원)가 D1(RBAC), D2(branchId 격리)를 구현하는 데 필요한 인프라를 정확히 제공한다.

**장점**
- `packages/types`를 통해 프론트/백엔드 타입 불일치로 인한 런타임 버그를 컴파일 타임에 차단 가능
- Prisma의 마이그레이션 이력이 그 자체로 스키마 변경의 감사 기록이 됨(D7 같은 구조 변경의 근거 추적 가능)
- npm workspaces는 별도 도구(Nx, Turborepo 등) 없이 표준 npm만으로 충분히 굴러가, 1인 개발의 도구 학습 비용을 최소화

**단점·리스크**
- npm workspaces는 Nx/Turborepo 대비 빌드 캐싱·태스크 그래프 최적화가 없어, 프로젝트가 커지면 `npm run build` 등이 매번 전체를 다시 빌드함 — 다만 이 프로젝트 규모(앱 3개)에서는 아직 체감될 문제는 아님
- Expo(React Native)는 Phase 3부터 착수 예정이라 아직 실제 통합 검증이 안 된 상태 — `packages/types`가 Expo 환경에서도 문제없이 import되는지(메트로 번들러 호환성 등)는 Phase 3 착수 시점에 처음 확인하게 됨

## D14. 비기능요구사항(가용성/성능 수치)을 설계 원칙으로 대체

**결정**: 원본 요구사항의 "CPU 90% 이하", "메모리 85% 이하" 같은 인프라 실측 목표를 포트폴리오 규모에서는 의미가 없다고 보고, 페이지네이션/인덱싱/AuditLog/입력 검증 같은 설계 원칙으로 대체했다. ([1-1문서](../../1.spec/00_공통/1-1_공통설계서.md) §5)

**쉽게 말하면**: "서버가 초당 몇 명을 버텨야 한다" 같은 실측 수치 목표 대신, "목록을 나눠서 보여주기", "검색 속도를 높이는 색인 만들기", "누가 뭘 바꿨는지 기록 남기기"처럼 실제로 지킬 수 있고 확인 가능한 설계 원칙으로 목표를 바꿔치기했습니다.

**근거**: 실측 인프라 지표는 실제 트래픽과 모니터링 인프라(Prometheus/Grafana 등)가 있어야 의미를 갖는데, 로컬 Docker Compose 환경의 1인 개발 프로젝트에서 이런 수치를 재현하는 것 자체가 목적을 상실한 형식적 작업이 된다.

**타당성**: 높음. "원본 요구사항의 정신(안정적으로 동작하는 시스템을 설계할 줄 아는가)"을 "표면적 형태(수치 재현)"보다 우선시한 합리적 판단이며, 문서에 "발표에서는 확장을 고려한 설계로 어필"이라고 명시해 이 조정이 회피가 아니라 대체 전략임을 분명히 했다.

**장점**
- 페이지네이션 필수화, DB 인덱스 명시, AuditLog 등은 실제로 구현 가능하고 코드 리뷰에서 검증 가능한 항목들이라 "말로만 어필"이 아니라 "코드로 증명"할 수 있음

**단점·리스크**
- 이 대체표(1-1문서 §5)에 언급된 항목 중 일부(Redis 캐싱, 온라인 도움말 Toast/Modal 등)는 아직 각 기능 문서의 Phase 1/2 우선순위에 명시적으로 배치되지 않아, 실제 구현 단계에서 빠뜨리기 쉬움 — Phase별 체크리스트를 작성할 때 이 표의 항목들이 어느 Phase에 들어가는지 명시적으로 매핑해두는 것을 권장

## D15. admin-web 디자인 토큰화 (Rounded Rectangle 기준)

**결정**: 별도 UI 프레임워크(Tailwind, MUI 등) 도입 없이 순수 CSS 커스텀 프로퍼티(`--radius-sm/md/lg/xl/pill`, `--color-*`, `--shadow-*`)로 디자인 토큰을 정의하고, 대시보드를 포함한 admin-web 전체 도형(카드/버튼/입력/뱃지/사이드바/네비게이션)을 Rounded Rectangle 계열로 통일했다. 대시보드는 KPI 요약 스트립(SUPER_ADMIN이 2개 지점 이상을 볼 때만 노출) + 지점별 통계 카드(아이콘 칩) 구조로 재작성했다.

**쉽게 말하면**: 화면 곳곳에 흩어져 있던 "둥근 정도·색깔·그림자" 값을 한 군데(디자인 변수)에 모아두고, 모든 버튼과 카드가 그 값을 그대로 따라 쓰게 만들어서 마치 한 사람이 한 번에 그린 것처럼 통일된 느낌을 냈습니다.

**근거**: 사용자가 "모던하고 깔끔한 디자인, 도형은 Rounded Rectangle 기준"이라고 방향을 명시했다(2026-09-05). 이미 순수 CSS(`styles.css` 단일 파일) 구조로 시작된 작은 프로젝트에 Tailwind 같은 빌드 의존성을 새로 얹는 것은 이 시점 규모에 비해 과한 비용이고, CSS 변수만으로도 전역 일관성이라는 목표를 충분히 달성할 수 있다고 판단했다.

**타당성**: 높음. 기존 `.card`, `.card-grid`, `table`, `.badge` 등 클래스를 그대로 재사용하면서 토큰(값)만 바꿨기 때문에, 회원/직원/프로그램/게시판/시설 페이지는 코드 수정 없이 새 톤을 자동으로 물려받았다(브라우저로 각 페이지 확인 완료).

**장점**
- 새 디자인을 적용하기 위해 손댄 페이지는 대시보드뿐이지만, 변수를 참조하는 다른 모든 페이지가 함께 갱신됨(변경 지점 최소화)
- 라이브러리 학습·의존성 비용 없이 "일관된 디자인 시스템이 있다"는 인상을 심사에서 어필 가능

**단점·리스크**
- 정식 디자인 시스템(컴포넌트 라이브러리)이 아니라 CSS 클래스 집합이므로, 페이지 수가 크게 늘어나면 클래스명 중복·불일치가 생길 위험이 있음
- 다크 모드는 고려하지 않음(라이트 전용 토큰) — 이 프로젝트 스코프상 우선순위는 낮다고 판단

**대안 및 미채택 사유**: Tailwind CSS 도입도 검토했으나, 이미 순수 CSS로 시작된 작은 코드베이스에 새 빌드 파이프라인을 추가하는 비용이 이 시점의 이득(유틸리티 클래스 생산성)보다 크다고 보아 채택하지 않음.

## D16. 지점→직원→회원/프로그램 드릴다운 + `Member.assignedStaffId` 추가

**결정**: 대시보드 지점 카드 클릭 시 `/branches/:branchId` 상세 페이지로 이동해 "직원(펼치면 담당 회원) → 담당 직원 없음 회원 → 프로그램" 순서로 조회할 수 있게 만들고, 이를 위해 `Member`에 담당 직원(선택) 연결 필드 `assignedStaffId`를 신설했다. Prisma 스키마·mock 데이터·`/members` API 응답(`assignedStaffName` 조인)·admin-web 타입까지 전 계층에 반영했다(마이그레이션은 아직 미실행).

**쉽게 말하면**: 회사 조직도를 그리듯 "지점 → 그 지점 직원 → (있다면) 그 직원이 담당하는 회원"의 순서로 클릭해 들어갈 수 있게 만들고, 회원 목록에도 "이 회원은 어느 트레이너 담당인지, 아니면 그냥 회원권만 있는지"를 새로 표시했습니다.

**근거**: 사용자가 조직 구조를 "지점이 최상위 대분류, 그 아래 직원, 그 아래(선택) 회원, 프로그램은 지점별로 별도"라고 명시적으로 정의했다(2026-09-05). 기존 스키마(`Member.branchId`, `Staff.branchId`)는 지점 단위 소속은 이미 표현했지만, "회원이 특정 직원에게 배정되는가"라는 관계 자체가 없어서 이 정보 구조를 화면으로 표현할 방법이 없었다.

**타당성**: 높음 — 구현 방향(드릴다운을 상세 페이지 이동으로 할지 인라인으로 할지, `assignedStaffId` 필드를 실제로 추가할지)을 사용자에게 직접 확인받고 진행했다(두 질문 모두 "추천" 옵션 선택). 기존 아키텍처 원칙([D2](#d2-멀티테넌시를-branchid-컬럼-격리로-구현), [D3](#d3-account-단일-테이블--staffmember-11-프로필-분리))과 같은 계열로, mock 데이터 계층이 실제 Prisma 스키마 구조를 그대로 따르게 해(`mock-data.types.ts` 주석 원칙) 나중에 실 DB 연동 시 컨트롤러 코드를 거의 안 건드려도 되도록 만들었다.

**장점**
- 실제 DB 마이그레이션 전에 스키마 변경 지점을 미리 검증(`prisma validate` 통과)해 나중 마이그레이션 리스크를 줄임
- 회원 목록 페이지(`MembersPage`)에도 "담당 직원" 컬럼을 추가해, 이 계층 정보가 대시보드 밖에서도 일관되게 노출됨

**단점·리스크**
- `assignedStaffId`는 `branchId`([D2](#d2-멀티테넌시를-branchid-컬럼-격리로-구현))처럼 가드+서비스 이중 검증이 아직 없음 — "다른 지점 소속 staffId를 회원의 담당 직원으로 배정"하는 것을 막는 서버측 검증이 없고, 지금은 mock 데이터를 만들 때 수동으로 지점을 맞춰뒀을 뿐이다. 실제 회원 등록/수정 쓰기 API를 구현하는 단계에서 "assignedStaffId가 회원의 branchId와 같은 지점 소속 staff인지" 검증 로직을 반드시 추가해야 함
- (2026-09-06 해소) 1-6문서(회원관리)의 데이터 모델·화면 목록에 이 필드가 반영됨

**대안 및 미채택 사유**: Member-Staff를 다대다(N:M, 여러 트레이너가 한 회원을 공동 담당) 관계로 설계하는 방안도 있었으나, 사용자가 요구한 모델이 "직원별로 회원이 붙어있거나, 아니면 회원권만 끊고 담당이 없거나"라는 1인 담당 모델을 명확히 지목했으므로 1:N(`Staff.assignedMembers`) 관계로 충분하다고 보아 채택하지 않음.

## D17. 본사 전용 "권한 관리"(Role 전환) 기능 추가

**결정**: SUPER_ADMIN 전용 `/permissions` 화면과 `GET/PATCH /api/v1/permissions/staff` API를 신설해, 지점 직원의 `Account.role`을 `STAFF` ↔ `BRANCH_ADMIN`으로 전환할 수 있게 했다. Mock 데이터 계층에서는 in-memory `accounts` 배열의 객체 프로퍼티를 직접 mutate하는 방식으로 구현했다.

**쉽게 말하면**: 본사 관리자가 화면 하나에서 "이 지점 직원을 지점 관리자로 승진시킬지, 다시 일반 직원으로 되돌릴지"를 드롭다운으로 바로 바꿀 수 있게 만들었습니다.

**근거**: [1-2문서](../../1.spec/10_인사조직/1-2_권한관리.md) §4/§5의 원래 설계는 "계정 생성/비활성화"만 SUPER_ADMIN 화면·API로 명시했을 뿐, "이미 만들어진 직원 계정의 Role을 나중에 바꾸는" 기능은 없었다. 그런데 사용자가 "본사 직원들은 지점별 직원들의 권한 제어가 가능해야 한다"고 명시적으로 요구했고(2026-09-05), 이는 계정 자체의 CRUD가 아니라 이미 있는 계정의 role 필드만 바꾸는 더 좁고 구체적인 요구라 별도의 작은 엔드포인트로 최소 구현했다.

**타당성**: 높음. `RolesGuard`(`@Roles('SUPER_ADMIN')`)로 서버단 강제까지 확인했고, `STAFF`/`BRANCH_ADMIN` 두 값만 `@IsIn`으로 화이트리스트 검증해 `SUPER_ADMIN` 승격 같은 위험한 값 주입을 원천 차단했다. 다만 이 기능은 1-2문서에 아직 문서화되지 않은 "사실상의 스펙 확장"이라는 점은 명확히 인지해야 한다.

**장점**
- ~~JWT가 로그인 시점 role을 그대로 서명해 담는 기존 설계와 상호작용하는 지점을 놓치지 않고, "role 변경이 즉시 전역 반영되지 않고 재로그인이 필요하다"는 한계를 화면 문구로 명시해 사용자 혼란을 방지함~~ **정정(2026-09-18)**: 이 "한계"는 애초에 1-2문서 §6이 요구하지 않는, JWT 설계상의 실제 버그였다 — access token엔 이제 role을 담지 않고 `sub`(accountId)만 담아, 매 요청 최신 Account 조회 결과로 role/branchId를 새로 구성하도록 고쳤다. 그 결과 재로그인 없이 다음 요청부터 즉시 반영되며, admin-web 안내 문구도 함께 정정했다.
- BRANCH_ADMIN 계정으로 로그인하면 이 메뉴 자체가 사이드바에서 사라지는 것까지 브라우저로 검증함

**단점·리스크**
- (2026-09-06 해소) 1-2문서 §4(화면 목록)·§5(API 명세)·§7(권한 매트릭스)에 이 화면/API/권한행이 반영됨
- mock 데이터 mutate는 서버 프로세스 재시작 시 원상복구되는 휘발성 상태라, 실제 DB 연동 전까지는 "영구 변경"이 아님 — 데모 중 API 서버를 재기동하면 권한 변경 내역이 사라진다는 것을 시연자가 인지하고 있어야 함
- `AuditLog`([1-1문서](../../1.spec/00_공통/1-1_공통설계서.md) §5) 연동 없이 role을 바꿀 수 있어 "누가 언제 이 직원을 승진시켰는지" 추적이 안 됨 — [D9](#d9-소프트-삭제-원칙-전반)·[D12](#d12-staff-role-분리-branch_admin과-구분)에서 강조한 감사 가능성 원칙과 어긋나는 지점이라, 실제 쓰기 로직 단계에서 AuditLog 연동을 권장

**대안 및 미채택 사유**: Account 전체를 관리하는 범용 CRUD(`GET/POST/PATCH/DELETE /accounts`)를 먼저 구현하고 그 일부로 role 변경을 포함하는 방법도 있었으나, 사용자가 요청한 범위(권한 제어)만 최소로 구현하는 것이 현재 단계(Phase 1 스캐폴딩)에 맞다고 판단해 별도의 작은 엔드포인트로 분리했다.

## D18. 자체개발·데이터 주권 원칙 (SaaS 벤더 미사용)

**결정**: 회원관리·예약·결제 데이터를 외부 SaaS ERP 벤더(멤버십/피트니스 관리 서비스)에 위탁하지 않고, 스포이즘이 직접 소유·운영하는 시스템(자체 DB, 자체 인프라)으로 구축한다. 이는 D2(멀티테넌시를 branchId 컬럼으로 격리)와는 다른 층위의 결정이다 — D2는 "한 시스템 안에서 지점 간 데이터를 어떻게 나누는가"이고, D18은 "애초에 이 시스템을 왜 자체 개발하는가"다. ([1-1문서 §1-1](../../1.spec/00_공통/1-1_공통설계서.md#1-1-사업-맥락-원본-rfp-재해석))

**쉽게 말하면**: 매장 포스기를 다른 회사 것을 빌려 쓰면 그 회사가 우리 매출을 실시간으로 들여다볼 수 있는 것과 같습니다. 스포이즘은 그 포스기를 아예 자기 회사 걸로 직접 만들어서, 어떤 외부 회사도 우리 매출·회원 데이터를 볼 수 없게 만든 것입니다.

**근거**: 원본 RFP(Ⅳ.과업내용 1.과업 목적)가 명시한, 기존 관리시스템(erp) 사용 시 문제점 세 가지가 이 결정의 직접적 근거다 — ① 기존 ERP 회사의 시스템을 사용하면 매출 공개 및 영업 노하우 노출로 경쟁사가 출현할 수 있음, ② 기존 ERP 회사가 도산하면 그 피해가 스포이즘의 신뢰성 타격으로 이어짐, ③ 범용 시스템이라 "98개 업장을 보유한" 스포이즘의 규모·특수성에 맞는 차별화가 되지 않음. 이 세 가지는 전부 "기술적으로 더 나은 선택"이 아니라 **"사업적으로 반드시 자체 소유해야 하는 이유"**이므로, 이 프로젝트의 다른 어떤 기술 결정보다 우선하는 전제 조건으로 다룬다.

**타당성**: 높음 — RFP가 직접 명시한 사업 배경이므로 별도 검증이 필요 없는, 이 프로젝트 존재 자체의 이유다. 다만 포트폴리오 프로젝트 특성상 실제 인프라 운영(장애 대응, 백업, 도산 리스크 자체는 스포이즘에도 동일하게 있음)까지 이 결정이 해결해주지는 않는다는 점은 별개로 인지해야 한다.

**장점**
- 매출·회원 데이터가 스포이즘 소유 DB 밖으로 나가지 않는다는 것 자체가, 문서화된 설계 원칙으로 존재한다는 것이 심사·영업 발표(2-4문서 참고) 모두에서 설득력 있는 근거가 됨
- D2(branchId 격리)·D9(소프트 삭제) 같은 이미 있는 결정들이 "왜 이렇게까지 안전장치를 겹겹이 뒀는가"에 대한 상위 맥락을 제공 — 개별 기술 선택이 아니라 하나의 일관된 사업 원칙에서 파생된 것임을 보여줌

**단점·리스크**
- 자체 개발·운영의 대가로 SaaS 벤더가 제공했을 법한 것(가용성 SLA, 보안 인증, 장애 대응 인력)을 스포이즘이 직접 감당해야 함 — 1인 개발 포트폴리오 규모에서는 이 트레이드오프를 "설계는 인지하고 있으나 실제 운영 역량은 범위 밖"으로 명시하는 것이 정직함(1-1문서 §5의 비기능요구사항 대체 원칙과 동일한 태도)
- "데이터가 안 샌다"는 주장은 접근 통제(1-2문서)·감사로그(AuditLog, 아직 미연동 — 2-3문서 §2-3)가 실제로 갖춰져야 완성되는데, 지금은 원칙 선언 단계이지 기술적으로 증명된 상태는 아님

**대안 및 미채택 사유**: 검토 대상이 아니었다 — RFP 자체가 "자체 개발"을 과업으로 발주했으므로, "SaaS 벤더 사용"은 애초에 이 프로젝트의 선택지에 없었다. 다만 이 문서가 다른 D-항목처럼 "왜 이 선택을 했는가"를 명시적으로 남기는 것은, 나중에 이 프로젝트를 심사·발표할 때 "왜 자체 개발 ERP인가"라는 가장 근본적인 질문에 답할 근거가 되기 때문에 별도 항목으로 정리했다.

## D19. 디자인 방향 전환 — SaaS 스타터 톤에서 고밀도 엔터프라이즈 라이트로

**결정**: D15에서 확정했던 admin-web 디자인 방향(인디고 포인트컬러 `#4f46e5`, 큰 라운드 `radius-lg/xl`, 소프트 섀도우, 파스텔 4색 아이콘 칩)을 폐기하고, **무채색(슬레이트) 기반 + 포인트 컬러 1개(`#0f766e` 티얼)만 기능적으로 사용하는 고밀도 엔터프라이즈 라이트** 방향으로 전환한다. 상세 토큰·레이아웃 원칙은 [디자인시스템 문서](../../3.design/3-1_디자인시스템.md)에 정의했다.

**쉽게 말하면**: 지금까지의 화면은 스타트업 서비스 소개 페이지처럼 둥글둥글하고 알록달록했는데, 이걸 "본사 직원이 매일 켜놓고 수십 개 매장을 관리하는 업무용 콘솔"답게 각지고 절제된 느낌으로 바꾸기로 했습니다. 카드에 큰 숫자만 띄우던 것도, 추세를 보여주는 작은 그래프가 들어간 패널로 바꿉니다.

**근거**: 사용자가 현재 구현을 "토이 프로젝트처럼 보인다"고 명시적으로 평가하고 "실제 프랜차이즈급 디자인의 대시보드"를 요구했다(2026-09-08). D15는 "모던하고 깔끔한" 방향으로 만들어졌지만, 그 결과물이 실제로는 SaaS 마케팅 페이지·스타터 템플릿에서 흔히 보이는 미학(장식적 파스텔 아이콘 칩, 과도한 라운드, 뜬 카드)에 가까웠고, 이는 "다지점을 실제로 운영하는 도구"라는 이 프로젝트의 정체성과 어긋난다는 데 사용자와 합의했다. 참고 삼은 것은 Mindbody·Zenoti·ServiceTitan 같은 실제 다지점 서비스업 운영관리 소프트웨어의 톤이다.

**타당성**: 높음 — 방향 자체는 사용자가 여러 옵션(고밀도 엔터프라이즈 라이트 / 다크 콘솔형 / 클래식 엔터프라이즈) 중 직접 선택한 것이라 주관적 판단이 아니라 명시적 요구사항이다. 다만 "프랜차이즈급으로 보이는가"는 실제 화면을 다시 만들어봐야 검증되는 것이라, 지금 단계는 방향 확정이지 완성이 아니다.

**장점**
- D15 대비 컴포넌트 수정 범위가 작다 — 클래스 구조(`.card`, `.kpi-card`, `table`, `.badge`)는 그대로 두고 토큰 값과 일부 컴포넌트 패턴(KPI 카드 → 스파크라인 패널)만 바뀌므로, D15의 "토큰화" 투자 자체는 유효하다
- 상태색(성공/경고/위험) 뱃지는 원래도 의미 전달용이었어서 그대로 유지 가능 — 바뀌는 건 "의미 없는 장식색"(아이콘 칩 4색)뿐

**단점·리스크**
- 방향 확정과 실제 구현 사이에 간극이 있다 — `apps/admin-web/src/styles.css`는 아직 D15 상태 그대로이고, 이번 결정은 문서화만 완료된 상태(§9-4에 "새 화면부터 순차 적용" 전략을 명시해둠)
- 디자인 방향이 또 바뀌면(D15→D19처럼) 그때마다 이미 만든 화면을 다시 손봐야 하는 비용이 있음 — 1인 개발에서는 이 시행착오 자체가 "일찍 사용자 피드백을 받는 게 낫다"는 근거로 보는 게 맞음(늦게 바꿀수록 더 비쌈)

**대안 및 미채택 사유**: 다크 콘솔형(Vercel/Datadog 스타일)과 클래식 엔터프라이즈(Salesforce 스타일)도 후보였다. 다크 콘솔형은 비개발자 대상 관리자 화면(회원관리 ERP 도메인)엔 과하게 "기술 인프라 대시보드"처럼 보일 우려로, 클래식 엔터프라이즈는 안정감은 최고지만 세련됨이 상대적으로 낮다는 점에서 밀렸다 — 최종적으로 사용자가 고밀도 엔터프라이즈 라이트를 선택했다.

## D20. 대시보드 우선순위 재편 + 위탁계약 필드 도입 + 지점 기준 정보구조(IA)

**결정**: 세 가지를 한 번에 바꿨다. ① 대시보드 최상단 KPI를 "전체 회원/전체 직원/진행중 프로그램"에서 "전체 지점 수/전체 직원 수/계약 갱신 임박 지점"으로 교체하고, ② 1-1문서 §2-1에 스펙으로만 있던 `Branch` 위탁계약 필드(`contractPartner`, `contractStartAt`, `contractEndAt`, `contractStatus`)를 mock 데이터로 처음 구현해 지점 카드에 계약 상태 뱃지로 노출했다. ③ `BranchDetailPage`의 드릴다운에 혼잡도 섹션을 추가해 "지점 → 직원/회원/프로그램/혼잡도" 4단 구조를 완성하고, 회원/직원/프로그램/시설·혼잡도 최상위 메뉴는 flat 목록 대신 지점별 섹션으로 묶어서 보여주도록 바꿨다(`groupByBranch` 헬퍼, `apps/admin-web/src/lib/group-by-branch.ts`).

**쉽게 말하면**: 지금까지 대시보드 맨 위에는 "회원 몇 명, 직원 몇 명, 프로그램 몇 개"가 떠 있었는데, 이걸 본사가 실제로 매일 신경 써야 할 숫자인 "몇 개 지점과 계약 중인지, 계약이 곧 끝나가는 지점이 있는지"로 바꿨습니다. 회원/프로그램 개수는 없앤 게 아니라 지점 카드 안으로 내려갔습니다. 그리고 회원/직원/프로그램/시설 메뉴를 눌렀을 때 모든 지점이 뒤섞인 표 하나가 아니라, "서초점" "강남점"처럼 지점별로 나뉜 섹션으로 보이게 만들었습니다.

**근거**: CLAUDE.md/1-1문서가 이미 규정한 사업 구조 — `Branch`는 매장이 아니라 위탁운영 계약 현장이고, "시스템 불안정 → 민원 → 계약 해지"가 이 프로젝트의 핵심 리스크 — 를 사용자가 다시 직접 짚으며 "대시보드 메인 카드는 전체 지점 수·전체 직원 수 두 개, 계약 만료 임박한 지점도 따로 띄워야 한다"고 요구했다(2026-09-08~09). 본사 관심사는 회원·프로그램 개수가 아니라 "몇 개 계약을 유지 중이고 어느 계약이 위험한가"라는 것이 이 요구의 실질적 의도다. 동시에 "회원/직원/프로그램은 다 지점보다 하위 단계"라는 정보 구조 원칙과 "최상위 메뉴로 봐도 지점별로 구분돼야 한다"는 요구가 함께 나와, KPI 재편과 IA 재구성을 한 세트로 처리했다.

**타당성**: 높음 — 코드를 짜기 전에 Plan 모드로 범위(계약 필드 4계층 반영 방식, `renewalNoticeAt`/`cancellationPolicy` 등 근태·예약 도메인 필드는 이번 범위 밖으로 명시적으로 제외)를 먼저 정리해 사용자 승인을 받고 진행했다. `contractStatus`는 스펙상 크론으로 전이되는 필드지만 크론이 없는 현재는 mock 시드에 지점별로 직접 값을 넣어(서초점 `ACTIVE`, 강남점 `RENEWAL_DUE`) 대시보드 경고 카드가 실제로 동작하는 것까지 브라우저로 확인했다.

**장점**
- `assignedStaffName`([D16](#d16-지점직원회원프로그램-드릴다운--memberassignedstaffid-추가))과 동일한 "컨트롤러에서 인라인 조인" 패턴을 그대로 재사용해 `branchName`을 4개 컨트롤러(members/staff/programs/facilities)에 일관되게 추가했다 — 새 패턴을 만들지 않고 기존 관례를 확장만 함
- `groupByBranch` 제네릭 헬퍼 하나로 4개 페이지의 그룹핑 로직을 공유해, BRANCH_ADMIN/STAFF처럼 API가 이미 한 지점으로 필터링된 경우 섹션이 자연히 1개로 축소되는 것까지 별도 분기 없이 처리됨
- Prisma 스키마도 mock 데이터와 함께 갱신해([D16](#d16-지점직원회원프로그램-드릴다운--memberassignedstaffid-추가)와 같은 관례) 1-1문서·스키마·mock·admin-web 타입이 어긋나지 않게 유지함

**단점·리스크**
- `contractStatus` 전이를 담당할 배치(크론)가 없으므로, 지금 뜨는 "계약 갱신 임박" 숫자는 실제 날짜 계산이 아니라 시드에 박아둔 값이다 — 실 데이터가 들어가는 시점에 크론 또는 API 계층에서 `contractEndAt` 기준 자동 계산 로직이 반드시 필요함
- `renewalNoticeAt`(갱신 알림 발송 기준일)은 스펙에 있지만 이번 구현에서 의도적으로 뺐다 — 지금 화면에 소비하는 곳이 없어 미사용 필드를 미리 만들지 않기 위함이지만, 나중에 알림 기능을 붙일 때 이 결정을 다시 열어봐야 함
- `groupByBranch`는 클라이언트에서 지점별로 묶을 뿐, 서버 API 자체는 여전히 flat 배열을 내려준다 — 지점 수·행 수가 커지면(포트폴리오 규모에서는 무관하지만) 페이지네이션이 지점 경계와 맞물리는 문제를 나중에 고려해야 함

**대안 및 미채택 사유**: "계약 만료 임박" 카드를 배치(크론) 없이 만들려면 `renewalNoticeAt`을 아예 안 만들고 `contractEndAt`에서 매번 60일 임박 여부를 실시간 계산하는 방법도 있었으나, 스펙(1-1문서 §2-1)이 `contractStatus`를 "배치로 전이되는 별도 저장 필드"로 명시하고 있어 실제 운영 시나리오(계약 담당자가 수동으로 갱신 처리 완료 표시를 하는 경우 등)와 더 맞는 저장 필드 모델을 그대로 따랐다. 최상위 메뉴 자체를 없애고 지점 드릴다운으로만 접근하게 하는 방안도 검토했지만, 사용자가 "회원/프로그램/시설혼잡도만 따로 봐도"라고 명시해 최상위 메뉴 유지를 전제로 요구했으므로 채택하지 않았다.

## D21. 98개 지점 규모 mock 데이터 + 대시보드 테이블화·검색/필터·접이식 그룹핑

**결정**: 1-1문서 §1-1이 인용하는 원본 RFP 수치("전국 98개 업장")를 실제로 mock 데이터에 반영했다 — 서초점·강남점(히어로 지점, 데모 로그인 계정이 물려 있음) 외에 96개 지점을 `apps/api/src/mock-data/branch-generator.ts`가 인덱스 기반으로 결정적으로 생성한다(계약상태 분포는 ACTIVE 81/RENEWAL_DUE 10/EXPIRED 4/TERMINATED 3, 합계 98). 이 규모에서 실제로 스캔 가능한지 검증하기 위해 화면 3곳을 같이 바꿨다: ① 대시보드의 지점 카드 그리드 → 검색·상태필터·위험도 우선 정렬이 있는 테이블(SUPER_ADMIN만, BRANCH_ADMIN 단일 지점 뷰는 기존 카드 유지), ② 회원/직원/프로그램/시설·혼잡도 4개 지점 횡단 페이지 → 지점명 검색 + 기본 접힘 아코디언(`CollapsibleBranchSection`, 검색 결과 3개 이하면 자동 펼침), ③ 권한 관리 → 아코디언 대신 통합검색만 추가(이 화면은 "지점별로 훑어보기"가 아니라 "직원 한 명을 찾아 권한을 바꾸는" 단발 작업이라 목적이 다름).

**쉽게 말하면**: 지금까지는 지점이 2개뿐이라 카드 나열이나 표를 쭉 펼쳐두는 방식이 자연스러웠는데, 실제 스포이즘 규모(98개 업장)로 채워보니 그 방식이 그대로는 무너집니다. 그래서 대시보드는 카드 대신 검색·필터·정렬되는 표로, 나머지 목록 화면들은 지점명을 검색해야 펼쳐지는 접이식 목록으로 바꿨습니다 — "조치가 필요한 지점"(계약 만료·갱신임박)이 항상 표 맨 위에 뜨는 것도 이번에 추가됐습니다.

**근거**: 밀도 레퍼런스(Mindbody Business 등)를 확정한 직후, 사용자가 "원본 RFP 98개 지점 규모를 고려해서 많은 양의 데이터를 접근하기 쉽게 정리해달라"고 명시적으로 요구했다(2026-09-09). 지점이 2개일 때 통했던 카드 그리드·flat 아코디언 나열은 98개에서는 "카드 98장 무한 스크롤"·"펼쳐진 표 98개가 한 페이지에 쌓임"이 되어 오히려 밀도/스캔성 요구와 정반대 결과를 낳는다 — 즉 이번 결정은 D19(밀도)·D20(IA)의 연장선에서, "실제 데이터 규모"라는 세 번째 축을 반영한 것이다.

**타당성**: 높음 — mock 데이터를 `Math.random` 없이 인덱스 기반으로 결정적 생성해 서버를 재기동해도 계약상태 분포·지점 수가 항상 동일하게 재현되는 것을 API 응답(`curl`)과 브라우저 양쪽에서 확인했다. 대시보드 위험도 우선 정렬(만료→갱신임박→정상→종료), 상태필터 4종, "계약 갱신 임박" KPI 클릭 시 필터 자동 적용, 지점 검색 3개 이하 자동 펼침까지 Claude-in-Chrome으로 실제 클릭해 동작을 검증했다.

**장점**
- `groupByBranch`([D20](#d20-대시보드-우선순위-재편--위탁계약-필드-도입--지점-기준-정보구조ia))와 `BranchDetailPage`의 기존 아코디언 패턴(`staff-row`/`chevron`)을 그대로 재사용해(`CollapsibleBranchSection`) 새 CSS·새 상호작용 패턴을 거의 안 만듦
- 서버 페이지네이션 없이도(범위 결정 — 아래 참고) 98개 지점·수백 건 규모에서 체감 지연 없이 동작함을 확인해, 이 규모에서는 클라이언트 필터링만으로 충분하다는 판단이 실증됨

**단점·리스크**
- 서버 사이드 페이지네이션/가상화는 의도적으로 안 함 — 지점 수가 한 자릿수 더 늘면(수백~수천) `/members`·`/staff`·`/programs`처럼 branchId 없이 전체를 내려주는 API가 먼저 병목이 될 것. 그 시점에 재검토 대상으로 남겨둠
- 생성된 96개 지점의 `MockStaff.accountId`는 `accounts` 배열에 대응 로그인 계정이 없다 — 권한관리에서 그 직원의 역할을 바꾸려 하면 404(`ACCOUNT_NOT_FOUND`)가 난다. 데모 시연 동선(히어로 계정 5개)에는 안 걸리지만, 실제 DB 전환 시 모든 Staff가 Account를 갖는다는 전제(§3.1)와의 차이를 인지하고 있어야 함

**대안 및 미채택 사유**: `contractStatus`를 배치(크론)로 매일 재계산하는 방식도 검토했으나, 아직 크론 자체가 없는 단계라 mock 시드에 인덱스 기준으로 직접 배정하는 쪽이 훨씬 단순하면서도 화면 검증 목적(분포가 실제로 보이는가)은 동일하게 달성한다고 판단했다. 지점 횡단 4개 페이지도 대시보드처럼 전부 테이블+필터로 바꾸는 방안이 있었으나, "지점별 구성을 훑어본다"는 그 페이지들의 원래 목적(D20)에는 접이식 그룹핑이 더 맞다고 보아 대시보드만 테이블화했다.

## D22. `Branch.region` 필드 도입(대시보드 지역별 그룹핑) + 지점 상세 "계약 정보" 섹션(OCR 전제 명시)

**결정**: 두 가지를 이어서 추가했다. ① `Branch`에 `region`(광역 단위, 예: "서울"·"경기") 필드를 신설해 대시보드 지점 테이블을 지역별 접이식 섹션(서울/경기/부산/대구/인천/광주/대전/울산)으로 다시 묶었다 — `address`(상세 주소, 자유 텍스트)와 별개로 그룹핑 전용 정규화 필드다. ② `BranchDetailPage`에 그동안 비어 있던 "계약 정보" 섹션(계약 상대방·계약 기간·계약 상태·잔여일수)을 추가하고, 이 필드들이 궁극적으로는 계약서 스캔본 OCR·AI 자동 추출([2-4문서 §1-1](../60_분석및제안/2-4_차별화전략.md#1-1-계약서-ocrai-분석-2026-09-08-추가-스코프를-계약서-1종으로-한정))로 채워질 것을 전제로 설계됐다는 캡션을 명시적으로 붙였다(실제 OCR 기능 자체는 이번에 구현하지 않음 — 그 문서가 이미 Phase 2~3 스트레치로 분류해둔 범위 그대로).

**쉽게 말하면**: 대시보드에서 98개 지점을 볼 때 "서울/경기/부산..."처럼 지역으로 한 번 더 접어서 보여주고, 지점 상세 페이지에는 그동안 안 보이던 계약 정보(누구랑, 언제부터 언제까지, 며칠 남았는지)를 카드로 추가했습니다. 이 계약 정보는 나중에 계약서를 스캔해서 자동으로 채워 넣는 기능(OCR)을 이미 설계해둔 것을 전제로 만든 것이라, 그 사실을 화면에 짧은 문구로 남겨서 나중에 실제 OCR 기능을 붙일 때 "이 화면은 수기 입력용이 아니라 OCR 결과를 보여주는 화면"이라는 걸 잊지 않게 했습니다.

**근거**: 사용자가 지역별 그룹핑을 직접 요구했고(2026-09-09), 동시에 "계약 관련 내용은 계약서 OCR로 긁어온다는 걸 잊지 말라"고 명시적으로 짚었다. 2-4문서 §1-1은 이미 이 기능을 "위탁계약 필드는 지금 설계상 관리자가 수기로 입력하는 것을 전제로 한다"는 갭을 인지하고 그 보완책으로 설계돼 있었는데, 정작 그 전제가 되는 "지점 상세 화면에 계약 정보 탭"(§1 본문)이 아직 구현 안 된 상태였다 — 이번 기회에 그 선행 조건을 채워 넣으면서, 화면 자체가 "OCR로 채워질 데이터를 보여주는 화면"이라는 맥락을 잃지 않도록 캡션을 남겼다.

**타당성**: 높음 — `region`은 D16·D20·D21과 같은 관례(Prisma 스키마 + mock 타입/서비스 + admin-web 타입 4계층 동시 갱신, 1-1문서 §2-1 표에도 반영)를 그대로 따랐다. 지역 그룹핑은 대시보드에서 실제로 서울(71개)·경기(9개)·나머지 6개 광역시(각 3개)로 정확히 나뉘어 접히고, 검색·상태필터가 걸리면 해당 지역이 자동으로 펼쳐지는 것까지 브라우저로 확인했다. 계약 정보 섹션도 RENEWAL_DUE 지점에서 "17일 남음"처럼 잔여일수가 정확히 계산되는 것을 확인했다.

**장점**
- `CollapsibleBranchSection`(D21)을 그대로 재사용해 지역 그룹핑에도 새 컴포넌트를 안 만듦 — "지점명" 대신 "지역명"을 넘기는 것만으로 동작함
- `CONTRACT_STATUS_LABEL`/`CONTRACT_STATUS_RANK`를 `DashboardPage.tsx`에서 `apps/admin-web/src/lib/contract-status.ts`로 뽑아 `BranchDetailPage.tsx`와 공유하게 됨 — D20에서 대시보드에만 있던 로직이 두 화면에서 쓰이게 되며 자연스럽게 중복을 없앰

**단점·리스크**
- `region`을 96개 생성 지점의 `area`(구/시) 단위 배열에서 정적으로 매핑했다 — 서울이 21/30 지역을 차지해 지역별 분포가 고르지 않다(서울 71 vs 나머지 각 3~9). 실제 스포이즘 지점 분포와는 무관한 mock 편향이라, 나중에 실 데이터로 바뀌면 이 쏠림은 사라짐
- "계약 정보" 캡션은 OCR 기능이 실제로 없다는 것을 문구로만 알릴 뿐, 업로드 버튼 등 시각적 placeholder는 의도적으로 안 넣었다(동작 안 하는 버튼이 "고장난 UI"처럼 보이는 것을 피하기 위해) — Phase 2~3에서 실제 업로드 기능을 붙일 때 이 섹션을 다시 손봐야 함

**대안 및 미채택 사유**: 지역 코드를 시/도 표준 코드(예: 통계청 행정구역코드)로 정규화하는 방안도 있었으나, mock 데이터 단계에서는 과한 정확도라 사람이 읽는 한글 지역명 문자열로 충분하다고 판단했다. 계약 정보 섹션에 "계약서 업로드" 버튼을 비활성 상태로라도 넣는 안도 검토했으나, 클릭해도 아무 일도 안 일어나는 버튼은 오히려 완성도가 낮아 보인다고 판단해 텍스트 캡션으로만 의도를 남겼다.

## D23. 배포 인프라 — Cloudflare Pages(admin-web) + Render(api) + Supabase(향후 실 DB)

**결정**: 세 서비스를 GitHub 연동(push 시 자동배포)으로 조합한다. ① `admin-web`(정적 SPA 빌드 결과물)은 **Cloudflare Pages**, ② `api`(NestJS 서버 프로세스)는 **Render** 무료 웹 서비스, ③ 아직 미착수인 실 DB 전환 시점의 PostgreSQL은 **Supabase** 무료 프로젝트를 쓰기로 한다. 세 서비스 모두 신용카드 없이 무료 티어로 시작 가능하고, GitHub push 한 번으로 재배포되는 것을 최우선 기준으로 골랐다.

**쉽게 말하면**: 화면(admin-web)은 Cloudflare에, 서버(api)는 Render에 올리고, 나중에 mock 데이터를 진짜 DB로 바꿀 때 그 DB는 Supabase에 둡니다. 셋 다 GitHub 저장소만 연결해두면 `git push` 할 때마다 알아서 다시 배포되고, 지금은 아무것도 결제하지 않아도 됩니다.

**근거**: 현재 `apps/api`는 [app.module.ts](../../../apps/api/src/app.module.ts) 주석대로 `PrismaModule` 대신 `MockDataModule`로 동작 중이라 부팅에 실제 DB 연결이 필요 없다 — 그래서 지금은 Render에 `DATABASE_URL` 없이도 그대로 띄울 수 있고, Supabase는 "나중에 실 DB로 이전"할 때를 위해 미리 정해만 두는 것이다. `main.ts`가 이미 `enableCors({ credentials: true })`로 열려 있고 인증은 쿠키가 아니라 `Authorization` 헤더 기반(`apps/admin-web/src/lib/api.ts`에 `withCredentials` 없음)이라, 웹(Cloudflare Pages 도메인)과 API(Render 도메인)가 서로 다른 도메인이어도 추가 설정 없이 붙는다. GitHub Actions 워크플로를 직접 작성해야 하는 GitHub Pages보다 Cloudflare Pages/Render의 자체 Git 연동이 손이 덜 간다.

**타당성**: 중간 — 무료 티어 특유의 제약을 감수하는 선택이다. Render 무료 웹 서비스는 15분 미사용 시 슬립되고 재요청 시 약 1분 콜드스타트가 발생하며 월 750시간 한도가 있다([Render 문서](https://render.com/docs/free)). Supabase 무료 프로젝트는 7일간 활동이 없으면 자동 일시정지되어 수동으로 재개해야 한다. 포트폴리오 시연처럼 트래픽이 간헐적인 용도에는 이 제약이 큰 문제가 아니지만, 시연 직전에는 미리 한 번 요청을 보내 슬립/일시정지를 깨워두는 절차가 필요하다.

**장점**
- 세 서비스 모두 카드 등록 없이 무료로 시작 가능해 "유지비용 없음" 조건을 만족한다
- 셋 다 GitHub 저장소 연결만으로 push 시 자동 재배포되고, Cloudflare Pages는 PR마다 프리뷰 URL까지 자동 생성해준다
- `apps/api`가 지금 DB 없이 동작하므로 Render 배포에 DB 프로비저닝이라는 선행 작업이 없다 — Cloudflare Pages + Render만으로 오늘 바로 배포 가능하고, Supabase는 실 DB 전환 시점에 붙이면 된다
- npm workspaces 구조를 그대로 활용해 두 서비스 모두 리포 루트에서 `npm install && npm run build --workspace=apps/<앱>` 패턴으로 빌드하므로 워크스페이스 호이스팅 문제 없이 별도 빌드 스크립트가 필요 없다

**단점·리스크**
- Render 무료 웹 서비스의 슬립/콜드스타트와 Supabase 무료 프로젝트의 7일 일시정지는 "상시 대기" 서비스가 아니라는 뜻이다 — 실제 스포이즘 운영이라면 D18(자체 인프라 운영)이 전제하는 안정성 요구를 만족 못 한다는 점을 인지해야 한다(포트폴리오 시연용으로만 타당)
- `apps/admin-web`이 `BrowserRouter`(히스토리 모드)를 쓰므로 Cloudflare Pages에 `apps/admin-web/public/_redirects`(`/* /index.html 200`)가 없으면 새로고침 시 404가 난다 — 이 프로젝트에서는 이번에 함께 추가했다
- Render/Cloudflare Pages 대시보드에서의 빌드 커맨드·환경변수 설정은 리포 안의 파일([render.yaml](../../../render.yaml))만으로 전부 재현되지 않는다(Cloudflare Pages는 Blueprint 파일이 아니라 대시보드 설정이 단일 진실 공급원) — 계정 접근 권한이 있는 사람만 재현/변경 가능하다는 한계가 있다

**대안 및 미채택 사유**: API를 Vercel/Cloudflare Workers 같은 서버리스 플랫폼에 올리는 안도 검토했으나, NestJS는 데코레이터·`reflect-metadata` 기반의 상시 구동 서버 모델이라 서버리스 어댑터(`serverless-http` 등)를 추가로 감싸야 해서 "가장 가볍게"라는 기준에 안 맞았다. Railway는 이전엔 무료였지만 지금은 가입 시 1회성 크레딧만 주고 이후 과금되어 "유지비용 없음" 조건에서 탈락시켰다. Fly.io는 Dockerfile과 `fly.toml`/flyctl CLI를 직접 다뤄야 해서 Render 대비 설정 부담이 컸다. DB는 Neon도 후보였으나 사용자가 Supabase를 지정해 그대로 따랐다.

## 종합 평가

지금까지의 결정들은 하나의 일관된 원칙을 따른다: **"원본 요구사항의 표면적 형태가 아니라 실질적 의도를 파악해, 1인 개발이 가능한 범위 안에서 그 의도를 가장 잘 구현하는 방식을 선택한다."** RBAC 단순화(D1), 결재 단계 축소(D11), Mock Payment(D5), 혼잡도 하이브리드 계산(D10)이 모두 이 원칙의 적용 사례다.

동시에 이 프로젝트는 스코프를 줄인 영역에서도 **핵심 안전장치는 타협하지 않았다** — 지점 격리(D2)를 가드+서비스 이중 적용으로 강제하고, 예약 동시성(D6)을 트랜잭션 락으로 정합성 보장하며, STAFF Role 분리(D12)로 최소 권한 원칙을 뒤늦게라도 바로잡은 것이 그 증거다.

가장 반복적으로 나타나는 리스크 패턴은 **"애플리케이션 레벨의 수동 필터에 의존하는 안전장치"**다 — branchId 필터(D2), 소프트 삭제 필터(D9)가 대표적이며, 둘 다 "새 쿼리를 짤 때마다 사람이 기억해서 조건을 넣어야 한다"는 공통 약점을 가진다. Phase 1 구현을 시작할 때 Prisma 미들웨어로 이 두 필터를 전역화하는 것을 최우선으로 검토할 가치가 있다.
