# 12. 원본 요구사항 추적표 및 구현 현황 차이 분석

> 이 문서는 두 가지를 다룹니다.
> 1. **요구사항 추적(Traceability)**: `reference/제안요청서 원본.pdf`(㈜유니비즈컨설팅, 2022.06)에 적힌 원문 요구사항 항목을 하나씩, 이 프로젝트의 어느 설계 문서(1-1~1-9)가 어떻게 받아서 어떤 조정을 거쳤는지 표로 연결합니다. 각 조정의 상세 근거는 이미 [decisions/](../decisions/README.md)에 ADR 형식으로 정리되어 있으므로, 이 문서는 "원본 → 설계 문서 → 결정 근거"를 잇는 인덱스 역할을 합니다.
> 2. **설계 대비 실제 구현 상태**: 도메인별로 API·관리자 웹 화면·자동 테스트가 어디까지 있는지, 그리고 **RFP가 요구하는데 아직 구현하지 않은 것**을 코드에서 실측한 결과입니다(§2, 2026-10-05 재실측 — 전 도메인이 실DB(Prisma·Supabase)로 옮겨진 뒤의 기준).
>
> 원본 PDF는 한글 텍스트에 ToUnicode 매핑이 없는 폰트로 저장되어 있어 `pdftotext`(poppler)로는 추출이 안 되고, PyMuPDF로 재추출했습니다(추출 스크립트 결과는 이 세션 스크래치패드에만 존재, 저장소에는 포함하지 않음).

## 2. 설계 대비 실제 구현 — 2026-10-05 재실측

> 기준 커밋 `49a662a`. 9월에 쓴 이전 판(mock 시절 실측, 인증 모듈 이원화 경위)은 git 이력과 [log/](../log/README.md)에 있다.
> 실측 방법: 컨트롤러의 라우트 데코레이터, 관리자 웹이 실제로 부르는 API 경로, `apps/api/test/*.spec.ts`를 grep으로 대조했다. 자동 테스트 실행 결과가 아니라 **존재 여부**만 본 것이다.

### 2-1. 전제 — 지금 시스템

- **데이터**: 전 도메인이 Prisma + Supabase Postgres(서울)다. 인메모리 `MockDataService`는 삭제됐다(D26~D36). DB 제약 CHECK 18개·지점 일치 트리거 7개·부분 unique가 앱 검증과 함께 규칙을 강제한다(D27·D28).
- **호스팅**: API는 AWS Lambda(서울), 관리자 웹과 `/api` 진입은 Cloudflare Worker다(D25·D37). Worker 경유 로그인·데이터 조회까지 확인했고, k6 실측도 했다(log/056).
- **규모(2026-10-05 기준 기록, 이후 갱신하지 않음)**: Prisma 모델 31개, enum 24개, API 라우트 78개, 관리자 웹 화면 16개, API 테스트 파일 28개(통합 27 + 단위 1).
- **대상 지점·회원 기능**: 대상은 수도권 83곳이다(§2-4, D40). 회원 기능은 회원 모바일 웹(`apps/member-web`, 같은 Worker의 `/m/`, D41)으로 만들었다(2026-10-08, log/083~085) — 로그인·세션 유지, 프로그램·회차 조회, 예약·모의 결제·취소, 공지, 혼잡도, 내 정보 조회·수정. 자동 테스트는 없고(lint·빌드·360px 수동 확인), Worker 배포는 수동이다.

### 2-3. RFP가 요구하는데 아직 구현하지 않은 것 (2026-10-05 확인, 2026-10-11 원본 재대조로 5건 추가, 2026-10-14 구현 도메인 재대조로 7건 추가)

의도적 범위 제외(§2-4)와 구분한다. 아래는 **RFP 요구이고, 제외하지 않았지만 아직 없는 것**이다. 산출물 문서에도 "미구현"으로 그대로 적는다.

| RFP | 항목 | 지금 상태(실측) |
|---|---|---|
| 게시판(1-1 #4) | 본사→현장 교육자료 첨부 | `Attachment` 테이블만 있고 API·화면이 없다 |
| 보안요건(1-2 #8) | 보안관리계획(인원·문서·장비) | 없다. 개인정보처리방침은 회원 웹 초안으로 작성(D51) |
| **개념도(p.4) 현장→본사** | **업무지원 요청** | 2026-10-11 원본 재대조로 발견 — 코드·설계 문서 어디에도 없었다. 현장이 본사로 올리는 두 흐름(업무일지·업무지원 요청) 중 하나(업무일지 열람은 D51로 구현). 새 테이블이 필요할 가능성이 커 스키마 승인 대상 |

**2026-10-14 재대조 후 채운 것(log/114)**: 본사→현장 근태관리(본사 "근태 현황" 조회 화면), 게시판 직원관리 탭("직원 교육자료" 탭 + `GET /posts?category=`), 회원용 강사 정보(회차 화면의 강사 소개·전문 종목), 혼잡도 30분 경과 경고(관리자·회원 화면), 오류 데이터 진단 절차([data-integrity](../architecture/data-integrity.md) §7, 점검 SQL 9개).

**부분 충족 — 보강 후보(2026-10-14 재대조)**: 현장→이용자 "각 시설에 대한 공지"(1-1 #4) — 공지는 지점 단위라 시설을 지정할 수 없다(넓게 읽으면 충족).

**다음에 풀 방법(계획, 2026-10-11 사용자 방향)**: 시연 데이터를 계약 상태별 지점 5곳(정상 2·갱신 임박·만료·종료)으로 줄이고 밀도 있게 다시 만들 때(STATUS 다음 할 일), 지점별 시나리오를 끝까지 돌리며 위 항목을 채운다. 프로그램 필터·캘린더형 예약·변경 이력 범위·느린 작업 알림은 데이터가 쌓이면 바로 드러나는 화면 작업이고, 업무지원 요청(스키마 승인)·첨부(파일 저장소 결정)·인사 변경 신청은 따로 결정·작업이 필요하다. 2026-10-14 우선순위를 "RFP 문구 회복"으로 정하고(D51) 업무일지 열람·경로 표시·회원 웹 이용 안내·개인정보처리방침 초안을 먼저 채웠다(log/112).

**성능 요구(1-1 #10·#11) — 측정·대응했고 위험이 남음**: Lambda 위 첫 k6(2026-10-04, [log/056](../log/056.md))에서 로그인 p95 237ms(Render 때 15.16초)였지만 요청당 처리 시간 W가 p50 약 110ms라 처리 한계가 약 50 rps였다(D42). 원인을 `pgbouncer=true`의 작업당 왕복으로 측정하고([D48](../decisions/D48.md)) DB 접속을 Session pooler로 바꿨다([D49](../decisions/D49.md)). 운영 재측정(2026-10-12, [log/109](../log/109.md))에서 **W 약 40ms, 과부하에서 실제 처리 약 80~90 rps**(측정 PC가 먼저 막혀 하한, [D50](../decisions/D50.md)). 남은 위험: 로그인 몰림 거절 38건(1,866건 중 2%)과 50 rps 조회 거절 47건 — 원인 미확인(STATUS).

**설계는 있지만 미구현인 도메인 규칙(RFP 직접 요구는 아님)**: 지금은 없다. 마지막 항목이던 지점 계약 종료 시 파견 종료·재배치 대기는 2026-10-10에 구현했다(인사정보관리 ADR-STF-07·08, log/099·103).

**API는 있고 화면이 없는 것**: 지금은 없다. 마지막 항목이던 관리자의 직원 업무일지 열람은 2026-10-14 직원 상세에 붙였다(D51, log/112).

**대상 지점·회원 앱 형태(2026-10-06, D40 — 2026-09-30 D37의 회원 앱 제외를 대체)**: 지점은 수도권 83곳(서울·경기·인천)만 대상으로 하고 지방 15곳은 뺀다. 98곳 전체면 회원 기능까지 열었을 때 하루 요청이 약 10.8만 건으로 엣지 무료 한도(10만)를 넘고, 83곳이면 약 9.3만 건이다(design-constants ⑬, 지점당 하루 100명 가정). 회원 기능은 네이티브 앱(`apps/member-app`, React Native)이 아니라 **모바일 웹**으로 만든다(2026-10-08 구현, D41). 관리자 웹과 같은 스택·같은 Worker라 인프라를 더 붙이지 않는다. RFP 6번의 "모바일결제"는 모바일 웹의 모의 결제로 대응한다.
