# 12. 원본 요구사항 추적표 및 구현 현황 차이 분석

> 이 문서는 두 가지를 다룹니다.
> 1. **요구사항 추적(Traceability)**: `reference/제안요청서 원본.pdf`(㈜유니비즈컨설팅, 2022.06)에 적힌 원문 요구사항 항목을 하나씩, 이 프로젝트의 어느 설계 문서(1-1~1-9)가 어떻게 받아서 어떤 조정을 거쳤는지 표로 연결합니다. 각 조정의 상세 근거는 이미 [decisions/](../decisions/README.md)에 ADR 형식으로 정리되어 있으므로, 이 문서는 "원본 → 설계 문서 → 결정 근거"를 잇는 인덱스 역할을 합니다.
> 2. **설계 대비 실제 구현 상태**: 도메인별로 API·관리자 웹 화면·자동 테스트가 어디까지 있는지, 그리고 **RFP가 요구하는데 아직 구현하지 않은 것**을 코드에서 실측한 결과입니다(§2, 2026-10-05 재실측 — 전 도메인이 실DB(Prisma·Supabase)로 옮겨진 뒤의 기준).
>
> 원본 PDF는 한글 텍스트에 ToUnicode 매핑이 없는 폰트로 저장되어 있어 `pdftotext`(poppler)로는 추출이 안 되고, PyMuPDF로 재추출했습니다(추출 스크립트 결과는 이 세션 스크래치패드에만 존재, 저장소에는 포함하지 않음).

> 실측 방법: 컨트롤러의 라우트 데코레이터, 관리자 웹이 실제로 부르는 API 경로, `apps/api/test/*.spec.ts`를 grep으로 대조했다. 자동 테스트 실행 결과가 아니라 **존재 여부**만 본 것이다.

### 2-1. 전제 — 지금 시스템

- **데이터**: 전 도메인이 Prisma + Supabase Postgres(서울)다. 인메모리 `MockDataService`는 삭제됐다(D26~D36). DB 제약 CHECK 18개·지점 일치 트리거 7개·부분 unique가 앱 검증과 함께 규칙을 강제한다(D27·D28).
- **호스팅**: API는 AWS Lambda(서울), 관리자 웹과 `/api` 진입은 Cloudflare Worker다(D25·D37). Worker 경유 로그인·데이터 조회까지 확인했고, k6 실측도 했다(log/056).
- **규모**: Prisma 모델 31개, enum 24개, API 라우트 78개, 관리자 웹 화면 16개, API 테스트 파일 28개(통합 27 + 단위 1).
- **대상 지점·회원 기능**: 대상은 수도권 83곳이다(§2-4, D40). 회원 기능은 회원 모바일 웹(`apps/member-web`, 같은 Worker의 `/m/`, D41)으로 만들었다(2026-10-08, log/083~085) — 로그인·세션 유지, 프로그램·회차 조회, 예약·모의 결제·취소, 공지, 혼잡도, 내 정보 조회·수정. 자동 테스트는 없고(lint·빌드·360px 수동 확인), Worker 배포는 수동이다.

### 2-3. RFP가 요구하는데 아직 구현하지 않은 것 (2026-10-05 확인)

의도적 범위 제외(§2-4)와 구분한다. 아래는 **RFP 요구이고, 제외하지 않았지만 아직 없는 것**이다. 산출물 문서에도 "미구현"으로 그대로 적는다.

| RFP | 항목 | 지금 상태(실측) |
|---|---|---|
| 데이터관리방안(1-2 #3) | 변경 이력(`AuditLog`) | 인사 변경 3종만 기록한다(D44). 회원·자산 상태 변경, 근태 정정은 기록하지 않는다 |
| 사용자인터페이스보안(1-2 #7) | 상세 열람 기록(전화번호 원문) | 목록 마스킹은 구현됐다(회원·직원·강사, ADR-MEM-04, 2026-10-07). 상세는 원문이고 열람을 AuditLog에 남기지 않는다(D44 범위 밖) |
| 인사정보관리(1-1 #2) | 인사 변경 신청 → 관리자 승인 | `StaffProfileChangeRequest` 테이블만 있고 API·화면이 없다 |
| 게시판(1-1 #4) | 본사→현장 교육자료 첨부 | `Attachment` 테이블만 있고 API·화면이 없다 |
| UI/UX(1-2 #6) | 캘린더/스케줄표형 예약, MAP형 위치 | 회차 목록 표로만 구현했다 |
| 보안요건(1-2 #8) | 개인정보처리방침 | 별도 문서가 없다 |

**성능 요구(1-1 #10·#11) — 측정은 했고 위험이 남음**: Lambda 위 k6(2026-10-04, [log/056](../log/056.md))에서 로그인 p95 237ms(Render 때 15.16초), 50 rps × 5분 p95 178ms, 300 rps 과부하에서 넘친 요청만 13ms에 거절됐다. 그러나 요청당 처리 시간이 p50 약 110ms(가정 50ms)라 상한 10에서 실질 처리 한계는 약 50~55 rps이고, 로그인 램핑 정점에서 거절 1건이 나왔다. 원인(풀러 왕복 × 요청당 쿼리 수)은 추정만 했다.

**설계는 있지만 미구현인 도메인 규칙(RFP 직접 요구는 아님)**: 지점 계약이 종료(TERMINATED)되면 그 지점에 파견 중인 직원의 파견을 종료하고 재배치 대상에 올리는 처리(architecture/entities.md §2-1). 지금은 신규 활동 차단(409)만 동작한다.

**API는 있고 화면이 없는 것**: 결근 확정(근태), 자산 정보 수정. 회원 가입·연동 화면은 2026-10-09에 붙었다(log/092).

### 2-4. 범위 제외 결정 (2026-09-20, 대상 지점·회원 앱 형태 2026-10-06)

미구현 항목 중 **RFP 요구가 아니거나, 우리에게 없는 인프라(스케줄러·알림·파일 스토리지)가 필요하거나, 화면에서 보이지 않거나, 다른 기능과 중복되는 것**은 "앞으로 할 일"에서 빼고 의도적 범위 제외로 확정했다. 각 항목의 근거와 향후 확장 가능성은 해당 설계 문서 §8/§9 상단의 "범위 제외" 인용에 적었다. 이후 "미구현"이라는 표현은 **RFP 요구인데 아직 안 한 것**만 가리키도록 구분한다.

| 도메인 | 범위 제외 항목 | 향후 확장 |
|---|---|---|
| 01 권한관리 | 범용 계정 발급/목록 API, 로그인 5회 잠금 | 필드 추가 수준으로 가능 |
| 03 근태관리 | 자동 결근 배치 | 조회 시점 계산 또는 스케줄러 도입 시 |
| 04 게시판 | 읽음 확인, 상단 고정 | 가능 |
| 06 예약및결제 | 강사 정산·원천징수(`commissionRate` 필드·UI도 코드에서 제거), 노쇼 자동처리, 5분 결제 TTL | 정산 필요 시 모델 복원, 나머지는 스케줄러 도입 시 |
| 07 강사·프로그램게시 | 시설 충돌 검사, 휴강 예약자 알림, 상태 자동 전이 배치 | 알림·스케줄러 도입 시 |
| 08 혼잡도관리 | QR 체크인/아웃, 5분 자동계산, 미체크아웃 마감, 현재 이용자 목록 | 회원 모바일 웹 착수 후 체크인 데이터 위에 확장 |
| 10 자원문서관리 | 감가상각 배치(`bookValue`), STAFF 본인 인사서류 조회(코드에서 제거), 실무 확장 목록 전체(reference/기업구조및관리시스템분석.md §7) | 소유 구분·이관·점검 이력 등은 가치가 커서 우선 후보 |

**대상 지점·회원 앱 형태(2026-10-06, D40 — 2026-09-30 D37의 회원 앱 제외를 대체)**: 지점은 수도권 83곳(서울·경기·인천)만 대상으로 하고 지방 15곳은 뺀다. 98곳 전체면 회원 기능까지 열었을 때 하루 요청이 약 10.8만 건으로 엣지 무료 한도(10만)를 넘고, 83곳이면 약 9.3만 건이다(design-constants ⑬, 지점당 하루 100명 가정). 회원 기능은 네이티브 앱(`apps/member-app`, React Native)이 아니라 **모바일 웹**으로 만든다(2026-10-08 구현, D41). 관리자 웹과 같은 스택·같은 Worker라 인프라를 더 붙이지 않는다. RFP 6번의 "모바일결제"는 모바일 웹의 모의 결제로 대응한다.

**제외하지 않는 것(RFP 요구인데 아직 없음)**은 §2-3에 실측 결과와 함께 정리했다.
