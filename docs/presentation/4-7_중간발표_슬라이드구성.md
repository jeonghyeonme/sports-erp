# 4-7. 중간발표 슬라이드 구성 — 6주차 이후 진행 + RFP 추적 현황 (2026-10-19 기준)

> 공통 지침은 [4-0](4-0_발표자료_공통지침.md). 파트 A(6주차 발표 이후 개발한 것)와 파트 B(RFP를 얼마나 구현했나) 두 파트를 다룬다. 덱 소스는 6주차 소스를 복사해 `assets/4-7_중간발표/deck-source/`에서 시작한다(아직 만들지 않음). **덱 미제작 — 이 문서는 구성안이다.**
>
> 파트 B의 수치는 모두 [요구사항추적표](../reference/요구사항추적표.md) §3(2026-10-19)에서만 가져온다. 새로 세거나 반올림을 바꾸지 않는다. 추적표가 바뀌면 이 문서의 수치를 추적표에 맞춰 고친다. 파트 A의 시연 데이터 수치는 STATUS·D58 값이다.

## 발표 조건

- **분량**: 장 수 제한 없음(사용자, 2026-10-19). 파트 A 6장 약 6분 + 파트 B 10장 약 10분 + 마무리 1장 = 17장 약 16.5분. 2026-10-19 사용자 결정: 파트 A는 장 수를 줄이고 RFP 재대조·추적표 정리 이야기를 빼 **개발 측면에서 완료된 것만** 남긴다(파트 B는 유지). 라이브 데모 없음.
- **청중**: 교수·평가자 — RFP 대비 완성도를 평가하는 사람. 관심은 "얼마나 했나"보다 **"그 숫자를 공정하게 셌나"**다. 그래서 판정 방법을 숫자보다 먼저 보이고, 유리한 수치(구현+조정)와 너그러운 수치(부분 포함)를 항상 함께 쓴다.
- **위치**: 중간발표 덱 안의 두 파트. 덱에 다른 파트가 없으면 표지(`cover`)와 마무리(`closing`)를 이 문서 기준으로 붙인다.
- **자료**: 6주차 덱 소스(`assets/4-6_6주차발표/deck-source/`)의 생성기·디자인 규칙을 이어 쓴다. 화면 캡처(파트 A 새 기능·점검 결과, 파트 B 조정 사례)와 엑셀 판정 시트. 충족률은 별도 도표 없이 큰 숫자 표로 보인다(사용자 선택 — 도표 미선택).
- **6주차와 다른 전제**: 6주차 덱은 RFP 누락 항목과 코드 결함(R1·R2)을 넣지 않았다(그때 사용자 결정). 이번에는 결함은 파트 A에 재현·수정한 결과로, RFP 미구현·부분은 파트 B에 판정으로 넣는다.
- **결정 근거(D53)**: 상위 목표가 "실무 노하우·도메인 지식 습득이 먼저"라, 파트 A는 완료된 개발만 짧게 보이고, 파트 B는 요구사항을 조항 단위로 추적하고 판정 기준을 공개하는 방식 자체를 보여준다.

## 서사

6주차 이후 화면·기능 16개를 더하고, 시연 데이터를 운영 중인 지점처럼 채운 뒤 그 데이터로 숨은 결함과 화면 문제를 찾아 고쳤다 → 그래서 지금 RFP를 얼마나 구현했나: 72조항을 다섯 가지로 판정해 전체 70%(부분 포함 94%), 기능·성능은 86% → 남은 것은 대부분 문서이고, 코드 / 문서 / 의도적 제외 유지로 나눠 메운다.

## 발표 노트 요점 (장별, 덱 제작 시 노트에 옮긴다)

- **A2 `after-features`**: 하나씩 읽지 않는다 — "인사·근태·예약 화면이 현장 업무 순서대로 이어지게 됐다" 정도로 묶어 말한다. 관리자·회원 웹은 자동 테스트가 없고 lint·빌드와 화면 점검(A6)으로 확인했다.
- **A3 `after-support`**: 배포 DB에 테이블을 적용하고 배포 API가 응답하는 것까지 확인했다. 첨부(교육자료)는 업로드 주소 발급까지만 배포에서 확인 — "첨부가 배포에서 동작한다"고 말하지 말 것.
- **A4 `after-dense`**: 시연 데이터는 로컬·테스트 DB 이야기다. 배포 화면은 아직 83곳 데이터라고 밝힌다(5곳 재시드는 승인 대기).
- **A5 `after-defects`**: 운영에서 실제로 사고가 난 것이 아니다 — 코드 읽기로 찾은 위험을 테스트로 재현한 것이다. "버그가 있었다"보다 "실패를 먼저 만들고 고쳤다"로 말한다.
- **A6 `after-qa`**: 속도 수치는 로컬 측정이다(운영 수치 아님). 화면 자동 테스트는 여전히 없다. 매출은 회차 예약 결제만 센다(수강·PT 패키지는 결제 기록이 없어 빠짐 — 화면에 적었다).
- **B2 `rfp-method`**: "조항을 어떻게 나누느냐가 숫자를 정한다"를 먼저 말한다. 해당 없음 8개(발주기관 승인·확약서·하자보수·대면 교육 등)를 분모에서 뺀 이유를 한 문장으로. **판정은 자기 평가다** — 외부 검수가 아니라고 먼저 밝힌다.
- **B4 `rfp-score`**: 70%와 94%를 반드시 같이 말한다. "94% 완성"이라고 말하지 말 것 — 94%는 일부만 한 조항까지 넣은 값이다.
- **B5 `rfp-function`**: "기능은 거의 다 했다"가 아니라 "기능 29조항 중 미구현 0, 부분 4"로 말한다. 부분 4개는 무엇이 빠졌는지 한 마디씩.
- **B6 `rfp-adjust`**: 조정을 충족으로 세는 이유 — 결과는 냈고 바꾼 이유가 결정 기록으로 남아 있어서. 납득하지 않는 평가자를 위해 부분 포함/제외 수치를 함께 둔 것이라고 덧붙인다.
- **B7 `rfp-adjust-shot`**: 회원 화면은 회원 모바일 웹(네이티브 앱 아님)이라고 밝힌다. 모의 결제는 실제 돈이 오가지 않는다.
- **B8 `rfp-gap`**: 의도적 제외는 "못 했다"가 아니라 "근거 없는 숫자를 만들지 않기로 했다"로 말한다. 미구현 4개 = 보안관리계획(N8-1) + 의도적 제외 3(T2-1·P2-2·P2-3).

## Q&A 대비

- **엿새(10/14~10/19)에 이만큼이 가능했나**: AI와 함께 작업했고, 결정마다 근거 기록·커밋 전 검사·CI가 막는 구조다(D53, CLAUDE.md 검증 수단). 각 작업의 경위는 진행 기록 log/110~131에 있다.
- **RFP를 다시 대조한 경위**: 6주차 발표 뒤 RFP 원문을 문구 단위로 다시 대조해 빠진 것을 추적표에 올렸고(log/112·113), 파트 A의 새 기능 대부분이 그 목록에서 나왔다. 슬라이드에서는 뺐다(사용자 결정).
- **코드 규모 변화**: API 라우트 81 → 99(로컬 전용 2개 포함), API 테스트 파일 34 → 42(`35e28ac` → `c15751d` 재실측). 숫자 요약 장은 넣지 않았다.
- **화면 점검 발견 14건의 성격**: 코드 결함 1(근태 시각)·시연 데이터 불일치 등 섞여 있다(log/125 표). 모두 고쳤다(log/127~130).
- **판정 주체**: 자기 평가다. 근거(경로·테스트·결정 번호)를 조항마다 공개해 검증 가능하게 했다(추적표 §3, 엑셀 시트).
- **해당 없음 8개를 빼는 게 유리하지 않나**: 분모에 넣어도 판정 대상이 될 수 없는 조항(발주기관·계약·대면)이다.
- **자동 테스트 범위**: API는 실DB로 지점 격리·계약 종료 차단·인사 권한·동시성·도메인 규칙을 본다(42개 파일 495건, CI 통과 — 추적표 §2). 관리자 웹·회원 웹은 자동 테스트가 없고 lint·빌드만이다.
- **성능 조항**: 운영 측정은 했지만 순간 몰림 거절(로그인 몰림 38건 등) 원인은 미확인이다(추적표 §2-3 성능 요구).
- **첨부(F4-2)**: 화면·API는 있으나 배포 저장소에서 실제 파일 올리기·내려받기는 검증 전이다.
- **세부 권한을 왜 안 했나**: 역할 4개 + 지점 격리로 조정(D1). 사용자별·기능별 권한 표는 범위가 커서 결정이 먼저다.
