# 4-7. 중간발표 슬라이드 구성 (구성 2026-10-19, RFP 이행 현황 형식·수치 2026-10-22 개편)

> 공통 지침은 [4-0](4-0_발표자료_공통지침.md). 파트 A(6주차 이후 개발한 것, 10/14~10/22)와 파트 B(중간발표 본론 — 개요·설계·RFP 요구사항별 이행 현황·검증과 운영)로 이루어진다. 덱 소스는 6주차 소스를 복사해 `assets/4-7_중간발표/deck-source/`에서 시작한다(아직 만들지 않음). **덱 미제작 — 이 문서는 구성안이다.**
>
> RFP 이행 상태는 모두 [요구사항추적표](../reference/요구사항추적표.md) §3(2026-10-22, log/169 반영)에서만 가져온다. 새로 세거나 판정을 바꾸지 않는다 — 슬라이드의 상태 이름만 아래 대응표대로 바꿔 부른다. 규모·테스트 수치는 `beea7ec`(2026-10-22) 재실측, 성능 수치는 [D50](../decisions/D50.md), 시연 데이터 수치는 STATUS·[D58](../decisions/D58.md) 값이다.

## 발표 조건

- **분량**: 약 20분, 24장(파트 A 8장 약 6.25분 + 파트 B 15장 약 12.25분 + 마무리 1장 1분) + 질문용 부록. 라이브 데모 없음.
- **청중**: 교수·평가자 — RFP 대비 완성도를 평가하는 사람.
- **RFP 전달 방식(사용자 결정 2026-10-22)**: 백분율로 뭉뚱그리지 않고 **중간보고 형식** — RFP 요구사항명마다 "RFP가 요구한 것 → 구현한 것(화면·기능 이름) → 이행 상태(조항 수)"를 표로 보인다. 평가자가 "RFP의 어느 부분까지 구현했나"를 조항 단위로 확인할 수 있어야 한다. 백분율은 슬라이드 본문에 쓰지 않고 노트·Q&A에만 둔다.
- **순서**: 파트 A(최근 진행) → 파트 B(본론). 사용자 결정(2026-10-19).
- **사용자 결정 이력**: 2026-10-19 — ① 파트 A는 개발 측면에서 완료된 것만 ② 파트 B는 중간발표 본론(개요·설계·RFP·검증) ③ 전체 20분 내외. 2026-10-22 — 파트 A에 10/20~22 작업 2장(A7·A8). 같은 날 — RFP를 중간보고 형식으로 바꾸고 10/22 보안·업그레이드 작업을 A8에 넣는다.
- **자료**: 6주차 덱 소스(`assets/4-6_6주차발표/deck-source/`)의 생성기·디자인 규칙과, 개요·설계 도식은 종합발표 덱 소스(`assets/4-5_종합발표/deck-source/`)의 도식을 최신 사실로 고쳐 재사용한다. 화면 캡처 6장(아래 목록).
- **6주차와 다른 전제**: 6주차 덱은 RFP 누락 항목과 코드 결함(R1·R2)을 넣지 않았다(그때 사용자 결정). 이번에는 결함은 파트 A에 재현·수정한 결과로, 부분·제외는 이행 현황 표와 마무리에 그대로 넣는다.
- **결정 근거(D53)**: 상위 목표가 "실무 노하우·도메인 지식 습득이 먼저"라, 본론은 **도메인 이해 → 그 이해가 만든 설계 규칙 → 요구사항별 이행 → 검증·측정**의 흐름으로 보인다. 실무 중간보고가 요구사항 이행 현황표로 보고하는 방식을 따르는 것도 같은 목표다.

## 서사

6주차 이후 화면·기능 16개를 더하고, 시연 데이터를 운영 중인 지점처럼 채운 뒤 그 데이터로 숨은 결함과 화면 문제를 찾아 고쳤고, 세부 권한·처리 대기함·화면 자동 테스트·보안 조치로 마무리했다 → 프로젝트 전체를 다시 보면: 헬스장 체인이 아니라 위탁운영 계약 사업이라 안정성이 곧 계약이고 → 그래서 지점 격리·계약 종료 차단·인사 권한 분리를 한 곳에서 강제하는 구조로 설계했다 → RFP를 원문 글머리 하나씩 72조항으로 나눠 요구사항마다 무엇을 구현했는지 보면, 기능·성능 29조항은 모두 완료·조정(원문이 미확정인 1조항 제외)이고, 비기능·과업·산출물도 대부분 완료다 → 그 규칙은 실DB 자동 테스트와 화면 자동 테스트로, 속도는 운영 측정으로 확인했다 → 남은 것은 실제 운영이 있어야 채울 부분 3조항과 근거 없는 숫자를 만들지 않으려 뺀 제외 3조항이다.

## 발표 노트 요점 (장별, 덱 제작 시 노트에 옮긴다)

- **A2 `after-features`**: 하나씩 읽지 않는다 — "인사·근태·예약 화면이 현장 업무 순서대로 이어지게 됐다" 정도로 묶어 말한다. 이 기능들은 B8·B9 이행 현황 표에 다시 나온다.
- **A3 `after-support`**: 배포 DB에 테이블을 적용하고 배포 API가 응답하는 것까지 확인했다. 첨부는 이후 배포에서 올리기·내려받기까지 확인했다(log/144).
- **A4 `after-dense`**: 시연 데이터는 로컬·테스트 DB 이야기다. 배포 DB도 10/20에 같은 5곳 + 시연 데이터로 재시드했다(log/143).
- **A5 `after-defects`**: 운영 사고가 아니라 코드 읽기로 찾은 위험을 테스트로 재현한 것이다. "실패를 먼저 만들고 고쳤다"로 말한다.
- **A6 `after-qa`**: 속도 수치는 로컬 측정이다. 매출은 회차 예약 결제만 센다(수강·PT 패키지는 결제 기록이 없어 빠짐 — 화면에 적었다).
- **A7 `after-permission`**: 세부 권한은 역할 상한 안에서만 좁히거나 넓힌다 — 직원에게 지점 관리자 일을 줄 수는 없다. 판정은 서버가 하고 화면 숨김은 편의다(D60).
- **A8 `after-quality`**: 화면 자동 테스트는 역할별 핵심 경로 11건뿐이다. 업그레이드 결함은 기대값을 바꾸지 않고 코드를 고쳤다 — "테스트가 있어서 운영에 나가기 전에 잡혔다"가 요점. 임시 비밀번호는 응답에 한 번만 싣고 해시만 저장한다.
- **B2 `ov-business`**: 기업 분석은 RFP와 일반 실무 관행을 조사해 재구성한 것이지 스포이즘 내부 자료가 아니다(4-0 §3).
- **B3 `ov-scope`**: 회원 화면은 회원 모바일 웹(네이티브 앱 아님)이다. 모의 결제는 실제 돈이 오가지 않는다. 83곳은 설계 대상이고, 시연은 5곳이다.
- **B6 `arch-system`**: 상한 10은 비용 사고를 막는 의도적 제한이다(D42). 넘치면 503 안내로 거절한다.
- **B7 `rfp-method`**: "조항을 어떻게 나누느냐가 결과를 정한다"를 먼저 말한다. **판정은 자기 평가다** — 외부 검수가 아니고, 대신 조항마다 근거를 공개했다(부록 X1~X4). 해당 없음 8개는 발주기관·계약·대면 행위라 대상이 없다고 한 문장. 백분율은 말하지 않는다 — 물으면 Q&A 답.
- **B8 `rfp-func-1`**: 표를 다 읽지 않는다. 요구사항명마다 "RFP는 ○○를 요구했고, ○○ 화면으로 했다"를 한 문장씩 — 권한관리는 "입력·수정·삭제·조회·출력을 기능별로"라는 원문을 그대로 구현한 것을 강조한다.
- **B9 `rfp-func-2`**: 조정 2건은 "못 했다"가 아니라 "방식을 바꿨다 — 이유는 결정 기록"으로 말한다. 회원관리의 "타현장 조회 불가"는 선택이 아니라 항상 강제(B6 가드)라고 연결한다. 결제내역 처리(F6-2)는 원문이 "추후 논의"라 해당 없음.
- **B10 `rfp-perf`**: 110 → 40ms·80~90 rps는 운영 실측(10/12)이고 80~90 rps는 측정 PC가 먼저 막힌 하한이다. 메모리 167MB는 콘솔 패턴 테스트에 잡힌 표본 3건의 값이다(10/22) — "평균이 계속 그렇다"고 말하지 않는다. 순간 몰림 거절은 원인 미확인이라고 그대로 말한다.
- **B11 `rfp-nonfunc`**: 해당 없음 6은 한 줄로 넘긴다. 부분 2(PG 실제 호출·위탁 계약서)는 "문서·설계까지 했고 실제 계약·호출만 남았다".
- **B12 `rfp-task`**: 제출물 이름을 읽는다 — 평가자가 저장소에서 바로 찾을 수 있게. 제외 3은 마무리에서 이유를 말한다고 넘긴다.
- **B13 `verify-tests`**: 551건은 API 테스트, 11건은 화면 자동 테스트다. 격리·계약·인사 테스트가 실패하면 기대값을 바꾸지 않고 코드 위반으로 다룬다는 규칙을 한 줄로.
- **B15 `verify-ai`**: "AI가 다 했다"가 아니라 "AI가 만든 것을 기계적 검사와 기록이 붙잡는 구조"로 말한다.
- **Z1 `next-all`**: 제외는 "못 했다"가 아니라 "근거 없는 숫자를 만들지 않기로 했다"로 말한다. 부분 3은 "코드·문서로는 더 채울 수 없는 것 — 포트폴리오에는 발주기관·실운영 계약이 없다".

## Q&A 대비

- **그래서 몇 퍼센트인가**: 해당 없음 8을 뺀 64조항 중 완료+조정 58 = 91%, 부분까지 넣으면 61 = 95%. 기능·성능만 보면 28/28. 95%를 "완성도"라고 말하지 않는다 — 일부만 한 조항까지 넣은 값이다. 첫 판정(10/19)은 70%였다.
- **조정을 완료로 세도 되나**: 결과는 냈고 바꾼 이유가 결정 기록으로 남아 있어 함께 셌다. 슬라이드에서는 완료와 조정을 다른 색으로 따로 보였다.
- **판정 주체**: 자기 평가다. 근거(경로·테스트·결정 번호)를 조항마다 공개해 검증 가능하게 했다(부록 X1~X4, 추적표 §3, 엑셀 시트).
- **해당 없음 8개를 빼는 게 유리하지 않나**: 분모에 넣어도 판정 대상이 될 수 없는 조항(발주기관·계약·대면)이다. 슬라이드에는 해당 없음도 숨기지 않고 조항 수로 보였다.
- **RFP 원문 번호 9가 없다**: 원문 표 자체의 결번이다. 임의로 채우지 않았다(추적표 §1).
- **아흐레(10/14~10/22)에 이만큼이 가능했나**: AI와 함께 작업했고, 결정마다 근거 기록·커밋 전 검사·CI가 막는 구조다(B15). 각 작업의 경위는 진행 기록 log/110~169에 있다.
- **RFP를 다시 대조한 경위**: 6주차 발표 뒤 RFP 원문을 문구 단위로 다시 대조해 빠진 것을 추적표에 올렸고(log/112·113), 파트 A의 새 기능 대부분이 그 목록에서 나왔다.
- **6주차 이후 코드 규모 변화**: API 라우트 81 → 99 → 105(로컬 전용 2개 포함, 10/22에도 105), API 테스트 파일 34 → 42 → 52(`35e28ac` → `c15751d` → `beea7ec` 재실측), 화면 자동 테스트 0 → 11건.
- **화면 점검 발견 14건의 성격**: 코드 결함 1(근태 시각)·시연 데이터 불일치 등 섞여 있다(log/125 표). 모두 고쳤다(log/127~130).
- **세부 권한은 어떻게 했나**: 역할 4개를 상한으로 두고 그 안에서 기능 15개 × 조회·입력·수정·삭제·출력을 역할 기본값·개인 예외로 본사가 설정한다(D60, D1 대체).
- **왜 네이티브 앱이 아닌가**: 같은 서버·같은 Worker에 붙는 모바일 웹이 인프라 추가 없이 무료 한도 안에 들어온다는 계산(D40). 설치형 웹(PWA, D45)으로 홈 화면 설치는 된다 — 실기기 설치는 미확인.
- **데모 계정 비밀번호가 공개돼 있다**: 시연용 더미 데이터라 수용했다(security-plan S1·S2, 실운영 계획 없음). 훼손되면 재시드로 되돌린다. 새로 채용한 계정은 무작위 임시 비밀번호와 첫 로그인 변경 강제를 받는다(ADR-AUTH-08).
- **비용·한도**: Workers 무료 한도(지점 90곳 초과 시 넘음, design-constants ⑬), DB 무료 용량 500MB(예약·결제 이력만으로 1~1.5년, 가정) — STATUS 열린 위험.
