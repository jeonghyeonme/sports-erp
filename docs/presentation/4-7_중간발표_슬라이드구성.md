# 4-7. 중간발표 슬라이드 구성 (2026-10-19 기준)

> 공통 지침은 [4-0](4-0_발표자료_공통지침.md). 파트 A(6주차 이후 개발한 것)와 파트 B(중간발표 본론 — 개요·설계·RFP 추적·검증과 운영)로 이루어진다. 덱 소스는 6주차 소스를 복사해 `assets/4-7_중간발표/deck-source/`에서 시작한다(아직 만들지 않음). **덱 미제작 — 이 문서는 구성안이다.**
>
> RFP 추적 수치는 모두 [요구사항추적표](../reference/요구사항추적표.md) §3(2026-10-19)에서만 가져온다. 새로 세거나 반올림을 바꾸지 않는다. 규모·테스트 수치는 추적표 §2, 성능 수치는 [D50](../decisions/D50.md), 시연 데이터 수치는 STATUS·[D58](../decisions/D58.md) 값이다.

## 발표 조건

- **분량**: 약 20분, 22장(파트 A 6장 약 6분 + 파트 B 15장 약 13.5분 + 마무리 1장 0.5분). 라이브 데모 없음.
- **청중**: 교수·평가자 — RFP 대비 완성도를 평가하는 사람. RFP 추적에서는 "얼마나 했나"보다 **"그 숫자를 공정하게 셌나"**가 관심이라 판정 방법을 숫자보다 먼저 보이고, 구현+조정 수치와 부분 포함 수치를 항상 함께 쓴다.
- **순서**: 파트 A(최근 진행) → 파트 B(본론). 사용자 결정(2026-10-19).
- **사용자 결정 이력(2026-10-19)**: ① 파트 A는 장 수를 줄이고 RFP 재대조·추적표 정리 이야기를 빼 개발 측면에서 완료된 것만 ② 파트 B는 RFP 추적 현황만이 아니라 중간발표 본론으로 — 프로젝트 개요·문제 정의, 설계·아키텍처, RFP 추적 현황, 검증·운영 ③ 전체 20분 내외.
- **자료**: 6주차 덱 소스(`assets/4-6_6주차발표/deck-source/`)의 생성기·디자인 규칙과, 개요·설계 도식은 종합발표 덱 소스(`assets/4-5_종합발표/deck-source/`)의 도식을 최신 사실로 고쳐 재사용한다. 화면 캡처 5장(아래 목록)과 엑셀 판정 시트. 충족률은 별도 도표 없이 큰 숫자 표(사용자 선택 — 도표 미선택).
- **6주차와 다른 전제**: 6주차 덱은 RFP 누락 항목과 코드 결함(R1·R2)을 넣지 않았다(그때 사용자 결정). 이번에는 결함은 파트 A에 재현·수정한 결과로, RFP 미구현·부분은 파트 B에 판정으로 넣는다.
- **결정 근거(D53)**: 상위 목표가 "실무 노하우·도메인 지식 습득이 먼저"라, 본론은 기능 나열보다 **도메인 이해 → 그 이해가 만든 설계 규칙 → 요구사항 추적 → 검증·측정**이라는 흐름으로 보인다.

## 서사

6주차 이후 화면·기능 16개를 더하고, 시연 데이터를 운영 중인 지점처럼 채운 뒤 그 데이터로 숨은 결함과 화면 문제를 찾아 고쳤다 → 프로젝트 전체를 다시 보면: 헬스장 체인이 아니라 위탁운영 계약 사업이라 안정성이 곧 계약이고 → 그래서 지점 격리·계약 종료 차단·인사 권한 분리를 한 곳에서 강제하는 구조로 설계했다 → RFP 72조항을 다섯 가지로 판정하면 전체 70%(부분 포함 94%), 기능·성능은 86%이고 → 그 규칙은 실DB 자동 테스트로, 속도는 운영 측정으로 확인했다 → 남은 것은 대부분 문서이고, 코드 / 문서 / 의도적 제외 유지로 나눠 메운다.

## 발표 노트 요점 (장별, 덱 제작 시 노트에 옮긴다)

- **A2 `after-features`**: 하나씩 읽지 않는다 — "인사·근태·예약 화면이 현장 업무 순서대로 이어지게 됐다" 정도로 묶어 말한다. 관리자·회원 웹은 자동 테스트가 없고 lint·빌드와 화면 점검(A6)으로 확인했다.
- **A3 `after-support`**: 배포 DB에 테이블을 적용하고 배포 API가 응답하는 것까지 확인했다. 첨부(교육자료)는 업로드 주소 발급까지만 배포에서 확인 — "첨부가 배포에서 동작한다"고 말하지 말 것.
- **A4 `after-dense`**: 시연 데이터는 로컬·테스트 DB 이야기다. 배포 화면은 아직 83곳 데이터라고 밝힌다(5곳 재시드는 승인 대기).
- **A5 `after-defects`**: 운영에서 실제로 사고가 난 것이 아니다 — 코드 읽기로 찾은 위험을 테스트로 재현한 것이다. "버그가 있었다"보다 "실패를 먼저 만들고 고쳤다"로 말한다.
- **A6 `after-qa`**: 속도 수치는 로컬 측정이다(운영 수치 아님). 화면 자동 테스트는 여전히 없다. 매출은 회차 예약 결제만 센다(수강·PT 패키지는 결제 기록이 없어 빠짐 — 화면에 적었다).
- **B2 `ov-business`**: 기업 분석은 RFP와 일반 실무 관행을 조사해 재구성한 것이지 스포이즘 내부 자료가 아니다(4-0 §3). "실무를 조사·분석해 설계로 연결했다"까지만 말한다.
- **B3 `ov-scope`**: 회원 화면은 회원 모바일 웹(네이티브 앱 아님)이다. 모의 결제는 실제 돈이 오가지 않는다. 83곳은 설계 대상이고, 시연은 5곳이다.
- **B6 `arch-system`**: 상한 10은 비용 사고를 막는 의도적 제한이다(D42). 넘치면 503 안내로 거절한다.
- **B7 `rfp-method`**: "조항을 어떻게 나누느냐가 숫자를 정한다"를 먼저 말한다. 해당 없음 8개(발주기관 승인·확약서·하자보수·대면 교육 등)를 분모에서 뺀 이유를 한 문장으로. **판정은 자기 평가다** — 외부 검수가 아니라고 먼저 밝힌다.
- **B8 `rfp-score`**: 70%와 94%를 반드시 같이 말한다. "94% 완성"이라고 말하지 말 것 — 94%는 일부만 한 조항까지 넣은 값이다.
- **B9 `rfp-function`**: "기능은 거의 다 했다"가 아니라 "기능 29조항 중 미구현 0, 부분 4"로 말한다. 부분 4개는 무엇이 빠졌는지 한 마디씩.
- **B10 `rfp-adjust`**: 조정을 충족으로 세는 이유 — 결과는 냈고 바꾼 이유가 결정 기록으로 남아 있어서. 납득하지 않는 평가자를 위해 부분 포함/제외 수치를 함께 둔 것이라고 덧붙인다.
- **B11 `rfp-gap`**: 의도적 제외는 "못 했다"가 아니라 "근거 없는 숫자를 만들지 않기로 했다"로 말한다. 미구현 4개 = 보안관리계획(N8-1) + 의도적 제외 3(T2-1·P2-2·P2-3).
- **B12 `verify-tests`**: 495건은 API 테스트다. 격리·계약·인사 테스트가 실패하면 기대값을 바꾸지 않고 코드 위반으로 다룬다는 규칙을 한 줄로.
- **B13 `verify-perf`**: 110 → 40ms는 운영 실측(10/12)이다. 80~90 rps는 측정 PC가 먼저 막힌 하한이라 실제 한계는 확인하지 않았다. 순간 몰림 거절은 원인 미확인이라고 그대로 말한다.
- **B15 `verify-ai`**: "AI가 다 했다"가 아니라 "AI가 만든 것을 기계적 검사와 기록이 붙잡는 구조"로 말한다.

## Q&A 대비

- **엿새(10/14~10/19)에 이만큼이 가능했나**: AI와 함께 작업했고, 결정마다 근거 기록·커밋 전 검사·CI가 막는 구조다(B15). 각 작업의 경위는 진행 기록 log/110~131에 있다.
- **RFP를 다시 대조한 경위**: 6주차 발표 뒤 RFP 원문을 문구 단위로 다시 대조해 빠진 것을 추적표에 올렸고(log/112·113), 파트 A의 새 기능 대부분이 그 목록에서 나왔다. 슬라이드에서는 뺐다(사용자 결정).
- **6주차 이후 코드 규모 변화**: API 라우트 81 → 99(로컬 전용 2개 포함), API 테스트 파일 34 → 42(`35e28ac` → `c15751d` 재실측).
- **화면 점검 발견 14건의 성격**: 코드 결함 1(근태 시각)·시연 데이터 불일치 등 섞여 있다(log/125 표). 모두 고쳤다(log/127~130).
- **판정 주체**: 자기 평가다. 근거(경로·테스트·결정 번호)를 조항마다 공개해 검증 가능하게 했다(추적표 §3, 엑셀 시트).
- **해당 없음 8개를 빼는 게 유리하지 않나**: 분모에 넣어도 판정 대상이 될 수 없는 조항(발주기관·계약·대면)이다.
- **첨부(F4-2)**: 화면·API는 있으나 배포 저장소에서 실제 파일 올리기·내려받기는 검증 전이다.
- **세부 권한을 왜 안 했나**: 역할 4개 + 지점 격리로 조정(D1). 사용자별·기능별 권한 표는 범위가 커서 결정이 먼저다.
- **왜 네이티브 앱이 아닌가**: 같은 서버·같은 Worker에 붙는 모바일 웹이 인프라 추가 없이 무료 한도 안에 들어온다는 계산(D40). 설치형 웹(PWA, D45)으로 홈 화면 설치는 된다 — 실기기 설치는 미확인.
- **비용·한도**: Workers 무료 한도(지점 90곳 초과 시 넘음, design-constants ⑬), DB 무료 용량 500MB(예약·결제 이력만으로 1~1.5년, 가정) — STATUS 열린 위험.
