같은 규모에서는 빠르게를 택했고, 규모는 돈으로 올릴 수 있는 손잡이로 남겼습니다

실측: 10/12 운영 k6 + CloudWatch(측정 PC가 먼저 막혀 실제 한계는 더 클 수 있음) · 예상 부하는 계산값(지점당 하루 100명 가정)

D49 "감수하는 것". 세션 모드는 Lambda 실행 환경 하나가 DB 연결 하나를 계속 쥔다(요청이 끝나도, 쉬는 동안에도). 그래서 동시에 처리할 수 있는 요청 수 ≈ 연결 수가 된다. 지금 먼저 걸리는 천장은 Lambda 동시 실행 상한 10이고, 그다음이 Supabase 풀러 연결 약 15개(Pool Size, 대시보드 값은 아직 확인 전). 11번째 동시 요청은 기다리지 않고 바로 "서버 바쁨"(503)으로 거절된다(D37·D42) — 느려지는 대신 빨리 실패. 10/12 운영 실측(D50·log/109): 요청당 서버 처리 약 40ms, 과부하 300 rps에서 실제 처리 약 90 rps(1분 평균, 순간 최대 초당 약 120 — k6를 돌린 PC가 먼저 막혀 실제 한계는 더 클 수 있음 — 이론값 250 rps는 말하지 말 것). 예상 부하 피크 약 3 rps·몰림 약 8 rps는 계산값(D40). 평균 rps보다 위험한 것은 같은 순간의 몰림: 로그인 사용자를 늘리는 동안 새 실행 환경 9개가 각 약 1.4초씩 뜨며 자리를 잡아 38건이 거절됐다(추정 원인). 50 rps 조회에서도 거절 47건(약 0.3%)이 났다. 동시 실행이 매분 최대 10에 닿았지만 초당 도착은 고르게 50 안팎이라, 1초보다 짧은 몰림인지 호출당 부가 시간인지 아직 가리지 못했다 — 질문이 나오면 그대로 말할 것. 이전(트랜잭션 모드)은 연결을 작업마다 빌렸다 반납해 상한만 올리면 됐지만, 지금은 상한을 올리려면 Pool Size(유료)부터 올려야 한다. 대안으로 트랜잭션 모드를 유지하며 왕복을 줄이는 Prisma driver adapter를 보류해 뒀다(D49 A3). "규모가 줄었다"고 말하지 말 것 — 같은 상한에서 처리량은 오히려 약 1.8배가 됐고(실측), 줄어든 것은 상한을 공짜로 올릴 여지다.
