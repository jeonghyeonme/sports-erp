Ⅲ. 설계 · 깨지면 안 되는 규칙

세 규칙이 모든 설계의 출발점입니다

지점 데이터 격리

지점 관리자는 자기 지점 데이터만 조회·수정한다. 다른 지점 주소는 서버가 막는다

어디서 왔나 — RFP "타현장 정보 조회 불가"

계약 종료 차단

종료 지점은 신규 회원·예약·게시글·채용·발령이 막히고, 과거 조회는 남는다

어디서 왔나 — 지점 = 위탁 계약

인사 권한 분리

채용·재배치는 본사만. 지점 관리자는 파견된 인력의 일상 관리만

어디서 왔나 — 본사 채용 → 현장 파견

세 규칙은 자동 테스트가 매번 확인합니다 — 실패하면 기대값이 아니라 코드를 고칩니다

세 규칙은 사업 구조에서 바로 나온다. 지점 격리: RFP가 "타현장 정보를 조회할 수 없게 하는 권한"을 명시했다. 서버의 전역 가드 한 곳이 경로·쿼리의 지점 id와 리소스의 주인 지점을 보고 막는다(D46) — 다른 지점 id로 공격하는 자동 테스트 표가 있다. 계약 종료 차단: 종료 지점은 회원 등록·예약·게시글 작성·채용·파견 발령이 409로 막히고 과거 조회는 유지, 만료·갱신 임박은 막지 않는다. 인사 권한 분리: 직원은 본사가 채용해 파견하므로 채용·재배치는 본사만, 지점 관리자는 파견된 인력의 일상 관리만. 세 규칙의 테스트가 실패하면 기대값을 바꾸지 않고 코드의 규칙 위반으로 본다(프로젝트 규칙).
