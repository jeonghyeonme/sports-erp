Ⅵ. 진행 경과 · 1~6주차 요약

분석에서 시작해, 측정한 문제를 구조로 풀었습니다

분석 · 설계(1~3주차)

RFP를 위탁운영사로 재해석 · 요구사항 추적표 · 도메인 9개 설계 · 디자인 기준

구현과 재점검(3~4주차)

9개 도메인 구현 → 도메인마다 근거·대안·결정·검증 사이클로 결함 수정

첫 배포와 측정(4주차)

공유 서버에서 동시 로그인 40명에 15초 — 추측 대신 숫자

실DB · 서버 이관(종합)

가짜 데이터 서비스를 걷어 내고 실DB로, API는 요청별로 도는 Lambda로

범위 재설정 · 회원 앱(6주차)

수도권 83개 지점, 회원 기능은 휴대폰 웹으로

성능 원인(6주차)

DB 접속 방식을 측정해 바꿔 요청당 약 110 → 40ms

자세히는 함께 낸 주차별 발표자료

1~6주차 요약. 자세한 내용과 그때의 수치는 주차별 발표자료에 있다. 분석·설계: RFP를 헬스장 체인이 아니라 위탁운영사로 재해석하고, 요구사항 추적표와 도메인 9개 설계, 디자인 기준을 만들었다. 구현: 3주차까지 9개 도메인을 인메모리 데이터로 구현하고, 4주차에 도메인마다 근거 → 대안 → 결정 → 구현 → 검증 사이클로 다시 돌며 불변식 위반 결함을 고쳤다. 첫 배포(Render)에서 동시 로그인 40명에 15초를 측정했다. 그 결과로 전 도메인을 실DB로 옮기고(가짜 데이터 서비스 삭제, DB 제약 추가), API를 AWS Lambda(서울)로 옮겼다. 그다음 대상 지점을 수도권 83개로 정하고 회원 기능을 모바일 웹으로 만들었으며, 처리 시간이 가정의 두 배인 원인을 측정해 DB 접속 방식을 바꿨다.
