상태

시스템가용성

F10-1

CPU 평균 사용률 90% 이하

요청마다 따로 실행되는 서버(동시 10개 상한)로 CPU를 나눠 쓰지 않게 했고, CPU 대신 처리 시간을 쟀다.

조정

F10-2

메모리 평균 사용률 85% 이하

메모리는 실측 최대 약 16%이고, 85%를 넘으면 이메일 경보가 온다.

완료

F10-3

이용자 수 증가에 따른 운용 안정성 확보

이용자가 몰리면 넘친 요청만 바로 거절하고 잠시 뒤 다시 시도하라고 안내한다.

완료

F10-4

빈도 높은·중요 기능의 운영 환경 성능 시험

자주 쓰는 기능(로그인·조회)을 실제 운영 환경에서 부하 시험했다.

완료

F10-5

과부하에 따른 안정성 사전 점검

초당 300건을 1분간 보내는 과부하 시험으로 버티는지 미리 확인했다.

완료

시스템성능

F11-1

성능 진단 도구로 정확한 성능 진단

부하 시험 도구(k6)로 재고, 느린 원인을 측정해 요청당 처리 시간을 약 110ms에서 40ms로 줄였다.

완료

F11-2

처리 속도가 느린 작업은 사용자에게 사전 알림

요청이 3초를 넘으면 '처리 중', 15초를 넘으면 '응답이 늦다'고 화면에 알린다.

완료

조항별 화면·결정 기록은 함께 낸 RFP 이행 증빙(PDF)의 같은 조항 번호

조정 1개: CPU 평균 90% 이하 — Lambda는 요청마다 따로 실행돼 CPU를 나눠 쓰지 않으므로 CPU 대신 요청당 처리 시간(운영 실측 약 40ms)으로 봤다(D37·D50). 메모리는 실측 최대 167MB/1,024MB(약 16%)이고 5분 평균 85% 초과 시 이메일 경보를 운영에 적용했다. 과부하 300 rps 시나리오에서 실제 처리 약 80~90 rps(측정 PC 한계 포함), 넘친 요청은 즉시 503.
