### PART 02 계약 관리 (8장)

| # | id | 제목 | 내용 (택한 방식 · 이유) |
|---|---|---|---|
| 5 | `p2` | 계약 관리 | 파트 표지. 아래 한 줄: 계약 상대방·기간을 입력·갱신하고 계약서를 관리하는 기능을 만들었다 |
| 6 | `c-round` | 계약 정보는 계약 회차에 저장 | 지점마다 회차(1, 2, 3…)를 두고 회차마다 상대방·시작일·종료일·계약서를 저장한다. 지점 화면에는 가장 최근 회차가 보인다. **이유**: 갱신할 때마다 그때의 계약서와 기간을 함께 남겨야 지난 계약을 확인할 수 있다. 지점에는 계약 칸을 두지 않는다 — 같은 값을 두 곳에 두지 않기 위해. 계약 파일은 계약 화면에서만 다룬다 — 계약서에 접근하는 경로를 하나로 두기 위해 |
| 7 | `c-files` | 계약서 종류별 처리 | 표(종류 · 처리 · 이유): **계약서** — 지점 등록·갱신 때 필수, 갱신하면 새 회차 / 계약 정보는 계약서를 근거로 입력하므로. **해지 합의서** — 종료 확정 전에 필수(다음 장) / 종료의 근거 문서. **진행 중 회차 파일** — 교체만 가능, 옛 파일은 남김 / 계약 원본이 지워지지 않게. **지난 회차** — 읽기만 / 끝난 계약은 바뀌면 안 되므로. 아래 한 줄(권한): 쓰기는 본사만, 지점 관리자는 자기 지점 계약서 열람만, 열람할 때마다 기록, 내려받기 주소는 60초 |
| 8 | `c-termination` | 계약 종료 확정에 해지 합의서를 요구 | RFP에 없는 기능이라 추가한 이유를 밝힌다. 처리: 종료 확정 버튼은 해지 합의서를 올려야 켜진다. 중도 해지든 기간 만료든 같다(D69 결정 5 — 기간 경과 여부는 보지 않음). 확정 뒤에는 그 지점에 파일을 올릴 수 없다. **이유**: 종료 확정은 버튼 하나로 그 지점의 신규 회원 등록·예약·게시·채용·발령을 막고 진행 중 파견을 모두 끝낸다 — 상태를 되돌려도 끝난 파견은 복구하지 않는다(ADR-STF-07, D68). 이렇게 영향이 큰 처리를 계약상 종료가 확정됐다는 문서 없이 할 수 없게 했다. 종료일이 지나도 자동으로 종료하지 않는 것도 같은 이유(본사가 문서를 보고 확정) |
| 9 | `c-guard` | 입력 오류 방지 | 세 칸. **필수값·날짜 검사** — 종료일 필수, 종료 ≥ 시작, 갱신 회차의 시작일은 지난 회차보다 뒤, 지점 코드 중복 불가(회원번호·직원코드 생성에 쓰이므로). **상태는 자동으로 바꾸지 않음** — 종료 60일 전부터 "갱신 임박", 종료일이 지나면 "기간 종료(N일 경과)"로 표시만 하고 상태 변경은 본사가 한다. **변경 이력은 같은 트랜잭션에** — 등록·갱신·정정·상태 변경·파일 올리기가 실패하면 이력도 남지 않는다 |
| 10 | `c-limit` | 한계: 계약서 내용은 시스템이 검증하지 않는다 | 두 칸. **시스템이 확인하는 것**: 파일 형식·용량, 필수값·날짜 규칙, 종료 확정 전 해지 합의서가 있는지. **확인하지 못하는 것**: 올린 파일이 그 지점의 맞는 문서인지, 입력값이 문서 내용과 같은지, 진짜 문서인지. 이유 한 줄씩: 자동 검증(OCR·AI)은 계약서를 외부 서비스로 보내야 해서 그 자체가 보안 위험이고, 사람 확인을 늘려도 실수나 의도적으로 잘못된 입력은 남는다. 그래서 막는 대신 **추적할 수 있게** 남긴다 — 누가 언제 올리고 입력했는지(변경 이력), 누가 열어 봤는지(열람 기록), 원본 파일(회차에 보존, 입력값과 대조 가능) |
| 11 | `c-retention` | 계약 파일 보존 | 보존 기간: 회차가 끝난 날부터 시스템 3년, 이후 실물 7년(사용자 결정). 본사가 파일마다 [실물 이관 완료]를 표시하고, 표시해도 보존 기간 동안은 열람된다. 시스템 파일은 "이관 완료 + 보존 기간 지남"일 때만 본사가 [보존 끝난 파일 정리]로 지운다. 보존 끝 6개월 전부터 미이관 파일을 처리 대기함에 띄운다. **이유**: 보존 기간 안에는 시스템에서 열 수 있어야 하고, 지우는 일은 사람이 확인한 뒤 누가 지웠는지 남겨야 한다. 정리가 실패하면 전부 되돌린다 |
| 12 | `c-shot` | 지점 상세 계약 회차 화면 | 캡처 1장: 계약 회차 표(회차·계약서·해지 합의서·보존 끝·이관 상태), 마포점. 요점 3개는 6~11장 내용을 짧게 |

### PART 03 동시성 점검 (3장)

세 곳 중 두 곳은 겹칠 수 있는 요청을 잠가서 순서대로 처리한 것이 전부다 — 특별한 기법이 아니므로 한 장으로 묶는다. 잠금으로 해결되지 않는 회차 번호 확인만 따로 한 장을 둔다.

| # | id | 제목 | 내용 |
|---|---|---|---|
| 13 | `p3` | 동시성 점검 | 파트 표지. 아래 한 줄: 쓰기 API 전부에서 "읽은 뒤 쓰기 전에 다른 요청이 끼어들 수 있는가"를 확인했고, 세 곳을 고쳤다 |
| 14 | `conc-lock` | 겹칠 수 있는 요청은 잠가서 순서대로 | 두 줄 표(문제 · 처리): **계약 종료 확정 ↔ 회원 등록·예약 등** — 종료 판정을 트랜잭션 밖에서 미리 읽어 종료된 지점에 새 데이터가 저장됨 → 쓰기 트랜잭션 안에서 지점 행을 잠그고 읽음. 공유 잠금으로 한 이유: 같은 지점의 평소 쓰기끼리는 서로 기다리지 않게. **퇴사 ↔ 파견 발령** — 퇴사자에게 파견이 남거나 동시 발령 한쪽이 서버 오류 → 두 처리 모두 직원 행을 잠금. |
| 15 | `conc-round` | 잠금으로 안 되는 곳 — 계약 정정의 회차 번호 | 문제: 1회차 화면을 열어 둔 사이 다른 사람이 갱신해 2회차가 생기면, 정정·파일 교체가 2회차에 들어갔다(저장 자체는 이미 잠금으로 순서대로였다 — 문제는 순서가 아니라 대상). 처리: 화면을 연 때의 회차 번호를 요청에 함께 보내고, 지금 회차와 다르면 거절하고 다시 열라고 안내한다. 잠금이 아닌 이유: 사람이 화면을 보는 시간 동안 DB 잠금을 유지할 수 없다 |

## Q&A 대비

- 내용 검증 한계(c-limit) 관련 검토 중인 안(미정·미구현 — 구현한 것처럼 말하지 않는다): 종료 확정·갱신만 다른 본사 계정이 문서와 입력값을 대조해 확인해야 반영되는 이중 확인(스키마 변경·본사 계정 2개 필요), 또는 확정 화면에서 문서와 입력값을 나란히 보여 주고 대조 체크를 받는 방식. 위조 여부는 전자계약·전자서명 연동 없이는 확인할 수 없어 범위 밖.

- **발표에서 언급하지 않는 것(사용자, 2026-11-02)**: D70 "하지 않은 것"(같은 요청 두 번 처리 등)은 슬라이드·노트·Q&A 답변에서 꺼내지 않는다. 나중에 고친다.
- 해지 합의서라는 이름: 기간 만료로 끝날 때도 같은 파일 종류(해지 합의서)를 요구한다. 실무에서 만료 종료 때 쓰는 문서(종료 확인서·갱신 거절 통지 등)와 이름이 다를 수 있다 — 슬라이드 표현은 사용자 확인.

- 동시성 수정 검증: 재현 테스트 13건을 먼저 만들어 고치기 전 코드에서 12건 실패(대조군 1건 통과)를 확인한 뒤 고쳤다(D70, log/194). 잠금 순서(직원 → 지점)와 계약 종료 처리(지점 → 파견)가 엇갈리지 않아 교착 없음.

- 이전 설계·버린 대안(슬라이드에 넣지 않음): 계약 이력을 지점 행 + 변경 이력으로만 두는 안(D68)에서 회차 테이블로 바꿈(D69). 계약서를 문서 관리에 두는 안은 문서 API마다 계약서 제외 조건이 필요해 택하지 않음. 실물 이관 = 즉시 삭제였던 설계를 이관 표시와 정리로 나눔(D71). 정리 주체는 조회 시 자동·매일 예약 작업 대신 본사 버튼(D71 대안). 종료 판정은 실DB 이전 시기의 임시 방식(D29)을 대체(D70).

- 화면 검증: 계약 화면은 화면 자동 테스트 2건이 본다 — 새 계약서로 갱신 → 회차·계약 이력 확인, 계약서와 함께 새 지점 등록(`e2e/tests/admin-hq.spec.ts`). 정정·종료 확정·계약서 열람 화면과 보존 화면(D71, 로컬 미리보기만)은 화면 자동 테스트 밖 — API 테스트로만 검증. 회차 번호 거절 안내는 운영 화면에서 직접 띄워 보지 않았다(log/194).
