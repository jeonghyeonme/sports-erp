## 발표 조건

- **형식**: 발표자가 말하는 발표(사용자, 2026-11-09). 장마다 메시지 하나, 말할 내용은 발표자 노트에.
- **시간**: 15분 안팎 → 내용 장 약 14장 + 장 구분 4장 + 표지·순서·마무리.
- **청중**: 개발 지식이 있는 사람(4-0 §3). 10주차까지 발표를 들은 사람으로 가정하되, 장마다 혼자 읽어도 맥락이 서게.
- **시연**: 라이브 데모 없음 — 캡처로(사용자, 2026-11-09). 캡처는 로컬 DB에 `seed:demo`를 다시 얹고 찍는다(4-0 §5).
- **이번 발표만의 전제**: RFP 충족률 산정 방식을 바꿨다(D76, 81% → 94%) — 바꾼 사실과 옛 값을 함께 보인다(사용자 요청).

## 서사

**10주차의 "다음 할 일" 세 개(문서 파일 · 사용감 · 회원 앱 재검토) 중 두 개를 끝냈다 — 사용감은 "느낌"이 아니라 작업 단계를 재서 줄였고, 그 과정에서 목록 일관화·운영 실적 차트까지 갔다. 마지막으로 RFP 충족률을 정직한 분모로 다시 셌다.**

## Q&A 대비 (슬라이드에는 넣지 않음)

- **"94%는 부풀린 것 아닌가"** — 분모에서 뺀 건 이 프로젝트가 할 수 없는 조항(발주기관 승인·납품 계약·대면 교육 등)뿐이고 건수(10개)를 표에 그대로 둔다. 하지 않기로 한 3개(의도적 제외)는 분모에 남겼다. 옛 방식 값은 81%(D76).
- **단계 수의 한계** — 가장 짧은 정상 경로의 누름·입력 수다. 화면을 읽고 찾는 시간, 서버 대기, 잘못 누르기는 세지 않았다(log/198).
- **검증 범위** — 직원·강사·문서 표 정렬, 자산·업무지원 검색·정렬 화면, 직원 상세 인사서류 열기, 900px 이하 폭은 화면 자동 테스트가 없다(API는 테스트). 운영 저장소 업로드·차트는 사용자가 운영에서 확인(2026-11-09).
- **확인 창 3곳·모달 접근성**(D74), **변경 이력 검색**(D44 원칙 — 이름을 복사하지 않고 대상 id로 거른다).
- **회원 앱 형태 재검토**는 하지 않았다 — 발표 뒤 선택 과제(D67 ③).
- **업무지원 대기 수**: 처리 대기함(요청+처리중)과 목록 기본 필터(요청)가 다르게 셈 — 알고 있고 발표 뒤.
