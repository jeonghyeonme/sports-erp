# PG(결제대행) 연계 가능 여부 확인

> RFP UI 보안 "결제 시스템의 금융·보안기관 연계 가능 여부 확인"(요구사항추적표 N7-3) 대응. 지금 결제는 모의 결제(D5·D6)이고, 실 PG를 붙일 자리는 예약및결제 ADR-RSV-03(`PaymentGateway` 어댑터)이다. 경위는 log/165.
> **확인 방식**: 문서 조사(2026-10-22). 이 세션 환경은 PG 개발자 문서·API 주소에 접속할 수 없어(DNS 차단) **테스트 키로 실제 승인 호출은 하지 않았다** — 판정이 "구현"이 아니라 "조정"인 이유다. 실제 호출 확인은 아래 §4 순서로 사용자 PC에서 한다. 키 정책은 토스페이먼츠 자체 글로 확인했고, §2의 연동 순서(성공 주소 → 서버 승인 API)는 PG 공개 연동 방식에 대한 작성자 지식이다 — 개발자 문서 원문과 대조하지 못했다(§4에서 함께 확인).

## 1. 결론

| 질문 | 답 | 근거 |
|---|---|---|
| 이 구조(서버 없는 화면 + Lambda api)에 PG를 붙일 수 있나 | **된다.** 결제 화면은 PG가 띄우고(결제창·위젯), 우리 서버는 결과 확인(승인 API)만 부른다 | §2 |
| 카드번호가 우리 서버·DB를 지나가나 | 지나가지 않는다 — 카드 정보는 사용자 브라우저와 PG 사이에서만 오간다. 우리는 결제 키·주문 번호·금액만 받는다 | §2, PG 결제창 방식 |
| 계약 없이 개발할 수 있나 | 된다 — 토스페이먼츠는 회원가입만으로 "개발자용 테스트상점" 테스트 키를 준다(실제 돈은 나가지 않는다) | [토스페이먼츠 — API 키 확인](https://www.tosspayments.com/blog/articles/29831) |
| 실서비스에 무엇이 더 필요한가 | 사업자등록·PG 가맹 계약과 심사(판매 서비스가 심사 기준에 맞는지) → 라이브 키 발급. 금융기관(카드사) 연계는 PG가 맡는다 — 가맹점은 전자금융업 등록 대상이 아니다 | §3 |
| 우리 코드에서 바뀌는 곳 | 결제 승인·취소의 어댑터 한 곳(ADR-RSV-03). 예약·정원·환불 규칙(ADR-RSV-01·07)은 그대로 | §2 |

## 2. 연계 구조 (토스페이먼츠 결제위젯 기준, 다른 PG도 같은 모양)

1. 회원 웹 결제 화면이 PG의 결제 위젯(클라이언트 키)을 띄우고 주문 번호·금액을 넘긴다.
2. 사용자가 PG 화면에서 카드·간편결제를 고르고 인증한다(카드 정보는 PG로만 간다).
3. PG가 회원 웹의 성공 주소로 돌려보내며 결제 키·주문 번호·금액을 붙인다.
4. api가 **시크릿 키로 승인 API를 부른다** — 이때 금액이 우리 DB의 예약 금액과 같은지 먼저 본다(화면이 보낸 금액을 믿지 않는다). 지금 모의 결제의 "승인" 자리가 여기다.
5. 승인되면 지금과 같은 트랜잭션에서 결제 PAID·예약 확정(ADR-RSV-07의 행 잠금 순서 유지). 취소는 PG 취소 API → 지금의 환불 규칙.

어댑터 모양(ADR-RSV-03): `approve(orderId, paymentKey, amount)`·`cancel(paymentKey, reason, amount?)` — 모의 구현과 PG 구현이 같은 인터페이스. 시크릿 키는 Lambda 환경변수(다른 비밀값과 같은 경로, security-plan §4). 클라이언트 키와 시크릿 키는 같은 상점의 한 세트로 써야 하고 테스트·라이브 키를 섞으면 거절된다(같은 출처).

## 3. 실서비스 전에 필요한 것 (발주처 몫)

- 사업자등록, PG 가맹 신청·심사(판매 서비스·환불 규정 확인), 정산 계좌 — 계약 후 상점 아이디(MID)에 테스트·라이브 키가 함께 나온다.
- 개인정보처리방침에 결제 위탁(PG)을 추가(security-plan §7 수탁자 표, D51 처리방침 화면).
- 환불 규정을 이용약관에 공개(지금 규칙: 회차 24시간 전 전액, 예약및결제 A-6).

## 4. 실제 호출 확인 순서 (사용자 PC — 이 세션은 PG 주소에 접속 불가)

1. 토스페이먼츠 회원가입 → 개발자센터에서 테스트 클라이언트·시크릿 키 확인.
2. 테스트 키로 결제위젯 → 성공 주소 → 승인 API 1회(테스트 카드) — 응답의 결제 키·상태를 기록.
3. 같은 결제를 취소 API로 취소.
4. 결과를 진행 기록에 남기면 N7-3을 "구현"으로 바꾼다.
