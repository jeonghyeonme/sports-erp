# 트래픽·인프라 관점 도메인 재검토 (2026-09-28 착수, 진행 중)

> **상태**: 진행 중 — 6개 도메인 1차 스캔 완료(2026-09-28), 나머지 3개(권한관리·인사정보관리·예약및결제) 및 확정 ADR 작성 남음. 아래 항목은 전부 **Driver(왜 문제가 되는가)만 정리된 상태**이고 대안 비교·결정은 아직이다 — 도메인 문서의 정식 ADR 형식(컨텍스트→대안→결정→결과)이 아니라 "후보 이슈"로 남겨두는 이유다.
>
> **계기**: 4주차 발표자료 준비 중, 발표자가 Part A(도메인 사이클 재검토)가 "기능 구현 관점"(RFP 요구 대비 빠진 것 — 지점 격리·계약종료 차단 같은 불변식 누락)에 치우쳐 있고, 같은 주 Part B/C가 다루는 인프라 서사(Render 무료 티어 CPU 스로틀링, k6 부하테스트, Lambda 이관 계획)와 관점이 안 맞는다고 지적했다. "각 도메인을 트래픽·인프라·시스템 아키텍처 흐름 관점에서 다시 보고, 거기서 나온 문제를 ADR로 검토하자"는 요청에 따라 이 문서를 만든다.
>
> **방법론**: 각 도메인의 목록/조회 엔드포인트와 쓰기 경로 코드를 직접 읽어 네 가지를 찾는다 — ① N+1 조회 패턴(목록 항목마다 다른 배열을 다시 스캔) ② 캐싱·ETag 없이 반복 호출될 폴링 대상 ③ 데이터가 쌓일수록 비용이 계속 늘어나는, 경계 없는 전체 스캔 ④ 동시 쓰기 시 경합하거나 매번 재계산되는 비용. 이번 주 k6로 이미 확인한 "공유 CPU 경합"(D24)과는 **다른 클래스의 문제**라는 게 핵심 — 그건 여러 요청이 하나의 공유 CPU를 다투는 문제였고, 이건 **요청 하나의 계산량 자체가 크거나 데이터 규모에 비례해 계속 나빠지는 문제**다. 그래서 Lambda로 옮겨도(D26 계획) 저절로 없어지지 않는다 — 오히려 Lambda의 동시 실행이 늘면 이런 무거운 스캔이 더 많이 동시에 돌게 돼, migration 슬라이드의 "남은 한계 ① DB 용량"을 더 빨리 만나게 만드는 요인이다.
>
> **다음(하네스 검토 대상)**: 이 목록은 아직 코드를 읽고 추론한 "후보"다 — 실제로 병목이 되는지는 각 도메인이 Prisma로 이관된 뒤 실제 DB 쿼리 패턴 위에서 부하테스트(k6)로 재검증해야 확정된다. 도메인별 Prisma 이관 시 이 목록을 체크리스트로 같이 검토하고, 쿼리 설계(인덱스, 페이지네이션, N+1 제거)에 반영할 것. 재검증 결과가 나오면 이 문서의 각 항목을 도메인 문서의 정식 ADR로 승격한다.

## 도메인별 후보 이슈

### 근태관리 — 심각도: 높음

| 항목 | 내용 |
|---|---|
| 근거 | `mock-data.service.ts:1622-1650`(`previewAbsences`), `:1656-1657`(`confirmAbsences`) |
| 무엇이 문제인가 | 후보 직원 × 이번 달 날짜 수의 이중 루프 안에서, 루프마다 전체 근태기록·휴가기록을 다시 `.some()` 스캔한다 — 비용이 사실상 O(직원×일수×누적기록). 근태 기록이 쌓일수록, 지점이 늘수록 계속 나빠진다 |
| 더 나쁜 지점 | 결근 확정 API(`POST /attendance/absence-confirm`, ADR-ATT-02)가 이 무거운 `previewAbsences()`를 **쓰기 경로 안에서 동기적으로 재실행**한다 |
| 검토 방향(미결정) | 월별 집계를 사전 계산해 캐싱하거나, 스캔 범위를 "해당 월"로 제한하는 인덱스/쿼리 설계 검토 필요 |
| 진행(2026-09-29, 2-1 D33) | DB 이관 때 **스캔 범위를 "해당 월·후보 직원"으로 제한**했다 — 후보 직원·파견 이력·그 달 근태(`staffId, date` 인덱스)·그 달과 겹치는 승인 휴가를 쿼리 4개로 한 번씩 읽고 메모리 Set으로 판정. 누적 기록이 늘어도 비용은 그 달 크기에 묶인다. 월별 집계 사전 계산(캐싱)은 쓰기마다 무효화가 필요해 보류. 확정 API의 동기 재계산은 "지금 이 순간의 후보"가 멱등의 근거라 유지 |

| 항목 | 내용 |

| 검토 방향(미결정) | 짧은 TTL 캐시(예: 5~10초) 또는 클라이언트 폴링 간격 제한, 지점 조회 N+1 제거(join/미리 로드) |

## 범위 밖 — 아직 이 관점으로 다시 안 본 도메인

권한관리·인사정보관리·예약및결제(원래 "상 우선순위" 4개 중 회원관리를 제외한 나머지 3개)는 이번 스캔에 포함되지 않았다. 예약및결제는 이미 D6(동시 예약 `FOR UPDATE` 락 계획)으로 트래픽 관점 검토가 일부 되어 있지만, 이 문서의 방법론(N+1·폴링·누적 스캔)으로 다시 훑지는 않았다 — 다음 순번 후보.
