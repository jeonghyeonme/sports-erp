# 시스템 개요 — 구성·인증·API 컨벤션·비기능·폴더·로드맵 (옛 1-1 공통설계서)

> 옛 1-1 공통설계서에서 공유 엔티티(§2 → [entities.md](entities.md))를 뺀 나머지다. 절 번호는 옛 1-1 공통설계서 그대로다(2026-10-01 이관). §7 로드맵은 2026-09 초기 계획이라 역사 기록으로 읽을 것 — 현재 상태는 [STATUS.md](../STATUS.md).

## 1. 시스템 구성

```
사용자
 ├─ 본사 관리자(SUPER_ADMIN)  ─┐
 ├─ 지점 관리자(BRANCH_ADMIN) ─┼─→  admin-web (React, 브라우저)
 └─ 회원(MEMBER)              ──→  member-web (React, 모바일 웹 — 개발 예정, D40)
                                          │
                                          ▼
                                   api (NestJS, REST)
                                          │
                                          ▼
                                  PostgreSQL (Prisma)
```

- 클라이언트 2종(admin-web, member-web)이 **동일한 REST API**를 공유합니다(둘 다 같은 Cloudflare Worker 뒤 — D40). 화면/UX만 다르고 도메인 로직은 API 서버에 집중시켜, "같은 데이터를 역할에 따라 다르게 보여준다"는 원칙을 지킵니다.
- 파일(이미지 등) 저장은 로컬 디스크 또는 무료 오브젝트 스토리지(예: Supabase Storage, Cloudflare R2 무료 티어) 중 택1. 포트폴리오 규모에서는 로컬 `uploads/` 디렉터리 + 정적 서빙으로도 충분합니다.

### 1-1. 사업 맥락 (원본 RFP 재해석)

1-2~1-9 문서는 지금까지 "여러 지점을 가진 헬스장 체인 본사 시스템"이라는 일반화된 틀로 설계되어 있었습니다. 그런데 원본 제안요청서(`reference/제안요청서 원본.pdf`, Ⅲ.사업개요~Ⅳ.과업내용)를 다시 읽어보면, 스포이즘의 실제 사업구조는 훨씬 구체적이고, 이 차이가 데이터 모델과 기능 우선순위에 실질적인 영향을 줍니다. **이 시스템은 ERP라는 이름과 달리 회계·재고·구매 같은 전통적 ERP 모듈은 다루지 않고, "다지점 위탁운영 특화 회원관리·운영 플랫폼"에 가깝습니다** — RFP 원문도 "업계에서 회원관리 프로그램을 'ERP 시스템'이라고 칭함"이라고 스스로 밝히고 있습니다.

**스포이즘은 헬스장 체인 본사가 아니라 "아파트·오피스텔 커뮤니티 시설 위탁운영사"입니다.** 전국 98개 업장(2022년 RFP 작성 시점 기준)을 이미 보유하고 있고(이 프로젝트의 대상은 그중 수도권 83곳 — D40), "각 지사 개념으로 퍼져있는" 조직 구조에 직원이 "해당 지역 또는 본사 파견 형태로" 투입됩니다. 즉 이 시스템의 `Branch`는 단순히 "회사가 소유한 지점"이 아니라 **"아파트 입주자대표회의/관리사무소와 맺은 위탁운영 계약 현장"**입니다(§2-1에서 계약 관련 필드로 구체화).

**RFP가 명시한, 기존(타사 벤더) ERP를 계속 쓰지 않으려는 이유** — 이 프로젝트가 왜 "직접 개발"이어야 하는지의 진짜 근거입니다:
1. 기존 ERP 회사의 시스템을 쓰면 매출·영업 노하우가 벤더사에 노출되어 경쟁사가 생기는 구조적 리스크가 있음
2. 기존 ERP 회사가 도산하면 그 피해가 고스란히 스포이즘의 신뢰성 타격으로 이어짐
3. 범용 시스템이라 "아파트 커뮤니티 시설 위탁운영"이라는 스포이즘의 사업 특수성에 맞지 않음
4. **시스템 불안정 → 민원 발생 → 위탁 업장 계약해지**로 이어지는 구조 — 즉 이 프로젝트에서 "안정성"은 단순 UX 품질이 아니라 **위탁계약 유지 여부와 직결되는 사업 리스크**입니다

**이 시스템의 숨은 용도 — 신규 계약 수주 영업 도구**: RFP는 "각종 사업공모(스포츠위탁사업)에서 현장발표(PT)를 할 때 최첨단 회원관리 시스템을 적용할 수 있다는 강점"을 자체 개발의 이유로 명시합니다. 즉 이 시스템은 내부 운영툴이면서 동시에, 신규 아파트 단지의 위탁운영권을 따내기 위한 입찰 발표(PT) 자리에서 "우리는 검증된 자체 시스템이 있다"를 보여주는 **영업 무기**이기도 합니다. 이 관점은 docs/decisions/D18.md, 그리고 신규 문서 [13_차별화전략](../reference/차별화전략.md)에서 구체적인 기능 제안으로 이어집니다.

이 재해석이 1-1~1-9 문서의 기존 설계를 뒤엎지는 않습니다 — 지점 격리(D2), RBAC(D1), 회원관리 중심 설계는 이미 이 맥락과 부합합니다. 다만 **Branch를 "이름/주소만 있는 얕은 엔티티"로 둔 것과, 이 시스템의 "영업 도구"로서의 역할을 설계에 전혀 반영하지 않은 것**이 실제 갭이며, 아래 §2-1과 차별화전략에서 보완합니다.

**추가 재해석(2026-09-08) — 직원도 "지점 소속"이 아니라 "본사 소속, 지점에 파견"**: 같은 절(Ⅳ.과업내용 1.과업 목적, p.3~4)은 "당사의 조직 구조는 각 지사 개념으로 퍼져있는 형태이기 때문에 **행정 및 트레이너들 역시** 해당 지역 또는 본사 파견 형태로 직원이 투입되고 있는 상황"이라고 명시합니다. "행정"(관리자급)과 "트레이너"를 나란히 언급하므로 BRANCH_ADMIN·STAFF 모두 대상입니다. 즉 `Branch`가 위탁계약 현장이듯, `Staff`도 "지점이 직접 고용한 인력"이 아니라 **"스포이즘 본사가 고용해 현장에 파견한 인력"**입니다. §2-2에서 데이터 모델로 구체화합니다.

## 3. 인증 · 인가(RBAC) 설계

### 3.1 계정 구조

- `Account` 테이블 하나로 로그인 주체를 통합 관리 (email/phone + passwordHash + role + isActive)
- `role ∈ { SUPER_ADMIN, BRANCH_ADMIN, STAFF, MEMBER }` — `STAFF`는 지점 소속 일반 직원(트레이너 등) 로그인용으로, `BRANCH_ADMIN`과 달리 관리 권한 없이 본인 근태·휴가·업무일지만 셀프서비스합니다(권한관리 A-7)
- Staff/Member 테이블은 Account와 1:1로 연결된 "역할별 상세 프로필" — `BRANCH_ADMIN`과 `STAFF` 모두 Staff 레코드를 가지며, 관리 권한 유무는 Account.role로만 구분됩니다

### 3.2 토큰 정책

| 토큰 | 수명 | 저장 위치 |
|---|---|---|
| Access Token (JWT) | 30분 | 클라이언트 메모리/헤더(Authorization: Bearer) |
| Refresh Token | 14일 | httpOnly Cookie(admin-web, member-web 모두 — 같은 출처) |

- 비밀번호는 bcrypt(cost 10~12)로 해시 저장
- 로그인 5회 연속 실패 시 15분 잠금(간단한 무차별대입 방지 — 포트폴리오 완성도용 최소 구현)
- `isActive=false`(퇴사/탈퇴)인 계정은 로그인 시점과 매 요청의 인증 미들웨어에서 즉시 차단 → 원본 요구사항 "퇴사처리 이후 시스템 접근 통제" 충족

### 3.3 인가(Authorization) 구현 방식 (NestJS 기준)

```
@Roles('SUPER_ADMIN', 'BRANCH_ADMIN')
@UseGuards(JwtAuthGuard, RolesGuard, BranchScopeGuard)
```

- `JwtAuthGuard`: 토큰 검증, `req.user`(accountId, role, branchId) 주입
- `RolesGuard`: 데코레이터에 선언된 역할만 허용
- `BranchScopeGuard`: BRANCH_ADMIN 요청에 대해 쿼리/파라미터의 `branchId`가 본인 소속과 일치하는지 검사 (불일치 시 403). 서비스 레이어에서도 이중으로 `where: { branchId: user.branchId }` 강제 적용(가드 우회 방지용 2중 안전장치)

### 3.4 권한 매트릭스(요약 — 상세는 권한관리 문서)

| 리소스 | SUPER_ADMIN | BRANCH_ADMIN | STAFF | MEMBER |
|---|---|---|---|---|
| 지점(Branch) | CRUD 전체 | 조회(본인 지점만) | 조회(본인 지점만) | - |
| 직원/근태 | 채용·파견 발령 CRUD 전체(§2-2) | 현재 파견된 직원 대상 일상 관리(수정·퇴사), 채용·파견 발령은 불가 | 본인 근태/휴가/업무일지만 CRUD, 타 직원 정보 조회 불가 | - |
| 회원 | 조회 전체 | CRUD(본인 지점만) | - | 본인 정보 조회/수정 |
| 예약/결제 | 조회 전체 | 조회(본인 지점만) | - | 본인 예약 CRUD |
| 게시판 | 본사→현장 작성 | 조회 + 현장→회원 작성 | 조회만 | 조회만 |
| 혼잡도 | 조회 전체 | 조회+수동보정(본인 지점) | 조회만 | 조회만 |

## 4. API 컨벤션

- Base URL: `/api/v1`
- 인증: `Authorization: Bearer <accessToken>`
- 응답 포맷(공통 envelope):
```json
{ "success": true, "data": { ... }, "meta": { "page": 1, "pageSize": 20, "total": 137 } }
```
```json
{ "success": false, "error": { "code": "MEMBER_NOT_FOUND", "message": "..." } }
```
- 목록 API는 페이지네이션 필수(`page`, `pageSize`, 기본 20/최대 100)
- 날짜/시간은 ISO 8601(UTC 저장) + 클라이언트에서 KST 변환 표시
- 소프트 삭제 원칙: 회원/직원 등 핵심 엔티티는 물리 삭제 대신 `isActive=false`(또는 상태값) 처리로 이력 보존(결제/예약 참조 무결성 유지). Program은 단순 불리언 대신 `status`(PREPARING/RUNNING/PAUSED/ENDED) 생애주기로 관리 — 지점별 "진행중 프로그램" 파악이 이 필드 하나로 가능해짐(강사프로그램게시 A-3)

## 5. 공통 비기능 설계 (성능/데이터관리/보안 요구사항의 실현 방식)

원본 요구사항의 "CPU 90% 이하", "메모리 85% 이하" 같은 실측 인프라 목표는 포트폴리오 규모에서 의미가 없으므로, **아래 설계 원칙으로 대체**하고 문서/발표에서는 "확장을 고려한 설계"로 어필합니다.

| 원본 요구사항 | 대체 구현 |
|---|---|
| 시스템 가용성/성능 | 목록 API 페이지네이션, 자주 조회되는 값(혼잡도 등) 캐싱(선택: Redis 또는 인메모리), DB 인덱스 설계(각 문서에 명시) |
| 데이터 관리방안(변경이력) | `AuditLog` 테이블 — 주요 쓰기 작업(회원 정보 수정, 예약 취소, 결제 상태 변경 등)마다 기록 |
| 오류 데이터 진단 | API 레벨 유효성 검증(class-validator), DB 제약조건(FK, NOT NULL, CHECK) |
| 온라인 도움말 / 상호작용 메시지 | 프론트엔드 공통 Toast/Modal 컴포넌트로 성공/실패 메시지 일관 처리. 툴팁 대신 화면별 도움말 패널(역할별 순서·오류 해결)과 오류 아래 해결 한 줄(log/089) |
| 사용자 인터페이스 보안 | 응답 DTO에서 비밀번호 해시 등 민감정보 제외(class-transformer `@Exclude`), 전화번호 등은 관리자 화면에서도 마스킹 옵션 |
| 보안요건(개인정보보호법 26조) | 개인정보 처리방침 문서화(형식적 산출물), 접근로그(AuditLog)로 오남용 추적 가능 |

## 7. 개발 로드맵 (1인 개발 기준, 총 8~10주 권장)

기능이 8개+공통 영역으로 많기 때문에, **모든 기능을 동시에 "완벽히" 만들려 하지 않고 세로로(수직으로) 하나씩 끝내는 방식**을 권장합니다. 각 Phase 종료 시점에 "실제로 눌러볼 수 있는 데모"가 나오는 것이 목표입니다.

| Phase | 기간(권장) | 범위 | 산출물 |
|---|---|---|---|
| Phase 0 | 3~5일 | 프로젝트 셋업, DB 스키마 전체 설계, 인증(로그인/토큰), 배포 파이프라인 뼈대 | 로그인만 되는 빈 앱 |
| Phase 1 | 1.5주 | 01 권한관리 + 05 회원관리(핵심) | 관리자가 회원 CRUD하는 웹 |
| Phase 2 | 1주 | 02 인사정보관리 + 03 근태관리 | 직원/근태 관리 |
| Phase 3 | 1.5주 | 07 강사·프로그램 게시 + 06 예약/결제(모의) | 회원 모바일 웹에서 예약 가능 |
| Phase 4 | 1주 | 04 게시판 + 08 혼잡도관리 | 공지/혼잡도까지 완성 |
| Phase 5 | 1~1.5주 | 통합 테스트, UI 폴리싱, 배포, 발표자료(ERD/시연 시나리오) | 최종 데모 |
| Phase 6(확장) | 1.5주 | [10 기업구조및자원관리분석](../reference/기업구조및관리시스템분석.md) — 자산·비품관리, 문서관리 · [06 예약및결제](../domains/예약및결제.md) — 부가세 분리, 매출 집계, 강사 정산 | 산출물2(기업 분석 자료) 대응 + 재무 연계 보강 — 원본 필수 요구사항(과업3)이 아니라 추가 스코프이므로 Phase 0~5 이후 후순위 |

각 기능 문서(1-2~1-9, 확장 범위인 1-10 포함)의 "Phase 1(필수) / Phase 2(선택)" 구분을 참고해, 시간이 부족하면 각 기능의 **Phase 2 항목부터 먼저 쳐낼 것**을 권장합니다.
