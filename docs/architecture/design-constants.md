# 공용 산정 상수 (Q-01 규모 산정)

> **상태**: 초안 (2026-09-22).
> **용도**: 도메인 사이클([process/03_도메인_사이클_템플릿.md](../process/03_도메인_사이클_템플릿.md)) 3단계(수치화)에서 매번 새로 리서치하지 않고 여기 값을 가져다 쓴다. **숫자를 다시 도출하지 말 것** — 가정이 틀렸다고 생각되면 이 문서를 고치고, 참조하는 모든 도메인 문서에 그 사실을 알린다.
> **결정 근거**: 사용자 확정 3건 — ① 실측 데이터 없음, 전부 산정으로 추정 ② 설계 목표는 3년 후 목표치 기준 ③ 대표 업장 규모 1,000세대.

## 산정 체인

| 단계 | 계산 | 값 | 근거 유형 |
|---|---|---|---|
| ① 대표 단지 상주인구 | 1,000세대 × 2.2명/가구 | **2,200명** | 실측: 2023 인구주택총조사 가구원수 분포(1인35.5%·2인28.8%·3인19.0%·4인이상16.8%, 4인이상=4.3인 가정)의 가중평균 |
| ② 지점당 등록 회원 수 | ③ 100명/일 × 7일 ÷ 주 2.5회 방문 | **≈280명** (상주인구의 약 13%) | **가정(약함)**: 하루 이용자(③)와 방문 빈도(주 2.5회, 헬스장 업계 경험칙)에서 역산(2026-10-06 D40). 문체부 2023 국민생활체육조사 민간체력단련장 이용경험률 42.1%가 상한 참고치. 이전 값 550명(등록률 25%)은 ③ 100명과 맞지 않아(주 1.3회 방문이 됨) 바꿨다 |
| ③ 일일 활성 방문자 | 사용자 추정 | **≈100명/일** | **가정(사용자 추정, 2026-10-06 D40)**: 아파트 커뮤니티 시설이 하루 100명을 넘기 어렵다고 봄. 이전 값 200명(방문율 36%, 헬스장 업계 경험칙)은 과했다 |
| ④ 피크 동시 재실자 | Little's Law(L=λW), 영업 18h·평균체류 70분·피크계수 2.5배 | **≈16명/지점** | 계산(Little's Law) + 가정(피크계수는 트래픽공학 관행 차용) |
| ⑤ 현재 전사 동시 재실 | 83개 업장(수도권, D40) × 16명 | **≈1,300명** | 계산 |
| ⑥ 3년 후 목표 | 연 10% 성장 가정(83→110개 업장) × 16명 | **≈1,760명** | **가정(제안값)**: RFP 산출물4 KPI(3년 신규계약 증가율)와 연결되지만 수치 자체는 제안 |
| ⑦ 전사 로그인 도착률 | 평균: 83곳 × ③ 100명 ÷ 영업 18h / 피크 시간대: 평균 × 2.5(④와 같은 피크계수) | **평균 ≈0.13명/초(7.7명/분) / 피크 시간대 ≈0.32명/초(19명/분)** | 계산 — 피크 시간대 값은 Little's Law 역산(⑤ 1,330명 ÷ 체류 70분)과 같다. "방문 1회 = 로그인 1회" 가정(약함, 아래 약한 고리). 2026-09-27 추가, 2026-10-06 평균·피크 분리 |
| ⑧ 순간 몰림 로그인 도착률 | ⑦ 피크 시간대 × 2.5(수업 시작 직전 등 분 단위 집중) | **≈0.79명/초(48명/분)** — 보수적 상한 | 계산 + 가정 — 피크계수를 **두 번** 곱한 값이라 평균의 약 6배다. 2026-10-06까지는 이 값을 "피크"로 썼는데, 시간대 피크(⑦)와 분 단위 몰림을 겹친 보수적 상한으로 고쳐 부른다 |
| ⑨ 동시 진행 중인 로그인 건수 | Little's Law 정방향: L=λW, λ=⑦ 피크·⑧ 몰림, W=로그인 1건 처리시간 | **Lambda 실측 로그인 p95 237ms 기준 피크 ≈0.08건·몰림 ≈0.19건** / 장애 상황(15.16초, 2026-09-27 Render 무료 티어 k6 p95) 기준 피크 ≈4.9건·몰림 ≈12건 | 계산 — **핵심 통찰**: 평소 트래픽은 결코 크지 않다(초당 1명 미만). 그런데 처리시간 W가 늘어나는 순간 Little's Law에 따라 동시 진행 건수 L도 그만큼 늘어난다 — "지연 → 동시 요청 누적 → CPU 경합 심화 → 더 심한 지연"으로 이어지는 **자기강화 루프**다. §31에서 관찰된 40 VU 램핑 중 응답시간이 완만히 늘지 않고 급격히 무너진 패턴(7.4s→15.16s→17.11s)이 이 구조와 정합적이다 |
| ⑩ 방문(로그인) 1회당 API 요청 수 | 회원 모바일 웹 화면 흐름: 로그인·내 정보·프로그램·회차·내 예약·예약·결제·공지·혼잡도 | **10건** (민감도 30건 — 혼잡도 새로고침 포함) | **가정(평균 방문) + 실측 범위**: 회원 웹 구현 후 로컬 Worker 경유 실측(2026-10-08, [log/085](../log/085.md)) — 혼잡도·공지만 보는 방문 3건, 재방문 +1(refresh·me), 기능을 다 쓰는 방문(로그인→공지 목록·상세→예약·결제→내 예약→내 정보) **11건**. 홈 카드 60초 캐시 적용 후 값. Worker 호출 = api 호출 + 깊은 경로 새로고침(D41). 평균이 어느 쪽에 가까운지는 실제 이용 패턴이 없어 10을 유지했다(사용자 결정 2026-10-08) — 11로 보면 ⑬ ≈10.1만으로 Workers 무료 한도를 넘으므로, Cloudflare 대시보드 실제 일일 요청이 9만을 넘으면 D40 재고 트리거와 함께 Workers 유료를 검토한다. 2026-09-30 D37 추가 |
| ⑪ 피크 API 도착률 | ⑦ 또는 ⑧ × ⑩ | **피크 시간대 ≈3.2 rps / 순간 몰림 ≈8 rps** · 3년 후(110곳) 피크 ≈4.2 rps·몰림 ≈10.6 rps · 민감도 30건 시 피크 ≈9.6 rps·몰림 ≈24 rps | 계산 — 2026-10-06 전에는 몰림 값(8 rps)을 "피크"로 썼다 |
| ⑫ 필요한 동시 실행 수(Lambda) | Little's Law L=λW, λ=⑪, W=Lambda 실측 p50 약 110ms([log/056](../log/056.md)) | **피크 ≈0.35칸 / 몰림 ≈0.9칸** · 3년 후 몰림 ≈1.2칸 · 민감도 몰림 ≈2.6칸 — 상한 10의 실질 처리 한계는 약 50 rps(실측) | 계산 — 상한 10은 관리자 웹과 회원 모바일 웹이 **함께** 쓴다. 같은 순간 11번째 요청은 503(2초 뒤 재시도). 설계 때 쓴 W=50ms 가정(처리 한계 200 rps)은 실측으로 대체. ⑨의 루프는 "L이 늘면 W가 는다"(공유 CPU)에서 생겼다. Lambda는 요청마다 CPU가 따로라 이 고리가 없고, 남는 공유 자원은 DB 커넥션이라 상한으로 묶는다(D37 결정 1) |
| ⑬ 일일 API 요청 수 | 지점 수 × ③ × ⑩ + 관리자 웹(계정 약 170명 × 하루 약 50건 ≈ 1만) | **≈9.3만/일(수도권 83개 지점)** / 98개 지점이면 ≈10.8만 | 계산 — Cloudflare Workers 무료 한도(10만/일, `/api/*`만 Worker를 거치고 정적 자산은 세지 않음) 안(93%). 98개 전체면 넘는다 → 지점 범위를 수도권으로 정한 근거(D40). **지점이 90곳을 넘으면 넘는다**(⑥ 3년 후 110곳이면 ≈12만) — 그때 Workers 유료(월 $5) 전환. 이전 값 19.6만(98개·200명)은 D37 §5 회원 앱 제외의 근거였다 |
| ⑭ 월 운영 비용 | ⑬ × 30일 = Lambda 요청 수, × 처리 시간(평균 약 0.12초) × 1GB = 연산량 | **지금 ≈월 $0.4**(Lambda 요청 ≈280만/월 — 무료 100만 초과분 요금 $0.2/백만, 연산 ≈33만 GB-s로 무료 40만 안, Workers 무료) / **3년 후 ≈월 $6**(Workers 유료 $5 + Lambda 요청 ≈360만/월·연산 ≈43만 GB-s 초과분) | 계산 — Supabase 무료 플랜 전제(⑮). 2026-10-06 추가 |
| ⑮ DB 저장 용량(Supabase 무료 500MB) | 하루 생기는 행 × 행 크기(인덱스 포함) | **refreshToken**: 로그인·갱신마다 1행(≈8천+/일, 행당 ≈300B) — 정리하지 않으면 **연 ≈1GB**, 발급 시 만료·폐기 토큰 정리(ADR-AUTH-04) 후에는 살아 있는 세션 수 이하(수 MB). **예약·결제**: 방문의 20%가 회차 예약이라 가정하면 ≈1,700건/일 × (예약+결제 2행) → 연 ≈0.3~0.4GB | 계산 + **가정(약함)**: 예약 비율 20%는 근거 없음. refreshToken 정리를 넣어도 예약·결제 이력만으로 **1~1.5년 안에 무료 용량에 닿는다** → 그 전에 이력 아카이빙이나 Supabase Pro(월 $25). 아카이빙은 프로젝트 기간 밖이라 범위 제외로 두었다(traffic-infra-review B4 분류 #19, 재고 트리거 DB 300MB). 2026-10-06 추가, 2026-10-07 참조 정정 |

## 약한 고리 (재검토 대상)

- **일일 방문자 100명**(③, 사용자 추정), **방문 빈도 주 2.5회**(②의 역산 근거), **3년 성장률 연 10%**(⑥) — 근거가 약하다. 실제 스포이즘 데이터를 확인할 수 있게 되면 이 문서를 갱신한다.
- **⑧·⑪의 몰림 값은 보수적 상한이다** — 피크계수 2.5를 시간대·분 단위로 두 번 곱했다. 판단(처리 한계 비교)은 몰림 값으로 하고, 평소 부하 설명은 피크 시간대 값으로 한다.
- ~~이 값은 동시 재실자이지 동시 API 요청자가 아니다. ... 이 배율은 아직 산정하지 않았다.~~ → **2026-09-27 ⑦~⑨로 해소**. 남은 약한 고리: "로그인 이벤트가 시설 도착과 1:1 대응한다"는 가정(약함) — 실제로는 예약 확인·PT 세션 조회 등으로 하루 중 여러 번 로그인할 수도, 반대로 refresh token(14일)으로 한 번 로그인하면 한동안 재로그인이 없을 수도 있다. member-app 출시 후 실제 로그인 로그가 쌓이면 갱신할 것.
- ⑨의 3년 후 버전: λ=⑥(1,760명)/70분≈25명/분, 피크≈1.05명/초, 장애 상황(15초) 동시 진행≈16건 — 지점 수가 늘수록 이 자기강화 루프의 임계점에 더 쉽게 도달한다는 뜻이다.
