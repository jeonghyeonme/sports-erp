# 데이터 정합성 — 어떤 규칙을 어느 계층이 강제하는가 (실DB 전환 전 정리)

> **상태**: DI-01·DI-03 결정·구현 완료(2026-09-29, D28). **DI-02는 결정 대기**(아래 대안 참고).
>
> **계기**: 사용자가 "최근 커밋에서 데이터 정합성 측면의 ADR을 뽑아 실DB로 전환하기 전에 적용하고 싶다"고 요청했다(2026-09-29). 9개 도메인 문서의 ADR 22개와 Tier2 규칙표에서 정합성 규칙을 모았고, 규칙마다 **"DB가 강제할 수 있는가, 있다면 어떤 수단으로"**를 기준으로 나눴다. 지금은 모든 규칙이 `MockDataService`의 앱 로직 한 겹으로만 지켜진다. 단일 Node 프로세스에서는 그걸로 충분했지만, Lambda 병렬 인스턴스(D26)에서는 "검사 후 쓰기" 사이 경합과 새 코드 경로의 검증 누락을 앱 한 겹으로 막을 수 없다.
>
> **관련**: [2-1_기술결정사항.md](../2.decisions/50_결정및이슈기록/2-1_기술결정사항.md) D26(실DB 전환 1단계)·D27(부분 unique·날짜)·D28(이 문서), [date-time-handling.md](./date-time-handling.md), [traffic-infra-review.md](./traffic-infra-review.md)(성능 관점 — 이 문서는 정확성 관점).

## 2. DI-01: 한 행 규칙은 DB CHECK로 이중화하되, 앱이 이미 검증하는 규칙만

- **컨텍스트**: 위 표의 "한 행 안에서 판정되는 규칙"은 지금 앱 한 겹이다. 앱은 친절한 에러 코드(400/409)를 내는 첫 방어선으로 필요하지만, 우회 경로(직접 SQL, 새 코드 경로의 검증 누락, 도메인을 Prisma로 옮기며 검증 하나를 빠뜨리는 실수)는 막지 못한다. 이 프로젝트는 이미 같은 이유로 "앱 체크 + 부분 unique 이중화"(ADR-RSV-02·STF-03·MEM-02)를 택했다.
- **대안**: A 앱만(현행) / B **앱 + DB CHECK 이중화, 앱이 검증하는 규칙만** / C 앱 검증이 없는 규칙까지 전부 CHECK
- **결정**: B. C를 뺀 이유: 앱이 검사하지 않는 규칙을 DB에만 걸면 사용자 입력 실수가 400이 아니라 **500(원인 불명 서버 에러)**으로 터진다. 규칙을 새로 만들 땐 앱 검증을 먼저 추가하고 CHECK를 따라 붙인다(§4 공백 표).
- **구현**: 마이그레이션 `20260929004339_d28_integrity_checks` — 14개 테이블 18개 CHECK. Prisma 5는 CHECK를 스키마로 표현하지 않지만 `migrate dev`가 지우지도 않는다(빈 마이그레이션 생성으로 확인). `schema.prisma` 상단 주석에 이 사실을 적었다.
- **검증**: 시드된 로컬 DB에서 18개 모두 위반 시도가 해당 제약 이름으로 거부되고, 정상 경계값(무료 프로그램 정원 없음, 소모품 수량 0, 고정자산 수량 1, 보존기한 있는 계약서, 비파트타임 휴무 요일, HQ 공지 비공개)은 통과함을 SQL로 확인. 전체 테스트 스위트에 변화 없음(기존 앱 로직과 충돌 없음). `integrity-helpers.spec.ts`에 Prisma 경로에서 CHECK가 거부하는 회귀 1건.
- **감수하는 것**: CHECK가 `schema.prisma`에 안 보인다. 규칙이 바뀌면 앱 검증과 마이그레이션 두 곳을 같이 고쳐야 한다(각 제약 옆 주석에 앱 쪽 위치를 적어 둠).

## 3. DI-02: 교차 테이블 "같은 지점" 규칙 — **결정 대기**

- **컨텍스트**: 프로그램↔시설·강사(ADR-PRG-03), 회원↔담당 직원(MEM-T02), 수강·PT↔프로그램(ADR-MEM-03) 모두 "두 행의 branchId가 같아야 한다"는 규칙이고, 지금은 쓰기 시점 `assert*`로만 검사한다. DB로 강제하려면 복합 FK나 트리거가 필요하다. 그런데 SQL로만 추가한 복합 FK(`Program(facilityId, branchId) → Facility(id, branchId)`)는 `prisma migrate diff`가 `DROP CONSTRAINT`/`DROP INDEX`를 생성해 다음 마이그레이션에서 지워진다(2026-09-29 로컬에서 확인). 부분 인덱스·CHECK·트리거는 Prisma가 건드리지 않으므로, 현실적인 수단은 트리거다.
- **조사 중 발견한 공백**: 파견 발령(`MockDataService.assignStaff`)은 그 직원을 담당자로 둔 회원(`Member.assignedStaffId`)과 그 직원의 강사 프로필(`Instructor.staffId`, 옛 지점 소속)을 정리하지 않는다. 그래서 **직원이 다른 지점으로 이동하는 순간 "회원↔담당 직원 같은 지점" 규칙이 조용히 깨진다.** 이 상태에서 "모든 쓰기에서 지점 일치 검사" 트리거를 걸면 파견 발령 자체가 막힌다 — 규칙보다 정책을 먼저 정해야 하는 이유다.
- **대안**:
  - A. **파견 발령 트랜잭션 안에서 담당 관계를 정리한다**: 담당 회원의 `assignedStaffId` 해제, 옛 지점 강사 프로필 비활성화. 이후 트리거는 "쓰기 시점 일치"를 강제한다. 인사 권한 분리(재배치는 본사 결정)와 지점 격리(옛 지점이 떠난 직원을 계속 담당자로 보지 않음)에 맞다. 대신 담당 회원이 사전 안내 없이 담당자를 잃는다(파견 응답에 영향 회원 수를 돌려주는 ADR-PRG-02식 가시화로 완화).
  - B. 담당 회원이 있으면 파견을 막는다(409): 정합성은 가장 강하지만 본사 인사 결정을 현장 데이터가 막는 구조라 인사 권한 분리와 충돌한다.
  - C. 담당 관계는 지점과 무관하다고 규칙을 완화한다: 구현은 가장 싸지만, BRANCH_ADMIN이 다른 지점 직원 정보를 담당자 필드로 보게 돼 지점 격리 불변식과 어긋난다.
  - D. 트리거를 INSERT와 "해당 FK 컬럼 UPDATE"에만 걸고 파견은 그대로 둔다: 새 쓰기는 막지만 파견으로 생긴 불일치는 남는다(현행 앱 동작을 DB로 옮긴 것).
- **권장**: A. 결정되면 인사정보관리 도메인 문서에 ADR로 올리고, 트리거 마이그레이션과 함께 구현한다.

## 4. 앱 검증 공백 — CHECK로 옮기기 전에 앱부터 필요한 규칙

DI-01 원칙상 이번 CHECK에서 뺐다. 각 도메인을 이관할 때 앱 검증(400)을 먼저 추가하고 CHECK를 붙인다.

| 규칙 | 현재 | 영향 |
|---|---|---|
| `Program.endDate ≥ startDate` | 검증 없음(`updateProgram`이 그대로 저장) | 종료일이 시작일보다 앞선 프로그램이 "진행중" 판정에 섞일 수 있음 |
| `CourseEnrollment.expiresAt ≥ enrolledAt` | 검증 없음 | 등록과 동시에 만료된 수강이 생성됨 |
| `ScheduleSlot.endTime > startTime` | 형식(HH:mm)만 검증 | 종료가 시작보다 이른 회차 생성 가능 |

## 5. DI-03: 트랜잭션 규칙 — 공용 헬퍼를 먼저 만들고 도메인 이관 때 가져다 쓴다

- **컨텍스트**: ADR-RSV-01(회차 행 락)·ADR-STF-02(채번)는 "실DB 전환 시 적용"으로 미뤄져 있었다. 도메인마다 따로 구현하면 같은 결함을 도메인마다 다르게 다시 만들 위험이 있다(이 프로젝트가 부분 unique 패턴을 통일한 이유와 같다).
- **결정**: `apps/api/src/prisma/integrity.ts`에 헬퍼 두 개를 두고, 실DB 동시성 테스트로 검증해 둔다. 도메인 이관 때 mock의 "개수+1"·무잠금 정원 검사를 이 헬퍼로 교체한다.
  - `allocateSequence`/`allocateBranchCode` — **설계 변경 하나**: ADR-STF-02는 "시퀀스 행을 `SELECT ... FOR UPDATE`로 잠그고 +1"이었는데, 그 방식은 **prefix의 첫 채번**(새 지점, 해가 바뀐 memberNo)에서 잠글 행이 없어 동시 요청이 모두 통과한다. ADR-RSV-01이 논파한 팬텀 삽입과 같은 구멍이다. `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`은 행이 없으면 만들고 있으면 잠근 채 증가시켜 두 경우를 한 문장으로 직렬화한다. memberNo 연도도 mock의 `getFullYear()`(호스트 시간대) 대신 `todayKst()`를 쓴다.
  - `lockScheduleSlot` — ADR-RSV-01 그대로(회차 행 `FOR UPDATE`).
- **발견**: 시드가 직원 `SEOCHO-001/002`, 회원 `SEOCHO2026-001`을 번호째로 넣는데 시퀀스는 비어 있어, 헬퍼의 첫 채번이 기존 번호와 **unique 충돌**한다. `seed.ts`가 시퀀스 행도 함께 넣도록 고쳤다. **실데이터를 이관할 때도 같은 초기화(prefix별 현재 최대 번호로 `CodeSequence` 채우기)가 필요하다.**
- **검증**(`apps/api/test/integrity-helpers.spec.ts`, 로컬 Postgres 16):
  - 새 prefix에 동시 20건 채번 → 1~20이 중복·누락 없이 나옴.
  - 시드 번호와 충돌하지 않는 다음 번호를 mock과 같은 형식으로 냄. 시드의 시퀀스 행을 지우면 이 테스트가 실패하는 것도 확인.
  - 예약 0건인 신규 회차(정원 2)에 5명 동시 요청 → 락이 있으면 정확히 2건만 확정되고, **대조군(락 없음)**은 정원을 넘겨 확정됨.

## 6. 도메인 이관 체크리스트 (정합성)

도메인을 Prisma로 옮길 때 [traffic-infra-review.md](./traffic-infra-review.md)(성능)와 함께 이 목록을 확인한다.

- [ ] 채번은 `allocateBranchCode`로(인사 STAFF·회원 MEMBER·자산 ASSET). 그 도메인의 기존 데이터를 이관한다면 `CodeSequence`부터 초기화.
- [ ] 예약 생성은 `$transaction` 안에서 `lockScheduleSlot` → 활성 예약 COUNT → 삽입. 부분 unique 위반(P2002)은 `ALREADY_RESERVED` 409로 변환.
- [ ] 퇴사: 계정 비활성화 + 진행 중 파견 종료 + HR_RECORD 보존기한 재계산을 한 `$transaction`으로(ADR-STF-01·RES-02).
- [ ] 파견 발령: 옛 파견 종료 + 새 파견 생성 + `Staff.branchId` 갱신을 한 `$transaction`으로. DI-02가 결정되면 담당 관계 정리도 같은 트랜잭션에.
- [ ] 연차 승인: 요청 상태 변경 + `LeaveBalance.usedDays` 증가를 한 `$transaction`으로(ADR-ATT-01).
- [ ] 프로그램 수정: 모든 검증을 끝낸 뒤 `update` 한 번(ADR-PRG-01 부분수정 결함 재발 방지).
- [ ] CHECK 위반 에러(제약 이름 포함)가 500으로 새지 않는지 — 앱 검증이 먼저 걸러야 정상이다. 새면 앱 검증 누락이다.
- [ ] §4 공백 규칙은 앱 검증을 추가한 뒤 CHECK를 붙인다.
