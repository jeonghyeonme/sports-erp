## 1. 확정된 슬라이드 구성 (총 10장)

### 1. 표지
프로젝트명, 발표자, 날짜, "2주차 진행상황 발표" 부제

### 2. 오늘 발표 한 줄 요약
지난 발표 이후 세 갈래로 진행됨:
1. 사업 구조 재해석 반영
2. 디자인·데이터 스케일업 (98개 지점 + 위탁계약 라이프사이클 관리)
3. 조회 전용이던 API에 Write 기능 첫 구현

### 3. 지난 발표 리마인드 (보강)
- 프로젝트 한 줄 소개: 아파트·오피스텔 커뮤니티 시설 위탁운영 ERP, 본사·지점·회원 3계층
- 사업 구조 다이어그램: 본사↔위탁센터(계약) · 위탁센터↔직원↔이용자(운영), `Branch`=계약현장 / `Staff`=파견인력 ([1-1_공통설계서.md](../1.spec/00_공통/1-1_공통설계서.md) §2-1)
- 1주차 발표 시점에 보여준 것: Phase 0(모노레포 + Prisma 스키마 26개 모델) + Phase 1 스캐폴딩(로그인/JWT/4-Role RBAC, 지점간 데이터 격리, 대시보드→지점 드릴다운→권한관리 화면) — 단, 전부 mock 데이터 기반이었음을 함께 언급
- (선택) 핵심 설계결정 1~2개만 짧게: D2(지점 데이터 격리), D12(STAFF/BRANCH_ADMIN 권한 분리)

### 4. 디자인 스케일업 — 규모 + 위탁계약 라이프사이클
- Before(카드 그리드) / After(98개 지점, 검색·상태필터·위험도 정렬 테이블) 스크린샷 대비 — `66d9ace`
- 계약상대방 / 계약기간 / 계약상태 필드, 대시보드 "계약 갱신임박" KPI, 지점 상세 계약 정보 탭
- "시스템 불안 → 민원 → 계약 해지"라는 RFP 리스크 구조와 연결 지어 설명 ([2-4_차별화전략.md](../2.decisions/60_분석및제안/2-4_차별화전략.md) §1)

### 5. 차별화 전략 — 계약서 OCR·AI 분석 (설계, 미구현)
- 플로우: 계약서 스캔본 업로드 → OCR 텍스트 추출 → AI가 필드 추출 + 3줄 요약 → **관리자 검토 후에만 `Branch` 필드 반영**
- 왜 자동반영이 아닌 검토 후 반영인가: OCR/AI 오류가 계약상태 전이의 근거 데이터에 그대로 파급되기 때문 (§1-1)
- 왜 계약서 1종에만 스코프를 한정했는가: 문서 유형을 늘리면 유형별 스키마가 무한정 늘어남
- **Phase 2~3 예정, 현재 코드 미구현**임을 슬라이드에 명시 — `BranchDetailPage.tsx`에도 동일 안내 캡션이 이미 박혀 있음

### 6. Write API 구현 주간
- 회원관리: 등록/수정/상태전환(탈퇴 시 로그인 즉시 차단) — `8da4875`
- 프로그램 상태전이: `PREPARING→RUNNING→PAUSED→ENDED` 전이표 그대로 구현, 잘못된 전이 차단 — `52edc7f`
- 인사정보관리: 채용/파견발령/퇴사, `StaffAssignment` mock 최초 구현 — `5fc04bc`
- "조회만 되던 시스템에 쓰기 기능이 처음 들어갔다"는 각도로 정리

### 참고 — 스크린샷 촬영 중 발견한 dev 환경 이슈

- `apps/api`를 `nest start --watch`로 띄울 때 `dist/tsconfig.tsbuildinfo`가 오래되면(예: 브랜치 전환·장시간 미재시작) 증분 빌드가 최신 소스 변경을 반영하지 못하는 문제가 있었다. 대시보드에 98개 지점이 아니라 2개만 뜨는 식으로 나타남 — 이런 증상이 재현되면 `apps/api/dist`를 삭제하고 재시작할 것.
- `npm run dev`(concurrently로 api+web 동시 기동)를 브라우저 자동화 도구의 포트 지정 방식과 함께 쓰면 `PORT` 환경변수가 두 프로세스에 동시 주입되어 충돌할 수 있다 — api/web을 별도 프로세스로 띄우는 편이 안전하다.
