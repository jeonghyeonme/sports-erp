# 4-0. 발표자료 공통 지침 (주간 진행상황 발표용)

> 진행상황 발표를 **매주** 만들기 때문에, 주차마다 다시 정하지 않도록 구성·디자인·제작 방식을 모아 둔 문서입니다. 2주차([4-2](4-2_2주차발표_슬라이드구성.md))와 3주차([4-3](4-3_3주차발표_슬라이드구성.md)) 제작 경험에서 정리했고, 새로 배운 것이 생기면 이 문서를 갱신합니다. 주차별 내용(무엇을 발표하나)은 이 문서가 아니라 각 주차의 구성안 문서에 둡니다.
>
> 발표자료 작업을 명시적으로 요청받았을 때만 이 폴더를 수정합니다([CLAUDE.md](../../CLAUDE.md) 보호 영역).

## 1. 매주 작업 순서

1. **범위 정하기** — 지난 발표의 마지막 커밋 다음부터 이번 발표 직전까지 `git log`로 커밋을 모으고, 발표에 넣을 것과 뺄 것을 정한다. 이번 주 성과를 나열하기보다 **하나의 서사**로 묶는다.
2. **구성안 작성** — `4-N_N주차발표_슬라이드구성.md`를 만든다(§2 형식). 슬라이드를 만들기 전에 구성(내용)을 먼저 확정한다.
3. **수치는 코드에서 재실측** — API 엔드포인트 수, 페이지 수, 엔티티 수 같은 숫자는 문서가 아니라 코드에서 다시 센다. 지난주 수치와 비교할 때는 기준 커밋을 적는다.
4. **화면 캡처** — §5 절차로 실제 admin-web 화면을 찍는다.
5. **덱 제작** — §4 디자인 규칙으로 슬라이드를 만들어 Slides 아티팩트로 게시한다.
6. **소스 보관** — 생성 스크립트·캡처·결과를 `assets/4-N_N주차발표/deck-source/`에 저장하고 커밋한다(§6). 덱 자체는 claude.ai 아티팩트에 있고 저장소에는 덱을 다시 만들 소스를 둔다.
7. **구성안 갱신** — 제작 중 구성이 바뀌면(눈으로 보면서 바뀌는 게 정상이다) 구성안 문서를 최종 덱에 맞게 고친다. 구성안과 덱이 어긋난 채로 두지 않는다.

## 2. 구성안 문서 형식

`4-N_N주차발표_슬라이드구성.md`에 아래 항목을 둔다.

- **발표 조건** — 시간, 청중, 시연 방식(라이브 데모 여부), 이번 주만의 전제
- **서사** — 한 문장으로 요약되는 흐름
- **슬라이드 목록** — 번호·슬라이드 id·핵심 메시지. 도메인 슬라이드는 RFP 요구·해석·도식·구현 화면을 함께 적는다
- **시간 배분** — 구간별 분량
- **캡처 목록과 계정** — 어떤 화면을 어떤 계정으로 찍었나
- **Q&A 대비** — 슬라이드에는 넣지 않지만 질문이 나올 수 있는 사실(검증 범위, 제외한 것, 한계)
- **참고 자료와 이번 발표 범위 커밋**

## 3. 내용 원칙

- **미구현·한계는 숨기지 않고 한 줄로 밝힌다.** RFP가 요구하는데 아직 없는 것은 "남긴 것"으로 보여주고, 의도적으로 제외한 것은 근거와 함께 제외했다고 말한다. 일부만 했으면 일부만 했다고 쓴다.
- **동작하는 것만 그린다.** 도식과 기능 목록은 실제로 동작하는 것만 넣는다. 화면이 없고 API만 있는 것(예: 채용·재배치)은 "API로 구현, 화면은 후속 과제"라고 명시한다.
- **검증되지 않은 것을 검증된 것처럼 쓰지 않는다.** 자동 테스트는 지점 격리·계약 종료 차단·인사 권한 3개 영역뿐이고 나머지는 lint·빌드까지만 검증됐다. 슬라이드에 쓸 때도 이 범위를 넘지 않는다.
- **분석 근거의 범위.** 기업 분석 자료(5-1)는 RFP와 일반적인 실무 관행을 조사해 재구성한 것이지 스포이즘 내부 자료가 아니다. "실무를 조사·분석해 설계로 연결했다"까지만 말한다.
- **RFP 산출물 표기.** 발표는 산출물 3종(기업 분석 자료·개발 작업계획서·ERP 앱)을 축으로 하되, 화면에는 "산출물 1/2/3" 같은 번호 문구를 쓰지 않는다(청중에게 필요한 정보가 아니다). 이름만 쓴다.
- **회원 앱이 미착수인 동안** 회원 시연 화면은 회원 계정으로 로그인한 admin-web 화면이다. 슬라이드에 그렇게 밝힌다.
- **청중은 개발 지식이 있는 사람**으로 가정한다. 지점 격리·상태 전이·환불 기준 같은 핵심 개념은 남기고, 클래스명·오류 코드·영문 상태값·내부 필드명은 슬라이드에 쓰지 않는다. 한글 업무 용어를 쓴다.
- **슬라이드 하나에 메시지 하나.** 도식 요소는 6개 안팎, 한 장에 넣는 정보는 청중이 읽을 수 있는 만큼만 넣는다. 청중이 궁금해하지 않을 내부 구현 디테일(예: 부가세 역산, 상태 전이 전체 표)은 슬라이드에서 빼고 Q&A 대비로 둔다.
- **범위 밖 결정은 문서와 일치시킨다.** 제외 항목은 [2-3 추적표 §2-4](../2.decisions/60_분석및제안/2-3_요구사항추적표.md)에 근거가 있어야 하고, 발표에서 그것과 다르게 말하지 않는다.

## 4. 슬라이드 디자인 규칙

기준은 2주차 발표 덱([링크](https://claude.ai/code/artifact/cea04fa5-eabc-4b78-a55b-838a5da1a402))의 언어이고, 3주차에서 같은 언어로 확장했다. 3주차 생성기(`assets/4-3_3주차발표/deck-source/viz/`)가 아래 규칙을 코드로 구현하고 있어, 새 주차는 이를 복사해서 시작한다.

### 캔버스와 형식

- 캔버스 **1920×1080**, 슬라이드마다 `slides/<id>.html` 하나 + `deck.json`(Slides 아티팩트 형식). 인라인 스타일만 쓰는 제한된 CSS 부분집합을 쓴다(클래스·`z-index`·`margin`·`var()` 금지). 배치가 필요하면 `position:absolute`로 고정한다.
- 좌우 여백 96px, 슬라이드 하단 각주는 24px로 왼쪽 아래(`bottom:40px`).
- 슬라이드 id는 의미 있는 이름으로 짓는다(`dom-auth`, `dom-auth-shot`). 번호는 순서를 바꾸면 깨진다.

### 색·글꼴

| 용도 | 값 |
|---|---|
| 배경 | `#F4F5F3`(웜 그레이), 카드 `#FFFFFF`, 보조 면 `#EBEEEC` |
| 글자 | 본문 `#14191C`, 보조 `#4B5563` |
| 포인트 | 네이비 `#1E3A5F`(라벨·강조), 앰버 `#9A5A0C`(주의·미완), 그린 `#187650`(완료·구현됨) |
| 선 | `#E1E4E1`, 강조선 `#CBD0CD` |
| 글꼴 | 제목 Gothic A1, 본문 Noto Sans KR, 라벨·URL·코드 JetBrains Mono |

### 글자 크기

- **모든 글자 24px 이상.** 발표장에서 읽혀야 한다. 제목 60px, 본문 28~32px, 카드 제목 40~48px, 표지 제목 176px.
- 라벨은 JetBrains Mono 24px + 자간을 준 대문자성 라벨(네이비).

### 공통 구성 요소

- **머리말** — 위쪽에 라벨 한 줄(구분·위치, 예: `도메인 2 / 9 · 구현 화면`) + 그 아래 큰 제목.
- **카드** — 흰 배경, 1px 선, 반경 14px, 옅은 그림자.
- **상태 알약** — 구현됨은 그린, 신설은 네이비 채움, 미완·진행 중은 앰버, 제외는 회색.
- **브라우저 프레임** — 화면 캡처는 점 3개 + URL(모노) 막대가 있는 프레임 안에 넣어 "실제 화면"임을 보인다. 캡처 화면의 계정·URL을 막대에 적는다.
- **표** — 큰 글자(28px)와 넉넉한 행 높이. 표 한 장은 4행 안팎.
- **점 격자** — 표지·마무리에서만 장식으로 쓴다.

### 도식(SVG)

- 도식 하나에 메시지 하나, 요소 6개 안팎, 화살표에는 라벨을 붙인다.
- 슬라이드 형식은 SVG 안의 `<text>`를 허용하지 않으므로 **글자는 SVG 위에 `<p>`로 겹쳐 놓는다**(`lib.js`의 `slide` 모드가 자동 처리). SVG 하나는 52KB 이하, 슬라이드당 요소 200개 이하.
- 도식은 도메인 슬라이드의 오른쪽 카드 안(약 1000×700)에 넣는다. 글자는 24px 미만이 되지 않게 도식 자체를 크게 그린다.

### 도메인 슬라이드 템플릿

도메인마다 슬라이드 2장을 만든다.

1. **구조 슬라이드** — 왼쪽 `RFP 요구 / 우리의 해석 / 동작하는 기능`, 오른쪽 카드에 도식 1개. 오른쪽 위에 상태 알약.
2. **구현 화면 슬라이드** — 브라우저 프레임 안의 실제 화면 + "이렇게 구현했습니다" 요점 3개. 세로가 긴 화면은 프레임 왼쪽·요점 오른쪽, 가로로 넓고 낮은 화면은 프레임 중앙·요점 3칸 아래. 화면이 두 단계(예: 예약 직후 → 결제 후)면 슬라이드 2장으로 나눈다.

슬라이드 수는 목표가 아니라 결과다. 도메인이 늘면 이 템플릿으로 장을 늘린다.

### 발표자 노트

모든 슬라이드에 노트를 단다(화면에는 보이지 않음). 넣을 것: 말할 내용, 시간 배분, 주의(과장하면 안 되는 표현), 질문이 나올 때의 사실. 구현 상태처럼 헷갈리기 쉬운 것은 노트에 "이렇게 말하지 말 것"까지 적는다.

## 5. 화면 캡처 규칙

- **실제 앱을 캡처한다.** API·admin-web을 띄우고(`npm run dev:api`, `npm run dev:web`) 로그인된 Chrome에 붙는 스크립트(`deck-source/capture/`)로 찍는다. 절차와 계정은 `assets/4-3_3주차발표/deck-source/README.md`에 있다.
- **로그인은 사람이 한다.** 데모 계정 카드를 사용자가 직접 클릭한다. 비밀번호 입력이나 로그인 버튼 클릭을 자동화하지 않는다.
- **새로고침하면 로그아웃된다**(토큰이 메모리에만 있다). 이동은 사이드바 링크 클릭으로 한다.
- **계정별로 다른 화면**: 본사(정하늘) — 권한 관리·지점 상세, 지점 관리자(김민수, 서초점) — 나머지 관리 화면, 회원(이수진, 서초점) — 예약·결제.
- **캡처 전에 mock 상태를 확인한다.** mock 데이터는 인메모리라 이전 캡처 작업이 남긴 변경(휴강 전환, 권한 전환, 채용)이 화면에 영향을 준다. API를 재시작하면 초기 상태로 돌아간다.
- **캡처 화면에서 개발자용 안내 문구는 가린다**(각 페이지의 설명 문구). 아래 여백은 잘라 낸다.
- 화면은 **실제로 동작한 결과**여야 한다. 조작해 상태를 만든 화면(예: 결제 대기 → 확정)은 그 조작을 실제 API로 수행한 것이어야 하고, 이미지를 합성하지 않는다.

## 6. 폴더와 파일

```
docs/4.presentation/
  4-0_발표자료_공통지침.md           # 이 문서
  4-N_N주차발표_슬라이드구성.md       # 주차별 구성안
  assets/4-N_N주차발표/
    deck-source/                      # 덱을 다시 만드는 소스
      README.md                       # 재생성·재게시·재캡처 방법, 알려진 한계
      viz/                            # 생성기(deckN.js), 도식(figs-*.js), 공용(lib.js)
      capture/                        # 캡처 스크립트
      screenshots/                    # 덱에 넣은 캡처 PNG
      deck-out/project/               # 생성 결과 스냅샷(deck.json + slides/*.html)
```

- 새 주차는 직전 주차의 `deck-source/`를 복사해 시작한다(`viz/lib.js`·`figs-*.js`·`capture/`를 재사용하고, `deckN.js`만 새로 쓴다).
- 이미지 자산은 아티팩트에 올리고 슬라이드에서 그 주소(`/_blob/<id>`)로 참조한다. **이 주소는 아티팩트에 묶여 있으므로** 새 아티팩트로 옮기면 다시 올려야 한다. 그래서 원본 PNG를 `screenshots/`에 보관한다.
- 덱 아티팩트 링크는 각 주차 구성안과 `deck-source/README.md`에 적는다. 아티팩트의 공유 설정(비공개/링크 공개)은 소유자만 바꿀 수 있고, 게시할 때마다 현재 공개 범위를 확인한다.
- 새 주차 문서를 만들면 [README](../../README.md)의 문서 표에 행을 추가한다.

## 7. 제작 전후 확인 목록

- [ ] 구성안이 최종 덱과 일치한다
- [ ] 수치는 코드에서 다시 셌고 기준 커밋이 적혀 있다
- [ ] 모든 글자가 24px 이상이다(생성기의 린트가 검사한다)
- [ ] 화면에 "산출물 N" 같은 번호 문구가 없다
- [ ] 미구현·제외·화면 없음(API만)이 슬라이드나 노트에 정직하게 적혀 있다
- [ ] 회원 화면이 admin-web 대용임을 밝혔다
- [ ] 캡처가 최신 mock 상태에서 찍혔고 개발자용 안내 문구가 없다
- [ ] 게시한 덱을 실제로 열어 슬라이드 겹침·잘림을 눈으로 확인했다(로컬 미리보기는 렌더러 스타일이 없어 정확하지 않다)
- [ ] `deck-source/`를 최신으로 커밋했다
- [ ] 검증되지 않은 것(자동 테스트 범위 밖)을 검증된 것처럼 쓰지 않았다
