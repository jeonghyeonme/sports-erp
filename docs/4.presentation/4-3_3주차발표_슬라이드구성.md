## 0. 발표 조건

- 형식: 슬라이드 + 실제 화면 캡처, 라이브 데모 없음
- 분량: 15분 내외(시간 배분은 §3). 슬라이드 수는 목표가 아니라 결과다 — 도메인 9개마다 구조 슬라이드와 구현 화면 슬라이드를 두어 29장이 됐다
- **청중: 개발 지식이 있는 분들** (2026-09-21 확정). 지점 격리·상태 전이·24시간 환불 기준 같은 핵심 개념은 남기되, 클래스명·오류 코드·영문 상태값·내부 필드는 슬라이드에 쓰지 않는다
- **도식 원칙**: 도식 하나에 메시지 하나, 요소 6개 안팎, 한글 업무 용어. **동작하는 것만 그린다.** 미구현·의도적 제외는 도식에 넣지 않고 슬라이드 6·28과 §5의 Q&A로만 다룬다
- 회원 앱(React Native)이 미착수라 회원 시연 화면(예약·결제)은 **회원 계정으로 로그인한 admin-web 화면**이다 — 슬라이드 19에 명시했다
- 화면에는 "산출물 1/2/3" 같은 번호 문구를 쓰지 않는다(2026-09-21 결정, [4-0 §3](4-0_발표자료_공통지침.md))

## 1. 서사

**분석하고, 계획하고, 구현했다.** 원본 RFP가 요구한 세 가지 — 기업 분석 자료, 개발 작업계획서, ERP 앱 — 를 순서대로 보여주고, ERP 앱은 도메인 9개를 같은 틀(RFP 요구 → 우리의 해석 → 도식 → 실제 화면)로 하나씩 보여준다.

2주차까지의 축(실무 분석 → 도메인 확장 → 도메인별 시연 → 구조 시각화)은 유지하되, 청중이 "무엇을 확실히 보여주려는지 모르겠다"는 피드백이 있어 **산출물 3종 + 도메인 단위**로 재구성했다.

### 17장 초안에서 뺀 것

- **확장 지도 + 판단 프레임**(넣을지 뺄지 가르는 4개 질문)과 **넣은 것/뺀 것/남긴 것 3열 표**는 슬라이드로 만들지 않았다. 대신 6번(제외 항목 칩)·4번(분석→설계→구현)·28번(남긴 것)으로 나눠 담았다.
- **공통 뼈대 "4개 역할 × 접근 범위 표"** 는 권한관리 도식(8번)에 흡수했다.
- 4·5번의 **계약 종료 시 막히는 3가지 시각화**는 별도 슬라이드가 아니라 4번 표의 첫 행(계약이 종료된 지점은 신규 회원 등록·예약·게시글 작성이 막힌다)으로 다룬다.
- 이 슬라이드들의 도식 SVG는 [assets/4-3_3주차발표/](assets/4-3_3주차발표/) 바로 아래에 남아 있다(9개). 현재 덱은 사용하지 않지만 PowerPoint 삽입용 대체 자료로 보관한다.

## 4. 화면 자료

### 캡처 (확보 완료, 2026-09-21)

실제 admin-web(로컬 개발 서버, mock 데이터) 화면을 스크립트로 캡처해 [deck-source/screenshots/](assets/4-3_3주차발표/deck-source/screenshots/)에 보관했다. 계정은 정하늘(본사) · 김민수(서초점 지점 관리자) · 이수진(서초점 회원). 로그인은 사용자가 데모 계정 카드를 직접 클릭했다.

- 5-1·5-2 문서 화면(슬라이드 3·5)은 `docs/5.deliverables/`의 HTML을 브라우저로 캡처해 아티팩트에 올렸다. 원본 PNG는 저장소에 없다.
- 캡처 규칙은 [4-0 §5](4-0_발표자료_공통지침.md).

### 검증 범위

- 도식의 상태·전이·구간값은 2026-09-21 코드에서 직접 확인했다. 글자 겹침·영역 이탈은 생성기 린트(24px 이상, `<text>` 금지, SVG 52KB 이하, 요소 200개 이하)로 검사했다.
- **게시된 덱은 브라우저에서 눈으로 전체를 확인하지 못했다**(아티팩트가 로그인이 필요한 화면이라 자동 확인이 안 됨). 로컬 미리보기는 슬라이드 렌더러 스타일이 없어 제목 위치·체크 아이콘이 실제와 다를 수 있다. 발표 전에 덱을 처음부터 끝까지 훑어보고 겹침·잘림을 고칠 것.
- 구현 화면 슬라이드의 요점 문구는 기능 목록 기준으로 썼고, 캡처 이미지와 문구를 한 장씩 대조하지는 않았다.

## 5. 발표 전 확인할 것 (Q&A 대비 포함)

1. **5-1이 아직 "구현 안 하기로 한 것"을 설계 결정으로 서술하고 있음.** 분석서 본문에 결근 자동판정 배치, 강사 정산·원천징수, 계약 종료 60일 전 자동 갱신임박 전환 배치가 "설계 결정"으로 적혀 있고, 말미 "설계 현황" 표에는 예약·결제가 "매출 인식·강사 정산까지 확장"으로 돼 있다. 이 중 정산·자동 배치는 2026-09-20에 구현 범위에서 제외했고(갱신임박 자동 전환도 현재는 시드 데이터의 고정 상태값), 분석서의 서술과 어긋난다. **결정(2026-09-20): 분석서는 그대로 두고 (b) 프레임으로 설명한다** — "분석서에는 실무 전체를 명시하되, 구현을 진행하면서 불필요하다고 판단한 것은 제외하는 방향으로 진행했다." 슬라이드 4(발표자 노트)와 6(제외 항목)에서 이 문장을 쓰고, 제외한 항목은 [2-3 추적표 §2-4](../2.decisions/60_분석및제안/2-3_요구사항추적표.md)에 근거와 함께 남아 있다고 안내한다. 질문이 나오면 "분석서는 실무 지도, 구현 범위는 별도 판단"으로 답할 것.
2. **분석의 근거 범위.** 5-1은 원본 RFP와 일반적인 한국 실무 관행(고정자산 기준, 재물조사 절차, 법정 보존연한 등 — [1-10 참고자료](../1.spec/40_자원문서관리/1-10_기업구조및자원관리분석.md#참고자료))을 조사해 **재구성한 것**이고, 스포이즘의 실제 내부 자료·수치가 아니다. 지점 분포·계약 현황 같은 수치는 mock 데이터라 분석 근거로 쓰지 않았다. "실무를 직접 조사·분석해 설계로 연결했다"로 말하면 정확하고, "스포이즘 내부 실무를 안다"로 말하면 과장이 된다.
3. 지역관리자(SV) 계층은 분석에서 발견했지만 RFP에 없어 **일부러 설계에 넣지 않은** 사례 — 확장 판단의 좋은 예시로 슬라이드 4·6을 말할 때 언급할 수 있다.
4. **계약 종료 시 막아야 하는 5곳 중 구현은 3곳.** 동작하는 것은 신규 회원 등록·예약·게시글 작성 차단 3가지이고, "5곳을 막는다"고 말하지 말 것. 지점 소속 계정(정책 미정)과 파견 직원 종료 처리(미구현) 2곳은 슬라이드 28의 "남긴 것"에 있다. 질문이 나오면 "무엇이 남았는지까지 분석했고, 계약 상태를 바꾸는 API와 함께 구현할 계획"으로 답한다. 근거: [2-3 추적표 §2-3](../2.decisions/60_분석및제안/2-3_요구사항추적표.md).
5. **인사정보관리 화면 범위.** admin-web에는 채용·재배치 화면이 없다(API와 통합 테스트만 있음). 슬라이드 10·11은 "API로 구현, 화면은 후속 과제"라고 적었다. "인사 화면에서 채용할 수 있나요?"에는 "API는 있고 화면은 아직"으로 답한다. 인사정보관리를 "화면에서 동작한다"고 말하지 말 것(슬라이드 7 제목은 "9개 도메인을 구현했습니다"로 고쳐 해결했다. 슬라이드 2의 "9개 도메인 동작" 알약은 API 기준 표현이다).
6. **(슬라이드에는 넣지 않고, 질문이 나올 때만) 검증·테스트 관련.** 2026-09-21 결정으로 가드레일·테스트·CI는 이번 발표 슬라이드에서 제외했다. 사실만 정리해 둔다.
   - *"자동 테스트가 있나요?"* → 핵심 규칙 3개 영역(지점 데이터 격리·계약 종료 지점 차단·인사 권한 분리)에 HTTP 통합 테스트 119건이 있고 CI(GitHub Actions)가 push마다 lint·빌드·테스트를 돌린다. **그 밖의 도메인 로직(예약·결제 계산, 근태, 자산 등)과 admin-web 화면에는 자동 테스트가 없어 lint·빌드까지만 검증된다.** 전체가 검증됐다고 말하지 말 것.
   - *"지점 격리는 정말 막히나요?"* → 자동 테스트로 확인했고, 그 과정에서 검사가 빠져 있던 라우트(프로그램 회차 조회) 1건을 찾아 수정했다. 격리는 가드와 컨트롤러별 검사의 조합이라 새 라우트에서 누락될 수 있어, 공통 가드로의 중앙화는 실DB 전환 이후에 하기로 했다([2-3 추적표 §3 6번](../2.decisions/60_분석및제안/2-3_요구사항추적표.md)).
7. **(슬라이드에는 넣지 않고, 질문이 나올 때만) 부가세 분리.** 2026-09-21 결정으로 발표 슬라이드에서 뺐다. 구현이 작고(결제 승인 시 `공급가액 = round(결제금액 ÷ 1.1)`, 부가세는 나머지) 결제 자체가 모의 결제라 설득력이 약하다는 판단이다.
   - *"부가세는 어떻게 처리하나요?"* → 결제 승인 시 총액에서 공급가액과 부가세를 역산해 결제내역에 나눠 기록한다(예: 30,000원 = 27,273 + 2,727). 다만 **모의 결제 위에서의 구현**이고, **프로그램 종류와 무관하게 일괄 10%를 적용**한다. 과세·면세 구분은 다루지 않으며, 실제 세무 처리는 범위 밖이다.
8. **(발견 — 미수정) 예약 화면의 "잔여좌석" 열이 실제로는 예약 인원/정원을 보여준다.** `ReservationsPage.tsx`의 열 제목은 "잔여좌석"인데 값은 `bookedCount / capacity`다(예약하면 0/2 → 1/2로 늘어난다). 슬라이드 19·20의 캡처에 이 표시가 그대로 나온다. 화면 코드는 이번 작업 범위 밖이라 고치지 않았고, 질문이 나오면 "열 제목 표기 오류로, 값은 예약 인원/정원"이라고 답한다. 화면을 고치면 캡처도 다시 찍어야 한다.
9. **(질문이 나올 때만) 동시 예약.** 문서는 DB 행 락(회차 행 먼저 잠금)을 설계했고, 현재는 동기 실행 mock이라 별도 락 없이 안전하며 DB 전환 시 락을 복원한다. 슬라이드 4의 넷째 행이 이 내용이다.
