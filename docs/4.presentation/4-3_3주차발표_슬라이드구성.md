# 4-3. 3주차 진행상황 발표 — 슬라이드 구성안 (확정)

> 2주차 발표([4-2](4-2_2주차발표_슬라이드구성.md), 2026-09-14) 이후 커밋을 분석해 정리한 3주차 발표용 슬라이드 구성안입니다. 2026-09-20 세션의 초안을 2026-09-21 세션에서 **15분 발표 기준 17장으로 압축·확정**했습니다. 슬라이드 비주얼 제작 전 구성(내용) 확정까지가 이 문서의 범위입니다.
>
> 다루는 커밋 범위: `4f0fe5f`(2026-09-17)부터 `abf8caf`(2026-09-20)까지 15개 커밋. 9/14의 `ccd2310`·`ee06568`은 2주차 발표 준비 커밋이라 제외합니다. **`abf8caf` 이후 커밋(가드레일·lint 복구·CI·통합 테스트·격리 누수 수정 등)은 발표 범위에서 제외하기로 했습니다(2026-09-21 결정)** — 슬라이드에는 넣지 않고 §5의 Q&A 대비로만 둡니다.

## 0. 발표 조건 (2주차와 동일 가정 — 변경 시 갱신할 것)

- 형식: PPT/스크린샷 위주, 라이브 데모 없음
- **분량: 15분 내외** → 17장(표지·마무리 제외 실질 15장, 슬라이드당 평균 약 50초). 시간 배분은 §2 하단 표 참고
- 청중은 이전 발표 내용을 상세히 기억하지 못한다는 전제 → 3번 슬라이드에서 짧게 리마인드
- 회원 앱(React Native)이 미착수라, 회원 시연 화면은 **회원 계정으로 로그인한 admin-web 화면**입니다 — 슬라이드에 "회원 앱 화면 대용"이라고 명시할 것

## 1. 발표 축 (네 가지)

1. **실무 분석** — 회사의 실무가 어떻게 굴러가는지 직접 조사·분석해 정리했다 ([5-1 기업 분석 자료](../5.deliverables/5-1_기업분석자료.html))
2. **도메인 확장과 확장의 판단** — 그 분석에서 무엇을 넣고 무엇을 뺐는가, 그 기준은 무엇인가
3. **도메인별 구현 시연** — 실제 화면에서 동작하는 모습
4. **도메인별 구조의 시각화** — 각 도메인이 어떤 엔티티·상태·권한으로 짜여 있는가

전체 서사: **실무를 이해했다 → 그 이해가 설계의 근거가 됐다 → 구현할 범위를 판단했다 → 이렇게 동작한다**

## 2. 슬라이드 구성 (총 17장 / 도입 + 3부 + 마무리)

### 도입 (1~3장)

**1. 표지** — 프로젝트명, 발표자, 날짜, "3주차 진행상황 발표"

**2. 오늘 발표 한 줄 요약**
지난 발표 이후 네 갈래: ① 회사 실무를 분석했고 ② 그 분석으로 도메인을 넓혔고 ③ 넓힘과 자름의 기준을 세웠고 ④ 모든 도메인을 화면에서 동작하게 만들었다.

**3. 지난 발표 리마인드 + 이번 주 변화량**
- 사업 구조 다이어그램(본사↔위탁센터 계약 / 위탁센터↔직원↔이용자 운영) 한 장 — [1-1문서](../1.spec/00_공통/1-1_공통설계서.md) §2-1
- 2주차 종료(9/10, `5fc04bc`) 대비: API 엔드포인트 **23 → 68**, admin-web 페이지 **9 → 16**, mock 엔티티 **8 → 19** (2026-09-21 코드에서 재실측해 일치 확인)
- 2주차 때 "근태·예약결제는 설계만"이었던 것이 이번에 구현됨

### 1부. 실무 분석 — 회사가 실제로 어떻게 굴러가는가 (4~6장)

**4. 왜, 무엇을 분석했나 (5-1 기업 분석 자료 소개)**
- RFP 과업1이 시스템 설계에 앞서 "경영시스템·관리시스템 분석"을 선행 과업으로 요구 → 산출물2 "기업 분석 자료"
- 분석서 구성 캡처: **6개 도메인 × (실무 상세 → 분석 결과 → 결론)** 3단 구조 — 도메인 하나만 읽어도 완결되도록 설계
- 6개 도메인: 사업 구조 / 위탁계약 라이프사이클 / 인력 운용(파견·근태·연차) / 예약·결제·정산 / 물적자원관리 / 문서관리
- 5-1 HTML 화면 캡처 + [보기 좋은 버전](https://claude.ai/code/artifact/460e474f-2ded-4031-ae5b-07cf1efa3731) 링크(QR 후보)

**5. 실무 지도 (시각화)**
- 왼쪽: 사업 구조 흐름(본사 → 위탁센터 → 파견 직원 → 이용자, 계약 관계 vs 운영 관계 구분)
- 오른쪽: 위탁계약 라이프사이클(정상 → 갱신임박 → 만료/종료) + **"계약이 끝나면 막아야 하는 곳 5개"** — 분석에서 "한 줄짜리 원칙이 실제로는 다섯 군데에 각각 걸려야 한다"고 도출했다는 점을 보여주되, **구현 현황을 정직하게 표시**할 것:

| 막아야 하는 곳 | 현황 |
|---|---|
| 신규 회원 등록 | ✅ 구현 (409) |
| 신규 예약 | ✅ 구현 (409) |
| 게시판 신규 작성 | ✅ 구현 (409, 기존 공지 열람은 유지) |
| 지점 소속 계정 | 🔲 설계 명시, 처리 정책은 "별개 정책"으로 미정 |
| 파견 직원(파견 종료·재배치 대상 등록) | 🔲 설계 명시, **미구현** — 계약 상태를 바꾸는 API와 함께 구현 예정 |

- 핵심 메시지: "우리 사업을 정확히 이해하고 있다" — 5곳 중 3곳은 동작하고, 나머지 2곳은 무엇이 남았는지까지 안다. (5곳 전부 막는 것처럼 말하면 과장이다)

**6. 실무 분석 → 설계 → 구현 추적 (이 발표의 핵심 슬라이드)**
분석에서 발견한 공백이 실제 설계와 코드로 이어졌음을 표로 보여줌. 발표에서는 아래 후보 중 **5~6행**만 고를 것.

| 실무에서 발견한 것 | 설계 결정 | 구현 상태 |
|---|---|---|
| 지점은 매장이 아니라 **계약 현장**(초기 설계엔 계약 정보가 없었음) | 계약상대방·기간·상태 4단계 엔티티로 재정의 | ✅ 계약 정보 화면, 종료 지점 신규 등록·예약·게시 차단 |
| 직원은 지점 채용이 아니라 **본사 채용·현장 파견** | `StaffAssignment`, 채용·재배치는 본사 전용 | ✅ 파견 이력 포함 |
| 휴가는 종류마다 차감 방식이 다름(연차만 차감) | 유형별 처리 | ✅ 연차만 잔여일수 차감 |
| 총액에서 부가세를 역산하는 것이 표준 | 공급가액 = 결제금액÷1.1 | ✅ 27,273 + 2,727 = 30,000 |
| 동시 예약에서 **팬텀 삽입**(빈 회차엔 잠글 대상이 없음) | 예약 행이 아니라 회차 행을 먼저 잠금 | ✅ 동작(동기 mock이라 락 없이 안전, DB 전환 시 락 복원) |
| 물적자원관리가 **설계 전체의 공백**이었음 | 자원문서관리 도메인 신설, 100만원 기준 자동 분류 | ✅ Phase 1 (재물조사는 보류) |
| 첨부파일과 법적 증빙 문서는 성격이 다름 | 별도 `Document` 모델 + 보존기한 자동계산 | ✅ 인사서류 +3년, 계약서 수동 |
| 정기휴무를 반영하지 않으면 결근 **오탐**이 매주 발생 | 결근 판정에 정기휴무·고용형태 조건 | 🔲 분석·설계 완료, 자동 배치는 **의도적 제외**(스케줄러 없음) |
| 프리랜서 강사 정산은 3.3% 원천징수 후 지급 | 월정산·원천징수 모델 | 🔲 분석 유지, 구현은 **의도적 제외**(RFP 요구 아님) |
| PT 패키지는 구매 시점에 결제(매출)가 잡혀야 함 | 구매 시점 Payment 생성 | ⬜ PT세션 자체가 미착수 |

- 핵심 메시지: **분석이 설계를 이끌었고, 구현 범위는 그 위에서 판단했다** — 마지막 3행이 다음 2부(확장 판단)의 다리

### 2부. 도메인 확장과 확장의 판단 (7~8장)

**7. 확장 지도 + 판단 프레임 (시각화)**
왼쪽 — 도메인 허브 다이어그램: RFP 원본 8개 기능 도메인을 한 색으로, 이번에 확장한 것을 다른 색으로 표시.
- 신설 도메인: **자원문서관리**(자산·비품 + 문서함) — 실무 분석(슬라이드 6)에서 드러난 공백 ([1-10문서](../1.spec/40_자원문서관리/1-10_기업구조및자원관리분석.md))
- 도메인 내 확장: 강사(`Instructor`) 엔티티, 프로그램 회차(`ScheduleSlot`), 결제 부가세 분리, 위탁계약 라이프사이클(2주차부터)
- 근거 자료: [5-2 개발작업계획서](../5.deliverables/5-2_개발작업계획서.html)의 도메인 허브 다이어그램 재사용 가능

오른쪽 — 넣을지 뺄지를 가르는 네 가지 질문 흐름도:
1. RFP가 요구했는가? → 예: 무조건 대상
2. 없는 인프라(스케줄러·알림·파일 스토리지)가 필요한가? → 예: 보류/제외
3. 화면에서 눈에 보이는가? → 아니오: 제외 후보
4. 다른 기능과 중복되는가? → 예: 제외
- 근거 자료: [2-3 추적표 §2-4](../2.decisions/60_분석및제안/2-3_요구사항추적표.md)
- 포인트: **실무 분석서는 "회사가 실제로 하는 일 전체"를 그린 지도이고, 이 프레임은 그중 우리가 만들 범위를 고르는 기준**이다

**8. 판단 사례 — 넣은 것 / 뺀 것 / 남긴 것 (3열 한 장)**

| 넣은 것 — 왜 | 뺀 것 — 왜 | 남긴 것 — 정직한 갭 |
|---|---|---|
| 자원문서관리: RFP가 "분석"을 요구한 영역인데 물적자원이 통째로 비어 있었음 → Phase 1만 | 강사 정산·원천징수 — RFP 요구 아님, 코드에서도 제거 | 회원 PT 잔여세션·수강내역 |
| 회차(`ScheduleSlot`): 예약이 성립하려면 필수 선행 엔티티 | 혼잡도 QR 체크인·5분 자동계산 — 수동 보정으로 요건 충족, 앱·스케줄러 없음 | 인사 변경 신청 승인 |
| 부가세 분리: 구현 비용은 두 줄, 화면에서 바로 보이는 재무 정보 → 설계상 Phase 6이었지만 앞당김 | 노쇼 자동처리·결제 TTL·자동 결근 — 스케줄러 없음 | AuditLog, 응답 마스킹 |
| | 감가상각 배치 — 회계 모듈이 없어 받는 곳이 없음 | 게시판 교육자료 첨부 |

- 핵심 메시지: **"분석은 끝까지 했고, 구현은 판단해서 잘랐다. 안 만든 것도 문서에 근거와 확장 방향을 남겼다. RFP 요구인데 아직 없는 것은 숨기지 않는다."**
- 이 장에서 §5-1번의 문장("분석서에는 실무 전체를 명시하되, 구현을 진행하면서 불필요하다고 판단한 것은 제외하는 방향으로 진행했다")을 그대로 쓴다. 지역관리자(SV) 계층은 분석에서 발견했지만 RFP에 없어 일부러 설계에 넣지 않은 사례로 "뺀 것" 열에 한 줄 언급 가능

### 3부. 도메인 구현 시연 + 구조 시각화 (9~15장)

> 도메인 슬라이드는 공통 템플릿: **왼쪽 = 구조 시각화, 오른쪽 = 시연 스크린샷 2~3장(순서 화살표) + 핵심 한 줄 + "실무 분석서의 어느 부분에서 왔는가" 태그**

**9. 공통 뼈대 — 권한과 지점 격리 (시각화 중심)**
4-Role × 화면/데이터 접근 매트릭스, 지점 격리(`BranchScopeGuard` + 서비스 레이어 이중 적용)로 타 지점 접근을 403으로 막는 흐름. 이어지는 모든 도메인이 이 뼈대 위에 있다는 점을 먼저 보여줌. 사이드바가 역할별로 다르게 구성된 화면 대비 캡처 포함.

**10. 인사·근태** (분석서 도메인 02)
- 시각화: 본사→`StaffAssignment`→지점 파견 구조 / 근태 상태(정상·지각·조퇴·결근·휴가)와 연차 자동 차감 흐름
- 시연: 체크인(지각 자동판정) → 휴가 신청 → 지점 관리자 승인 → 잔여연차 감소

**11. 회원 · 강사 · 프로그램**
- 시각화: 엔티티 관계(Branch–Member / Instructor–Program) + `Program.status` 상태 전이도(PREPARING→RUNNING→PAUSED→ENDED)
- 시연: 회원 등록(미성년 생년월일 입력 시 보호자 동의 요구) → 프로그램 등록(자유이용 선택 시 가격·정원 비활성) → 상태 전이 드롭다운

**12. 예약·결제 ① 구조 (시각화 중심)** (분석서 도메인 03)
- 엔티티 흐름: `Program → ScheduleSlot → Reservation → Payment`
- 상태 전이 두 개: Reservation(REQUESTED→CONFIRMED→COMPLETED/CANCELLED) + Payment(PENDING→APPROVED→REFUNDED)
- 취소 정책 타임라인: 회차 시작 24시간 전 기준 환불/불가 분기
- 동시성 판단 한 줄: 문서는 DB 행 락, 현재는 동기 실행 mock이라 별도 락 없이 안전, DB 전환 시 락 복원

**13. 예약·결제 ② 시연**
회원 예약 → 결제 대기 → 모의결제 → 확정 → 취소(자동 환불) → 재예약 / 지점 관리자 체크인·결제내역(공급가액 27,273 + 부가세 2,727 = 30,000)

**14. 게시판 · 혼잡도**
- 시각화: 게시글 scope 매트릭스(본사→지점 / 지점→회원, 전체공지 vs 지점 지정) / 혼잡도 5단계 매핑 구간표

## 5. 발표 전 확인할 것 (Q&A 대비 포함)

1. **5-1이 아직 "구현 안 하기로 한 것"을 설계 결정으로 서술하고 있음.** 분석서 본문에 결근 자동판정 배치, 강사 정산·원천징수, 계약 종료 60일 전 자동 갱신임박 전환 배치가 "설계 결정"으로 적혀 있고, 말미 "설계 현황" 표에는 예약·결제가 "매출 인식·강사 정산까지 확장"으로 돼 있다. 이 중 정산·자동 배치는 2026-09-20에 구현 범위에서 제외했고(갱신임박 자동 전환도 현재는 시드 데이터의 고정 상태값), 분석서의 서술과 어긋난다. **결정(2026-09-20): 분석서는 그대로 두고 (b) 프레임으로 설명한다** — "분석서에는 실무 전체를 명시하되, 구현을 진행하면서 불필요하다고 판단한 것은 제외하는 방향으로 진행했다." 슬라이드 6·8에서 이 문장을 그대로 쓰고, 제외한 항목은 [2-3 추적표 §2-4](../2.decisions/60_분석및제안/2-3_요구사항추적표.md)에 근거와 함께 남아 있다고 안내한다. 질문이 나오면 "분석서는 실무 지도, 구현 범위는 별도 판단"으로 답할 것.
2. **분석의 근거 범위.** 5-1은 원본 RFP와 일반적인 한국 실무 관행(고정자산 기준, 재물조사 절차, 법정 보존연한 등 — [1-10 참고자료](../1.spec/40_자원문서관리/1-10_기업구조및자원관리분석.md#참고자료))을 조사해 **재구성한 것**이고, 스포이즘의 실제 내부 자료·수치가 아니다. 지점 분포·계약 현황 같은 수치는 mock 데이터라 분석 근거로 쓰지 않았다. "실무를 직접 조사·분석해 설계로 연결했다"로 말하면 정확하고, "스포이즘 내부 실무를 안다"로 말하면 과장이 된다 — 질문이 나오면 이 구분으로 답할 것.
3. 지역관리자(SV) 계층은 분석에서 발견했지만 RFP에 없어 **일부러 설계에 넣지 않은** 사례 — 확장 판단의 좋은 예시로 슬라이드 7·8에서 언급할 수 있다.
4. **계약 종료 시 막아야 하는 5곳 중 구현은 3곳.** 슬라이드 5에서 "5곳을 막는다"고 말하지 말 것 — 신규 회원 등록·예약·게시글 작성 3곳은 동작하고, 지점 소속 계정(정책 미정)과 파견 직원 종료 처리(미구현)는 설계에만 있다. 질문이 나오면 "무엇이 남았는지까지 분석했고, 계약 상태를 바꾸는 API와 함께 구현할 계획"으로 답한다. 근거: [2-3 추적표 §2-3](../2.decisions/60_분석및제안/2-3_요구사항추적표.md).
5. **(슬라이드에는 넣지 않고, 질문이 나올 때만) 검증·테스트 관련.** 2026-09-21 결정으로 가드레일·테스트·CI는 이번 발표 슬라이드에서 제외했다. 다만 질문 대비로 사실만 정리해 둔다.
   - *"자동 테스트가 있나요?"* → 핵심 규칙 3개 영역(지점 데이터 격리·계약 종료 지점 차단·인사 권한 분리)에 HTTP 통합 테스트 119건이 있고 CI(GitHub Actions)가 push마다 lint·빌드·테스트를 돌린다. **그 밖의 도메인 로직(예약·결제 계산, 근태, 자산 등)과 admin-web 화면에는 자동 테스트가 없어 lint·빌드까지만 검증된다.** 전체가 검증됐다고 말하지 말 것.
   - *"지점 격리는 정말 막히나요?"* → 자동 테스트로 확인했고, 그 과정에서 검사가 빠져 있던 라우트(프로그램 회차 조회) 1건을 찾아 수정했다. 격리는 가드와 컨트롤러별 검사의 조합이라 새 라우트에서 누락될 수 있어, 공통 가드로의 중앙화는 실DB 전환 이후에 하기로 했다([2-3 추적표 §3 6번](../2.decisions/60_분석및제안/2-3_요구사항추적표.md)).
