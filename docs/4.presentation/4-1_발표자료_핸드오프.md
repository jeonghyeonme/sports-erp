# 11. 발표자료 핸드오프 (Claude Desktop 전달용)

> 이 문서는 2026-09-07 "첫 진행상황 발표"(PPT)를 준비하기 위해, Claude Code 세션(이 리포지토리)에서 진행한 작업 내용을 Claude Desktop으로 넘기려고 작성한 핸드오프 문서입니다. Claude Code와 Claude Desktop은 대화 기록이 서로 자동 연동되지 않으므로, 이 파일 하나를 Desktop 대화창에 붙여넣거나 업로드하면 PPT 제작을 바로 이어갈 수 있습니다.
>
> **2026-09-07 갱신**: §2~§5는 2026-09-06 밤 작성 당시 스냅샷입니다. 그 이후 `git pull` 병합 과정에서 인증/도메인 모듈이 두 갈래(로컬 실DB 구현 vs origin mock 구현)로 각자 만들어져 있었다는 사실이 드러났고, mock 쪽을 채택하는 결정을 내렸습니다. 또한 원본 RFP를 사업 맥락 관점에서 재해석한 D18·12·13 문서가 추가됐습니다. §3-3에 이 내용을 정리했으니, 발표 자료에는 §2~§5뿐 아니라 §3-3까지 반드시 포함하세요 — 특히 "왜 두 갈래로 구현됐는가"는 발표에서 나올 가능성이 높은 질문입니다.

## 0. 발표 조건 (범위 판단의 전제)

- **발표 형식**: PPT/스크린샷 위주. 라이브 데모(직접 화면 조작) 없음.
- **구현 범위**: 새 기능·DB 연동 없이, 기존 Phase 1 스캐폴딩을 안정화하고 설계문서를 구현과 일치시키는 것까지만 진행. 발표 전날 밤 리스크를 키우지 않기 위한 의도적 판단.

## 1. 프로젝트 한 줄 소개

**스포이즘 ERP** — 아파트·오피스텔 커뮤니티 시설(헬스장·수영장·골프연습장 등)을 여러 지점에서 위탁 운영하는 회사를 가정한, 본사·지점·회원 3계층 구조의 **다지점(멀티테넌트) 회원·인사 관리 ERP**. 실제 제안요청서(RFP)를 기반으로 설계했지만 **실배포용이 아닌 포트폴리오/졸업작품 프로젝트**.

기술 스택: NestJS + Prisma + PostgreSQL(API) / React + Vite(관리자 웹) / React Native·Expo(회원 앱, Phase 3 예정) — npm workspaces 모노레포.

## 2. 현재 구현 상태 (2026-09-06 기준)

- **Phase 0 완료**: 모노레포 구조, Prisma 스키마 26개 모델, Docker Compose(PostgreSQL 로컬 실행용)
- **Phase 1 스캐폴딩 완료** — 단, **전부 인메모리 mock data(`MockDataService`) 기반이며 실 PostgreSQL에는 아직 연결되지 않음**(마이그레이션 파일 자체가 없음):
  - 로그인/JWT/RBAC 4-Role(`SUPER_ADMIN`/`BRANCH_ADMIN`/`STAFF`/`MEMBER`)
  - `BranchScopeGuard` — 지점 간 데이터 격리
  - admin-web: 대시보드(KPI 요약 스트립 + 지점별 카드), 지점 드릴다운(지점→직원→담당 회원/미배정 회원→프로그램), 본사 전용 "권한 관리"(직원 Role을 STAFF↔BRANCH_ADMIN으로 전환) 화면
- 대부분의 API는 **조회(GET) 전용** — 회원/직원/프로그램/게시판 등의 등록·수정·삭제(Write API)는 아직 없음
- `PrismaService`는 코드상 존재하지만 어떤 모듈에서도 실제로 쓰이지 않음(주석으로 "실 DB 연동 시 교체 예정"이라고 명시돼 있음)

## 3. 오늘(2026-09-06) 밤 진행한 작업

### 3-1. 안정성 점검 (라이브로 재검증 완료, 문제 없음)

- API(`localhost:3000`)/admin-web(`localhost:5173`) dev 서버 정상 기동
- 데모 계정 5개(4개 Role 전체: 본사 관리자, 서초점/강남점 지점 관리자, 서초점 트레이너, 서초점 회원) 전원 로그인 성공
- `BranchScopeGuard` 실동작 확인 — BRANCH_ADMIN 계정으로 `/branches`, `/members` 호출 시 본인 지점 데이터만 반환됨(타 지점 데이터 차단 확인)
- `RolesGuard` 실동작 확인 — BRANCH_ADMIN 계정으로 `/permissions/staff` 호출 시 403 차단
- 지점 드릴다운 API(`/branches/:id/programs/summary`) 정상 응답
- 브라우저로 전 화면(로그인 → 대시보드 → 지점 드릴다운 → 권한관리 → 회원/직원/프로그램/게시판/시설·혼잡도) 클릭 확인, **콘솔 에러 0건**

### 3-2. 문서 동기화 (구현과 설계문서 불일치 해소)

- `1-2_권한관리.md`: "권한 관리(Role 전환)" 화면, `GET/PATCH /api/v1/permissions/staff` API, 권한 매트릭스 반영
- `1-6_회원관리.md`: `Member.assignedStaffId` 필드, "지점 상세(드릴다운)" 화면 반영
- `2-1_기술결정사항.md`: D16/D17 항목의 "문서 미동기화" 상태를 "동기화 완료"로 갱신

## 3-3. 2026-09-07 발생한 일 — 모듈 중복 발견과 RFP 재해석

`git pull`로 원격(origin/main)과 병합하는 과정에서, **같은 저장소를 로컬과 원격이 서로 모르는 채로 인증/도메인 모듈을 독립적으로 각자 구현**했다는 사실이 드러났습니다.

| | 로컬(폐기, 보존됨) | origin/main(채택, 현재 `main`) |
|---|---|---|
| 데이터 소스 | 실제 Prisma + PostgreSQL | `MockDataService`(인메모리) |
| 인증 기능 | 로그인+refresh+logout+비밀번호변경, bcrypt 계정 잠금 | 로그인 + `/auth/me`만 |
| 현재 위치 | `wip/real-db-auth-phase1` 브랜치로 보존, main 미병합 | `main`에 병합되어 동작 중 |

**채택 이유**: origin의 mock 구현 위에 admin-web 프론트엔드 전체(대시보드·드릴다운·권한관리)가 이미 만들어져 있어, 이를 살리는 쪽이 손실이 적다고 판단했습니다. 실제 코드에도 이 흔적이 남아있습니다 — `apps/api/src/modules/account/`+`member/`(실DB용, 죽은 모듈)와 `apps/api/src/modules/members/`(mock용, 살아있음)가 지금 `main`에 동시에 존재합니다. 실DB 전환 시점에 `wip/real-db-auth-phase1`을 참고해 교체하는 것이 다음 단계입니다. 상세 근거는 [12_요구사항추적표](../2.decisions/2-3_요구사항추적표.md) §2-1 참고.

같은 날, 원본 제안요청서(RFP)를 사업 맥락 관점에서 다시 읽으며 다음을 확정했습니다:
- **스포이즘은 헬스장 체인 본사가 아니라 "아파트·오피스텔 커뮤니티 시설 위탁운영사"** — `Branch`는 "회사가 소유한 매장"이 아니라 "위탁운영 계약을 맺은 현장"([1-1문서 §1-1](../1.spec/1-1_공통설계서.md#1-1-사업-맥락-원본-rfp-재해석), §2-1)
- **자체 개발의 이유가 RFP에 명시**: 벤더 데이터유출·도산 리스크·범용시스템 부적합 3가지 ([2-1문서 D18](../2.decisions/2-1_기술결정사항.md#d18-자체개발데이터-주권-원칙-saas-벤더-미사용))
- 이 시스템은 내부 운영툴이면서 동시에 신규 위탁계약 수주 입찰(PT) 발표용 영업 도구이기도 함 — [13_차별화전략](../2.decisions/2-4_차별화전략.md)에 구체적 제안 4가지 정리

## 4. PPT 핵심 스토리라인 (제안 — 그대로 슬라이드 구조로 써도 됨)

1. **문제 정의** — 실제 RFP 기반, 다지점 위탁운영사가 왜 통합 ERP가 필요한가 (지점 격리, 인사/근태, 회원/예약·결제, 혼잡도)
2. **아키텍처 개요** — 본사/지점/회원 3계층, 기술스택, 모노레포 구조도(README 폴더 구조 인용 가능)
3. **핵심 설계 결정 3~4개** (근거는 `2-1_기술결정사항.md`에 ADR 스타일로 상세 정리돼 있음, 그대로 인용 가능)
   - **D2**: 멀티테넌시를 `branchId` 컬럼 격리로 구현 — "타 지점 정보 조회 불가"라는 요구사항 핵심을 어떻게 풀었는가
   - **D6**: 예약 동시성 제어(`SELECT ... FOR UPDATE`) — 정원 초과 방지, 도메인 이해도 어필 포인트
   - **D7**: `Program.status` 4단계 라이프사이클 — 불리언 플래그의 한계를 미리 발견하고 고친 리팩터링 사례
   - **D12**: `STAFF` Role을 `BRANCH_ADMIN`과 분리 — 최소 권한 원칙을 뒤늦게라도 바로잡은 사례(정직하게 "왜 나중에 발견됐는지"까지 말하면 오히려 설득력 있음)
4. **지금까지 구현된 화면** (스크린샷, §7 참고) — 로그인 데모계정 원클릭 → 대시보드 → 지점 드릴다운 → 권한관리
5. **다음 계획** — 실 DB(Prisma/PostgreSQL) 연동, Write API(등록/수정/삭제) 구현, README 로드맵의 Phase 2~5

## 5. 발표 중 나올 수 있는 질문에 대한 정직한 답변 (미리 준비)

- **"DB는 연동됐나요?"** → 아니요, 지금은 인메모리 mock data입니다. Prisma 스키마(26개 모델)는 설계·검증 완료했고, 다음 단계에서 실제 PostgreSQL로 전환할 예정입니다. (의도적 순서 — 구조/화면을 먼저 검증하고 DB는 나중에 붙이는 전략)
- **"회원 등록 같은 건 되나요?"** → 지금은 조회만 가능합니다. Write API는 다음 Phase입니다.
- **"권한 변경하면 로그도 남나요?"** → 아직 AuditLog 연동 전입니다(2-1문서 D17에 개선 항목으로 명시).
- **"왜 인증 모듈이 두 갈래로 구현됐나요?"** → 로컬과 원격 브랜치가 서로 모르는 채로 각자 개발을 진행하다 병합 시점에 발견했습니다. 프론트엔드가 이미 붙어있는 mock 구현을 채택하고, 실DB 구현은 `wip/real-db-auth-phase1` 브랜치에 보존해뒀습니다 — 실수를 숨기지 않고 병합 결정 근거를 2-3문서에 그대로 남긴 것 자체가 이 프로젝트의 문서화 원칙(2-1문서와 동일한 태도)입니다.
- **"이 시스템이 왜 자체 개발이어야 하나요?"** → RFP 원문이 직접 명시한 이유입니다(벤더 데이터유출 리스크, 벤더 도산 리스크, 범용시스템의 한계) — 2-1문서 D18 참고.

이런 질문에 "모른다"가 아니라 "알고 있고, 다음 단계 계획이 있다"로 답하는 것이 포트폴리오 발표에서 훨씬 설득력 있습니다 — 실제로 2-1문서 전체가 이런 자기 인식(트레이드오프를 알고 선택했다는 것)을 근거로 구성되어 있습니다.

## 7. 스크린샷

이번 세션에서 브라우저로 화면은 전부 확인했지만 이미지 파일로 저장하지는 않았습니다. PPT에 넣을 스크린샷이 필요하면:
1. Claude Code 세션에서 다시 요청해 화면을 캡처하고 파일로 저장, 또는
2. 로컬에서 `npm run dev` 실행 후 `http://localhost:5173` 접속해 직접 캡처

로그인 화면에 데모 계정 원클릭 버튼이 있고, 비밀번호는 전 계정 공통 `demo-password-1234` 입니다.
