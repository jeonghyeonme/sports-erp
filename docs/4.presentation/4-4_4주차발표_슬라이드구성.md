## 0. 발표 조건

- 형식: 슬라이드 + **로그인만 라이브 데모**(2026-09-28 확정), 나머지는 슬라이드와 도식으로 전달
- 분량: 15분 내외(지난 2회와 동일하게 가정 — 별도 안내가 있으면 §3만 조정)
- 청중: 3주차와 동일하게 개발 지식이 있는 분들로 가정. 내부 필드명·에러 코드는 쓰지 않는다
- **이번 주는 신규 UI가 거의 없다.** 3주 차까지 "9개 도메인을 구현했다"는 이미 보여줬으므로, 이번 주는 **그 구현을 실제로 띄우면서 만난 진짜 문제(트래픽 병목)를 실측하고 구조적으로 고치는 과정**이 중심이다 — 도메인 슬라이드 템플릿(구조+구현 화면 2장)을 쓰지 않고, 인프라 흐름 중심의 단일 서사로 구성한다
- **도식 원칙**: 3주차와 동일 — 도식 하나에 메시지 하나, 요소 6개 안팎, 한글 업무 용어, 동작하는/실제로 일어난 것만 그린다
- 이번 주 방향성 결정(B+C: 무료 킵얼라이브 + 전체 도메인 Prisma 이관) 중 **B는 합의만 됐고 아직 착수 전, C는 1단계(인증 모듈)만 완료**다 — 슬라이드에서 "완료"로 과장하지 않는다(§5 Q&A 대비 1번)

## 1. 서사

**기능은 이미 다 됐다. 이번 주는 그걸 실제로 띄우다가 만난 진짜 문제를 실측하고, 임시방편이 아니라 구조를 고치는 방향을 정한 한 주였다.**

두 갈래로 구성한다.

- **Part A (9/23~9/26) — 도메인 사이클이 실제로 작동했다.** 3주차까지 만든 9개 도메인을 `architecture-driver` 방법론(Driver→대안→ADR→구현→검증→기록)으로 다시 한 번씩 돌며, 실제 도메인 불변식 위반 버그 5건을 찾아 ADR 근거로 고쳤다. 회원관리는 이 과정에서 신규 기능(오프라인↔앱 연동, 앱 자체 회원가입)까지 얻어 다음 단계(회원 앱)의 선행 작업이 됐다.
- **Part B (9/27~9/28) — 배포하자마자 진짜 병목을 만났고, 원인을 구조적으로 없애는 방향으로 풀었다.** Render+Supabase에 실제로 배포(D23) → k6로 부하테스트를 실측(D24)해 "동시 로그인이 몰리면 15초까지 느려진다"는 사실과 Little's Law로 설명되는 **자기강화형 지연 폭증** 구조를 확인 → 즉시 대응(엣지 rate limit)과 함께, 배포 중 드러난 구조적 버그(오리진 분리)도 땜질이 아니라 통합으로 없앰(D25) → 근본 원인(인메모리 상태라 서버를 늘릴 수 없다)을 없애기 위해 MockDataService→Prisma 전환에 실제로 착수(D26, 가장 위험한 인증 모듈부터 실제 Postgres 위에서 검증).

닫는 메시지: **"이번 주 진행이 화면 기준으로는 더뎌 보일 수 있지만, 실측 없이 추측하던 문제를 숫자로 확인하고, 그 숫자가 가리키는 구조적 원인까지 고치기 시작한 한 주였다."**

## 4. 화면 자료

이번 주는 신규 admin-web 화면이 없어(인프라 작업 위주) **도메인 구현 화면 캡처가 없다.** 슬라이드 대부분은 도식(SVG)이다.

- **라이브(캡처 아님)**: 로그인 — 발표 중 실제 배포 주소(Cloudflare Worker, `sports-erp-api-gateway...workers.dev` 또는 이후 확보한 커스텀 도메인)에서 사람이 데모 계정 카드를 직접 클릭한다. 계정은 김민수(서초점 지점 관리자, `kim.minsu@spoism.example`) 권장 — 로그인 직후 지점 대시보드가 바로 보여 "동작한다"는 확인이 빠르다. [4-0 §5](4-0_발표자료_공통지침.md) 규칙(로그인은 사람이 직접) 그대로 따른다.
- **안전장치(권장, 필수 아님)**: 라이브 데모가 실패할 경우를 대비해 같은 화면의 정적 캡처 1장을 미리 찍어 예비 슬라이드로만 준비해 둔다(발표 흐름에는 넣지 않음).
- **발표 전 확인할 것**: Render 무료 티어는 15분 미사용 시 슬립한다 — 발표 시작 10분 전에 한 번 접속해 깨워 둘 것. Supabase 무료 프로젝트도 7일 비활동 시 일시정지되므로 사전에 접속 상태를 확인한다.

## 5. Q&A 대비 (슬라이드에는 넣지 않음)

1. **B(무료 킵얼라이브)·C(전 도메인 Prisma 이관) 진행 상태를 과장하지 말 것.** "여유 있는 트래픽 확보"를 위해 B(Cloudflare Cron으로 Render·Supabase 깨워두기)+C(전 도메인 Prisma 이관 후 AWS Lambda 이관)로 방향을 합의했지만(2026-09-28), **B는 아직 착수 전이고 C는 16개 도메인 중 인증 1개만 끝났다.** "결정했다"와 "다 했다"를 구분해서 답한다.
2. **이중 경로(Prisma-우선/mock-폴백) 설계는 임시다.** `AuthService`·`JwtStrategy`가 Prisma에서 먼저 찾고 없으면 mock으로 폴백하는 구조인 이유: `/auth/login`이 모든 도메인이 공유하는 단일 진입점인데 아직 15개 도메인이 mock이라, 순수 Prisma로만 바꾸면 그 도메인들의 테스트 116개가 한꺼번에 깨진다. 두 저장소는 ID 체계가 겹치지 않아(Prisma UUID vs mock 문자열 ID) 폴백이 안전하다. 도메인이 하나씩 이관될 때마다 이 폴백을 지워나간다.
3. **`it.skip` 3건 이유.** `auth-lifecycle.spec.ts` 2건·`staff-assignment.spec.ts` 1건은 퇴사·Role전환이 아직 mock 도메인 로직이라 Prisma Account에 즉시 반영되지 않는, 정확히 진단된 과도기 한계다. 기대값을 낮춘 게 아니라 해당 도메인이 이관되기 전까지 "검증 보류"로 남겨둔 것이다.
4. **k6 부하테스트는 이 발표 준비 환경(현재 세션)에서 재현할 수 없다** — 조직 egress 정책이 `onrender.com`을 막는다. 수치는 사용자가 로컬/외부 환경에서 직접 실행해 얻은 실측값이며, 계산 과정은 `docs/architecture/design-constants.md` ⑦~⑨에 코드가 아니라 문서로 남아 있다(Little's Law 역산 + 정산).
5. **"무료 티어 문제가 지금 당장 심각한가?"** 아니다. 평소 트래픽(초당 2명 미만)에서는 동시 진행 로그인이 0.12건 수준이라 전혀 문제가 안 된다. 문제는 **성장 시나리오**(98→130개 지점, 그리고 아직 없는 회원 앱이 출시돼 실제 회원 로그인이 붙는 시점)에서 자기강화 루프의 임계점에 가까워진다는 것 — 3년 후 추정으로도 장애 상황 동시 진행 로그인이 38.4건까지 갈 수 있다.
6. **AWS Lambda 이관은 아직 시작 안 했다.** 전 도메인이 Prisma 기반으로 무상태가 된 뒤에 진행한다 — 지금 옮기면 아직 mock인 도메인이 인스턴스마다 다른 데이터를 들고 있는 문제가 그대로 재현된다.
7. **"GitHub Actions로 자동배포하면 되지 않나?"에 대한 답.** 배포 자동화(push마다 재배포)와 애플리케이션이 실제로 여러 인스턴스에서 안전하게 동작하는가(무상태화)는 별개 문제다. 전자는 지금도 설정 가능하지만, 후자(Prisma 전환)가 끝나지 않으면 자동배포를 걸어도 Lambda의 동시 인스턴스 문제가 그대로 재현된다.
8. **검증 범위.** 자동 테스트는 지점 데이터 격리·계약 종료 지점 차단·인사 권한 분리 3개 영역 + 이번에 실DB 기준으로 검증된 인증 모듈(로그인·토큰갱신·비밀번호변경을 실제 Postgres 위에서 수동 curl로 확인)뿐이다. 이번 주 도메인 사이클에서 고친 나머지 항목(근태·시설·프로그램·게시판·자원문서관리)은 lint·빌드까지만 검증됐다 — "전부 검증됐다"고 말하지 않는다.
9. **CI에 Postgres가 추가된 이유.** `PrismaModule`이 앱 부팅 시 DB 연결을 시도하게 되면서, 기존엔 DB 없이 돌던 CI가 조용히 깨질 뻔했다 — `postgres:16-alpine` 서비스 컨테이너를 추가해 미리 잡았다(로컬에서 완전히 새 DB로 재현해 검증 후 커밋).
