## 0. 이 도메인 개요 (사용자 스토리)

- 본사 관리자로서, 전 지점(또는 특정 지점)에 공지를 올리고 필요시 교육자료 파일을 첨부하고 싶다.
- 지점 관리자로서, 본사 공지를 확인하고 우리 지점 회원들에게 전달할 공지를 따로 작성하고 싶다.
- 회원으로서, 내가 다니는 지점의 공지사항을 앱에서 확인하고 싶다.

## 6. 현행 구조 진단 (Baseline)

코드(`posts.controller.ts`)를 직접 확인한 결과:

**D1 — 실제 위반 확인됨**: `list()`와 `findVisibleOrThrow()`가 `user.role !== 'SUPER_ADMIN'`으로만 분기한다 — BRANCH_ADMIN, STAFF, **MEMBER를 전혀 구분하지 않는다**. `visibleToMember` 필드 자체가 `MockPost` 타입에도 없다. 즉 회원 계정으로 로그인해도 "교육자료"·직원 전용 `HQ_TO_BRANCH` 공지가 그대로 노출된다 — 부록 A-7이 명시한 "회원에게는 비공개가 기본값" 요구사항이 **코드로 구현된 적이 없다**. 스펙에는 있었지만 구현 시 누락된, 실제 정보 노출 결함.

**D2**: `list()`가 `this.mockData.posts.filter(...)` 결과를 그대로 반환한다 — `Query`에 `page`/`limit` 파라미터가 없고, 컨트롤러 어디에도 `slice`가 없다. 게시글이 100건이든 10,000건이든 한 번에 다 내려온다.

**BRD-T03 확인**: 최초 진단 당시 컨트롤러 `create()`만 보고 `Branch.contractStatus` 체크가 없다고 판단했으나, 실제 체크는 서비스 계층(`MockDataService.createPost`)에 있었다 — 2026-09-25 ADR-BRD-01 구현 중 재확인, `contract-termination.spec.ts`가 이미 이 케이스를 통과시키고 있었다. 오진단이었음을 기록해둔다.

## 10. ADR

### ADR-BRD-01: 회원 대상 공지 가시성 필터 (`visibleToMember`)
- **컨텍스트**: 코드 진단 결과 회원이 직원 전용 HQ 공지를 그대로 볼 수 있음이 확인됨(§6) — 부록 A-7이 이미 정해둔 규칙이 미구현
- **검토한 대안**: A 현행 / B visibleToMember 플래그 / C 전면 차단
- **결정**: B. 기존 스펙 결정을 코드로 옮김
- **결과**: 좋아진 것 — 정보 노출 결함 해소 / 감수하는 것 — 없음 / 숙제 — 없음
- **구현됨(2026-09-25)**: `MockPost.visibleToMember`(기본 false) 추가. `PostsController.isVisibleTo()`가 `list()`·`findVisibleOrThrow()`(상세/수정/삭제 공용)에서 MEMBER role일 때 `scope==='BRANCH_TO_MEMBER' || visibleToMember===true`만 통과시킨다. `CreatePostDto.visibleToMember`(SUPER_ADMIN만 의미 있음, BRANCH_TO_MEMBER는 서비스가 항상 true로 강제해 무관)로 HQ 공지 작성 시 회원 공개 여부를 선택할 수 있다. admin-web `BoardPage`의 작성 폼에 SUPER_ADMIN 전용 "회원에게도 공개" 체크박스 추가. 회귀 테스트: `apps/api/test/posts-member-visibility.spec.ts`(7케이스 — 비공개 HQ 공지가 회원 목록/상세에서 제외되는지, 직원·관리자에게는 그대로 보이는지 대조군 포함, visibleToMember=true 작성 시 노출되는지, 기본값 false 확인).

### ADR-BRD-02: 목록 조회 페이지네이션
- **컨텍스트**: `list()`가 전체 배열을 무제한 반환(§6)
- **검토한 대안**: A 현행 / B page/limit / C 커서
- **결정**: B. 기존 `ok()` meta 포맷과 일관
- **결과**: 좋아진 것 — 응답 크기 상한 확보 / 감수하는 것 — 없음 / 숙제 — 없음
- **구현됨(2026-09-25)**: `GET /posts`가 `page`(기본 1)·`limit`(기본 20) 쿼리를 받아 `ok(items, {page, pageSize, total})`로 응답한다. 잘못된 값(음수·비숫자)은 `Math.max(1, ...)`로 안전하게 1/20로 대체. **구현 중 발견한 사실**: `common/interceptors/response.interceptor.ts`에 `Paginated<T>`를 자동으로 `meta`로 바꿔주는 `ResponseInterceptor`가 이미 만들어져 있었지만 **어디에도 등록돼 있지 않아 죽은 코드였다**(main.ts·app.module.ts·test/helpers/app.ts 어디에도 `useGlobalInterceptors`/`APP_INTERCEPTOR` 없음). 이걸 지금 등록하면 이 프로젝트 전체 컨트롤러 응답에 영향을 주는 더 큰 변경이 되므로, 이번 ADR 범위 밖이라 판단해 손대지 않고 `ok(data, meta)`를 직접 호출하는 기존 방식(다른 도메인과 동일)으로 구현했다. **정리됨(2026-09-25 추가 작업)**: `git log`로 확인해보니 이 인터셉터는 `eb79377`(실DB 기반 인증/회원관리 Phase1, 이후 폐기된 `wip/real-db-auth-phase1` 브랜치의 커밋)에서 만들어진 채 한 번도 등록된 적 없이 남아있던 것이었다 — 진행 중인 미완성 작업이 아니라 이미 지나간 아키텍처 국면의 잔재였으므로, 등록(전역 영향 있는 변경)보다 삭제 쪽이 맞다고 판단해 `response.interceptor.ts`·`paginated.interface.ts` 둘 다 제거했다. admin-web `BoardPage`는 그동안 전체 목록을 한 번에 불러와 클라이언트에서 `scope` 필터링하던 방식이었는데, 서버가 페이지 단위로 자르기 시작하면 그 방식대로 두면 **21번째 글부터 조용히 안 보이는 회귀**가 생기므로 함께 고쳤다: `scope` 필터를 서버 쿼리로 옮기고, 이전/다음 페이지 버튼 + "N/M페이지(전체 T건)" 표시를 추가했다. 회귀 테스트: `apps/api/test/posts-member-visibility.spec.ts`(ADR-BRD-02 절, 5건).

## 12. 이월 사항 + 문서 마이그레이션 메모

- **DB 이관(2026-09-29, 2-1 D36)**: 게시글 원천이 `PostService`(Prisma)로 옮겨졌다. 가시성(ADR-BRD-01)은 where 조건으로, 페이지네이션(ADR-BRD-02)은 count + skip/take로 내려 아래 트래픽 이슈의 "페이지네이션 이전 전체 스캔"과 작성자·지점 N+1을 없앴다. 조회수는 원자적 증가(mock의 `+= 1`은 동시 조회 시 증가분 유실). `Post.authorId`에 외래키가 없다 — 추가는 스키마 변경이라 승인 후 후속. 화면 확인 중 삭제 직후 상세 쿼리가 무효화되며 404를 한 번 받는 것을 봤다(이관 전부터 동일, 화면 영향 없음).
- **트래픽/인프라 후보 이슈(2026-09-28, 검토 중 — 아직 ADR 아님)**: 목록 조회가 페이지네이션(ADR-BRD-02) 이전에 전체 게시글 배열을 필터링하고, 반환 항목마다 작성자·지점을 N+1 조회한다. 게시글이 삭제되지 않고 계속 쌓이는 구조라 이 필터링 비용은 계속 늘어난다 — 전체 6개 도메인 분석과 검토 방향은 [architecture/traffic-infra-review.md](../architecture/traffic-infra-review.md#게시판--심각도-중간) 참고. 대안 비교·결정 전이라 정식 ADR로 승격하지 않았다.
- `TrainingLog`(교육 실시 기록)는 부록 A-8이 "Phase 6(확장)"으로 이미 이월해놓은 항목 — 이번 사이클에서 재분석하지 않고 그대로 이월한다(RFP 근거가 있어 완전 폐기 대상은 아님).
- 옛 스펙 문서와의 겹침 판정은 [log/archive/05_문서_마이그레이션_추적.md](../log/archive/05_문서_마이그레이션_추적.md)에 기록했다(이 문서에서 실행하지 않음).

### A-6. 비즈니스 로직 & 엣지케이스
> 옛 1-5 설계서 §6 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- `scope=HQ_TO_BRANCH`이고 `branchId=null`인 게시글은 "전체 지점 공지"로 취급해 모든 BRANCH_ADMIN 화면에 노출
- BRANCH_ADMIN이 작성하는 `BRANCH_TO_MEMBER` 게시글은 자동으로 본인 `branchId`가 세팅되어(수정 불가) 다른 지점에 실수로 노출되는 것을 원천 차단
- 첨부파일 업로드는 용량 제한(예: 파일당 10MB, 이미지 5장/문서 3개까지) 및 확장자 화이트리스트(jpg/png/pdf) 적용 — 보안 요구사항(임의 파일 업로드 방지)
- 삭제는 소프트 삭제(`deletedAt`)로 처리해 회원이 이미 본 공지의 참조 무결성 유지
- 회원 앱에서는 미열람 공지 뱃지(빨간 점) 표시를 위해 `PostReadReceipt` 활용(Phase 2)
- **위탁계약 종료 지점의 게시판**: `Branch.contractStatus=TERMINATED`가 되어도 기존 게시글은 삭제하지 않고 열람만 유지합니다(소프트 삭제 원칙과 동일한 태도 — [architecture/entities.md §2-1](../architecture/entities.md#2-1-branch지점-데이터-모델--위탁계약-필드)). 다만 해당 지점을 대상으로 한 신규 `BRANCH_TO_MEMBER` 작성은 409(`BRANCH_TERMINATED`)로 차단합니다. `HQ_TO_BRANCH` 공지는 본사가 작성 주체이므로 이 제약과 무관합니다.
- **교육 실시 기록은 등록 전용, 워크플로 없음**: 승인/일정조율/알림 같은 절차는 만들지 않습니다 — 이미 일어난 교육을 사후에 기록하는 단순 로그입니다(신청→승인 흐름이 있는 인사정보관리 문서의 변경 신청과는 성격이 다름). 지점별 누적 횟수는 `TrainingLog(branchId, method='ONSITE')` 카운트로 계산하며 별도 캐시 필드를 두지 않습니다(빈도가 낮아 실시간 집계로 충분).

### A-9. 테스트 체크리스트
> 옛 1-5 설계서 §9 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- [ ] BRANCH_ADMIN이 작성한 공지가 타 지점 회원에게 노출되지 않음
- [ ] 전체공지(branchId=null)가 모든 지점 관리자에게 노출됨
- [ ] 첨부파일 10MB 초과/허용되지 않은 확장자 업로드 시 거부
- [ ] 삭제된 게시글이 목록에서 사라지되 기존 알림/참조는 깨지지 않음
- [ ] BRANCH_ADMIN이 교육 실시 기록 등록 API 호출 시도 시 403(SUPER_ADMIN 전용)
- [ ] 지점별 대면(ONSITE) 교육 횟수가 정확히 집계됨
