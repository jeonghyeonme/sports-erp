## 0. 이 도메인 개요 (사용자 스토리)

- 본사 관리자로서, 전 지점(또는 특정 지점)에 공지를 올리고 필요시 교육자료 파일을 첨부하고 싶다.
- 지점 관리자로서, 본사 공지를 확인하고 우리 지점 회원들에게 전달할 공지를 따로 작성하고 싶다.
- 회원으로서, 내가 다니는 지점의 공지사항을 앱에서 확인하고 싶다.

### 제약
- 첨부파일 실제 업로드 인프라(용량 제한·확장자 검증·스토리지)는 이번 범위에서 제외 — 1-5문서 §8이 이미 명시, 문서관리(`1-10`)와 동일하게 URL 방식으로 대체 가능.

### 불변규칙 (협의 불가)
1. **BRANCH_TO_MEMBER 게시글은 작성 지점 회원에게만 노출된다.** (CLAUDE.md 지점 데이터 격리 정신의 연장 — 타 지점 공지가 새어나가면 안 됨)
2. **회원(Role=MEMBER)은 직원 대상 내부 공지를 볼 수 없다.** (1-5문서 §7이 이미 "HQ 공지는 기본적으로 직원 대상, 회원에게는 비공개가 기본값"이라고 명시 — 협의 대상이 아니라 이미 확정된 요구사항)

## 6. 현행 구조 진단 (Baseline)

코드(`posts.controller.ts`)를 직접 확인한 결과:

**D1 — 실제 위반 확인됨**: `list()`와 `findVisibleOrThrow()`가 `user.role !== 'SUPER_ADMIN'`으로만 분기한다 — BRANCH_ADMIN, STAFF, **MEMBER를 전혀 구분하지 않는다**. `visibleToMember` 필드 자체가 `MockPost` 타입에도 없다. 즉 회원 계정으로 로그인해도 "교육자료"·직원 전용 `HQ_TO_BRANCH` 공지가 그대로 노출된다 — 1-5문서 §7이 명시한 "회원에게는 비공개가 기본값" 요구사항이 **코드로 구현된 적이 없다**. 스펙에는 있었지만 구현 시 누락된, 실제 정보 노출 결함.

**D2**: `list()`가 `this.mockData.posts.filter(...)` 결과를 그대로 반환한다 — `Query`에 `page`/`limit` 파라미터가 없고, 컨트롤러 어디에도 `slice`가 없다. 게시글이 100건이든 10,000건이든 한 번에 다 내려온다.

**BRD-T03 확인**: 최초 진단 당시 컨트롤러 `create()`만 보고 `Branch.contractStatus` 체크가 없다고 판단했으나, 실제 체크는 서비스 계층(`MockDataService.createPost`)에 있었다 — 2026-09-25 ADR-BRD-01 구현 중 재확인, `contract-termination.spec.ts`가 이미 이 케이스를 통과시키고 있었다. 오진단이었음을 기록해둔다.

## 10. ADR

### ADR-BRD-01: 회원 대상 공지 가시성 필터 (`visibleToMember`)
- **컨텍스트**: 코드 진단 결과 회원이 직원 전용 HQ 공지를 그대로 볼 수 있음이 확인됨(§6) — 1-5문서 §7이 이미 정해둔 규칙이 미구현
- **검토한 대안**: A 현행 / B visibleToMember 플래그 / C 전면 차단
- **결정**: B. 기존 스펙 결정을 코드로 옮김
- **결과**: 좋아진 것 — 정보 노출 결함 해소 / 감수하는 것 — 없음 / 숙제 — 없음
- **구현됨(2026-09-25)**: `MockPost.visibleToMember`(기본 false) 추가. `PostsController.isVisibleTo()`가 `list()`·`findVisibleOrThrow()`(상세/수정/삭제 공용)에서 MEMBER role일 때 `scope==='BRANCH_TO_MEMBER' || visibleToMember===true`만 통과시킨다. `CreatePostDto.visibleToMember`(SUPER_ADMIN만 의미 있음, BRANCH_TO_MEMBER는 서비스가 항상 true로 강제해 무관)로 HQ 공지 작성 시 회원 공개 여부를 선택할 수 있다. admin-web `BoardPage`의 작성 폼에 SUPER_ADMIN 전용 "회원에게도 공개" 체크박스 추가. 회귀 테스트: `apps/api/test/posts-member-visibility.spec.ts`(7케이스 — 비공개 HQ 공지가 회원 목록/상세에서 제외되는지, 직원·관리자에게는 그대로 보이는지 대조군 포함, visibleToMember=true 작성 시 노출되는지, 기본값 false 확인).

### ADR-BRD-02: 목록 조회 페이지네이션
- **컨텍스트**: `list()`가 전체 배열을 무제한 반환(§6)
- **검토한 대안**: A 현행 / B page/limit / C 커서
- **결정**: B. 기존 `ok()` meta 포맷과 일관
- **결과**: 좋아진 것 — 응답 크기 상한 확보 / 감수하는 것 — 없음 / 숙제 — 없음
- **구현됨(2026-09-25)**: `GET /posts`가 `page`(기본 1)·`limit`(기본 20) 쿼리를 받아 `ok(items, {page, pageSize, total})`로 응답한다. 잘못된 값(음수·비숫자)은 `Math.max(1, ...)`로 안전하게 1/20로 대체. **구현 중 발견한 사실**: `common/interceptors/response.interceptor.ts`에 `Paginated<T>`를 자동으로 `meta`로 바꿔주는 `ResponseInterceptor`가 이미 만들어져 있었지만 **어디에도 등록돼 있지 않아 죽은 코드였다**(main.ts·app.module.ts·test/helpers/app.ts 어디에도 `useGlobalInterceptors`/`APP_INTERCEPTOR` 없음). 이걸 지금 등록하면 이 프로젝트 전체 컨트롤러 응답에 영향을 주는 더 큰 변경이 되므로, 이번 ADR 범위 밖이라 판단해 손대지 않고 `ok(data, meta)`를 직접 호출하는 기존 방식(다른 도메인과 동일)으로 구현했다. **정리됨(2026-09-25 추가 작업)**: `git log`로 확인해보니 이 인터셉터는 `eb79377`(실DB 기반 인증/회원관리 Phase1, 이후 폐기된 `wip/real-db-auth-phase1` 브랜치의 커밋)에서 만들어진 채 한 번도 등록된 적 없이 남아있던 것이었다 — 진행 중인 미완성 작업이 아니라 이미 지나간 아키텍처 국면의 잔재였으므로, 등록(전역 영향 있는 변경)보다 삭제 쪽이 맞다고 판단해 `response.interceptor.ts`·`paginated.interface.ts` 둘 다 제거했다. admin-web `BoardPage`는 그동안 전체 목록을 한 번에 불러와 클라이언트에서 `scope` 필터링하던 방식이었는데, 서버가 페이지 단위로 자르기 시작하면 그 방식대로 두면 **21번째 글부터 조용히 안 보이는 회귀**가 생기므로 함께 고쳤다: `scope` 필터를 서버 쿼리로 옮기고, 이전/다음 페이지 버튼 + "N/M페이지(전체 T건)" 표시를 추가했다. 회귀 테스트: `apps/api/test/posts-member-visibility.spec.ts`(ADR-BRD-02 절, 5건).

## 부록 A. 레퍼런스 스펙 (결정을 반영한 현재 상태)

> §1~12(분석·결정)의 **결과물**이다. 옛 [1-5_게시판_공지사항.md](../1.spec/30_운영지원/1-5_게시판_공지사항.md)에서 병합했다.

### A-1. 데이터 모델

**Post**: `id, scope(HQ_TO_BRANCH/BRANCH_TO_MEMBER), branchId(FK, nullable), authorId(FK), category(공지/교육자료/이벤트/기타), title, content, attachments(URL 방식), pinned(미구현), viewCount, visibleToMember(boolean, 기본 false — ADR-BRD-01, 구현됨), publishedAt, deletedAt, createdAt/updatedAt`

**Attachment**: `id, postId(FK), url, fileName, fileType` — 실제 업로드 대신 URL 방식.

**TrainingLog**(이월, 미구현): `id, branchId(FK), conductedAt, method(ONSITE/ONLINE), attendeeStaffId(FK, nullable), materialPostId(FK, nullable), conductedBy(FK), note` — 지점별 대면교육 2회 이상 요건 집계용.

**PostReadReceipt**: 범위 제외(2026-09-20, RFP 요구 아님).

### A-2. 화면 목록
| 화면 | 대상 | 상태 |
|---|---|---|
| 본사 공지 목록/작성 | SUPER_ADMIN | 구현됨(첨부 제외) |
| 지점 게시판(본사 공지 열람) | BRANCH_ADMIN | 구현됨 |
| 지점 공지 작성 | BRANCH_ADMIN | 구현됨 |
| 회원 공지함 | Member(앱) | admin-web은 구현, Member 앱은 Phase 3 미착수 |
| 교육자료함 | BRANCH_ADMIN | category 필터 UI 미구현 |
| 교육 실시 기록 | SUPER_ADMIN | 미구현 |

### A-3. API 명세
| Method | Endpoint | 권한 | 구현 상태 |
|---|---|---|---|
| GET | /api/v1/posts?scope=&page=&limit= | scope별 권한 분기 | 구현됨, 회원 가시성 필터 구현됨(ADR-BRD-01), 페이지네이션 구현됨(ADR-BRD-02, 기본 limit=20) |
| POST | /api/v1/posts | SUPER_ADMIN/BRANCH_ADMIN | 구현됨, 계약종료 지점 차단 구현됨(BRD-T03), `visibleToMember` 지정 가능(SUPER_ADMIN, ADR-BRD-01) |
| GET | /api/v1/posts/:id | 열람 권한자 | 구현됨(viewCount 증가 포함) |
| PATCH | /api/v1/posts/:id | 작성자 본인 | 구현됨 |
| DELETE | /api/v1/posts/:id | 작성자 본인 또는 SUPER_ADMIN | 구현됨(소프트 삭제) |
| POST | /api/v1/posts/:id/attachments | 작성자 | 미구현(URL 방식이면 `create`/`update` DTO에 포함하는 형태로 대체 가능, 별도 엔드포인트 불필요) |
| POST | /api/v1/training-logs | SUPER_ADMIN | 미구현 |
| GET | /api/v1/training-logs?branchId= | SUPER_ADMIN, BRANCH_ADMIN(본인 지점) | 미구현 |

### A-4. 권한 요약
- HQ_TO_BRANCH 작성: SUPER_ADMIN만
- BRANCH_TO_MEMBER 작성: BRANCH_ADMIN(본인 지점), 회원은 읽기 전용
- STAFF: 본인 지점 게시글 조회만
- MEMBER: 본인 지점 BRANCH_TO_MEMBER + `visibleToMember=true`인 HQ 공지만(ADR-BRD-01, 구현·검증됨)

### A-5. 구현 우선순위
**Phase 1(완료, 2026-09-18)**: Post CRUD·scope 분기·목록/상세 화면. 첨부파일 업로드·`pinned`는 제외.
**Phase 2**: viewCount 증가 구현됨. 읽음 확인·category 필터 UI 미구현.
**Phase 6(확장, 미착수)**: TrainingLog.
