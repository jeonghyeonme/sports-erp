## 0. 이 도메인 개요 (사용자 스토리)

- 회원으로서, 원하는 프로그램의 회차를 조회하고 예약하고 싶다.
- 회원으로서, 유료 회차는 예약 후 모의결제로 확정하고 싶다.
- 회원으로서, 사정이 생기면 예약을 취소하고(마감시간 전이면) 환불받고 싶다.
- 지점 관리자로서, 회원이 현장에 도착하면 체크인 처리하고 싶다.
- 지점 관리자로서, 우리 지점 예약·결제 현황을 조회하고 싶다(타 지점은 불가).

RFP는 "무/유료 프로그램 정보 게시 후 프로그램별 예약, 모바일 결제 기능"만 요구하고 "결제내역 처리방법은 추후 논의"로 남겼다(F06). 이 도메인은 그 공백을 **모의결제 + 상태 전이만 구현하되 외부 결제 연동 시 필요한 경계는 미리 준비**하는 방식으로 메운다(Q-05, §8 D3).

4. **결제 금액은 클라이언트가 아니라 서버가 Program 가격을 재조회해 결정한다.** (기본적인 결제 보안 원칙 — 협의 대상 아님)

## 6. 현행 구조 진단 (Baseline)

**D1**: 부록 A-6이 이미 이 진단을 상세히 해 뒀다(2026-09-15 "락 대상 정정") — 그대로 가져온다. 기존 설계(`SELECT COUNT(*) FROM Reservation WHERE scheduleSlotId=? FOR UPDATE`)는 **이미 존재하는 행에만** 락을 건다. 정원이 비어 있는(기존 예약 0건) 회차에 두 트랜잭션이 동시에 이 쿼리를 실행하면 둘 다 잠글 대상이 없어 그대로 통과하고 둘 다 `INSERT`할 수 있다 — 팬텀 삽입. 이게 D1을 만든 원인이다.
현재 Mock 구현은 `MockDataService`가 단일 Node 프로세스에서 동기 실행되는 인메모리 배열이라는 점을 이용해, 별도 락 코드 없이도 팬텀 삽입이 원천적으로 안 일어난다(부록 A-8) — **실DB 전환 시 문서의 락 방식을 그대로 적용해야 한다**는 전제가 이미 문서화돼 있다.

**D2**: `createReservation`은 애플리케이션 레벨에서만 중복을 체크한다(`this.reservations.find(...)`). 실DB에서 이 체크와 `INSERT` 사이에 경합이 생기면(동시 요청 두 건이 모두 "중복 없음"을 확인한 뒤 둘 다 삽입) 뚫릴 수 있다.

**D3**: `mockPay`는 `MockDataService`의 평범한 동기 메서드일 뿐, 결제 게이트웨이를 추상화하는 인터페이스가 없다. 나중에 실제 PG를 붙이려면 이 메서드 내부를 통째로 바꿔야 하고, 타임아웃·재시도·서킷브레이커 개념이 들어갈 자리가 코드에 아예 없다.

## 8. 대안 → 트레이드오프 → 결정

### 질문 1: 정원 초과 방지 락 대상

| 대안 | 장점 | 단점 |
|---|---|---|
| A. `SELECT COUNT(*) ... FOR UPDATE`(기존 설계, 카운트 대상 락) | 직관적 | **팬텀 삽입**(§6 baseline) — 신규 개설 회차에서만 뚫리는, 발견하기 어려운 결함 |
| **B. `SELECT * FROM ScheduleSlot WHERE id=? FOR UPDATE`로 회차 행을 먼저 잠근다 (채택)** | 회차 행은 예약이 0건이어도 항상 존재해 반드시 잠글 대상이 있음 — 두 번째 트랜잭션이 첫 번째 커밋까지 대기, 이후 `COUNT` 쿼리엔 `FOR UPDATE` 불필요(이미 직렬화됨) | 회차 단위로 락이 걸려 같은 회차의 다른 연산(예: 정원 수정)과 짧게 경합 가능 |
| C. 낙관적 락(버전 컬럼) | 경합 적을 때 처리량 높음 | 인기 회차는 경합이 집중돼 재시도 비용이 커짐 — 정원이 딱 채워지는 순간이 이 시스템의 정상 상태라 오히려 최악의 경우가 흔함 |

**결정**: B. 판단 기준: 불변규칙 1을 "항상" 만족시켜야 하는데 A는 신규 개설 회차라는 흔한 케이스에서 뚫린다. C는 이 도메인의 트래픽 패턴(인기 회차 집중)과 안 맞음.
**감수하는 것**: 지금(Mock)은 실측 불가능한 가설이다 — 실DB 전환 후 부하·동시성 테스트로 검증해야 한다(§11 "남은 것").

### 질문 2: 중복 예약 방지 강제 계층

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 애플리케이션 체크만(현행) | 구현됨, 단순 | 경합 시 우회 가능(§6 baseline) |
| **B. 애플리케이션 체크 + 부분 unique 인덱스(`Reservation(memberId, scheduleSlotId) WHERE status IN ('REQUESTED','CONFIRMED')`) 이중화 (채택)** | 이 프로젝트의 표준 패턴(회원관리 ADR-MEM-02, 인사정보관리 ADR-STF-03과 동일 원칙) — 이 도메인이 사실 그 패턴의 **원조**다. 취소 이력이 쌓여도 활성 상태만 걸리므로 재예약은 항상 허용 | MockDataService에는 부분 인덱스가 없어 지금은 A만으로 방어 — **실DB에는 적용됨(2026-09-29, D27: `Reservation_memberId_scheduleSlotId_active_key`, 이전 스키마의 전역 unique는 재예약을 막아 이 ADR과 모순이었음)** |

**결정**: B. 판단 기준: 애플리케이션 체크 단독은 경합에 취약하다는 게 이미 이 문서에 명시돼 있고, DB 레벨 이중화가 이 프로젝트의 검증된 표준.
**감수하는 것**: 지금은 가설이다 — 실DB 전환 시 적용.

### 질문 3: 결제 모듈의 실연동 대비 경계

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 지금처럼 `mockPay`를 평범한 메서드로 유지, 실PG 전환 시 내부를 통째로 교체 | 지금 가장 적은 코드 | 나중에 타임아웃·재시도·서킷브레이커까지 한 번에 새로 설계해야 함 — 재작성 비용이 이연될 뿐 사라지지 않음 |
| **B. `PaymentGateway` 인터페이스를 지금 도입하고 `MockPaymentGateway` 구현체 하나만 꽂는다 (채택)** | 영상의 "결제 모듈을 어댑터로 분리" 결정과 동일 원리 — 실PG 추가 시 예약 도메인 코드는 안 건드림 | 지금 당장 쓰임새가 하나뿐인 추상화 계층(YAGNI 우려) |
| C. 요청은 동기/알림은 비동기로 분리(영상 원안) | 외부 장애 격리가 가장 강함 | 메시지 큐·이벤트 버스가 이 프로젝트에 없음 — 인프라 초과 |

**결정**: B. 판단 기준: 이 프로젝트는 "나중에 필요해지면 그때 확장"이 아니라 "지금 배관만 놓아두면 나중 비용이 적은 것"을 우선한 전례가 있다(이 문서의 부가세 분리를 Phase 1로 앞당긴 것과 같은 태도). C는 인프라가 없어 배제.
**감수하는 것**: 지금은 구현체가 Mock 하나뿐이라 인터페이스의 가치가 눈에 보이지 않는다 — 실PG를 실제로 붙이기 전까지는 "왜 이렇게 했나"를 코드만 보고는 설득하기 어렵다(그래서 이 ADR이 필요하다).

## 9. 감수하는 것 (종합)

- D1·D2: 정확히 권한관리·인사정보관리 도메인과 같은 처지 — Mock 환경에서는 검증도 실효도 없는 가설이다.
- D3: 지금 당장 이득이 안 보이는 추상화를 미리 넣는 결정이라, 실PG 연동 전까지는 "과한 설계 아니냐"는 의문이 계속 남는다.
- **이 사이클 전체가 감수하는 것**: 가장 정교한 설계를 가진 도메인이 가장 테스트가 없다(§11) — Driver 결정의 품질과 검증 수준이 반비례하는 상태를 그대로 보고한다.

## 10. ADR

### ADR-RSV-01: 정원 초과 방지 — ScheduleSlot 행 락
- **컨텍스트**: 카운트 대상 락은 신규 개설 회차에서 팬텀 삽입으로 뚫림(§6 baseline)
- **검토한 대안**: A 카운트 FOR UPDATE / B 회차 행 FOR UPDATE / C 낙관적 락
- **결정**: B. 항상 잠글 대상이 있음 + 인기 회차 트래픽 패턴과 부합
- **결과**: 좋아진 것 — 신규 개설 회차 포함 모든 경우에 정원 보장 / 감수하는 것 — 실측 전 가설 / 숙제 — 실DB 전환 후 부하·동시성 테스트

- **구현 준비(2026-09-29, D28)**: 헬퍼 `lockScheduleSlot`(`apps/api/src/prisma/integrity.ts`)을 실DB에서 검증했다 — 예약 0건인 신규 회차(정원 2)에 5명 동시 요청 시 정확히 2건만 확정, 락 없는 대조군은 정원 초과. "실측 전 가설"이던 감수 사항이 로컬 Postgres 기준으로 해소됐다(부하 수준 재검증은 이관 후 k6로). 회차 정원 ≥ 1, 공급가액+부가세=결제금액은 CHECK로 이중화됐다([architecture/data-integrity.md](../architecture/data-integrity.md)).

- **새로 발견·수정한 격리 결함(2026-09-29, DI-02)**: `createReservation`이 회원 지점과 프로그램 지점을 비교하지 않아, 회차 id만 알면 **다른 지점 회차를 예약할 수 있었다**(회차 조회는 막혀 있어 화면에선 안 보였음). `MEMBER_BRANCH_MISMATCH`(403) 앱 검증 + `reservation_branch` DB 트리거로 막았다. 회귀 테스트: `branch-isolation.spec.ts`("회원 수진은 다른 지점 프로그램 회차를 예약할 수 없다"), 수정 전 코드에서 201로 실패함을 확인.

### ADR-RSV-02: 중복 예약 방지 — 애플리케이션 체크 + 부분 unique 인덱스 이중화
- **컨텍스트**: 애플리케이션 체크 단독은 경합 시 우회 가능(§6 baseline)
- **검토한 대안**: A 애플리케이션만 / B 이중화
- **결정**: B. 이 프로젝트의 표준 패턴(회원관리·인사정보관리와 동일 원칙) — 이 도메인이 원조
- **결과**: 좋아진 것 — DB가 최종 방어선 / 감수하는 것 — 지금은 A만 실효 / 숙제 — 실DB 전환 시 적용

### ADR-RSV-03: 결제 모듈 — PaymentGateway 어댑터 인터페이스 도입
- **컨텍스트**: 실PG 전환 시 예약 도메인까지 재작성해야 하는 구조(§6 baseline)
- **검토한 대안**: A 현행 유지 / B 어댑터 인터페이스 / C 동기/비동기 분리
- **결정**: B. "나중 비용을 줄이는 배관을 지금 놓는다"는 이 프로젝트의 기존 태도와 일치, C는 인프라 초과
- **결과**: 좋아진 것 — 실PG 추가 시 예약 도메인 무변경 / 감수하는 것 — 지금은 가치가 안 보이는 추상화 / 숙제 — 없음(구현만 남음)

### ADR-RSV-04: 결제 목록의 날짜 필터를 DB 조건으로 내리고 페이지네이션한다 (2026-10-07, B4)
- **컨텍스트**: `GET /payments`(`payment.service.ts` `list`)는 지점 범위의 **결제 이력 전체**를 읽은 뒤 `dateFrom`·`dateTo`를 메모리에서 거른다. D32 결정 5에서 KST 날짜 비교로 고칠 때 이 구조가 그대로 남았다. 결제는 예약과 같은 속도로 쌓인다(design-constants ⑮, 하루 약 1,700건 가정). 그래서 날짜를 좁혀도 비용은 누적 이력 크기에 비례한다. 이 도메인은 traffic-infra-review 1차 스캔에서 빠졌다가 B4에서 새로 찾았다.
- **검토한 대안**: A 현행(메모리 필터) / B KST 날짜 경계를 `approvedAt` 범위 조건으로 바꿔 where에 넣고, D43 페이지네이션을 함께 적용 / C 날짜 범위를 필수로 요구
- **결정**: B. 메모리 필터를 그대로 두고 페이지네이션만 붙이면 total과 쪽이 틀린다(D43 결정 3). 지금 규칙 "미승인 건은 날짜 필터에서 빠지지 않는다"는 `approvedAt IS NULL OR 범위`로 그대로 옮긴다. C는 매출 화면의 "전체 기간" 조회를 막아 화면 변경이 더 크다.
- **결과**: 좋아진 것 — 비용이 조회 기간·쪽 크기에 묶인다 / 감수하는 것 — KST 경계 계산(`kst-date.ts`)을 쿼리 쪽에 하나 더 둔다 / 숙제 — B8에서 구현한다. 이때 KST 경계 회귀 테스트를 추가한다(지금 날짜 필터는 자동 테스트 없음, §11). `Payment(approvedAt)` 인덱스는 스키마 변경이라 사용자 승인 대상이다. 지점 범위 조인만으로 충분한지 먼저 재 보고 판단한다.

### ADR-RSV-05: 이미 시작했거나 지난 회차는 예약할 수 없다 (2026-10-08, B1-3)
- **컨텍스트**: `POST /reservations`는 회차 날짜를 보지 않았다. 회원 웹(B1-2, log/083)은 지난 회차를 화면에서 숨기지만, api를 직접 부르면 지난 회차도 예약·결제됐다. 시드 회차(`slot-seocho-yoga-1·2`)가 2026-09-21·22로 고정돼 있어 테스트는 그동안 지난 회차를 예약하고 있었다.
- **검토한 대안**: A 화면에서만 숨김(현행) / B api가 회차 시작 시각(KST)을 지났으면 409 / C 회차 날짜만 비교(오늘 회차는 허용)
- **결정**: B(사용자 결정 2026-10-08). 판정은 `회차 시작 시각 <= 지금`이며 시각은 KST(`+09:00`)로 해석한다(D32 결정 5, 취소 마감과 같은 함수 `kstSlotStart`). 검사 순서는 계약 종료 다음, 중복 앞이다. C는 이미 끝난 오늘 아침 회차를 예약하게 둔다.
- **결과**: 좋아진 것 — 화면을 거치지 않는 호출도 막힌다 / 감수하는 것 — 테스트가 시드 회차를 예약하려면 미래 날짜여야 한다. 워커 DB를 만들 때 두 회차를 오늘(KST)+7·+8일로 옮긴다(`test/setup/test-db.ts` `moveSeedSlotsToFuture`). 기준 DB와 시드 원천은 그대로다 / 숙제 — 없음
- **재고 트리거**: 시작 후 일정 시간까지 지각 예약을 받자는 요구가 생기면 지점 설정으로 유예 시간을 둔다.

**중복예약 방지 제약 — 조건부 unique로 정정(2026-09-15)**: `(memberId, scheduleSlotId)`에 **무조건적인** unique 제약을 걸면 안 됩니다 — 회원이 한 번 취소(`CANCELLED`)한 회차는 그 조합이 이미 테이블에 남아있어, 같은 회원이 같은 회차를 다시는 예약할 수 없게 막혀버립니다(§6 "REQUESTED/CONFIRMED 상태일 때만 재예약 차단"이라는 의도와 어긋남). PostgreSQL의 **부분 unique 인덱스(partial unique index)**로 정정합니다: `CREATE UNIQUE INDEX ON "Reservation" (memberId, scheduleSlotId) WHERE status IN ('REQUESTED','CONFIRMED')` — Prisma 스키마는 조건부 unique를 선언적으로 표현하지 못하므로 마이그레이션에 raw SQL로 추가해야 합니다. 이렇게 하면 "활성 예약은 회원당 회차당 1건"만 강제되고, 취소된 이력은 몇 건이 쌓여도 재예약을 막지 않습니다.

### A-6. 비즈니스 로직 & 엣지케이스 (이 기능이 가장 까다로운 영역 — 상세 기술)
> 옛 1-7 설계서 §6 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- **동시 예약(정원 초과) 방지 — 락 대상 정정(2026-09-15)**: 기존 설계(`SELECT COUNT(*) FROM Reservation WHERE scheduleSlotId=? ... FOR UPDATE`)는 **기존에 이미 존재하는 Reservation 행에만** 락을 겁니다. 정원이 비어있거나(기존 예약 0건) 여유가 있을 때 두 트랜잭션이 동시에 이 쿼리를 실행하면 **둘 다 잠글 대상이 없어 그대로 통과**하고 둘 다 `INSERT`할 수 있습니다(팬텀 삽입 — `FOR UPDATE`는 존재하는 행의 수정·삭제만 막지, 새 행이 끼어드는 것은 막지 못함). 이러면 이 로직이 막으려던 정원 초과가 그대로 발생합니다.
  - **정정된 방식**: `bookedCount`를 별도 캐시 필드로 두지 않는 원칙은 유지하되, 잠그는 대상을 "카운트할 테이블"이 아니라 **"정원이 걸려있는 리소스 자체"**로 바꿉니다 — 트랜잭션 시작 시 먼저 `SELECT * FROM ScheduleSlot WHERE id=? FOR UPDATE`로 회차 행을 잠급니다(회차 행은 예약이 0건이어도 항상 존재하므로 반드시 잠금 대상이 있고, 두 번째 트랜잭션은 첫 번째가 커밋할 때까지 이 시점에서 대기하게 됨). 그 다음에야 `SELECT COUNT(*) FROM Reservation WHERE scheduleSlotId=? AND status IN ('REQUESTED','CONFIRMED')`로 현재 인원을 세고 `capacity`와 비교 → 초과 시 409(`SLOT_FULL`), 아니면 `INSERT`. `ScheduleSlot` 락이 이미 두 트랜잭션을 순서대로 직렬화하므로 이 두 번째 `SELECT`엔 `FOR UPDATE`가 필요 없습니다.
  - 포트폴리오에서 "동시성 처리를 고려했다"를 보여줄 수 있는 포인트라는 원래 취지는 그대로 유지되고, 오히려 "왜 카운트 대상이 아니라 리소스 자체를 잠가야 하는지"까지 설명할 수 있어 더 설득력 있는 포인트가 됩니다.
- **중복 예약 방지**: 동일 회원이 동일 회차에 이미 `REQUESTED`/`CONFIRMED` 상태 예약이 있으면 재예약 차단 — 애플리케이션 레벨 체크뿐 아니라 §3의 부분 unique 인덱스가 DB 레벨에서도 강제합니다(둘 중 하나만 있으면 동시 요청 경합 시 애플리케이션 체크를 우회할 수 있음). `CANCELLED`/`COMPLETED`/`NO_SHOW` 이력은 몇 건이 쌓여도 재예약을 막지 않습니다
- **진행중이 아닌 프로그램**: `Program.status`가 `PREPARING`/`PAUSED`/`ENDED`인 프로그램에는 예약 자체가 불가합니다(409 `PROGRAM_NOT_RUNNING`) — 강사프로그램게시 A-3
- **자유이용형(`FREE_ACCESS`) 프로그램**: 애초에 이 API의 대상이 아닙니다. 예약이라는 개념 자체가 없고, 이용 기록은 혼잡도관리 문서의 `FacilityCheckIn`(QR 체크인)만으로 남습니다 — `Reservation`/`Payment` 어느 쪽에도 row가 생기지 않음
- **무료 회차(`PAID_SESSION`, price=0)**: 정원 관리는 필요하지만 결제는 없는 경우 — Payment 레코드 없이 즉시 `Reservation.status=CONFIRMED`
- **유료 회차(`PAID_SESSION`, price>0) 결제 흐름**: `예약 생성(status=REQUESTED, Payment.status=PENDING)` → `모의결제 승인 API 호출` → 성공 시 `Payment.status=APPROVED` + `Reservation.status=CONFIRMED`. 5분 내 결제 미완료 시 예약 자동 취소(배치 or TTL) — 좌석 선점 방지
- **취소/환불 정책**: 회차 시작 `Branch.cancellationDeadlineHours`시간 전(기본 24시간) 취소는 전액 환불, 그 이내는 환불 불가(architecture/entities.md §2-1 참고 — 하드코딩 금지, Program 단위 override 필요 시 Program에도 nullable로 추가). 모의결제이므로 실제 환불 처리는 상태값만 변경(`Payment.status=REFUNDED`)
- **부가세 분리는 이제 구현**: `Payment` 생성 시 `amount`(회원이 실제로 낸 금액)만 입력받고, 서버가 `supplyAmount = round(amount / 1.1)`, `vat = amount - supplyAmount`를 자동 계산해 저장합니다. 환불(`REFUNDED`) 시에도 두 값을 그대로 보존해(0으로 리셋하지 않음) 환불 전 매출 이력이 감사 목적으로 남도록 합니다.
- **청약철회권은 여전히 의도적 범위 외**: 전자상거래법상 소비자 청약철회권과 "24시간 전 취소" 정책의 정합성은 실서비스라면 약관에 명시해야 하지만, Mock Payment로 실제 법적 분쟁 리스크가 없는 이 프로젝트에서는 다루지 않습니다(D14와 동일한 판단 — 부가세와 달리 이건 "돈이 실제로 오가지 않으므로" 시스템에 배관을 놓을 유인 자체가 없는 항목이라 구분했습니다).
- **매출 집계(`/revenue/summary`)**: `Payment.status=APPROVED`인 건만 집계 대상(PENDING/FAILED는 매출 아님, REFUNDED는 환불 시점 이후 매출에서 제외 — 즉 `status=APPROVED`인 것만 더하고 `REFUNDED`로 전환된 건은 자동으로 집계에서 빠짐). 지점 매출은 `Payment.memberId`가 속한 회원의 `branchId`가 아니라 **결제 대상 프로그램의 `branchId`**로 집계합니다(회원이 타 지점 프로그램을 이용하는 경우는 없지만, 향후 확장을 대비해 명시).
- **강사 정산 생성(`/settlements/instructors/generate`)**: 지정 월의 `Program.instructorId`가 있는 모든 프로그램의 `Payment(status=APPROVED, approvedAt이 해당 월)`을 강사별로 그룹핑해 `supplyAmount` 합계를 `grossRevenue`로, 그 시점 `Instructor.commissionRate`를 스냅샷으로 `InstructorSettlement`를 일괄 생성합니다. `commissionRate`가 `null`인 강사(본사 직속 등 별도 급여 체계)는 정산 생성 대상에서 제외합니다.
- **원천징수 계산**: `withholdingTax = round(commissionAmount * 0.033)`(사업소득세 3% + 지방소득세 0.3%, 국세청 기준 표준 세율). 이 금액은 실제 홈택스 신고·지급명세서 제출로 이어져야 하지만, 그 연동은 사업자 인증이 필요해 범위 밖 — 화면에는 "원천징수영수증 발급 대상"이라는 안내만 노출합니다(Mock).
- **정산 확정 후 불변**: `CONFIRMED` 이후에는 `grossRevenue`가 재계산되지 않습니다(예: 확정 후 환불이 발생해도 해당 월 정산은 소급 변경하지 않고 다음 달 정산에서 마이너스로 조정) — 급여성 지급의 소급 변경은 실무에서도 지양되는 방식입니다.
- **위탁계약 종료 지점 차단**: 예약 생성 API는 예약 대상 프로그램의 `Branch.contractStatus`가 `TERMINATED`면 409(`BRANCH_TERMINATED`)로 거부합니다 — [architecture/entities.md §2-1](../architecture/entities.md#2-1-branch지점-데이터-모델--위탁계약-필드)의 "신규 예약 차단" 원칙의 실제 구현 지점입니다
- **노쇼 처리**: 회차 종료 후 체크인 안 된 `CONFIRMED` 예약은 배치로 `NO_SHOW` 처리(환불 대상 아님)
- **PT세션형(`PT_PACKAGE`) 프로그램과의 관계**: 회원관리 문서의 `PTSession`으로 별도 관리하며, `Program.pricingType=PT_PACKAGE`로 어느 트랙을 탈지 판별. **패키지 구매(`PTSession` 생성) 시점에 `Payment(ptSessionId=...)`를 함께 생성해 매출로 기록**하고, 이후 세션을 실제로 쓸 때(`usedSessions` 차감)는 이미 선불 결제된 것이므로 추가 Payment 없이 차감만 처리합니다 — Reservation/Payment 트랙과는 여전히 분리되지만, PT 매출 자체는 Payment를 통해 매출 집계·정산에 반영됩니다(위 비고 참고)

### A-7. 권한 요약

- 회원은 본인 예약만 생성/취소/조회
- BRANCH_ADMIN은 본인 지점 프로그램에 연결된 예약만 조회/체크인/취소
- 결제 금액은 서버 재조회(불변규칙 4)
- 강사 정산 생성·확정·지급은 SUPER_ADMIN 전용이지만 **범위 제외**(RSV-T07) — 화면 자체가 없음

### A-9. 테스트 체크리스트
> 옛 1-7 설계서 §9 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- [ ] 정원이 1자리 남은 회차에 2명이 동시에 예약 요청 → 1명만 성공
- [ ] **기존 예약이 0건인(방금 개설된) 회차에 정원만큼(또는 그 이상) 동시 예약 요청 → 정확히 `capacity`만큼만 성공**(팬텀 삽입 시나리오 — `ScheduleSlot` 락 없이는 이 케이스에서만 뚫림)
- [ ] 동일 회원이 같은 회차 중복 예약 시도 시 차단
- [ ] **회원이 예약을 취소(`CANCELLED`)한 뒤 같은 회차를 다시 예약 시도 → 정상 성공**(부분 unique 인덱스가 활성 상태만 막는지 확인 — 무조건적 unique였다면 여기서 실패했을 것)
- [ ] 유료 예약 후 결제 미완료 상태에서 취소 시 정상 롤백
- [ ] 취소 정책 시간(24시간) 기준 환불 여부 분기 정확히 동작
- [ ] BRANCH_ADMIN이 타 지점 예약을 체크인 처리 시도 시 403
- [ ] `FREE_ACCESS`/`PT_PACKAGE` 프로그램에 예약 생성 시도 시 400(NOT_RESERVABLE)
- [ ] `PAUSED`/`ENDED` 상태 프로그램에 예약 생성 시도 시 409(PROGRAM_NOT_RUNNING)
- [ ] 결제 승인 시 `supplyAmount + vat = amount`가 항상 성립(반올림 오차 없이 합산 일치)
- [ ] PT 패키지 구매(`PTSession` 생성) 시 `Payment(ptSessionId=...)`가 함께 생성되고 매출 집계에 반영됨
- [ ] `reservationId`·`ptSessionId`가 둘 다 null이거나 둘 다 값이 있는 Payment 생성 시도 시 거부
- [ ] 정산 생성 시 `commissionRate=null`인 강사는 대상에서 제외됨
- [ ] 원천징수액이 `commissionAmount * 3.3%`로 정확히 계산됨
- [ ] BRANCH_ADMIN이 정산 확정/지급 API 호출 시도 시 403(SUPER_ADMIN 전용)
- [ ] 같은 강사·같은 월에 정산 중복 생성 시도 시 409
