## 0. 이 도메인 개요 (사용자 스토리)

- 본사 관리자로서, 모든 지점 데이터를 조회하고 신규 지점 관리자 계정을 발급하고 싶다.
- 지점 관리자로서, 로그인하면 내 지점 데이터만 보이길 원하고 실수로도 다른 지점 정보에 접근할 수 없기를 바란다.
- 회원으로서, 내 정보와 내가 속한 지점의 프로그램만 보고 싶다.
- 본사 관리자로서, 직원이 퇴사하면 그 즉시 시스템 접근을 막고 싶다.
- 직원(트레이너 등)으로서, 로그인해서 내 근태·휴가·업무일지만 스스로 관리하고 싶다 — 다른 직원 정보나 회원 관리 화면은 볼 필요도, 보여서도 안 된다.

RFP는 "사용자별·프로그램별 세부 권한(입력/수정/삭제/조회/출력)"을 요구하지만, 위 스토리들의 실질(지점 간 격리·퇴사 즉시 차단·관리자/직원 분리)만 충족하도록 4-Role RBAC로 조정했다 — 조정 이유는 ADR-AUTH-03(§10).

### 불변규칙 (협의 불가)
영상의 "동일 좌석 중복판매 금지"에 대응하는, 이 도메인의 협의 불가 규칙 세 가지:
1. **퇴사·탈퇴 처리된 계정은 즉시 접근이 차단된다.** (F01d, RFP 원문 그대로 — "몇 분까지는 봐준다"가 성립할 수 없는 성격)
2. **채용·재배치·Role 변경은 본사(SUPER_ADMIN)만 한다.** (CLAUDE.md 4대 불변식 — 인사 권한 분리)
3. **BRANCH_ADMIN·STAFF·MEMBER는 자기 소속 범위를 벗어난 데이터에 접근할 수 없다.** (CLAUDE.md 4대 불변식 — 지점 데이터 격리. 권한관리 도메인은 이 규칙을 *구현하는 메커니즘*의 근원이다)

## 4. Architecture Driver 식별 (3개로 제한)

| # | Driver | 왜 구조를 바꾸는가 |
|---|---|---|
| D1 | 퇴사·권한변경 즉시 반영 메커니즘 | 캐싱 여부·조회 방식이 API 전체의 요청 경로(critical path)를 결정 |

## 5. Driver 우선순위

**불변규칙(§1) 항상 최우선** → D1(불변규칙 1을 직접 구현) → D2(불변규칙 3의 계약측 구체화) → D3(범위·일정 제약에서 나온 결정, 구조적이지만 리스크는 상대적으로 낮음)

## 6. 현행 구조 진단 (Baseline)

옛 부록 A-6이 이미 이 진단을 산문으로 해 뒀다 — 그대로 가져와 정식화한다: **정정 전(2026-09-15 이전) 구조**는 JWT를 순수 stateless로 검증(서명·만료만 확인)했다. 이 구조로는 퇴사 처리 이후에도 이미 발급된 Access Token이 **만료(최대 30분) 전까지 계속 유효**해, 불변규칙 1("즉시 차단")을 위반했다. 이게 D1을 만든 원인이다.

D1의 현재 해법(매 요청 Account PK 재조회) 자체의 baseline 리스크: 지금은 `MockDataService`(인메모리)라 조회 비용이 사실상 0이다. **실DB 전환 시 이 조회가 모든 API 요청의 critical path에 들어간다** — 이게 D1을 단순 "이미 끝난 일"이 아니라 계속 감시해야 할 Driver로 남기는 이유다.

## 8. 대안 → 트레이드오프 → 결정

### 질문 1: 즉시 반영 메커니즘

| 대안 | 장점 | 단점 |
|---|---|---|
| A. Stateless JWT만(재확인 없음) | DB 조회 0, 성능 최고 | **불변규칙 1 위반**(최대 토큰 만료 시간까지 접근 가능) — 후보 탈락 |
| **B. 매 요청 Account PK 재조회 (채택, 현재 구현)** | 정확성 100%, 구현 단순, 파견 재배치도 동일 메커니즘으로 즉시 반영 | 매 요청 DB round-trip 추가(실DB 전환 시 latency·부하 증가) |
| C. 토큰 블랙리스트/revocation(Redis 등 외부 캐시) | DB 직접 조회보다 빠를 수 있음, 확장성 | 별도 인프라 신규 도입 필요(현재 스택에 없음), 캐시 무효화 타이밍 이슈, 인프라 하나 더 운영 |
| D. Access Token 초단명(예: 1분)+잦은 refresh | 인프라 추가 없음 | Refresh 검증도 결국 DB 조회 필요(RefreshToken 조회) + "최대 1분"은 불변규칙 1의 "즉시"에 못 미침 + 클라이언트 refresh 폭증 |

**결정**: B (현행 유지). 판단 기준은 불변규칙 1(A, D 탈락) + 현재 인프라 제약(C는 새 컴포넌트 요구, C01 일정상 정당화 안 됨). PK 인덱스 조회는 통상 수 ms대라 §3의 "응답시간 예산 10%" 상대 기준을 가설로는 만족한다고 본다.
**감수하는 것**: 실DB 전환 후 이 조회가 실제로 병목이 되는지는 아직 실측하지 못했다(11단계로 이월). 병목으로 드러나면 이미 스펙이 적어 둔 대로 "accountId 기준 수 초짜리 in-memory 캐시"로 완화한다(=C를 축소한 버전, Redis 없이).

### 질문 2: 계약 종료 지점 계정 처리

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 즉시 일괄 비활성화 | 규칙 단순·확실 | 과거 이력 조회·인수인계 업무까지 막음, 되돌리기(재활성화) 필요 시 수동 개입 필요 — 오히려 운영 부담 |
| **B. 쓰기 API만 차단 + 비활성화는 SUPER_ADMIN 수동 판단 (채택, 현재 구현)** | 비가역적 작업을 사람이 최종 결정, 다른 도메인(회원등록·예약·게시글)과 동일한 409 규칙 재사용 | 자동화가 안 돼 SUPER_ADMIN이 놓치면 방치 위험 |
| C. 유예기간 후 자동 비활성화(B + 스케줄러) | 방치 위험 완화 | 유예기간 값이라는 새 모호함 추가, 스케줄러 인프라 없음(다른 도메인의 노쇼 자동처리 등과 동일 사유로 이미 범위 제외됨 — 예약및결제 A-8) |

**결정**: B (현행 유지). 판단 기준: "되돌리기 힘든 작업은 사람이 판단한다"는 이 프로젝트의 일관된 원칙(옛 설계서 §6, 지금 부록 A-6에 이미 명시돼 있었음) + 스케줄러 인프라 부재.
**감수하는 것**: 방치 위험은 자동화가 아니라 운영 체크리스트(사업보고 절차 P03과 연결 가능)로 완화해야 한다 — 숙제로 남긴다.

### 질문 3: 권한 세밀도

| 대안 | 장점 | 단점 |
|---|---|---|
| A. RFP 문자 그대로(사용자×기능×CRUD 개별 ACL) | RFP 문구 100% 충족, 최대 유연성 | 엔터프라이즈 IAM 수준 — 1인 개발·C01 일정 초과 |
| **B. 4-Role 고정 RBAC (채택, 현재 구현)** | 구현 단순, Role×API 조합이 유한해 테스트 가능(hr-authority.spec.ts로 이미 일부 검증됨) | "사용자별" 세밀함 미충족 — RFP 문구와 괴리 |
| C. Role + 지점별 커스텀 오버라이드 | A와 B의 절충 | 오버라이드 규칙까지 테스트해야 해 조합이 다시 늘어남 — B를 고른 이유가 무효화됨 |

**결정**: B (현행 유지). 판단 기준: 기준②(지점 격리라는 RFP의 실질 핵심은 충족) + C01(일정) 제약.
**감수하는 것**: RFP 문구("사용자별·프로그램별 세부 권한")를 문자 그대로 만족하지 못한다 — 발표 시 "왜 조정했는가"를 원문 대비로 설명해야 한다(§0 개요에 이미 이 설명이 있음).

## 9. 감수하는 것 (종합)

- D1: 실DB 전환 전까지 "매 요청 조회가 병목이 아니다"는 가설로 남는다.
- D2: 방치 위험은 프로세스(사람)로 막는다 — 시스템이 보장하지 않는다.
- D3: RFP 문구와의 괴리를 스스로 설명해야 하는 부담이 있다(포트폴리오 발표 리스크가 아니라 오히려 "조정 판단력"을 보여줄 기회로 삼는다).

## 10. ADR

### ADR-AUTH-01: 퇴사·권한변경 즉시 반영 — 매 요청 Account 재조회
- **컨텍스트**: 불변규칙 1(퇴사 즉시 차단)이 stateless JWT로는 위반됨(§6 baseline)
- **검토한 대안**: A stateless만 / B 매 요청 재조회 / C 외부 revocation 캐시 / D 초단명 토큰
- **결정**: B. 불변규칙 위반(A·D) 및 인프라 제약(C)으로 배제
- **결과**: 좋아진 것 — 정확성 100%, 구현 단순 / 감수하는 것 — 실DB 전환 후 latency 실측 필요(가설 상태) / 숙제 — accountId 캐시 완화안을 실측 후 재평가

### ADR-AUTH-02: 계약 종료 지점 계정 — 쓰기 차단 + 수동 비활성화
- **컨텍스트**: 불변규칙 3(지점 격리)과 별개로, TERMINATED 지점 소속 계정의 취급을 정해야 함
- **검토한 대안**: A 즉시 일괄 비활성화 / B 쓰기 차단+수동 / C 유예기간 후 자동
- **결정**: B. "비가역 작업은 사람이 판단"이라는 프로젝트 원칙 + 스케줄러 인프라 부재(C 배제)
- **결과**: 좋아진 것 — 조회·인수인계 업무 방해 없음, 다른 도메인과 규칙 일관성 / 감수하는 것 — 방치 위험 / 숙제 — 운영 체크리스트화

### ADR-AUTH-03: 4-Role 고정 RBAC (개별 ACL 대신)
- **컨텍스트**: F01b가 사용자별·프로그램별 세부 권한(CRUD별)을 요구하나 1인 개발 범위를 초과
- **검토한 대안**: A 개별 ACL / B 4-Role RBAC / C Role+지점 오버라이드
- **결정**: B. RFP의 실질 핵심(지점 격리)은 충족, C01 일정 제약
- **결과**: 좋아진 것 — 구현·테스트 단순 / 감수하는 것 — RFP 문구 미충족(설명 책임) / 숙제 — 없음(확정 사항)

### ADR-AUTH-04: Refresh Token 발급 시 만료·폐기 토큰 정리 (2026-10-06)
- **컨텍스트**: 1회용 rotate(A-6) 구조라 로그인·갱신·가입 직후 발급마다 `RefreshToken` 행이 하나 생기고, 폐기(`revokedAt`)만 할 뿐 지우지 않았다. 수도권 83곳·하루 100명 기준 하루 8천 행 이상, 연 약 1GB로 Supabase 무료 용량(500MB)을 반년 안에 넘는다(design-constants ⑮). 배포 DB에는 k6로 약 1.2만 행이 이미 쌓였다
- **검토한 대안**: A 주기 배치로 일괄 삭제 / B 발급할 때 그 계정의 만료·폐기 토큰 삭제 / C 폐기 대신 즉시 삭제(rotate·logout 시)
- **결정**: B. 스케줄러가 없어 A 불가(ADR-AUTH-02와 같은 인프라 제약). C는 로그인 없이 만료만 되는 토큰이 남는다. B는 `accountId` 인덱스로 한 계정 범위만 지워 비용이 작고, 계정당 행 수가 살아 있는 세션 수로 묶인다
- **결과**: 좋아진 것 — 행 수가 자라지 않음, 재사용 거부는 그대로(행이 없어도 401) / 감수하는 것 — 다시 로그인하지 않는 계정의 만료 토큰은 남는다(계정당 소수), 배포 DB의 기존 행은 별도 정리(사용자 승인 후 2026-10-06 실행, 2,371 → 6행, log/073) / 숙제 — 없음

### ADR-AUTH-05: 비밀번호 변경 — 데모 계정 잠금, 불일치 400, 세션 전부 폐기 (2026-10-09, log/091)
- **컨텍스트**: `PATCH /auth/password`는 있었지만 화면이 없었다. 화면을 붙이며 세 가지가 드러났다. ① 배포 화면에서 누군가 데모 계정 비밀번호를 바꾸면 로그인 화면의 "데모 계정으로 바로 체험하기"가 모두 깨진다. ② 현재 비밀번호가 틀리면 401 `INVALID_CREDENTIALS`라, 회원 웹 인터셉터가 "토큰 만료"로 보고 refresh 후 재시도·로그아웃한다. ③ 바꿔도 다른 기기의 refresh token이 살아 있어, 예전 비밀번호로 열린 세션을 끊지 못한다.
- **검토한 대안**: ① 데모 계정 막기 / 막지 않고 망가지면 시드 재적용(배포 DB 쓰기 — 승인 필요). ② 400 새 코드 / 401 유지하고 클라이언트에서 예외 처리. ③ 그 계정의 refresh token 모두 폐기 / 유지.
- **결정(사용자 결정 3건)**: ① 시드 데모 계정 5개 id(`DEMO_ACCOUNT_IDS`, fixtures/demo-password.ts)는 403 `DEMO_ACCOUNT_LOCKED`. 채용으로 만든 계정은 같은 임시 비밀번호여도 바꿀 수 있다. ② 400 `CURRENT_PASSWORD_MISMATCH` — 호출자가 이 화면뿐이라 영향이 없다. ③ 비밀번호 갱신과 refresh token 폐기를 한 트랜잭션에서 한다. 화면은 성공하면 로그아웃시키고 로그인 화면에 안내를 남긴다.
- **결과**: 좋아진 것 — 데모 체험 보호, 틀려도 로그아웃되지 않음, 유출된 세션을 비밀번호 변경으로 끊을 수 있음 / 감수하는 것 — 이미 발급된 access token은 만료(기본 30분)까지 유효하다(JWT 무상태, ADR-AUTH-01의 매 요청 재조회는 비활성 계정만 막는다). 데모 계정 목록이 api와 두 화면(admin-web `lib/demo-account.ts`, member-web `lib/demo-account.ts`)에 따로 있다 / 숙제 — 비밀번호 재설정(분실)은 여전히 없다

### A-6. 비즈니스 로직 & 엣지케이스
> 옛 1-2 설계서 §6 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- **인증 방식 정정(2026-09-15) — "퇴사 즉시 접근차단"이 실제로 즉시가 되도록 수정**: 기존 설계는 JWT를 순수 stateless로 검증(서명·만료만 확인)해, `Account.isActive`가 로그인·refresh 시점에만 체크됐습니다. 이러면 퇴사 처리 이후에도 **이미 발급된 Access Token이 만료(기본 30분) 전까지 계속 유효**해, 원본 요구사항("퇴사처리 이후에는 시스템 접근 통제")이 말하는 "즉시"와 실제 동작이 어긋납니다. 수정: `JwtAuthGuard`는 서명·만료 검증 후 **JWT payload의 `sub`(accountId)로 매 요청마다 `Account`를 PK 조회**해 `isActive`를 재확인하고, `role`도 JWT에 박제된 값이 아니라 이 조회 결과를 신뢰합니다(BRANCH_ADMIN/STAFF는 `Staff.branchId`도 같은 조회에서 함께 가져와 파견 발령도 재로그인 없이 즉시 반영). PK 인덱스 조회 1회 추가 비용으로 "즉시"를 문자 그대로 만족시킵니다 — 트래픽이 실제로 커지면(포트폴리오 규모에서는 해당 없음) accountId 기준 수 초짜리 캐시(in-memory)로 완화할 수 있습니다.
- 로그인 실패 5회 → `lockedUntil = now+15min`, 이후 성공 시 카운트 초기화
- `isActive=false` 계정으로 로그인 시도 → 401 + `ACCOUNT_DEACTIVATED` 명시적 에러코드(막연한 "로그인 실패"와 구분해 UX상 명확히 안내). **인증된 요청 중에도 동일하게 적용** — 위 수정 이후로는 로그인 이후 언제 퇴사 처리가 나든 다음 요청에서 바로 401이 남
- **지점 자체가 TERMINATED될 때의 계정 처리**(개인 퇴사와는 별개 정책 — [architecture/entities.md §2-1](../architecture/entities.md#2-1-branch지점-데이터-모델--위탁계약-필드)): 위탁계약이 종료된 지점 소속 `BRANCH_ADMIN`/`STAFF` 계정은 개별 퇴사 처리와 달리 즉시 일괄 비활성화하지 않습니다 — 계약 종료 후에도 과거 회원·결제 이력 조회, 인수인계 문서화 등 관리자 업무가 남을 수 있기 때문입니다. 대신 해당 계정들은 **신규 회원 등록·예약 생성 같은 쓰기 API만 차단**(1-5/1-6/예약및결제 문서와 동일하게 409)되고, 실제 계정 비활성화 여부는 SUPER_ADMIN이 지점 상세 화면에서 수동으로 결정합니다(자동 일괄 비활성화는 하지 않음 — 오작동 시 복구가 어려운 되돌리기 힘든 작업이므로 사람이 판단)
- Access Token 만료 시 클라이언트는 자동으로 `/auth/refresh` 호출 후 원 요청 재시도(인터셉터 패턴)
- Refresh Token도 탈취 대비 1회용(rotate) 방식 권장: refresh 성공 시 기존 토큰 revoke + 신규 발급
- BRANCH_ADMIN이 다른 지점 리소스 id를 파라미터로 직접 조작 시도 → `BranchScopeGuard`에서 403 (예: `/staff/:id` 조회 시 해당 staff.branchId ≠ 본인 branchId)
- 회원(MEMBER) 탈퇴 시 즉시 로그인 차단하되, 결제/예약 이력은 보존(소프트 삭제 원칙, architecture/system-overview.md §4 참고)
- Role 전환(STAFF↔BRANCH_ADMIN)도 위와 같은 이유로 **재로그인 없이 다음 요청부터 즉시 반영**됩니다(2026-09-15 이전엔 "만료 전까지 이전 role 유지 → 재로그인 필요"였던 문제). 역할 전환은 2026-10-08부터 같은 트랜잭션에서 AuditLog(`ROLE_CHANGED`, 처리자·전후 역할)에 남고 본사 "변경 이력" 화면에서 본다([D44](../decisions/D44.md) — D17 숙제 해소)
