## 0. 이 도메인 개요 (사용자 스토리)

- 본사 관리자로서, 신규 구매한 운동기구를 특정 지점에 자산으로 등록하고 싶다.
- 지점 관리자로서, 우리 지점 자산 목록과 각 자산의 상태(정상/수리중/폐기대상/폐기됨)를 확인하고 싶다.
- 본사 관리자로서, 신규 위탁계약 체결 시 계약서 파일을 해당 지점에 연결해 보관하고 싶다.
- 본사 관리자로서, 직원의 근로계약서를 업로드하고, 법정 보존기간이 지나면 알림을 받고 싶다.
- 지점 관리자로서, 우리 지점과 관련된 문서(계약서, 인사서류 등)만 조회하고 싶다(타 지점 문서 조회 불가).

이 도메인은 원본 RFP의 명시적 기능요구(F01~F08처럼 번호가 매겨진 항목)가 아니라, RFP "Ⅳ.과업내용" 과업1("인적/물적자원 관리 현황" 분석)이 요구했지만 지금까지 어떤 설계 문서도 다루지 않았던 공백을 메우려고 이 프로젝트가 재해석해 신설한 도메인이다(reference/기업구조및관리시스템분석.md §1). 그래서 Tier(우선순위) 분류에서도 "하"다 — CLAUDE.md 4대 불변식과 직접 겹치지 않고, 사업 존속 리스크(계약 해지)와도 간접적이다([process/02_도메인별_우선순위.md](../process/02_도메인별_우선순위.md) #9).

- 회계 모듈이 없어 감가상각 정밀 계산(월할·자산군별 상각률)을 연동할 재무제표가 없음 — 부록 A-1이 이미 "연 1회 스냅샷" 수준으로 단순화하기로 조정했었고, 그마저도 2026-09-20에 완전히 범위 제외됨(§7).

### 불변규칙 (협의 불가)
1. **BRANCH_ADMIN은 자기 지점 자산·문서만 CRUD한다.** (CLAUDE.md 4대 불변식 — 지점 데이터 격리)
2. **HR_RECORD(인사서류)는 대상 직원(`relatedStaffId`)을 반드시 지정해야 한다.** (누구의 서류인지 모르는 인사서류는 존재 의미가 없음 — 부록 A-3이 이미 이렇게 설계)
3. **문서 삭제는 SUPER_ADMIN 전용이다.** (계약서·인사서류는 법적 증빙 성격이라 지점 관리자가 임의로 지울 수 없어야 함 — 부록 A-7)
4. **문서는 소프트 삭제(D9)를 따른다.** (계약·인사 분쟁 시 감사 목적 복구 가능성 — 부록 A-6)

## 6. 현행 구조 진단 (Baseline)

**D1**: `MockDataService.createAsset`·`createDocument`(`mock-data.service.ts`) 어디에도 `Branch.contractStatus` 체크가 없다. 회원등록·예약생성·게시글작성·시설등록·혼잡도보정에는 이미 있는 "계약종료 지점 신규활동 차단" 패턴이 이 도메인에만 또 빠져 있다 — 계약이 끝난 지점에서도 새 자산을 계속 등록하고 새 문서를 계속 업로드할 수 있다. 게다가 부록 A-6이 이미 "지점 계약 종료 시 잔여 자산은 자동 처리 없이 화면에 경고만 노출"이라고 설계해뒀는데, 그 경고(`admin-web`의 지점 상세 화면 "미처리 자산 N건")도 실제로는 어디에도 구현돼 있지 않다(`BranchDetailPage.tsx`에 자산 관련 코드 없음).

**D2**: `resignStaff`(`mock-data.service.ts`)는 `Staff.status`·`Account.isActive`·활성 `StaffAssignment.endDate` 세 가지를 원자적으로 처리하지만, `Document` 배열은 전혀 건드리지 않는다. `computeRetentionUntil`은 `category=HR_RECORD`일 때 `staff?.resignDate ?? todayKst()`를 기산일로 쓰는데, 이 계산은 **문서 업로드 시점에 한 번만** 일어난다 — 재직 중에 인사서류를 올리면 그 시점의 "임시값"(업로드일+3년)으로 영구히 고정되고, 나중에 그 직원이 실제로 퇴사해도 재계산되지 않는다. 부록 A-6이 이미 "퇴사 처리 시점에 재계산"을 요구했지만, §5-8이 이를 "Phase 2(선택), 미구현"으로 이월해뒀던 항목이다.

**D3**: `CreateDocumentDto.retentionUntil`은 `@IsOptional()`이고, `computeRetentionUntil(category='CONTRACT', ...)`은 `manualRetentionUntil`을 검증 없이 그대로 반환한다(비어 있으면 `undefined`=영구보관). admin-web `DocumentsPage.tsx`의 업로드 폼도 `retentionUntil` 입력을 강제하지 않는다(`dto.category === 'CONTRACT' && dto.retentionUntil ? dto.retentionUntil : undefined` — 빈 값이면 그냥 넘어감). 부록 A-6은 "관리자가 직접 입력하도록 함"이라고 의도를 밝혔을 뿐 실제로 입력을 강제하는 코드는 어디에도 없다 — 관리자가 깜빡하면 계약서가 조용히 영구 보관 취급되어 `retention-alerts`(F10d)에 영원히 나타나지 않는다.

## 7. 설계 질문 (Driver당 1개)

1. 계약이 끝난 지점에서도 새 자산 등록·문서 업로드를 계속 허용해야 할까, 그리고 그 지점에 남은 자산을 어떻게 보여줘야 할까?
2. 직원이 퇴사하면 그 직원의 인사서류 보존기한을 언제, 어떻게 다시 계산해야 할까?
3. 계약서(CONTRACT) 문서에 보존기한을 입력하지 않으면 어떻게 해야 할까?

|---|---|---|
| A. 현행 유지(체크 없음, 경고 없음) | 없음 | CLAUDE.md 핵심 불변식과 이 도메인만 계속 어긋남 |
| **B. `createAsset`·`createDocument`에 다른 5개 도메인과 동일한 409 `BRANCH_TERMINATED` 체크 추가(자산은 역할과 무관하게 대상 branchId로 판정), 자산 상태전이(`updateAssetStatus`)·정보수정(`updateAsset`)·문서삭제(`deleteDocument`)는 제외("신규 활동 vs 정정" 원칙 재적용), 지점 상세 화면에 "미처리 자산 N건" 경고 추가 (채택)** | 이미 검증된 패턴 재사용(FAC-03과 동일 판단 기준), 기존 자산의 정당한 관리(수리 완료 처리, 이관 전 상태 정리)는 막지 않음, 부록 A-6이 원래 의도했던 경고를 실제로 채움 | 자산은 SUPER_ADMIN도 직접 만들 수 있어, "BRANCH_ADMIN일 때만 체크"가 아니라 "만들어질 branchId 자체를 항상 체크"해야 함 — 다른 도메인보다 분기가 하나 더 필요 |
| C. 자산·문서 전체 쓰기(등록+수정+상태전이) 차단 | 가장 엄격 | 기존 자산의 정당한 관리(수리 완료, 폐기 처리)까지 막아 과도 — 혼잡도관리 ADR-FAC-03에서 이미 배제한 것과 같은 이유 |

**결정**: B. 판단 기준: CLAUDE.md가 이미 "과거 데이터 조회는 유지, 신규 활동만 차단"이라는 선을 그어뒀고(혼잡도관리 ADR-FAC-03이 이미 이 도메인 특유의 "신규 vs 정정" 판단 선례를 남겨둠), 그 선을 그대로 재사용.
**감수하는 것**: 자산 도메인은 역할별 분기가 다른 도메인보다 하나 더 필요하다(위 표 참고) — 구현 시 유의사항으로 남긴다.

### 질문 2: 퇴사 시 HR_RECORD 보존기한 재계산

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(재계산 없음) | 구현 없음 | 재직 중 업로드된 인사서류는 실제 퇴사일과 무관하게 "업로드일+3년"으로 영구 고정 — 법정 기산일(근로관계 종료일)과 어긋남 |
| **B. `resignStaff`에서 해당 직원의 미삭제 `HR_RECORD` 문서 전부를 찾아 `retentionUntil = 퇴사일 + 3년`으로 일괄 재계산 (채택)** | 사람이 기억해야 하는 실패 모드를 없앰, `resignStaff`가 이미 같은 성격의 부수효과(계정 비활성화, 파견 종료)를 원자적으로 처리하는 패턴이 있어 구조적으로 자연스러운 확장 | 인사 도메인 함수가 문서 도메인 데이터를 직접 갱신 — 모듈 경계가 흐려짐 |
| C. 관리자가 퇴사 처리 후 각 문서를 수동으로 열어 재입력 | 구현 없음 | "관리자가 잊으면 안 되는 값"을 사람 기억에 의존시키는 것 — 근태관리 ADR-ATT-02 때 사용자가 지적한 "인간 실수" 관점과 같은 결로 배제 대상 |

**결정**: B. 판단 기준: 법정 보존기한 기산일은 추측·방치하면 안 되는 값이라는 점에서 강사프로그램게시 ADR-PRG-01("정원은 추측하면 안 되는 값")과 같은 판단 기준을 적용. C는 인간 실수에 결과를 맡기므로 배제.
**감수하는 것**: 문서 도메인 로직이 인사 도메인 함수 안에서 직접 갱신됨 — 강사프로그램게시 ADR-PRG-02(프로그램 컨트롤러가 예약 데이터를 조회)와 같은 종류의 비용이고, 지금은 `MockDataService`가 이미 전 도메인 데이터를 갖고 있어 비용이 낮지만 실DB 전환 후 서비스 분리 시 재검토 대상.

## 10. ADR

### ADR-RES-01: 계약종료 지점의 신규 자산 등록·문서 업로드 차단 + 잔여자산 가시화
- **컨텍스트**: `createAsset`·`createDocument`에 `TERMINATED` 체크가 없음(§6) — CLAUDE.md 불변식이 이 도메인에만 또 빠져 있었음(혼잡도관리·게시판에 이어 세 번째 발견)
- **검토한 대안**: A 현행 / B 등록·업로드만 차단 + 정정은 허용 + 잔여자산 경고 / C 전체 차단
- **결정**: B. "신규 활동 vs 정정" 구분을 혼잡도관리 ADR-FAC-03과 동일하게 적용
- **결과**: 좋아진 것 — 불변식 일관 적용, 이 문서가 원래 의도했던 잔여자산 경고를 실제로 채움 / 감수하는 것 — 자산은 역할 무관 branchId 판정이 필요해 분기 하나 추가 / 숙제 — 없음
- **구현됨(2026-09-25)**: `MockDataService.createAsset`·`createDocument`에 `Branch.contractStatus==='TERMINATED'` 체크 추가 — `createMember`/`createPost`/`createFacility`와 동일한 인라인 패턴(공통 가드 중앙화는 실DB 전환 이후로 미룬다는 기존 CLAUDE.md 결정에 따름). `createAsset`은 역할 분기 없이 대상 `branchId`만으로 판정(설계대로 SUPER_ADMIN도 차단 대상). `createDocument`는 `branchId`가 있을 때만 검사하고 전사 문서(`branchId=null`)는 대상에서 제외. `updateAsset`·`updateAssetStatus`·`deleteDocument`(기존 정정)는 의도적으로 제외. admin-web `BranchDetailPage`에 "미처리 자산 N건"(`status !== 'DISPOSED'`) 경고를 추가해 부록 A-6이 원래 의도했던 가시성을 실제로 채웠다. 회귀 테스트: `contract-termination.spec.ts`에 자산/문서 등록 차단·유지·비대상 상태·전사 문서 예외 케이스 8건 추가.

### ADR-RES-02: 퇴사 처리 시 HR_RECORD 문서 보존기한 자동 재계산
- **컨텍스트**: `resignStaff`가 문서를 전혀 건드리지 않아, 재직 중 업로드된 인사서류의 보존기한이 실제 퇴사일과 무관하게 고정됨(§6)
- **검토한 대안**: A 현행(재계산 없음) / B resignStaff에서 일괄 재계산 / C 관리자 수동 재입력
- **결정**: B. 법정 기산일은 추측·방치하면 안 되는 값
- **결과**: 좋아진 것 — 법정 보존기한 정확성 확보 / 감수하는 것 — 인사 도메인이 문서 도메인을 직접 갱신(모듈 경계 흐려짐) / 숙제 — 없음
- **구현됨(2026-09-25)**: `resignStaff`가 계정 비활성화·파견 종료와 같은 자리에서, 그 직원의 미삭제 `HR_RECORD` 문서 전부(`relatedStaffId===id && category==='HR_RECORD' && !deletedAt`)를 찾아 `retentionUntil = 퇴사일 + 3년`으로 일괄 갱신한다(`addYearsToDateString` 재사용, KST 규칙 준수). 다른 직원의 HR_RECORD·다른 카테고리 문서·소프트 삭제된 문서는 건드리지 않는다. 회귀 테스트: `apps/api/test/staff-assignment.spec.ts`에 대상 문서 갱신 + 3종 대조군(타 직원/타 카테고리/삭제됨 불변) 케이스 추가.

### ADR-RES-03: CONTRACT 문서 보존기한 서버 필수화
- **컨텍스트**: `retentionUntil`이 옵션이라 관리자가 비우면 계약서가 조용히 영구보관 취급됨(§6)
- **검토한 대안**: A 현행(미입력 허용) / B 서버 필수화(400) / C 경고만 표시
- **결정**: B. 기존 `STAFF_REQUIRED` 패턴 재사용, 감사·법적 대응력이 걸린 값이라 경고보다 강제가 맞음
- **결과**: 좋아진 것 — 계약서 보존기한 누락 원천 차단 / 감수하는 것 — 없음 / 숙제 — 없음
- **구현됨(2026-09-25)**: `createDocument`에 `category==='CONTRACT' && !retentionUntil`이면 400 `RETENTION_UNTIL_REQUIRED`를 던지는 체크 추가 — `STAFF_REQUIRED`와 동일한 위치·패턴. `CreateDocumentDto.retentionUntil`은 여전히 DTO 레벨에서는 optional로 두고(class-validator로 카테고리 조건부 필수를 표현하기보다 서비스 계층에서 판단하는 기존 관례를 그대로 따름) 서비스가 최종 검증한다. admin-web `DocumentsPage`도 `category=CONTRACT`일 때 보존기한 입력을 `required`로 바꾸고 제출 전 가드를 추가해 백엔드 왕복 없이 바로 막는다. 회귀 테스트: `apps/api/test/document-retention.spec.ts`(신규 파일, 4건 — 미입력 거부·입력 성공·타 카테고리 대조군·차단 시 미영속).

- **자산 DB 이관(2026-09-29, 2-1 D35)**: 자산 원천이 `AssetService`(Prisma)로 옮겨졌다. 채번은 D28 헬퍼(`allocateBranchCode(ASSET)`, RES-T04 해소), 상태 전이는 "읽은 상태 그대로일 때만" 갱신(동시 전이 중 하나만 성공). 옮기면서 mock `updateAsset`이 고정자산 수량 검사 **전에** 이름·위치를 먼저 바꿔 두던 부분 수정 결함(ADR-PRG-01과 같은 형태)을 발견해, 모든 검사를 끝낸 뒤 한 번에 쓰도록 고쳤다. 폐기 자산 누적(traffic-infra-review)은 화면 설계와 함께 정할 일이라 이번 범위 밖. 이로써 이 도메인(자산·문서) 전체가 DB다.

ADR-RES-02(퇴사 시 재계산)는 `StaffService.resign`의 퇴사 트랜잭션 안으로 들어갔다(`recalculateHrRetention`). 시드 문서 2건은 Supabase에도 적용했다. `Document.relatedStaffId`·`uploadedBy`에 DB 외래키가 없다 — 추가는 스키마 변경이라 사용자 승인 후 후속. **자산은 아직 mock**(다음 이관 대상).

- **트래픽/인프라 후보 이슈(2026-09-28, 검토 중 — 아직 ADR 아님)**: 보존기한 임박 알림 조회가 전체 문서를 매번 스캔·정렬하고, 자산·문서 목록도 항목마다 N+1 조회한다. 폐기된 자산(`DISPOSED`)이 배열에서 영원히 안 빠져 무한 누적된다. 관리자 전용 화면이라 다른 도메인보다 우선순위는 낮게 본다 — 전체 6개 도메인 분석과 검토 방향은 [architecture/traffic-infra-review.md](../architecture/traffic-infra-review.md#자원문서관리--심각도-낮음중간) 참고. 대안 비교·결정 전이라 정식 ADR로 승격하지 않았다.

### A-6. 비즈니스 로직 & 엣지케이스
> 옛 1-10 설계서 §4-6·§5-6 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

#### 자산(옛 §4-6)
- `assetCode` 생성 규칙: 지점 코드 + 지점 내 순번(zero-padded, 예 `SEOCHO-A012`) — `staffCode`(인사정보관리 문서)와 동일한 패턴을 재사용해 일관성 유지. 동시 등록 race condition 방지는 `staffCode`와 동일하게 트랜잭션 + `SELECT ... FOR UPDATE`.
- `assetType` 자동 판정: `acquisitionCost > 1,000,000`이면 `FIXED_ASSET`, 이하면 `CONSUMABLE`(§3-2 기준). 등록 화면에서 자동 판정 결과를 보여주되 관리자가 수동으로 덮어쓸 수 있게 함(예: 고가 소모품을 실무 판단으로 고정자산 취급하고 싶은 경우).
- **재물조사 개시는 SUPER_ADMIN 전용** — `StaffAssignment`(인사정보관리 문서)의 "채용·배치는 본사만"과 같은 원칙: 재물조사는 지점이 스스로 시작하는 게 아니라 본사가 감사 목적으로 개시하는 행위이기 때문.
- 재물조사 마감(`/close`) 시 `AssetInventoryCheckItem.actualStatus`가 `Asset.status`와 다르면 **`Asset.status`를 실사 결과로 갱신** — 이 갱신은 `AuditLog`에 "재물조사 #{checkId}에 의한 자동 반영"으로 기록해, 나중에 "왜 이 자산 상태가 바뀌었는지"를 관리자가 아닌 사람이 임의로 바꾼 것과 구분할 수 있게 함.
- `CONSUMABLE`은 재물조사 대상에서 제외(§3-2 "소모품은 실사 대상이 아니다") — `AssetInventoryCheck` 생성 시 `assetType=FIXED_ASSET`인 자산만 `AssetInventoryCheckItem`으로 스냅샷.
- 지점 계약 종료(`Branch.contractStatus=TERMINATED`) 시 해당 지점의 잔여 `Asset`은 자동으로 아무 처리도 하지 않음(물리적 이관·폐기는 사람이 판단할 문제) — 대신 지점 상세 화면에 "미처리 자산 N건" 경고만 노출.

#### 문서(옛 §5-6)
- **법정 보존연한 기준**(카테고리별 `retentionUntil` 자동 계산, [참고자료](#참고자료)):
  - `HR_RECORD`(인사서류): 근로기준법 기준 근로관계 종료일로부터 **3년**
  - `CONTRACT`(위탁계약서): 상법상 상업장부 보존 원칙(10년)을 참고하되, 계약 관련 문서는 법정 의무 기간이 계약 유형마다 달라 **일괄 자동계산 대신 관리자가 직접 입력**하도록 함(과잉 일반화 방지) — `category=CONTRACT`는 자동계산 로직에서 제외하고 입력 필드를 노출
  - `MANUAL`, `OTHER`: 법정 보존 의무 없음 → `retentionUntil=null`(영구 보관) 기본값
- `HR_RECORD` 문서 업로드 시 `relatedStaffId`가 가리키는 `Staff.resignDate`가 이미 있으면(퇴사자) 그 날짜 기준으로, 없으면 업로드일 기준 임시값으로 계산 후 **퇴사 처리(인사정보관리 문서 `/resign`) 시점에 재계산**(트리거 방식은 인사정보관리 문서의 "퇴사 처리가 여러 부수효과를 원자적으로 처리"하는 패턴에 이 재계산을 추가로 편입).
- 보존기한이 지난 문서는 **자동 삭제하지 않음** — 법정 의무는 "최소 보존 기간"이지 "그 이후 즉시 폐기 의무"가 아니므로, 목록에 경고 배지만 표시하고 실제 삭제는 관리자 판단(SUPER_ADMIN)에 맡김.
- `Document`는 소프트 삭제(D9) 원칙을 그대로 따름 — 계약 분쟁·인사 분쟁 시 삭제된 문서도 감사 목적으로 복구 가능해야 하기 때문.

### A-7. 권한 요약

- BRANCH_ADMIN: 본인 지점 자산·문서 CRUD(문서 삭제 제외) + 전사 문서(`branchId=null`) 조회
- SUPER_ADMIN: 전체 접근, 문서 삭제·보존기한 임박 목록 전용
- STAFF, MEMBER: 이 도메인 전체 접근 불가(권한 매트릭스에 자산·문서 도메인 자체가 없음)

### A-8. 구현 우선순위

**Phase 1(완료, 2026-09-19)**: Asset CRUD·자동판정·상태전이, Document CRUD·보존기한 자동계산(CONTRACT 제외)·소프트삭제·보존기한 임박 목록.
