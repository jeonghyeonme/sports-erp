# 도메인 사이클 — 자원문서관리

> **상태**: 초안 (2026-09-25). [process/03_도메인_사이클_템플릿.md](../process/03_도메인_사이클_템플릿.md) 11단계 적용 — 9호 사이클(마지막 도메인, 하 우선순위, 스킬 산출물).
> **대상 코드**: `apps/api/src/modules/assets/`, `apps/api/src/modules/documents/`
> **이 문서가 자원문서관리 도메인의 단일 문서다.** 옛 [1-10_기업구조및자원관리분석.md](../1.spec/40_자원문서관리/1-10_기업구조및자원관리분석.md)의 §4·§5(신규 설계 부분)를 병합했다. §1~3(기업 구조·관리시스템 분석)은 산출물2(기업 분석 자료) 성격의 서술이라 도메인 사이클 형식에 안 맞아 원본에 유지한다(§12에서 판단 근거를 밝힌다). 1-10문서는 §4·§5만 **대체 배너**를 달아 폐기 예정 — 진행 상황은 [process/05_문서_마이그레이션_추적.md](../process/05_문서_마이그레이션_추적.md).
> **9개 도메인 중 마지막 도메인이다.** 나머지 8개는 이미 사이클을 완료했다.

## 0. 이 도메인 개요 (사용자 스토리)

- 본사 관리자로서, 신규 구매한 운동기구를 특정 지점에 자산으로 등록하고 싶다.
- 지점 관리자로서, 우리 지점 자산 목록과 각 자산의 상태(정상/수리중/폐기대상/폐기됨)를 확인하고 싶다.
- 본사 관리자로서, 신규 위탁계약 체결 시 계약서 파일을 해당 지점에 연결해 보관하고 싶다.
- 본사 관리자로서, 직원의 근로계약서를 업로드하고, 법정 보존기간이 지나면 알림을 받고 싶다.
- 지점 관리자로서, 우리 지점과 관련된 문서(계약서, 인사서류 등)만 조회하고 싶다(타 지점 문서 조회 불가).

이 도메인은 원본 RFP의 명시적 기능요구(F01~F08처럼 번호가 매겨진 항목)가 아니라, RFP "Ⅳ.과업내용" 과업1("인적/물적자원 관리 현황" 분석)이 요구했지만 지금까지 어떤 설계 문서도 다루지 않았던 공백을 메우려고 이 프로젝트가 재해석해 신설한 도메인이다(1-10문서 §1). 그래서 Tier(우선순위) 분류에서도 "하"다 — CLAUDE.md 4대 불변식과 직접 겹치지 않고, 사업 존속 리스크(계약 해지)와도 간접적이다([process/02_도메인별_우선순위.md](../process/02_도메인별_우선순위.md) #9).

### 품질
- 없음(도메인 고유 품질 요구 없음 — 근태관리·강사프로그램게시와 같은 결).

### 제약
- 실제 파일 업로드 인프라(스토리지·용량 제한·바이러스 검사) 없음 — `fileUrl`은 문자열만 받는다(1-10문서 §5-1, §7이 이미 범위 제외).
- 회계 모듈이 없어 감가상각 정밀 계산(월할·자산군별 상각률)을 연동할 재무제표가 없음 — 1-10문서 §4-1이 이미 "연 1회 스냅샷" 수준으로 단순화하기로 조정했었고, 그마저도 2026-09-20에 완전히 범위 제외됨(§7).

### 불변규칙 (협의 불가)
1. **BRANCH_ADMIN은 자기 지점 자산·문서만 CRUD한다.** (CLAUDE.md 4대 불변식 — 지점 데이터 격리)
2. **HR_RECORD(인사서류)는 대상 직원(`relatedStaffId`)을 반드시 지정해야 한다.** (누구의 서류인지 모르는 인사서류는 존재 의미가 없음 — 1-10문서 §5-3이 이미 이렇게 설계)
3. **문서 삭제는 SUPER_ADMIN 전용이다.** (계약서·인사서류는 법적 증빙 성격이라 지점 관리자가 임의로 지울 수 없어야 함 — 1-10문서 §5-7)
4. **문서는 소프트 삭제(D9)를 따른다.** (계약·인사 분쟁 시 감사 목적 복구 가능성 — 1-10문서 §5-6)

## 2. 되묻기 확정

이 도메인에 해당하는 미해결 되묻기 없음(01번 문서에 자원문서관리 관련 항목 없음 — 원본 RFP 요구가 아니라 이 프로젝트가 재해석으로 신설한 도메인이라 애초에 RFP 문장 자체가 없다).

## 5. Driver 우선순위

**불변규칙(§1) 항상 최우선** → D1(CLAUDE.md 핵심 불변식의 적용 범위 문제 — 이미 5개 도메인에서 확립된 패턴과의 일관성) → D2(법정 보존기한 기산일 정확성 — 틀리면 법적 분쟁 시 실제 피해로 이어짐) → D3(같은 종류의 법정 준수 문제지만 D2보다 범위가 좁고 구현 비용도 더 낮음)

## 6. 현행 구조 진단 (Baseline)

**D1**: `MockDataService.createAsset`·`createDocument`(`mock-data.service.ts`) 어디에도 `Branch.contractStatus` 체크가 없다. 회원등록·예약생성·게시글작성·시설등록·혼잡도보정에는 이미 있는 "계약종료 지점 신규활동 차단" 패턴이 이 도메인에만 또 빠져 있다 — 계약이 끝난 지점에서도 새 자산을 계속 등록하고 새 문서를 계속 업로드할 수 있다. 게다가 1-10문서 §4-6이 이미 "지점 계약 종료 시 잔여 자산은 자동 처리 없이 화면에 경고만 노출"이라고 설계해뒀는데, 그 경고(`admin-web`의 지점 상세 화면 "미처리 자산 N건")도 실제로는 어디에도 구현돼 있지 않다(`BranchDetailPage.tsx`에 자산 관련 코드 없음).

**D2**: `resignStaff`(`mock-data.service.ts`)는 `Staff.status`·`Account.isActive`·활성 `StaffAssignment.endDate` 세 가지를 원자적으로 처리하지만, `Document` 배열은 전혀 건드리지 않는다. `computeRetentionUntil`은 `category=HR_RECORD`일 때 `staff?.resignDate ?? todayKst()`를 기산일로 쓰는데, 이 계산은 **문서 업로드 시점에 한 번만** 일어난다 — 재직 중에 인사서류를 올리면 그 시점의 "임시값"(업로드일+3년)으로 영구히 고정되고, 나중에 그 직원이 실제로 퇴사해도 재계산되지 않는다. 1-10문서 §5-6이 이미 "퇴사 처리 시점에 재계산"을 요구했지만, §5-8이 이를 "Phase 2(선택), 미구현"으로 이월해뒀던 항목이다.

**D3**: `CreateDocumentDto.retentionUntil`은 `@IsOptional()`이고, `computeRetentionUntil(category='CONTRACT', ...)`은 `manualRetentionUntil`을 검증 없이 그대로 반환한다(비어 있으면 `undefined`=영구보관). admin-web `DocumentsPage.tsx`의 업로드 폼도 `retentionUntil` 입력을 강제하지 않는다(`dto.category === 'CONTRACT' && dto.retentionUntil ? dto.retentionUntil : undefined` — 빈 값이면 그냥 넘어감). 1-10문서 §5-6은 "관리자가 직접 입력하도록 함"이라고 의도를 밝혔을 뿐 실제로 입력을 강제하는 코드는 어디에도 없다 — 관리자가 깜빡하면 계약서가 조용히 영구 보관 취급되어 `retention-alerts`(F10d)에 영원히 나타나지 않는다.

## 7. 설계 질문 (Driver당 1개)

1. 계약이 끝난 지점에서도 새 자산 등록·문서 업로드를 계속 허용해야 할까, 그리고 그 지점에 남은 자산을 어떻게 보여줘야 할까?
2. 직원이 퇴사하면 그 직원의 인사서류 보존기한을 언제, 어떻게 다시 계산해야 할까?
3. 계약서(CONTRACT) 문서에 보존기한을 입력하지 않으면 어떻게 해야 할까?

## 8. 대안 → 트레이드오프 → 결정

### 질문 1: 계약종료 지점의 자산·문서 신규활동

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(체크 없음, 경고 없음) | 없음 | CLAUDE.md 핵심 불변식과 이 도메인만 계속 어긋남 |
| **B. `createAsset`·`createDocument`에 다른 5개 도메인과 동일한 409 `BRANCH_TERMINATED` 체크 추가(자산은 역할과 무관하게 대상 branchId로 판정), 자산 상태전이(`updateAssetStatus`)·정보수정(`updateAsset`)·문서삭제(`deleteDocument`)는 제외("신규 활동 vs 정정" 원칙 재적용), 지점 상세 화면에 "미처리 자산 N건" 경고 추가 (채택)** | 이미 검증된 패턴 재사용(FAC-03과 동일 판단 기준), 기존 자산의 정당한 관리(수리 완료 처리, 이관 전 상태 정리)는 막지 않음, 1-10문서 §4-6이 원래 의도했던 경고를 실제로 채움 | 자산은 SUPER_ADMIN도 직접 만들 수 있어, "BRANCH_ADMIN일 때만 체크"가 아니라 "만들어질 branchId 자체를 항상 체크"해야 함 — 다른 도메인보다 분기가 하나 더 필요 |
| C. 자산·문서 전체 쓰기(등록+수정+상태전이) 차단 | 가장 엄격 | 기존 자산의 정당한 관리(수리 완료, 폐기 처리)까지 막아 과도 — 혼잡도관리 ADR-FAC-03에서 이미 배제한 것과 같은 이유 |

**결정**: B. 판단 기준: CLAUDE.md가 이미 "과거 데이터 조회는 유지, 신규 활동만 차단"이라는 선을 그어뒀고(혼잡도관리 ADR-FAC-03이 이미 이 도메인 특유의 "신규 vs 정정" 판단 선례를 남겨둠), 그 선을 그대로 재사용.
**감수하는 것**: 자산 도메인은 역할별 분기가 다른 도메인보다 하나 더 필요하다(위 표 참고) — 구현 시 유의사항으로 남긴다.

### 질문 2: 퇴사 시 HR_RECORD 보존기한 재계산

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(재계산 없음) | 구현 없음 | 재직 중 업로드된 인사서류는 실제 퇴사일과 무관하게 "업로드일+3년"으로 영구 고정 — 법정 기산일(근로관계 종료일)과 어긋남 |
| **B. `resignStaff`에서 해당 직원의 미삭제 `HR_RECORD` 문서 전부를 찾아 `retentionUntil = 퇴사일 + 3년`으로 일괄 재계산 (채택)** | 사람이 기억해야 하는 실패 모드를 없앰, `resignStaff`가 이미 같은 성격의 부수효과(계정 비활성화, 파견 종료)를 원자적으로 처리하는 패턴이 있어 구조적으로 자연스러운 확장 | 인사 도메인 함수가 문서 도메인 데이터를 직접 갱신 — 모듈 경계가 흐려짐 |
| C. 관리자가 퇴사 처리 후 각 문서를 수동으로 열어 재입력 | 구현 없음 | "관리자가 잊으면 안 되는 값"을 사람 기억에 의존시키는 것 — 근태관리 ADR-ATT-02 때 사용자가 지적한 "인간 실수" 관점과 같은 결로 배제 대상 |

**결정**: B. 판단 기준: 법정 보존기한 기산일은 추측·방치하면 안 되는 값이라는 점에서 강사프로그램게시 ADR-PRG-01("정원은 추측하면 안 되는 값")과 같은 판단 기준을 적용. C는 인간 실수에 결과를 맡기므로 배제.
**감수하는 것**: 문서 도메인 로직이 인사 도메인 함수 안에서 직접 갱신됨 — 강사프로그램게시 ADR-PRG-02(프로그램 컨트롤러가 예약 데이터를 조회)와 같은 종류의 비용이고, 지금은 `MockDataService`가 이미 전 도메인 데이터를 갖고 있어 비용이 낮지만 실DB 전환 후 서비스 분리 시 재검토 대상.

### 질문 3: CONTRACT 문서 보존기한 미입력

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(미입력 시 조용히 영구보관) | 없음 | 계약서가 보존기한 임박 알림(F10d)에 영원히 안 뜨는 조용한 실패 — 감사·법적 분쟁 대응력이 걸린 문제를 방치 |
| **B. `category=CONTRACT`인데 `retentionUntil` 미입력이면 400으로 거부(서버 필수화) (채택)** | 이미 있는 `STAFF_REQUIRED`(HR_RECORD 필수값) 검증과 동일한 패턴 재사용 — 구현 비용 거의 없음, 원인 시점에 바로 명확한 에러 | 계약 유형에 따라 정말로 보존기한을 아직 정하지 못한 경우(예: 협상 중)에는 임시값을 억지로 넣어야 함 |
| C. 필수화하지 않고 응답에 `warnings` 필드로 경고만 포함(회원관리 `guardianConsent` 경고 패턴 재사용) | 유연함, 이 프로젝트에 이미 "차단 대신 경고"를 쓰는 선례가 있음 | 경고는 "본 사람만" 확인하는 정보라, 계약서처럼 놓치면 안 되는 값에는 회원관리의 부가 정보성 경고보다 약한 보장 |

**결정**: B. 판단 기준: 계약서 보존기한 누락은 이용률 낮은 부가 기능이 아니라 감사·법적 분쟁 대응력 자체가 걸린 문제라, 경고보다 강제가 맞다고 판단(질문 2와 같은 "법정 준수 값은 추측·방치 금지" 기준).
**감수하는 것**: 없음 — 기존 `STAFF_REQUIRED` 패턴 재사용이라 사실상 무비용.

## 9. 감수하는 것 (종합)

- D1: 자산 도메인은 역할별 분기가 아니라 대상 branchId로 직접 판정해야 해 다른 도메인보다 분기가 하나 더 필요하다.
- D2: 인사 도메인 함수(`resignStaff`)가 문서 도메인 데이터를 직접 갱신 — 모듈 경계가 흐려짐, 실DB 전환 시 재검토 대상.
- D3: 없음.

## 10. ADR

### ADR-RES-01: 계약종료 지점의 신규 자산 등록·문서 업로드 차단 + 잔여자산 가시화
- **컨텍스트**: `createAsset`·`createDocument`에 `TERMINATED` 체크가 없음(§6) — CLAUDE.md 불변식이 이 도메인에만 또 빠져 있었음(혼잡도관리·게시판에 이어 세 번째 발견)
- **검토한 대안**: A 현행 / B 등록·업로드만 차단 + 정정은 허용 + 잔여자산 경고 / C 전체 차단
- **결정**: B. "신규 활동 vs 정정" 구분을 혼잡도관리 ADR-FAC-03과 동일하게 적용
- **결과**: 좋아진 것 — 불변식 일관 적용, 1-10문서가 원래 의도했던 잔여자산 경고를 실제로 채움 / 감수하는 것 — 자산은 역할 무관 branchId 판정이 필요해 분기 하나 추가 / 숙제 — 없음(구현만 남음)

### ADR-RES-02: 퇴사 처리 시 HR_RECORD 문서 보존기한 자동 재계산
- **컨텍스트**: `resignStaff`가 문서를 전혀 건드리지 않아, 재직 중 업로드된 인사서류의 보존기한이 실제 퇴사일과 무관하게 고정됨(§6)
- **검토한 대안**: A 현행(재계산 없음) / B resignStaff에서 일괄 재계산 / C 관리자 수동 재입력
- **결정**: B. 법정 기산일은 추측·방치하면 안 되는 값
- **결과**: 좋아진 것 — 법정 보존기한 정확성 확보 / 감수하는 것 — 인사 도메인이 문서 도메인을 직접 갱신(모듈 경계 흐려짐) / 숙제 — 없음(구현만 남음)

### ADR-RES-03: CONTRACT 문서 보존기한 서버 필수화
- **컨텍스트**: `retentionUntil`이 옵션이라 관리자가 비우면 계약서가 조용히 영구보관 취급됨(§6)
- **검토한 대안**: A 현행(미입력 허용) / B 서버 필수화(400) / C 경고만 표시
- **결정**: B. 기존 `STAFF_REQUIRED` 패턴 재사용, 감사·법적 대응력이 걸린 값이라 경고보다 강제가 맞음
- **결과**: 좋아진 것 — 계약서 보존기한 누락 원천 차단 / 감수하는 것 — 없음 / 숙제 — 없음(구현만 남음)
