## 0. 이 도메인 개요 (사용자 스토리)

- 본사 관리자로서, 신규 채용한 직원을 특정 지점에 배치(최초 파견)하고 싶다.
- 본사 관리자로서, 직원을 다른 지점으로 재배치(파견 전환)하고 그 이력을 남기고 싶다.
- 지점 관리자로서, 현재 우리 지점에 파견된 직원들의 직급/연락처 등 일상적인 인사정보를 관리하고 싶다.
- 본사 관리자로서, 전 지점 직원 현황을 하나의 화면에서 조회하고 싶다(원본 "한 화면 조회" 요건).
- 직원으로서, 내 인적사항 변경(연락처 등)을 신청하면 관리자 승인 후 반영되길 원한다.
- 지점 관리자로서, 퇴사 처리 시 퇴사일을 기록하고 계정을 자동으로 비활성화하고 싶다.

RFP 원문("행정 및 트레이너들 역시 해당 지역 또는 본사 파견 형태로 직원이 투입")이 이 도메인의 핵심 데이터 모델을 직접 결정한다 — `Staff.branchId`는 고정 소속이 아니라 **현재 파견 지점**이고, 파견 이력은 `StaffAssignment`로 별도 관리한다(CLAUDE.md "Staff는 지점 소속이 아니라 본사 소속 파견 인력" 재해석과 동일 원천).

### 불변규칙 (협의 불가)
1. **채용·재배치는 본사(SUPER_ADMIN)만 한다.** (CLAUDE.md 4대 불변식 — 인사 권한 분리. 권한관리 도메인의 불변규칙 2와 같은 원천, 이 도메인은 그 실제 구현 지점이다)
2. **한 직원은 활성(`endDate=null`) `StaffAssignment`가 항상 최대 1건이어야 한다.** (파견이 이 도메인의 핵심 모델인 이상, 한 사람이 동시에 두 지점에 파견될 수는 없다는 건 협의 대상이 아니다)
3. **퇴사 처리는 계정 비활성화와 분리될 수 없다.** (권한관리 도메인 불변규칙 1 "퇴사 즉시 접근 차단"의 트리거가 바로 이 도메인의 `/resign`이다 — 두 도메인이 공유하는 불변식의 서로 다른 쪽 절반)

## 6. 현행 구조 진단 (Baseline)

**D1**: `resignStaff`·`assignStaff` 둘 다 코드 주석이 스스로 인정하듯 "실DB 전환 시 여기가 트랜잭션으로 묶여야 할 지점"이다. 지금은 `MockDataService`가 단일 Node 프로세스에서 동기 실행되는 배열이라 중간 실패가 없지만, 실DB에서는 `Staff.status` 갱신 후 `Account.isActive` 갱신 전에 실패하면 "퇴사 처리됐는데 로그인은 여전히 된다"는 불변규칙 3 위반 상태가 남는다.

**D2**: `generateStaffCode`는 `this.staff.filter(...).length + 1`로 카운트한다 — **이건 예약및결제 문서가 이미 "정원 초과 방지" §6에서 논파한 바로 그 결함 패턴**이다(팬텀 삽입: 두 채용 요청이 동시에 카운트를 읽으면 같은 순번을 계산해 같은 `staffCode`를 발급할 수 있다). 지금은 단일 프로세스라 실제로 터지지 않지만, 실DB+다중 인스턴스에서는 예약및결제 문서와 같은 이유로 뚫린다.

**D3**: 활성 파견 최대 1건이라는 불변식은 현재 "`endDate=null`인 레코드를 찾아서 먼저 마감" 로직으로만 지켜진다. DB 제약이 아니라 애플리케이션 로직이 유일한 방어선이다.

## 8. 대안 → 트레이드오프 → 결정

### 질문 1: 트랜잭션 경계

| 대안 | 장점 | 단점 |
|---|---|---|
| **A. 하나의 DB 트랜잭션으로 Staff/Account/StaffAssignment 갱신을 묶는다 (채택)** | 표준적인 방법, 실패 시 전체 롤백으로 불변규칙 3 위반 상태가 절대 남지 않음 | 실DB 전환 전까지는 적용할 대상(트랜잭션)이 없음 — 지금은 문서화만 가능 |
| B. 순차 mutation 유지 + 실패 시 보상 로직(SAGA) | 마이크로서비스로 쪼개져도 동작 | 이 프로젝트는 단일 NestJS 모놀리스라 오버엔지니어링 — 트랜잭션 하나로 충분한 문제에 분산 트랜잭션 패턴을 쓸 이유가 없음 |

**결정**: A. 판단 기준: 단일 DB·단일 서비스 안에서의 다중 레코드 갱신은 표준 트랜잭션이 정답이고, B는 이 프로젝트 규모에 맞지 않음.
**감수하는 것**: 지금(Mock) 상태에서는 검증 불가능한 결정이다 — 실DB 전환 시점의 숙제로 명시적으로 이월한다.

### 질문 2: staffCode 채번

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현재 카운트 방식 유지 | 이미 구현됨, 단순 | **동시 채용 시 중복 채번**(팬텀 삽입, D2 baseline) |
| **B. 지점별 시퀀스 테이블 + 행 락(`SELECT ... FOR UPDATE`) (채택)** | 예약및결제 문서(정원 초과 방지)가 이미 검증한 해법과 완전히 같은 원리 재사용 — 이 프로젝트의 "카운트 대신 잠글 대상이 있는 리소스를 잠근다"는 표준 패턴의 세 번째 적용 | 시퀀스 테이블이라는 작은 새 엔티티 필요 |
| C. Postgres `SEQUENCE` 객체(지점별 또는 전역) | DB 네이티브라 락 코드 불필요 | 지점별 시퀀스는 지점 추가마다 동적 생성이 번거롭고, 전역 시퀀스는 "지점 내 001부터 시작"이라는 채번 규칙(§3)과 의미가 어긋남 |

**결정**: B. 판단 기준: 이미 검증된 같은 패턴을 재사용하는 게 새 해법(C)을 들이는 것보다 일관성 있고 위험이 적음.
**감수하는 것**: 지금(Mock)은 단일 프로세스라 A로도 실제로는 안 터진다 — 이 결정도 실DB 전환 전까지는 가설이다.

### 질문 3: 활성 파견 유일성 강제

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 애플리케이션 로직만(현행) | 이미 구현됨 | 동시 재배치 요청 2건이 겹치면 실DB에서 활성 파견이 2건 생길 수 있음 |
| **B. 부분 unique 인덱스(`StaffAssignment(staffId) WHERE endDate IS NULL`) (채택)** | 회원관리 ADR-MEM-02(이메일 재사용), 예약및결제 문서(예약 중복방지)와 같은 패턴 — 이 프로젝트의 세 번째 부분 unique 적용 사례, 팀 전체가 "활성 상태만 유일성 강제"라는 하나의 원칙으로 일관됨 | MockDataService에는 부분 인덱스 개념이 없어 지금은 애플리케이션 로직(A)이 대리 역할을 함 — **실DB에는 적용됨(2026-09-29, D27: `StaffAssignment_staffId_active_key`)** |

**결정**: B. 판단 기준: 이 프로젝트가 이미 두 번 검증한 패턴과의 일관성 — 이번이 세 번째라 "표준 패턴"이라고 부를 수 있는 수준이 됐다.
**감수하는 것**: A가 현재 유일한 방어선이라는 사실은 실DB 전환 전까지 안 바뀐다.

## 9. 감수하는 것 (종합)

- D1·D2·D3 모두 **"결정은 났지만 Mock 환경에서는 검증도 실효도 없는" 가설**이다 — 권한관리 도메인 ADR-AUTH-01과 같은 처지(실DB 전환 후 숙제로 이월).
- 이번 사이클은 유독 "실DB 전환 이후에나 의미가 생기는 결정"이 몰렸다 — 이 도메인 자체가 다중 레코드 갱신·동시성 문제가 많은 영역이기 때문(파견·퇴사가 Staff/Account/StaffAssignment 셋을 동시에 건드림).

## 10. ADR

### ADR-STF-01: 퇴사/파견발령 — 단일 DB 트랜잭션
- **컨텍스트**: 여러 레코드를 순차 mutation으로 갱신 중 — 실DB 전환 시 중간 실패가 불변규칙 3 위반 상태를 남길 수 있음(§6)
- **검토한 대안**: A DB 트랜잭션 / B SAGA(보상 로직)
- **결정**: A. 단일 모놀리스에 분산 트랜잭션 패턴은 과함
- **결과**: 좋아진 것 — 실패 시 항상 일관 상태 / 감수하는 것 — 지금은 검증 불가 / 숙제 — 실DB 전환 시점에 실제로 트랜잭션으로 묶기

### ADR-STF-02: staffCode 채번 — 지점별 시퀀스 테이블 + 행 락
- **컨텍스트**: 현재 카운트 방식은 예약및결제 문서가 이미 논파한 팬텀 삽입 패턴과 동일한 결함(§6)
- **검토한 대안**: A 카운트 유지 / B 시퀀스 테이블+행 락 / C DB SEQUENCE 객체
- **결정**: B. 예약및결제 문서와 같은 검증된 패턴 재사용
- **결과**: 좋아진 것 — 중복 채번 방지 / 감수하는 것 — 새 엔티티 필요 / 숙제 — 실DB 전환 시 적용

- **구현 준비(2026-09-29, D28)**: 헬퍼 `allocateBranchCode`(`apps/api/src/prisma/integrity.ts`)로 만들어 실DB 동시성 테스트까지 마쳤다. 단 **설계를 하나 바꿨다**: "시퀀스 행 `FOR UPDATE`"는 prefix의 첫 채번에서 잠글 행이 없어 팬텀 삽입이 되므로 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`으로 대체했다(근거: [architecture/data-integrity.md](../architecture/data-integrity.md) §5). 기존 번호가 있는 데이터를 이관할 때는 `CodeSequence`를 현재 최대 번호로 먼저 초기화해야 한다.
- **새로 발견한 공백(2026-09-29) → ADR-STF-04로 해소**: `assignStaff`가 이 직원을 담당자로 둔 회원(`Member.assignedStaffId`)과 옛 지점 강사 프로필을 정리하지 않아, 파견 이동 즉시 "회원↔담당 직원 같은 지점"(MEM-T02)이 깨진다. 대안과 권장안: [architecture/data-integrity.md](../architecture/data-integrity.md) §3.

### ADR-STF-03: 활성 파견 유일성 — 부분 unique 인덱스
- **컨텍스트**: "활성 파견 최대 1건" 불변식이 현재 애플리케이션 로직에만 의존(§6)
- **검토한 대안**: A 애플리케이션 로직만 / B 부분 unique 인덱스
- **결정**: B. 회원관리 ADR-MEM-02, 예약및결제 문서와 같은 원칙(이 프로젝트의 세 번째 적용)
- **결과**: 좋아진 것 — DB가 최종 방어선이 됨, 도메인 간 패턴 일관성 / 감수하는 것 — 지금은 A가 유일한 방어선 / 숙제 — 실DB 전환 시 적용

### ADR-STF-04: 파견 발령 시 담당 관계 정리 — 같은 트랜잭션에서 해제 (2026-09-29, DI-02)
- **컨텍스트**: `assignStaff`가 이 직원을 담당자로 둔 회원(`Member.assignedStaffId`)과 옛 지점 강사 프로필(`Instructor.staffId`)을 그대로 둬, 파견 이동 즉시 "회원↔담당 직원 같은 지점"(MEM-T02)이 깨진다. 이 상태에선 지점 일치를 DB 트리거로 강제할 수 없다(트리거가 파견 자체를 막음). 근거·조사: [architecture/data-integrity.md](../architecture/data-integrity.md) §3
- **검토한 대안**: A 파견 트랜잭션에서 담당 관계 정리 / B 담당 회원이 있으면 파견 거부 / C 담당 관계는 지점 무관으로 완화 / D 새 쓰기만 검사하는 트리거
- **결정**: A(사용자 결정). B는 본사 인사 결정을 현장 데이터가 막아 인사 권한 분리(불변규칙 1)와 충돌하고, C는 BRANCH_ADMIN이 타 지점 직원을 담당자 필드로 보게 돼 지점 격리와 어긋나며, D는 이미 생긴 불일치를 방치한다.
- **결과**: 좋아진 것 — 파견 후에도 지점 일치가 항상 성립해 DB 트리거로 강제 가능, 옛 지점이 떠난 직원을 계속 담당자로 보지 않음 / 감수하는 것 — 담당 회원이 사전 안내 없이 담당자를 잃는다(파견 응답에 해제된 회원 목록을 돌려줘 본사가 즉시 인지 — ADR-PRG-02와 같은 가시화 방식), 옛 지점 강사 프로필은 비활성화되고 직원 연결이 끊긴다(`staffId`가 unique라 새 지점에서 새 프로필을 만들려면 연결을 풀어야 함, 프로그램 이력은 옛 프로필을 계속 가리켜 보존) / 숙제 — mock 강사에는 직원 연결 필드가 없어 강사 프로필 정리는 강사 도메인 Prisma 이관 때 `assignStaff` 트랜잭션에 추가(DB 트리거가 누락을 막음). **D30(2026-09-29)**: 파견이 DB 트랜잭션(`StaffService.assign`)으로 옮겨지며 DB 쪽 강사 프로필 비활성화·연결 해제는 들어갔다. mock 강사 쪽은 강사 이관 때 합친다. **D31(2026-09-29)로 해소** — 강사 원천도 DB가 되어, 파견 커밋 뒤 연결을 푼 강사 행을 미러에 다시 반영한다(`catalog-flow.spec.ts`(D31 당시 이름 catalog-mirror))

### ADR-STF-05: 계약 종료 지점으로의 채용·파견 발령 차단 (2026-10-09, log/090)
- **컨텍스트**: 채용·발령 화면을 만들며 보니 API가 TERMINATED 지점으로의 채용·발령을 막지 않았다. 루트 불변식은 "계약 종료 지점은 신규 활동 차단"인데, 새 파견은 그 지점에 새 운영 인력을 넣는 신규 활동이다.
- **검토한 대안**: A API에서 409 / B 화면 지점 선택에서만 뺀다 / C 막지 않는다
- **결정**: A(사용자 결정). 판정은 Prisma 도메인이라 `loadGate()` 대신 트랜잭션 안에서 대상 지점의 `contractStatus`를 읽는다(branch-gate.ts 주석의 이관 후 방식). 대상 지점만 본다 — 종료 지점에서 **빼내는** 재배치는 종료 후 해야 할 일이라 허용한다. EXPIRED·RENEWAL_DUE는 막지 않는다(다른 도메인과 같다).
- **결과**: 좋아진 것 — 종료 지점에 활성 파견이 새로 생기지 않는다 / 감수하는 것 — 읽은 뒤 커밋 전 계약 상태가 바뀌는 경합은 막지 않는다(계약 상태를 바꾸는 API가 없음) / 숙제 — TERMINATED 전이 시 기존 파견 자동 종료(entities.md §2-1, `contract-termination.spec` todo). **ADR-STF-07(2026-10-10)로 해소** — 경합도 지점 행 락으로 막았다

### ADR-STF-06: 퇴사 시 담당 회원 해제 (2026-10-09, log/093)
- **컨텍스트**: 파견 발령은 담당 회원을 풀지만(ADR-STF-04) 퇴사는 풀지 않아, 퇴사한 직원이 회원 상세·지점 상세에 담당으로 남았다(log/090에서 발견).
- **검토한 대안**: A 퇴사 트랜잭션에서 담당을 풀고 응답에 풀린 회원 목록 / B 그대로 둔다
- **결정**: A(사용자 결정 1A). 파견과 같은 방식이다. 감사 기록(D44)의 `after`에 `releasedMemberCount`를 더한다. 강사 프로필 연결은 이번 범위가 아니다.
- **결과**: 좋아진 것 — 퇴사자가 담당으로 남지 않는다. 지점 관리자는 퇴사 직후 warning 알림으로 새 담당을 정할 회원을 안다 / 감수하는 것 — 퇴사 처리로 회원의 담당 이력이 사라진다(이력은 감사 기록의 건수만 남는다)

### ADR-STF-07: 지점 계약 종료 전이 시 진행 중 파견 자동 종료 (2026-10-10, log/099)
- **컨텍스트**: entities.md §2-1은 "TERMINATED 지점에 파견 중인 직원은 파견을 종료하고 본사 재배치 대상 목록에 올린다"고 설계했지만, 계약 상태를 바꾸는 코드 경로(API·배치)가 아예 없어 미구현이었다. 종료 지점에 활성 파견이 남으면 운영이 끝난 현장에 인력이 "배치된" 상태로 보인다.
- **검토한 대안**: 붙일 곳 — A SUPER_ADMIN 전용 `PATCH /branches/:branchId/contract-status` 신설 / B 서비스 메서드만(라우트 없음, 실제로는 아무도 부르지 않음) / C DB 트리거(수동 SQL에도 작동하지만 마이그레이션 필요, 감사 기록·응답 목록이 어려움). 종료일 — 전이한 날(KST 오늘) / `contractEndAt`(null 가능, 시작일보다 앞설 수 있음). 담당 관계 — ADR-STF-06처럼 해제 / 그대로. `Staff.branchId` — 그대로 두고 "활성 파견 없는 재직 직원 = 재배치 대기"로 판정 / nullable로 스키마 변경 / 본사 지점 행으로 이동.
- **결정**: 모두 앞의 안(사용자 결정, 2026-10-10). 한 트랜잭션에서 상태 변경 → (ACTIVE 등 → TERMINATED일 때만) 그 지점 활성 파견 `endDate=오늘` → 담당 회원 해제 → 강사 프로필 연결 해제·비활성화 → 직원별 감사 기록 `ASSIGNMENT_ENDED`(D44 이벤트 추가, 처리자는 본사 관리자). 응답에 `reassignmentTargets`(재배치 대상 직원)·`unassignedMembers`. 계정·재직 상태는 건드리지 않는다(퇴사가 아니다). 이미 TERMINATED인 지점의 재지정, RENEWAL_DUE·EXPIRED·ACTIVE로의 변경은 파견을 건드리지 않는다. TERMINATED에서 되돌려도 끝난 파견은 복구하지 않는다(본사가 다시 발령). 코드: `BranchService.changeContractStatus`, `staff/terminated-branch-assignments.ts`.
- **경합(ADR-STF-05가 감수했던 것)**: API가 생기며 "ACTIVE로 읽은 발령이 종료 뒤 커밋돼 종료 지점에 활성 파견이 남는" 경합이 실제로 가능해졌다. 상태 변경은 지점 행을 `FOR UPDATE`로, 채용·발령은 대상 지점 행을 `FOR SHARE`(`lockBranchForShare`, DI-03 헬퍼 옆)로 읽어 직렬화한다. 공유 락이라 같은 지점으로의 발령끼리는 막지 않는다.
- **결과**: 좋아진 것 — 종료 지점에 활성 파견·담당 관계가 남지 않고, 본사가 재배치할 직원을 응답으로 바로 안다 / 감수하는 것 — 수동 SQL로 상태를 바꾸면 자동 종료가 일어나지 않는다(API를 써야 한다). 재배치 대기 직원을 따로 모아 보는 목록·화면은 없다(직원 목록에서 종료 지점 소속으로 보인다). D44 결정 파일의 이벤트 표는 고치지 않았다(D38 — 결정 파일은 고치지 않는다, 이벤트 정의는 이 ADR과 `prisma/audit.ts`) / 숙제 — 계약 상태 변경 화면(admin-web), 지점 소속 계정 일괄 처리(entities.md §2-1 "계정", 권한관리 범위)

### A-6. 비즈니스 로직 & 엣지케이스
> 옛 1-3 설계서 §6 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- `staffCode` 생성 규칙: **최초 배치 지점** 코드 + 해당 지점 내 순번(zero-padded 3자리). 동시 등록 race condition 방지를 위해 DB 트랜잭션 + 지점별 시퀀스 테이블 또는 `SELECT ... FOR UPDATE` 사용. 이후 파견 전환이 일어나도 재생성하지 않음(§3 참고)
- 퇴사 처리(`/resign`)는 **트랜잭션으로 Staff.status 변경 + Account.isActive=false + 활성 StaffAssignment.endDate 마감을 원자적으로 처리**(권한관리 A-6과 연결되는 핵심 지점 — 이 API가 "퇴사 즉시 접근차단"의 실제 트리거. "즉시"가 문자 그대로 성립하려면 [권한관리 A-6](권한관리.md)의 `JwtAuthGuard` 매 요청 재조회가 함께 있어야 함 — `isActive=false`만 세팅하고 인증 가드가 여전히 JWT만 믿으면 토큰 만료 전까지 접근이 계속 가능함)
- **파견 발령(`/assignments`)**: 한 직원은 항상 `endDate=null`인 `StaffAssignment`가 최대 1건이어야 함(불변식) — 새 파견 생성 시 기존 활성 레코드를 먼저 마감하고 `Staff.branchId`를 새 지점으로 갱신하는 것까지 하나의 트랜잭션으로 묶음. 이 API는 SUPER_ADMIN 전용(§7) — 지점 관리자가 임의로 소속 직원을 다른 지점으로 보낼 수 없음(파견은 본사의 인력 배치 결정)
- 변경 신청은 필드 단위로 diff 저장(전체 프로필 재제출이 아님) → 승인자가 무엇이 바뀌는지 명확히 확인 가능
- 퇴사한 직원은 목록에서 기본적으로 숨기되(`status != 퇴사`), 필터로 조회 가능하게 유지(이력 보존)

### A-7. 권한 요약

- BRANCH_ADMIN: 현재 파견 지점의 직원만 CRUD(퇴사 포함), 타 지점 403
- SUPER_ADMIN 전용: 신규 등록(채용), 파견 발령
- STAFF 본인: 자기 레코드 조회만(직접 수정 불가, 변경 신청 경로는 미구현)

<details><summary>옛 1-3 설계서 §7 원문 — 위 요약이 현재 상태이고, 이 원문은 코드 주석이 인용하는 세부를 위해 보존한다(2026-10-01 복원)</summary>

- BRANCH_ADMIN은 **현재 파견되어 있는 지점**의 직원만 CRUD(퇴사 처리 포함), 타 지점 staffId 접근 시 403(architecture/entities.md BranchScopeGuard) — 파견 이동 즉시 예전 지점 관리자는 접근 권한을 잃고 새 지점 관리자가 얻음
- **신규 등록·파견 발령은 SUPER_ADMIN 전용**(§1, §5) — 본사가 채용·배치의 주체라는 원본 RFP 구조를 그대로 반영. BRANCH_ADMIN은 "현재 배정된 인력의 일상 관리"만 담당
- Staff 본인(Role=STAFF)은 자신의 레코드 조회 + 변경 신청만 가능(직접 수정 불가). 권한관리 문서의 STAFF 권한 매트릭스와 동일하게 타 직원 레코드는 조회조차 불가
- 전화번호 등 연락처는 목록 화면에서는 뒷자리 마스킹(`010-****-1234`), 상세 화면 진입 시 전체 노출(접근 로그 AuditLog 기록)

</details>
