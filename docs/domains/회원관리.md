## 0. 이 도메인 개요 (사용자 스토리)

- 회원으로서, 앱에서 회원가입 후 내가 다니는 지점을 선택하고 이용을 시작하고 싶다.
- 지점 관리자로서, 신규 방문 회원을 현장에서 직접 등록(오프라인 등록)할 수도 있어야 한다.
- 지점 관리자로서, 회원의 수강/예약/PT 잔여 세션을 한 화면에서 확인하고 싶다.
- 회원으로서, 내 PT 잔여 세션이 몇 회 남았는지 앱에서 확인하고 싶다.

RFP 원본 요구사항(회원 인적사항·수강내역·예약및결제내역·PT잔여세션 기록, 타 현장 조회 불가)은 이 도메인이 시스템의 핵심(원본 산출물의 본질)이라 **조정 없이** 그대로 구현 대상이다 — 권한관리처럼 범위를 줄인 지점이 없다. 다만 "회원 등급제(VIP 등 마케팅 세그먼트)"처럼 원본에 없는 기능은 추가하지 않는다(범위 확장 금지, 이 원칙 자체가 §1 불변규칙은 아니지만 §8 대안 검토에서 계속 적용됨).

## 6. 현행 구조 진단 (Baseline)

옛 §6이 이미 D1의 baseline을 진단해 뒀다 — 그대로 가져온다: 원래 Phase 1 권장안이던 "회원번호만 입력하면 연결"은 `memberNo`가 `{지점코드}{연도}-{순번}`로 **순차 생성되는 예측 가능한 값**이라는 걸 놓친 설계였다. 몇 번만 시도하면 타인의 회원번호를 맞혀 PT 세션·수강내역·연락처에 접근할 수 있다. 이게 D1을 만든 원인이다(정정된 방식은 §8에서 ADR로 재확인).

**D3의 baseline**: `MembersController.detail()`이 현재 인적사항만 반환하고, 수강내역·예약/결제내역·PT세션은 "해당 mock 엔티티가 아직 없어 후속 작업으로 남겨둔다"는 주석과 함께 비어 있다. RFP F05a("수강내역·예약및결제내역·PT잔여세션 기록")와 사용자 스토리("한 화면에서 확인")의 핵심을 아직 못 채운 상태 — 이게 이 도메인에서 가장 시급한 실제 구현 공백이다.

**D2의 baseline**: `/members/register`(앱 회원가입) 자체가 미구현이라 아직 실제로 터진 문제는 없다. 하지만 Account.email이 전역 unique이고 탈퇴 시 값 변형 없이 `isActive=false`만 하는 현재 패턴(권한관리 도메인 §10 ADR-AUTH-01·02와 동일 계열)을 그대로 두면, 나중에 `/members/register`를 구현하는 순간 "탈퇴 후 같은 이메일로 재가입 불가"라는, 누구도 요구하지 않은 제약이 생긴다.

## 8. 대안 → 트레이드오프 → 결정

### 질문 1: 오프라인↔앱 연동 인증 방식

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 회원번호만 입력 | 구현·UX 최단순 | **회원번호가 순차값이라 브루트포스 가능** — 개인정보 유출로 이어짐(불변규칙과는 별개지만 Q10 위반) |
| B. 회원번호+전화번호 둘 다 일치 (채택) | 전화번호는 추측 불가능한 개인정보라 브루트포스 방어, 관리자 승인 워크플로 없이 Phase 1 그대로 유지 | SMS 인증만큼의 소유권 증명은 아님(전화번호를 "안다"는 것과 "그 번호를 실제로 쓴다"는 건 다름) |
| C. SMS 인증(실제 소유권 증명) | 가장 안전 | 문자 발송 인프라·비용 필요, Phase 1 범위 초과 |

**결정**: B. 판단 기준: A는 Q10(개인정보 비노출) 위반 소지가 있어 배제, C는 인프라·일정 제약(C01)으로 Phase 2로 미룸.
**감수하는 것**: SMS만큼의 소유권 증명은 아니라서, 이미 그 사람의 전화번호를 알고 있는 지인이 회원번호까지 안다면 뚫릴 수 있다 — 시간당 5회 제한으로 대입 공격만 늦춘다.

### 질문 2: 탈퇴 회원 이메일 재사용

| 대안 | 장점 | 단점 |
|---|---|---|
| A. Account.email 전역 unique 유지(현행) | 구현 단순, 이메일=영구 고유 식별자로 감사 추적 쉬움 | 탈퇴 후 같은 이메일로 재가입이 영구히 불가 — 누구도 요구하지 않은 제약, 실사용자 불편 |
| B. 탈퇴 시 이메일 값을 변형(`withdrawn+timestamp+원본`)해 unique 제약 우회 | 재가입 허용, DB 제약 그대로 사용 가능 | 원본 이메일 조회 시 변형 로직을 항상 거쳐야 함(CS 응대 시 번거로움) |
| **C. 부분 unique 인덱스(활성 계정끼리만 유일) — 채택** | 이메일 값 원본 그대로 보존(감사·CS 유리), 재가입 시 완전히 새 Account 생성 | MockDataService(배열)에는 부분 unique 인덱스 개념이 없어 앱 레벨에서 "isActive인 계정끼리만 검사"를 직접 구현해야 함(실DB 전환 시 진짜 부분 인덱스로 교체 — **적용됨 2026-09-29, D27: `Account_email_active_key`**) |

**결정**: C. 판단 기준: 이 프로젝트가 이미 예약 중복 방지(예약및결제 문서)에서 쓴 "부분 unique 인덱스" 패턴과 원칙을 통일 — 같은 문제(활성 상태만 유일성 강제)를 도메인마다 다른 방식으로 풀지 않는다.
**감수하는 것**: 아직 `/members/register`가 미구현이라 이 결정은 코드로 확인되지 않은 가설이다. 구현 시 이 ADR대로 만든다.
**권한관리 도메인 갱신 필요**: [domains/권한관리.md](권한관리.md) 부록 A-3의 Account 데이터모델과 AUTH-T05 항목이 이 결정을 반영하도록 갱신해야 한다(§12에서 처리).

### 질문 3: 회원 상세 응답 범위

| 대안 | 장점 | 단점 |
|---|---|---|
| A. `GET /:id`가 수강+예약+PT를 전부 조인해서 반환 | 프론트 API 호출 1번, 스토리("한 화면") 문구와 가장 직접적으로 일치 | 상세 진입마다 무거운 조인, members 컨트롤러가 다른 도메인(reservations·payments) mock 데이터에 의존하게 됨(실DB 전환 시 서비스 간 호출로 리팩터링 필요) |
| **B. `GET /:id`는 요약 카운트만(수강중 N건·PT 잔여 합계·최근 결제일), 탭 클릭 시 `/:id/enrollments` 등 개별 API로 지연 로드 — 채택** | 이미 §5 API 명세가 이 하이브리드 형태로 설계돼 있었음(상세="요약 포함", 탭별=별도 API), 상세 진입이 가볍고 탭은 필요할 때만 로드 | 요약 카운트 계산 로직과 탭 API 로직이 일부 중복 |
| C. 요약 없이 탭 API만(상세는 인적사항만) | 가장 단순 | 스토리("PT 잔여 세션이 몇 회 남았는지 확인")를 상세 진입 즉시 못 보여줌 — 탭을 눌러야 앎 |

**결정**: B. 판단 기준: 이미 §5(API 명세)가 이 형태로 설계돼 있었다 — 새로 만드는 게 아니라 **설계된 대로 구현이 안 된 공백을 메우는 것**. C는 사용자 스토리를 약화시켜 배제.
**감수하는 것**: 요약 카운트(예: `enrollmentCount`, `ptRemainingTotal`, `lastPaymentAt`)를 계산하는 로직이 각 탭 API의 카운트 로직과 별개로 한 번 더 필요하다 — 중복이지만, 상세 진입 성능과 맞바꾼다.

## 9. 감수하는 것 (종합)

- D1: SMS 수준의 소유권 증명은 아니다 — Phase 2로 이월.
- D2: 아직 코드로 검증되지 않은 가설이다 — `/members/register` 구현 시점에 실제로 이 ADR대로 만들어야 한다.
- D3: 요약 카운트 로직 중복 — 성능과 맞바꾼 선택.
- **이 사이클에서 발견한 가장 큰 공백은 D3 자체가 아니라, RFP 핵심 요구(F05a)의 절반이 아직 코드에 없다는 사실이다.** Driver 결정은 끝났지만 구현은 남아 있다(§11).

## 10. ADR

### ADR-MEM-01: 오프라인↔앱 연동 — 회원번호+전화번호 동시 일치
- **컨텍스트**: 회원번호 단독 연결은 순차값이라 브루트포스 가능(§6 baseline)
- **검토한 대안**: A 회원번호만 / B 회원번호+전화번호 / C SMS 인증
- **결정**: B. A는 Q10 위반 소지, C는 일정·인프라 제약
- **결과**: 좋아진 것 — 대입 공격 방어, Phase 1 범위 유지 / 감수하는 것 — 소유권 완전 증명은 아님 / 숙제 — Phase 2 SMS 인증
- **구현(2026-09-26)**: `POST /members/link`(공개 라우트). `mock-data.service.ts`의 `linkMemberAccount()`가 memberNo+phone 동시 일치를 확인하고, 불일치 사유(회원번호 오류 vs 전화번호 오류)를 구분하지 않고 동일하게 `MEMBER_LINK_MISMATCH`(400)로 응답한다 — 부분 정보를 공격자에게 주지 않기 위함. 실패 횟수는 memberNo 기준으로 추적(공격 대상 회원번호별 1시간 슬라이딩 윈도, 5회 초과 시 429 `LINK_ATTEMPTS_EXCEEDED`). WITHDRAWN 회원은 연동 대상에서 제외(대조군: DORMANT는 허용). 연동 성공 시 `AuthService.issueSession()`(로그인과 동일한 토큰 발급 경로를 재사용)으로 즉시 로그인시킨다. **부수 발견**: `BranchScopeGuard`가 `@Public()` 메타데이터를 확인하지 않아 인증 없는 요청을 전부 403으로 막고 있었다 — `JwtAuthGuard`와 동일하게 `Reflector`로 `IS_PUBLIC_KEY`를 확인하도록 고쳤다(D2도 같은 문제를 겪었을 것이라 미리 공통 해결됨).

### ADR-MEM-02: 탈퇴 회원 이메일 — 부분 unique(활성 계정끼리만)
- **컨텍스트**: Account.email 전역 unique를 그대로 두면 탈퇴 후 재가입이 영구 불가(§6 baseline, AUTH-T05 이월)
- **검토한 대안**: A 전역 unique 유지 / B 탈퇴 시 이메일 값 변형 / C 부분 unique 인덱스
- **결정**: C. 예약및결제 문서(예약 중복방지)와 같은 패턴 원칙 통일
- **결과**: 좋아진 것 — 원본 이메일 보존, 도메인 간 설계 일관성 / 감수하는 것 — MockDataService에서는 앱레벨 구현 필요 / 숙제 — `/members/register` 구현 시 이 ADR대로
- **구현(2026-09-26)**: `POST /members/register`(공개 라우트). `mock-data.service.ts`에 `isEmailTakenByActiveAccount()`(이메일 유일성을 `isActive !== false`인 계정끼리만 검사)를 신설해 회원가입 시 사용했고, D1에서 이미 구현한 `linkMemberAccount()`의 이메일 중복 검사도 같은 메서드로 바꿔 두 기능이 일관되게 동작하도록 했다(§8 "같은 문제를 도메인마다 다르게 풀지 않는다" 원칙을 도메인 내부에서도 그대로 적용). `registerMember()`는 이메일 중복 검사를 먼저 하고 나서 기존 `createMember()`(계약종료 409·미성년 무동의 400·전화번호 중복 경고를 이미 갖고 있음)를 그대로 호출한다 — 인메모리 배열이라 트랜잭션이 없으므로 "실패 가능성이 있는 검사를 먼저 해서 부분 생성을 막는" 순서로 롤백을 대신했다. 가입 성공 시 D1과 동일하게 `AuthService.issueSession()`으로 즉시 로그인시킨다.

### ADR-MEM-03: 회원 상세 응답 — 요약 카운트 + 탭별 지연 로드
- **컨텍스트**: `GET /:id`가 현재 인적사항만 반환, F05a·사용자 스토리 미충족(§6 baseline)
- **검토한 대안**: A 전체 조인 / B 요약+탭별 지연 로드 / C 요약 없음
- **결정**: B. 기존 API 명세(§5)가 이미 이 형태로 설계돼 있었음
- **결과**: 좋아진 것 — 상세 진입 가벼움, 스토리 충족 / 감수하는 것 — 카운트 로직 중복 / 숙제 — 없음
- **구현(2026-09-26)**: `mock-data.service.ts`에 `memberSummary()`(enrollmentCount·ptRemainingTotal·lastPaymentAt 집계) + `courseEnrollments`/`ptSessions`/`ptSessionLogs` 배열 신설. `createEnrollment`/`createPTSession`은 `assertProgramInBranch`(프로그램-회원 지점 불일치 400)와 계약종료 지점 차단(409, 불변규칙 2)을 통과해야 하고, `usePTSession`(세션 차감)은 "신규 활동"이 아니라 TERMINATED 지점에서도 허용(ADR-FAC-03과 동일한 신규활동 vs 정정 구분). 예약·결제 내역 탭은 새 엔드포인트 대신 기존 `GET /reservations`에 `?memberId=` 필터만 추가해 재사용(`ReservationRow`가 이미 `payment`를 중첩).

### ADR-MEM-04: 전화번호 응답 마스킹 — 목록만, 전 역할, `010-****-1234`
- **컨텍스트**: Q10(개인정보가 별도 절차 없이 노출되지 않음)과 RFP 사용자인터페이스보안(1-2 #7)이 마스킹을 요구하는데 코드가 없었다([요구사항추적표](../reference/요구사항추적표.md) §2-3). 응답은 지점 격리·역할로만 제한돼, 본사 계정은 83곳 회원 전화번호를 목록 한 번에 받았다. 강사 목록은 MEMBER도 조회할 수 있어 강사 연락처가 회원에게 그대로 나갔다.
- **검토한 대안**: A 목록만 마스킹하고 상세·본인은 원문 / B 상세도 마스킹하고 원문 조회 API(`GET /members/:id/phone`)를 따로 둠 / C 상세는 MEMBER 본인만 원문, 관리자 수정 폼은 비워 둠
- **결정**: A(2026-10-07 사용자 선택). 옛 설계(A-7 원문 "목록 기본 마스킹, 상세 진입 시 전체 노출", 인사정보관리 STF-T03)와 같다. 상세로 들어가는 동작을 Q10의 "별도 절차"로 본다. 마스킹은 **역할과 무관**하게 적용한다. 본사 목록이 노출 범위가 가장 넓기 때문이다. 범위는 회원·직원·강사 목록(`GET /members`·`/staff`·`/instructors`)이다. 형식은 숫자 10자리 이상이면 앞 3자리·끝 4자리를 남기고, 그보다 짧으면 끝 4자리만 남긴다. 하이픈은 제자리에 둔다.
- **결과**: 좋아진 것 — 목록·지점 상세·강사 목록에서 원문이 사라졌다. 관리자 수정 폼은 상세 응답(원문)으로 채워지므로 마스킹값이 저장될 경로가 없다. B의 별도 API·버튼, C의 폼 변경이 필요 없다. / 감수하는 것 — 상세를 열면 원문을 본다. 열람 기록(AuditLog)은 B5-2에서 정한다. `?q=` 검색은 서버에서 원문으로 맞추므로, 번호를 아는 사람은 그 번호의 회원을 찾을 수 있다(자기 지점·본사 범위 안에서만). 강사는 상세 API가 없어 관리자도 목록에서는 원문을 볼 수 없다(등록·수정 응답은 원문). / 숙제 — 상세 열람 AuditLog(B5-2), 회원 모바일 웹이 쓰는 응답도 같은 규칙인지 확인(D40).
- **구현(2026-10-07)**: `src/common/privacy/mask-phone.ts`(`maskPhone`·`maskPhones`)를 세 목록 컨트롤러가 응답 직전에 부른다. 서비스 `list()`는 원문을 유지한다(검색·중복 경고가 원문을 쓴다).

### ADR-MEM-05: 회원 웹 가입 — 공개 지점 목록, 지점 등록 여부를 먼저 묻기 (2026-10-09, log/092)
- **컨텍스트**: `POST /members/register`·`/link`는 있었지만 회원 웹에 화면이 없어, 이미 계정이 있는 회원만 로그인할 수 있었다. 가입에는 `branchId`가 필요한데 `GET /branches`는 로그인해야 부를 수 있다. 지점에서 이미 등록한 회원이 새로 가입하면 같은 사람이 회원 둘이 된다(ADR-MEM-01이 막으려던 것).
- **검토한 대안**: 지점 선택 — A 공개 목록 API / B 지점 코드 직접 입력. 진입 — 한 화면에서 먼저 묻기 / 로그인 아래 링크 두 개. 가입 항목 — 연락처·생년월일 화면 필수 / API처럼 선택.
- **결정(사용자 결정 3건)**: `GET /branches/public`을 `@Public()`으로 둔다. 응답은 id·이름·지역만이고(계약상대방·기간·인원은 본사 데이터라 뺀다), 가입이 막힌 TERMINATED 지점은 뺀다. 로그인 화면 → `/join`에서 "지점에서 이미 등록했나요?"를 먼저 묻는다. 가입 화면은 연락처·생년월일을 필수로 받는다(API는 그대로 선택). 생년월일로 만 19세 미만이면 동의란을 보인다.
- **함께 고친 것**: 연동은 전화번호를 **숫자만** 비교한다. 지점이 `010-1234-5678`로 적었는데 본인이 `01012345678`로 넣으면 불일치가 나고, 그때마다 시간당 5회 시도를 잃었다. 저장된 번호가 비어 있으면 일치로 보지 않는다.
- **결과**: 좋아진 것 — 처음 오는 회원이 회원 웹에서 시작할 수 있고, 지점 등록 회원은 연동으로 이끈다. 가입·연동 응답의 세션으로 바로 로그인해 `/auth/login`을 다시 부르지 않는다(⑩) / 감수하는 것 — 지점 이름·지역 83곳이 공개된다(영업상 공개 정보로 본다). 공개 목록은 Worker rate limit 대상이 아니다(GET 1회, 쓰기 없음) / 숙제 — 약관·개인정보 수집 동의 화면은 없다(보안요건 1-2 #8 개인정보처리방침과 함께)

### A-6. 비즈니스 로직 & 엣지케이스
> 옛 1-6 설계서 §6 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- **전화번호 중복 체크**: 같은 지점 내 활성 회원 전화번호 중복 시 경고(완전 차단은 아님 — 가족 공유폰 등 현실적 케이스 고려), 앱 회원가입 시에는 Account.email/phone 유니크로 원천 차단
- **미성년 회원 가입**: `birthDate` 기준 만 19세 미만이면 등록/가입 API에서 `guardianConsent=true`를 요구(false 또는 미전달 시 400) — 실제 서명·증빙 첨부 없이 체크박스 동의로만 처리하는 포트폴리오 범위의 단순화입니다
- **오프라인 등록 → 앱 연동 — 연결 조건 정정(2026-09-15)**: `accountId=null`로 생성된 Member를 회원 본인이 앱에서 연결할 때, 원래 Phase 1 권장안이던 "**회원번호만 입력하면 연결**"은 `memberNo`가 `{지점코드}{연도}{순번}`로 **순차 생성되는 예측 가능한 값**이라는 걸 놓친 설계였습니다 — 몇 번만 시도하면 타인의 회원번호를 맞혀 그 사람의 PT 세션·수강내역·연락처에 접근할 수 있습니다("동일 전화번호 자동 매칭은 개인정보 리스크가 있다"고 인지했으면서, 대안으로 제시한 회원번호 단독 방식도 같은 리스크 범주였다는 걸 놓쳤습니다).
  - **정정된 방식**: **회원번호 + 전화번호를 함께 입력**받아 **둘 다 같은 Member 레코드와 일치할 때만** 연결합니다. 회원번호(추측 가능)와 전화번호(추측 불가능한 개인정보) 중 하나만으로는 안 되고 반드시 둘 다 맞아야 하므로, 이미 그 사람의 전화번호를 알고 있는 게 아닌 이상 회원번호를 브루트포스해도 뚫리지 않습니다. SMS 인증(Phase 2, 실제 소유권 증명)까지는 아니지만 회원번호 단독보다 훨씬 안전하고 관리자 승인 워크플로 없이 Phase 1 그대로 유지됩니다.
  - 연결 시도 실패는 계정 잠금(권한관리 A-6)과 같은 이유로 **횟수 제한**(예: 계정당 시간당 5회)을 둬 대입 공격을 늦춥니다.
- **PT 세션 차감**: `remainingSessions = totalSessions - usedSessions`는 항상 서버에서 계산(클라이언트 신뢰 안 함), 0 이하로 차감 시도하면 400 에러
- **타 지점 회원 조회 차단**: BranchScopeGuard로 BRANCH_ADMIN의 모든 회원 API에 `branchId` 강제 필터(원본 요구사항 5번 핵심 — "타현장 정보 조회 불가능하게 할 수 있는 권한 필요"를 기본 동작으로 강제 구현, 선택 옵션이 아니라 항상 적용)
- **회원 탈퇴**: 소프트 삭제(`status=WITHDRAWN`) + Account.isActive=false, 결제/예약 이력은 보존
- **담당 직원 배정(`assignedStaffId`)**: 회원의 `branchId`와 배정하려는 Staff의 `branchId`가 반드시 일치해야 함(1인 담당 모델, N:M 아님). 다른 지점 소속 staffId를 배정하는 것을 막는 서버측 검증은 아직 미구현 — 실제 회원 등록/수정 쓰기 API 구현 시 반드시 추가(docs/decisions/D16.md)
- **위탁계약 종료 지점 등록 차단**: 회원 등록(현장 등록·앱 가입 모두)은 대상 `Branch.contractStatus`가 `TERMINATED`면 409(`BRANCH_TERMINATED`)로 거부합니다 — [architecture/entities.md §2-1](../architecture/entities.md#2-1-branch지점-데이터-모델--위탁계약-필드)의 "신규 회원 등록 차단" 원칙의 실제 구현 지점입니다

### A-7. 권한 요약

- BRANCH_ADMIN: 본인 지점 회원 CRUD, 타 지점 불가(하드 룰)
- SUPER_ADMIN: 전체 조회, 개별 수정은 기술적으로 허용(예외 상황 대응)
- MEMBER 본인: 자신의 레코드만 조회/일부 수정(`assignedStaffId`·`memo`는 관리자 전용, 컨트롤러에서 차단)
- STAFF: 회원 관리 API 접근 불가(403)
- 전화번호: 목록(`GET /members`)은 모든 역할에 마스킹, 상세·본인 조회는 원문(ADR-MEM-04). 상세 열람 AuditLog는 미구현(B5-2)

### A-8. 구현 우선순위

**Phase 1(완료, API+화면)**: 회원 CRUD(현장 등록/조회/수정/상태전환), 지점별 격리, 미성년 동의 검증, 회원 상세 요약+수강내역·PT잔여세션·예약결제 탭(ADR-MEM-03, 2026-09-26), 오프라인↔앱 연동(ADR-MEM-01, `/members/link`, 2026-09-26), 앱 회원가입(ADR-MEM-02, `/members/register`, 2026-09-26).
**Phase 1(미완)**: 없음 — D1·D2·D3 전부 구현 완료. §12의 AUTH-T05 문서 동기화만 남음.
**Phase 2(선택)**: 오프라인↔앱 연동 승인 플로우, 회원 상태 자동 휴면 전환(6개월 미방문 배치). 전화번호 마스킹은 ADR-MEM-04로 구현(2026-10-07) — 상세 열람 AuditLog만 B5-2로 남음.

### A-9. 테스트 체크리스트
> 옛 1-6 설계서 §9 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- [ ] BRANCH_ADMIN이 타 지점 회원 상세 조회 시 403
