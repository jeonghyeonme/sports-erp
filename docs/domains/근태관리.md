## 0. 이 도메인 개요 (사용자 스토리)

- 직원으로서, 출근/퇴근 시 앱(또는 웹)에서 버튼 하나로 체크인/아웃하고 싶다.
- 직원으로서, 연차를 신청하면 지점 관리자가 승인/반려할 수 있길 원한다.
- 지점 관리자로서, 우리 지점 직원들의 이번 달 근태 현황(지각/결근/휴가)을 한눈에 보고 싶다.
- 직원으로서, 오늘 업무일지를 작성해 관리자와 공유하고 싶다.

원본 요구사항(현장별/개인별 근태 등록, 휴무·연차·병가 기록 및 일수 관리, 업무일지)에서 생체인증·GPS 기반 출퇴근 체크(위치 검증)는 제외하고 수동 체크인/체크아웃 버튼 방식으로 조정했다 — 연차 일수 자동 계산은 포함하되, 회계연도별 이월/소멸 같은 세부 인사 규정은 단순화했다.

### 제약

### 불변규칙 (협의 불가)
1. **같은 직원이 같은 날짜에 두 번 체크인할 수 없다.** (`ALREADY_CHECKED_IN` — 하루 1레코드라는 데이터 모델 자체가 이걸 전제한다)
2. **연차(`ANNUAL`) 승인 없이는 `LeaveBalance.usedDays`가 줄어들지 않는다.** (신청만으로 차감되면 반려 시 복구 로직이 필요해지고, 그 복구가 실패하는 경로가 곧 데이터 정합성 버그로 이어진다 — 협의 대상이 아니라 설계 원칙)
3. **BRANCH_ADMIN·STAFF는 자기 소속 범위를 벗어난 근태·휴가·업무일지에 접근할 수 없다.** (CLAUDE.md 4대 불변식 — 지점 데이터 격리)

## 5. Driver 우선순위

**불변규칙(§1) 항상 최우선** → D3(근태 데이터 자체의 정확성 — "현장별" 요건과 직결, 이미 왜곡이 실재함) → D2(불변규칙과 직결은 아니지만 RFP 명시 기능(F03b)의 핵심) → D1(이미 구현·정합성 확보된 결정, 재확인 성격)

## 6. 현행 구조 진단 (Baseline)

**D1**: `approveLeaveRequest`가 이미 승인 시점에만 `usedDays`를 더하고, `rejectLeaveRequest`는 애초에 건드리지 않는다 — 복구 로직 자체가 필요 없는 구조로 이미 되어 있다. 이게 D1을 "재확인"으로 만드는 이유다.

**D2**: 1-4문서 §8이 스스로 인정하듯 자동 결근 배치는 스케줄러가 없어 범위 제외됐다. 그 결과 코드를 다 훑어봐도 **`ABSENT` 상태를 실제로 대입하는 곳이 단 한 군데도 없다** — `AttendanceStatus` 타입에는 정의돼 있지만 죽은 코드다. `attendanceSummary`의 `absent: own.filter(r => r.status === 'ABSENT').length`는 항상 0을 반환한다. RFP F03b("결근 기록")가 문자 그대로는 지금 충족되지 않는다.

**D3**: `attendanceSummary(branchId, month)`는 **현재** `Staff.branchId`가 그 지점인 직원만 골라서, 그 직원의 **월 전체** 기록을 합산한다. 파견 이동은 월 중 언제든 일어날 수 있다(인사정보관리 도메인, ADR-STF-01). 9월 15일에 서초→강남으로 이동한 직원이 있다면, 9월 1~14일 서초에서의 실제 근무 기록이 **강남 요약에 잡히고 서초 요약에는 아예 나타나지 않는다** — "현장별 근태"라는 원본 요건(F03a)과 정면으로 어긋나는, 이번 사이클에서 새로 발견한 데이터 정확성 문제다.

**추가 baseline(2026-09-23, 사용자 지적으로 발견 — Driver는 아니고 횡단 결함)**: 체크인 날짜(`checkIn()`의 `date`)는 `new Date().toISOString().slice(0, 10)`로 구하는데, 이 함수는 서버 시간대와 무관하게 항상 UTC 기준이다. 이 서비스는 KST(UTC+9) 전용이라 **매일 00:00~08:59 KST 사이의 모든 체크인이 하루 전 날짜로 기록된다** — 드문 경계 케이스가 아니라 매일 상시 발생. 같은 패턴이 회원가입일·입사일·게시일·문서 보존기한 판정 등 5개 도메인 6곳에 더 있어 근태관리 국지적 수정이 아니라 [architecture/date-time-handling.md](../architecture/date-time-handling.md)로 분리해 다룬다 — 근태관리 사이클에서 발견됐지만 근태관리 소관이 아니다.

## 8. 대안 → 트레이드오프 → 결정

### 질문 1: 연차 차감 시점 (재확인)

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 신청 시점 차감 + 반려 시 복구 | "신청 즉시 잔여 반영"이라는 직관적 UX | 복구 로직이 별도로 필요하고, 그 로직이 실패하면 잔여일수가 영구히 어긋남 |
| **B. 승인 시점에만 차감 (채택, 현재 구현)** | 복구 로직 자체가 불필요 — 상태가 하나 줄어든 만큼 버그 표면적도 준다 | 신청자가 승인 전까지는 잔여일수 변화를 못 봄(신청 목록의 `warning` 필드로 사전 안내하는 것으로 보완) |

**결정**: B(현행 유지). 판단 기준: 상태를 하나 줄이는 쪽이 항상 안전하다는 원칙 — 복구 로직이 필요 없다는 것 자체가 버그 유형 하나를 원천 차단한다.
**감수하는 것**: 신청 시점엔 "잔여일수가 부족할 수 있다"는 경고만 보이고, 확정된 차감은 승인 후에야 안다.

### 질문 2: 결근 처리 방식

> **재검토(2026-09-23)**: 최초 결정(B, 조회 시점 지연 계산)은 "숫자가 정확한가"만 보고 "그 숫자가 날짜별 이력으로 남는가"를 놓쳤다 — 사용자 지적으로 발견. 근태관리는 급여·징계 근거가 되는 도메인이라 "그 순간 조회하면 맞는 값"과 "언제 결근이었는지 영구히 남는 기록"은 다른 요구다. 대안 D를 추가해 재결정한다.

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 스케줄러 도입 후 매일 자정 배치(1-4문서 원안) | 정확, "결근 즉시 기록"이라는 원래 설계 의도에 가장 가까움 | 스케줄러 인프라가 이 프로젝트에 아직 없음(1-7문서 노쇼 처리 등과 동일 사유로 이미 범위 제외) |
| B. 조회 시점 지연 계산, 미영속(최초 결정, 철회) | 스케줄러 없이도 숫자는 정확 | **결근 "이력"이 DB에 안 남는다** — 감사·급여 근거로 못 씀. 이번 달 지나면 그 결근이 있었다는 기록 자체가 사라짐(재현 불가) |
| C. 최초 조회 시 자동 영속화(materialize-on-read) — 과거 날짜를 누군가 처음 조회하는 순간 `ABSENT` 레코드를 써버림 | 스케줄러 없이도 이력이 남음 | 아무도 그 달을 조회 안 하면 영원히 기록이 안 남는 등 "언제 기록되는지"가 불확실. **GET 요청에 부작용(쓰기)이 생기는 것도 API 설계상 꺼림칙함** — 근태 데이터는 되돌리기 어려운데 그게 조회 한 번으로 확정되는 셈 |
| **D. 관리자가 명시적으로 "결근 확정"하는 액션 (채택)** — 현황판은 잠정 결근 수를 계속 미리보기로 보여주되(B와 같은 계산), 실제 `AttendanceRecord(status=ABSENT)` 저장은 BRANCH_ADMIN이 확정 액션을 눌러야만 일어남 | ADR-AUTH-02와 같은 원칙(되돌리기 어려운 인사 조치는 사람이 트리거) 재사용. 이력이 영속됨. 마침 1-4문서 §7이 이미 "근태기록 직접 수정은 관리자만(정정 사유 필수)"이라고 규정해 뒀는데 그 API 자체가 미구현이었다 — 이걸 실제로 만드는 계기가 됨 | 관리자가 확정을 안 누르면(방치) 여전히 이력이 안 남음 — 다만 이건 시스템 결함이 아니라 운영 절차(월말 확정 체크리스트)로 다뤄야 할 문제 |

**결정**: D. 판단 기준: 결근 확정은 급여·징계로 이어질 수 있는 되돌리기 어려운 조치라 ADR-AUTH-02와 같은 급으로 취급해야 한다. B는 이력이 아예 안 남아 배제, C는 GET에 쓰기 부작용을 넣는 게 이 프로젝트의 API 설계 관례와 안 맞아 배제.
**감수하는 것**: 관리자가 확정을 잊으면 이력이 안 남는다는 D 자체의 "방치 위험"은 여전히 있다 — ADR-AUTH-02가 이미 감수한 것과 같은 종류의 리스크이고, 같은 해법(운영 체크리스트)으로 완화한다.

### 질문 3: 근태 기록의 지점 귀속

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현재 파견 지점 기준(현행) | 구현 단순, 추가 필드 없음 | **소급 왜곡**(§6 baseline) — 월중 이동 시 과거 근무 기록이 잘못된 지점에 집계됨 |
| **B. `AttendanceRecord`에 체크인 시점의 `branchId`를 스냅샷으로 저장 (채택)** | 왜곡 없는 정확한 귀속, 이 프로젝트가 파견 이력(`StaffAssignment`)에서 이미 쓰는 "시점 스냅샷" 원칙과 일치 | 스키마 필드 추가 + `checkIn`/`attendanceSummary` 로직 변경 필요 |
| C. 왜곡을 알면서 방치 | 비용 0 | RFP F03a("현장별") 요건과 정면 충돌 — 이미 알고 있는 결함을 묵인하는 것 |

**결정**: B. 판단 기준: 이 프로젝트가 같은 유형의 문제(파견 이력)를 이미 스냅샷 원칙으로 풀어 둔 전례와 일치시킴 — 같은 문제를 도메인마다 다른 방식으로 풀지 않는다는 원칙(회원관리·인사정보관리·예약및결제의 부분 unique 인덱스 재사용과 같은 결의 판단).
**감수하는 것**: 아직 구현되지 않았다 — `AttendanceRecord.branchId` 필드 추가와 `checkIn`/`attendanceSummary` 수정이 실제 작업으로 남는다.

## 9. 감수하는 것 (종합)

- D1: 없음(현행 유지, 재확인) — 다만 신청자 입장의 UX 트레이드오프는 여전히 존재.
- D2: 관리자가 확정을 잊으면 이력이 안 남는다 — 운영 절차로 완화해야 하는 리스크.
- D3: 아직 구현되지 않았다 — 이번 사이클의 가장 명확한 실제 작업.
- **이 사이클 전체가 감수하는 것**: D2·D3 둘 다 "결정은 났지만 구현은 없다"로 끝났다 — 회원관리 사이클과 같은 패턴이다.

## 10. ADR

### ADR-ATT-01: 연차 차감 — 승인 시점에만 (반려 시 복구 로직 불필요)
- **컨텍스트**: 신청 시점 차감은 반려 시 복구 로직이 필요해 버그 표면적이 늘어남(§6)
- **검토한 대안**: A 신청 시점 차감+복구 / B 승인 시점에만 차감
- **결정**: B. 상태를 하나 줄이는 쪽이 항상 안전하다는 원칙
- **결과**: 좋아진 것 — 복구 로직 자체가 불필요 / 감수하는 것 — 신청 시점엔 확정 반영 안 보임 / 숙제 — 없음(확정 사항)

### ADR-ATT-02: 결근 처리 — 관리자 명시적 확정 액션 (2026-09-23 재결정, 최초 결정은 조회 시점 지연 계산이었으나 이력 미영속 문제로 철회)
- **컨텍스트**: 스케줄러 없이 결근 배치를 실행할 수 없어 `ABSENT`가 죽은 코드로 남아 있음(§6). 조회 시점 계산만으로는 급여·징계 근거가 되는 결근 "이력"이 DB에 안 남는다는 문제를 사용자가 지적해 재검토
- **검토한 대안**: A 스케줄러 배치 / B 조회 시점 지연 계산(미영속) / C 최초 조회 시 자동 영속화 / D 관리자 명시적 확정 액션
- **결정**: D. ADR-AUTH-02(되돌리기 어려운 인사 조치는 사람이 트리거)와 같은 원칙. 1-4문서 §7이 이미 규정하고도 미구현이던 "근태기록 직접 수정(정정 사유 필수)" API를 실제로 만드는 계기
- **결과**: 좋아진 것 — 결근 이력이 영속됨, 기존 프로젝트 원칙과 일관 / 감수하는 것 — 관리자가 확정을 잊으면 여전히 이력 공백(운영 절차로 완화) / 숙제 — `offDays` 필드(ATT-T05) + 확정 API 구현

### ADR-ATT-03: 근태 기록 지점 귀속 — 체크인 시점 branchId 스냅샷
- **컨텍스트**: 현재 파견 지점 기준 집계는 월중 이동 시 소급 왜곡됨(§6)
- **검토한 대안**: A 현재 파견 지점 기준(현행) / B 체크인 시점 스냅샷 / C 방치
- **결정**: B. 이 프로젝트의 "시점 스냅샷" 원칙(StaffAssignment)과 일치
- **결과**: 좋아진 것 — 왜곡 없는 정확한 귀속 / 감수하는 것 — 아직 미구현 / 숙제 — `AttendanceRecord.branchId` 필드 추가 + `checkIn`/`attendanceSummary` 로직 변경

### A-1. 데이터 모델

**AttendanceRecord**: `id, staffId(FK), date, checkInAt, checkOutAt(nullable), status(NORMAL/LATE/EARLY_LEAVE/ABSENT/ON_LEAVE), note`. `staffId+date` unique.
**LeaveRequest**: `id, staffId, type(ANNUAL/SICK/FAMILY_EVENT/OTHER), startDate, endDate, days(자동계산), reason, status(PENDING/APPROVED/REJECTED), approverId, reviewedAt`

**WorkLog**: `id, staffId, date, content, createdAt`. `staffId+date` 하루 1건(재작성 시 덮어씀).

인덱스: `AttendanceRecord(staffId, date)` unique, `LeaveRequest(staffId, status)`
