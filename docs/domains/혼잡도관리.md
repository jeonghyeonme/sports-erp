## 0. 이 도메인 개요 (사용자 스토리)

- 회원으로서, 헬스장에 가기 전 앱에서 지금 얼마나 붐비는지 확인하고 싶다.
- 지점 관리자로서, 자동 계산된 혼잡도가 실제와 다르면 수동으로 보정하고 싶다(예: 특별 이벤트로 사람이 몰릴 때).
- 지점 관리자로서, 시설별 정원 대비 이용률을 설정/관리하고 싶다.

원본 요구사항(시설별 이용현황·혼잡도를 5단계로 게시, 실시간 혹은 최대 30분 이내 반영)에서 IoT 센서·CCTV 기반 인원 계측은 하드웨어가 필요해 불가능하므로, **예약/체크인 데이터 기반 자동 계산은 Phase 2로 미루고 Phase 1은 관리자 수동 보정**으로 구현한다. QR 체크인·5분 주기 자동 계산 스케줄러는 모바일 앱과 스케줄러 인프라가 없어 범위 제외됐다(CLAUDE.md).

## 1. 요구사항 재분류

### 기능
| ID | 내용 |
|---|---|
| F08a | 시설별 이용현황·혼잡도를 5개 항목으로 나눠 게시 |
| F08b | 실시간 혹은 최대 30분 이내 이용현황 반영 |

### 품질
- F08b가 사실상 품질 요구(신선도)를 겸한다 — 아래 §3에서 수치화.

### 제약
- 하드웨어(IoT 센서·CCTV) 기반 계측 불가 — §0이 이미 명시.
- 스케줄러 인프라 없음(Phase 2 QR·자동계산이 이 제약으로 범위 제외됨).

### 불변규칙 (협의 불가)
1. **BRANCH_ADMIN은 자기 지점 시설만 관리한다.** (CLAUDE.md 4대 불변식 — 지점 데이터 격리)
2. **정원(`capacity`)은 0이 될 수 없다.** (0으로 나누면 계산 자체가 성립하지 않음 — 협의 대상이 아니라 수학적 제약)

## 6. 현행 구조 진단 (Baseline)

**D1**: `MockFacility`는 `currentCount`/`level`만 갖고 "언제 그 값이 정해졌는지"를 기록하는 필드가 전혀 없다. 관리자가 한 달 전에 수동 보정하고 잊어버려도, 회원 화면에는 방금 갱신된 값처럼 똑같이 보인다 — RFP F08b("최대 30분 이내 반영")를 **검증할 방법 자체가 없다**(신선한 값인지 오래된 값인지 시스템도, 사용자도 구분 불가).

**D2**: 부록 A-3에 `Facility.isActive`가 명시돼 있지만 `MockFacility` 타입에는 없다. 컨트롤러에도 `DELETE`가 없다 — 리모델링 등으로 운영을 멈춘 시설을 표현할 방법이 없어, 계속 목록·혼잡도 조회에 노출된다.

**D3**: `createFacility`·`setManualCongestion` 어디에도 `Branch.contractStatus` 체크가 없다. 회원등록·예약생성·게시글작성에는 이미 있는 "계약종료 지점 신규활동 차단"(CLAUDE.md 4대 불변식) 패턴이 이 도메인에만 빠져 있다 — 계약이 끝난 지점에서도 새 시설을 계속 등록하고 혼잡도를 조작할 수 있다.

## 7. 설계 질문 (Driver당 1개)

1. 혼잡도 값이 언제 갱신됐는지 어떻게 알 수 있게 할까?
2. 더 이상 운영하지 않는 시설을 어떻게 표시할까?
3. 계약이 끝난 지점에서도 시설 등록·혼잡도 보정을 계속 허용해야 할까?

### 질문 1: 값의 신선도 추적

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(추적 없음) | 없음 | RFP 요건 검증 자체가 불가능 |

| C. 스펙대로 별도 `CongestionSnapshot` 이력 테이블 전체 구현 | 정확한 이력 추적 | 이력이 의미 있으려면 주기적 자동 기록이 전제인데 스케줄러가 없어 지금은 "수동 보정 시점만 기록되는 듬성듬성한 이력"이 됨 — Phase2와 함께 가야 실효 |

### 질문 3: 계약종료 지점의 시설 신규활동

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(체크 없음) | 없음 | CLAUDE.md 핵심 불변식과 이 도메인만 어긋남 |
| **B. `createFacility`·`setManualCongestion`에 다른 도메인과 동일한 409 `BRANCH_TERMINATED` 체크 추가, `updateFacility`(기존 시설 속성 정정)는 제외 (채택)** | 기존 패턴 재사용. "신규 활동"과 "기존 데이터 정정"을 구분해 과도한 차단을 피함(정정은 조회에 준하는 관리 활동이라는 CLAUDE.md "과거 데이터 조회는 유지" 정신과 일치) | 어디까지가 "신규 활동"이고 어디까지가 "정정"인지 경계 판단이 한 번 더 필요 |
| C. 모든 쓰기(등록·수정·보정)를 다 차단 | 가장 엄격 | 기존 시설의 오타 수정 같은 정당한 관리 작업까지 막아 과도함 |

**감수하는 것**: "생성/보정 = 신규 활동, 수정 = 정정"이라는 구분이 다른 도메인(회원·예약 등)과 완전히 같은 칼로 그어진 건 아니다 — 이 도메인 특유의 판단이라는 걸 명시해 둔다.

## 10. ADR

### ADR-FAC-01: 혼잡도 값에 lastUpdatedAt 추가
- **컨텍스트**: 값의 신선도를 알 방법이 없어 RFP F08b 요건 검증이 불가능(§6)
- **검토한 대안**: A 현행 / B lastUpdatedAt 추가 / C 전체 이력 테이블
- **결정**: B. C는 스케줄러 없이는 절반만 의미 있어 과함
- **결과**: 좋아진 것 — 요건 검증 가능 / 감수하는 것 — 이력 없음 / 숙제 — 없음
- **구현됨(2026-09-25)**: `MockFacility.lastUpdatedAt` 추가 — `createFacility`(등록 시점)·`setManualCongestion`(보정 시점)에서 갱신. `updateFacility`(정원 등 속성 정정)는 의도적으로 갱신 대상에서 제외했다 — capacity가 바뀌어도 `currentCount`(실측값) 자체는 새로 들어온 게 아니므로, ADR 문구("수동 보정 시 갱신")를 문자 그대로 지켰다. admin-web `FacilitiesPage`에 "N분/시간/일 전 갱신" 표시를 추가해 RFP F08b 요건을 실제로 화면에서 확인할 수 있게 했다(값만 만들고 UI에서 못 보면 검증 불가능한 건 매한가지이므로 — ADR-BRD-01 때와 같은 이유). 회귀 테스트: `apps/api/test/facility-lifecycle.spec.ts`.

### ADR-FAC-02: Facility.isActive + 비활성화 API
- **컨텍스트**: 운영 중단 시설을 표현할 방법이 없음(§6)
- **검토한 대안**: A 현행 / B isActive 추가 / C 물리삭제
- **결정**: B. 소프트 삭제 원칙과 일치
- **결과**: 좋아진 것 — 운영중단 시설 목록에서 배제 가능 / 감수하는 것 — 없음 / 숙제 — 없음
- **구현됨(2026-09-25)**: `MockFacility.isActive`(기본 true) 추가. 별도 엔드포인트 대신 기존 `PATCH /facilities/:id`(`UpdateFacilityDto.isActive`)로 비활성화·재활성화를 모두 처리 — Instructor의 `DELETE`(비활성화 전용) 패턴과 다르게, 이쪽은 ADR 문구("비활성화 PATCH")를 그대로 따라 토글 가능한 PATCH 하나로 통일했다. `GET /facilities`는 `isActive=true`만 기본 노출(문자 그대로 "목록은 기본 isActive=true만"). admin-web `FacilitiesPage`에 BRANCH_ADMIN 전용 "운영 중단" 버튼 추가. 회귀 테스트: `apps/api/test/facility-lifecycle.spec.ts`.
- **이월 항목 해소(2026-09-25 추가 작업)**: 최초 구현 당시엔 "비활성 시설 보기" 화면이 없어 재활성화가 API 직접 호출로만 가능했다(감수하는 것으로 기록해둠). `GET /facilities`에 `?isActive=false` 쿼리를 추가해 비활성 시설만 조회할 수 있게 하고, admin-web `FacilitiesPage`에 BRANCH_ADMIN 전용 "운영 중/운영 중단" 탭을 추가했다 — "운영 중단" 탭에서는 각 카드에 "재활성화" 버튼이 뜬다(`PATCH isActive=true`, ADR 결정대로 같은 엔드포인트 재사용). 회귀 테스트 2건 추가: `?isActive=false`가 비활성만 돌려주는지, 비활성 목록에서 재활성화하면 활성 목록으로 되돌아오는지.

### ADR-FAC-03: 계약종료 지점의 시설 신규등록·보정 차단
- **컨텍스트**: CLAUDE.md 불변식이 이 도메인에만 적용 안 돼 있음(§6)
- **검토한 대안**: A 현행 / B 생성·보정만 차단, 수정은 허용 / C 전체 차단
- **결정**: B. "신규 활동 vs 정정" 구분을 CLAUDE.md 정신대로
- **결과**: 좋아진 것 — 불변식 일관 적용 / 감수하는 것 — 이 도메인 특유의 경계 판단 / 숙제 — 없음
- **구현됨(2026-09-25)**: `MockDataService.createFacility`·`setManualCongestion`에 `Branch.contractStatus==='TERMINATED'` 체크 추가(`createMember`/`createPost`와 동일한 인라인 패턴 — 공통 가드 중앙화는 실DB 전환 이후로 미룬다는 CLAUDE.md 결정에 따름). `updateFacility`는 의도적으로 제외. `contract-termination.spec.ts`에 시설 등록·혼잡도 보정·목록 조회·기존 시설 수정(차단 제외 확인) 케이스를 추가했다.

### ADR-FAC-04: 혼잡도 조회는 자동 폴링하지 않는다 (2026-10-07, B4 — traffic-infra-review 혼잡도 항목)
- **컨텍스트**: `GET /facilities`에는 캐시·ETag가 없다. 회원 모바일 웹(D40)이 이 화면을 몇 초 간격으로 자동 새로고침하면, 방문당 요청 수가 design-constants ⑩의 가정 10건을 넘어 민감도 값 30건 쪽으로 간다. 그러면 Workers 무료 한도(⑬, 지금 93%)와 Lambda 처리 한계(⑫)를 먼저 깎는다. 한편 혼잡도 값은 **관리자가 수동 보정할 때만 바뀐다**(D10, 자동 계산은 A-8 범위 제외). 몇 초 간격의 폴링으로 새 값을 받을 일이 거의 없다. 지점 N+1은 D31에서 이미 조인으로 없앴다.
- **검토한 대안**: A 회원 웹이 자동 폴링하지 않음(화면 진입·수동 새로고침만, 최소 간격) / B 서버·Worker에 5~10초 TTL 캐시 / C ETag·304
- **결정**: A. 값이 드물게 바뀌므로 폴링에 이득이 없다. B를 Worker에 두면 캐시가 api의 `BranchScopeGuard`보다 앞에 있어, 캐시 적중 시 지점 격리 검사를 건너뛴다. api 안에 두어도 Worker를 지나는 요청 수(⑬)는 줄지 않는다. C는 전송량만 줄고 요청은 그대로 Lambda·DB까지 간다.
- **결과**: 좋아진 것 — 서버 변경 없이 ⑩ 가정을 지킨다 / 감수하는 것 — 관리자가 보정한 값은 회원이 새로고침해야 보인다. `lastUpdatedAt`(ADR-FAC-01)으로 "N분 전 갱신"을 함께 보여 준다 / 숙제 — B1-3(혼잡도 화면)에서 적용하고, 방문당 실제 호출 수를 ⑩ 실측으로 확인한다(B1-4)
- **재고 트리거**: 자동 계산(D10 Phase 2)이 들어와 값이 주기적으로 바뀔 때 → 그 주기에 맞춘 폴링 + B(캐시)를 다시 검토한다.

### A-6. 비즈니스 로직 & 엣지케이스
> 옛 1-9 설계서 §4·§7 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

#### 혼잡도 계산 로직(옛 §4)

```
현재 이용 인원 = COUNT(FacilityCheckIn WHERE facilityId=? AND checkOutAt IS NULL)
                 + (해당 시간대 예약 확정 건수 중 아직 체크인 전인 임박 예약, 옵션)
이용률(%) = 현재 이용 인원 / capacity * 100

5단계 매핑(원본 "5개 항목" 요건):
  0~20%   → 1단계(여유)
  21~40%  → 2단계(보통)
  41~60%  → 3단계(약간 붐빔)
  61~80%  → 4단계(붐빔)
  81%~    → 5단계(매우 붐빔)
```

- **자동 스냅샷**: 5분 주기 스케줄러(Cron)가 시설별 현재 이용 인원을 계산해 `CongestionSnapshot(source=AUTO)` 기록 → 원본의 "최대 30분 이내 반영" 요건을 5분 주기로 상회 달성
- **수동 보정**: 관리자가 값을 직접 입력하면 `source=MANUAL`로 별도 기록되고, 이후 자동 계산이 재개될 때까지(다음 스케줄 tick) 그 값이 조회 API의 최신값으로 우선 노출
- **입장/퇴장 체크인 방식**: 회원 모바일 웹에 시설별 QR 코드를 게시(정적 이미지로 충분) → 회원이 스캔 시 `POST /facility-checkins`, 나갈 때 다시 스캔 시 체크아웃 처리. QR 스캔이 번거로운 회원을 위해 관리자가 대리로 체크인/아웃 처리하는 화면도 제공(현실적 사용성 확보)

#### 비즈니스 로직 & 엣지케이스(옛 §7)

- **체크아웃 누락 처리**: 회원이 퇴장 스캔을 깜빡하는 경우가 실무에서 매우 흔함 → **시설 운영 마감 시각에 배치로 미체크아웃 건을 자동 체크아웃 처리**(그렇지 않으면 혼잡도가 영원히 부풀어 표시됨). 예: 매일 23:00에 `checkOutAt IS NULL`인 모든 건을 강제 마감
- **정원 0 또는 미설정 시설**: `capacity`가 0이면 이용률 계산에서 나눗셈 오류가 나므로 등록 시 capacity 필수값(1 이상) 검증
- **자동/수동 값 충돌**: 수동 보정 후 5분 뒤 자동 계산이 다시 override — 이게 의도한 동작임을 관리자 화면에 "자동 계산은 O분 후 갱신됩니다" 안내 문구로 명시(사용자 혼란 방지)
