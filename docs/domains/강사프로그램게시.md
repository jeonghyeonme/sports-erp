## 0. 이 도메인 개요 (사용자 스토리)

- 지점 관리자로서, 신규 강사를 등록하고 프로필(경력/전문분야)을 관리하고 싶다.
- 지점 관리자로서, 새 프로그램(요가, PT 등)을 개설하고 시간표를 등록하고 싶다.
- 회원으로서, 종목/시간대/연령대로 프로그램을 필터링해서 찾고 싶다.

원본 요구사항(종목별 강사/프로그램 정보 게시, 종목·시간대·연령대별 리스트)은 CRUD+필터링 수준이라 조정 없이 그대로 구현한다. 예약및결제(1-7)·혼잡도관리(1-9)와 데이터로 강하게 연결되는 "기준정보(마스터 데이터)" 성격이다.

## 5. Driver 우선순위

**불변규칙(§1) 항상 최우선** → D3(관계 무결성 — 이미 강사에서 검증하는 패턴을 시설에 빠뜨린 비일관성) → D2(RFP 산출물 품질에 직결되는 관리자 안내) → D1(입력 검증 시점 개선, 리스크는 상대적으로 낮음)

## 6. 현행 구조 진단 (Baseline)

**D1**: `CreateProgramDto.capacity`는 `@IsOptional()`이라 `pricingType=PAID_SESSION`으로 프로그램을 만들면서 `capacity`를 안 보내도 통과한다. 실제 오류는 한참 뒤 `createScheduleSlot` 호출 시점에야(`capacity ?? program.capacity` → `undefined` → `INVALID_CAPACITY`) 나온다 — 관리자 입장에서는 "프로그램은 만들어졌는데 회차 등록이 알 수 없이 실패"하는 것처럼 보인다.

**D2**: `updateProgramStatus`는 `program.status`만 바꾸고 `scheduleSlots`·`reservations`는 전혀 건드리지 않는다. 부록 A-6이 "이미 예약된 미래 회차는 유지하되 관리자에게 휴강 처리 필요 안내"라고 명시했지만, 그 "안내"에 해당하는 코드가 어디에도 없다 — 관리자가 프로그램을 PAUSED로 바꿔도 거기 몇 명이 예약돼 있는지 알 방법이 API 응답에 없다.

**D3**: `createProgram`/`updateProgram`은 `instructorId`가 들어오면 `assertInstructorInBranch`로 지점 일치를 검증하지만, 같은 함수 안에서 `facilityId`는 아무 검증 없이 그대로 저장한다 — 다른 지점 시설 id를 그대로 넣어도 통과한다. 같은 클래스의 문제(다른 지점 리소스를 프로그램에 잘못 연결)를 강사에는 막아두고 시설에는 빠뜨린 비일관성이다.

## 7. 설계 질문 (Driver당 1개)

1. `PAID_SESSION` 프로그램에 `capacity`가 없으면 언제 막아야 할까?
2. 프로그램이 `PAUSED`/`ENDED`로 바뀔 때 이미 확정된 예약을 관리자가 어떻게 알 수 있을까?
3. `facilityId`도 `instructorId`처럼 지점 일치를 검증해야 할까?

## 8. 대안 → 트레이드오프 → 결정

### 질문 1: capacity 필수 강제 시점

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(회차 생성 시점에야 발견) | 구현 없음 | 원인(프로그램 생성 시 capacity 누락)과 증상(회차 생성 실패)이 멀어 관리자가 헷갈림 — 근태관리 사이클에서 사용자가 지적한 "인간 실수" 관점과 같은 결 |
| **B. `createProgram`/`updateProgram`에서 `pricingType=PAID_SESSION`이면 `capacity>=1` 필수 검증 (채택)** | 원인 시점에 바로 명확한 에러 — 회차 생성까지 안 가봐도 앎 | `PAID_SESSION`으로 바꾸는 수정(`updateProgram`)에도 같은 검증이 필요해 조건 분기가 한 군데 더 생김 |
| C. `capacity` 없으면 프로젝트 전역 기본값(예: 10) 적용 | 입력 부담 최소 | 관리자가 실제 정원을 잊고 넘어갈 위험 — 정원은 임의로 추측할 성질의 값이 아님 |

**결정**: B. 판단 기준: C는 정원이라는, 추측하면 안 되는 값을 시스템이 대신 정하는 셈이라 배제.
**감수하는 것**: `updateProgram`에서 `pricingType`을 나중에 `PAID_SESSION`으로 바꾸는 경로도 같은 검증을 타야 해, 검증 로직이 생성·수정 두 곳에 필요하다(공통 헬퍼로 묶으면 완화 가능).

### 질문 2: 상태 전이 시 확정 예약 가시화

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(아무 정보 없음) | 없음 | 부록 A-6이 명시한 "안내" 요건 미충족 |
| **B. 상태 전이 응답에 그 프로그램의 미래(오늘 이후) 확정 예약 건수·목록을 포함 (채택)** | 알림 인프라 없이 바로 구현 가능, 응답 하나로 관리자가 즉시 인지 | 예약 도메인 데이터를 프로그램 도메인 응답에 섞어야 함(모듈 간 참조) |
| C. 실시간 알림(이메일/푸시)로 예약자에게 통보 | 가장 사용자 친화적 | 알림 채널이 이 프로젝트에 없음(부록 A-8이 이미 이 이유로 제외) |

**감수하는 것**: 프로그램 컨트롤러가 예약 데이터를 조회해야 해 모듈 경계가 살짝 흐려진다 — `MockDataService`가 이미 전 도메인 데이터를 갖고 있어 지금은 비용이 낮지만, 실DB 전환 후 서비스 분리 시 다시 볼 지점.

## 10. ADR

### ADR-PRG-01: PAID_SESSION 프로그램의 capacity 필수 검증을 생성/수정 시점으로
- **컨텍스트**: 현재는 회차 생성 시점에야 간접적으로 걸려 원인-증상이 멀다(§6)
- **검토한 대안**: A 현행 유지 / B 생성·수정 시 필수 검증 / C 기본값 적용
- **결정**: B. 정원은 추측하면 안 되는 값
- **결과**: 좋아진 것 — 즉시 명확한 에러 / 감수하는 것 — 검증 로직 두 곳 필요 / 숙제 — 없음
- **구현됨(2026-09-25)**: `assertCapacityForPricingType` 헬퍼를 추가해 `createProgram`·`updateProgram` 양쪽에서 호출한다(ADR이 예상한 "검증 로직 두 곳 필요"를 헬퍼 공유로 완화 — 로직은 한 곳, 호출은 두 곳). `updateProgram`을 구현하다가 **기존에 있던 별개 버그**를 발견해 같이 고쳤다: 이 함수는 원래 필드별로 "검증 → 즉시 반영"을 순서대로 하고 있어서, 뒤쪽 필드(예: capacity) 검증이 실패해도 앞쪽 필드(name·category 등)는 이미 살아있는 `program` 객체에 반영된 뒤였다 — 400을 반환하면서도 일부 필드는 조용히 바뀌는 반쪽짜리 수정 결함이었다. 이번에 모든 검증(instructorId·facilityId·capacity)을 먼저 끝내고 나서 한 번에 필드를 반영하도록 순서를 바꿔 해소했다(`program-integrity.spec.ts`의 "검증 실패 시 다른 필드도 함께 반영되지 않는다" 케이스로 고정). admin-web `ProgramsPage`도 `pricingType=PAID_SESSION`일 때 정원 입력을 `required`로 바꾸고 제출 전 가드를 추가해 백엔드까지 왕복하지 않고 바로 막는다. 회귀 테스트: `apps/api/test/program-integrity.spec.ts`.

### ADR-PRG-02: 상태 전이 응답에 확정 예약 정보 포함
- **컨텍스트**: 부록 A-6의 "안내" 요건이 구현 안 됨(§6)
- **검토한 대안**: A 현행 유지 / B 응답에 포함 / C 실시간 알림
- **결정**: B. 알림 인프라 없이 즉시 구현 가능
- **결과**: 좋아진 것 — 관리자가 즉시 인지 / 감수하는 것 — 모듈 간 참조 증가 / 숙제 — 없음(구현만 남음)

### A-3. 데이터 모델

**Instructor**: `id, branchId(FK), name, specialty, bio, photoUrl, phone, isActive`. (`commissionRate`는 강사 정산 범위 제외로 코드에서 제거됨 — CLAUDE.md 범위 제외 목록)

**Program**: `id, branchId(FK), facilityId(FK, nullable), instructorId(FK, nullable), name, category, ageGroup(ALL/CHILD/TEEN/ADULT/SENIOR), description, pricingType(FREE_ACCESS/PAID_SESSION/PT_PACKAGE), price, capacity(nullable), status(PREPARING/RUNNING/PAUSED/ENDED), startDate, endDate(nullable)`

**상태 전이표**: `PREPARING→{RUNNING,ENDED}`, `RUNNING→{PAUSED,ENDED}`, `PAUSED→{RUNNING,ENDED}`, `ENDED→{}`(종결)

**ProgramScheduleTemplate**(요일별 기본 시간표, 회차 대량 생성용, **미구현**): `id, programId, dayOfWeek, startTime, endTime`

인덱스: `Program(branchId, status)`, `Program(branchId, category, ageGroup, pricingType)`, `Instructor(branchId)`

#### 3-1. `pricingType` — 지점별 유·무료 프로그램 관리의 핵심

`Program`이 이미 `branchId`를 갖고 있어 같은 종목이라도 지점마다 별도 row로 관리되고, 가격도 지점 관리자가 독립적으로 설정합니다. 여기에 더해 "이용 방식" 자체가 다른 세 갈래를 명시적인 enum으로 구분합니다 — `price===0`이라는 암묵적 규칙 대신 코드/화면 분기의 기준으로 삼습니다.

| pricingType | 의미 | 예약/결제 방식 | 예시 |
|---|---|---|---|
| `FREE_ACCESS` | 자유이용형 — 예약 없이 상시 이용 | 예약및결제 문서 Reservation/Payment 대상 아님. 혼잡도관리 문서 `FacilityCheckIn`(QR 체크인)만으로 이용 기록 | 헬스장 자유이용, 독서실 |
| `PAID_SESSION` | 회차 예약형 (무료 회차도 가능) | 예약및결제 문서 `Reservation` 생성, `price>0`이면 `Payment`까지 진행 | 요가·필라테스 그룹 클래스 |
| `PT_PACKAGE` | 세션 차감형(PT) | 회원관리 문서 `PTSession`으로 관리, Reservation/Payment 미사용 | 개인 PT, 골프레슨 |

> `PAID_SESSION`인데 `price=0`인 경우는 "정원은 관리해야 하지만 무료인 클래스"(예: 신규 회원 체험 클래스)로, "예약 자체가 없는 자유이용(`FREE_ACCESS`)"과는 구분됩니다.

#### 3-2. `status` — 지점별 "진행중인 프로그램" 파악

원본 요구사항에는 없지만, 실사용 단계에서 "이 지점은 지금 뭘 운영 중인가"를 바로 답할 수 있어야 한다는 요구가 있어 추가했습니다. `isActive` 불리언 하나로는 "아직 시작 전"과 "끝난 것"을 구분할 수 없어서, 4단계 상태로 명시했습니다.

| status | 의미 | 허용되는 다음 상태 |
|---|---|---|
| `PREPARING` | 준비중 — 등록됐지만 `startDate` 이전 | → RUNNING, ENDED(개강 취소) |
| `RUNNING` | 진행중 — 현재 운영 중 | → PAUSED, ENDED |
| `PAUSED` | 휴강(일시중단) — 강사 공백 등으로 임시 중단 | → RUNNING, ENDED |
| `ENDED` | 종료 — 더 이상 운영하지 않음(과거의 `isActive=false`에 대응) | (종결 상태) |

지점별로 "지금 진행중인 프로그램"을 파악하는 것은 `Program(branchId, status)` 인덱스를 태운 단순 조회 하나로 해결됩니다 — `WHERE branchId=? AND status='RUNNING'`. 지점 대시보드에는 상태별 개수(준비중 N · 진행중 N · 휴강 N)를 함께 보여줍니다.

> 상태 전이는 Phase 1에서는 관리자가 수동으로 변경합니다. Phase 2에서 `startDate`/`endDate` 도달 시 자동으로 PREPARING→RUNNING, RUNNING→ENDED 전환하는 배치를 추가할 수 있는데, 관리자가 수동으로 PAUSED로 바꿔둔 경우는 자동 전이가 덮어쓰지 않도록 예외 처리가 필요합니다.

### A-6. 비즈니스 로직 & 엣지케이스
> 옛 1-8 설계서 §6 원문을 2026-10-01 그대로 옮겼다(병합 때 빠졌던 절). 범위 제외·변경된 항목은 본문 ADR과 A-8이 우선한다.

- 강사 비활성화(`isActive=false`)는 기존에 연결된 예약/PT세션 데이터를 깨뜨리지 않도록 물리 삭제 대신 소프트 삭제 원칙 적용(architecture/system-overview.md §4)
- 프로그램은 `isActive` 대신 `status`로 생애주기를 관리합니다 — `ENDED`(또는 `PAUSED`)로 전환 시 이후 신규 예약만 차단하고, 이미 예약된 미래 회차는 유지하되 관리자에게 "휴강 처리 필요" 안내
- `PATCH /programs/:id/status`는 §3-2 표에 없는 전이(예: ENDED → RUNNING)를 요청하면 409(`INVALID_STATUS_TRANSITION`)로 거부
- 회차 일괄 생성 시 기존 회차와 시간 중복 검사(같은 시설, 겹치는 시간대에 다른 프로그램이 이미 있으면 경고 — 시설 스케줄 충돌 방지, 혼잡도관리 문서 Facility와 연동)
- 필터 조합(`category`+`ageGroup`+`pricingType`)은 쿼리 파라미터 조합에 따라 동적 WHERE 절 구성, 인덱스는 가장 많이 쓰이는 `branchId+category` 우선
- `pricingType=FREE_ACCESS`인 프로그램을 등록/수정할 때는 `price`·`capacity`(회차 정원) 입력을 비활성화하고 혼잡도관리 문서의 `Facility`와 연결만 요구(자유이용은 시설 자체의 정원으로 관리되므로 프로그램 단의 정원은 무의미)

### A-7. 권한 요약

- BRANCH_ADMIN: 본인 지점 강사·프로그램 CRUD
- 회원/전체: 조회만, 기본적으로 본인 소속 지점만 노출(2026-09-20 정책 확정)

### A-8. 구현 우선순위

### A-9. 테스트 체크리스트
