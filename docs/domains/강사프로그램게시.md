> **상태**: 초안 (2026-09-23). [process/03_도메인_사이클_템플릿.md](../process/03_도메인_사이클_템플릿.md) 11단계 적용 — 6호 사이클(중 우선순위, 스킬 산출물).

## 0. 이 도메인 개요 (사용자 스토리)

- 지점 관리자로서, 신규 강사를 등록하고 프로필(경력/전문분야)을 관리하고 싶다.
- 지점 관리자로서, 새 프로그램(요가, PT 등)을 개설하고 시간표를 등록하고 싶다.
- 회원으로서, 종목/시간대/연령대로 프로그램을 필터링해서 찾고 싶다.

원본 요구사항(종목별 강사/프로그램 정보 게시, 종목·시간대·연령대별 리스트)은 CRUD+필터링 수준이라 조정 없이 그대로 구현한다. 예약및결제(1-7)·혼잡도관리(1-9)와 데이터로 강하게 연결되는 "기준정보(마스터 데이터)" 성격이다.

## 4. Architecture Driver 식별 (3개로 제한)

| # | Driver | 왜 구조를 바꾸는가 |
|---|---|---|
| D1 | 가격유형(`pricingType`)별 필드 요구사항 강제 시점 | 검증을 어디서 하느냐가 에러 발생 시점·메시지의 명확성을 결정 |
| D2 | 상태 전이가 연결된 예약에 미치는 영향의 가시화 | 관리자가 "휴강 처리 필요"를 알 방법이 있는지 — 응답 스키마를 결정 |
| D3 | `facilityId`의 지점 일치 검증 | 데이터 관계 무결성 — `instructorId`와 같은 수준으로 강제할지 |

**Driver로 승격하지 않은 것 (Tier2 — 규칙표로만 관리)**

| ID | 규칙 | 근거 | 처리 |
|---|---|---|---|
| PRG-T01 | `FREE_ACCESS`는 `price`/`capacity`를 서버가 0/undefined로 강제 정규화 | 이미 구현·검증 가능한 단순 규칙 | 구현 완료, **테스트 없음** |
| PRG-T02 | 시설 시간대 충돌 검사 | 1-8문서 §8이 이미 명시적으로 범위 제외(스케줄러·알림 없음) | 미구현, 재론 대상 아님 |
| PRG-T03 | 휴강 처리 시 예약자 알림 | 알림 채널 없어 범위 제외(1-8문서 §8) | 미구현, 재론 대상 아님(D2는 "알림"이 아니라 "관리자 화면에서 확인 가능"까지만 — 범위 다름) |
| PRG-T04 | 요일 템플릿 기반 회차 일괄 생성 | Phase2, 관리자 입력 부담 경감 목적 — 구조적 결정 아님 | 미구현 |

## 5. Driver 우선순위

**불변규칙(§1) 항상 최우선** → D3(관계 무결성 — 이미 강사에서 검증하는 패턴을 시설에 빠뜨린 비일관성) → D2(RFP 산출물 품질에 직결되는 관리자 안내) → D1(입력 검증 시점 개선, 리스크는 상대적으로 낮음)

## 6. 현행 구조 진단 (Baseline)

**D1**: `CreateProgramDto.capacity`는 `@IsOptional()`이라 `pricingType=PAID_SESSION`으로 프로그램을 만들면서 `capacity`를 안 보내도 통과한다. 실제 오류는 한참 뒤 `createScheduleSlot` 호출 시점에야(`capacity ?? program.capacity` → `undefined` → `INVALID_CAPACITY`) 나온다 — 관리자 입장에서는 "프로그램은 만들어졌는데 회차 등록이 알 수 없이 실패"하는 것처럼 보인다.

**D2**: `updateProgramStatus`는 `program.status`만 바꾸고 `scheduleSlots`·`reservations`는 전혀 건드리지 않는다. 1-8문서 §6이 "이미 예약된 미래 회차는 유지하되 관리자에게 휴강 처리 필요 안내"라고 명시했지만, 그 "안내"에 해당하는 코드가 어디에도 없다 — 관리자가 프로그램을 PAUSED로 바꿔도 거기 몇 명이 예약돼 있는지 알 방법이 API 응답에 없다.

**D3**: `createProgram`/`updateProgram`은 `instructorId`가 들어오면 `assertInstructorInBranch`로 지점 일치를 검증하지만, 같은 함수 안에서 `facilityId`는 아무 검증 없이 그대로 저장한다 — 다른 지점 시설 id를 그대로 넣어도 통과한다. 같은 클래스의 문제(다른 지점 리소스를 프로그램에 잘못 연결)를 강사에는 막아두고 시설에는 빠뜨린 비일관성이다.

## 7. 설계 질문 (Driver당 1개)

1. `PAID_SESSION` 프로그램에 `capacity`가 없으면 언제 막아야 할까?
2. 프로그램이 `PAUSED`/`ENDED`로 바뀔 때 이미 확정된 예약을 관리자가 어떻게 알 수 있을까?
3. `facilityId`도 `instructorId`처럼 지점 일치를 검증해야 할까?

## 8. 대안 → 트레이드오프 → 결정

### 질문 1: capacity 필수 강제 시점

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(회차 생성 시점에야 발견) | 구현 없음 | 원인(프로그램 생성 시 capacity 누락)과 증상(회차 생성 실패)이 멀어 관리자가 헷갈림 — 근태관리 사이클에서 사용자가 지적한 "인간 실수" 관점과 같은 결 |
| **B. `createProgram`/`updateProgram`에서 `pricingType=PAID_SESSION`이면 `capacity>=1` 필수 검증 (채택)** | 원인 시점에 바로 명확한 에러 — 회차 생성까지 안 가봐도 앎 | `PAID_SESSION`으로 바꾸는 수정(`updateProgram`)에도 같은 검증이 필요해 조건 분기가 한 군데 더 생김 |
| C. `capacity` 없으면 프로젝트 전역 기본값(예: 10) 적용 | 입력 부담 최소 | 관리자가 실제 정원을 잊고 넘어갈 위험 — 정원은 임의로 추측할 성질의 값이 아님 |

**결정**: B. 판단 기준: C는 정원이라는, 추측하면 안 되는 값을 시스템이 대신 정하는 셈이라 배제.
**감수하는 것**: `updateProgram`에서 `pricingType`을 나중에 `PAID_SESSION`으로 바꾸는 경로도 같은 검증을 타야 해, 검증 로직이 생성·수정 두 곳에 필요하다(공통 헬퍼로 묶으면 완화 가능).

### 질문 2: 상태 전이 시 확정 예약 가시화

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(아무 정보 없음) | 없음 | 1-8문서 §6이 명시한 "안내" 요건 미충족 |
| **B. 상태 전이 응답에 그 프로그램의 미래(오늘 이후) 확정 예약 건수·목록을 포함 (채택)** | 알림 인프라 없이 바로 구현 가능, 응답 하나로 관리자가 즉시 인지 | 예약 도메인 데이터를 프로그램 도메인 응답에 섞어야 함(모듈 간 참조) |
| C. 실시간 알림(이메일/푸시)로 예약자에게 통보 | 가장 사용자 친화적 | 알림 채널이 이 프로젝트에 없음(1-8문서 §8이 이미 이 이유로 제외) |

**결정**: B. 판단 기준: C는 인프라 부재로 배제. A는 스펙이 명시한 요건을 방치하는 것이라 배제.
**감수하는 것**: 프로그램 컨트롤러가 예약 데이터를 조회해야 해 모듈 경계가 살짝 흐려진다 — `MockDataService`가 이미 전 도메인 데이터를 갖고 있어 지금은 비용이 낮지만, 실DB 전환 후 서비스 분리 시 다시 볼 지점.

### 질문 3: facilityId 지점 일치 검증

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 현행 유지(검증 없음) | 없음 | `instructorId`와 비일관 — 같은 성격의 버그를 한쪽만 막은 상태 |
| **B. `assertFacilityInBranch` 추가 — `assertInstructorInBranch`와 동일 패턴 (채택)** | 이미 검증된 패턴 재사용, 구현 위험 거의 없음 | 없음 |
| C. 시설을 지점 간 공유 자원으로 재정의 | — | `Facility.branchId`가 이미 FK로 지점 전용이라 스펙과 정면 충돌, 배제 |

**결정**: B.
**감수하는 것**: 없음 — 사실상 무비용 수정.

## 10. ADR

### ADR-PRG-01: PAID_SESSION 프로그램의 capacity 필수 검증을 생성/수정 시점으로
- **컨텍스트**: 현재는 회차 생성 시점에야 간접적으로 걸려 원인-증상이 멀다(§6)
- **검토한 대안**: A 현행 유지 / B 생성·수정 시 필수 검증 / C 기본값 적용
- **결정**: B. 정원은 추측하면 안 되는 값
- **결과**: 좋아진 것 — 즉시 명확한 에러 / 감수하는 것 — 검증 로직 두 곳 필요 / 숙제 — 없음

### ADR-PRG-02: 상태 전이 응답에 확정 예약 정보 포함
- **컨텍스트**: 1-8문서 §6의 "안내" 요건이 구현 안 됨(§6)
- **검토한 대안**: A 현행 유지 / B 응답에 포함 / C 실시간 알림
- **결정**: B. 알림 인프라 없이 즉시 구현 가능
- **결과**: 좋아진 것 — 관리자가 즉시 인지 / 감수하는 것 — 모듈 간 참조 증가 / 숙제 — 없음(구현만 남음)

### ADR-PRG-03: facilityId 지점 일치 검증 추가
- **컨텍스트**: instructorId만 검증되고 facilityId는 빠져 있던 비일관(§6)
- **검토한 대안**: A 현행 / B 검증 추가 / C 시설 공유자원화
- **결정**: B. 기존 패턴 재사용
- **결과**: 좋아진 것 — 관계 무결성 / 감수하는 것 — 없음 / 숙제 — 없음
- **구현됨(2026-09-25)**: `assertFacilityInBranch`를 `assertInstructorInBranch`와 동일한 형태로 추가하고, `createProgram`·`updateProgram`의 `facilityId` 처리에 그대로 연결했다(다른 지점 시설이거나 존재하지 않는 id면 `FACILITY_BRANCH_MISMATCH` 400). admin-web `ProgramsPage`는 이미 `branchId` 쿼리로 필터링된 시설만 드롭다운에 보여주고 있어 화면 변경은 필요 없었다 — 이번 수정은 API 직접 호출을 막는 방어 계층. 회귀 테스트: `apps/api/test/program-integrity.spec.ts`.

## 부록 A. 레퍼런스 스펙 (결정을 반영한 현재 상태)

> §1~12(분석·결정)의 **결과물**이다. 옛 [1-8_강사프로그램게시.md](../1.spec/20_이용자서비스/1-8_강사프로그램게시.md)에서 병합했다.

### A-1. 데이터 모델

**Instructor**: `id, branchId(FK), name, specialty, bio, photoUrl, phone, isActive`. (`commissionRate`는 강사 정산 범위 제외로 코드에서 제거됨 — CLAUDE.md 범위 제외 목록)

**Program**: `id, branchId(FK), facilityId(FK, nullable), instructorId(FK, nullable), name, category, ageGroup(ALL/CHILD/TEEN/ADULT/SENIOR), description, pricingType(FREE_ACCESS/PAID_SESSION/PT_PACKAGE), price, capacity(nullable), status(PREPARING/RUNNING/PAUSED/ENDED), startDate, endDate(nullable)`

**상태 전이표**: `PREPARING→{RUNNING,ENDED}`, `RUNNING→{PAUSED,ENDED}`, `PAUSED→{RUNNING,ENDED}`, `ENDED→{}`(종결)

**ProgramScheduleTemplate**(요일별 기본 시간표, 회차 대량 생성용, **미구현**): `id, programId, dayOfWeek, startTime, endTime`

인덱스: `Program(branchId, status)`, `Program(branchId, category, ageGroup, pricingType)`, `Instructor(branchId)`

### A-4. 권한 요약
- BRANCH_ADMIN: 본인 지점 강사·프로그램 CRUD
- 회원/전체: 조회만, 기본적으로 본인 소속 지점만 노출(2026-09-20 정책 확정)

### A-5. 구현 우선순위
**Phase 1(완료)**: 강사/프로그램 CRUD, 필터 목록, 상태 수동 전이, 지점 현황판, **회차 개별 등록(정정: 완료)**.
**Phase 2(미구현)**: 요일 템플릿 기반 회차 일괄 생성, 시설 시간대 충돌 검사, 휴강 처리 시 예약자 알림, 상태 자동 전이 배치.
**Phase 6(확장, 범위 제외)**: `commissionRate` 설정 UI·강사 정산 연동.
