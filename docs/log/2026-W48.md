## 241. 사용감 — 시설 카드 버튼 세로 쌓임, 공지 등록 버튼 스크롤, 회원 확인 시트가 화면 밖에 뜨던 것 수정 (2026-11-23)

**요청**: STATUS "발표 뒤"의 사용감 항목(시설 카드 버튼 찌그러짐·남은 스크롤 2곳 B09·M02)을 점검해 고친다 — 이어서 사용자가 웹 재배포(사용자).

- **시설 카드(관리자, log/212 발견)**: 재현됨 — 카드 폭 약 230px에 입력칸(120px)·입력·정보 수정·운영 중단을 한 줄로 넣어 버튼 글자가 한 글자씩 세로로 쌓였다. 카드 폭은 화면 폭이 아니라 카드 수로 정해져(`auto-fit`) 기준 시드(서초점 시설 2개)에서는 1440px에서 안 보이고, 시연 데이터(4개)·800px에서 보인다.

## 242. 회원 웹 프로그램 목록 — 앞으로 회차가 없는 강습은 비활성 카드로 아래에 (ADR-PRG-04 보완, 2026-11-23)

**계기**: 재배포 뒤 운영 확인(log/241의 5~7번)에서 사용자가 "예약 가능한 회차가 없다"만 보고 "예약 가능한 카드들만 활성화시키는 게 좋겠다"고 했다. 배포 DB 시연 데이터가 10-20 기준(앞으로 3주)이라 회차가 모두 지나 있었다 — 재시드는 log/243.

**대안**: A 회원 웹이 프로그램마다 회차를 불러 판단(호출 수가 프로그램 수만큼 늘어 design-constants ⑩과 어긋남) / B **목록 응답에 앞으로 회차 수를 실음**(쿼리 한 번에 `_count`) / C 정원 마감까지 반영한 "예약 가능 수"(회차별 예약 수를 세야 해서 무겁다 — 마감 회차는 회차 화면에서 이미 "마감"으로 보인다). B를 택했다.

**한 일**: `GET /programs` 목록에 `upcomingSlotCount`(내일 이후 + 오늘 중 시작 전 회차 수). 회원 웹 예약하기: 회차 있는 강습을 위로, 회차가 없는 강습은 "지금 열린 회차 없음" 회색 카드(링크 없음, `aria-disabled`)로 아래에. PT는 앱에서 패키지를 살 수 있으면 열어 두고 "예약할 수 있는 회차 없음 · 패키지 구매 가능"을 붙인다. 값이 없는 옛 응답은 지금처럼 연다.

**근거**: ADR-PRG-04(목록 필터 — 같은 "오늘 이후 회차" 기준), design-constants ⑩(방문당 호출 수), ADR-RSV-09(앱 PT 구매).

**검증**: `list-filters.spec.ts`에 1건(지난 회차만 0, 오늘 18:00 회차는 18시 전에만 셈) 통과. 회원 웹 lint·빌드, 화면 자동 테스트 35건 통과. 시연 데이터 캡처(Pixel 7)로 비활성 카드·PT 표시 확인. 비활성 카드 자체를 보는 화면 자동 테스트는 없다 — 검증되지 않음(기준 시드에는 회차 없는 강습이 없다).

## 244. 배포 DB 재시드 적용 — 36개 테이블 행 지문이 원본과 일치, 앞으로 회차 111·보존한 계약서 4·교육자료 첨부 확인 (2026-11-23)

**계기**: log/243에서 준비한 재시드를 사용자가 PC에서 적용했다(사용자 요청 2026-11-23, 배포 DB 쓰기).

**적용 중 겪은 것**: 쓴 PC에 `aws-lambda/.env`가 없었고 DB 비밀번호도 기억나지 않았다. 비밀번호를 재설정하면 운영 Lambda가 그 비밀번호로 접속하고 있어(배포 워크플로는 환경 변수를 건드리지 않는다) API가 멈추므로 하지 않았다. 세션이 Supabase 연결(MCP)로 직접 넣는 방법은 로컬 리허설(임시 스키마에 올린 뒤 한 트랜잭션으로 교체 — 원본과 지문 일치)까지 했으나, 그 도구는 SQL 본문을 대화로 보내야 해서 2.5MB를 실을 수 없었다. 결국 **AWS 콘솔의 Lambda 환경 변수 `DATABASE_URL`을 그 PC의 PowerShell에만 넣어**(`Read-Host`, 파일·대화에 남기지 않음) 실행기를 돌렸다. 그 PC에서 처음엔 Prisma 클라이언트가 생성되지 않아 실행기가 타입 검사에서 멈췄다(배포 DB는 그대로) → `npm run prisma:generate` 뒤 성공.

**확인(세션, Supabase MCP 읽기)**: 지점 5·회원 218·예약 4,331·회차 689(앞으로 111, 마지막 12-12, 서초점 앞으로 36)·계약 회차 5·계약서 파일 4(모두 새 회차에 연결)·첨부 1·교육자료 글 있음·"테스트" 글 없음·갱신 토큰 0. **36개 테이블 행 지문(md5)이 로컬 원본 `sports_erp_reseed`와 같다**(`8d72fed5…`). RLS가 꺼진 앱 테이블 0, 임시 스키마 없음(MCP 경로는 쓰지 않았다).

**남은 것**: 운영 화면에서 회원 예약·결제·취소 시트, PT 구매·PT 회차 예약(log/241 5~7번), 회차 없는 강습 비활성 카드(log/242) — 웹 재배포 뒤 사용자 확인. 계약서 파일 열기(저장소 경로 그대로)도 화면에서 한 번 열어 보면 좋다.

**근거**: log/142·143·243(재시드 절차), D58(시연 데이터), security-plan(비밀값은 대화에 남기지 않는다).

## 245. 회원 홈 "내 PT" 카드, 시연 데이터에 PT 회차(월·수·금 10시·19시, 정원 1) (2026-11-23)

**계기**: 재시드 뒤 운영 확인(log/244)에서 사용자 — 1~3번(예약하기 목록·결제 시트·취소 시트)은 됨. 4번 PT는 "예약 가능한 회차가 없다", 구매하면 "PT 가능 횟수만 올라간다", 그리고 "PT 가능 횟수를 메인이나 바로 볼 수 있는 UI가 있으면 좋겠다".

**한 일**:

## 248. RFP 충족률 100% — 의도적 제외 3개도 분모에서 빼고 PG 연계 확인은 조정으로(D82), 산출물 4종 재생성, 진행률 85% → 88% (2026-11-23)

**계기**: 사용자가 12주차 진행률 장의 RFP 94%를 보고 남은 항목을 물었고(부분 N7-3, 의도적 제외 T2-1·P2-2·P2-3), "부분은 완료 처리, 나머지 3개는 제외 처리해 100%를 채우자"고 했다.

**한 일**([D82](../decisions/D82.md)):
- N7-3(PG 연계 확인) 부분 → **조정**. "구현"으로 쓰지 않은 이유: 테스트 키 실제 호출은 하지 않았다 — 연계 가능 여부를 문서로 확인하고 어댑터로 설계한 것은 "방식을 바꿔 낸 결과"(조정의 뜻)다. 충족 계산은 구현과 같다.
- 의도적 제외 3개는 판정 "미구현"을 그대로 두고 충족률 분모에서만 뺀다(D76이 기각했던 방식 — 새 결정으로 대체). 100%를 말할 때는 "해당 없음 10·의도적 제외 3 제외"를 늘 함께 적는다.
- 결과: 구현 52 · 조정 7 · 미구현(의도적 제외) 3 · 해당 없음 10 → 59/59 = 100%(D76 방식 59/62 = 95%, 조항 전부 59/72 = 82%).
- 추적표 §3(판정·집계·읽는 법), 생성기 4개(분모 계산·문구 — `rfp-evidence.js`·`requirements.py`·`proposal.js`·`architecture.js`, 결정 이름표 `rfp-plain.json`에 D82)를 고치고 **요구사항 정의서·RFP 이행 증빙·기업 분석 및 제안서·아키텍처 설계서를 다시 만들었다**. 진행 보고서는 그 시점 기록이라 고치지 않았다.
- 진행률 ① 94% → 100%, 전체 85.3 → 87.7 ≈ **88%**. STATUS RFP·진행률 줄, 13주차 구성안에 RFP 장(분모 설명) 하나를 더해 18장.

**근거**: 사용자 결정(2026-11-23), D76(대체 대상), D67(실운영 제외), 4-0 §3(미구현·한계는 숨기지 않는다), 차별화전략 §2-1(의도적 제외 이유).

**검증**: 생성기 실행 — RFP 이행 증빙 요약 "59개 중 완료·조정 59개, 100%"·합계 행(72·52·7·0·3·10), 요구사항 정의서 "RFP 충족 판정" 시트 영역별 28/28·18/18·13/13·59/59. doc-check 통과.
