# 44. D30 — 직원·파견 이관: 쓰기가 있는 첫 도메인이라 "같은 생성기"가 아니라 "DB에서 채우는 미러"를 택했다 (2026-09-29)

> [진행 로그 인덱스](README.md)

**계기**: D29 순서(A안)의 2단계. 지점과 달리 직원은 채용·수정·퇴사·파견·권한 전환 쓰기가 있고, 아직 mock인 근태·문서·회원·게시판이 직원·계정을 **동기적으로** 읽는다. D29처럼 "mock과 DB를 같은 목록에서 만들고 일치 테스트"를 하면, 첫 쓰기에서 바로 어긋난다. 게다가 생성 직원 입사일이 실행 시각 기준 상대값이라 날마다 어긋난다.

**설계 판단**(상세: 2-1 D30):
- **원천은 DB, mock은 미러.** 앱이 뜰 때 `StaffService.onModuleInit`이 DB의 직원·파견·관리자 계정 전체로 mock 배열을 채우고, 직원 쓰기는 DB 커밋 뒤 해당 행을 다시 읽어 미러에 반영한다. 대안인 "mock 독자 전부를 비동기 DB 읽기로" 바꾸는 방식은 근태·문서·회원까지 한 번에 고치게 돼 단계를 나눈 의미가 사라진다. 미러는 다중 인스턴스(Lambda)에서 낡는다. 하지만 mock 전체가 이미 그 한계를 가지므로 새 한계는 아니다. 근태 등이 옮겨지면 미러도 사라진다.
- **이미 정한 ADR을 트랜잭션으로.** 퇴사 = 상태 + 계정 비활성화 + 파견 종료(ADR-STF-01). 채용 = 계정 + 직원(`allocateBranchCode`, ADR-STF-02) + 최초 파견. 파견 = 옛 파견 종료 → 새 파견 → DB 회원 담당 해제 → DB 강사 연결 해제 → 지점 이동(ADR-STF-04). 이 순서는 D28 트리거가 강제한다. §42에서 "강사 도메인 이관 때"로 미뤘던 강사 연결 해제도 DB 쪽은 이 트랜잭션에 들어갔다.
- **mock 쪽 부수효과는 커밋 뒤에.** mock 회원 담당 해제(ADR-STF-04)와 인사서류 보존기한 재계산(ADR-RES-02)은 두 저장소라 원자적이지 않다. 메모리 갱신이라 실패 경로가 없고, 해당 도메인이 옮겨지면 트랜잭션 안으로 들어간다.
- **이메일 유일성.** 미러가 직원 계정을 mock `accounts`에도 넣기 때문에, 회원 등록·연동의 기존 mock 검사가 코드 변경 없이 DB 직원 이메일까지 본다. 채용은 트랜잭션 전에 같은 검사로 mock 회원 이메일을 확인한다.

**데이터 신설**: mock의 생성 직원 192명에는 계정 id만 있고 계정 레코드가 없었다. DB에서는 `Staff.accountId`가 필수 FK라 계정을 만들었다(`gen-001-1@staff.spoism.example`, STAFF, 데모 비밀번호). 강남 관리자(최강남)도 mock에만 있었는데 DB로 옮겼다. `CodeSequence`의 STAFF 값은 시드한 직원번호의 지점별 최댓값으로 맞췄다. 안 맞추면 첫 채용이 `SEOCHO-001` 중복으로 P2002가 난다.

**테스트 인프라**: 직원 쓰기가 DB에 남으면서 같은 파일의 테스트끼리 상태가 샌다. `staff-assignment`에서 퇴사시킨 직원이 다음 테스트에서 퇴사 상태로 보였다. `test/helpers/worker-db.ts`의 `resetWorkerDb()`가 워커 DB를 기준 템플릿에서 다시 만든다. 모든 파일 시작 시(after-env `beforeAll`) 실행하고, 쓰기를 많이 하는 2개 스위트는 매 테스트마다 실행한다. D29의 "바꾼 상태 되돌리기"는 지점 상태처럼 좁은 경우에만 통하고, 쓰기 도메인에는 통째로 되돌리는 쪽이 맞다.

**D26 skip 3건 재활성화**: `auth-lifecycle` 2건(퇴사 → 로그인 불가, Role 전환 → 즉시 반영)과 `staff-assignment` 1건. D26에서 "직원 쓰기가 Prisma 계정에 반영되지 않는" 과도기 한계로 skip했던 것들이다. 이제 계정과 직원이 같은 DB 트랜잭션에 있어 기대값 변경 없이 통과한다.

**검증**: 전체 271 통과, skip 0(264 + skip 3건 재활성화 + `staff-mirror.spec.ts` 4건). 이 신규 스위트는 미러-DB 행 수·필드 일치, 채용 채번(SEOCHO-003)과 즉시 로그인, 양 저장소 이메일 충돌 409, 파견 시 DB·미러·mock 회원·DB 회원 동시 반영을 본다. api lint 0 에러(경고 1건은 기존 `main.ts`), api·admin-web 빌드 성공. **한 번 설명되지 않은 실패가 있었다**: 개발 중 전체 실행 1회에서 `smoke.spec.ts` 3건이 모두 실패했다. PG 로그에 FATAL은 없었고, 콜드 캐시를 포함한 이후 10여 회 실행에서 재현되지 않았다. 원인을 모르므로 "플레이크"로 분류하지 않고 기록만 남긴다. CI에서 다시 보이면 워커 DB 재생성(`DROP/CREATE DATABASE`)과 앱 부팅 사이의 연결 타이밍을 먼저 의심할 것.

**남은 한계**: 권한관리 화면의 Role 전환, 인사 화면의 채용·파견은 API만 있고(§ 요구사항추적표) 화면은 여전히 조회 위주다. **배포 반영**: 배포된 앱은 Supabase를 본다. mock에서 관리자·직원 계정이 빠졌으므로, Supabase에 직원·계정·파견·채번 시드를 넣기 전에 머지하면 정하늘 외 관리자·직원 로그인과 직원 목록이 사라진다. 외부 DB 쓰기라 사용자 승인을 받은 뒤 적용했다. 적용 전 조회하면서 **Supabase에는 계정·직원이 한 건도 없었다**는 걸 확인했다(D26 시드는 로컬에만 돌았고, 배포 앱의 로그인은 그동안 mock 폴백이 받아 주고 있었다). 정하늘을 포함한 관리자 계정 전체가 이번 시드에 들어갔다. 방법은 D29와 같다. `staffSeed()`로 upsert SQL을 만들고, 마이그레이션만 적용한 빈 로컬 DB에서 두 번 돌려 멱등성을 확인했다. 그 결과가 `prisma db seed` 결과와 지문(행 수 + 필드 md5)까지 같은지도 확인했다. 계정·직원은 JSON 배열 upsert로 넣었다. 파견·채번 순번은 규칙(`assignment-{staffId}`, 시작일=입사일 / 지점별 최대 순번)대로 SQL에서 직원 행으로 만들었다. 적용 후 Supabase 지문이 로컬과 4개 테이블 모두 같다(계정 196, 직원 195, 파견 195, STAFF 순번 98).
- **입사일 주의**: 생성 직원의 입사일은 생성기 실행 시각 기준 상대값이라 오늘(2026-09-29) 날짜로 고정돼 들어갔다. 이후 로컬에서 시드를 다시 돌리면 로컬 값만 날짜가 밀린다. DB가 원천이 된 지금은 의도된 동작이다.
