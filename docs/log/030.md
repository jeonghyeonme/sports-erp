# 30. Render에 admin-web·api를 배포했다 (2026-09-27)

> [진행 로그 인덱스](README.md)

**계기**: §29(Supabase 스키마 배포)에 이어 "인프라에 올리는 것" 두 번째 단계. Vercel도 커넥터로 연결돼 있었지만 툴 목록이 조회/디버깅용(`list_projects`, `get_deployment` 등)뿐이라 새 배포를 만들 수 없었다 — Render는 `create_web_service`·`create_static_site`가 있어 실제로 생성까지 가능해서 admin-web·api 둘 다 Render 하나로 몰았다.

**한 일**: Render 워크스페이스(`Jeonghyeonme's workspace`)에 두 서비스를 만들었다 — `sports-erp-api`(Web Service, Node, Singapore, free)와 `sports-erp-web`(Static Site). 모노레포라 MCP `create_*` 툴에 root-directory 옵션이 없어서, buildCommand 자체를 `npm install && npm run build --workspace=apps/api`처럼 워크스페이스 플래그로 해결했다. admin-web이 API URL을 빌드 타임에 굳히는 구조(Vite)라, **api를 먼저 만들어 URL(`https://sports-erp-api.onrender.com`)을 확정한 뒤 그 값을 admin-web의 `VITE_API_BASE_URL`에 넣어 만드는 순서**로 진행했다.

**버그 발견·수정**: api 첫 빌드가 16초 만에 `sh: 1: nest: not found`로 실패했다. 원인은 내가 넣은 `NODE_ENV=production` 환경변수 — npm이 이걸 보고 `npm install`을 devDependencies 제외 모드로 돌려서 `@nestjs/cli`(devDependency, `nest` 바이너리 제공)가 설치 안 됐다. `NPM_CONFIG_PRODUCTION=false`를 추가해 npm이 NODE_ENV와 무관하게 devDependencies를 설치하도록 강제해 해결했다. admin-web(Static Site)은 애초에 NODE_ENV를 안 건드려서 같은 문제 없이 첫 시도에 성공했다.

**JWT 시크릿**: `.env.example`의 `change-me` 계열 기본값 대신 `crypto.randomBytes(32).toString('hex')`로 실제 프로덕션용 시크릿을 생성해 `JWT_ACCESS_SECRET`·`JWT_REFRESH_SECRET`으로 넣었다(레포에는 커밋 안 함 — Render 환경변수로만 존재).

**검증**: Render `get_deploy`로 두 서비스 다 `status: live` 확인. 이 컨테이너 자체의 네트워크 정책이 `onrender.com`을 막고 있어서(egress policy — curl이 `CONNECT tunnel failed, response 403`) 내가 직접 curl로 확인할 수는 없었지만, Render `list_logs`(type=app)로 Nest 부팅 로그(`AppModule dependencies initialized`, `/api/v1/health` 라우트 매핑까지)를 확인해 실제 기동을 검증했다.

**Cloudflare는 이번엔 보류**: DDoS/WAF는 사용자 소유 도메인을 Cloudflare가 DNS 서빙하면서 붙는 기능이라, 지금처럼 Render의 `*.onrender.com` 무료 서브도메인만 있는 상태에선 성립하지 않는다(Render가 소유한 존이라 Cloudflare 앞에 못 세움). 연결해둔 "Cloudflare Developer Platform" 커넥터도 Workers/KV/D1/R2용이라 DNS/Zone/방화벽 툴 자체가 없다. 사용자가 "도메인 확보 전까지 보류"를 선택 — 부하테스트(k6)는 도메인과 무관하니 다음 단계로 그대로 진행.

**커밋**: 코드 변경 없음(Render 서비스 생성은 원격 인프라 작업). 이 로그 절이 유일한 기록.
