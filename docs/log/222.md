# 222. 리팩토링 ① — api 응답 타입의 인메모리 시절 이름(`Mock*`) 정리, 죽은 코드 삭제 (2026-11-12)

> [진행 로그 인덱스](README.md)

**계기**: 사용자 요청 "리팩토링해서 코드 좀 가볍게". 조사해 보니 죽은 코드는 적고(자체 스크립트로 "다른 파일에서 안 쓰는 export" 61개 — 대부분 반환 타입이라 export가 필요하거나 무해), 가장 큰 짐은 **읽는 사람을 헷갈리게 하는 이름**이었다: DB로 다 옮긴 지 오래인데(D36) 응답 형식 타입이 `src/fixtures/mock-data.types.ts`에 `MockProgram`·`toMockProgram` 같은 이름으로 214곳 남아, "아직 mock을 쓰나?"를 매번 다시 확인하게 했다.

**한 일** (동작 변경 없음):
- `src/fixtures/mock-data.types.ts` → `src/common/api-response.types.ts`. 시드 원천이 아니라 응답 계약이라 `common/`으로.
- 이름: `Mock<X>` → `<X>Response`, `toMock<X>` → `to<X>Response`, `MOCK_DEMO_PASSWORD` → `DEMO_PASSWORD`. 겹치는 기존 이름이 없는지 먼저 확인하고 스크립트로 일괄 변경(35개 파일).
- 삭제: 어디서도 안 쓰는 `MockRefreshToken`(리프레시 토큰은 Prisma 모델로 다룬다), `CONTRACT_FILE_LABEL`(화면이 자기 표를 쓴다).
- 낡은 주석: "MockDataService가 인메모리 상태를 가지므로…"(테스트 3곳)·"mock-data.service.ts"(테스트 도우미) — 지금 이유로 고침.

**안 한 것**: "파일 밖에서 안 쓰는 export" 떼기 — api는 `declaration: true`라 public 메서드 반환 타입의 export를 떼면 빌드가 깨지고, 줄 수도 줄지 않는다. D36·D16 결정 문서의 옛 이름은 결정 당시 기록이라 그대로 둔다.

**근거**: D36(실DB 전환 끝 — 그때 "폴더 이름 변경은 파일이 많이 흔들려 범위에서 뺀다"고 미뤄 둔 정리).

**검증**: api lint·빌드 통과, jest 60개 스위트 639건 통과(로컬 실DB).
