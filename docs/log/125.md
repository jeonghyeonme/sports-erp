# 125. 시연 데이터로 화면 점검 — 역할별 핵심 경로 15화면, 발견 목록 (2026-10-19)

> [진행 로그 인덱스](README.md)

**계기**: STATUS 다음 할 일 3(a). 관리자 웹·회원 웹을 고밀도 시연 데이터(D58)로 열어 본 적이 없었다("검증되지 않음").

**사용자 결정(D53 방식)**: 상위 목표 = 노하우 습득(D53), 클라이언트 = 현장 사용자·사용성과 속도(D58).
- **답안지**: 출시 전 QA는 실제와 비슷한 양의 데이터로 역할별 핵심 경로를 걷는다. 실제 기기 폭, 많은 데이터에서 깨지는 것(긴 목록·빈 상태·표), 느린 화면을 본다. **핵심 변수**: 현장 사용자가 매일 여는 화면이 데이터가 많아졌을 때 읽기 어렵거나 느려지는가.
- 범위: 역할별 핵심 경로(추천안). 점검: 화면 밀도·깨짐 + 속도 수치(추천안). 처리: 이번에는 목록만 만들고 보고(추천안) — 고칠 것은 사용자가 고른다.
- **사용자 설명**: 없음 — 추천안 선택.

**방법**: 기준 DB와 분리한 별도 DB `sports_erp_demo`에 `seed:demo`(기준일 2026-10-19)를 얹었다. 로컬에서 api(`dist/main.js`)와 admin-web·member-web 개발 서버를 띄웠다. Playwright(Chromium, `Asia/Seoul`·`ko-KR`)로 화면을 클릭해 이동했다. 화면마다 측정한 것: api 요청이 모두 끝나고 0.4초 조용해질 때까지의 시간, api 호출 수, 가로 넘침, 4xx/5xx·콘솔 오류, 전체 페이지 스크린샷. 스크립트와 스크린샷은 세션 임시 폴더에만 있다(커밋하지 않음).

## 속도 (로컬 측정 — 운영 수치 아님)

| 화면 | 시간 | api 호출 |
|---|---|---|
| 지점 관리자: 대시보드(로그인 포함)·회원 목록·회원 상세 | 248·83·86ms | 2·1·4 |
| 지점 관리자: 예약 관리·근태관리 | 162·97ms | **12**·7 |
| 지점 관리자: 직원 목록·직원 상세 | 60·106ms | 2·8 |
| 본사: 대시보드(로그인 포함)·지점 상세·변경 이력 | 234·137·63ms | 2·7·2 |
| 회원(360px): 홈(로그인 포함)·예약하기·회차·내 예약·내 정보 | 256·64·60·77·64ms | 5·2·2·2·2 |

모든 화면이 로컬에서 0.3초 안에 떴다. 가로 넘침은 0건, api 4xx/5xx도 0건이다. 예약 관리의 12회는 주간 시간표가 프로그램마다 회차를 부르는 구조 때문이다(ADR-RSV-06이 감수한 것). 운영(W 약 40ms, D50)에서는 왕복이 붙어 이 화면이 가장 무겁다.
