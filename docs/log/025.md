# 25. 회원관리 D3(ADR-MEM-03, 회원 상세 요약+탭별 지연 로드)를 구현했다 (2026-09-26)

> [진행 로그 인덱스](README.md)

**계기**: §11(2026-09-22, 상 우선순위 4개 도메인 문서화) 때부터 "D3는 RFP 핵심 요구(F05a)의 미완 부분이라 가장 시급"이라고 남겨뒀던 것을, 사용자가 "회원관리 D3 진행해주고 이후 따라오는 작업들 전부 진행해줘"로 지정해 처리했다. 이후 상황 대처 능력을 시험할 대화를 예고했기 때문에, 평소보다 더 꼼꼼하게(브라우저 실동작 확인까지) 마무리했다.

**한 일**: `MockDataService`에 `CourseEnrollment`/`PTSession`/`PTSessionLog` 인메모리 모델을 신설했다(A-1 데이터모델에 이미 스케치돼 있던 형태 그대로). `GET /members/:id`가 `memberSummary()`(활성 수강 건수·PT 잔여세션 합계·최근 결제일)를 함께 반환하도록 바꾸고, `enrollments`/`pt-sessions`/`pt-sessions/:id/use` 3개 하위 리소스 엔드포인트를 추가했다. "예약·결제 내역" 탭은 새 엔드포인트를 만드는 대신 기존 `GET /reservations`에 `?memberId=` 필터만 얹어 재사용했다 — `ReservationRow`가 이미 `payment`를 중첩해서 반환하고 있어 변경 범위를 최소로 유지할 수 있었다.

**도메인 불변식 적용**: `createEnrollment`/`createPTSession`(신규 등록)은 계약종료 지점 409(`BRANCH_TERMINATED`)로 막았지만, `usePTSession`(이미 구매한 세션 차감)은 막지 않았다 — ADR-FAC-03에서 확립한 "신규 활동 vs 정정" 구분을 그대로 재적용한 것이다(재고 소진 처리는 새 계약을 만드는 게 아니라 기존 계약 이행). 지점 격리는 `assertReadable`/`assertWritable`(회원 소속 지점)과 `assertProgramInBranch`(등록하려는 프로그램이 회원과 같은 지점인지, 신설)로 이중 검사했다.

**검증**: `apps/api/test/member-detail-summary.spec.ts`(신규 14건) — 요약 필드, 수강내역 GET/POST+지점불일치 400+계약종료 409+타지점 403, PT세션 GET/POST/사용+소진 409+계약종료 시 신규구매만 차단(기존 세션 사용은 허용)+타지점 403, 예약·결제 내역 스코프(SUPER_ADMIN/본인지점 OK, 타지점 403, MEMBER는 파라미터와 무관하게 항상 자기 것만)까지 전부 커버. `npm run test`(232 passed), `eslint`·`nest build`·admin-web `tsc -b && vite build` 전부 클린. 추가로 admin-web dev 서버를 직접 띄우고 Playwright로 서초점 관리자 로그인 → 이수진(member-sujin) 상세 진입 → 3개 탭(수강내역/PT잔여세션/예약결제) 클릭 → 스크린샷까지 확인했다 — 요약 카드(수강중 1건/PT 잔여세션 7회), 수강내역 표, PT 세션 카드(사용 이력 3건+세션 사용 폼), 예약·결제 빈 상태 문구가 실제로 렌더링되는 것을 눈으로 봤다(SPA라 페이지 리로드 시 인증이 풀린다는 것도 확인 — 이 과정에서 알게 된 사실이지 이번에 고칠 버그는 아님).
