# 199. 작업 단계 줄이기 ② — 기본값 채우기(PT 구매일·수강 등록일 = 오늘, 누락일 출근 = 지점 기준 출근 시각), 회원 찾기 ① 대안 (2026-11-08)

> [진행 로그 인덱스](README.md)

**계기**: log/198 기준선에서 사용자가 후보 ②(기본값 없는 칸)부터, ①(회원 찾기 3단계)은 대안 제안으로 결정.

**한 일 (②)**
- **PT 패키지 구매일·수강 등록일 = 오늘**(관리자 웹 회원 상세 `MemberDetailPage`): 처음 열 때와 등록 뒤 다시 비울 때 모두 `kstToday()`. 만료일은 그대로 빈칸(선택 칸).
- **누락일 등록 출근 시각 = 파견 지점의 기준 출근 시각**(직원 상세 `StaffDetailPage` → `CorrectAttendanceModal`): `Branch.standardCheckInTime`(근태관리 A-6 지각 판정 기준 — 시드 서초 09:00·강남 09:30)을 쓴다. 이 값을 화면이 받도록 `GET /branches` 응답(`BranchService.toContractView`)에 `standardCheckInTime`을 더했다 — 스키마 변경 없음, 응답 필드 추가만. 기존 기록 정정은 지금처럼 그 기록의 값, 퇴근은 기준이 없어 빈칸, 지점 값이 없으면 빈칸.

**검토한 대안(누락일 출근 시각)**: (a) 09:00 고정 — 강남(09:30)처럼 기준이 다른 지점에서 틀린 값이 들어간다. (b) 직원의 지난 출근 시각 평균 — 새 집계가 필요하고 근거가 약하다. (c) **지점 기준 출근 시각(채택)** — 이미 지각 판정에 쓰는 값이라 새 규칙이 없다. **감수하는 것**: 확인 없이 저장하면 실제와 다른 시각이 남을 수 있다 — 칸이 보이고 사유가 필수이며 변경 이력(D52)에 남아 되짚을 수 있어 받아들였다.

**전후(측정 도구로 다시 잼, log/198 방식)**: B03 PT 패키지 등록 10 → **9**, B10 누락일 등록 8 → **7**(기준 시드·시연 데이터 같음). 나머지 18건은 그대로. 측정 스크립트는 기본값이 실제로 채워졌는지(`toHaveValue`) 확인한 뒤 그 칸을 건너뛴다.

## ① 회원 찾기 — 대안 (결정 전)

지금: 회원 메뉴 → 검색어 → 검색 버튼 → 행 = 상세까지 4단계(B02), PT 작업은 여기에 PT 탭 1단계(B03·B04). 쓸 수 있는 것: `GET /members?q=&limit=`(이름·회원번호·전화 부분 일치, 서버 쪽 나누기, 지점 격리 자동 — D43·D46), 회원 목록은 본사·지점 관리자만(직원은 회원 메뉴 없음).

| 안 | 내용 | 예상(B02 / B03 / B04) | 비용·위험 |
|---|---|---|---|
| A. 입력 즉시 검색 | 회원 목록 검색창에 치면 잠시 뒤 자동 검색(검색 버튼 없앰) | 3 / 8 / 5 | 가장 작다. 글자마다 호출이 늘 수 있어 지연(약 0.3초)·2자 이상 조건 필요 — Workers 하루 한도(D40)에 영향은 작다 |
| B. 상단 바 회원 빠른 찾기 | 모든 화면 상단에 검색창, 결과 5건 목록에서 바로 상세로 | 2 / 7 / 4 | 상단 바 부품 하나 + 같은 API(limit 5). 회원 조회 권한이 없으면 숨김(D60). 화면 어디서든 쓰여 회원 관련 작업 전체가 줄어든다 |
| C. 상세 탭을 주소에·PT 먼저 | 회원 상세 탭을 `?tab=pt`처럼 주소에 두고, 진행 중 PT가 있으면 PT 탭을 먼저 연다 | 4 / 9 / 5 | 작다. 다른 탭을 보려던 사람에겐 한 번 더 누르게 할 수 있다 |
| D. 빠른 찾기 결과에서 바로 세션 사용 | B의 결과 줄에 PT 잔여와 "세션 사용" 버튼 | 2 / 7 / **2** | 목록 응답에 PT 잔여를 붙이는 API 변경(조회 비용 증가), 실수로 누르기 쉬워 확인 단계가 필요할 수 있다 |

**제안**: B + C. B는 회원을 다루는 모든 작업의 앞머리를 4 → 2로 줄이고 API를 새로 만들지 않는다. C는 PT를 매 수업 차감하는 B04에 1단계를 더 줄인다(합쳐서 B04 6 → 3). D는 효과가 가장 크지만 API 변경과 잘못 누르기 위험이 있어 B+C 뒤 실제로 부족할 때 본다. 고르면 횡단 결정(새 D번호)으로 남기고 구현 뒤 측정 도구로 전후를 잰다.

**근거**: log/198(기준선), 근태관리 A-6(지각 판정 기준), ADR-ATT-04(관리자 정정·누락일 등록), D52(변경 이력), D43·D46·D60(① 대안의 기존 장치).

**검증**: api lint(경고 1건은 기존 `main.ts` — 이번 변경 아님)·빌드, `branch-parity.spec.ts`(응답에 `standardCheckInTime: '09:00'` 기대 추가) 통과, admin-web lint·빌드 통과, 화면 자동 테스트 16건 통과, 측정 20건 기준 시드·시연 데이터 통과. 전체 jest는 커밋 전 hook이 돌린다. 강남(09:30) 직원의 누락일 기본값은 화면에서 확인하지 않았다 — 검증되지 않음(값은 같은 응답 필드에서 온다).
