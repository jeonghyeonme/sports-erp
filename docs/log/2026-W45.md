## 195. 계약 파일 보존·실물 이관·정리 — D69 2차 첫 단계 (D71, 2026-11-02) (2026-11-02)

**한 일**

- api: 보존 계산 `contract-retention.ts`(회차가 끝난 날 + 3년, 6개월 알림 — 회차 표·보존 현황·처리 대기함이 같은 함수), `POST /branches/:branchId/contract/files/:fileId/archive`(본사, `@ScopedResource('contractFile')`, 이미 표시하면 409), `GET /branches/contract-files/retention`(이관 필요·정리 대상), `POST /branches/contract-files/purge`(본사, 고른 파일이 모두 정리 가능해야 함, 행 락 → 저장소 삭제 → 기록, 실패하면 전부 되돌림), 정리된 파일 열기 410, 회차 목록에 보존 끝·이관·정리 상태, 처리 대기함(본사) 2항목. `StorageService.remove`(실패를 던지는 삭제) 추가.

**근거**: D71(D69 결정 7 대체), D69, D61(처리 대기함), D57(저장소), D46(지점 범위), D44(변경 이력).

## 197. 사용감 확보 전수조사 — 목록·검색·정렬·시각화·디자인·RFP 추적·미뤄 둔 일을 한 목록으로, 추적표 D68~D71 재대조 (2026-11-08)

### 조사 결과 목록

**A. 사용감(D67 ①)**
- A-1 목록 쪽 나누기: 서버 쪽 나누기(D43)는 회원·예약·결제·자산·지점 상세·회원 상세·업무지원·게시판·변경 이력. 전부 한 번에 불러오는 목록은 직원·프로그램·강사·시설·문서·계약 보존 — 쌓이는 문서가 첫 후보(D69 2차 파일 업로드와 겹친다).
- A-2 검색: 글자 검색은 회원(이름·번호·전화)·직원·권한, 지점명 검색만 대시보드·시설·강사·프로그램. 예약·자산·문서·업무지원·변경 이력은 선택 필터만.
- A-3 정렬: 머리글 정렬은 0곳(`aria-sort` 없음). 디자인시스템 §3 "정렬 가능한 열은 머리글에 표시"가 적용된 화면이 없다. 화면마다 정렬이 코드에 고정.
- A-4 CSV: 회원·예약·근태·본사 근태 4곳. 직원·자산·문서·프로그램은 없음 — 필요 여부 결정 필요.
- A-5 시각화: 차트 라이브러리 없음, 대시보드 숫자는 현재값만(log/129에서 가짜 추세를 뺀 뒤 기간 집계 API가 없음). 기간 데이터는 지점 상세 월 실적 표뿐. 차별화전략 §2 영업 리포트(`performance-report`) 미구현 — 겹친다.
- A-6 작업 단계: 역할별 주요 작업의 클릭·화면 수 기준선이 없다 — 측정이 먼저.

## 205. 서버 목록 정렬 — 회원·자산·업무지원 머리글 정렬을 서버가(sort·dir) (D74 2차) (2026-11-08)

**계기**: 목록 일관화 2차(D74) 중 사용자가 "서버 목록 정렬"을 골랐다. D74 1차는 화면 전체 로드 목록만 화면에서 정렬했고, 서버가 쪽을 나누는 목록은 화면에서 정렬하면 지금 쪽 20건만 정렬돼 오해를 낳는다(D74 대안 b) — 서버에 정렬을 더했다. 새 브랜치 `claude/list-sort`.

**범위 판단**: 서버 쪽 나누기 목록 7개 중 **회원·자산·업무지원**만. 결제·예약·게시판·변경 이력은 시간순이 그 목록의 뜻이라(최근 것부터, 예약은 현장 순서인 회차 시각순 — ADR-RSV-08) 넣지 않았다.

**한 일**
- **API**: `sort=열&dir=asc|desc`(`common/http/pagination.ts` `parseSort`). 열은 서비스마다 허용 목록(`MEMBER_SORT_KEYS`·`ASSET_SORT_KEYS`·`SUPPORT_SORT_KEYS` — 화면 표의 열과 같다)이고, 목록 밖 값·이상한 방향은 무시해 기본 순서로(400을 내지 않는다 — 모르는 필터 값과 같은 태도). 정렬 뒤 같은 값은 `id`로 이어 정해 쪽 경계가 흔들리지 않는다. 지점·요청자·담당 직원은 관계의 이름으로, 상태·분류는 enum 선언 순서로, 위치(빈 값 가능)는 빈 값을 뒤로.
  - 회원: 지점·회원번호(기본)·이름·담당 직원·상태·가입일 — 연락처는 가린 값이라 넣지 않았다.
  - 자산: 지점·자산코드(기본)·품명·분류·구분·취득가액·수량·위치·상태.
  - 업무지원: 요청일(기본 최근부터)·지점·분류·제목·요청자·상태.
- **화면**: 세 표의 머리글을 `SortTh`로(D74 1차와 같은 모양·`aria-sort`), 정렬 상태를 서버 인자로(`setSortParams`), 정렬이 바뀌면 1쪽부터. 회원·자산 CSV도 같은 순서로 받는다. 정렬 열 이름은 api와 화면에 따로 적혀 있다(화면 쪽 타입 주석에 api 상수 이름을 남김).
- **테스트**: api `list-sort.spec.ts`(고밀도 템플릿, 4건) — 이름순을 쪽 넘겨 이어 붙이면 DB의 이름 → id 순서와 같다(빠짐·겹침 없음)·역순, 모르는 열·방향은 기본 순서와 같다, 지점 정렬도 자기 지점만(격리), 취득가액 내림차순, 요청일 오름차순 = 기본의 반대. 화면 자동 테스트 1건(22건) — 회원 이름 머리글 → 서버에 `sort=name&dir=asc`·`desc`.

**근거**: D74(2차 — 사용자 선택, 대안 b를 피한 이유), D43(서버 쪽 나누기), D46(격리), ADR-MEM-04(가린 연락처), ADR-RSV-08(예약 순서).

**검증**: api `list-sort` 4건 통과, api 타입체크·lint(경고 1건은 기존 `main.ts`), admin-web lint·타입체크·빌드, 화면 자동 테스트 22건 통과, 측정 19건 통과·1건 건너뜀(B05, 23시 이후 — log/204). 전체 jest는 커밋 전 hook. 자산·업무지원 화면의 머리글 정렬은 화면 테스트가 없다 — 검증되지 않음(API는 테스트). 한글 이름 순서는 DB 정렬 규칙(collation)을 따른다 — 운영 DB(Supabase)의 정렬 결과는 확인하지 않았다(검증되지 않음).

**커밋**: `apps/api/src/common/http/pagination.ts`, `apps/api/src/modules/{members,assets,support-requests}/*`, `apps/api/test/list-sort.spec.ts`(새), `apps/admin-web/src/lib/table-sort.ts`, `apps/admin-web/src/pages/{Members,Assets,SupportRequests}Page.tsx`, `e2e/tests/admin-branch.spec.ts`, `docs/decisions/README.md`(D74 상태), `docs/design/디자인시스템.md`, `docs/STATUS.md`, `docs/log/205.md`, `docs/log/README.md`, `CLAUDE.md`·`apps/admin-web/CLAUDE.md`(화면 테스트 건수).
