# 17. 혼잡도관리 3개 ADR(FAC-01~03)을 전부 구현했다 (2026-09-25)

> [진행 로그 인덱스](README.md)

**계기**: 사용자가 "ADR 한 개씩 진행하고 끝나면 검토·수정·보고, 다음 ADR로" 순서로 §15에서 발견해둔 7개 ADR(PRG 3개, FAC 3개, BRD-02)을 전부 쳐내자고 지정. 각 도메인 문서의 "다음 행동 제안" 우선순위를 따라 FAC-03(CLAUDE.md 핵심 불변식과 직결) → FAC-01 → FAC-02 순서로 진행했다.

**FAC-03(계약종료 차단)**: `createFacility`·`setManualCongestion`에 `createMember`/`createPost`와 동일한 인라인 `TERMINATED` 체크를 추가했다(공통 가드 중앙화는 실DB 전환 이후로 미룬다는 기존 CLAUDE.md 결정을 그대로 따름 — 새 추상화를 만들지 않았다). `updateFacility`(기존 시설 정정)는 ADR 결정대로 제외.

**FAC-01(lastUpdatedAt)**: `MockFacility.lastUpdatedAt`을 등록·수동보정 시점에만 갱신하고, `updateFacility`의 capacity 변경은 갱신 대상에서 뺐다 — ADR 원문 "수동 보정 시 갱신"을 문자 그대로 지킨 것이다(capacity가 바뀌어도 `currentCount` 실측값 자체는 새로 들어온 게 아니므로). 값을 만들기만 하고 화면에서 못 보면 RFP F08b(30분 이내 반영) 요건을 여전히 검증할 수 없어(§16 ADR-BRD-01의 "체크박스 없으면 flag가 무용지물" 교훈과 같은 이유), admin-web `FacilitiesPage`에 "N분/시간/일 전 갱신" 표시를 같이 넣었다.

**FAC-02(isActive)**: 별도 DELETE 엔드포인트(Instructor가 쓰는 패턴) 대신, ADR 문구 "비활성화 PATCH"를 그대로 따라 기존 `PATCH /facilities/:id`가 `isActive` 토글까지 겸하게 했다 — 비활성화·재활성화를 API 하나로 처리한다. `GET /facilities`는 `isActive=true`만 기본 노출. **구현하면서 새로 발견한 감수 사항**: admin-web에 "비활성 시설 보기" 화면이 없어서, 일단 비활성화한 시설을 다시 활성화하려면 API를 직접 호출해야 한다 — ADR 문구 자체에 없던 범위라 이번엔 화면을 만들지 않았고, 그 사실을 비활성화 버튼의 확인 대화상자에 명시해 사용자가 알고 누르게 했다(무자각 데이터 유실 방지 차원).

**검증**: `apps/api/test/facility-lifecycle.spec.ts`(FAC-01 3건 + FAC-02 3건 신규) + `contract-termination.spec.ts`(FAC-03 7건 추가, §16 커밋에 포함). `npm run test`(13 suites, **179 passed**), `eslint`·`nest build`·admin-web `tsc -b && vite build` 전부 클린. 매 ADR마다 구현 직후 diff를 다시 읽으며 자체 리뷰했다 — 이번 3개에서는 추가로 고칠 문제를 찾지 못했다(FAC-02의 "재활성화 화면 없음"은 버그가 아니라 의도적으로 남긴 범위 밖 항목이라 위에 명시).
