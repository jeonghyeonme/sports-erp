# 173. 혼잡도에 진행 중 회차의 예약 인원을 더한다 — 키오스크 입장 방식은 검토 후 보류 (2026-10-22)

> [진행 로그 인덱스](README.md)

**계기**: 사용자가 "혼잡도가 관리자 수동 입력뿐이라 회원 앱 예약과 연동되는 느낌이 없다"고 했다. 예약 인원·비예약 인원·비회원을 어떻게 셀지 대화로 좁혀 갔다 — 시중 사례 조사(완벽한 수단 없음), 화면 문구 확정(약 N명·구성·기준 시각), 이용자 비율(예약 ≈10%, 예약 없는 회원 ≈85%, 비회원 ≈5% — 가정), 키오스크 입장 + 체류 시간 만료 설계(v2)까지 갔다가, RFP가 수단을 요구하지 않고 비용(기기 인증·스키마·Workers 한도)이 커 사용자가 "키오스크는 너무 갔다"며 예약 연동만 골랐다. 결정은 혼잡도관리 ADR-FAC-05(대안 C로 보류 설계를 함께 남김).

**한 일**:
- api `facility.service.ts` — 목록·쓰기 응답에 `reservedCount`(오늘 KST·시작 ≤ 지금 < 끝 회차의 CONFIRMED·COMPLETED 예약 수, 회차 쿼리 1개)·`totalCount`(+ `currentCount`)를 붙이고 `level`을 합계로 다시 매긴다. 스키마 변경 없음 — `currentCount`는 "예약 외 현장 인원"으로 의미만 바꿈.
- member-web 홈 혼잡도 카드 — 시설마다 `약 21명/60 · 강습 3 + 현장 18 (12분 전)`, 아래에 구성 설명 한 줄, 30분 경고는 "현장 인원"으로. 360px에서 한 줄(캡처 확인).
- admin-web 시설·혼잡도 — 합계/정원, "진행 중 강습(예약) a명 + 현장 b명", 입력칸 "예약 외 현장 인원"·버튼 "입력", 머리말·도움말·오류 해결 문구. 지점 상세 시설 카드도 합계 기준.
- 테스트: jest `facility-occupancy` 5건, e2e `admin-congestion`·`member-congestion`.
- 문서: 혼잡도관리 ADR-FAC-05·요약 카드·§11·A-3·A-6·A-8, entities.md, 요구사항추적표 F8-2(조정 유지, 근거 갱신)·§2-2·§1-1 #8, 요구사항 정의서 재생성.

**제안과 달라진 점**: ① 제안서의 "예약·취소 성공 후 홈 카드 캐시 비우기"를 넣었다가 뺐다 — 예약은 시작 전 회차만 받고(`SLOT_ALREADY_STARTED`) 취소도 시작 전 마감까지라, 결제·취소가 "지금" 혼잡도를 바꾸는 경우가 없다. 예약 인원은 회차가 시작되는 순간 조회에 잡힌다. ② "현재 시각을 주입 가능한 함수로"도 하지 않았다 — 테스트가 지금 시각(KST) 앞뒤 30분 회차를 DB에 직접 만들고 00:00·24:00에서 잘라 자정 근처에도 같은 날 안에 머물게 했다.

**근거**: 혼잡도관리 ADR-FAC-05(대안 A 수동 유지 / B 예약 합산 / C 키오스크 입장 — C 보류 이유: 기기 토큰 인증·`FacilityCheckIn` 스키마·배포 DB 마이그레이션, Workers 무료 한도 ≈10.05만으로 초과, RFP F8-2는 수단을 요구하지 않음), D10, ADR-FAC-01·04, design-constants ③·⑩·⑬, D53(시중 사례: 출입 스캔 + 퇴장 추정이 일반적, 모두 추정치).

**검증**: api jest `facility-occupancy` 5건·`facility-lifecycle`·`catalog-flow` 통과(커밋 hook에서 전체 jest), 세 앱 lint·빌드, 화면 자동 테스트 로컬 14건 통과, 회원 카드 360px 캡처. 배포 화면은 병합·Worker 재배포 전이라 검증되지 않음.
