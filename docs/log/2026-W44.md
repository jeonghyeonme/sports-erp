## 185. 위탁계약 갱신 기능 계획 — 지금은 계약 정보를 바꿀 방법이 없다 (2026-10-26)

**계기**: "OCR 통해서 계약서 필드 긁어온다는거, 지금은 어떻게 하고 있지? 재갱신 같은 거 어떻게 함?"(사용자). 확인해 보니 OCR은 설계만, 그리고 그 전에 **계약 상대방·기간을 입력·수정하는 API·화면 자체가 없다**(값은 시드). 바꿀 수 있는 건 계약 상태 하나(`PATCH /branches/:branchId/contract-status`)이고 그 변경도 변경 이력에 남지 않는다. 새 지점을 만드는 기능도 없다. 지점 상세 안내 문구("본사가 입력한 계약 정보", "Phase 2~3 예정")는 코드와 어긋난다.

**한 일**: 사용자와 설계를 정해 [D68](../decisions/D68.md)로 남겼다 — 갱신·정정(본사), 이력은 `AuditLog`(스키마 변경 없음), 종료 지점 갱신 409, 종료 임박 표시(조회 때 계산, 자동 전환 없음), 신규 지점 등록. 사용자 지시는 "계획만 세워둬" — 코드는 바꾸지 않았다.

**다음**: 착수는 사용자. 신규 지점 등록은 범위가 커서 갱신·정정·이력·임박 표시와 나눠 두 번에 할 수 있다.

## 189. 배포 DB 신규 테이블 3개 RLS 켜기 — Supabase 보안 경고 대응 (2026-10-28)

**계기**: Supabase가 `rls_disabled_in_public`(Critical) 경고 메일을 보냈다. anon key만 있으면 PostgREST(`/rest/v1/<테이블>`)로 해당 테이블을 읽기·수정·삭제할 수 있는 상태.

**원인**: RLS는 저장소 밖(Supabase 마이그레이션 `enable_rls_*`)에서만 켜 왔다(log/029·040, D37 "Supabase 전용 설정(RLS)은 저장소 밖"). 그 뒤 Prisma 마이그레이션으로 생긴 `SupportRequest`(D56)·`AccountPermission`·`RolePermission`(D60) 3개는 RLS를 켜는 단계가 빠졌다. 나머지 31개는 이미 켜져 있었다.

**한 일**: 사용자가 "정책 없이 RLS만 켜기"(log/029와 같은 방식)를 선택 — Supabase 마이그레이션 `enable_rls_d56_d60_tables`로 3개 테이블 `ENABLE ROW LEVEL SECURITY`. 배포 DB 쓰기는 사용자 승인(2026-10-28 대화).

**근거**: api는 `postgres` 역할로 접속한다(D37·D46). 이 역할은 `rolbypassrls = true`(실측)라 앱 동작은 바뀌지 않는다. 앱은 Supabase 클라이언트·anon key를 쓰지 않으므로 REST 경로를 막아도 잃는 기능이 없다.

**검증**: `public`의 RLS 꺼진 테이블 0개(실측). `anon` 역할로 `SupportRequest`·`Member` 조회 0행, `postgres` 역할로 `SupportRequest` 16행 조회(실측). 보안 어드바이저 `rls_disabled_in_public` 사라짐, 남은 것은 34개 `rls_enabled_no_policy`(INFO, 의도된 상태). 배포 api를 실제로 호출해 본 확인은 하지 않았다 — 검증되지 않음(역할 속성으로 추정).

**남은 위험**: 새 테이블을 만드는 Prisma 마이그레이션을 배포할 때마다 RLS를 손으로 켜야 하는 구조는 그대로다.

**커밋**: 문서만(이 로그, log/README, STATUS). DB 변경은 저장소 밖.

## 186. 위탁계약 갱신·정정·계약 이력·종료 임박 표시 구현 — D68 1차, 신규 지점 등록은 2차로 (2026-10-30)

**계기**: "B부터 진행"(사용자) — STATUS의 다음 할 일 중 D68(계획 확정, 착수는 사용자). D68이 권한 대로 두 번에 나눠, 이번에는 갱신·정정·이력·임박 표시를 하고 신규 지점 등록은 남겼다.

**한 일**
- API(본사 전용, `@Roles('SUPER_ADMIN')`, 경로 파라미터 `branchId`라 전역 `BranchScopeGuard`가 본다):
  - `POST /branches/:branchId/contract/renewals` `{ contractEndAt, contractPartner? }` — 새 종료일은 지금 종료일(상시 계약이면 시작일)보다 뒤, 상태를 정상(ACTIVE)으로. 종료(TERMINATED) 지점은 409 `BRANCH_TERMINATED`(D68 결정 1).
  - `PATCH /branches/:branchId/contract` `{ contractPartner?, contractStartAt?, contractEndAt? }` — 오타 정정, 상태는 그대로, 시작일 ≤ 종료일(D68 결정 2).
  - 날짜가 맞지 않으면 400 `INVALID_CONTRACT_PERIOD`. 날짜 형식은 `YYYY-MM-DD`만(시각이 붙거나 없는 날짜는 400).
  - 세 쓰기(갱신·정정·기존 상태 변경)를 `AuditLog`(entity `Branch`, action `CONTRACT_RENEWED`·`CONTRACT_CORRECTED`·`CONTRACT_STATUS_CHANGED`)에 **같은 트랜잭션**으로 남긴다. 정정은 바뀐 필드만, 바뀐 게 없으면 남기지 않는다. 상태 변경은 같은 상태로 다시 지정하면 남기지 않는다(D68 결정 3, D44). 지점 행 `FOR UPDATE` 락은 기존 상태 변경과 같다.
  - 지점 응답에 `contractDaysLeft`(KST 오늘 기준, 지난 종료일은 음수)와 `renewalNotice`(상태가 정상인데 종료 60일 이내)를 조회 때 계산해 붙였다. 상태 자동 전환은 없다(D68 결정 4, entities.md `renewalNoticeAt`).
- 관리자 웹: 지점 상세 계약 카드에 "계약 갱신"·"정보 수정" 버튼(`ContractEditModal`), "종료 60일 이내" 배지, 카드 아래 "계약 이력"(본사만, 최신 20건). 사실과 달랐던 안내 문구("본사가 입력한 계약 정보", "Phase 2~3 예정")를 고쳤다. 대시보드 "계약 갱신 임박 지점" 카드와 "갱신임박" 필터에 정상이지만 60일 이내인 지점을 포함하고, 계약만료일 옆에 남은 일수 배지. 변경 이력 화면에 계약 세 가지와 대상 "지점 OO점". 화면 도움말·오류 안내에 갱신·정정과 `INVALID_CONTRACT_PERIOD`.
- 남은 일수 계산이 화면(`Date.now()`, UTC 자정 파싱)에서 서버(KST)로 옮겨졌다.

**근거**: D68 결정 1~4·6·7, D44(이력은 변경과 같은 트랜잭션), ADR-STF-07(종료 지점 처리·행 락), D46(격리는 전역 가드).

**검증**
- 새 `test/contract-renewal.spec.ts` 12건 — 지점 관리자 403(자기 지점, 본사 대조군 성공), 갱신 성공·이력 값, 종료일이 같으면 400·무변경, 종료 지점 409, 날짜 형식 400, 정정은 바뀐 필드만·상태 유지·무변경이면 이력 없음·종료<시작 400, 상태 변경 이력은 바뀔 때만, **이력 쓰기가 실패하면(없는 처리자 id → 외래키 위반) 계약 변경도 롤백**, 60일 경계(60일 알림·61일 아님), 갱신 임박 상태·지난 종료일은 알림 없음.
- `branch-isolation.spec.ts` 공격 표에 3건(갱신·정정·지점 계약 이력 조회) — 강남 관리자 → 서초점 403.
- api jest 전체(54개 파일 571건), admin-web lint·빌드, 화면 자동 테스트 15건(본사 계약 갱신 1건 추가: 지점 상세에서 갱신 → 카드 기간·계약 이력 → 변경 이력 화면) 로컬 통과.
- 사용자 매뉴얼(산출물, 화면 도움말이 원천)은 재생성하지 않았다.

**커밋**: `apps/api/src/modules/branches/`(서비스·컨트롤러·DTO 2), `apps/api/src/prisma/audit.ts`, `audit-log.service.ts`(지점 이름), 테스트 2, `apps/admin-web`(ContractEditModal, 지점 상세·대시보드·변경 이력, contract-status·types·help·error-hints), `e2e/tests/admin-hq.spec.ts`, entities.md §2-1.

## 187. 신규 지점 등록 — 새 위탁계약 = 새 지점, 본사 전용, 지점 코드는 영문 대문자·유일 (D68 2차, 2026-10-30) (2026-10-30)

**계기**: "PR 만들고 신규 지점 등록도 진행"(사용자). D68 1차(log/186)에 이어 결정 5를 구현했다. 지금까지 새 지점은 시드로만 생겼다.

**한 일**
- API: `POST /branches`(본사 전용). 받는 값은 이름·지점 코드·지역(필수), 주소·대표 전화·출근 기준 시각(선택), 계약 상대방·시작일(필수)·종료일(선택, 비우면 상시)이다. 상태는 정상(ACTIVE)으로 시작한다. 응답은 지점 목록과 같은 형식이고 건수는 0이다.
  - 지점 코드: **영문 대문자 2~12자**. 회원번호가 `코드+연도-순번`(예: `SEOCHO2026-001`)이라 코드에 숫자가 섞이면 연도와 붙어 읽히므로 숫자를 받지 않는다. 기존 다섯 곳도 모두 영문 대문자다. 중복이면 409 `BRANCH_CODE_TAKEN`(유일 제약 P2002를 변환), 종료일이 시작일보다 앞서면 400 `INVALID_CONTRACT_PERIOD`.
  - 채번 시퀀스(`CodeSequence`)는 첫 채번 때 upsert로 생기므로(`src/prisma/integrity.ts`) 등록 때 준비하지 않는다. 새 지점에 채용하면 `PANGYO-001`이 매겨지는 것을 테스트로 확인했다.
  - 등록도 계약 이력 첫 줄로 남긴다(`AuditLog` action `BRANCH_CREATED`, 같은 트랜잭션). D68 결정 3에 등록은 없었지만, 이력이 등록부터 이어져야 "언제 누가 이 계약을 넣었나"가 보인다. 액션 하나만 늘었고 스키마 변경은 없다.
- 관리자 웹: 대시보드 머리에 "+ 지점 등록"(본사만). 등록 창의 지역 칸은 기존 지역을 고를 수 있는 입력칸이고, 지점 코드는 대문자로 바꿔 받는다. 등록하면 새 지점 상세로 옮겨 간다(시설·프로그램·파견은 기존 화면). 계약 이력·변경 이력 화면에 "지점 등록", 도움말·오류 안내 2건.

**근거**: D68 결정 5·6·7, D44, D46(경로 파라미터 없는 본사 전용 라우트는 `branch-scope-coverage`가 면제).

**검증**
- `contract-renewal.spec.ts`에 3건(총 15건): 지점 관리자 403 후 본사 201 → 지점 목록·공개 목록(회원 가입 지점 선택)·계약 이력 1줄, 새 지점 첫 채용이 `PANGYO-001`, 코드 중복 409·소문자/숫자 400·기간 역전 400(지점 수 그대로).
- api jest 전체(54개 파일 574건), admin-web lint·빌드, 화면 자동 테스트 16건(본사 지점 등록 1건 추가: 소문자 코드 입력 → 상세로 이동 → 계약 이력 "지점 등록") 로컬 통과.
- 새 지점의 시설·프로그램 등록과 지점 관리자 채용 흐름은 기존 화면 그대로이고 이번에 따로 따라가지 않았다(검증되지 않음).

**커밋**: `branches`(서비스 `createBranch`·컨트롤러·`create-branch.dto.ts`), `audit.ts`, 테스트, admin-web(`BranchCreateModal`, 대시보드, contract-status·help·error-hints·변경 이력), e2e 1건, entities.md §2-1.

## 188. 사용자 매뉴얼 재생성(D68 화면 반영)과 CI 화면 테스트 러너 고정 (2026-10-30)

**한 일**

GitHub의 `ubuntu-latest` 러너가 Ubuntu 26.04로 바뀌었고, Playwright 1.56.1이 그 OS에 브라우저 설치를 거부했다("Playwright does not support chromium on ubuntu26.04-x64"). 그래서 테스트가 시작되지 않았다. `.github/workflows/ci.yml`의 e2e 작업만 `ubuntu-24.04`로 고정했다. 다른 작업(api·웹 빌드·doc-check)은 26.04에서 통과하므로 그대로 둔다. Playwright를 26.04를 지원하는 판으로 올리면 고정을 풀 수 있다.
- **사용자 매뉴얼 재생성**: 화면 캡처 22장을 `capture-manual.mjs`로 다시 찍었다. 시연 데이터가 실행일 기준이라 바뀐 화면이 아니어도 날짜·숫자가 바뀐다. 이어서 `manual.js`로 `사용자매뉴얼.docx`·`교육자료_빠른시작.docx/.pdf`를 다시 만들었다. 원천은 화면 도움말(`help-content.ts`)과 오류 안내(`error-hints.ts`)이다. 따라서 log/186·187에서 고친 지점 등록·계약 갱신·정보 수정·계약 이력 안내와 `BRANCH_CODE_TAKEN`·`INVALID_CONTRACT_PERIOD` 해결 문구가 그대로 들어간다.

**근거**: D59(화면 자동 테스트), RFP 과업4·산출물5(log/152 매뉴얼 생성 방식), D38(한 사실은 한 곳 — 매뉴얼은 도움말에서 생성).

## 190. Worker 재배포로 D68 계약 화면 운영 반영 — STATUS 정리, 계약서 OCR·AI 검토 착수 (2026-10-31)

**계기**: log/186·187의 계약 갱신·정정·이력·신규 지점 등록 화면은 Lambda(`dev` 병합 때 자동)에는 올라갔지만 정적 자산은 Worker 재배포가 있어야 운영에 보였다(STATUS 다음 할 일 2번, 사용자 몫).

- **계약 회차 번호**: `CorrectContractDto`·`SetContractFileDto`에 `roundNo`(필수), `lockContract`가 다르면 409 `CONTRACT_ROUND_CHANGED`. 관리자 웹 정정 창·파일 올리기 창이 연 때의 회차 번호를 보내고 오류 안내 문구를 더했다.
