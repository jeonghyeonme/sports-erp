# 32. Little's Law로 "동시 로그인" 배율을 산정하고, D24(인증 경로 확장성 로드맵)로 정리했다 (2026-09-27)

> [진행 로그 인덱스](README.md)

**계기**: §31에서 로그인 CPU 스로틀링을 발견한 뒤, 사용자가 정확한 질문을 던졌다 — "지금 이 문제는 로그인 기능에 한해서고, 무료 인프라라 50명도 안 되는 동시 로그인에 문제가 생기는 건데, 이미 위탁계약이 98개인데 접속 인원이 꽤 많지 않겠냐"는 것. 이건 "테스트에서 발견한 버그를 고쳐라"가 아니라 "이 발견이 이 프로젝트가 원래 노리는 규모(98→130개 지점)에서 실제로 문제가 되는가"를 수치로 검증하라는 요구였다.

**한 일 — 정량화**: `design-constants.md`가 이미 산정해둔 ④(피크 동시 재실자 33명/지점, Little's Law)와 ⑤(전사 동시 재실 3,200명)를 그대로 재사용하되, **Little's Law를 반대 방향으로 적용**했다 — 기존엔 "도착률×체류시간=동시 인원"으로 동시 재실자 수를 구했다면, 이번엔 그 동시 재실자 수에서 거꾸로 "도착률"(⑦, ≈45.7명/분)을 역산하고, 이걸 다시 "로그인 처리시간"에 곱해(Little's Law를 정방향으로 한 번 더 적용) "동시 진행 중인 로그인 건수"(⑨)를 구했다. 결과가 핵심을 정확히 짚었다 — **정상 처리(65ms) 시 동시 진행 로그인은 0.12건에 불과해 평소엔 전혀 문제가 안 되지만, 처리시간이 늘어나는 순간(§31의 15초) 같은 공식이 동시 진행 건수를 28.5건으로 밀어올린다.** 즉 "지연이 지연을 부르는" 자기강화 루프라는 걸 계산으로 보여준 것이다 — §31에서 40 VU 램핑 중 응답시간이 완만히 늘지 않고 급격히 무너진 관찰과 정확히 들어맞는다.

**부수 발견 — D23이 실제와 어긋나 있었다**: D24를 쓰려고 기존 배포 결정(D23)을 다시 읽다가, D23이 "admin-web은 Cloudflare Pages"라고 적혀 있는데 §30에서 실제로는 Cloudflare Pages 커넥터에 생성 툴이 없어 **admin-web도 Render로 통합했다**는 사실이 반영이 안 돼 있는 걸 발견했다. 계획(D23 원문)과 실행(§30)이 각각 다른 시점에 기록되면서 어긋난 전형적인 사례라, D23을 실제 배포 상태로 정정하고 "변경 이력" 절로 왜 계획이 바뀌었는지(도구 한계를 실행 단계에서 발견)를 남겼다. 겸사겸사 D20~D23이 요약표에 빠져 있던 것도 이번에 채웠다(문서 자체가 이번 세션 이전부터 그 누락을 갖고 있었음).

**D24 결정 — 왜 "하나 고르기"가 아니라 "단계적으로 쌓기"인가**: 대안을 비교하면서 가장 중요하게 짚은 건, §31에서 1순위로 꼽았던 "로그인 rate limit"이 **이 문제를 안 푼다는 것**이다. Rate limit은 "악의적으로 무제한 요청을 퍼붓는 것"을 막는 보안 대책이지, "진짜 회원 수백 명이 퇴근 후 동시에 정상적으로 로그인하려는" 용량 문제는 못 막는다 — 오히려 너무 빡빡하게 걸면 정상 사용자를 튕겨낸다. 이 둘을 뒤섞지 않고 분리한 게 이번 결정의 핵심이다. 그리고 "수평 확장"(여러 인스턴스로 트래픽 분산) 대안을 검토하다가, **지금 아키텍처(MockDataService, 인스턴스별 인메모리 상태)로는 애초에 수평 확장이 불가능하다**는 걸 짚었다 — 여러 인스턴스를 띄우면 각자 다른 mock 데이터를 들고 있게 되기 때문이다. 그래서 `log/` §29에서 이미 "다음 할 일"로 미뤄뒀던 "MockDataService → PrismaService 전환"이, 이번 일로 "단순 데이터 영속성 문제"에서 "수평 확장의 전제조건"이라는 새로운 무게를 얻었다 — 서로 다른 시점에 내려진 결정 두 개가 이번 계산으로 연결된 사례다.

**결정**: 1단계(즉시, 코드 레벨) = 로그인 rate limit 구현(보안). 2단계(실DB 전환 시, 아키텍처 레벨) = MockDataService→PrismaService 전환(수평 확장의 전제조건). 3단계(성장 시점, 인프라 레벨) = Render 유료 플랜+다중 인스턴스 실제 가동. 선택(도메인 확보 시) = Cloudflare rate limiting을 1단계 위에 얹기. 자세한 대안 비교표와 각 단계의 근거는 docs/decisions/D24.md 참고.

**검증**: 계산 자체(Little's Law 역산·정산)이며 코드 변경은 없다. `design-constants.md`에 ⑦~⑨ 계산 과정과 "약한 고리"(로그인=시설도착 1:1 가정) 명시, `decisions/`에 D23 정정 + D24 신설, 이 로그 절로 기록했다.

**다음 작업**: D24의 1단계(로그인 rate limit) 구현부터 시작.
