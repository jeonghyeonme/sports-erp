## 125. 시연 데이터로 화면 점검 — 역할별 핵심 경로 15화면, 발견 목록 (2026-10-19)

**계기**: STATUS 다음 할 일 3(a). 관리자 웹·회원 웹을 고밀도 시연 데이터(D58)로 열어 본 적이 없었다("검증되지 않음").

**사용자 결정(D53 방식)**: 상위 목표 = 노하우 습득(D53), 클라이언트 = 현장 사용자·사용성과 속도(D58).
- **답안지**: 출시 전 QA는 실제와 비슷한 양의 데이터로 역할별 핵심 경로를 걷는다. 실제 기기 폭, 많은 데이터에서 깨지는 것(긴 목록·빈 상태·표), 느린 화면을 본다. **핵심 변수**: 현장 사용자가 매일 여는 화면이 데이터가 많아졌을 때 읽기 어렵거나 느려지는가.
- 범위: 역할별 핵심 경로(추천안). 점검: 화면 밀도·깨짐 + 속도 수치(추천안). 처리: 이번에는 목록만 만들고 보고(추천안) — 고칠 것은 사용자가 고른다.
- **사용자 설명**: 없음 — 추천안 선택.

**방법**: 기준 DB와 분리한 별도 DB `sports_erp_demo`에 `seed:demo`(기준일 2026-10-19)를 얹었다. 로컬에서 api(`dist/main.js`)와 admin-web·member-web 개발 서버를 띄웠다. ## 127. 화면 점검 F1·F2 수정 — 근태 화면 KST(새벽 체크인 막힘 포함), 연차 사용일 정합 (2026-10-19)

**계기**: log/125 발견 F1·F2. 사용자가 둘 다 고치자고 했다. 판단이 갈릴 대안이 없는 결함 수정이라 D53 질문은 생략하고 근거 규칙만 인용한다. F1은 date-time-handling의 "KST 기준" 규칙이고, F2는 근태관리 A-3과 ADR-ATT-01(승인 때 ANNUAL만 차감)이다.

### F1 — 근태관리 화면(`apps/admin-web/src/pages/AttendancePage.tsx`)

- **시각 표시**: `formatTime`에 `timeZone: 'Asia/Seoul'`이 없어, 한국이 아닌 기기에서 9시간 밀려 보였다. 직원 상세(`StaffDetailPage`)와 같게 지정했다.
- **"오늘"(더 큰 결함, 점검 중 새로 확인)**: `todayStr()`이 `toISOString().slice(0, 10)`(UTC)였다. 그래서 **한국 기기에서도 00:00~08:59 KST에는 어제가 "오늘"이 된다.** "오늘의 근태"가 어제 기록을 보여 주면 체크인 버튼이 비활성이 된다. 새벽 근무 직원(06:30 새벽 수영 등)이 화면에서 출근을 누를 수 없었다. 휴가 신청·업무일지의 기본 날짜도 어제로 들어갔다. KST 날짜로 고쳤다.
- **재현**: 2026-10-19 03:06 KST, 시연 DB(어제까지 근태)에서 Playwright로 확인했다.

| | 수정 전 | 수정 후 |
|---|---|---|
| UTC 기기 | "오늘의 근태" 체크인 오후 11:38·체크아웃 오전 08:52(어제 기록, 9시간 밀림), 이번 달 첫 행 오후 11:35 / 오전 08:35 | 체크인 -·체크아웃 -(오늘 기록 없음), 첫 행 오전 08:35 / 오후 05:35 |
| 한국 기기 | "오늘의 근태"에 **어제 기록**(오전 08:38 / 오후 05:52) → 체크인 버튼 비활성 | 체크인 -·체크아웃 -, 버튼 활성 |

**같은 종류가 남은 곳(이번에 고치지 않음, 후속)**: UTC "오늘"(`new Date().toISOString().slice(0, 10)`)이 아래 곳에 더 있다. 모두 새벽에 기본 날짜가 하루 앞선다.
- admin-web `ReservationsPage.tsx:31`(회차 추가 기본 날짜)
- admin-web `AssetsPage.tsx:69`(취득일 기본값)
- admin-web `DocumentsPage.tsx:32`(보존기한 판정 기준일)
- `AbsenceConfirmSection.tsx:33`
- member-web `ProgramSlotsPage.tsx:194`
- `WeeklyTimetable.tsx`는 이미 KST 함수를 쓴다.

### F2 — 연차 사용일(`apps/api/prisma/demo-layer.ts`)

- **log/125 정정**: F2를 "시연 직원 15명 중 11명 불일치"로 적었는데, 그 SQL은 병가·경조사까지 셌다. 앱은 승인 때 **연차(ANNUAL)만** 차감한다(ADR-ATT-01). 연차만 세면 시연 층이 만든 직원 14명은 이미 맞았다. 틀린 것은 **기준 시드 직원**(김민수·박서연·마포·노원 등)에게 시연 층이 얹은 승인 연차였다. 김민수는 잔여 행이 있는데 사용 0일이었고, 나머지는 잔여 행이 아예 없어 앱이 처음 조회할 때 0일로 만들었다.

JSON 형식을 밝히고 본문이 비면 Storage 서버(Fastify)가 본문 해석 단계에서 400으로 거부한다. storage-js의 `createSignedUploadUrl`도 이 호출에 `{}`를 보낸다.
- 세션 프록시가 supabase.co 직접 접속을 막아 같은 요청을 여기서 재현하지는 못했다 — 원인 판단은 로그와 storage-js 동작에 근거한다.

**한 일**: `SupabaseDriver.createUploadUrl`이 본문 `'{}'`를 보낸다. 다른 호출(`sign`·`remove`)은 이미 본문이 있고 `info`는 GET이라 content-type을 붙이지 않는다. 새 `test/storage-supabase-driver.spec.ts`가 fetch를 가로채 요청 URL·메서드·본문·두 인증 헤더와 거부 시 502를 본다 — 수정을 빼면 첫 케이스가 실패하는 것을 확인했다. 그동안 첨부 테스트는 메모리 드라이버만 거쳐 REST 요청 모양을 본 테스트가 없었다.

**남은 것**: 병합 → Lambda 배포 뒤 업로드 URL 201 확인. 그다음 실제 PDF 올리기·붙이기·내려받기(배포 DB에 `Attachment` 행과 저장소 파일이 생긴다 — 사용자 허락 뒤). `info` 경로(붙이기 때 크기·형식 재확인)는 그때 처음 실제 저장소로 검증된다.

**한 일**: `apps/api/test/branch-scenarios.spec.ts`(8건)로 장면마다 재현 테스트를 먼저 쓰고 돌렸다.
- 마포(갱신 임박) 계약 종료 전이와 채용 5건을 동시에 → 활성 파견 0, 종료보다 먼저 커밋된 채용은 재배치 대기 결과에 들어간다. 이상 없음(지점 행 락, ADR-STF-07). 발령 동시성은 `contract-termination`이 이미 보고 있었다.
- 파견 이동 날 근태 귀속(서초 → 강남): 발령 뒤 체크인은 강남 기록(서초 요약에 없음), 체크인 뒤 같은 날 발령은 서초에 남고 체크아웃이 두 번째 기록을 만들지 않는다. 이상 없음(ADR-ATT-03).
- 재시도 중복(느린 응답 15초 안내·몰림 503 뒤 다시 누름, D55): 같은 회차 예약 동시 2건 → 1건·409, 결제 승인 동시 2건 → 1건. 이상 없음.
- **휴가 신청 — 결함**: 겹침 검사가 없어 같은 3일 연차를 두 번 신청하면 둘 다 받아졌고, 둘 다 승인하면 사용 일수가 0 → 6일이 됐다. 동시에 5번 보내면 5건이 생겼다.

**사용자 결정(D53 방식, 2026-10-20)**: 상위 목표 = 노하우 습득(D53). 고치는 방식 — 앱에서 직원 행 락 + 겹침 검사(추천안). 대안은 DB 제외 제약(btree_gist, 배포 DB 확장·마이그레이션 필요)과 승인 때만 막기였다. **사용자 설명**: 없음 — 추천안 선택.

**고친 것(근태관리 ADR-ATT-05)**: `integrity.ts`에 `lockStaff`(직원 행 `FOR UPDATE`). 신청은 그 락 뒤 대기·승인 휴가와 하루라도 겹치면 409 `LEAVE_REQUEST_OVERLAP`(반려된 것과는 겹쳐도 된다), 승인도 같은 락 뒤 이미 승인된 휴가와 겹치면 409 — 막기 전에 쌓인 겹침이 있어도 연차는 한 번만 깎인다. 관리자 웹 오류 "해결" 문구 추가. 시연 DB에 겹치는 대기·승인 휴가는 0건(SQL 확인)이라 시연 데이터는 그대로다.

**돌리지 않은 것**: 몰림 503 자체(Lambda 동시 실행 상한 10 초과) — 로컬에서 상한을 재현할 수 없다. 503 뒤 재시도의 데이터 측면은 위 재시도 중복으로 봤다. 운영 측정은 STATUS 5(S2 거절 원인)와 함께.

**검증**: `branch-scenarios.spec.ts` 8건 + `attendance-rules.spec.ts` 9건 통과. 수정 전에는 휴가 두 건(재신청 201, 동시 5건 생성)이 실패하는 것을 확인했다. 전체 jest는 커밋 hook에서.

**커밋**: api 근태·integrity, 시나리오 테스트, 관리자 웹 오류 문구, 근태관리 ADR-ATT-05·검증현황, engineering-risks §4 결과 표, data-integrity §6, STATUS, log.

## 142. 배포 DB 재시드 준비 — 스키마 지문 일치 확인, 한 트랜잭션 실행기, 빈 복제 2회 검증 (2026-10-20)

**계기**: 완성도 순서 ③ 배포 상태 맞추기(log/140). 배포 DB는 83곳·시연 데이터 없음이라 로컬(5곳 + 시연 층, D58)과 달랐다. 사용자가 "검증 후 적용까지" 승인했다(2026-10-20, 배포 DB 쓰기 — CLAUDE.md 승인 대상). 첨부 실제 파일 시험은 재시드 뒤로.

**배포 DB 현황(읽기만, 2026-10-20)**: 지점 83(종료 3)·직원 168·회원 169, 예약 2·결제 2·게시글 2·변경 이력 8(모두 전화번호 열람)·첨부 0, 갱신 토큰 1,865(대부분 k6), 10-09 이후 생긴 계정 0. 지울 운영 데이터는 사실상 없다. `_prisma_migrations` 테이블이 없다 — 배포 DB 스키마는 SQL로 맞춰 왔다(log/044~050, log/121).

**한 일**:
- 스키마 대조: 열·인덱스·제약·트리거·함수·enum 6종을 정렬한 문자열의 md5로 비교 — 로컬 마이그레이션으로 새로 만든 DB와 **6종 모두 일치**(열 276·인덱스 89·제약 100·트리거 7·함수 6·enum 26). 처음엔 인덱스만 달랐는데 두 DB의 정렬 규칙(C.UTF-8 vs Supabase 기본) 차이였다 — `collate "C"`로 맞추면 같다.
- 데이터: 로컬 `sports_erp_reseed`에 마이그레이션 → `npm run seed:demo`(기준 시드 + 시연 층, 2026-10-20 KST 기준 지난 90일·앞으로 3주) → `pg_dump --data-only --inserts --rows-per-insert=200`(약 2.9MB, INSERT 106문).
- 실행기 `apps/api/prisma/apply-reseed.ts`: 앱 테이블 32개 TRUNCATE → INSERT 전부 → 행 수 출력을 **한 트랜잭션**으로. `RESEED_CONFIRM_HOST`가 `DATABASE_URL` 호스트와 같아야 돈다. pg_dump 16.10+가 넣는 psql 전용 줄(`\restrict`)은 버린다(처음 실행에서 이 줄 때문에 문법 오류).
- 검증(빈 복제 DB): 2회 적용 모두 원본과 32개 테이블 행 지문(md5) 일치 — 같은 파일을 다시 돌려도 같다. 일부러 깨진 INSERT를 붙이면 실패하고 기존 데이터가 그대로다(롤백). 호스트를 틀리게 주면 실행 전 거부.

**적용 방법(사용자 PC, 승인됨)**: SQL 파일은 세션에서 전달(저장소에 넣지 않는다 — 실행일 기준 날짜라 다시 만들면 된다). `apps/api`에서 `DATABASE_URL`(aws-lambda/.env의 Lambda 접속 문자열)·`RESEED_CONFIRM_HOST`를 두고 `npx ts-node prisma/apply-reseed.ts <파일>`. 적용 뒤 모든 로그인(갱신 토큰)이 끊긴다 — 데모 계정은 다시 로그인. 스키마는 바꾸지 않으므로 Lambda 재배포는 필요 없다.

**남은 것**: 적용(사용자) → 세션이 배포 DB 행 수·화면 확인 → 첨부 실제 파일 시험 → 로그 한 건.

## 143. 배포 DB 재시드 적용 — 첫 시도는 열 순서 차이로 실패·롤백, 열 이름 형식으로 다시 만들어 적용 (2026-10-20)

**계기**: log/142에서 준비·검증한 재시드를 사용자가 자기 PC에서 실행했다(사용자 승인 2026-10-20, 배포 DB 쓰기).

**첫 시도 — 실패, 배포 DB는 그대로**: `invalid input syntax for type timestamp: "{}"`. 원인은 적재 SQL 형식이었다 — `pg_dump --inserts`는 열 이름 없이 값만 순서대로 넣어 **대상 테이블의 물리적 열 순서**에 기댄다. 배포 DB는 마이그레이션 도구가 아니라 SQL로 맞춰 와서(`_prisma_migrations` 없음, log/044~050·121) 열을 나중에 더한 테이블 5개(AttendanceRecord·Facility·Member·Payment·Staff)의 순서가 로컬과 달랐다. log/142의 스키마 대조는 열 **집합**만 정렬해 비교해서 순서 차이를 못 잡았다. 실행기가 한 트랜잭션이라 전부 되돌아갔다(설계대로 동작).

**고친 것**: 같은 원본 DB에서 `pg_dump --column-inserts`(INSERT마다 열 이름)로 다시 만들었다(v2). 실행기 `apply-reseed.ts`는 이제 열 이름 없는 INSERT가 하나라도 있으면 시작 전에 거부한다(v1 파일로 확인 — 106문 거부, v2는 적용).

**적용 결과(v2)**: 사용자 PC에서 성공. 세션이 배포 DB를 읽어 확인했다.
- 32개 테이블 행 수가 로컬 원본과 모두 같다(지점 5·직원 23·회원 218·예약 5,534·결제 5,534·회차 700·근태 1,497·변경 이력 83 등, 갱신 토큰 0).
- 행 내용 지문: 27개 테이블은 행 문자열 md5가 일치. 열 순서가 다른 5개는 행 문자열이 순서에 따라 달라지므로 `to_jsonb(r)`(키 정렬) md5로 다시 비교해 일치.
- 배포 URL api: 지점 5, 서초 회원 60·결제 1,526·예약 1,526, 회원 이수진 예약 34, 업무지원 요청 16.
- 종료 지점 데이터 정리(log/104, ADR-STF-08)는 재시드에 흡수됐다 — 5곳 시드의 노원(종료)에는 진행 중 파견이 없다.

**배운 것**: 스키마 "같음"은 집합 비교로는 부족하다 — 위치에 기대는 형식(값만 나열하는 INSERT, `COPY` 열 생략)을 쓸 때는 열 순서까지 본다. 더 단단한 쪽은 위치에 기대지 않는 형식을 쓰는 것이다.

**남은 것**: 첨부 실제 파일 시험 — 세션 네트워크가 supabase.co 직접 접속을 막아 업로드를 세션이 할 수 없다. 사용자가 브라우저에서 올리고 세션이 `Attachment` 행·`storage.objects`를 확인한다. Worker 재배포. 접속 문자열(DB 비밀번호 포함)이 이번에 다시 대화에 노출됐다 — 교체 권장(security-plan §8 S1).

## 144. 배포 데모 로그인 실패(로컬 api 주소 번들) 재발 방지·첨부 실제 파일 확인·관리자 웹 이미지 미리보기 (2026-10-20)

## 145. 공지 대상 시설 지정 — RFP F4-3 완전 충족(게시판 ADR-BRD-05) (2026-10-20)

**계기**: 사용자가 부분 충족 조항 중 "사용자 직접 작업·문서 작업을 뺀 것"을 진행하라고 했다. 남은 코드 조항 셋 중 F4-3(시설별 공지)은 스키마 변경 승인, F1-2·N7-2(세부 권한)는 "역할 기본값 + 개인 예외"로 결정, N7-3(PG 연계)은 보류(사용자 작업이 필요하고 세션은 PG 서버 접속이 막혀 있다). 이 기록은 F4-3이다. 세부 권한은 다음 작업.

**한 것**(ADR-BRD-05):
- 스키마: `Post.facilityId`(선택, Facility FK, `ON DELETE SET NULL`). 마이그레이션 `20261020120300_f43_post_facility`에 같은 지점 트리거 `post_facility_branch`(D28 방식, search_path 고정)를 함께 넣었다.
- api: 작성은 `@ScopedResource('facility', { body: 'facilityId' })` — 다른 지점 시설 403, 없는 시설 404(D46, 컨트롤러에 지점 검사를 손으로 쓰지 않음). 본사 공지에 시설 400 `POST_FACILITY_NOT_ALLOWED`. 수정은 경로가 글 id라 서비스가 그 글 지점의 시설인지 본다(400 `FACILITY_BRANCH_MISMATCH`), `null`은 해제. 목록 `?facilityId=`는 보이는 글 안에서만 거른다. 응답에 `facilityId`·`facilityName`.
- 관리자 웹: 지점 관리자 글쓰기·수정에 "대상 시설"(비우면 지점 전체), 목록·상세에 시설 표시. 회원 웹: 공지 목록에 시설 고르기(홈 혼잡도와 같은 `GET /facilities` 60초 캐시), 목록·상세에 시설 표시.
- 시연 데이터 층: 지점별 "시설 휴관 안내"를 헬스장 대상으로(기준 시드는 그대로).
- 산출물: 요구사항 정의서·데이터 정의서 재생성. 데이터 정의서 생성기는 업무지원 요청 테이블(D56) 설명이 없어 10-17부터 실패하고 있었다 — 설명을 더하고 옛 "미사용" 문구 2개(인사 변경 신청·첨부)를 지금 상태로 고쳤다.

**검증**: api jest 45개 파일 510건 통과(새 `post-facility.spec.ts` 5건 — 작성·필터·회원 표시·다른 지점 403·없는 시설 404·본사 400·수정 변경/해제/다른 지점 400·DB 트리거, `branch-isolation`에 강남 관리자 → 서초 시설 공격 케이스). 세 앱 lint·빌드, 화면 자동 테스트 7건 통과(`admin-branch`가 시설을 골라 쓰고 목록·상세 표시를, `member-notice`가 시설로 거른 목록과 상세를 본다). doc-check 통과.

## 146. 세부 권한 1단계 — 역할 상한 안의 역할 기본값·개인 예외, 서버 판정(D60, ADR-AUTH-07) (2026-10-20)

## 155. Lambda 배포 실패(health 502) — sanitize-html의 ESM 전용 파서를 CommonJS 판으로 고정 (2026-10-22)

**계기**: log/154(PR #107) 병합 직후 api 배포 #53이 health check 502로 실패했고, 워크플로가 별칭 `live`를 이전 버전 49로 자동 복귀했다. 그 사이 새 버전 50의 오류 1건으로 CloudWatch 경보 `sports-erp-api-Errors`가 울렸다(사용자가 메일 전달). 운영은 복귀 뒤 옛 버전으로 계속 동작 — 서식 본문 정화(D62)는 아직 운영에 없다.

**원인**: `sanitize-html` 2.18.1이 쓰는 `htmlparser2` 12는 ESM 전용이다. 로컬 Node 22.22는 CommonJS에서 ESM을 `require`할 수 있어(require(esm)) 빌드·jest·e2e가 모두 통과했지만, Lambda Node 22 런타임에서는 부팅 중 `require`가 실패한 것으로 본다 — 로컬에서 `node --no-experimental-require-module`로 묶음을 읽으면 같은 자리에서 `ERR_REQUIRE_ESM`이 난다. Lambda 로그(CloudWatch)는 이 세션에서 볼 수 없어 **추정**이다(배포 성공으로 간접 확인 예정). log/154의 "Node 22의 require(esm)로 Lambda 번들은 그대로 돈다"는 로컬 Node로만 확인한 틀린 결론이었다.

**한 일**:
- 루트 `package.json` `overrides`로 `htmlparser2`를 10.1.0(CommonJS·ESM 둘 다 내보냄)에 고정. `sanitize-html`은 2.18.1 그대로(2.17.x 이하 XSS 권고 회피는 유지). 잠금 파일은 npm으로 다시 풀었다(손으로 고치지 않음).
- log/154에서 넣은 jest ESM 변환 예외를 되돌렸다(이제 필요 없음).
- `scripts/package-lambda.sh`가 zip 전에 묶음을 `--no-experimental-require-module`로 한 번 읽어 보고 실패하면 멈춘다 — 다음에 ESM 전용 운영 의존성이 들어오면 Lambda를 건드리기 전에 배포가 멈춘다.

**검증**: 묶음에서 `--no-experimental-require-module`로 `sanitize-html`과 `post-content` 정화 동작 확인(스크립트·이벤트 속성·`javascript:` 제거, 인라인 시작 → 문단). 같은 묶음에 `htmlparser2` 12를 다시 넣으면 새 검사가 `ERR_REQUIRE_ESM`으로 멈추는 것도 확인(음성 대조). 핸들러 콜드 스타트는 Prisma 엔진 탐색까지 진행(묶음에는 Lambda용 엔진만 있어 로컬에서 그 뒤는 못 봄). jest `post-rich-content`·`post-rules`, 커밋 hook 전체. 실제 Lambda 부팅은 병합 뒤 배포 워크플로 health check로 본다.

**커밋**: 루트 `package.json`(overrides)·`package-lock.json`, `apps/api/jest.config.js`, `apps/api/scripts/package-lambda.sh`, docs.

**한 일**(D62 · 게시판 ADR-BRD-06 범위 안, 결정 변경 없음):
- `RichEditor` `blockStyle` — 한 문단 안의 일부를 고르고 제목·소제목을 누르면 고른 범위의 앞뒤를 `splitBlock`으로 끊고 가운데만 바꾼다. 커서만 있으면(고른 글자 없음) 그 문단 전체 — 워드·한글과 같다. 줄바꿈(Shift+Enter)으로 이은 줄은 한 문단이라 함께 바뀐다(감수).
- 링크 입력칸 — 도구 막대 아래에 주소 칸 + 적용·링크 빼기·취소, 잘못된 주소는 칸 아래 안내(alert 없음). 열 때의 선택 범위를 기억해 적용하고, 고른 글자가 없으면 주소를 링크 글자로 넣는다. Enter는 바깥 글쓰기 form을 제출하지 않게 막고, Esc는 닫는다.
- 도움말(작성 화면) 두 줄, CSS.

## 182. RFP 충족률 — 분모를 조항 수 전부로, 영역별 완료+조정 비율 (2026-10-25)

**계기**: "RFP 조항 총 72개에서 어떻게 64개가 돼?"(사용자). 증빙 요약이 "판정 대상 58/64(91%)"였는데, 해당 없음 8개를 분모에서 뺀 계산이 화면에 드러나지 않았고, 같은 "안 한 것"인 제외 3개는 분모에 남아 기준이 설명되지 않았다. 사용자 결정: **영역 행마다 (완료+조정) / 그 행의 조항 수를 퍼센트로** — 어떤 판정도 분모에서 빼지 않는다.

**한 일**:
- 기준 원천 [요구사항추적표](../reference/요구사항추적표.md) §3-0 — 충족률 열을 "구현+조정 / 조항"으로: 기능·성능 28/29 = 97%, 시스템~제약 17/25 = 68%, 과업·산출물·개념도 13/18 = 72%, 전체 58/72 = **81%**(옛 91%). "부분 포함" 값은 뺐다. 판정 기준의 "해당 없음은 분모에서 뺀다"를 "분모에 남긴다"로. 본문 괄호 속 옛 비율 변화(73% → 80% 등)는 옛 기준 값이라고 밝혀 두고 고치지 않았다.
- RFP 이행 증빙(`rfp-evidence.js`) — 요약 큰 숫자 81%("전체 72개 조항 중 완료·조정 58개"), 집계 표 마지막 열 "완료+조정 비율". 기능·성능 "모두 충족" 문장은 F6-2(원문 "추후 논의")를 빼면 모두라고 고쳤다. PDF·HTML 재생성, 아티팩트 재게시.
- 중간보고서 덱(`deck47.js`) rfp-count 장 — 같은 비율 열 추가, 제목 "— 기능·성능은 모두 충족" → "— 완료·조정 81%". 열 머리·영역 이름 줄바꿈 막음. 그 장만 아티팩트에 재게시.
- 산출물 — 요구사항정의서.xlsx(표지·충족 판정 시트, 추적표에서 읽음), 기업분석및제안서·아키텍처설계서·진행보고서 5의 91% 문장을 81%로 바꿔 재생성. 진행보고서 5의 로그 이력 표에 남은 "89% → 91%" 등은 당시 기록이라 그대로.
- 중간 제출 묶음 재조립(저장소 밖). 압축은 UTF-8 파일 이름 표시를 켜서 만든다 — Info-ZIP `zip`으로 만든 한글 이름 압축이 Windows에서 "잘못된 파일"로 열리지 않았다.

**검증**: 증빙 PDF 1쪽·덱 rfp-count 장을 렌더해 눈으로 확인(줄바꿈·숫자). xlsx 표지·충족 판정 시트의 값 58/72 = 81% 확인. 압축 무결성 검사 통과(Windows에서 직접 풀어 보지는 않음 — 검증되지 않음).

**남은 것**: `presentation/assets/4-7_중간발표/deck-source/appx-sheet.png`(지금 덱이 쓰지 않는 옛 xlsx 캡처)는 58/64 그대로다.
