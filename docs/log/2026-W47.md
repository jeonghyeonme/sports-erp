## 229. 계약 갱신용 영업 리포트(D81) — 지점 하나의 계약·운영 성과·서비스 품질을 인쇄용 한 장으로, 기업 분석 대체 문서 점검 (2026-11-16)

RFP 과업1의 항목(지점현황·지역분포·근무자구조·조직도, 인적/물적자원·본사와 지점·현장관리·관리 효율성)이 모두 있다. 다만 상태 표가 낡아 있었다(2026-09 기준 "Phase 1", 문서관리 "파일 업로드 미구현") — 지금 상태로 고치고 위탁계약 행을 더했다. 추적표 §1-3·P2-1에 대체 구성(요약 제출본 + 분석 본문 문서)을 적었다.

**근거**: D81, D75, D69, 차별화전략 §2, 요구사항추적표 §1-3.

**검증**: api `renewal-report.spec`(새 6건 — 회차가 DB와 같음, 운영 성과가 운영 실적 API 13개월과 같고 12개월 합계는 이번 달 제외, 품질 숫자가 DB와 같음, 업무지원 처리 반영, 지점 관리자 자기 지점 403, 없는 지점 404)·`branch-isolation`(공격 표 1줄)·`branch-scope-coverage`·`permission-coverage` 통과. 화면 자동 테스트 35건(새 2건 — 본사 리포트 세 묶음·인쇄 버튼, 지점 관리자 버튼 없음·직접 주소 본사 전용 안내) 통과. admin-web lint·빌드 통과. 인쇄본은 시연 데이터로 PDF를 떠 눈으로 확인. 전체 jest는 커밋 전 hook.

**한 일**: D63의 방식(같은 메이저 안에서만 올린다) 그대로 — `@nestjs/common·core·platform-express·testing` 11.2.7 → 11.2.10(platform-express가 multer 2.5.0을 고정), `follow-redirects` 1.16.1 → 1.16.3. 잠금 파일은 사용자 PC와 같은 npm 11.5.2로 만들었다 — 컨테이너의 npm 10으로 `npm audit fix`를 돌리면 잠금 파일 서식이 통째로 바뀌고 api 쪽 중첩 설치는 그대로 남아(옛 platform-express 11.2.7) 되돌렸다. 실제 버전이 바뀐 것은 위 패키지와 그 하위 패치 몇 개(encodeurl·on-finished·range-parser 등)이고, 나머지 줄은 같은 버전의 위치 이동이다.

**근거**: D63(같은 메이저 고정), D65(운영 취약점 0 유지), D64(개발 도구 취약점은 별도 — 이번 범위 밖, 23건 중 나머지 20건).

## 232. 비정상 접근 테스트 9건 — 만료 토큰·권한 밖 직접 호출·잘못된 입력, 깨진 JSON의 파서 문구 노출을 `INVALID_JSON`으로 (2026-11-20)

**계기**: 12주차 덱 "다음 할 일"의 비정상 접근 경로. 사용자가 범위를 세 경로(액세스 토큰 만료, 권한 밖 직접 호출, 잘못된 입력)로 정하고(토큰 위조·변조는 제외), 상태 코드와 오류 코드는 정확히, 메시지는 문구를 고정하지 않고 내부 정보가 없는지만 보기로 했다(사용자 결정 C — 401·403 메시지가 Nest 기본 영어 문구라 의도한 문구가 아니다).

**한 일**: 기존 61개 파일과 겹침을 먼저 대조했다. 토큰 없이 401(상태만)은 smoke·branches-public, 역할별 채용 403과 데이터 미변경은 hr-authority, 회원의 처리 대기함 403은 inbox가 이미 본다 — 기존 파일은 옮기거나 고치지 않고, 새 파일 `apps/api/test/abnormal-access.spec.ts`에 빈 곳만 넣었다(9건): 만료 토큰 401 `UNAUTHORIZED`·대조군 200, 토큰 없음 401, 회원·직원이 `GET /members` 403 `FORBIDDEN`·자기 지점 관리자 대조군 200, `POST /members`에 깨진 JSON 400 `INVALID_JSON`·정의되지 않은 필드·타입 오류 400 `VALIDATION_ERROR`. 만료 토큰은 서버의 `JwtService`로 만료 시각만 과거로 발급해 테스트가 서명 키를 읽지 않는다.
처음 실행에서 깨진 JSON 응답이 `400 BAD_REQUEST "Unterminated string in JSON at position 13 …"`로 파서 문구를 그대로 내보내 실패했다. 사용자 결정(전용 코드)에 따라 `AllExceptionsFilter`가 JSON 요청에서 Nest가 body-parser SyntaxError를 바꿔 넘긴 BadRequestException을 골라 400 `INVALID_JSON` "요청 본문(JSON) 형식이 올바르지 않습니다."로 답한다(이 저장소 코드는 BadRequestException을 직접 던지지 않는다). 두 웹앱의 오류 표에 없는 코드는 서버 메시지를 그대로 쓰므로 표는 고치지 않았다.

**근거**: 보안약점 체크리스트 에러-1(오류 메시지 정보노출), 진행률 D80 검증 묶음. 공통 에러 포맷 system-overview §4.

**검증**: 새 파일 9건 통과, api 전체 jest 62파일 680건 통과(로컬 실DB), eslint·tsc 통과. 처음 전체 실행에서 PT 구매 2건이 실패했는데 원인은 로컬 기준 DB 시드가 옛 값(PT 횟수 비어 있음·60,000원)이라서였고, `prisma:seed`(upsert)로 다시 넣은 뒤 통과했다. 경로의 잘못된 % 인코딩(URIError)도 같은 방식으로 파서 문구가 나갈 수 있으나 이번 범위 밖 — 검증되지 않음. 진행률 문서(검증 11/11)에 이 항목을 더할지는 사용자 결정 대기.

**커밋**: `apps/api/test/abnormal-access.spec.ts`(새 파일), `apps/api/src/common/filters/all-exceptions.filter.ts`, `docs/architecture/secure-coding-checklist.md` 에러-1, 기록(`docs/log/2026-W47.md`·`docs/log/README.md`·`docs/STATUS.md`).

## 233. `AGENTS.md`에 Codex 작업 순서·기획·화면 설계·PR 리뷰 절차 — Codex 문서는 PR로 `dev`에 넣고 Claude가 구현 (2026-11-21)

**근거**: 사용자 결정(2026-11-21) — 문서는 기존 폴더, `dev`에는 PR로 병합. D39(브랜치·PR 절차), 전역 가드레일 11절.
