# 131. 배포 첨부 업로드 URL 502 — 빈 JSON 본문을 Supabase가 거부 (2026-10-19)

> [진행 로그 인덱스](README.md)

**계기**: 사용자가 Lambda에 `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`를 넣고 재배포(Deploy api #40, dev `cbecd41`)한 뒤 확인을 요청했다(log/121 "배포" 3번).

**확인한 것**:
- `GET /health` 200, 로그인 200, 게시판 목록 200. 업로드 URL 요청(`POST /posts/post-hq-manual/attachments/upload-url`)은 503 `STORAGE_NOT_CONFIGURED`가 아니라 **502** — 비밀값은 들어갔고 Supabase 드라이버가 동작하기 시작했다는 뜻이다(Worker가 502 본문을 Cloudflare 오류 페이지로 바꿔 보여 준다).
- Supabase edge 로그(MCP `query_logs`): `POST /storage/v1/object/upload/sign/attachments/posts/post-hq-manual/<uuid>.pdf` → **400**. 키는 `service_role` JWT로 인식됐고(두 헤더 모두), 요청은 `content-type: application/json`에 `content_length: 0`. JSON 형식을 밝히고 본문이 비면 Storage 서버(Fastify)가 본문 해석 단계에서 400으로 거부한다. storage-js의 `createSignedUploadUrl`도 이 호출에 `{}`를 보낸다.
- 세션 프록시가 supabase.co 직접 접속을 막아 같은 요청을 여기서 재현하지는 못했다 — 원인 판단은 로그와 storage-js 동작에 근거한다.

**한 일**: `SupabaseDriver.createUploadUrl`이 본문 `'{}'`를 보낸다. 다른 호출(`sign`·`remove`)은 이미 본문이 있고 `info`는 GET이라 content-type을 붙이지 않는다. 새 `test/storage-supabase-driver.spec.ts`가 fetch를 가로채 요청 URL·메서드·본문·두 인증 헤더와 거부 시 502를 본다 — 수정을 빼면 첫 케이스가 실패하는 것을 확인했다. 그동안 첨부 테스트는 메모리 드라이버만 거쳐 REST 요청 모양을 본 테스트가 없었다.

**남은 것**: 병합 → Lambda 배포 뒤 업로드 URL 201 확인. 그다음 실제 PDF 올리기·붙이기·내려받기(배포 DB에 `Attachment` 행과 저장소 파일이 생긴다 — 사용자 허락 뒤). `info` 경로(붙이기 때 크기·형식 재확인)는 그때 처음 실제 저장소로 검증된다.
