# 41. D28 — 정합성 ADR을 모아 "DB가 강제할 수 있는 것"부터 실DB 전환 전에 적용했다 (2026-09-29)

> [진행 로그 인덱스](README.md)

**계기**: 사용자가 "데이터 정합성 측면의 ADR을 뽑아 실DB로 전환하기 전에 적용하고 싶다"고 요청했다. 9개 도메인 문서의 ADR 22개와 Tier2 규칙표를 훑어 정합성 규칙 27개를 [architecture/data-integrity.md](../architecture/data-integrity.md) 인벤토리로 모았다. D27과 기존 unique가 막는 5개를 빼면 전부 `MockDataService` 앱 로직 한 겹이었다.

**분류 기준 — "무엇이 강제할 수 있나"**: 규칙을 ① 한 행 안에서 판정(CHECK 가능) ② 두 테이블의 지점 일치(복합 FK·트리거 필요) ③ 여러 행을 함께 바꾸거나 동시 요청을 직렬화(트랜잭션·락 — 코드 규칙)로 나눴다. ②·③은 설계 판단이 걸려 있어 사용자에게 물었고, ②는 "파견 정책 먼저 결정", ③은 "공용 헬퍼만 지금"으로 정했다.

**①에서 세운 원칙 — 앱이 검증하는 것만 DB로**: 처음엔 눈에 띄는 규칙을 전부 CHECK로 옮기려 했다. 하나씩 앱 코드와 대조해 보니 프로그램 기간·수강 만료일·회차 시각 3개는 앱에 검증이 아예 없었다. 이런 규칙을 DB에만 걸면 사용자 입력 실수가 400이 아니라 500으로 터진다. 그래서 CHECK는 앱 검증의 거울로만 두고(18개), 그 3개는 "앱 검증부터" 공백으로 문서에 남겼다. 18개 전부 시드된 DB에서 위반 거부·정상 경계값 통과를 SQL로 확인했다. 처음 보고할 때 19개라고 셌는데 실제로는 18개여서 바로잡았다.

**②에서 발견한 공백**: "회원↔담당 직원 같은 지점" 규칙을 트리거로 옮기려고 파견 발령 코드를 보니, `assignStaff`가 담당 회원(`assignedStaffId`)과 강사 프로필을 정리하지 않는다. 직원이 이동하는 순간 규칙이 조용히 깨지는 구조라, 트리거를 먼저 걸면 파견 자체가 막힌다. 정책을 먼저 정하기로 했다(DI-02, 권장 A: 파견 트랜잭션에서 담당 관계 정리). 수단도 확인했다 — SQL로만 넣은 복합 FK는 `prisma migrate diff`가 DROP을 생성해 지워지므로 트리거만 현실적이다.

**③에서 바뀐 설계와 발견**: 채번 헬퍼를 ADR-STF-02 문구대로("시퀀스 행 `FOR UPDATE`") 만들려다가, prefix의 **첫 채번**(새 지점·새해 memberNo)에는 잠글 행이 없어 ADR-RSV-01이 논파한 팬텀 삽입과 똑같이 뚫린다는 걸 알아챘다. `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 한 문장으로 바꿔 동시 20건 채번을 1~20 무중복으로 확인했다. 테스트를 쓰다가 시드가 `SEOCHO-001/002`를 번호째 넣어 헬퍼의 첫 번호와 충돌한다는 것도 발견해 시드에 시퀀스 초기화를 넣었다. 시퀀스 행을 지우면 테스트가 실패하는 것까지 확인했다. 실데이터 이관 때도 같은 초기화가 필요하다고 체크리스트에 적었다. 회차 행 락은 정원 2 신규 회차에 5명 동시 요청으로 검증했다(락 있음 → 정확히 2건, 대조군 락 없음 → 초과).

**검증**: `integrity-helpers.spec.ts` 5건 신규, 전체 256 통과(251 + 5, D26 skip 3건 유지), lint 0 에러, 빌드 성공. `migrate dev`가 CHECK를 지우지 않는 것(빈 마이그레이션) 확인. Supabase는 적용 전 지문 일치(데이터 0행)를 확인하고 적용했다. 적용 후 제약 지문이 어긋나 당황했는데, md5 하나만 보고 판단하지 않고 91개 제약을 이름별 해시로 뽑아 대조하니 차이는 로컬 비교 DB에만 있는 `_prisma_migrations_pkey`뿐이었다. 지문 쿼리의 결함이었지 스키마 차이가 아니었다.
