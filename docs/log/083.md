# 083. 회원 웹 조회·예약 — 실제 api 연동 확인, 예약·모의 결제·취소 화면 (2026-10-08)

> [진행 로그 인덱스](README.md)

**계기**: 브리프 B1-2. B1-1([077](077.md))은 로그인·토큰 갱신을 모의 api로만 확인했다. 회원이 휴대폰(360px)에서 프로그램 목록 → 회차 → 예약 → 모의 결제 → 내 예약·취소를 끝까지 하게 한다.

**한 일**

1. **실제 연동 확인(로컬 PG16 + api)**. 로그인, 새로고침 시 세션 복원(`refresh` → `me`), 로그아웃(서버에서 refresh token 폐기를 DB로 확인)이 동작했다. 어긋난 곳은 1건이었다.
   - 라우터 basename이 `/m`이었다. 그래서 로그인 뒤 주소가 `/m`(끝 슬래시 없음)이 됐다. 이 주소를 새로고침하면 vite 개발 서버는 404를 냈다. Worker에서는 `/m/*` 규칙(D41 결정 2) 밖이라 관리자 웹으로 갈 수 있다. basename을 `/m/`로 바꿨다.
2. **화면 결정(사용자, 2026-10-08)** — 도메인 규칙과 상관없는 화면 결정이라 D 번호 없이 여기에만 남긴다.

   | 질문 | 답 |
   |---|---|
   | 화면 구성 | 하단 탭(홈·예약하기·내 예약). B1-3에서 탭을 더한다 |
   | 결제 시점 | **예약 직후에만**. 내 예약에는 결제 버튼이 없다 |
   | 취소 확인 | 하단 시트 모달 |

   - 결제 시점 결정의 결과: 결제 화면을 벗어나면 그 예약은 "결제 대기"로 남는다. 결제 미완료 자동취소는 범위 제외다(예약및결제 A-8). 회원이 할 수 있는 일은 취소뿐이다. 결제 화면 주소(`/m/pay/:id`)를 새로고침하면 결제를 이어 할 수 있다.
3. **화면 구현(기존 API만, 새 API 없음)**: `ProgramsPage`, `ProgramSlotsPage`, `PaymentPage`, `MyReservationsPage`를 만들었다. 공통 부품은 `BottomSheet`, `StatusBadge`, `lib/use-load.ts`(화면 진입 때 GET 1회), `lib/errors.ts`, `lib/format.ts`다.
   - 회차 예약을 받는 것은 `PAID_SESSION`뿐이다. 자유이용·PT는 "예약 없이 이용"으로 따로 보여 준다.
   - 지난 회차는 화면에서 거른다(아래 알려진 문제).
4. **오류 처리**: 공통 에러 포맷의 `error.code`로 문구를 고른다. 서버 message는 관리자 기준 문장이라 모르는 code일 때만 쓴다.
   - 계약 종료 `BRANCH_TERMINATED`, 정원 초과 `SLOT_FULL`(남은 자리를 다시 받는다), 이미 예약 `ALREADY_RESERVED`, `PAYMENT_NOT_PENDING`, Worker의 `RATE_LIMITED`·`SERVER_BUSY`, 네트워크 끊김을 다룬다.
   - **취소 마감**은 api 오류가 없다. 마감 이내 취소도 성공하고 환불만 하지 않는다(예약및결제 A-6). 그래서 취소 시트가 미리 "환불되지 않습니다"를 알린다. 결과 안내는 응답의 결제 상태(`REFUNDED`/`APPROVED`)로 정한다.
   - 마감 시간은 지점 설정(`cancellationDeadlineHours`)을 부르지 않고 24시간으로 안내한다. 시드 83곳이 모두 24이고, 호출 1회를 아낀다. 실제 판정은 서버가 한다.
   - **토큰 만료 후 재시도 실패**: 사용 중 refresh가 실패하거나, 시작할 때 저장된 토큰이 401이면 로그인 화면에 "로그인이 만료됐습니다"를 띄운다.

**근거**: D40·D41(같은 Worker `/m/`, 토큰 보관), 예약및결제 불변식 ③(TERMINATED 409)·④(금액은 서버가 정함 — 화면은 금액을 보내지 않는다), A-6(취소·환불), design-constants ⑩(방문당 약 10회, 가정).

**요청 수(실측, 로컬 프로덕션 빌드 `vite preview`)**

| 화면 | 호출 |
|---|---|
| 로그인 → 홈 | 1 (`POST /auth/login`). 홈은 부르지 않는다 |
| 다시 방문(저장된 세션) | 2 (`refresh`, `me`) |
| 예약하기(프로그램 목록) | 1 |
| 회차 | 1 (프로그램 정보는 목록이 넘겨 준다. 주소로 바로 들어오면 +1) |
| 예약 | 1 (정원 초과면 회차 다시 받기 +1) |
| 결제 | 1 (주소로 바로 들어오면 내 예약 +1) |
| 내 예약 | 1 |
| 취소 | 1 (응답으로 목록을 고치고 다시 부르지 않는다) |
| **한 방문(로그인 → 예약 → 결제 → 내 예약 → 취소)** | **7** |

- 개발 서버에서는 조회가 2번씩 찍힌다. React StrictMode가 effect를 두 번 돌리기 때문이고, 프로덕션 빌드에서는 1번이다.
- ⑩을 실측값으로 바꾸는 일은 배포 후 B1-4에서 한다. 혼잡도·공지가 B1-3에서 더해진다.

**알려진 문제**

- **시드 회차가 지난 날짜다**(서초 요가 2026-09-21·22). 로컬 확인은 BRANCH_ADMIN으로 미래 회차를 만들어 했다. 배포 DB에도 미래 회차가 없으면 시연 전에 만들어야 한다. 이는 배포 DB 쓰기라 사용자 승인이 필요하다.
- **api `POST /reservations`가 지난 회차 예약을 막지 않는다.** 화면은 지난 회차를 보여 주지 않지만, api를 직접 부르면 예약된다. 고칠지는 별도로 판단한다.
- refresh token이 다른 세션에서 rotate되면, 이 기기는 다음 401에서 로그인 화면으로 간다. 의도한 동작이다(D41 감수).

**검증**

- member-web: lint 경고 0, `npm run build:web`(admin → member) 성공.
- 커밋 전 hook으로 api jest 전체를 통과했다(api는 바꾸지 않았다).
- 360px Playwright: 실제 api와 로컬 DB로 아래를 확인했다. 스크린샷은 세션 scratchpad에만 있고 저장소에는 넣지 않았다.
  - 로그인 → 프로그램 → 회차 → 예약 → 결제 → 내 예약 → 취소(환불·환불 불가 안내 모두)
  - 오류 화면 4종(이미 예약, 정원 초과, 계약 종료, 세션 만료)
- 자동 테스트는 없다. 화면 동작은 **"검증되지 않음(수동 확인)"**이다.
- Worker(`wrangler dev`) 경유로는 확인하지 않았다(B1-4).
- 로컬 주의: jest가 기준 DB(`sports_erp`)를 템플릿으로 복제한다. 그래서 수동 확인용 api는 복사본 DB(`sports_erp_dev`)로 띄워야 한다. 기준 DB에 수동 로그인 기록이 남으면 `auth-refresh-token.spec`이 실패한다.
