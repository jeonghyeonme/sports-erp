## 057. 회원 앱을 범위에서 뺀 이유를 기록했다 — 무료 한도를 넘어 인프라를 더 붙여야 해서 (2026-10-05)

**계기**: 발표자료에 회원 앱을 뺀 이유를 쓰려고 기록을 찾았다. [052](2026-W40.md#052)와 D37 §5에는 "웹에 집중한다(사용자 결정)"만 있고 이유가 없었다. 사용자에게 확인했다.

**이유(사용자 확인)**: 무료 한도·비용 문제다.
- 회원 앱을 붙이면 하루 API 요청이 약 19.6만 건이다(design-constants ⑬, 계산). Cloudflare Workers 무료 한도(10만/일)를 넘는다. 월 Lambda 요청도 약 590만 건으로 무료 한도(100만/월)를 넘는다(D37 결정 2).
- 이걸 감당하려면 유료 전환이나 다른 인프라를 추가로 구성해 지금 인프라와 연결해야 한다. 그러면 개발 범위가 너무 넓어진다. 그래서 회원 앱을 보류했다.
- 처리 성능은 문제로 보지 않았다. 계산상 필요한 동시 실행은 약 1.3건이고, 상한 10이면 처리 한계는 200 rps다(D37 §1).

**근거**: D37 §1·결정 2·§5, design-constants ⑩~⑬. 숫자는 로컬 실측에 가정을 얹은 계산이다. 세션당 요청 10건(⑩)은 약한 가정이다. Lambda 위 k6 실측은 아직 없다(`loadtest/k6-lambda.js`는 작성만 됨).

**검증**: 기록만 추가했다(코드 변경 없음).

**커밋**: 이 파일과 `docs/log/README.md` 한 줄.

## 059. Lambda로 운영을 옮겼다 — Worker 경유 로그인·조회 확인, 종합 발표 덱 반영 (2026-10-05)

**계기**: 종합 발표 덱을 검토하던 사용자가 현황을 알려 줬다.
- Worker가 Lambda를 가리키도록 전환했고, Worker로 접속해 로그인과 데이터 조회까지 확인했다.
- DB와 API 사이의 헬스체크는 따로 하지 않았다. 배포 워크플로의 헬스체크는 DB를 거치지 않는 고정 응답이다([056](2026-W40.md#056)).

**한 일**:
- STATUS를 "Lambda로 운영 전환"으로 갱신했다. 남은 일은 k6 재측정과 Render 정리다.
- 덱을 고쳤다([4-5 구성안](../presentation/4-5_종합발표_슬라이드구성.md)).
  - 구성도·진화·스택·주간 슬라이드의 Lambda 상태를 "첫 배포"에서 "운영 전환"으로 바꿨다.
  - Render 문제와 Lambda 전환 방침은 4주차 발표에서 이미 다뤘다. 그래서 9/30 배포 점검 슬라이드를 뺐고, Lambda 슬라이드는 "예고한 전환을 이렇게 설계했다"로 바꿨다.
  - 요구사항 조정 슬라이드에서 결정 번호 표기를 뺐다. 발표자만 아는 정보라서다.
  - AI 검증 슬라이드 뒤에 문서 구조 슬라이드를 추가했다(읽는 시점별 3계층).
  - 사용자가 편집기에서 한 편집 6건은 생성기에도 반영했다: 숫자 슬라이드 삭제, 연결 띠 3개 삭제, 마무리 문장 삭제, 남은 것 배너 삭제.

**근거**: D37, D38, 사용자 확인(10/5).

**검증**: 생성기 린트 통과, doc-check 통과. Lambda 동작은 사용자가 브라우저로 확인한 것이다. 이 세션에서는 확인하지 않았다(네트워크 정책상 접속 불가). 부하 상황은 **검증되지 않음**. 게시한 덱의 렌더 결과는 확인하지 않았다.

**커밋**: STATUS, 이 파일, 4-5 구성안, deck-source(생성기·결과 스냅샷).

### 2. refreshToken 정리 — [권한관리](../domains/권한관리.md) ADR-AUTH-04

- **문제**: 로그인·갱신·가입 직후 발급할 때마다 행이 하나씩 생기는데, 폐기만 하고 지우지 않았다.
- **고친 것**: `auth.service.ts`의 `issuePrismaRefreshToken`에서 발급 전에 그 계정의 만료·폐기 토큰을 `deleteMany`로 지운다. 폐기된 토큰을 다시 쓰려 하면 행이 없으므로 여전히 401이다.
- **테스트**: `test/auth-refresh-token.spec.ts`를 새로 만들었다.
  - 회전: 새 토큰이 발급되고, 쓴 토큰을 다시 쓰면 401
  - 정리: 그 계정의 만료·폐기 행만 지우고, 살아 있는 세션과 다른 계정 행은 남긴다
  - 로그아웃한 토큰은 다음 발급 때 지워지고, 다시 쓰면 401
  - 수정 전 코드에서는 정리 테스트 2건이 실패하는 것을 확인했다.
- **문서·코드 불일치 발견**: 권한관리 §11은 AUTH-T02(rotate)를 "자동+수동 테스트 통과(2026-09-28)"라고 적었다. 그런데 `/auth/refresh`를 부르는 자동 테스트 파일이 없었다. 이번 spec으로 메웠고 §11에 그 사실을 적었다.

### 3. 배포 DB 기존 행 정리 — **사용자 승인 대기**

배포 DB에는 k6로 약 1.2만 행이 쌓였다. 만료·폐기되지 않은 행이 대부분이라 위 코드만으로는 바로 줄지 않는다. 아래 SQL을 로컬 DB에서 트랜잭션 안에서 돌려 보고 롤백해서 확인했다. 확인 내용: 계정당 최신 5개만 남고, 만료 행은 지워진다.

```sql
-- 확인
SELECT count(*) AS total,
       count(*) FILTER (WHERE "expiresAt" < now() OR "revokedAt" IS NOT NULL) AS dead
FROM "RefreshToken";
SELECT "accountId", count(*) FROM "RefreshToken" GROUP BY 1 ORDER BY 2 DESC LIMIT 5;

-- 정리(한 트랜잭션): 만료·폐기 행 삭제 → 계정마다 최신 5개만 남김
BEGIN;
DELETE FROM "RefreshToken" WHERE "expiresAt" < now() OR "revokedAt" IS NOT NULL;
DELETE FROM "RefreshToken" r USING (
  SELECT id FROM (SELECT id, row_number() OVER (PARTITION BY "accountId" ORDER BY "createdAt" DESC) AS rn
                  FROM "RefreshToken") t WHERE rn > 5
) old WHERE r.id = old.id;
SELECT count(*) FROM "RefreshToken";
COMMIT;
```

영향: 계정마다 최근 5개보다 오래된 기기 세션은 다시 로그인해야 한다.

## 074. 지점 83곳 축소 — 시드·테스트·관리자 웹 문구, 배포 DB에서 지방 15곳 삭제 (2026-10-06)

**계기**: D40 결정 1(수도권 83곳)은 덱·문서·산출물에만 반영돼 있었고 시드·테스트·관리자 웹은 98곳 그대로였다. 사용자가 코드 반영을 요청했다.

**구현 방식 — 지방 차례를 건너뛴다**
- 대안 A: `branch-generator.ts`의 `AREAS`에서 지방 6개 지역을 지운다. 목록은 깔끔하지만 `i % AREAS.length`가 바뀌어 뒤 차례 지점의 id·이름·직원·회원이 전부 밀린다. 배포 DB와 82곳이 어긋나 "15곳만 지우기"가 불가능해진다.
- 대안 B(채택): 목록은 두고 `TARGET_REGIONS`(서울·경기·인천)가 아닌 차례만 `continue`한다. 남는 지점의 id·데이터가 98곳 시절과 같아서, 배포 DB에서는 정확히 15곳만 지우면 된다.
- 결과: 83곳(서울 71·경기 9·인천 3), 상태 ACTIVE 71 / RENEWAL_DUE 5 / EXPIRED 4 / TERMINATED 3. [기업구조및관리시스템분석](../reference/기업구조및관리시스템분석.md) §2-2의 수치와 같다. TERMINATED 3곳(계약 종료 테스트 대상)은 그대로 남는다.
- 빠지는 지점: `branch-gen-` 022·023·025·026·027 / 052·053·055·056·057 / 082·083·085·086·087 (부산·대구·대전·광주·울산 × 3)

**바뀐 것**
- `branch-generator.ts`(건너뛰기), 시드·픽스처 주석 98→83, 96→81
- 테스트 기대값 2건 — 시드 규모를 세는 값이고 격리·계약·인사 규칙 테스트는 아니다: `branch-parity` 98→83, `catalog-flow` 시설 수 99→84(히어로 3 + 생성 81)
- 관리자 웹 안내 문구·주석 "98개 지점 규모" → "83개"(회원·직원·프로그램·시설 화면, 대시보드 "서울/경기/부산" → "서울/경기/인천")

**검증**: 로컬 기준 DB를 새로 만들어(마이그레이션 → 시드) 지점 83곳 확인. api jest 28개 파일 312 passed(1 todo), api·admin-web lint·빌드 통과.

### 배포 DB 삭제 — 사용자 승인 후 실행

시드는 upsert만 하므로 배포 DB(Supabase)의 15곳은 SQL로 지워야 한다. FK를 확인한 결과 두 가지를 조심해야 한다.
- **RESTRICT**: 결제·예약·수강·PT·회차가 지점 행 삭제를 막는다 → 자식부터 지운다.
- **SET NULL**: `Post.branchId`·`Document.branchId`는 지점이 지워지면 null이 된다. 그러면 지방 지점 공지가 **전 지점 공지로 바뀌어 보인다** → 직접 지운다.

**로컬 검증**: 98곳 시드 DB에 아래 SQL을 적용한 뒤, 83곳으로 새로 시드한 DB와 모든 테이블의 행 수·id 지문을 비교했다. 차이는 시드가 매번 무작위 UUID를 붙이는 서초 행 2개(혼잡도 스냅샷·체크인, 내용은 같음)뿐이었다. 같은 SQL을 다시 실행하면 안전장치(15곳·비수도권 확인)에 걸려 전체가 롤백된다.
변화: 지점 98→83, 계정 197→170, 직원 195→168, 회원 193→169, 프로그램 149→128, 시설 99→84, 강사 97→82.

배포 DB에는 시드 밖의 데이터(사용 중 생긴 예약·게시글 등)가 있을 수 있다. 실행 전에 15곳에 딸린 행 수를 읽기 전용으로 먼저 보고한다.

```sql
-- D40 — 비수도권 지점 15곳과 딸린 데이터 삭제. 한 트랜잭션, 실패하면 전부 롤백.
BEGIN;

CREATE TEMP TABLE gone_branch ON COMMIT DROP AS
SELECT id FROM "Branch" WHERE id IN (
  'branch-gen-022','branch-gen-023','branch-gen-025','branch-gen-026','branch-gen-027',
  'branch-gen-052','branch-gen-053','branch-gen-055','branch-gen-056','branch-gen-057',
  'branch-gen-082','branch-gen-083','branch-gen-085','branch-gen-086','branch-gen-087');
-- 안전장치: 지울 지점이 정확히 15곳이고 전부 비수도권이어야 한다
DO $$ BEGIN
  IF (SELECT count(*) FROM gone_branch) <> 15
     OR EXISTS (SELECT 1 FROM "Branch" b JOIN gone_branch g ON g.id = b.id WHERE b.region IN ('서울','경기','인천'))
  THEN RAISE EXCEPTION 'gone_branch 검증 실패'; END IF;
END $$;

CREATE TEMP TABLE gone_member  ON COMMIT DROP AS SELECT id, "accountId" FROM "Member"  WHERE "branchId" IN (SELECT id FROM gone_branch);
CREATE TEMP TABLE gone_staff   ON COMMIT DROP AS SELECT id, "accountId" FROM "Staff"   WHERE "branchId" IN (SELECT id FROM gone_branch);
CREATE TEMP TABLE gone_program ON COMMIT DROP AS SELECT id FROM "Program" WHERE "branchId" IN (SELECT id FROM gone_branch);

-- 결제·예약(RESTRICT 경로): 그 지점 회원의 것 + 그 지점 회차에 걸린 것
DELETE FROM "Payment" WHERE "memberId" IN (SELECT id FROM gone_member)
   OR "reservationId" IN (SELECT r.id FROM "Reservation" r JOIN "ScheduleSlot" s ON s.id = r."scheduleSlotId"
                          WHERE s."programId" IN (SELECT id FROM gone_program));
DELETE FROM "Reservation" WHERE "memberId" IN (SELECT id FROM gone_member)
   OR "scheduleSlotId" IN (SELECT id FROM "ScheduleSlot" WHERE "programId" IN (SELECT id FROM gone_program));
DELETE FROM "CourseEnrollment" WHERE "programId" IN (SELECT id FROM gone_program) OR "memberId" IN (SELECT id FROM gone_member);
DELETE FROM "PTSession"        WHERE "programId" IN (SELECT id FROM gone_program) OR "memberId" IN (SELECT id FROM gone_member);

DELETE FROM "Member"  WHERE id IN (SELECT id FROM gone_member);        -- 체크인 등 CASCADE
DELETE FROM "Program" WHERE id IN (SELECT id FROM gone_program);       -- 회차·템플릿 CASCADE
DELETE FROM "Instructor" WHERE "branchId" IN (SELECT id FROM gone_branch);
DELETE FROM "Facility"   WHERE "branchId" IN (SELECT id FROM gone_branch); -- 혼잡도·체크인 CASCADE

-- SET NULL이면 전 지점 공지·본사 문서로 바뀌어 보이므로 직접 지운다
DELETE FROM "Post"     WHERE "branchId" IN (SELECT id FROM gone_branch);   -- 첨부·읽음 CASCADE
DELETE FROM "Document" WHERE "branchId" IN (SELECT id FROM gone_branch);

DELETE FROM "Asset"            WHERE "branchId" IN (SELECT id FROM gone_branch);
DELETE FROM "AttendanceRecord" WHERE "branchId" IN (SELECT id FROM gone_branch);
DELETE FROM "StaffAssignment"  WHERE "branchId" IN (SELECT id FROM gone_branch);
DELETE FROM "CodeSequence"     WHERE "branchId" IN (SELECT id FROM gone_branch);

-- 직원은 계정을 지우면 CASCADE(근태·휴가·업무일지·파견 이력·토큰 포함). 회원 계정도 함께 지운다
DELETE FROM "Account" WHERE id IN (SELECT "accountId" FROM gone_staff)
   OR id IN (SELECT "accountId" FROM gone_member WHERE "accountId" IS NOT NULL);
DELETE FROM "Staff" WHERE id IN (SELECT id FROM gone_staff);           -- 계정 없는 직원이 있으면

DELETE FROM "Branch" WHERE id IN (SELECT id FROM gone_branch);

COMMIT;
```

### 배포 DB 실행 결과

- **실행 전 확인**(읽기 전용): 지점 98 · 계정 197. 지울 15곳은 모두 비수도권이었고, 딸린 데이터는 회원 24(계정 연결 0) · 직원 27 · 프로그램 21 · 시설 15뿐이었다. 회차·예약·결제·게시글·문서·자산·근태는 0건으로, 운영 중에 생긴 데이터는 없었다. 로컬 검증 상태와 같다.
- **1차 시도(Claude, Supabase 연결)**: 위 SQL을 한 문장짜리 DO 블록으로 바꿔 보냈으나 60초 시간 초과로 끊겼다. 직후 연결이 인증 오류(Unauthorized)로 막혀 확인할 수 없었다. 사용자가 대시보드에서 조회해 보니 98 / 197로, 반영되지 않았다. DO 블록은 한 문장이라 일부만 반영되는 일은 없다.
- **2차(사용자, SQL Editor)**: 같은 DO 블록을 사용자가 직접 실행했다. 결과는 **지점 83 · 계정 170**으로 로컬 기대값과 같다.

## 077. 회원 모바일 웹 형태를 정하고(D41) 뼈대를 만들었다 — B1-1 (2026-10-07)

**계기**: [작업 브리프](../process/04_작업_브리프.md) B1-1. D40이 회원 기능을 모바일 웹으로 만들기로 했지만, 앱 형태와 Worker 배포 경로는 정하지 않았다.

**한 일**:
- 사용자가 브리프의 A/B/C안 중 **B안(`apps/member-web` 별도 앱, 같은 Worker)**과 **refresh token을 localStorage에 두는 방식**을 골랐다. → [D41](../decisions/D41.md)
- `wrangler dev`로 `/m/*` 새로고침을 먼저 시험했다(가짜 자산 폴더 + scratch 설정). 결과는 아래 표와 같다.
  - Worker 코드에 임시 로그를 넣어 Worker를 거치는 요청만 셌다. `/members`, `/m/`, `/m/assets/*`는 Worker를 거치지 않았다. `/m/login`, `/m/favicon.svg`는 Worker를 거쳤다.
  - 처음 설정(`!/m/assets/*`만 제외)에서는 회원 웹에 들어올 때마다 Worker를 1회 거쳤다. design-constants ⑬(하루 9.3만 건, 한도 10만)에 83곳 × 100명 = 하루 약 0.83만 건이 더해져 한도를 넘는다(계산). 그래서 `!/m/`를 추가해 진입 경로는 자산 계층이 바로 처리하게 했다.

| 경로(navigate 요청) | 결과 | Worker 경유 |
|---|---|---|
| `/`, `/members/abc` | 관리자 `index.html` | 아니오 |
| `/m` | 307 → `/m/` | 아니오 |
| `/m/` | 회원 `index.html` | 아니오(`!/m/`) |
| `/m/login`, `/m/reservations/123` | 회원 `index.html` | 예 |
| `/m/assets/*.js` | 파일 그대로 | 아니오 |
| `/api/v1/*` | 프록시(시험에서는 origin이 없어 502) | 예 |

## 079. Worker 로그인 rate limit 429 실동작 확인 — 연결을 재사용할 때만 걸린다 (2026-10-07)

**계기**: [log/033](2026-W39.md#033)에서 Worker를 배포한 뒤로 rate limit(로그인·회원가입·연동, IP+경로 기준 60초당 10회)이 실제로 429를 내는지 확인하지 않았다(브리프 B3).

**한 일**: 사용자 PC(로컬 데스크톱 세션, 네트워크 제약 없음)에서 배포된 Worker `https://sports-erp-api-gateway.01-beauty-minimal.workers.dev/api/v1/auth/login`에 `{"email":"x","password":"x"}`로 POST를 반복했다. 가짜 계정이라 origin(Lambda)은 400 `VALIDATION_ERROR`를 돌려준다. 배포된 Worker 코드가 저장소 `cloudflare-worker/src/index.ts`와 같은 것은 Cloudflare 커넥터(`workers_get_worker_code`)로 확인했다.

| 실행 (UTC) | 방식 | 결과 |
|---|---|---|
| 10:24:08~15 | 요청마다 새 연결(README의 curl 반복), 12회 | 12회 모두 400 |
| 10:43:14~42 | 요청마다 새 연결, 30회 | 30회 모두 400. CF-Ray 로케이션은 HKG 약 20회, NRT 약 10회 |
| 10:51:34~37 | 연결 하나 재사용(`curl --next`), 15회 | 1~11번째 400, **12~15번째 429**. 바로 뒤 새 연결 1회는 400 |
| 10:51:48~51 | 연결 하나 재사용, 14회(앞 실행 14초 뒤) | 1~11번째 400, **12~14번째 429**. 카운트가 0부터 다시 시작했다 |

429 응답(HKG):

```
HTTP/1.1 429 Too Many Requests
Content-Type: application/json

{"success":false,"error":{"code":"RATE_LIMITED","message":"요청이 너무 잦습니다. 잠시 후 다시 시도하세요."}}
```

`Retry-After` 헤더는 없다(503 `SERVER_BUSY`에는 있다).

**해석**
- 바인딩은 동작한다. 공통 에러 포맷으로 429를 낸다. 다만 걸리는 시점은 11번째가 아니라 12번째였다.
- 요청마다 새 연결을 열면 같은 로케이션(HKG)에서 60초 안에 20회를 보내도 걸리지 않았다. Cloudflare 문서(Workers Rate Limiting "Locality"·"Accuracy")는 카운터가 Worker가 도는 머신에 캐시되고 같은 로케이션의 저장소와 비동기로 맞춰지며, 이 API가 "permissive, eventually consistent"라서 정확한 집계용이 아니라고 한다. 새 연결이 다른 머신에 떨어져 카운트가 합쳐지지 않은 것으로 **추정**한다. Cloudflare 내부 동작은 확인하지 못했다.
- 그래서 연결을 재사용하는 클라이언트(브라우저, 단순 스크립트)에는 제한이 걸리고, 요청마다 연결을 새로 여는 클라이언트는 사실상 제한을 피한다. 그때는 Lambda 동시 실행 상한 10과 503 `SERVER_BUSY`([D37](../decisions/D37.md))가 2차 방어가 된다. 그 사이 bcrypt 부하는 Lambda가 받는다.

**결정**: 사용자가 A안을 골랐다. Worker 코드는 그대로 두고 한계를 기록한다. 검토한 다른 안은 B(Durable Object로 IP별 전역 카운터 — 새 Cloudflare 서비스 도입, 로그인마다 호출 하나가 더 생겨 지연과 무료 한도 소모)와 C(API에서 이메일 기준 시도 횟수 제한 — Lambda는 메모리를 공유하지 않아 DB 저장, 스키마 변경 필요)다. 둘 다 구현하지 않았다.

**검증**: 위 실측이 전부다. 고친 README "동작 확인" 명령도 그대로 한 번 실행해 1~11번째 400, 12~14번째 429를 다시 확인했다. 코드는 바꾸지 않았다. `node scripts/doc-check.mjs`는 커밋 전에 실행했다.

**커밋**: 이 로그와 인덱스 한 줄, STATUS(B3 삭제, 열린 위험 추가), 작업 브리프(B3 삭제), `cloudflare-worker/README.md` "동작 확인"(연결 재사용 명령과 한계).

**한 일**

1. **실제 연동 확인(로컬 PG16 + api)**. 로그인, 새로고침 시 세션 복원(`refresh` → `me`), 로그아웃(서버에서 refresh token 폐기를 DB로 확인)이 동작했다. 어긋난 곳은 1건이었다.

   | 취소 확인 | 하단 시트 모달 |

| 방문 유형 | api 호출 | Worker 호출 |

**하지 못한 것**

  npx wrangler deploy

- **회원 가입·연동 화면**: B1 범위에 없었다. API(`POST /members/register`·`/members/link`)만 있다. 지금 회원 웹은 이미 계정이 있는 회원만 로그인할 수 있다.
- 덱의 `req-shot-member` 캡처 갱신: 보호 영역이라 요청이 있을 때만 한다.

## 087. admin-web 공통 Toast — 쓰기 성공은 Toast, 오류는 인라인 (2026-10-08)

**계기**: 브리프 B5-3. 요구사항추적표 §2-3에서 RFP 1-2 #4·#5(온라인도움말·상호작용메시지)가 "Modal만 있고 Toast가 없다"로 남아 있었다. 조사해 보니 상황은 이랬다.
- admin-web의 쓰기 34곳은 성공해도 아무 알림이 없었다. 모달이 닫히거나 목록이 새로 그려질 뿐이었다.
- 오류는 화면마다 인라인 `forbidden-note`로 보였다.
- 프로그램 휴강·종료의 영향 예약 안내(ADR-PRG-02)만 `window.alert`였다.

**사용자 결정(2026-10-08)**

| 질문 | 답 |
|---|---|
| Toast 범위 | 성공은 Toast, 오류는 인라인을 유지한다. 인라인으로 보일 자리가 없는 쓰기 오류만 error Toast로 보인다 |
| 영향 예약 `window.alert` | 닫을 때까지 남는 경고 Toast로 바꾼다 |

- 화면 패턴 결정이라 D 번호를 쓰지 않았다. 규칙은 [디자인시스템](../design/디자인시스템.md) §5에 둔다.

**한 일**

1. **부품**: `lib/use-toast.ts`(context·`useToast`)와 `components/ToastProvider.tsx`(Provider·화면 오른쪽 아래 표시). 둘을 파일로 나눈 것은 react-refresh lint 규칙 때문이다.
   - 성공은 3초, 오류는 6초 뒤 닫힌다. 경고는 자동으로 닫히지 않는다. 최근 3개까지만 쌓는다.
   - 성공은 `role=status`, 오류·경고는 `role=alert`로 스크린리더에 알린다.
2. **적용**: 12개 화면의 쓰기 34곳 전부에 성공 Toast를 붙였다. 대상 이름을 넣은 완료형 문구다.
   - 인라인으로 보일 자리가 없던 오류 3곳은 error Toast로 보인다: 예약 취소, 체크인, 강사 재활성화. 셋 다 그전에는 실패해도 아무것도 보이지 않았다.
3. **ADR-PRG-02 안내**: `window.alert`를 경고 Toast로 바꿨다.
   - 함께 고친 결함: 예전 alert는 휴강·종료뿐 아니라 **진행중으로 되돌릴 때도** "직접 안내해 주세요"를 띄웠다. api가 어떤 전이에서든 건수를 주기 때문이다. 이제 PAUSED·ENDED일 때만 안내한다.
4. **문서**: 디자인시스템 §5 "알림" 규칙(언제 Toast, 언제 인라인), 요구사항추적표 §2-3·§3, 브리프에서 B5 절 삭제, STATUS.

**남긴 것**

## 088. 쌓이는 목록 페이지네이션 — 회원·예약·결제·자산, 결제 날짜 필터를 DB 조건으로 (2026-10-09)

**계기**: 브리프 B8. D43이 정한 대로 쌓이는 목록 4개에 offset 페이지네이션을 넣는다. 결제 목록의 메모리 날짜 필터는 DB 조건으로 내린다(ADR-RSV-04). D43이 "B8에서 정한다"고 남긴 화면 결정을 사용자에게 받았다.

**사용자 결정(2026-10-09)**

| 질문 | 답 |
|---|---|
| 회원·자산 목록 화면 | 지점별 아코디언 → **표 하나 + 지점 필터(본사만) + 검색·상태 필터 + 쪽 넘김** |
| 지점 상세의 직원별 회원 | 회원 전체를 받지 않고 **직원을 펼칠 때 그 직원 회원만**(`assignedStaffId` 필터, `none` = 미배정) |
| 예약·결제 정렬 | **최근 것부터**(D43 결정 2의 미결) |
| 자산 폐기 | **기본 목록에서 빼고** `status=DISPOSED`로 따로(D43 결정 4의 미결) |

- 모두 D43 안의 미결 항목을 채운 것이어서 새 D 번호는 쓰지 않았다. D43 파일은 고치지 않고(D38) 인덱스 상태만 "구현"으로 바꿨다.

**한 일**

1. **api**
   - 공통 `common/http/pagination.ts`의 `parsePage`·`pageMeta`: `page`·`limit`, 기본 20, 상한 100. 잘못된 값은 1·20으로 바꾼다.
   - 4개 서비스의 `list`가 `{ items, total }`를 돌려주고 `count` + `skip/take`를 쓴다. 정렬에는 `id`를 덧붙여 쪽 경계가 흔들리지 않게 했다.
   - 회원: `assignedStaffId` 필터를 더했다(새 라우트가 아니라 기존 라우트의 쿼리다. 지점 범위는 BranchScopeGuard가 그대로 강제한다).
   - 자산: 상태를 지정하지 않으면 DISPOSED를 뺀다.
   - 예약·결제: `createdAt desc`로 정렬한다.
   - 결제 날짜 필터: `kstDayRange`(kst-date.ts에 새로 추가)로 KST 하루 경계를 만들어 `approvedAt` 범위 조건으로 넣었다.
     - 미승인 건은 `approvedAt IS NULL OR 범위`로 예전처럼 남는다.
     - 형식이 틀린 날짜는 빈 목록을 준다. 예전에는 문자열 비교라 결과가 이상했다.
2. **admin-web**
   - 공통: `useApiPage`(쪽 + total, 쪽을 넘길 때 이전 데이터 유지), `Pager`, `BranchFilter`.
   - 회원: 지점·상태·검색(이름·회원번호·전화, 제출할 때) 필터를 서버 조건으로 바꿨다.
   - 자산: 지점과 상태 칩("보유 중(폐기 제외)"이 기본)을 쓴다.
   - 예약 관리의 목록 3개와 회원 상세 예약 탭에 쪽 넘김을 붙였다. 역할에 맞는 목록만 부른다(예전에는 세 목록을 다 불렀다).
   - 지점 상세
     - 직원을 펼칠 때만 그 직원 회원 쪽을 부른다. "담당 없음"은 `none`으로 부른다.
     - 미처리 자산 수는 자산 기본 목록의 total이다(`limit=1`, ADR-RES-01).
3. **member-web**
   - 내 예약은 `limit=100`(상한)으로 한 번에 받는다. 100건을 넘으면 "최근 100건만" 안내를 보인다.
   - 결제 화면이 예약을 다시 찾을 때는 첫 쪽만 본다. 최근 것부터 오므로 방금 만든 예약이 첫 쪽에 있다.

**`Payment(approvedAt)` 인덱스는 넣지 않았다**(스키마 변경, 승인 대상)
- 이제 비용은 쪽 크기와 지점 범위 조인에 묶인다.
- 시드에는 결제가 없어 실측할 대상이 없다.
- 결제가 수만 건 쌓여 날짜 조회가 느려지면 다시 본다.

**근거**: D43, ADR-RSV-04, ADR-BRD-02(같은 형식), D32 결정 5(KST), ADR-RES-01, ADR-MEM-04(목록 마스킹 유지).

**검증**

    - 예약 최근 것부터
    - 결제 KST 00:30 승인 건이 그 날짜로 걸림·미승인 건 포함·전날 대조군·최근 결제부터·형식 오류는 빈 목록
  - `kst-date.spec`에 경계 2건을 더했다.
  - `branch-isolation`의 기존 케이스는 그대로 통과했다(지점 범위 변경 없음).

**배포 순서 주의**

## 090. 인사 채용·파견·퇴사 화면 — 직원 상세 신설, 종료 지점 파견 409 (2026-10-09)

**계기**: 채용·파견·퇴사는 API만 있고 `StaffPage`는 조회만 됐다([요구사항추적표](../reference/요구사항추적표.md) §3 "API만 있는 기능의 화면" 중 가장 큰 것). 인사 권한 분리 불변식(채용·재배치=본사, 일상 관리·퇴사=지점 관리자)을 화면에서 보여 줄 근거가 없었다.

**사용자 결정(2026-10-09)**
1. 화면: 직원 상세 화면(`/staff/:id`)을 새로 만든다. 목록 행 버튼 + 모달 안은 고르지 않았다(파견 이력을 못 보여서).
2. 지점 관리자의 일상 정보 수정(`PATCH /staff/:id`)도 이번에 넣는다.
3. 채용 성공 안내에 로그인 정보(이메일 / 데모 공통 임시 비밀번호)를 보인다 — 닫을 때까지 남는 warning Toast.
4. 계약 종료 지점으로의 채용·파견 발령은 API에서도 409로 막는다 → [인사정보관리](../domains/인사정보관리.md) ADR-STF-05.

**한 일**
- **api**
  - `StaffService.hire`·`assign`: 대상 지점이 TERMINATED면 409 `BRANCH_TERMINATED`. Prisma 도메인이라 트랜잭션 안에서 지점을 읽어 판정한다. 떠나는 지점이 종료인 재배치는 허용한다.
  - `history`: 응답에 `branchName`을 붙였다. 지점 관리자는 `GET /branches`로 자기 지점만 받아, 화면이 예전 파견 지점을 `branch-gangnam` 같은 id로 보였다(Playwright에서 발견).
- **admin-web**
  - 직원 목록: 본사 "+ 직원 채용" 모달(종료 지점 제외), 재직/퇴사 탭, 행 → 상세. STAFF는 그대로 본인 정보만.
  - 직원 상세: 인적사항, 파견 이력(최근부터, 파견 중 표시), 역할별 버튼.
    - 본사: "파견 발령" 모달(현재·종료 지점 제외). 담당이 풀린 회원이 있으면 이름을 warning Toast로 남긴다(ADR-STF-04 가시화).
    - 지점 관리자(자기 지점, 재직): "정보 수정"(이름·연락처·직급·고용형태·휴무 요일, 파트타임은 휴무 요일 비활성 ATT-T05), "퇴사 처리" 확인 모달. 자기 자신의 퇴사 버튼은 숨겼다(자기 접근을 끊으므로).
  - 도움말(log/089): 직원·직원 상세 항목, `BRANCH_TERMINATED`·`EMAIL_ALREADY_EXISTS` 해결 문구.
  - 데모 비밀번호 상수를 `lib/demo-account.ts`로 옮겨 로그인 화면과 같이 쓴다.

## 091. 비밀번호 변경 화면 — 데모 계정 잠금, 불일치 400, 세션 전부 폐기 (2026-10-09)

**계기**: `PATCH /auth/password`는 있었지만 화면이 없었다([요구사항추적표](../reference/요구사항추적표.md) §3). 인사 화면(log/090)으로 채용한 직원은 데모 공통 임시 비밀번호로 시작하는데, 바꿀 방법이 없었다.

**사용자 결정(2026-10-09)** → [권한관리](../domains/권한관리.md) ADR-AUTH-05

## 093. 사용자 결정 일괄 처리 — 퇴사 시 담당 해제, env 스크립트 중단, 외래키·unique, statement_timeout (2026-10-09)

**계기**: STATUS의 "사용자 승인 대기"를 한 번에 정리했다. 사용자 결정(2026-10-09): **1A, 2A, 3 하자, 5 하자**. 4(공통 가드)·6(처리 한계)·7(비밀값 교체)은 이번에 고르지 않았다.

**결정과 한 일**
1. **퇴사 시 담당 회원 해제(1A)** → [인사정보관리](../domains/인사정보관리.md) ADR-STF-06
   - `StaffService.resign`이 같은 트랜잭션에서 담당 회원을 풀고 응답에 `unassignedMembers`를 돌려준다. 감사 기록 `after`에 `releasedMemberCount`.

2. **env 스크립트(2A, [log/056](2026-W40.md#056) 미정 표)**: `aws-lambda/set-lambda-env.sh`가 `LAMBDA_DATABASE_URL`이 6543 + `pgbouncer=true` 형식이 아니면 경고 대신 `exit 1`. log/056 6번 장애의 재발을 막는다. B(스크립트 3개 보관)는 고르지 않았다.
3. **외래키·unique(3)** — D33·D34의 숙제
   - `Document.relatedStaffId → Staff`, `Document.uploadedBy → Account`, `Post.authorId → Account`(모두 ON DELETE RESTRICT — 직원·계정은 지우지 않고 퇴사·비활성화한다), `WorkLog(staffId, date)` unique(기존 인덱스 대체). 업무일지의 앱 잠금(D33)은 그대로 둔다.
   - 마이그레이션 `20261009180000_log093_fk_worklog_unique`는 `prisma migrate diff`로 만들었다. 4개 변경 외에는 없다.
   - 적용 전 점검: 로컬 두 DB와 배포 DB 모두 고아 참조 0건, 업무일지 중복 0건(배포 DB는 읽기 전용 조회).
4. **statement_timeout(5)**: D37 결정 1의 설계값 5초를 `postgres` 역할에 건다.
   - Lambda는 Supavisor 풀러를 거쳐 `postgres` 역할로 접속한다(`pg_stat_activity`로 확인).
   - 대시보드 SQL Editor와 관리 API도 같은 역할이라 그쪽에도 5초가 걸린다. 사용자가 이를 알고 "postgres 역할에 5초"를 골랐다. 긴 작업은 그 세션에서 `SET statement_timeout = 0`으로 푼다.

**배포 DB 적용 — 커넥터는 실패, 사용자가 SQL Editor로 실행해 완료(2026-10-09)**
- 3번 마이그레이션을 Supabase 커넥터(`apply_migration`, 이어서 `execute_sql`의 단일 트랜잭션)로 두 번 시도했다. 두 번 다 60초 시간 초과였다.
- 두 번 모두 직후 조회에서 아무것도 적용되지 않았다(옛 인덱스 그대로, 새 제약 0개, 잠금 대기 0, 멈춘 세션 없음). 그래서 반쯤 적용된 상태는 없다.
- 같은 세션 작업자가 매번 재시작돼 더 시도하지 않았다. 5번도 같은 경로라 사용자 실행으로 넘긴다(log/074와 같은 방식).

실행할 SQL(Supabase → SQL Editor, 위에서 아래로 한 번에):

```sql
-- 3. log/093 외래키·unique (apps/api/prisma/migrations/20261009180000_log093_fk_worklog_unique 와 같다)
BEGIN;
DROP INDEX "WorkLog_staffId_date_idx";
CREATE INDEX "Document_relatedStaffId_idx" ON "Document"("relatedStaffId");
CREATE UNIQUE INDEX "WorkLog_staffId_date_key" ON "WorkLog"("staffId", "date");
ALTER TABLE "Post" ADD CONSTRAINT "Post_authorId_fkey" FOREIGN KEY ("authorId") REFERENCES "Account"("id") ON DELETE RESTRICT ON UPDATE CASCADE;
ALTER TABLE "Document" ADD CONSTRAINT "Document_relatedStaffId_fkey" FOREIGN KEY ("relatedStaffId") REFERENCES "Staff"("id") ON DELETE RESTRICT ON UPDATE CASCADE;
ALTER TABLE "Document" ADD CONSTRAINT "Document_uploadedBy_fkey" FOREIGN KEY ("uploadedBy") REFERENCES "Account"("id") ON DELETE RESTRICT ON UPDATE CASCADE;
COMMIT;

-- 5. D37 결정 1 — 새 연결부터 적용된다(되돌리기: ALTER ROLE postgres RESET statement_timeout;)
ALTER ROLE postgres SET statement_timeout = '5s';

-- 확인: 제약 3 + 인덱스 2가 보이고, 마지막 줄에 statement_timeout=5s
SELECT conname FROM pg_constraint WHERE conname IN ('Post_authorId_fkey','Document_relatedStaffId_fkey','Document_uploadedBy_fkey')
UNION ALL SELECT indexname FROM pg_indexes WHERE indexname IN ('WorkLog_staffId_date_key','Document_relatedStaffId_idx')
UNION ALL SELECT array_to_string(rolconfig, ',') FROM pg_roles WHERE rolname = 'postgres';
```

- **적용 확인(2026-10-09)**: 사용자가 위 SQL을 실행하고 확인 쿼리 결과를 붙였다. 커넥터로 다시 조회한 결과는 다음과 같다. 외래키 3개가 생겼고 기존 행 검사(`convalidated`)를 통과했다. 새 인덱스 2개가 생기고 옛 `WorkLog_staffId_date_idx`는 없어졌다. `postgres` 역할에 `statement_timeout=5s`가 걸렸고, 새 연결인 조회 세션의 현재 값도 5s였다.
- 순서 무관: 코드(Prisma 관계 선언)는 DB 제약이 없어도 동작한다. PR 병합(Lambda 배포)과 SQL 실행 중 무엇이 먼저여도 된다.

**검증**
- api: `staff-assignment`·`audit-log`·`hr-authority` 30건, `integrity-helpers` 13건(새 거부 4건 + 대조군 1건) 통과. 퇴사 해제 테스트는 변경 전 코드에서 실패하는 것을 확인했다. 커밋 hook에서 api jest 전체, 세 앱 lint·빌드 통과.
- 마이그레이션은 로컬 기준 DB·개발 DB에 `migrate deploy`로 적용했다. CI는 빈 DB에 전체 마이그레이션을 다시 적용한다.
- env 스크립트: `bash -n` 문법 확인과 잘못된 URL에서 `exit 1`만 확인했다. AWS 호출 부분은 실행하지 않았다(검증되지 않음).
- 퇴사 알림 화면은 자동 테스트가 없어 **검증되지 않음**.

**커밋**: `apps/api`(staff.service·schema.prisma·마이그레이션·staff-assignment·integrity-helpers spec), `apps/admin-web`(StaffDetailPage·help-content), `aws-lambda/set-lambda-env.sh`, 문서(인사정보관리 ADR-STF-06·§11, data-integrity 규칙표, aws-lambda README, STATUS).

## 095. 지점 격리 검사 중앙화 — 전역 BranchScopeGuard + `@ScopedResource` + 선언 누락 검사 (2026-10-10)

**계기**: STATUS "사용자 승인 대기"에 남아 있던 공통 가드 중앙화를 사용자가 승인했다("지점 격리 검사를 공통 가드로 모으는 작업 먼저"). QR 설치 안내는 계속 뺀다. → [D46](../decisions/D46.md)

**한 일**
- `common/guards/branch-scope.guard.ts`
  - `APP_GUARD`로 전역 등록했다.
  - 1단계: branchId 파라미터·쿼리를 검사한다(기존 동작).
  - 2단계: `@ScopedResource`가 붙은 라우트의 리소스 주인을 확인한다.
- `common/guards/scope-owners.ts`: 리소스 9종(회원·직원·프로그램·시설·강사·자산·문서·예약·휴가 신청)의 주인을 필요한 열만 읽는다. 없을 때 코드와 거부 코드는 이관 전 값을 그대로 쓴다.
- `common/decorators/scoped-resource.decorator.ts`: `@ScopedResource(kind, { param | query | body, code, skipFor })`, `@BranchScopeExempt(이유)`.
- 컨트롤러 13개에서 `findXOrThrow`·`assert*`·`@UseGuards(BranchScopeGuard)`를 걷어내고 선언으로 바꿨다. 이제 쓰지 않는 서비스 메서드 3개(`staffBranchId` ×2, `leaveRequestStaffId`)를 지웠다.
- `test/branch-scope-coverage.spec.ts`(신규): 라우트 표에서 선언이 빠진 라우트와 선언이 가리키는 파라미터 오타를 잡는다.
- `branch-isolation.spec.ts` 공격 표에 6건을 추가했다. 이전에는 조용히 본인 지점으로 바뀌던 것들이다.
  - 자산·문서·결제 목록, 근태 요약, 결근 미리보기의 `branchId=서초`
  - 회원 예약 내역의 `memberId=서초 회원`

**동작이 바뀐 곳**
- BRANCH_ADMIN이 자산·결제·근태 요약·결근 미리보기·문서 목록에 남의 `branchId`를 주면 403이다(전에는 무시하고 본인 지점).
- 남의 리소스에 잘못된 본문을 보내면 400보다 403·404가 먼저 난다(가드가 파이프보다 먼저).
- 휴가 승인·반려·잔여·근태 조회에서 없는 직원·신청은 404다(전에는 일부가 403).

**지킨 것**
- 회원이 `/reservations?memberId=남`을 주면 지금처럼 본인 예약만 보인다(`skipFor: ['MEMBER']`, `member-detail-summary` spec 기대값 유지).
- 거부 코드는 이관 전 값 그대로다(`DOCUMENT_SCOPE_VIOLATION`·`RESERVATION_SCOPE_VIOLATION`·`ATTENDANCE_SCOPE_VIOLATION`은 `code` 옵션으로).
- 기존 테스트 기대값은 하나도 바꾸지 않았다.

**검증**
- api jest 34 스위트 386건 통과(로컬 PG16), lint 0 오류, 타입체크.
- 변이 확인: 시설 수정의 `@ScopedResource`를 빼면 선언 누락 검사 1건과 격리 공격 2건이 실패했다. 되돌린 뒤 통과했다.
- **검증되지 않음**: 배포(Lambda)에서의 실제 응답. 병합 후 자동 배포된다. admin-web·member-web 화면은 API 계약이 같아 손대지 않았다(남의 branchId를 보내는 화면은 없다 — 검색으로 확인).

## 098. 회원 웹 오류 해결 안내 — 오류 문구 아래 "해결:" 한 줄 (2026-10-10)

**계기**: 사용자가 "회원 웹 오류 해결 안내 시작하자"고 했다. 관리자 웹은 log/089에서 오류 아래에 "해결: …" 줄을 붙였고, 회원 웹은 STATUS에 남은 일로 적혀 있었다.

**한 일**
- `lib/errors.ts`의 문구 표를 `code → { message, hint }`로 나눴다. 관리자 웹 `error-hints.ts`와 같은 생각이다 — message는 "무엇이 안 됐는지", hint는 "어떻게 하면 되는지".
  - 기존 문구는 대부분 두 문장이 한 줄로 붙어 있었다. 이를 나누고, hint가 없던 코드에는 새로 썼다.
  - 새로 다루는 코드: `INVALID_CREDENTIALS`, `ACCOUNT_INACTIVE`, `VALIDATION_ERROR`.
  - `VALIDATION_ERROR`는 서버 검증 문구(어느 칸이 왜 틀렸는지)를 message로 그대로 쓰고 hint만 붙인다.
- 네트워크 끊김도 message("네트워크에 연결할 수 없습니다.")와 hint(연결 확인)로 나눴다.
- `describeError()`는 지금처럼 문자열 하나를 돌려준다(`message\n해결: hint`). 호출하는 화면 17곳은 고치지 않았다. 줄바꿈은 `.form-error`·`.error-panel p`에 `white-space: pre-line`을 줘서 보이게 했다.
- **함께 고친 버그**: 비밀번호를 틀리면 "로그인이 만료됐습니다. 다시 로그인해 주세요."가 나왔다.
  - 원인: `INVALID_CREDENTIALS`(401)가 표에 없어서 "401 = 세션 만료" 분기로 떨어졌다.
  - 이제 "이메일 또는 비밀번호가 맞지 않습니다. / 해결: 대소문자를 구분합니다."로 나온다.

## 102. 처리 한계(약 50 rps)의 원인 측정 — 풀러 모드가 Prisma 작업마다 왕복 3번을 더한다. 1단계로 인증 조회·목록 조회를 합쳤다 (2026-10-10)

**계기**: STATUS "열린 위험" — Lambda 요청당 처리 p50 약 110ms(D37 가정 50ms), 상한 10에서 실질 약 50~55 rps. 원인은 "풀러 왕복 × 쿼리 수"로 추정만 했다(D42, [056](2026-W40.md#056), [085](2026-W41.md#085)). 그 뒤 전역 BranchScopeGuard(D46)가 들어와 쿼리 수가 바뀌었다.

**측정 방법(로컬 실측)**
- 로컬 PG16 + 시드 DB에 앱을 Lambda와 같은 접속 옵션(`pgbouncer=true&connection_limit=1`)으로 띄웠다. Prisma `query` 이벤트로 요청당 SQL 문 수를 셌다.
- **순차 왕복 수**는 DB 앞에 왕복당 10ms를 지연시키는 TCP 프록시를 두고 `(p50(지연 10ms) − p50(지연 0)) ÷ 10`으로 역산했다(7회, 오차 ±1).
- 계정은 회원 서수진(회원 웹 라우트)과 서초점 관리자(k6 S2 조회 4종)다. 예약 측정용으로 로컬 DB에만 미래 회차 1개를 넣었다.
- 측정 스크립트는 저장소에 넣지 않았다(사용자 결정 대기). 스크립트가 기준 DB에 예약·토큰을 남겨 jest가 8건 실패했다 — 측정 뒤에는 `prisma migrate reset`으로 기준 DB를 다시 만들어야 한다.

**알게 된 것**
1. **`pgbouncer=true`에서 Prisma 5.22는 작업마다 `BEGIN` → `DEALLOCATE ALL` → 쿼리 → `COMMIT`을 보낸다.** 작업 하나에 왕복 3번이 더 든다. 같은 라우트를 플래그 없이 재면 왕복이 약 1/3.5이다(S2 평균 20.8 → 5.9).
2. **인증된 모든 요청이 인증에만 왕복 약 11회를 썼다.** `JwtStrategy`의 Account 조회(작업 1)와 `buildRequestUser`의 Branch 조회(작업 2)가 따로였다.
3. `connection_limit=1`이라 `Promise.all([count, findMany])`도 차례로 실행된다. 순차 → 병렬 변환은 효과가 없다.
4. 취소·결제는 가드의 소유 조회와 핸들러가 같은 예약을 두 번 읽고, 생성·취소·결제는 트랜잭션 뒤 응답용 뷰를 다시 읽는다(이번에는 고치지 않음).
5. 운영 W 110ms를 S2 평균 왕복 20.8회로 나눠 보면 풀러 왕복은 약 4ms(CPU 25~35ms 가정, **추정**)다. D37의 "쿼리 4~8개 × 1~3ms" 가정과 달리 왕복 수가 3~5배였다.

**한 일(사용자 선택 B1+B2, 2026-10-10)** — 근거와 대안 비교는 [D48](../decisions/archive.md#D48)
- B1: 계정 + 직원·회원 프로필 + 소속 지점 이름을 Prisma 작업 하나로 읽는다(`ACCOUNT_PROFILE_INCLUDE`). `JwtStrategy`·로그인·가입 직후 세션 발급이 같은 include를 쓰고 `buildRequestUser`는 DB를 읽지 않는다. 매 요청 재조회(ADR-AUTH-01)는 그대로다.
- B2: 공지·예약·회원 목록의 count + findMany를 일괄 트랜잭션(`$transaction([...])`) 하나로 묶었다. 공지 작성자 이름은 따로 조회하지 않고 `author` 관계 include로 읽는다(Post.author, [093](2026-W41.md#093)).

## 103. 계약 상태 변경 화면·재배치 대기 목록·본사의 종료 지점 직원 퇴사 — ADR-STF-07 후속 (2026-10-10)

## 104. 배포 DB 종료 지점 정리 SQL 준비 — 파견 6건 종료·담당 회원 4명 해제 (2026-10-10)

**계기**: ADR-STF-08(log/103)에서 시드 생성기는 고쳤지만, 배포 DB(Supabase)의 계약 종료 지점 3곳에는 ADR-STF-07 이전 데이터가 그대로 남아 있다. 배포 DB 쓰기는 사용자 승인 대상이라 SQL만 준비했다. **아직 실행하지 않았다.**

**배포 DB 현황**(2026-10-10 읽기 전용 조회): `branch-gen-094`·`095`·`096`(모두 TERMINATED)에 진행 중 파견 6건(`staff-gen-094-1`, `095-1`, `095-2`, `096-1`, `096-2`, `096-3`)이 있다. 담당 회원은 4명(`staff-gen-094-1`에 2명, `staff-gen-095-1`에 2명)이고 강사 연결은 없다. 계약 종료일은 2026-02-21·2026-01-22·2025-12-23으로 로컬 시드와 다르다(시드가 실행 시점 기준 상대 날짜). 그래서 SQL은 날짜를 고정하지 않고 `Branch.contractEndAt`을 읽는다.

**하는 일**: 종료 전이(ADR-STF-07)가 했을 정리를 그대로 한다.
1. 대상 직원의 담당 회원을 해제한다.
2. 대상 직원의 강사 프로필 연결을 해제한다(지금은 0건).
3. 파견을 계약 종료일로 닫는다. 종료일이 없으면 오늘(KST)로 닫고, 시작일보다 앞서지 않게 한다(`StaffAssignment_period_ck`).

감사 기록(`ASSIGNMENT_ENDED`)은 남기지 않는다. 사람이 한 인사 처리가 아니라 시드 데이터를 맞추는 일이기 때문이다. 이 기록이 그 경위다.

**안전장치**:
- 한 트랜잭션이다.
- 사전 검사: 알려진 6명 밖의 진행 중 파견이 종료 지점에 있으면 예외를 내고 전체를 롤백한다.
- 사후 검사: 종료 지점에 진행 중 파견이나 담당 회원이 하나라도 남으면 롤백한다.
- 이미 적용된 DB에서 다시 돌리면 아무것도 바꾸지 않는다.

**실행 절차(사용자, Supabase SQL Editor)**:
1. 미리 세기 — 6과 4가 나와야 한다.

   ```sql
   SELECT
     (SELECT count(*) FROM "StaffAssignment" a JOIN "Branch" b ON b.id = a."branchId"
       WHERE b."contractStatus" = 'TERMINATED' AND a."endDate" IS NULL) AS 진행중_파견,
     (SELECT count(*) FROM "Member" m JOIN "Branch" b ON b.id = m."branchId"
       WHERE b."contractStatus" = 'TERMINATED' AND m."assignedStaffId" IS NOT NULL) AS 담당_회원;
   ```

2. 아래 SQL을 통째로 실행한다. 오류가 나면 아무것도 바뀌지 않는다.

   ```sql
   -- 배포 DB 종료 지점 정리 — 인사정보관리 ADR-STF-07·08. 시드로 들어간 계약 종료 지점 3곳은 ADR-STF-07 이전 데이터라
   -- 진행 중 파견과 담당 회원이 남아 있다. 종료 전이가 했을 일을 그대로 한다: 파견을 계약 종료일로 닫고 담당을 푼다.
   -- 한 트랜잭션이다. 사전·사후 검사가 어긋나면 예외로 전체가 롤백된다. 이미 적용된 DB에서 다시 돌리면 0건으로 끝난다.
   BEGIN;

   -- 1) 사전 검사: 대상이 알려진 6건(직원 6명)을 넘지 않는지. 다른 데이터가 섞였으면 멈춘다.
   DO $$
   DECLARE unexpected int;
   BEGIN
     SELECT count(*) INTO unexpected
     FROM "StaffAssignment" a JOIN "Branch" b ON b.id = a."branchId"
     WHERE b."contractStatus" = 'TERMINATED' AND a."endDate" IS NULL
       AND a."staffId" NOT IN ('staff-gen-094-1','staff-gen-095-1','staff-gen-095-2',
                               'staff-gen-096-1','staff-gen-096-2','staff-gen-096-3');
     IF unexpected > 0 THEN
       RAISE EXCEPTION '예상 밖 진행 중 파견 %건 — 중단', unexpected;
     END IF;
   END $$;

   -- 2) 담당 회원 해제(파견을 닫기 전에 — ADR-STF-07과 같은 정리). 대상 직원의 담당 회원만.
   UPDATE "Member" m
   SET "assignedStaffId" = NULL, "updatedAt" = now()
   FROM "StaffAssignment" a JOIN "Branch" b ON b.id = a."branchId"
   WHERE b."contractStatus" = 'TERMINATED' AND a."endDate" IS NULL
     AND m."assignedStaffId" = a."staffId";

   -- 3) 강사 프로필 연결 해제(지금은 0건이지만 전이 규칙과 같게 둔다).
   UPDATE "Instructor" i
   SET "staffId" = NULL, "isActive" = false
   FROM "StaffAssignment" a JOIN "Branch" b ON b.id = a."branchId"
   WHERE b."contractStatus" = 'TERMINATED' AND a."endDate" IS NULL
     AND i."staffId" = a."staffId";

   -- 4) 파견 종료: 계약 종료일(없으면 오늘 KST). 시작일보다 앞서지 않게(StaffAssignment_period_ck).
   UPDATE "StaffAssignment" a
   SET "endDate" = GREATEST(a."startDate", COALESCE(b."contractEndAt", (now() AT TIME ZONE 'Asia/Seoul')::date))
   FROM "Branch" b
   WHERE b.id = a."branchId" AND b."contractStatus" = 'TERMINATED' AND a."endDate" IS NULL;

   -- 5) 사후 검사: 종료 지점에 진행 중 파견·담당 회원이 남지 않았는지.
   DO $$
   DECLARE open_left int; members_left int;
   BEGIN
     SELECT count(*) INTO open_left FROM "StaffAssignment" a JOIN "Branch" b ON b.id = a."branchId"
     WHERE b."contractStatus" = 'TERMINATED' AND a."endDate" IS NULL;
     SELECT count(*) INTO members_left FROM "Member" m JOIN "Branch" b ON b.id = m."branchId"
     WHERE b."contractStatus" = 'TERMINATED' AND m."assignedStaffId" IS NOT NULL;
     IF open_left > 0 OR members_left > 0 THEN
       RAISE EXCEPTION '정리 후에도 남음: 파견 %건, 담당 회원 %명', open_left, members_left;
     END IF;
   END $$;

   COMMIT;
   ```

3. 1단계 쿼리를 다시 실행해 0과 0을 확인한다. 관리자 웹 직원 화면의 "재배치 대기" 탭에 이 6명이 보이면 된다(Worker 재배포 뒤).
4. 실행 날짜와 결과를 `docs/log/`에 한 건 남긴다.

**검증**(로컬 PG16):
- 기준 DB를 복제해 배포 DB와 같은 상태(진행 중 파견 6건, 담당 회원 4명)를 만들었다.
- 1회차 실행: 진행 중 파견이 168 → 162, 담당 회원이 100 → 96이 됐다. 종료 지점 외 파견의 지문(id·종료일 md5)은 그대로였다.
- 2회차 실행: 바뀐 것이 없었다.
- 예상 밖 진행 중 파견 2건을 섞어 실행하자 사전 검사가 "예상 밖 진행 중 파견 2건 — 중단"으로 멈췄고, 아무것도 바뀌지 않았다.
- 배포 DB에서는 **실행하지 않았다(검증되지 않음)**.

**근거**: 인사정보관리 ADR-STF-07·08, 루트 CLAUDE.md "배포 DB 쓰기는 사용자 승인", log/044~050(배포 DB 작업은 로컬 복제에서 먼저 확인).

## 105. Lambda DB 접속을 Session pooler로 — 로컬 검증, 배포 스크립트 검사, 목록 일괄 트랜잭션 되돌리기 (2026-10-11)

3. Supabase 문서(search_docs): 세션 모드는 클라이언트당 전용 연결이고 prepared statement를 지원한다. 세션 모드 동시 클라이언트는 Pool Size로 제한된다. Supavisor 트랜잭션 모드는 prepared statement를 지원하지 않는다 → A2 기각의 근거.
4. 배포 DB 읽기 전용 조회 1회(SELECT): `max_connections` 60, 연결 15개(대부분 Supabase 내부, 유휴). Pool Size 값은 SQL로 보이지 않는다 — **대시보드 확인 필요**.

**근거**: D48(원인·A안), D37 결정 1·R1·R2, D42(상한 10), log/056(42P05 장애).

**검증**
- 기본 설정 jest 35 스위트 410건 통과, api lint 오류 0(기존 경고 1), 빌드 성공.
- **검증되지 않음**: 운영 전환(Lambda 환경 변수)과 운영 k6 S2. 기대 W 약 50~60ms·처리 한계 약 100 rps는 풀러 왕복 4ms 가정의 추정이다.

**남은 일(사용자)**: 대시보드 Database Settings에서 Pool Size 확인(10 + 여유) → `aws-lambda/.env`의 `LAMBDA_DATABASE_URL`을 Session pooler 문자열로 → `bash aws-lambda/set-lambda-env.sh` → Actions 재배포 → k6 S2·CloudWatch 확인. 되돌리기는 이전 값으로 같은 절차.

**커밋**: posts·reservations·members 서비스, auth.service 주석, `aws-lambda/`(스크립트·README·런북), `.env.example`, 문서(D49, STATUS).

- **종목·시간대·연령대별 프로그램 목록**: 부분 구현이다(목록 필터 없음).
- **처리 느린 작업의 사용자 사전 알림**: 운영자 경보만 있다.
- **이용자 매뉴얼 앱 탑재**: 관리자 웹 도움말만 있다.
- 추적표의 어긋난 문장도 고쳤다: "계약 종료 시 파견 종료 미구현" → 2026-10-10 구현됨.
