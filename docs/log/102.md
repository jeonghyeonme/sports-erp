# 102. 처리 한계(약 50 rps)의 원인 측정 — 풀러 모드가 Prisma 작업마다 왕복 3번을 더한다. 1단계로 인증 조회·목록 조회를 합쳤다 (2026-10-10)

> [진행 로그 인덱스](README.md)

**계기**: STATUS "열린 위험" — Lambda 요청당 처리 p50 약 110ms(D37 가정 50ms), 상한 10에서 실질 약 50~55 rps. 원인은 "풀러 왕복 × 쿼리 수"로 추정만 했다(D42, [056](056.md), [085](085.md)). 그 뒤 전역 BranchScopeGuard(D46)가 들어와 쿼리 수가 바뀌었다.

**측정 방법(로컬 실측)**
- 로컬 PG16 + 시드 DB에 앱을 Lambda와 같은 접속 옵션(`pgbouncer=true&connection_limit=1`)으로 띄웠다. Prisma `query` 이벤트로 요청당 SQL 문 수를 셌다.
- **순차 왕복 수**는 DB 앞에 왕복당 10ms를 지연시키는 TCP 프록시를 두고 `(p50(지연 10ms) − p50(지연 0)) ÷ 10`으로 역산했다(7회, 오차 ±1).
- 계정은 회원 서수진(회원 웹 라우트)과 서초점 관리자(k6 S2 조회 4종)다. 예약 측정용으로 로컬 DB에만 미래 회차 1개를 넣었다.
- 측정 스크립트는 저장소에 넣지 않았다(사용자 결정 대기). 스크립트가 기준 DB에 예약·토큰을 남겨 jest가 8건 실패했다 — 측정 뒤에는 `prisma migrate reset`으로 기준 DB를 다시 만들어야 한다.

**알게 된 것**
1. **`pgbouncer=true`에서 Prisma 5.22는 작업마다 `BEGIN` → `DEALLOCATE ALL` → 쿼리 → `COMMIT`을 보낸다.** 작업 하나에 왕복 3번이 더 든다. 같은 라우트를 플래그 없이 재면 왕복이 약 1/3.5이다(S2 평균 20.8 → 5.9).
2. **인증된 모든 요청이 인증에만 왕복 약 11회를 썼다.** `JwtStrategy`의 Account 조회(작업 1)와 `buildRequestUser`의 Branch 조회(작업 2)가 따로였다.
3. `connection_limit=1`이라 `Promise.all([count, findMany])`도 차례로 실행된다. 순차 → 병렬 변환은 효과가 없다.
4. 취소·결제는 가드의 소유 조회와 핸들러가 같은 예약을 두 번 읽고, 생성·취소·결제는 트랜잭션 뒤 응답용 뷰를 다시 읽는다(이번에는 고치지 않음).
5. 운영 W 110ms를 S2 평균 왕복 20.8회로 나눠 보면 풀러 왕복은 약 4ms(CPU 25~35ms 가정, **추정**)다. D37의 "쿼리 4~8개 × 1~3ms" 가정과 달리 왕복 수가 3~5배였다.

**한 일(사용자 선택 B1+B2, 2026-10-10)** — 근거와 대안 비교는 [D48](../decisions/D48.md)
- B1: 계정 + 직원·회원 프로필 + 소속 지점 이름을 Prisma 작업 하나로 읽는다(`ACCOUNT_PROFILE_INCLUDE`). `JwtStrategy`·로그인·가입 직후 세션 발급이 같은 include를 쓰고 `buildRequestUser`는 DB를 읽지 않는다. 매 요청 재조회(ADR-AUTH-01)는 그대로다.
- B2: 공지·예약·회원 목록의 count + findMany를 일괄 트랜잭션(`$transaction([...])`) 하나로 묶었다. 공지 작성자 이름은 따로 조회하지 않고 `author` 관계 include로 읽는다(Post.author, [093](093.md)).

- 기준선은 `97bbcd0`(ADR-STF-07 반영)에서 쟀다. D47(`f193a2a`)은 관리자의 회원·직원 상세에만 쿼리를 더해 위 라우트와 겹치지 않는다.
- 기대 효과(추정, 풀러 왕복 4ms 가정): S2 평균 왕복 −4회 ≈ −16ms → W 약 110 → 약 94ms, 상한 10의 처리 한계 약 50 → 약 60 rps. **운영에서 재지 않았다.**
- `pgbouncer=true`를 빼면(A안, 미승인) B2의 일괄 트랜잭션이 BEGIN·COMMIT 2왕복을 더한다(회원 목록 6.9 → 8.2, 공지 6.7 → 8.1). A를 할 때 B2는 `Promise.all`로 되돌린다.

**근거**: D37 R5(요청당 쿼리 수, "측정 후 판단"), D42 대안 B·재고 트리거, ADR-AUTH-01(매 요청 재조회 유지), D46(가드 소유 조회).

**검증**
- 실DB jest 전체 35 스위트 405건 통과(최신 `dev` rebase 후, 기준 DB 재생성). `auth-lifecycle.spec.ts`에 1건 추가: 직원·회원의 `branchName`, 본사는 없음, 파견 직후 같은 토큰에서 새 지점 이름. 공지 작성자 이름은 기존 `post-rules.spec.ts`가 본다.
- 커밋 hook에서 `post-rules` 동시 조회 20건이 `ECONNRESET`으로 간헐 실패했다(변경 전 코드에서도 6회 중 1회). 원인은 테스트 헬퍼가 listen하지 않은 서버를 supertest에 넘긴 것이다 — supertest가 요청마다 같은 서버를 열고 끝난 요청이 닫아 버린다. `createApp()`이 임의 포트로 미리 listen하게 고쳤다(`test/helpers/app.ts`). 고친 뒤 동시 요청이 있는 3개 스위트를 8회 연속 통과했다(전에는 5회 중 2회 실패).
- api 타입체크·lint 오류 0(기존 `main.ts` 경고 1건). 커밋 hook으로 세 앱 lint·빌드와 jest.
