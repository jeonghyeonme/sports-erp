# 21. 자원문서관리 3개 ADR(RES-01~03)을 전부 구현했다 (2026-09-25)

> [진행 로그 인덱스](README.md)

**계기**: §20에서 문서화한 자원문서관리 도메인의 3개 ADR을, 사용자가 "3개 ADR 하나씩 진행해줘"로 지정해 §17~19와 같은 방식("구현 → 리뷰 → 수정 → 보고 → 다음")으로 처리했다. 도메인 문서 §11 우선순위대로 RES-01 → RES-02 → RES-03 순서로 진행했다.

**RES-01(계약종료 차단)**: `createAsset`·`createDocument`에 `createMember`/`createPost`/`createFacility`와 동일한 인라인 `TERMINATED` 체크를 추가했다. 자산은 SUPER_ADMIN도 직접 만들 수 있어 다른 도메인과 달리 역할 분기 없이 대상 `branchId`로만 판정했고, 문서는 `branchId=null`(전사 문서)이면 검사 자체를 건너뛰게 했다 — 두 예외 모두 도메인 문서 §8이 미리 짚어둔 것이라 구현 중 새로 발견한 문제는 없었다. 자원문서관리 A-6이 원래 의도했던 "미처리 자산 N건" 경고도 `BranchDetailPage.tsx`에 함께 추가했다(값만 만들고 화면에서 못 보면 결정 취지가 성립하지 않는다는, §16 이후 반복 확인한 교훈).

**RES-02(퇴사 시 보존기한 재계산)**: `resignStaff`가 계정 비활성화·파견 종료를 처리하는 자리에 HR_RECORD 문서 재계산을 추가했다. 테스트에서 "오늘 날짜 기준 계산이라 재직 중 값과 퇴사 후 값이 같은 날엔 구분이 안 된다"는 문제를 미리 피하려고, 실제 시나리오(같은 날 업로드→퇴사) 대신 일부러 틀린 값으로 시드한 문서가 올바른 값으로 고쳐지는지 확인하는 방식을 썼다 — 대조군(타 직원의 HR_RECORD, 타 카테고리, 소프트 삭제된 문서)이 안 바뀌는 것도 같이 확인했다.

**RES-03(CONTRACT 보존기한 필수화)**: `createDocument`에 `STAFF_REQUIRED`와 같은 자리·같은 패턴으로 `RETENTION_UNTIL_REQUIRED` 체크를 추가했다. `CreateDocumentDto`는 여전히 `retentionUntil`을 optional로 뒀다 — class-validator로 "카테고리에 따라 조건부 필수"를 표현하려면 커스텀 validator가 필요한데, 이 코드베이스가 이미 `HR_RECORD`의 `relatedStaffId` 같은 조건부 필수값을 전부 서비스 계층에서 검증하는 관례를 따르고 있어 그 관례를 그대로 재사용했다. admin-web `DocumentsPage`의 보존기한 입력도 CONTRACT일 때 `required`로 바꿨다.

**검증**: `apps/api/test/document-retention.spec.ts`(신규, RES-03 4건), `staff-assignment.spec.ts`(RES-02 1건 + 대조군 3개), `contract-termination.spec.ts`(RES-01 8건 추가) — 매 ADR마다 diff를 다시 읽는 자체 리뷰를 거쳤고, 이번 3개에서는 추가로 고칠 문제를 찾지 못했다(FAC/PRG 사이클과 달리 이번엔 부수 버그 발견이 없었다 — 이 도메인 자체가 최근에 만들어져 코드가 더 단순했던 것으로 보인다). `npm run test`(15 suites, **216 passed**), `eslint`·`nest build`·admin-web `tsc -b && vite build` 전부 클린.

**9개 도메인 전체 진행 상황 갱신**: 자원문서관리까지 포함해 이번에 발견한 총 11개 ADR(강사프로그램게시 3·혼잡도관리 3·게시판 2·자원문서관리 3) 전부 구현·검증 완료됐다. 근태관리(구현까지 완료, §12~13)와 합치면, 9개 도메인 전체가 "문서화 완료"이고 그중 발견된 구조적 격차는 전부 구현까지 끝난 상태다.
