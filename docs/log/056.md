# 056. api 운영을 Lambda로 넘겼다 — 첫 부하 측정의 실패는 성능이 아니라 DB URL 누락이었다 (2026-10-04)

> [진행 로그 인덱스](README.md)

**계기**: [055](055.md)에서 비밀값 env·GitHub 설정·첫 배포·Worker 전환·k6가 남았다. 이번 세션에서 끝까지 진행했다. 비밀값이 필요한 단계는 사용자가 직접 실행했다(Claude는 `.env`를 읽지 않음).

**한 일**(순서대로):
1. 사용자가 `aws-lambda/.env`를 쓰고 `set-lambda-env.sh`를 실행했다. 첫 실행은 PowerShell의 `bash`가 WSL로 떠서 `aws`를 못 찾았고, Git Bash로 다시 실행해 키 5개가 들어갔다. **이때 `.env`의 URL에 `?pgbouncer=true...`가 없었다**(스크립트는 경고만 내고 진행했다 — 아래 6번).
2. 사용자가 GitHub Actions Variables 2·Secrets 2를 등록했다(Repository 단위 — 워크플로에 `environment:`가 없다).
3. Run workflow 버튼이 없었다. 기본 브랜치(`main`)에 워크플로 파일이 없어서다. 대안(기본 브랜치 변경 / `main`에 병합 / push 트리거) 중 **저장소 기본 브랜치를 `main-5x9td9`로 바꿨다**(사용자 선택). 실제 작업이 모두 이 브랜치라 병합은 같은 문제를 반복한다.
4. 첫 실행이 `Not authorized to perform sts:AssumeRoleWithWebIdentity`로 실패했다. CloudTrail을 보니 GitHub OIDC 토큰의 `sub`가 고유 ID를 붙인 새 형식(`repo:owner@ID/repo@ID:ref:...`)이었다. 신뢰 정책 `sub`를 그 값으로 정확히 바꿨다(사용자 실행 — IAM 변경은 자동 권한 검사가 막았다). 재실행 성공: 별칭 `live` → v2, health 200, 비밀 헤더 없음·틀림 403.
5. Worker 전환(런북 5번): `--secrets-file`로 코드와 `API_ORIGIN`·`ORIGIN_SECRET`을 한 번에 배포했다. Worker 경유 health 200, 요청이 Lambda 로그에 찍힘, 브라우저 로그인 성공(사용자 확인). 기존 일반 변수와의 이름 충돌은 없었다.
6. **k6 1차(Function URL 직접)가 대량 실패했다.** 진단 요청 5건으로 로그인이 500임을 확인했고, Lambda 로그는 `42P05 prepared statement "s46" already exists`였다. 함수 env의 `DATABASE_URL`을 값 없이 `contains()`로만 검사하니 `pgbouncer=true`·`connection_limit=1`이 없었다(1번의 누락). **이 시점부터 운영 로그인도 500이었다**(사용자 없음). 사용자가 `.env`를 고친 뒤 스크립트를 재실행했고, Actions 재배포로 v3를 발행해 복구했다(로그인 200, 조회 4종 200, `42P05` 0건).
7. 1차의 S1은 설정 오류와 별개로 설계 문제도 있었다. VU가 쉬지 않고 로그인해서, 거절 응답(약 10ms)마다 즉시 재시도해 분당 약 13만 건을 보냈다. 사용자 승인으로 `loadtest/k6-lambda.js`의 S1에 `sleep(1)`을 넣었다(최대 40 VU ≈ 초당 40회).
8. k6 2차 — 결과는 아래 근거 표. 사용자가 경보 메일의 unsubscribe를 잘못 눌러 SNS 구독이 지워졌고, 다시 구독했다(사용자가 확인 링크 클릭).

**근거**: [D37](../decisions/D37.md)(§2 결정, §4 검증 기준), CLI-RUNBOOK 1~5·7번. 실측(2026-10-04 15:39~15:48 UTC, 사용자 PC → Function URL 직접, 서울):

| 시나리오 | 기준(D37 §4) | 실측 | 판정 |
|---|---|---|---|
| S1 로그인 0→40 VU(1초 간격) | p95 < 500ms, 에러 0 | p95 237ms, 에러 **1**(정점에서 상한 10 도달로 거절) | 에러 기준 미달 |
| S2 50 rps × 5분 | p95 < 300ms, 거절 0 | p95 178ms, 거절 0, 실패 0 | 통과 |
| S3 300 rps × 1분 | 거절 p95 < 100ms, 성공 p95 < 500ms | 거절 p95 13ms(1.38만 건), 성공 p95 182ms, 실패 0 | 통과 |
| S4 콜드 스타트 | Init < 1.5초 | 첫 배포 직후 REPORT의 Init Duration 1,063ms(30분 유휴 조건은 아님) | 통과로 갈음 |

- **가정과 다른 점(실측)**: 요청 하나의 Lambda 처리 시간이 D37 §1의 가정(약 50ms)이 아니라 p50 약 110ms·p95 약 165ms다. 그래서 상한 10에서 실질 처리량은 약 50~55 rps이다(S3에서 300 rps를 보내도 성공은 분당 약 3,100건). S2 동안 동시 실행이 9~10으로 상한에 붙어 있었다. 처리 시간이 긴 원인(Lambda↔풀러 왕복 × 요청당 쿼리 수)은 **추정이고 확인하지 않았다**.
- D37 §4는 Worker 주소에 대해 재라고 했지만 Function URL에 직접 쟀다. Worker 로그인 rate limit(IP당 60초 10회)이 S1을 막고 Workers 무료 일일 한도를 쓰기 때문이다(`k6-lambda.js` 머리 주석).
- 부수 효과: 배포 DB에 데모 계정(`kim.minsu`) refreshToken이 약 1.2만 행 생겼다(1차 약 1만 + 2차 약 1.8천, 사용자 승인 — 그대로 둔다). Supabase egress는 사용자가 확인한 시점에 거의 0이었다(무료 5GB).

**검증**: 위 실측과 CloudWatch(Invocations·Throttles·Errors·ConcurrentExecutions·Duration), Lambda 로그 확인. 2차 실행 동안 Errors 0. `k6-lambda.js`는 `k6 inspect`로 파싱만 확인했다. 앱 코드는 바꾸지 않았다. admin-web 화면은 로그인 외에 **검증되지 않음**.

**보안 메모**: `ORIGIN_SECRET`과 DB 비밀번호가 대화창에 두 번 붙여넣어졌다. 사용자는 교체하지 않고 진행하기로 했다. Render를 멈춘 뒤 DB 비밀번호를 바꾸면 Render 쪽 영향 없이 교체할 수 있다.
