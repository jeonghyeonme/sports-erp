# 145. 공지 대상 시설 지정 — RFP F4-3 완전 충족(게시판 ADR-BRD-05) (2026-10-20)

> [진행 로그 인덱스](README.md)

**계기**: 사용자가 부분 충족 조항 중 "사용자 직접 작업·문서 작업을 뺀 것"을 진행하라고 했다. 남은 코드 조항 셋 중 F4-3(시설별 공지)은 스키마 변경 승인, F1-2·N7-2(세부 권한)는 "역할 기본값 + 개인 예외"로 결정, N7-3(PG 연계)은 보류(사용자 작업이 필요하고 세션은 PG 서버 접속이 막혀 있다). 이 기록은 F4-3이다. 세부 권한은 다음 작업.

**한 것**(ADR-BRD-05):
- 스키마: `Post.facilityId`(선택, Facility FK, `ON DELETE SET NULL`). 마이그레이션 `20261020120300_f43_post_facility`에 같은 지점 트리거 `post_facility_branch`(D28 방식, search_path 고정)를 함께 넣었다.
- api: 작성은 `@ScopedResource('facility', { body: 'facilityId' })` — 다른 지점 시설 403, 없는 시설 404(D46, 컨트롤러에 지점 검사를 손으로 쓰지 않음). 본사 공지에 시설 400 `POST_FACILITY_NOT_ALLOWED`. 수정은 경로가 글 id라 서비스가 그 글 지점의 시설인지 본다(400 `FACILITY_BRANCH_MISMATCH`), `null`은 해제. 목록 `?facilityId=`는 보이는 글 안에서만 거른다. 응답에 `facilityId`·`facilityName`.
- 관리자 웹: 지점 관리자 글쓰기·수정에 "대상 시설"(비우면 지점 전체), 목록·상세에 시설 표시. 회원 웹: 공지 목록에 시설 고르기(홈 혼잡도와 같은 `GET /facilities` 60초 캐시), 목록·상세에 시설 표시.
- 시연 데이터 층: 지점별 "시설 휴관 안내"를 헬스장 대상으로(기준 시드는 그대로).
- 산출물: 요구사항 정의서·데이터 정의서 재생성. 데이터 정의서 생성기는 업무지원 요청 테이블(D56) 설명이 없어 10-17부터 실패하고 있었다 — 설명을 더하고 옛 "미사용" 문구 2개(인사 변경 신청·첨부)를 지금 상태로 고쳤다.

**검증**: api jest 45개 파일 510건 통과(새 `post-facility.spec.ts` 5건 — 작성·필터·회원 표시·다른 지점 403·없는 시설 404·본사 400·수정 변경/해제/다른 지점 400·DB 트리거, `branch-isolation`에 강남 관리자 → 서초 시설 공격 케이스). 세 앱 lint·빌드, 화면 자동 테스트 7건 통과(`admin-branch`가 시설을 골라 쓰고 목록·상세 표시를, `member-notice`가 시설로 거른 목록과 상세를 본다). doc-check 통과.

**배포 순서 주의**: Prisma는 글을 읽을 때 모든 열을 고르므로, 코드가 먼저 배포되면 배포 DB에 `facilityId`가 없어 게시판 조회가 500이 된다. 배포 DB에 마이그레이션 SQL을 먼저 적용(사용자 승인 대상)한 뒤 병합한다. 배포 DB는 마이그레이션 도구가 아니라 SQL로 맞춰 왔다(log/143).

**추적표**: F4-3 부분 → 구현. 전체 80% → 81%(52/64), 기능·성능 89% → 93%(26/28).
