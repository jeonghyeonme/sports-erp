# 128. 관리자 웹의 UTC "오늘" 3곳 수정 + KST 오늘 함수 하나로 (2026-10-19)

> [진행 로그 인덱스](README.md)

**계기**: log/127 후속. 사용자가 "UTC 오늘 버그 5곳"을 고치자고 했다. 근거 규칙은 date-time-handling(화면의 "오늘"은 KST)이다. 결함 수정이라 D53 질문은 생략했다.

**log/127 정정**: 후보 5곳 중 2곳은 결함이 아니었다.
- `AbsenceConfirmSection.tsx:33`: 이미 KST로 구한 날짜 문자열에 하루를 더하는 계산이다. 월은 `kstMonth`가 KST로 구한다.
- member-web `ProgramSlotsPage.tsx:194`: `dateStrip`이 KST 오늘(`Intl`, `Asia/Seoul`)에서 시작해 날짜 문자열을 더한다.

`toISOString()`을 날짜 문자열 계산에 쓰는 것 자체는 문제가 아니다. "지금 시각"을 UTC 날짜로 자르는 것만 문제다.

**한 일**:
- `apps/admin-web/src/lib/kst-date.ts`에 `kstToday()`를 새로 만들었다(`Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Seoul' })`).
- 실제 결함 3곳을 이 함수로 바꿨다:
  - 예약 관리(`ReservationsPage`): 회차 목록의 "오늘 이후" 필터와 회차 추가 기본 날짜.
  - 자산(`AssetsPage`): 등록 폼의 취득일 기본값.
  - 문서함(`DocumentsPage`): 보존기한 D-day 기준일. 새벽에는 하루 늘어 보였다.
- 화면마다 따로 있던 KST "오늘" 함수 3개도 이 함수를 쓰게 했다: `AttendancePage`(log/127), `StaffDetailPage`, `WeeklyTimetable`. 같은 규칙이 여러 벌 있으면 하나만 고쳐지는 일이 다시 생긴다.
- member-web은 이미 `lib/format.ts`의 `todayKst()`가 있어 손대지 않았다.

**남긴 것**:
- `MembersPage.tsx:56`의 나이 계산은 기기 현지 시각(`getMonth`·`getDate`)을 쓴다. 생일 경계에서 몇 시간만 차이 나므로 이번에는 그대로 둔다.
- `AssetsPage`의 빈 폼은 모듈이 처음 읽힐 때 날짜를 정한다. 자정을 넘겨 탭을 열어 두면 기본값이 전날로 남는다(이전에도 같았다).

**검증**:
- 2026-10-19 05:13 KST에 시연 DB로 Playwright 확인. 예약 관리의 회차 추가 기본 날짜가 수정 전에는 UTC·한국 기기 모두 2026-10-18(어제), 수정 후에는 둘 다 2026-10-19.
- admin-web lint·빌드 통과. 자산·문서 화면은 같은 함수로 바꾼 것만 확인했고, 화면은 따로 열어 보지 않았다(검증되지 않음). 화면 자동 테스트는 없다.

**커밋**: admin-web 7파일(`lib/kst-date.ts` 신규), 문서(log/128, STATUS).
