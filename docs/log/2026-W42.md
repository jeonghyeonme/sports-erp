## 108. Session pooler 운영 전환 확인 — Lambda `DATABASE_URL`이 5432·`pgbouncer` 없음, 운영 k6 재측정은 아직 (2026-10-12)

**계기**: 6주차 덱 18장(성능)에 "전환은 준비 완료"라고 썼는데 사용자가 이미 전환했는지 기억나지 않는다고 확인을 요청했다.

**확인한 것**
- GitHub Actions: D49 병합(`71e7d42`, 2026-10-11 02:29 UTC push 배포) 4분 뒤 02:33에 `Deploy api (AWS Lambda)` 수동 실행(workflow_dispatch) 성공 — log/105 절차의 마지막 단계("set-lambda-env.sh → Actions 재배포")와 순서가 맞는다.
- 배포 DB 읽기 전용 조회 2회(SELECT만): 활성 연결은 Supavisor 유휴 1개뿐(트래픽 없음). `pg_stat_statements`의 `DEALLOCATE ALL`(트랜잭션 모드 + `pgbouncer=true`에서만 나온다)은 9/27 이후 누적 73,003회 — 누적값이라 전환 여부를 가리지 못했다. 운영 주소로 요청을 보내 증가를 보려 했으나 이 세션의 네트워크 정책이 막았다.
- **사용자가 AWS 콘솔에서 확인: Lambda `DATABASE_URL`이 5432이고 `pgbouncer` 파라미터가 없다** → D49 결정 1이 운영에 적용돼 있다.

**바꾼 것**: 6주차 덱 18장 — 막대 이름 "이전/바꾼 접속 방식", 대응 "둘 다 운영에 적용", 남은 것 "운영에서 다시 재기"(발표자 노트 포함). STATUS 다음 할 일 5·열린 위험의 처리 한계 줄.

**검증**: 전환 사실은 사용자의 콘솔 확인에 근거한다. **운영 k6 S2 재측정·CloudWatch 확인은 하지 않았다** — W 약 50~60ms·처리 한계 약 100 rps는 여전히 추정(검증되지 않음). 대시보드 Pool Size 확인 여부도 기록이 없다.

**커밋**: 덱 생성기·perf 슬라이드, STATUS, 이 로그.

## 109. Session pooler 전환 후 운영 k6·CloudWatch 재측정 — W 110 → 약 40ms, 순간 몰림 거절 증가 (2026-10-12)

**계기**: log/108에서 Session pooler 전환이 운영에 적용돼 있음을 확인했고, 6주차 덱 18·19장의 "처리 한계 2배는 예상치"를 실측으로 바꾸려고 사용자가 재측정을 결정했다. 대화 중 "몰릴 때 8 rps는 가볍게 넘지 않나"라는 질문에서, 위험은 평균 rps가 아니라 같은 순간의 동시 실행(상한 10)이라는 점을 정리했다.

**한 일**
- 사용자가 새 PC에 k6를 설치하고(`winget install k6`) `loadtest/k6-lambda.js`를 Function URL 직접으로 실행(2026-10-12 06:02~06:11 UTC). `BASE_URL`에 콘솔 주소가 두 번 붙어 404가 난 것을 바로잡은 뒤 진행했다.
- 사용자가 CloudWatch Logs Insights에서 REPORT 줄을 1분 단위로 집계(p50·p95·max·콜드 스타트 수·Init 최대)해 붙였다. 이 세션은 운영 주소에 접근할 수 없다(네트워크 정책) — 측정은 모두 사용자 쪽.

**결과** — 표와 결정은 [D50](../decisions/D50.md)
- 서버 W(조회): p50 약 40ms·p95 약 51ms(S2·S3 모두). 10/4의 약 110ms에서 약 2.7배 빨라졌다. D49 재고 기준(70ms) 아래.
- k6 판정: S2 성공 p95 150ms(통과), S1 로그인 p95 234ms(통과). **미달**: 로그인 거절 38, S2 거절 47, S3 성공 p95 3.07s·거절 p95 1.28s.
- S3 지연은 같은 시간 서버 p95가 약 50ms이고 k6가 2,169건을 못 보냈으므로 측정 PC 병목으로 판단했다. S3 성공 처리량은 분당 약 5,600(약 93 rps, k6 출력에서 역산) — 10/4 약 52 rps의 약 1.8배.
- 콜드 스타트 Init 약 1,420ms(S1 중 9회, 10/4 1,063ms). 로그인 거절 38은 이 기간과 겹친다(추정).
- 5xx 0 — 세션 모드 연결 부족(P2024) 없음.

**추가 확인(같은 날, 사용자 콘솔 캡처·쿼리)**
- Lambda 모니터링: Throttles는 06:10까지 거의 0, 06:11에 최대 9,964(S3 과부하 — 의도한 거절). **총 동시 실행 수는 06:04~06:11 내내 1분 최대 10** — S2(50 rps, 평균 약 2칸)에서도 매분 한 번은 10칸이 찼다. 오류 0·성공률 100%.
- Logs Insights 1초 집계: S2 구간(06:04:30~06:09:30) 초당 성공 호출은 최대 58(평균 50) — **1초 단위로는 고르게 도착했다**. S3 구간은 초당 103~120(과부하에서 서버가 실제로 처리한 순간 최대).
- 그래서 S2 거절 47건(약 0.3%)은 1초보다 짧은 몰림(약 40ms 안에 10개 이상)이나 호출당 부가 시간(실행 시간 밖에서 자리를 잡는 시간) 중 하나로 보이지만, 1초·1분 단위 지표로는 가릴 수 없어 **원인 미확인으로 둔다**. 측정 PC가 아닌 곳(클라우드 러너)에서 다시 재거나 고밀도화 몰림 시나리오에서 함께 본다.

- 사용자가 Supabase 대시보드에서 **Pool Size 15**를 확인했다(무료 등급 Nano CPU 기준값). 상한 10에 여유 5 — D49의 가정과 같다.

**바꾼 것**: D50(D42 결정 4 대체), design-constants ⑫(W 40ms, 칸 수 재계산, 순간 몰림 주의), 6주차 덱 18장(실측 표시)·19장(과부하 실측 처리량, 로그인 몰림 거절 38건), STATUS 다음 할 일 5, 열린 위험의 처리 한계 줄.

**검증되지 않음**: S2 거절 47건의 원인(그 구간 콜드 스타트 없음 — Throttles·ConcurrentExecutions 그래프 미확인), S3 실제 한계(측정 PC가 먼저 막힘), 콜드 스타트 증가 원인(세션 연결 생성 시간이라는 추정). Worker 경유 지연은 재지 않았다. 부수 효과로 배포 DB에 데모 계정 refreshToken 약 1,900행이 더 생겼다(10/4처럼 그대로 둔다).

**커밋**: D50, decisions README, design-constants, 덱 생성기·슬라이드, STATUS, 이 로그.

## 123. 결제·취소 경합(R1)과 갱신 토큰 재사용(R2) — 재현 테스트로 먼저 실패시키고 고침 (2026-10-18)

**계기**: STATUS 다음 할 일 3 "고밀도 데이터로 시나리오 돌리기". engineering-risks §1의 R1·R2는 코드 읽기로만 확인한 미해결 결함이었다.

**사용자 결정(D53 방식)**: 상위 목표 = 노하우 습득(D53), 클라이언트 = 현장 사용자·사용성과 속도(D58).
- 범위: (a) R1·R2 재현 → 수정만. 화면 Playwright 점검·§4 시나리오 전부·시연 층 AuditLog는 다음으로 미룸.
- R1: 예약 행 `FOR UPDATE` 선잠금 + 결제 상태 조건부 변경(추천안). 조건부 갱신만으로는 잠금 순서가 반대로 남아 교착이 그대로라 제외.
- R2: 원자적 폐기만(추천안). 재사용 탐지로 세션 전부 끊기는 정상 경합(두 탭)도 로그아웃시키고 인증 동작 변경이라 제외.
- **사용자 설명**(2026-10-18, 작업 후 대화에서 풀이를 듣고): R1 — "순서가 반대라 서로 기다렸다". R2 — "탭 두 개로 로그아웃되면 불편하다".

**한 일**:
1. **순서를 고정하는 재현 도구** `apps/api/test/helpers/row-lock.ts` — `Promise.all`만으로는 두 요청이 실제로 겹칠지 운이다. 테스트가 별도 연결로 대상 행을 `FOR UPDATE`로 잡고, 요청들이 그 행에서 기다리는 것을 `pg_stat_activity`(`wait_event_type = 'Lock'`)로 확인한 뒤 놓는다. 먼저 보낸 요청이 먼저 락을 얻는다.
2. **재현(수정 전 코드)**: 세 테스트 모두 예측대로 실패.
   - 결제 먼저 → 취소: 취소가 락 전에 읽은 PENDING으로 승인 건을 `FAILED`로 덮어씀(기대 REFUNDED).
   - 취소 먼저 → 결제: `40P01 deadlock detected` — 취소는 예약 → 결제, 결제는 결제 → 예약 순서로 잠가 서로 기다림. 결제가 500.
   - 같은 갱신 토큰 동시 2건: 200·200(기대 200·401).
3. **수정**:
   - `lockReservation`(prisma/integrity.ts) 신설. 결제 승인(`payment.service.ts` mockPay)·취소(`reservation.service.ts` cancel) 트랜잭션 맨 앞에서 예약 행을 잠근다. 취소는 락 뒤에 결제를 다시 읽고, 결제 상태 변경은 `updateMany(where status = 읽은 값)` — 0행이면 409로 롤백. 예약및결제 ADR-RSV-07.
   - `auth.service.ts` refresh의 폐기를 `updateMany(where id, revokedAt = null)` 한 문장으로, 0행이면 401. 권한관리 ADR-AUTH-06.

**근거**: engineering-risks R1·R2, ADR-RSV-01(같은 방식의 행 락), 권한관리 A-6(1회용 rotate), RFC 9700(재사용 탐지 — 채택 안 함), D53·D58.

**검증**: 수정 후 새 테스트 3건 통과(3회 반복 통과). api 전체 jest 41개 파일 486건 통과, `nest build` 통과, eslint 오류 0(경고 1건은 기존 `src/main.ts`). R1 테스트는 고밀도 템플릿(`reservation-capacity.spec.ts`), R2는 기준 템플릿(`auth-refresh-token.spec.ts`)에서 돈다. 화면은 바뀌지 않았다.

**커밋**: `apps/api/src/prisma/integrity.ts`·`modules/payments/payment.service.ts`·`modules/reservations/reservation.service.ts`·`modules/auth/auth.service.ts`, 테스트 2파일 + `test/helpers/row-lock.ts`, 문서(예약및결제·권한관리 ADR·검증 현황·요약 카드, engineering-risks, data-integrity §6, STATUS).

## 124. 시연 데이터에 변경 이력(AuditLog) — 지금 상태에서 역으로 만들어 화면끼리 말이 맞게 (2026-10-18)

**계기**: STATUS 다음 할 일 3(c). 시연 층(D58, log/122)에 변경 이력이 없어 본사 "변경 이력" 화면이 비어 있었다.

**사용자 결정(D53 방식)**: 상위 목표 = 노하우 습득(D53). 이 화면을 보는 사람은 본사 관리자다.
- **답안지**: 실제 시스템에서 변경 이력은 변경의 부산물이라 따로 생기지 않는다. 그래서 시연 데이터도 이력과 지금 상태가 맞물려야 한다. **핵심 변수**: 이력의 "바뀐 뒤" 값이 지금 데이터와 같은가.
- 방식: 지금 데이터에서 역으로(추천안). 무작위로 독립 생성하는 안은 이력과 상태가 어긋날 수 있어 제외(예: 이력엔 "정상으로 복구"인데 자산은 수리 중).
- 이벤트: 상태와 맞물리는 4종만(추천안) — 재배치·계약 종료 지점 파견 종료·회원 상태·자산 상태. 전화번호 열람·근태 정정·인사 정보 변경 승인은 넣지 않음(근태·변경 신청 데이터까지 고쳐야 하거나 화면을 열람 기록으로 덮는다).
- 양: 화면 몇 쪽 분량(추천안).
- **사용자 설명**: 없음 — 사용자가 "그냥 너가 채워줘"라고 AI에게 맡겼다. 아래는 사용자의 설명이 아니라 **AI가 정리한 이유**다: 이력은 변경이 일어날 때 함께 남는 기록이라, 이력 화면의 "바뀐 뒤" 값과 회원·자산·직원 화면의 지금 값이 다르면 발표에서 데이터가 가짜라는 게 바로 드러난다.

**한 일**: `apps/api/prisma/demo-layer.ts`에 변경 이력 절을 추가했다. 쓰기 트랜잭션의 마지막에 넣는다.
- 별도 난수(`SEED + 1`)를 써서 기존 시연 데이터는 이 절이 있든 없든 똑같다. 기록 모양(entity·action·before·after)은 각 도메인의 `recordAudit` 호출과 같다(D44·D52).
- 재배치 `ASSIGNED` 4건: "인력 재배치" 파견 이력마다 한 건, 본사가 처리, 옮긴 날 10시.
- 파견 종료 `ASSIGNMENT_ENDED` 4건: 노원 종료일(2026-06-20)에 끝난 파견마다 한 건. 기준 시드 직원 2명과 새 직원 2명.
- 회원 상태 `MEMBER_STATUS_CHANGED` 45건: 휴면·탈퇴 회원마다 활성에서 바꾼 한 건, 그 지점 관리자가 처리. 가입일 이후 ~ 활동 기간 끝 사이의 업무 시간.
- 자산 상태 `ASSET_STATUS_CHANGED` 27건: 정상이 아닌 자산마다 한 건. 폐기는 "폐기 대기"를 거쳐 2건(전이표 `STATUS_TRANSITIONS`). 계약 종료 지점의 폐기 대기는 종료 뒤 본사가 처리한 것으로 둔다.
- 기준 시드(히어로) 행에는 이력을 만들지 않는다.
