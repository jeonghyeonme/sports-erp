# 18. 강사프로그램게시 3개 ADR(PRG-01~03)을 전부 구현했다 (2026-09-25)

> [진행 로그 인덱스](README.md)

**계기**: §17에 이어 같은 방식(ADR 한 개씩 구현→리뷰→수정→보고→다음)으로 강사프로그램게시 도메인을 처리. 이 도메인 문서의 우선순위(무비용 순)를 따라 PRG-03 → PRG-01 → PRG-02 순서로 진행했다.

**PRG-03(facilityId 검증)**: `assertInstructorInBranch`와 완전히 같은 형태로 `assertFacilityInBranch`를 추가하고 `createProgram`·`updateProgram`에 연결했다 — 새 개념 없이 기존 패턴을 그대로 복제한 가장 낮은 리스크의 변경.

**PRG-01(capacity 필수 검증)**: `assertCapacityForPricingType` 헬퍼를 만들어 생성·수정 두 곳에서 호출했다. **구현하다가 `updateProgram`의 기존 버그를 발견했다** — 이 함수가 필드마다 "검증 → 즉시 반영"을 순서대로 하고 있어서, 뒤쪽 필드(capacity) 검증이 실패해도 앞쪽 필드(name·category 등)는 이미 mutable `program` 객체에 반영된 뒤였다. 즉 PATCH가 400을 반환하면서도 일부 필드는 조용히 바뀌는 반쪽 수정 결함이 새 검증을 추가하기 전부터 있었다(PRG-03의 facilityId 검증도 같은 구조라 잠재적으로 이미 노출돼 있었을 것). 모든 검증을 먼저 끝내고 한 번에 필드를 반영하도록 함수 구조를 바꿔 해소했고, `program-integrity.spec.ts`에 "검증 실패 시 다른 필드도 반영 안 됨" 케이스를 넣어 회귀를 고정했다.

**PRG-02(상태전이 확정예약 가시화)**: `futureActiveReservationsForProgram`을 추가하면서, ADR 원문이 "상태 전이 응답"이라고만 적어놨던 범위를 `PATCH /status`뿐 아니라 `DELETE`(소프트 ENDED 전이)까지 넓혔다 — ENDED도 PAUSED와 똑같이 disruptive한 전이인데, 문구를 문자 그대로만 따르면 절반만 고치는 셈이라고 판단했다(§16 ADR-BRD-01 때의 "결정 자체는 그대로, 구현 시 스펙이 놓친 세부는 채운다"는 판단 기준과 같은 결). admin-web에도 값을 그대로 알람으로 보여주는 로직을 넣었다 — ADR-BRD-01·ADR-FAC-01에서 반복 확인한 교훈("플래그·값만 만들고 화면에서 못 보면 요건 검증이 여전히 불가능")을 세 번째로 적용한 사례.

**검증**: `apps/api/test/program-integrity.spec.ts` 신규 파일, 3개 ADR 합쳐 15건(PRG-03 4 + PRG-01 7 + PRG-02 4). `npm run test`(14 suites, **194 passed**), `eslint`·`nest build`·admin-web `tsc -b && vite build` 전부 클린. 매 ADR 구현 직후 diff를 다시 읽으며 자체 리뷰했다 — PRG-01에서 위의 부분수정 버그를 그 리뷰 과정에서 찾았다(코드를 옮기다가 "검증이 실패하면 이미 반영된 앞쪽 필드는 어떻게 되지?"라는 질문이 생겨서 확인함).

**커밋**: `27ef4e2`(PRG-03), `8588c92`(PRG-01), 이 절을 포함한 커밋(PRG-02).
