# 16. ADR-BRD-01(회원 대상 공지 가시성 결함)을 수정했다 (2026-09-25)

> [진행 로그 인덱스](README.md)

**계기**: §15에서 발견해둔 8개 ADR 중 실제 정보 노출 결함인 ADR-BRD-01이 가장 급하다고 판단해 사용자가 우선 지정. "구현 작업 원칙"에 따라 [domains/게시판.md](../domains/게시판.md) §8의 기존 결정(대안 B — `visibleToMember` 플래그, 전면 차단 대신 선택적 공개)을 그대로 코드로 옮겼다.

**구현**: `MockPost.visibleToMember: boolean`(기본 false) 추가. `PostsController`에 `isVisibleTo(post, user)` 헬퍼를 만들어 `list()`와 `findVisibleOrThrow()`(상세·수정·삭제 공용)가 공유하게 했다 — MEMBER role일 때만 `scope==='BRANCH_TO_MEMBER' || visibleToMember===true`를 추가로 요구하고, STAFF·BRANCH_ADMIN은 기존과 동일하게 지점 소속만으로 판정(불변규칙은 "회원에게 비공개"이지 "직원에게 비공개"가 아니므로). `MockDataService.createPost`는 `BRANCH_TO_MEMBER`(지점 공지)는 scope 자체로 이미 회원에게 노출되므로 `visibleToMember`를 항상 true로 강제하고, `HQ_TO_BRANCH`(본사 공지)만 호출자가 지정한 값(미지정 시 false)을 쓴다. `CreatePostDto.visibleToMember`(옵션, SUPER_ADMIN만 의미 있음)를 추가하고, admin-web `BoardPage`의 작성 폼에 SUPER_ADMIN 전용 "회원에게도 공개" 체크박스를 달았다 — 플래그를 만들어놓고 UI에서 절대 true로 못 만들면 "모든 HQ 공지가 회원에게 영구히 안 보이는" 새로운 결함이 되므로, 최소 구현 범위에 이 체크박스까지 포함시켰다(수정 화면에서 토글하는 기능은 이번 범위 밖 — ADR이 다룬 건 작성 시점 판단이었다).

**부수 발견**: 구현 중 §15의 BRD-T03(계약종료 지점 신규 게시 차단) 진단이 오판이었음을 확인했다 — `createPost`의 컨트롤러 쪽만 보고 "차단 없음"이라고 적었지만, 실제 체크는 서비스 계층(`MockDataService.createPost`)에 이미 있었고 `contract-termination.spec.ts`가 이미 이 케이스를 통과시키고 있었다. 코드 구현 전에는 "테스트가 통과하면 검증됨"이 맞지만, **진단(구현 안 됨 판정) 자체도 테스트 실행이나 전체 호출 경로 추적 없이 컨트롤러만 읽고 내리면 틀릴 수 있다**는 사례로 기록해둔다. 문서(§6·§11·부록 A-3)를 정정했다.

**검증**: 새 회귀 테스트 `apps/api/test/posts-member-visibility.spec.ts` 7건 — 시드된 직원 전용 HQ 공지가 회원 목록/상세에서 빠지는지, 같은 공지가 본사관리자·지점관리자·직원에게는 보이는지(대조군), 회원이 본인 지점 지점공지는 그대로 보는지, `visibleToMember=true`로 작성한 HQ 공지가 회원에게 노출되는지, 플래그 미지정 시 기본값 false인지. `npm run test`(12 suites, **163 passed**, 기존 1 todo 포함 164), `eslint`(api·admin-web 둘 다 0 errors — api에 사전부터 있던 `main.ts`의 무관한 warning 1건 제외), `nest build`·`tsc -b && vite build` 둘 다 성공.

**남은 것**: ADR-BRD-02(페이지네이션)가 게시판 도메인의 마지막 미구현 ADR. 자원문서관리(9번째 도메인) 사이클은 여전히 미착수.
