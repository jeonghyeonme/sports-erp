# 45. D31 — 시설·강사·프로그램·회차 이관: 같은 미러 패턴, 그리고 D28 CHECK가 잡아낸 생성 데이터 결함 (2026-09-29)

> [진행 로그 인덱스](README.md)

**계기**: D29 순서의 3단계. 네 엔티티 모두 쓰기 API가 있고, 아직 mock인 예약·결제·회원·지점 건수가 동기적으로 읽는다. D30 직원과 같은 조건이라, 새 패턴을 만들지 않고 **D30 결정 1(DB 원천 + mock 미러)을 그대로 재사용**했다(상세: 2-1 D31). 새로 검토한 대안은 "예약까지 같이 옮기기"였다. 예약은 회원(4단계)을 참조하므로, 예약만 옮기면 D29가 막으려던 "참조되는 쪽이 아직 mock" 상태가 반대 방향으로 생긴다. 그래서 기각했다.

**구현**: `FacilityService`·`InstructorService`·`ProgramService`(회차 포함)를 만들고 세 컨트롤러를 옮겼다. 자기 조회 API는 DB에서 읽는다. mock의 해당 쓰기 메서드는 지웠고, 검증 규칙(ADR-PRG-01~03, ADR-FAC-01~03, 강사프로그램게시 A-3 전이표·§6 가격 정규화, 혼잡도관리 A-6 5단계)은 문구·순서 그대로 옮겼다. 미러 갱신 헬퍼(`src/mock-data/mirror.ts`)는 배열 참조를 유지한다. mock 독자가 `mockData.programs` 배열을 그대로 들고 읽기 때문이다.

- **ADR-STF-04 숙제 해소**: D30 파견 트랜잭션은 DB 강사만 정리하고 mock 강사는 못 건드렸다. mock 강사 타입에 직원 연결 필드가 없었기 때문이다. 이제 강사 원천이 DB라, 연결을 푼 강사 id를 트랜잭션에서 돌려받아 커밋 뒤 미러에 반영한다.
- **상태 전이 조건부 갱신**: mock은 단일 스레드라 "읽고 → 전이표 확인 → 쓰기" 사이에 끼어들 틈이 없었다. DB에서는 두 요청이 같은 옛 상태를 읽고 둘 다 통과할 수 있다. 그래서 `updateMany({ where: { id, status: 읽은 값 } })`로 바꿨다. 새 동작이지만 전이표(강사프로그램게시 A-3)를 DB 동시성 아래에서도 지키기 위한 최소한이다. 동시 전이 테스트는 없어 **검증되지 않음**.
- **알 수 없는 필터값**: mock은 `?status=없는값`이면 빈 목록이었는데, Prisma는 enum 밖 값에 500을 낸다. 서비스에서 먼저 걸러 예전 동작(빈 목록)을 유지했다.

**발견 — D28 CHECK가 잡은 생성 데이터 결함**: 첫 시드가 `Program_paid_session_capacity_ck` 위반으로 실패했다. mock 생성기가 96개 지점의 PAID_SESSION 프로그램을 **정원 없이** 만들고 있었다. ADR-PRG-01이 API로는 막아 둔 상태가 데모 데이터에는 그대로 있었던 것이다. mock 예약은 회차 정원으로 검사해서 드러나지 않았다. 다만 이 프로그램들에 회차를 추가하려 하면 `INVALID_CAPACITY`가 났을 것이다. §43(순서 오류를 FK·트리거가 드러냄)에 이어, **DB 제약이 mock 시절의 암묵적 결함을 드러낸 두 번째 사례**다. 생성기가 정원(10/15/20)을 넣도록 고쳤다.

**데이터 원천 통일**: seed.ts의 서초 시설·프로그램 값이 mock과 달랐다(요가 설명 없음, 헬스장 현재 인원 0, 강사 id가 uuid). D29 지점 때와 같은 종류의 차이다. mock 값을 기준으로 `catalog-fixtures.ts` 한 곳에서 만든다. 박서연 강사는 `instructor-seoyeon`, 직원 연결 `staff-seoyeon`이다.

**테스트**: 미러 배열을 직접 고치던 테스트 2곳(`reservation-capacity`의 미래 회차 추가, `program-integrity`의 회차 날짜 되돌리기)을 Prisma로 쓰고 `ProgramService.onModuleInit()`으로 미러를 다시 채우게 바꿨다. 두 스위트는 DB에 쓰므로 매 테스트 `resetWorkerDb()`를 부른다. 새 `catalog-mirror.spec.ts` 5건은 네 가지를 본다: 미러-DB 일치, 상태 전이 → mock 예약 `PROGRAM_NOT_RUNNING`, 새 회차 → mock 예약 가능, 파견 → 강사 미러. **미러 갱신 한 줄을 일부러 빼면 상태 전이 테스트가 실패함을 확인했다**(테스트가 실제로 미러 누락을 잡는다는 증거).

**검증**: 전체 276 통과(271 + 5), skip 0. 격리·계약 종료·인사 권한 테스트는 기대값 변경 없이 통과했다. api lint 에러 0(경고 1건은 기존 `main.ts`), api·admin-web 빌드 성공. 응답 형태(`branchName`·`instructorName` 포함)는 그대로라 admin-web 변경은 없다. 다만 화면에서 직접 확인하지는 않았다(**검증되지 않음**). 목록 순서는 mock 배열 순서에서 id 순으로 바뀌었다.

**Supabase 시드**: 사용자 승인 뒤 적용했다. D30과 같은 방식이다. `catalogSeed()`로 upsert SQL을 만들고, 마이그레이션만 적용한 빈 로컬 DB(지점·직원 선적용)에서 두 번 돌려 멱등성을 확인했다. `prisma db seed` 결과와 지문(행 수 + 필드 md5)이 같은지도 확인했다. 프로그램 설명은 7종이 반복돼 사전으로 빼 SQL 크기를 줄였다. 적용 후 Supabase 지문이 로컬과 4개 테이블 모두 같다(시설 99, 강사 97, 프로그램 149, 회차 2). 비교에서 생성 시설의 `lastUpdatedAt`은 제외했다. 시드 실행 시각이라 로컬과 다를 수밖에 없다. 생성 프로그램 개강일은 시드한 날 기준으로 고정된다(D30과 같다). seed.ts가 로컬에만 만드는 예약·결제·PT 데모 행과 그 회차 1건은 회원 단계 소관이라 Supabase에 넣지 않았다.
