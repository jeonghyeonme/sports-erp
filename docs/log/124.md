# 124. 시연 데이터에 변경 이력(AuditLog) — 지금 상태에서 역으로 만들어 화면끼리 말이 맞게 (2026-10-18)

> [진행 로그 인덱스](README.md)

**계기**: STATUS 다음 할 일 3(c). 시연 층(D58, log/122)에 변경 이력이 없어 본사 "변경 이력" 화면이 비어 있었다.

**사용자 결정(D53 방식)**: 상위 목표 = 노하우 습득(D53). 이 화면을 보는 사람은 본사 관리자다.
- **답안지**: 실제 시스템에서 변경 이력은 변경의 부산물이라 따로 생기지 않는다. 그래서 시연 데이터도 이력과 지금 상태가 맞물려야 한다. **핵심 변수**: 이력의 "바뀐 뒤" 값이 지금 데이터와 같은가.
- 방식: 지금 데이터에서 역으로(추천안). 무작위로 독립 생성하는 안은 이력과 상태가 어긋날 수 있어 제외(예: 이력엔 "정상으로 복구"인데 자산은 수리 중).
- 이벤트: 상태와 맞물리는 4종만(추천안) — 재배치·계약 종료 지점 파견 종료·회원 상태·자산 상태. 전화번호 열람·근태 정정·인사 정보 변경 승인은 넣지 않음(근태·변경 신청 데이터까지 고쳐야 하거나 화면을 열람 기록으로 덮는다).
- 양: 화면 몇 쪽 분량(추천안).
- **사용자 설명**: 없음 — 사용자가 "그냥 너가 채워줘"라고 AI에게 맡겼다. 아래는 사용자의 설명이 아니라 **AI가 정리한 이유**다: 이력은 변경이 일어날 때 함께 남는 기록이라, 이력 화면의 "바뀐 뒤" 값과 회원·자산·직원 화면의 지금 값이 다르면 발표에서 데이터가 가짜라는 게 바로 드러난다.

**한 일**: `apps/api/prisma/demo-layer.ts`에 변경 이력 절을 추가했다. 쓰기 트랜잭션의 마지막에 넣는다.
- 별도 난수(`SEED + 1`)를 써서 기존 시연 데이터는 이 절이 있든 없든 똑같다. 기록 모양(entity·action·before·after)은 각 도메인의 `recordAudit` 호출과 같다(D44·D52).
- 재배치 `ASSIGNED` 4건: "인력 재배치" 파견 이력마다 한 건, 본사가 처리, 옮긴 날 10시.
- 파견 종료 `ASSIGNMENT_ENDED` 4건: 노원 종료일(2026-06-20)에 끝난 파견마다 한 건. 기준 시드 직원 2명과 새 직원 2명.
- 회원 상태 `MEMBER_STATUS_CHANGED` 45건: 휴면·탈퇴 회원마다 활성에서 바꾼 한 건, 그 지점 관리자가 처리. 가입일 이후 ~ 활동 기간 끝 사이의 업무 시간.
- 자산 상태 `ASSET_STATUS_CHANGED` 27건: 정상이 아닌 자산마다 한 건. 폐기는 "폐기 대기"를 거쳐 2건(전이표 `STATUS_TRANSITIONS`). 계약 종료 지점의 폐기 대기는 종료 뒤 본사가 처리한 것으로 둔다.
- 기준 시드(히어로) 행에는 이력을 만들지 않는다.

**검증**:
- 별도 DB(`sports_erp_demo`, 기준 DB 아님)에 `seed:demo` → 80건. SQL 점검 7항목 모두 0건: 최신 이력의 "바뀐 뒤" 상태와 현재 상태 불일치, 재배치 이력의 지점과 현재 지점 불일치, 미래 시각, 가입 전 회원 이력, 취득 전 자산 이력, 이력 없는 휴면·탈퇴 시연 회원, 이력 없는 비정상 시연 자산.
- 처리자 역할: 회원 상태는 지점 관리자만(API `@Roles('BRANCH_ADMIN')`과 같음), 재배치·파견 종료는 본사.
- 화면: 이 DB로 api·admin-web을 띄워 본사 계정으로 "변경 이력"을 Playwright로 열었다 — 4쪽 80건. 대상 이름·지점·전후 상태·처리자가 나온다(수동 확인, 자동 테스트 없음).
- api jest 41개 파일 486건 통과(고밀도 템플릿에도 이 절이 들어간다), `tsc --noEmit` 통과. `prisma/`는 eslint 대상이 아니다.
