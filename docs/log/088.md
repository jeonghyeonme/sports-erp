# 088. 쌓이는 목록 페이지네이션 — 회원·예약·결제·자산, 결제 날짜 필터를 DB 조건으로 (2026-10-09)

> [진행 로그 인덱스](README.md)

**계기**: 브리프 B8. D43이 정한 대로 쌓이는 목록 4개에 offset 페이지네이션을 넣는다. 결제 목록의 메모리 날짜 필터는 DB 조건으로 내린다(ADR-RSV-04). D43이 "B8에서 정한다"고 남긴 화면 결정을 사용자에게 받았다.

**사용자 결정(2026-10-09)**

| 질문 | 답 |
|---|---|
| 회원·자산 목록 화면 | 지점별 아코디언 → **표 하나 + 지점 필터(본사만) + 검색·상태 필터 + 쪽 넘김** |
| 지점 상세의 직원별 회원 | 회원 전체를 받지 않고 **직원을 펼칠 때 그 직원 회원만**(`assignedStaffId` 필터, `none` = 미배정) |
| 예약·결제 정렬 | **최근 것부터**(D43 결정 2의 미결) |
| 자산 폐기 | **기본 목록에서 빼고** `status=DISPOSED`로 따로(D43 결정 4의 미결) |

- 모두 D43 안의 미결 항목을 채운 것이어서 새 D 번호는 쓰지 않았다. D43 파일은 고치지 않고(D38) 인덱스 상태만 "구현"으로 바꿨다.

**한 일**

1. **api**
   - 공통 `common/http/pagination.ts`의 `parsePage`·`pageMeta`: `page`·`limit`, 기본 20, 상한 100. 잘못된 값은 1·20으로 바꾼다.
   - 4개 서비스의 `list`가 `{ items, total }`를 돌려주고 `count` + `skip/take`를 쓴다. 정렬에는 `id`를 덧붙여 쪽 경계가 흔들리지 않게 했다.
   - 회원: `assignedStaffId` 필터를 더했다(새 라우트가 아니라 기존 라우트의 쿼리다. 지점 범위는 BranchScopeGuard가 그대로 강제한다).
   - 자산: 상태를 지정하지 않으면 DISPOSED를 뺀다.
   - 예약·결제: `createdAt desc`로 정렬한다.
   - 결제 날짜 필터: `kstDayRange`(kst-date.ts에 새로 추가)로 KST 하루 경계를 만들어 `approvedAt` 범위 조건으로 넣었다.
     - 미승인 건은 `approvedAt IS NULL OR 범위`로 예전처럼 남는다.
     - 형식이 틀린 날짜는 빈 목록을 준다. 예전에는 문자열 비교라 결과가 이상했다.
2. **admin-web**
   - 공통: `useApiPage`(쪽 + total, 쪽을 넘길 때 이전 데이터 유지), `Pager`, `BranchFilter`.
   - 회원: 지점·상태·검색(이름·회원번호·전화, 제출할 때) 필터를 서버 조건으로 바꿨다.
   - 자산: 지점과 상태 칩("보유 중(폐기 제외)"이 기본)을 쓴다.
   - 예약 관리의 목록 3개와 회원 상세 예약 탭에 쪽 넘김을 붙였다. 역할에 맞는 목록만 부른다(예전에는 세 목록을 다 불렀다).
   - 지점 상세
     - 직원을 펼칠 때만 그 직원 회원 쪽을 부른다. "담당 없음"은 `none`으로 부른다.
     - 미처리 자산 수는 자산 기본 목록의 total이다(`limit=1`, ADR-RES-01).
3. **member-web**
   - 내 예약은 `limit=100`(상한)으로 한 번에 받는다. 100건을 넘으면 "최근 100건만" 안내를 보인다.
   - 결제 화면이 예약을 다시 찾을 때는 첫 쪽만 본다. 최근 것부터 오므로 방금 만든 예약이 첫 쪽에 있다.

**`Payment(approvedAt)` 인덱스는 넣지 않았다**(스키마 변경, 승인 대상)
- 이제 비용은 쪽 크기와 지점 범위 조인에 묶인다.
- 시드에는 결제가 없어 실측할 대상이 없다.
- 결제가 수만 건 쌓여 날짜 조회가 느려지면 다시 본다.

**근거**: D43, ADR-RSV-04, ADR-BRD-02(같은 형식), D32 결정 5(KST), ADR-RES-01, ADR-MEM-04(목록 마스킹 유지).

**검증**
- api: jest 전체를 통과했다(커밋 hook).
  - 새 `list-pagination.spec.ts` 10건:
    - 회원 쪽·total·마지막 쪽·쪽 사이 중복 없음
    - limit 상한 100·잘못된 값 대체
    - 담당 직원·none 필터, 지점 관리자 total
    - 자산 기본 폐기 제외·DISPOSED 따로
    - 예약 최근 것부터
    - 결제 KST 00:30 승인 건이 그 날짜로 걸림·미승인 건 포함·전날 대조군·최근 결제부터·형식 오류는 빈 목록
  - `kst-date.spec`에 경계 2건을 더했다.
  - `branch-isolation`의 기존 케이스는 그대로 통과했다(지점 범위 변경 없음).
- admin-web·member-web: lint·빌드를 통과했다.
- 1280px Playwright(로컬 api + dev DB)로 확인한 것:
  - 본사 회원 169명이 9쪽으로 나뉘고, 다음 쪽과 검색이 동작한다.
  - 자산 화면을 연다.
  - 지점 상세: 진입 때 "담당 없음"만 부르고, 직원을 펼치면 그 직원 쪽을 1회 부른다.
  - 예약 관리에서는 지점 관리자에게 필요한 목록만 부른다.
- 화면은 자동 테스트가 없어 **검증되지 않음(수동 확인)**이다.

**배포 순서 주의**
- api(Lambda)는 병합하면 배포되고, 화면(Worker)은 사용자가 따로 배포한다.
- 그 사이 이미 배포된 admin-web·member-web은 배열 응답을 그대로 읽어서 깨지지 않는다. 다만 목록이 첫 20건만 보인다.
- 회원 웹은 아직 배포 전이다.
