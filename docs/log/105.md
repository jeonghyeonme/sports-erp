# 105. Lambda DB 접속을 Session pooler로 — 로컬 검증, 배포 스크립트 검사, 목록 일괄 트랜잭션 되돌리기 (2026-10-11)

> [진행 로그 인덱스](README.md)

**계기**: D48 A안(`pgbouncer=true` 제거)을 사용자가 승인했다(2026-10-11, "A1 해보고 확실성 체크"). 세션 모드(A1)와 트랜잭션 모드에서 플래그만 빼는 안(A2)의 차이, driver adapter 안(A3)은 대화에서 설명했다.

**한 일** — 결정은 [D49](../decisions/D49.md)
- D48 B2의 목록 count + findMany 일괄 트랜잭션(공지·예약·회원)을 `Promise.all`로 되돌렸다. B1(인증 조회 합치기)과 공지 작성자 include는 그대로다.
- `aws-lambda/set-lambda-env.sh`의 URL 검사를 바꿨다. 허용: Session pooler(5432) + `connection_limit=1`, 이전 형식 6543 + `pgbouncer=true`(되돌리기용). 중단: 6543에서 플래그 누락(log/056 장애), 5432 + `pgbouncer=true`, `connection_limit`이 1이 아닌 값(예: 10), 직접 연결. 검사부만 떼어 6가지 URL로 확인했다.
- `aws-lambda/README.md`·`CLI-RUNBOOK.md`·`apps/api/.env.example`의 접속 문자열 안내를 Session pooler로 고쳤다.
- 측정 스크립트는 임시로 만들어 쓰고 지웠다(사용자 결정: 저장소에 넣지 않음).

**확실성 확인**
1. 로컬, 세션 모드와 같은 조건(`pgbouncer=true` 없음, `connection_limit=1&pool_timeout=5`)으로 jest 전체를 돌렸다. 410건 중 409건 통과, P2024·prepared statement 오류 0. 실패 1건은 `integrity-helpers`의 "락이 없으면 정원을 넘는다" 대조군이다. 연결이 1개라 경합이 재현되지 않는 것으로, D37 R1에 기록된 예상 결과다.
2. 순차 왕복(로컬 실측, 왕복당 10ms 지연 주입으로 역산, 7회 중앙값) — 운영(현재) 값은 [log/102](102.md)의 "후" 열이다.

| 라우트 | 현재(6543 + `pgbouncer=true`) | Session pooler |
|---|---|---|
| POST /auth/login | 17.1 | 4.8 |
| POST /auth/refresh | 21.2 | 4.4 |
| GET /auth/me | 9.2 | 3.3 |
| GET /facilities | 15.1 | 5.1 |
| GET /posts?sort=latest&limit=3 | 18.7 | 6.6 |
| GET /programs?status=RUNNING | 16.8 | 5.8 |
| GET /programs/:id/slots | 17.5 | 5.0 |
| POST /reservations | 41.2 | 17.2 |
| POST /payments/:id/mock-pay | 36.1 | 14.2 |
| GET /reservations?limit=20 | 23.6 | 10.0 |
| PATCH /reservations/:id/cancel | 42.6 | 18.3 |
| k6 S2 조회 4종 평균 | 16.8 | 5.9 |

3. Supabase 문서(search_docs): 세션 모드는 클라이언트당 전용 연결이고 prepared statement를 지원한다. 세션 모드 동시 클라이언트는 Pool Size로 제한된다. Supavisor 트랜잭션 모드는 prepared statement를 지원하지 않는다 → A2 기각의 근거.
4. 배포 DB 읽기 전용 조회 1회(SELECT): `max_connections` 60, 연결 15개(대부분 Supabase 내부, 유휴). Pool Size 값은 SQL로 보이지 않는다 — **대시보드 확인 필요**.

**근거**: D48(원인·A안), D37 결정 1·R1·R2, D42(상한 10), log/056(42P05 장애).

**검증**
- 기본 설정 jest 35 스위트 410건 통과, api lint 오류 0(기존 경고 1), 빌드 성공.
- **검증되지 않음**: 운영 전환(Lambda 환경 변수)과 운영 k6 S2. 기대 W 약 50~60ms·처리 한계 약 100 rps는 풀러 왕복 4ms 가정의 추정이다.

**남은 일(사용자)**: 대시보드 Database Settings에서 Pool Size 확인(10 + 여유) → `aws-lambda/.env`의 `LAMBDA_DATABASE_URL`을 Session pooler 문자열로 → `bash aws-lambda/set-lambda-env.sh` → Actions 재배포 → k6 S2·CloudWatch 확인. 되돌리기는 이전 값으로 같은 절차.

**커밋**: posts·reservations·members 서비스, auth.service 주석, `aws-lambda/`(스크립트·README·런북), `.env.example`, 문서(D49, STATUS).
