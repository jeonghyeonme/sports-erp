# 19. ADR-BRD-02(게시글 목록 페이지네이션)를 구현하고, §15~18의 7개 ADR 정리 사이클을 마쳤다 (2026-09-25)

> [진행 로그 인덱스](README.md)

**계기**: §16~18에서 순서대로 처리해온 7개 ADR의 마지막 항목.

**구현**: `GET /posts`에 `page`/`limit` 쿼리를 추가하고 `ok(items, {page, pageSize, total})`로 응답한다(기본 `limit=20`). **구현하다가 죽은 코드를 하나 발견했다**: `common/interceptors/response.interceptor.ts`의 `ResponseInterceptor`가 정확히 이 용도(`Paginated<T>` → `meta` 자동 변환)로 이미 만들어져 있었는데, `main.ts`·`app.module.ts`·`test/helpers/app.ts` 어디에도 등록돼 있지 않아 한 번도 실행된 적 없는 코드였다. 지금 등록하면 이 프로젝트 전체 컨트롤러 응답 경로에 영향을 주는 변경이 되므로(이번 ADR이 요구하는 범위를 넘어섬), 손대지 않고 다른 도메인과 같은 방식(`ok()` 직접 호출)으로 구현했다 — 이 죽은 코드 정리는 별도 판단 대상으로 남겨뒀다.

**admin-web 회귀 방지**: `BoardPage`가 그동안 전체 게시글을 한 번에 받아 클라이언트에서 `scope` 필터링하던 방식이었는데, 서버가 페이지 단위로 자르기 시작하면 그대로 둘 경우 **21번째 글부터 화면에서 조용히 사라지는 회귀**가 생긴다. `scope` 필터를 서버 쿼리로 옮기고 이전/다음 페이지 버튼을 추가해 회귀를 막았다 — §16(ADR-BRD-01)·§17(ADR-FAC-01)·§18(ADR-PRG-02)에서 반복 확인한 "값만 만들고 화면에서 못 쓰면 결정 취지가 실제로 성립하지 않는다"는 같은 판단을 네 번째로 적용한 사례.

**검증**: `apps/api/test/posts-member-visibility.spec.ts`에 ADR-BRD-02 절 5건 추가(기본 limit·page 이동·limit 지정·scope와 조합·잘못된 값 방어). `npm run test`(14 suites, **199 passed**), `eslint`·`nest build`·admin-web `tsc -b && vite build` 전부 클린.

**7개 ADR 정리 사이클 종합**: §15에서 발견한 8개 ADR 중 ADR-BRD-01(§16)을 먼저 처리하고, 이어서 나머지 7개(§17~19)를 "구현 → 리뷰 → 수정 → 보고 → 다음"으로 하나씩 처리해 전부 닫았다. 이 과정에서 구현과 무관하게 **기존 코드에서 발견한 것 세 가지**를 함께 기록해둔다: (1) 게시판 BRD-T03(계약종료 차단) 최초 진단이 컨트롤러만 보고 내린 오판이었음(§16), (2) 강사프로그램게시 `updateProgram`의 부분수정 결함(§18), (3) 응답 인터셉터가 죽은 코드였음(이 절). 셋 다 이번 ADR 구현과 직접 관련 없는 코드를 리뷰하다가 우연히 걸린 것들이라, "구현 전 Driver/ADR 인용 → 구현 → 리뷰" 사이클의 리뷰 단계가 실제로 별도의 결함을 잡아내는 안전망으로 작동했다는 근거로 남긴다.

**커밋**: 이 절을 포함한 커밋(BRD-02).
