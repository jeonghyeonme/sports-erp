# 106. RFP 원본 재대조 — 누락 5건을 추적표에 추가, 시연 데이터 고밀도화를 계획으로 남김 (2026-10-11)

> [진행 로그 인덱스](README.md)

**계기**: 발표 준비 중 사용자가 RFP·요구사항 정의서에서 놓친 기능이 없는지 물었다. 원본 PDF p.3~7(요구사항 표·개념도·산출물 표)을 요구사항추적표와 지금 코드에 다시 맞대 봤다.

**찾은 것**(요구사항추적표 §2-3에 추가)
- **업무지원 요청**(개념도 p.4, 현장→본사): 코드·설계 문서 어디에도 없었다.
- **관리자의 직원 업무일지 열람**: API는 허용하는데 관리자 웹은 본인 일지만 보여 준다. 그래서 "API는 있고 화면이 없는 것: 없음"이라던 문장이 틀렸다.
- **종목·시간대·연령대별 프로그램 목록**: 부분 구현이다(목록 필터 없음).
- **처리 느린 작업의 사용자 사전 알림**: 운영자 경보만 있다.
- **이용자 매뉴얼 앱 탑재**: 관리자 웹 도움말만 있다.
- 추적표의 어긋난 문장도 고쳤다: "계약 종료 시 파견 종료 미구현" → 2026-10-10 구현됨.

**사용자 방향(2026-10-11)**: 지금 시드는 83곳 중 81곳이 직원 1~3명·회원 0~4명·이력 없는 이름표다. 회원 수·직원 배치를 모르는 채로 규모만 채운 셈이다.
- 그래서 계약 상태별 지점 5곳(정상 2·갱신 임박·만료·종료)을 밀도 있게 다시 만든다.
- 그 시나리오로 위 누락을 채운다.
- **판단 근거(사용자)**: 실제 서비스를 하려면 어차피 인프라에 투자해야 하고, 그때는 무료 한도(D40의 83곳 산정 기준) 같은 제약이 의미를 잃는다. 실제로 쓰이려면 먼저 한 지점이 밀도 있고 빠르고 불편 없이 돌아가는 시스템을 만들고, 규모는 그 위에서 늘리는 게 맞다. 무료 한도는 시연 환경의 제약이지 서비스의 기준이 아니다.
- **지금은 계획만** 남긴다(STATUS 다음 할 일 2). 착수할 때 D21·D40의 데이터 부분을 대체하는 새 결정 번호로 기록한다.
- 시연 데이터의 지점 수와 설계 규모(83곳 기준 요청량·처리 한계, D37·D40·D42)는 분리한다.

**하지 않은 것**: 코드·시드 변경 없음, 배포 DB 쓰기 없음. 발표 슬라이드에는 이 누락을 넣지 않기로 했다(사용자).
