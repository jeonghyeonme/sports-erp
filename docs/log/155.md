# 155. Lambda 배포 실패(health 502) — sanitize-html의 ESM 전용 파서를 CommonJS 판으로 고정 (2026-10-22)

> [진행 로그 인덱스](README.md)

**계기**: log/154(PR #107) 병합 직후 api 배포 #53이 health check 502로 실패했고, 워크플로가 별칭 `live`를 이전 버전 49로 자동 복귀했다. 그 사이 새 버전 50의 오류 1건으로 CloudWatch 경보 `sports-erp-api-Errors`가 울렸다(사용자가 메일 전달). 운영은 복귀 뒤 옛 버전으로 계속 동작 — 서식 본문 정화(D62)는 아직 운영에 없다.

**원인**: `sanitize-html` 2.18.1이 쓰는 `htmlparser2` 12는 ESM 전용이다. 로컬 Node 22.22는 CommonJS에서 ESM을 `require`할 수 있어(require(esm)) 빌드·jest·e2e가 모두 통과했지만, Lambda Node 22 런타임에서는 부팅 중 `require`가 실패한 것으로 본다 — 로컬에서 `node --no-experimental-require-module`로 묶음을 읽으면 같은 자리에서 `ERR_REQUIRE_ESM`이 난다. Lambda 로그(CloudWatch)는 이 세션에서 볼 수 없어 **추정**이다(배포 성공으로 간접 확인 예정). log/154의 "Node 22의 require(esm)로 Lambda 번들은 그대로 돈다"는 로컬 Node로만 확인한 틀린 결론이었다.

**한 일**:
- 루트 `package.json` `overrides`로 `htmlparser2`를 10.1.0(CommonJS·ESM 둘 다 내보냄)에 고정. `sanitize-html`은 2.18.1 그대로(2.17.x 이하 XSS 권고 회피는 유지). 잠금 파일은 npm으로 다시 풀었다(손으로 고치지 않음).
- log/154에서 넣은 jest ESM 변환 예외를 되돌렸다(이제 필요 없음).
- `scripts/package-lambda.sh`가 zip 전에 묶음을 `--no-experimental-require-module`로 한 번 읽어 보고 실패하면 멈춘다 — 다음에 ESM 전용 운영 의존성이 들어오면 Lambda를 건드리기 전에 배포가 멈춘다.

**검증**: 묶음에서 `--no-experimental-require-module`로 `sanitize-html`과 `post-content` 정화 동작 확인(스크립트·이벤트 속성·`javascript:` 제거, 인라인 시작 → 문단). 같은 묶음에 `htmlparser2` 12를 다시 넣으면 새 검사가 `ERR_REQUIRE_ESM`으로 멈추는 것도 확인(음성 대조). 핸들러 콜드 스타트는 Prisma 엔진 탐색까지 진행(묶음에는 Lambda용 엔진만 있어 로컬에서 그 뒤는 못 봄). jest `post-rich-content`·`post-rules`, 커밋 hook 전체. 실제 Lambda 부팅은 병합 뒤 배포 워크플로 health check로 본다.

**커밋**: 루트 `package.json`(overrides)·`package-lock.json`, `apps/api/jest.config.js`, `apps/api/scripts/package-lambda.sh`, docs.
