# 143. 배포 DB 재시드 적용 — 첫 시도는 열 순서 차이로 실패·롤백, 열 이름 형식으로 다시 만들어 적용 (2026-10-20)

> [진행 로그 인덱스](README.md)

**계기**: log/142에서 준비·검증한 재시드를 사용자가 자기 PC에서 실행했다(사용자 승인 2026-10-20, 배포 DB 쓰기).

**첫 시도 — 실패, 배포 DB는 그대로**: `invalid input syntax for type timestamp: "{}"`. 원인은 적재 SQL 형식이었다 — `pg_dump --inserts`는 열 이름 없이 값만 순서대로 넣어 **대상 테이블의 물리적 열 순서**에 기댄다. 배포 DB는 마이그레이션 도구가 아니라 SQL로 맞춰 와서(`_prisma_migrations` 없음, log/044~050·121) 열을 나중에 더한 테이블 5개(AttendanceRecord·Facility·Member·Payment·Staff)의 순서가 로컬과 달랐다. log/142의 스키마 대조는 열 **집합**만 정렬해 비교해서 순서 차이를 못 잡았다. 실행기가 한 트랜잭션이라 전부 되돌아갔다(설계대로 동작).

**고친 것**: 같은 원본 DB에서 `pg_dump --column-inserts`(INSERT마다 열 이름)로 다시 만들었다(v2). 실행기 `apply-reseed.ts`는 이제 열 이름 없는 INSERT가 하나라도 있으면 시작 전에 거부한다(v1 파일로 확인 — 106문 거부, v2는 적용).

**적용 결과(v2)**: 사용자 PC에서 성공. 세션이 배포 DB를 읽어 확인했다.
- 32개 테이블 행 수가 로컬 원본과 모두 같다(지점 5·직원 23·회원 218·예약 5,534·결제 5,534·회차 700·근태 1,497·변경 이력 83 등, 갱신 토큰 0).
- 행 내용 지문: 27개 테이블은 행 문자열 md5가 일치. 열 순서가 다른 5개는 행 문자열이 순서에 따라 달라지므로 `to_jsonb(r)`(키 정렬) md5로 다시 비교해 일치.
- 배포 URL api: 지점 5, 서초 회원 60·결제 1,526·예약 1,526, 회원 이수진 예약 34, 업무지원 요청 16.
- 종료 지점 데이터 정리(log/104, ADR-STF-08)는 재시드에 흡수됐다 — 5곳 시드의 노원(종료)에는 진행 중 파견이 없다.

**배운 것**: 스키마 "같음"은 집합 비교로는 부족하다 — 위치에 기대는 형식(값만 나열하는 INSERT, `COPY` 열 생략)을 쓸 때는 열 순서까지 본다. 더 단단한 쪽은 위치에 기대지 않는 형식을 쓰는 것이다.

**남은 것**: 첨부 실제 파일 시험 — 세션 네트워크가 supabase.co 직접 접속을 막아 업로드를 세션이 할 수 없다. 사용자가 브라우저에서 올리고 세션이 `Attachment` 행·`storage.objects`를 확인한다. Worker 재배포. 접속 문자열(DB 비밀번호 포함)이 이번에 다시 대화에 노출됐다 — 교체 권장(security-plan §8 S1).
