# 43. D29 — "회원관리 이관"을 조사하다 순서를 바꿨다: 참조되는 쪽부터, 1단계 지점 (2026-09-29)

> [진행 로그 인덱스](README.md)

**계기**: 사용자가 D26 순서대로 회원관리 Prisma 이관을 요청했다. 착수 전 조사에서 회원이 지점·직원·프로그램을 참조하는데 셋 다 mock에만 실데이터가 있다는 걸 확인했다(mock 98/195/149 vs DB 2/3/4). 회원만 옮기면 D27·D28의 FK·트리거가 96개 지점의 회원 등록을 막고, 두 저장소를 오가는 동기화 코드가 필요해진다. 구현 전에 멈추고 A(참조되는 쪽부터)·B(회원 먼저 + 복사본 동기화)·C(회원+지점)를 제시했고, 사용자가 A를 택했다. **D28까지 쌓은 DB 제약이 "순서를 잘못 잡으면 바로 막힌다"는 형태로 설계 오류를 드러낸 사례다.** 제약이 없었다면 회원을 먼저 옮기고 나중에 FK를 붙이며 데이터를 고쳤을 것이다.

**지점이 특이했던 점**: 쓰기 API가 없는 기준 데이터다. 그래서 "이관"의 실체는 ① 계약 상태의 원천을 DB 하나로 만드는 것과 ② 아직 mock인 9개 쓰기 경로가 동기적으로 하던 계약 종료 판정을 DB 기반으로 바꾸는 것이었다.

**설계 판단 세 가지**(상세: 2-1 D29):
- **mock 사본에서 계약 필드를 타입째 지웠다.** "계약 상태를 mock에서 읽지 않는다"를 규칙으로 두는 대신, 읽는 코드가 남아 있으면 컴파일이 실패하게 했다. 실제로 테스트 5곳과 `branchSummary`가 컴파일 단계에서 잡혔다.
- **계약 종료 판정은 gate 인자로 넘긴다.** 컨트롤러에서 미리 검사하는 방식은 예약처럼 판정 대상 지점이 mock 내부에서 정해지는 경로가 있고 에러 순서도 바뀐다. 그래서 종료 지점 집합을 한 번 읽어 mock 메서드에 필수 인자로 넘겼다. 기존 판정 자리·순서가 그대로이고, 넘기지 않은 호출부 10곳을 컴파일러가 전부 찾아줬다.
- **테스트를 워커별 DB로 바꿨다.** 계약 상태가 DB로 가는 순간 "스위트마다 새 앱 = 새 상태"라는 기존 격리가 깨진다. 한 스위트가 서초를 TERMINATED로 바꾸면 병렬로 도는 다른 스위트가 그걸 본다. 기준 DB를 템플릿으로 워커 수만큼 복제하고, 바꾼 상태는 공용 헬퍼가 매 테스트 뒤 되돌린다. 앞으로 옮겨질 모든 도메인이 이 인프라를 쓴다.

**발견**: `seed.ts`의 서초·강남 값이 mock과 달랐다(계약 종료일·취소 기준 시간 누락). 두 곳이 같은 목록(`branch-fixtures.ts`)에서 만들어지게 바꾸고, 어긋남을 잡는 사본 일치 테스트를 넣었다.

**검증**: 전체 264 통과. gate를 일부러 비우면 계약 종료 테스트 8건이 실패함을 확인했다(판정이 실제로 DB에서 온다는 증거). 워커 DB 정리·기준 DB 무오염도 확인했다. **Supabase 시드**: 배포된 앱은 Supabase를 보므로 시드 없이 머지하면 지점 목록이 비어 보인다. 외부 DB 쓰기라 사용자 확인을 받은 뒤 적용했다. 같은 원천에서 만든 upsert SQL을 로컬의 빈 DB에 두 번 돌려 멱등성과 시드 결과 일치를 먼저 확인했고, 적용 후 Supabase 해시가 로컬과 같다(98개, 종료 3).
