# 42. DI-02 A안 — 파견 시 담당 관계 정리 + 지점 일치 트리거, 그리고 타 지점 예약 결함 (2026-09-29)

> [진행 로그 인덱스](README.md)

**계기**: §41에서 결정 대기로 남긴 DI-02에 대해 사용자가 A안(파견 트랜잭션에서 담당 관계 정리)을 택했다. [인사정보관리 ADR-STF-04](../domains/인사정보관리.md)로 먼저 기록하고 구현했다.

**구현**: 앱의 `assignStaff`는 옛 지점 담당 회원의 `assignedStaffId`를 해제하고, 해제한 회원을 파견 응답 `unassignedMembers`로 돌려준다. mock 강사에는 직원 연결 필드가 없어서, 강사 프로필 정리는 강사 도메인 이관 때 추가하도록 남겼다. DB에는 트리거 7개를 넣었다. 쓰는 쪽 6개(프로그램 시설·강사, 회원 담당 직원, 수강·PT 프로그램, 예약 회차, 강사 직원)와 참조되는 쪽 1개(직원 지점 이동)다. 마지막 트리거가 핵심이다. "담당 관계를 먼저 정리한 뒤 이동"하지 않으면 거부해서, A안의 순서를 코드 리뷰가 아니라 DB가 강제한다.

**발견 — 타 지점 예약**: 트리거 대상 규칙을 앱 코드와 하나씩 대조하다가(DI-01 원칙: 앱이 먼저 검증해야 함) `createReservation`에 회원·프로그램 지점 비교가 없다는 걸 알았다. 서초 회원이 강남 회차 id로 예약하면 **201로 성공**했다. 수정 전 코드로 테스트를 돌려 직접 확인했다. 회차 조회(`GET /programs/:id/slots`)가 이미 막혀 있어 화면에선 드러나지 않았던 것이다. CLAUDE.md 핵심 불변식인 지점 격리 결함이라 `MEMBER_BRANCH_MISMATCH`(403)로 막고 `branch-isolation.spec.ts`에 케이스를 추가했다(CLAUDE.md 규칙). 지난 도메인 사이클들이 "조회 격리"는 표로 훑었지만 "쓰기 시 참조 대상의 지점"은 체계적으로 보지 않았다는 신호다. 트리거 인벤토리를 만든 것이 그 빈틈을 드러냈다.

**Supabase 어드바이저가 잡은 것**: 트리거 적용 직후 `function_search_path_mutable`(WARN) 6건이 떴다. 이미 적용한 마이그레이션을 고치면 로컬 체크섬이 어긋나므로, 별도 마이그레이션으로 함수 `search_path`를 `public, pg_temp`로 고정했다. 적용 후 WARN이 사라진 것을 확인했다. 매 DDL 뒤에 어드바이저를 돌리는 습관이 실제로 결함을 잡은 사례다.

**검증**: 트리거 9개 케이스 SQL 확인(위반 거부·정상 경로 통과). 앱·DB 테스트 5건 추가, 전체 261 통과(256 + 5, D26 skip 3건 유지). lint 0 에러, api·admin-web 빌드 성공. `migrate diff`가 트리거를 무시함을 확인했다. Supabase는 적용 전 지문 일치(이번엔 지문 쿼리에서 이력 테이블을 제외하도록 고쳐 로컬과 정확히 일치)와 데이터 0행을 확인했고, 적용 후 트리거·함수 정의 해시가 로컬과 동일함을 확인했다.

**커밋**: 마이그레이션 `20260929005902_d28_branch_consistency_triggers`·`20260929010205_d28_trigger_search_path`, `mock-data.service.ts`(`assignStaff`·`createReservation`), `staff.controller.ts`, 테스트 3개 파일, `data-integrity.md`·도메인 문서(인사정보관리 ADR-STF-04·예약및결제)·2-1 D28, 이 로그 절.
