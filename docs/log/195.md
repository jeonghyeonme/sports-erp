# 195. 계약 파일 보존·실물 이관·정리 — D69 2차 첫 단계 (D71, 2026-11-02)

> [진행 로그 인덱스](README.md)

**계기**: STATUS 다음 할 일 1번(D69 2차) 착수. 설계를 질문과 답으로 정했다 — D69 결정 7의 "이관 = 즉시 삭제"를 사용자가 "이관해도 3년 동안은 열람, 지우는 건 이관 완료 + 3년 경과 뒤 본사 정리 버튼"으로 바꿨다(결정 전문 [D71](../decisions/D71.md)). 순서는 계약 보존 먼저, 문서 실제 업로드는 다음 단계.

**한 일**
- 스키마(마이그레이션 `20261102120000_d71_contract_file_retention`): `ContractFile`에 이관·정리 시각과 처리자 4칸, CHECK `ContractFile_purge_after_archive_ck`.
- api: 보존 계산 `contract-retention.ts`(회차가 끝난 날 + 3년, 6개월 알림 — 회차 표·보존 현황·처리 대기함이 같은 함수), `POST /branches/:branchId/contract/files/:fileId/archive`(본사, `@ScopedResource('contractFile')`, 이미 표시하면 409), `GET /branches/contract-files/retention`(이관 필요·정리 대상), `POST /branches/contract-files/purge`(본사, 고른 파일이 모두 정리 가능해야 함, 행 락 → 저장소 삭제 → 기록, 실패하면 전부 되돌림), 정리된 파일 열기 410, 회차 목록에 보존 끝·이관·정리 상태, 처리 대기함(본사) 2항목. `StorageService.remove`(실패를 던지는 삭제) 추가.
- admin-web: 지점 상세 회차 표에 파일마다 보존 끝·상태 배지·실물 이관 완료 버튼(본사)·이관 필요 안내, 새 화면 "계약 파일 보존"(`/contract-retention`, 본사 메뉴 — 이관 필요 목록과 [보존 끝난 파일 정리]), 오류 안내·이력 문구.
- 테스트: `contract-retention.spec`(신규 8건), `branch-isolation` 표에 이관 라우트, `inbox.spec`의 본사 항목 목록.

**계획과 달라진 것**: 계획의 "지점 목록에 이관 필요 파일 수"는 넣지 않았다 — 지점 상세가 이미 회차 목록을 받아 거기서 센다(같은 정보를 두 번 계산하지 않음).

**근거**: D71(D69 결정 7 대체), D69, D61(처리 대기함), D57(저장소), D46(지점 범위), D44(변경 이력).

**검증**: api jest 56개 파일 609건(신규 `contract-retention` 8건 — 정리 뒤 저장소 객체가 실제로 없는지까지), tsc·eslint(오류 0), admin-web lint·빌드, 화면 자동 테스트 16건(로컬 우회 실행), doc-check 통과. 로컬 미리보기에서 본사로 회차 표(보존 끝·이관 필요 배지·안내) → 실물 이관 완료 → 보존 현황 → 처리 대기함 "정리할 계약 파일 1건" → 정리 → 회차 표 "시스템 파일 정리됨"을 확인(콘솔 오류 없음, 미리보기용으로 바꾼 로컬 데이터는 되돌림). Supabase 저장소의 실제 삭제 호출은 로컬에서 볼 수 없다 — 검증되지 않음(메모리 저장소로만 확인).
