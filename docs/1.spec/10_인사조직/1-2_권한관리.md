# 01. 권한관리 (Access Control)

> 00_공통설계서의 인증/RBAC 설계를 실제 기능(화면/API) 단위로 구체화한 문서입니다.

## 1. 개요 및 원본 요구사항 대비 조정사항

원본 요구사항은 "사용자별·프로그램별 세부 권한 설정(입력/수정/삭제/조회/출력)"을 요구하지만, 이는 엔터프라이즈 ERP 수준의 세밀한 개별 권한 부여(ACL) 기능으로 1인 개발 범위를 크게 초과합니다.

**조정**: 사용자 개별 커스텀 권한 대신 **4개 고정 Role(SUPER_ADMIN/BRANCH_ADMIN/STAFF/MEMBER) 기반 RBAC**로 단순화합니다. `STAFF`는 지점 소속 일반 직원(트레이너 등)이 로그인해서 본인 근태·업무일지만 셀프서비스하도록 만든 역할로, 관리 권한이 있는 `BRANCH_ADMIN`과는 명확히 분리됩니다(직원이라고 다 지점 관리자 권한을 갖는 건 아니라는 원칙). 대신 아래 항목들은 실사용 가능하도록 실제로 구현합니다.
1. 지점 간 데이터 격리(멀티테넌시) — 이게 원본 요구사항의 실질적 핵심
2. 퇴사/탈퇴 즉시 접근 차단
3. 관리자(BRANCH_ADMIN)와 일반 직원(STAFF)의 권한 분리 — 트레이너가 실수로(혹은 악의적으로) 다른 직원 정보나 회원 관리 기능에 접근할 수 없어야 함

## 2. 사용자 스토리

- 본사 관리자로서, 나는 모든 지점의 데이터를 조회하고 신규 지점 관리자 계정을 발급하고 싶다.
- 지점 관리자로서, 나는 로그인하면 내 지점 데이터만 보이길 원하고, 실수로도 다른 지점 정보에 접근할 수 없기를 바란다.
- 회원으로서, 나는 내 정보와 내가 속한 지점의 프로그램만 보고 싶다.
- 본사 관리자로서, 직원이 퇴사하면 그 즉시 시스템 접근을 막고 싶다.
- 직원(트레이너 등)으로서, 나는 로그인해서 내 근태·휴가·업무일지만 스스로 관리하고 싶다 — 다른 직원 정보나 회원 관리 화면은 볼 필요도, 보여서도 안 된다.

## 3. 데이터 모델

### Account
| 필드 | 타입 | 설명 |
|---|---|---|
| id | UUID (PK) | |
| email | string, unique | 로그인 ID |
| passwordHash | string | bcrypt |
| role | enum(SUPER_ADMIN, BRANCH_ADMIN, STAFF, MEMBER) | |
| isActive | boolean, default true | false=접근차단(퇴사/탈퇴) |
| failedLoginCount | int, default 0 | 잠금 로직용 |
| lockedUntil | datetime, nullable | |
| lastLoginAt | datetime, nullable | |
| createdAt / updatedAt | datetime | |

인덱스: `email` unique index, `role` index(관리자 목록 조회용)

### RefreshToken
| 필드 | 설명 |
|---|---|
| id, accountId(FK), tokenHash, expiresAt, revokedAt | 재발급/강제로그아웃 관리용. 토큰 원문 대신 해시 저장 |

## 4. 화면 목록

| 화면 | 대상 | 설명 |
|---|---|---|
| 로그인 | 전체(웹/앱 공통 UX, 클라이언트만 다름) | 이메일/비밀번호, 5회 실패 시 잠금 안내 |
| 계정 목록/발급(관리자) | SUPER_ADMIN | 지점 관리자 계정 생성/비활성화 |
| 권한 관리(Role 전환) | SUPER_ADMIN | 지점 직원(Staff)의 `Account.role`을 STAFF ↔ BRANCH_ADMIN으로 전환. §6의 인증 방식 변경(2026-09-15) 이후로는 **재로그인 없이 다음 요청부터 즉시 반영**됨 — 2-1문서 D17 참고 |
| 비밀번호 변경 | 전체 | 로그인 후 |
| (선택) 비밀번호 재설정 | 전체 | 이메일 링크 방식 — Phase 2 |

## 5. API 명세

| Method | Endpoint | 권한 | 설명 |
|---|---|---|---|
| POST | /api/v1/auth/login | 공개 | email/password → accessToken, refreshToken |
| POST | /api/v1/auth/refresh | Refresh Token | 토큰 재발급 |
| POST | /api/v1/auth/logout | 인증 필요 | Refresh Token revoke |
| GET | /api/v1/auth/me | 인증 필요 | 내 정보(role, branchId 포함) |
| PATCH | /api/v1/auth/password | 인증 필요 | 비밀번호 변경 |
| POST | /api/v1/accounts | SUPER_ADMIN | 지점 관리자 계정 생성 |
| PATCH | /api/v1/accounts/:id/deactivate | SUPER_ADMIN, BRANCH_ADMIN(본인 지점 직원만) | 접근 차단 |
| GET | /api/v1/accounts | SUPER_ADMIN | 전체 계정 목록 |
| GET | /api/v1/permissions/staff | SUPER_ADMIN | 전 지점 직원 목록 + 현재 Role 조회 |
| PATCH | /api/v1/permissions/staff/:staffId/role | SUPER_ADMIN | 해당 직원의 Role을 STAFF ↔ BRANCH_ADMIN으로 전환(`@IsIn`으로 두 값만 화이트리스트 검증, SUPER_ADMIN 승격 등 위험한 값 주입 차단) |

## 6. 비즈니스 로직 & 엣지케이스

- **인증 방식 정정(2026-09-15) — "퇴사 즉시 접근차단"이 실제로 즉시가 되도록 수정**: 기존 설계는 JWT를 순수 stateless로 검증(서명·만료만 확인)해, `Account.isActive`가 로그인·refresh 시점에만 체크됐습니다. 이러면 퇴사 처리 이후에도 **이미 발급된 Access Token이 만료(기본 30분) 전까지 계속 유효**해, 원본 요구사항("퇴사처리 이후에는 시스템 접근 통제")이 말하는 "즉시"와 실제 동작이 어긋납니다. 수정: `JwtAuthGuard`는 서명·만료 검증 후 **JWT payload의 `sub`(accountId)로 매 요청마다 `Account`를 PK 조회**해 `isActive`를 재확인하고, `role`도 JWT에 박제된 값이 아니라 이 조회 결과를 신뢰합니다(BRANCH_ADMIN/STAFF는 `Staff.branchId`도 같은 조회에서 함께 가져와 파견 발령도 재로그인 없이 즉시 반영). PK 인덱스 조회 1회 추가 비용으로 "즉시"를 문자 그대로 만족시킵니다 — 트래픽이 실제로 커지면(포트폴리오 규모에서는 해당 없음) accountId 기준 수 초짜리 캐시(in-memory)로 완화할 수 있습니다.
- 로그인 실패 5회 → `lockedUntil = now+15min`, 이후 성공 시 카운트 초기화
- `isActive=false` 계정으로 로그인 시도 → 401 + `ACCOUNT_DEACTIVATED` 명시적 에러코드(막연한 "로그인 실패"와 구분해 UX상 명확히 안내). **인증된 요청 중에도 동일하게 적용** — 위 수정 이후로는 로그인 이후 언제 퇴사 처리가 나든 다음 요청에서 바로 401이 남
- **지점 자체가 TERMINATED될 때의 계정 처리**(개인 퇴사와는 별개 정책 — [1-1문서 §2-1](../00_공통/1-1_공통설계서.md#2-1-branch지점-데이터-모델--위탁계약-필드)): 위탁계약이 종료된 지점 소속 `BRANCH_ADMIN`/`STAFF` 계정은 개별 퇴사 처리와 달리 즉시 일괄 비활성화하지 않습니다 — 계약 종료 후에도 과거 회원·결제 이력 조회, 인수인계 문서화 등 관리자 업무가 남을 수 있기 때문입니다. 대신 해당 계정들은 **신규 회원 등록·예약 생성 같은 쓰기 API만 차단**(1-5/1-6/1-7문서와 동일하게 409)되고, 실제 계정 비활성화 여부는 SUPER_ADMIN이 지점 상세 화면에서 수동으로 결정합니다(자동 일괄 비활성화는 하지 않음 — 오작동 시 복구가 어려운 되돌리기 힘든 작업이므로 사람이 판단)
- Access Token 만료 시 클라이언트는 자동으로 `/auth/refresh` 호출 후 원 요청 재시도(인터셉터 패턴)
- Refresh Token도 탈취 대비 1회용(rotate) 방식 권장: refresh 성공 시 기존 토큰 revoke + 신규 발급
- BRANCH_ADMIN이 다른 지점 리소스 id를 파라미터로 직접 조작 시도 → `BranchScopeGuard`에서 403 (예: `/staff/:id` 조회 시 해당 staff.branchId ≠ 본인 branchId)
- 회원(MEMBER) 탈퇴 시 즉시 로그인 차단하되, 결제/예약 이력은 보존(소프트 삭제 원칙, 1-1문서 §4 참고)
- Role 전환(STAFF↔BRANCH_ADMIN)도 위와 같은 이유로 **재로그인 없이 다음 요청부터 즉시 반영**됩니다(2026-09-15 이전엔 "만료 전까지 이전 role 유지 → 재로그인 필요"였던 문제). 다만 현재는 AuditLog 연동 없이 role이 바뀌어 "누가 언제 승진시켰는지" 추적이 안 됨(2-1문서 D17, 실제 쓰기 로직 구현 시 AuditLog 연동 권장)

## 7. 권한/보안 규칙 (상세 매트릭스)

| API 그룹 | SUPER_ADMIN | BRANCH_ADMIN | STAFF | MEMBER |
|---|---|---|---|---|
| /accounts | 전체 CRUD | 본인 지점 직원 계정만 생성/비활성화 | - | - |
| /permissions/staff (Role 전환) | 전체 조회/전환(STAFF↔BRANCH_ADMIN) | 접근 불가(403) | 접근 불가(403) | - |
| /branches | 전체 CRUD | 조회(본인 지점) | 조회(본인 지점) | - |
| /staff, /staff/:id | 전체 CRUD | 본인 지점 CRUD | 본인 레코드만 조회(수정은 1-3문서 변경 신청으로만) | - |
| /attendance, /leave-requests, /work-logs | 조회 전체 | 본인 지점 조회 + 휴가 승인 | 본인 레코드만 CRUD(휴가는 신청만, 승인 불가) | - |
| /members, /reservations, /programs 등 관리 리소스 | 조회 전체 | 본인 지점 CRUD | 조회 불가(403) | 본인 데이터만 |
| 모든 조회 API의 list 파라미터 | branchId 필터 자유 지정 | branchId 강제 고정(본인 값, 파라미터 무시) | branchId 강제 고정 + 본인 staffId로 추가 필터 | memberId 강제 고정(본인 값) |

> STAFF는 `BranchScopeGuard`로 지점이 고정되는 것에 더해, 근태/휴가/업무일지 API에서는 `staffId`까지 본인 값으로 강제됩니다(동료 직원의 근태를 열람하는 것도 차단) — 02·1-4문서의 "Staff 본인" 액터가 바로 이 Role입니다.

## 8. 구현 우선순위

> **범위 제외(2026-09-20, 향후 확장 가능성만 남김)**: 범용 계정 발급/목록 API(`POST/GET /accounts` — 채용(02)·회원 등록(05)이 각자 계정을 만들고 있어 중복)와 로그인 5회 실패 잠금(RFP 요구가 아님). 필요해지면 `lockedUntil`/`failedLoginCount` 필드를 추가하는 정도로 확장할 수 있다. 퇴사·탈퇴 즉시 접근 차단은 RFP 요구이므로 제외 대상이 아니며 이미 구현돼 있다.

**Phase 1(필수)**: 로그인/로그아웃/토큰 갱신, Role 4종 Guard(SUPER_ADMIN/BRANCH_ADMIN/STAFF/MEMBER), BranchScopeGuard, 계정 비활성화(퇴사처리) — `JwtAuthGuard`의 매 요청 `Account` PK 조회(§6)는 "계정 비활성화" 기능의 일부이지 별도 항목이 아님(이게 없으면 비활성화가 최대 30분 지연되어 요구사항을 충족 못 함) — **완료(2026-09-18)**. 매 요청 재조회는 구현돼 있었지만 role/branchId를 여전히 로그인 시점 JWT 값으로 반환하던 버그가 있어 이번에 같이 고침(§6 실제 동작이 문서와 어긋나 있었음)
**Phase 2(선택, 시간 남으면)**: 로그인 잠금(5회 실패), 이메일 기반 비밀번호 재설정, Refresh Token rotate, 계정별 최근 로그인 이력 화면 — **Refresh Token rotate만 완료(2026-09-18)**, 나머지 3개는 여전히 미구현

## 9. 테스트 체크리스트

- [ ] SUPER_ADMIN 로그인 → 전체 지점 데이터 조회 가능
- [ ] BRANCH_ADMIN 로그인 → 타 지점 회원 id로 직접 API 호출 시 403
- [ ] 퇴사 처리된 계정 → 즉시 로그인 실패(ACCOUNT_DEACTIVATED)
- [ ] **로그인된 상태(Access Token 유효기간 내)에서 퇴사 처리 → 같은 토큰으로 바로 다음 API 호출 시 401(ACCOUNT_DEACTIVATED), 토큰 만료를 기다리지 않음**
- [ ] Role 전환 직후(재로그인 없이) 같은 토큰으로 새 Role 권한의 API 호출 시 정상 동작
- [ ] Access Token 만료 후 자동 갱신 플로우 동작
- [ ] 비밀번호 5회 오입력 → 잠금 → 15분 후 해제
- [ ] STAFF 로그인 → 회원/예약/프로그램 관리 API 접근 시 403
- [ ] STAFF 로그인 → 동료 직원의 근태·휴가 데이터 조회 시 403(본인 것만 조회됨)
