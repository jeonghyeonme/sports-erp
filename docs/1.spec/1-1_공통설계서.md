# 00. 공통 설계서 — 아키텍처 / 인증·권한 / 개발 로드맵

> 스포이즘 ERP 포트폴리오 프로젝트의 기반 설계 문서입니다. 이후 1-2~1-9 문서는 모두 이 문서의 규칙(엔티티 네이밍, 인증 방식, API 컨벤션)을 전제로 작성되었습니다.
> 전제 조건: **1인 개발**, **실제 서비스처럼 동작하되 상용 인프라 규모는 아님**, 목표는 "졸업작품 심사 + 포트폴리오 시연"에서 실사용 가능한 완성도를 보여주는 것.

---

## 1. 시스템 구성

```
사용자
 ├─ 본사 관리자(SUPER_ADMIN)  ─┐
 ├─ 지점 관리자(BRANCH_ADMIN) ─┼─→  admin-web (React, 브라우저)
 └─ 회원(MEMBER)              ──→  member-app (React Native, 모바일)
                                          │
                                          ▼
                                   api (NestJS, REST)
                                          │
                                          ▼
                                  PostgreSQL (Prisma)
```

- 클라이언트 2종(admin-web, member-app)이 **동일한 REST API**를 공유합니다. 화면/UX만 다르고 도메인 로직은 API 서버에 집중시켜, "같은 데이터를 역할에 따라 다르게 보여준다"는 원칙을 지킵니다.
- 파일(이미지 등) 저장은 로컬 디스크 또는 무료 오브젝트 스토리지(예: Supabase Storage, Cloudflare R2 무료 티어) 중 택1. 포트폴리오 규모에서는 로컬 `uploads/` 디렉터리 + 정적 서빙으로도 충분합니다.

### 1-1. 사업 맥락 (원본 RFP 재해석)

1-2~1-9 문서는 지금까지 "여러 지점을 가진 헬스장 체인 본사 시스템"이라는 일반화된 틀로 설계되어 있었습니다. 그런데 원본 제안요청서(`제안요청서 원본.pdf`, Ⅲ.사업개요~Ⅳ.과업내용)를 다시 읽어보면, 스포이즘의 실제 사업구조는 훨씬 구체적이고, 이 차이가 데이터 모델과 기능 우선순위에 실질적인 영향을 줍니다. **이 시스템은 ERP라는 이름과 달리 회계·재고·구매 같은 전통적 ERP 모듈은 다루지 않고, "다지점 위탁운영 특화 회원관리·운영 플랫폼"에 가깝습니다** — RFP 원문도 "업계에서 회원관리 프로그램을 'ERP 시스템'이라고 칭함"이라고 스스로 밝히고 있습니다.

**스포이즘은 헬스장 체인 본사가 아니라 "아파트·오피스텔 커뮤니티 시설 위탁운영사"입니다.** 전국 98개 업장(2022년 RFP 작성 시점 기준)을 이미 보유하고 있고, "각 지사 개념으로 퍼져있는" 조직 구조에 직원이 "해당 지역 또는 본사 파견 형태로" 투입됩니다. 즉 이 시스템의 `Branch`는 단순히 "회사가 소유한 지점"이 아니라 **"아파트 입주자대표회의/관리사무소와 맺은 위탁운영 계약 현장"**입니다(§2-1에서 계약 관련 필드로 구체화).

**RFP가 명시한, 기존(타사 벤더) ERP를 계속 쓰지 않으려는 이유** — 이 프로젝트가 왜 "직접 개발"이어야 하는지의 진짜 근거입니다:
1. 기존 ERP 회사의 시스템을 쓰면 매출·영업 노하우가 벤더사에 노출되어 경쟁사가 생기는 구조적 리스크가 있음
2. 기존 ERP 회사가 도산하면 그 피해가 고스란히 스포이즘의 신뢰성 타격으로 이어짐
3. 범용 시스템이라 "아파트 커뮤니티 시설 위탁운영"이라는 스포이즘의 사업 특수성에 맞지 않음
4. **시스템 불안정 → 민원 발생 → 위탁 업장 계약해지**로 이어지는 구조 — 즉 이 프로젝트에서 "안정성"은 단순 UX 품질이 아니라 **위탁계약 유지 여부와 직결되는 사업 리스크**입니다

**이 시스템의 숨은 용도 — 신규 계약 수주 영업 도구**: RFP는 "각종 사업공모(스포츠위탁사업)에서 현장발표(PT)를 할 때 최첨단 회원관리 시스템을 적용할 수 있다는 강점"을 자체 개발의 이유로 명시합니다. 즉 이 시스템은 내부 운영툴이면서 동시에, 신규 아파트 단지의 위탁운영권을 따내기 위한 입찰 발표(PT) 자리에서 "우리는 검증된 자체 시스템이 있다"를 보여주는 **영업 무기**이기도 합니다. 이 관점은 2-1문서 D18, 그리고 신규 문서 [13_차별화전략](../2.decisions/2-4_차별화전략.md)에서 구체적인 기능 제안으로 이어집니다.

이 재해석이 1-1~1-9 문서의 기존 설계를 뒤엎지는 않습니다 — 지점 격리(D2), RBAC(D1), 회원관리 중심 설계는 이미 이 맥락과 부합합니다. 다만 **Branch를 "이름/주소만 있는 얕은 엔티티"로 둔 것과, 이 시스템의 "영업 도구"로서의 역할을 설계에 전혀 반영하지 않은 것**이 실제 갭이며, 아래 §2-1과 2-4문서에서 보완합니다.

**추가 재해석(2026-09-08) — 직원도 "지점 소속"이 아니라 "본사 소속, 지점에 파견"**: 같은 절(Ⅳ.과업내용 1.과업 목적, p.3~4)은 "당사의 조직 구조는 각 지사 개념으로 퍼져있는 형태이기 때문에 **행정 및 트레이너들 역시** 해당 지역 또는 본사 파견 형태로 직원이 투입되고 있는 상황"이라고 명시합니다. "행정"(관리자급)과 "트레이너"를 나란히 언급하므로 BRANCH_ADMIN·STAFF 모두 대상입니다. 즉 `Branch`가 위탁계약 현장이듯, `Staff`도 "지점이 직접 고용한 인력"이 아니라 **"스포이즘 본사가 고용해 현장에 파견한 인력"**입니다. §2-2에서 데이터 모델로 구체화합니다.

## 2. 전체 ERD 개요 (엔티티 목록)

상세 컬럼은 각 기능 문서(1-2~1-9)에서 정의합니다. 여기서는 **엔티티 간 관계**만 전체 조망합니다.

```
Branch(지점) 1─N Facility(시설: 헬스장/수영장/골프장/독서실 등)
Branch 1─N StaffAssignment(파견 이력) N─1 Staff(직원, 본사 소속 — §2-2)
Branch 1─N Member(회원)
Branch 1─N Program(프로그램/강좌)
Branch 1─N Post(게시글, scope=BRANCH_TO_MEMBER인 경우)

Account(로그인계정) 1─1 Staff  (Role=SUPER_ADMIN/BRANCH_ADMIN)
Account 1─1 Member            (Role=MEMBER)

Staff 1─N AttendanceRecord(근태기록)
Staff 1─N LeaveRequest(휴가신청)
Staff 1─N WorkLog(업무일지)

Facility 1─N Program
Facility 1─N CongestionSnapshot(혼잡도 스냅샷)

Program 1─N ScheduleSlot(회차/시간대)
Program N─1 Instructor(강사)

Member 1─N Reservation(예약)
Member 1─N PTSession(PT 잔여세션)
ScheduleSlot 1─N Reservation
Reservation 1─1 Payment(결제, nullable — 무료 프로그램은 결제 없음)

모든 주요 엔티티 → AuditLog(변경이력)에 기록 (누가/언제/무엇을 변경했는지)
```

**핵심 설계 원칙(멀티테넌시 격리)**: `Branch`에 속한 엔티티(Staff, Member, Program, Post 등)는 반드시 `branchId`를 가지며, `BRANCH_ADMIN` 역할의 모든 조회/수정 API는 **자신의 branchId로 자동 필터링**됩니다(요구사항 5번 "타현장 정보 조회 불가능" 구현). `SUPER_ADMIN`만 전체 지점을 넘나들 수 있습니다.

### 2-1. Branch(지점) 데이터 모델 — 위탁계약 필드

§1-1에서 정리했듯 `Branch`는 "회사가 소유한 매장"이 아니라 "위탁운영 계약을 맺은 현장"입니다. 기존 설계는 `id/name/address`뿐이었는데, 이는 회원·직원을 지점별로 나누는 용도로는 충분해도 **"전산화 대상인 실제 업무"— 계약 관리 — 를 전혀 담지 못합니다.** 아래 필드를 추가합니다.

> **이 표가 `Branch`의 전체 스키마입니다.** 다른 문서(03, 06 등)에서 Branch에 필드가 더 필요하면 이 표에 추가하고 이 절을 참조하세요 — 문서마다 개별적으로 "Branch에 필드 추가"라고 선언하면 스키마가 여러 곳에 흩어져 전체를 한눈에 볼 수 없게 됩니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | UUID (PK) | |
| name | string | 지점명(예: "서초점") |
| address | string, nullable | |
| code | string, unique | 지점 코드(staffCode/memberNo 생성에 사용, 3f6ea31 커밋에서 이미 추가됨) |
| contractPartner | string | 위탁계약 상대방(예: "서초 OO아파트 입주자대표회의") — 회원에게 노출되지 않는 관리자 전용 정보 |
| contractStartAt | date | 계약 시작일 |
| contractEndAt | date, nullable | 계약 종료(예정)일 — 상시계약 등 미정이면 null |
| contractStatus | enum(ACTIVE, RENEWAL_DUE, EXPIRED, TERMINATED) | 계약 상태. `RENEWAL_DUE`는 `contractEndAt` 임박(예: 60일 이내) 시 배치로 자동 전이 |
| renewalNoticeAt | date, computed | `contractEndAt - 60일`(정책값) — 갱신 알림 발송 기준일. 하드코딩 금지, Branch 또는 전역 설정값으로 관리 |
| standardCheckInTime | time | 지점별 출근 기준 시각(예: 09:00). 10분 초과 시 지각 자동 판정에 사용 — [03_근태관리 §6](1-4_근태관리.md#6-비즈니스-로직--엣지케이스) |
| cancellationPolicy | JSON 또는 개별 컬럼(예: `cancellationDeadlineHours`) | 예약 취소/환불 정책값(예: 24시간 전까지 무료 취소). Program 단위로 override 가능하면 Program에도 nullable로 둘 수 있음 — [06_예약및결제 §6](1-7_예약및결제.md#6-비즈니스-로직--엣지케이스) |

인덱스: `Branch.contractStatus`(본사 대시보드에서 "갱신 임박 지점" 조회용), `Branch.contractEndAt`

**비즈니스 로직**: 매일 배치(Cron)로 `contractEndAt`이 임박한(`renewalNoticeAt` 경과) `ACTIVE` 지점을 `RENEWAL_DUE`로 전이하고, `SUPER_ADMIN` 대시보드에 알림 카드로 노출합니다. `TERMINATED` 지점은 물리 삭제하지 않고(소프트 삭제 원칙, §5) 과거 데이터(회원/결제 이력) 조회는 유지하되 신규 회원 등록·예약은 차단합니다. 상세 기능 설계는 [13_차별화전략](../2.decisions/2-4_차별화전략.md) §1을 참고하세요 — 이 필드들은 "위탁계약 라이프사이클 관리"라는 차별화 기능의 기반 데이터입니다. 이 필드들을 수기 입력 대신 계약서 스캔본에서 OCR·AI로 자동 추출하는 기능은 [2-4문서 §1-1](../2.decisions/2-4_차별화전략.md#1-1-계약서-ocrai-분석-2026-09-08-추가-스코프를-계약서-1종으로-한정)에서 다룹니다(계약서 1종에 한정, 프로그램 신청서·자격증 등은 보류).

**TERMINATED 전이가 하위 도메인에 미치는 영향** — "신규 회원 등록·예약 차단"은 선언만으로 끝나지 않고, 각 도메인의 실제 API 전제조건에 반영되어야 합니다:
- 회원 등록(`POST /api/v1/members`): `Branch.contractStatus`가 `TERMINATED`면 409 — [05_회원관리](1-6_회원관리.md) 참고
- 예약 생성(`POST /api/v1/reservations`): 동일하게 409 — [06_예약및결제](1-7_예약및결제.md) 참고
- 게시판: TERMINATED 지점의 기존 공지는 열람만 유지하고 신규 작성은 차단 — [04_게시판_공지사항](1-5_게시판_공지사항.md) 참고
- 계정: 지점이 TERMINATED되면 그 지점 소속 계정 전체를 어떻게 처리할지는 개인 퇴사 처리와 별개 정책 — [01_권한관리](1-2_권한관리.md) 참고
- 파견 직원: TERMINATED 지점에 현재 파견 중(`StaffAssignment.endDate=null`)인 직원이 있으면, 그 파견을 종료 처리하고 본사가 재배치할 대상 목록에 올려야 함 — 아래 §2-2, [02_인사정보관리](1-3_인사정보관리.md) 참고

### 2-2. Staff(직원) 파견(Assignment) 모델

§1-1에서 정리했듯, 원본 RFP는 "행정 및 트레이너들 역시 해당 지역 또는 본사 파견 형태로 직원이 투입"된다고 명시합니다. 즉 `Staff`는 "지점이 직접 고용한 인력"이 아니라 **"스포이즘 본사가 고용해 현장에 파견한 인력"**입니다. 이 원칙에 따라 `Staff.branchId`는 "고정 소속"이 아니라 **"현재 파견 지점"**을 가리키는 비정규화 캐시 필드로 재정의하고, 파견 이력의 원천은 별도 엔티티 `StaffAssignment`가 담당합니다.

- **`Staff.branchId`**: 현재 활성(`endDate=null`) `StaffAssignment.branchId`와 항상 동기화되는 캐시. `BranchScopeGuard` 등 기존 지점 격리 로직(§3.3)은 이 필드를 그대로 사용하면 되므로, 1-2/1-4/1-6/1-8문서의 권한 필터링 로직 자체는 변경할 필요가 없습니다 — 바뀌는 것은 "이 값이 언제, 누구에 의해 갱신되는가"입니다.
- **`StaffAssignment`**: `id, staffId(FK), branchId(FK), startDate, endDate(nullable — null=현재 진행 중), assignedBy(FK→Account, 항상 SUPER_ADMIN), note`. 상세 필드·API는 [02_인사정보관리 §3~§7](1-3_인사정보관리.md)에서 정의합니다.
- **채용·배치 권한**: 신규 채용 등록과 파견 발령(재배치)은 **SUPER_ADMIN 전용**입니다 — 본사가 채용·배치의 주체라는 원본 구조를 그대로 반영합니다. BRANCH_ADMIN은 "현재 파견되어 있는 인력"의 일상적 인사 관리(수정, 퇴사 처리)만 담당합니다.
- 이 모델은 스텁이나 스트레치 기능이 아니라 **원본 RFP가 명시한 기본 고용구조**이므로 Phase 1 핵심 데이터 모델에 포함됩니다(2-4문서 §3에 한때 "확인 전 보류"로 있었으나, 원본 재확인 후 이 위치로 승격·이관되었습니다).

## 3. 인증 · 인가(RBAC) 설계

### 3.1 계정 구조

- `Account` 테이블 하나로 로그인 주체를 통합 관리 (email/phone + passwordHash + role + isActive)
- `role ∈ { SUPER_ADMIN, BRANCH_ADMIN, STAFF, MEMBER }` — `STAFF`는 지점 소속 일반 직원(트레이너 등) 로그인용으로, `BRANCH_ADMIN`과 달리 관리 권한 없이 본인 근태·휴가·업무일지만 셀프서비스합니다(1-2문서 §7)
- Staff/Member 테이블은 Account와 1:1로 연결된 "역할별 상세 프로필" — `BRANCH_ADMIN`과 `STAFF` 모두 Staff 레코드를 가지며, 관리 권한 유무는 Account.role로만 구분됩니다

### 3.2 토큰 정책

| 토큰 | 수명 | 저장 위치 |
|---|---|---|
| Access Token (JWT) | 30분 | 클라이언트 메모리/헤더(Authorization: Bearer) |
| Refresh Token | 14일 | httpOnly Cookie(admin-web) / SecureStore(member-app) |

- 비밀번호는 bcrypt(cost 10~12)로 해시 저장
- 로그인 5회 연속 실패 시 15분 잠금(간단한 무차별대입 방지 — 포트폴리오 완성도용 최소 구현)
- `isActive=false`(퇴사/탈퇴)인 계정은 로그인 시점과 매 요청의 인증 미들웨어에서 즉시 차단 → 원본 요구사항 "퇴사처리 이후 시스템 접근 통제" 충족

### 3.3 인가(Authorization) 구현 방식 (NestJS 기준)

```
@Roles('SUPER_ADMIN', 'BRANCH_ADMIN')
@UseGuards(JwtAuthGuard, RolesGuard, BranchScopeGuard)
```

- `JwtAuthGuard`: 토큰 검증, `req.user`(accountId, role, branchId) 주입
- `RolesGuard`: 데코레이터에 선언된 역할만 허용
- `BranchScopeGuard`: BRANCH_ADMIN 요청에 대해 쿼리/파라미터의 `branchId`가 본인 소속과 일치하는지 검사 (불일치 시 403). 서비스 레이어에서도 이중으로 `where: { branchId: user.branchId }` 강제 적용(가드 우회 방지용 2중 안전장치)

### 3.4 권한 매트릭스(요약 — 상세는 1-2문서)

| 리소스 | SUPER_ADMIN | BRANCH_ADMIN | STAFF | MEMBER |
|---|---|---|---|---|
| 지점(Branch) | CRUD 전체 | 조회(본인 지점만) | 조회(본인 지점만) | - |
| 직원/근태 | 채용·파견 발령 CRUD 전체(§2-2) | 현재 파견된 직원 대상 일상 관리(수정·퇴사), 채용·파견 발령은 불가 | 본인 근태/휴가/업무일지만 CRUD, 타 직원 정보 조회 불가 | - |
| 회원 | 조회 전체 | CRUD(본인 지점만) | - | 본인 정보 조회/수정 |
| 예약/결제 | 조회 전체 | 조회(본인 지점만) | - | 본인 예약 CRUD |
| 게시판 | 본사→현장 작성 | 조회 + 현장→회원 작성 | 조회만 | 조회만 |
| 혼잡도 | 조회 전체 | 조회+수동보정(본인 지점) | 조회만 | 조회만 |

## 4. API 컨벤션

- Base URL: `/api/v1`
- 인증: `Authorization: Bearer <accessToken>`
- 응답 포맷(공통 envelope):
```json
{ "success": true, "data": { ... }, "meta": { "page": 1, "pageSize": 20, "total": 137 } }
```
```json
{ "success": false, "error": { "code": "MEMBER_NOT_FOUND", "message": "..." } }
```
- 목록 API는 페이지네이션 필수(`page`, `pageSize`, 기본 20/최대 100)
- 날짜/시간은 ISO 8601(UTC 저장) + 클라이언트에서 KST 변환 표시
- 소프트 삭제 원칙: 회원/직원 등 핵심 엔티티는 물리 삭제 대신 `isActive=false`(또는 상태값) 처리로 이력 보존(결제/예약 참조 무결성 유지). Program은 단순 불리언 대신 `status`(PREPARING/RUNNING/PAUSED/ENDED) 생애주기로 관리 — 지점별 "진행중 프로그램" 파악이 이 필드 하나로 가능해짐(1-8문서 §3-2)

## 5. 공통 비기능 설계 (성능/데이터관리/보안 요구사항의 실현 방식)

원본 요구사항의 "CPU 90% 이하", "메모리 85% 이하" 같은 실측 인프라 목표는 포트폴리오 규모에서 의미가 없으므로, **아래 설계 원칙으로 대체**하고 문서/발표에서는 "확장을 고려한 설계"로 어필합니다.

| 원본 요구사항 | 대체 구현 |
|---|---|
| 시스템 가용성/성능 | 목록 API 페이지네이션, 자주 조회되는 값(혼잡도 등) 캐싱(선택: Redis 또는 인메모리), DB 인덱스 설계(각 문서에 명시) |
| 데이터 관리방안(변경이력) | `AuditLog` 테이블 — 주요 쓰기 작업(회원 정보 수정, 예약 취소, 결제 상태 변경 등)마다 기록 |
| 오류 데이터 진단 | API 레벨 유효성 검증(class-validator), DB 제약조건(FK, NOT NULL, CHECK) |
| 온라인 도움말 / 상호작용 메시지 | 프론트엔드 공통 Toast/Modal 컴포넌트로 성공/실패 메시지 일관 처리, 주요 화면에 툴팁 |
| 사용자 인터페이스 보안 | 응답 DTO에서 비밀번호 해시 등 민감정보 제외(class-transformer `@Exclude`), 전화번호 등은 관리자 화면에서도 마스킹 옵션 |
| 보안요건(개인정보보호법 26조) | 개인정보 처리방침 문서화(형식적 산출물), 접근로그(AuditLog)로 오남용 추적 가능 |

## 7. 개발 로드맵 (1인 개발 기준, 총 8~10주 권장)

기능이 8개+공통 영역으로 많기 때문에, **모든 기능을 동시에 "완벽히" 만들려 하지 않고 세로로(수직으로) 하나씩 끝내는 방식**을 권장합니다. 각 Phase 종료 시점에 "실제로 눌러볼 수 있는 데모"가 나오는 것이 목표입니다.

| Phase | 기간(권장) | 범위 | 산출물 |
|---|---|---|---|
| Phase 0 | 3~5일 | 프로젝트 셋업, DB 스키마 전체 설계, 인증(로그인/토큰), 배포 파이프라인 뼈대 | 로그인만 되는 빈 앱 |
| Phase 1 | 1.5주 | 01 권한관리 + 05 회원관리(핵심) | 관리자가 회원 CRUD하는 웹 |
| Phase 2 | 1주 | 02 인사정보관리 + 03 근태관리 | 직원/근태 관리 |
| Phase 3 | 1.5주 | 07 강사·프로그램 게시 + 06 예약/결제(모의) | 회원앱에서 예약 가능 |
| Phase 4 | 1주 | 04 게시판 + 08 혼잡도관리 | 공지/혼잡도까지 완성 |
| Phase 5 | 1~1.5주 | 통합 테스트, UI 폴리싱, 배포, 발표자료(ERD/시연 시나리오) | 최종 데모 |

각 기능 문서(1-2~1-9)의 "Phase 1(필수) / Phase 2(선택)" 구분을 참고해, 시간이 부족하면 각 기능의 **Phase 2 항목부터 먼저 쳐낼 것**을 권장합니다.

## 8. 이 문서군의 사용법

1-2~1-9 각 문서는 아래 동일한 목차로 작성됩니다.

1. 개요 및 원본 요구사항 대비 조정사항

## 9. 디자인 시스템

admin-web의 디자인 토큰·레이아웃 원칙은 별도 문서 [docs/3.design/3-1_디자인시스템.md](../3.design/3-1_디자인시스템.md)로 분리했습니다 — 페이지·컴포넌트가 늘어날수록 계속 자라날 성격의 내용이라, 1-1문서 본문을 무겁게 하지 않기 위함입니다. 방향 요약: 기존 SaaS 스타터 톤(D15)을 폐기하고 **고밀도 엔터프라이즈 라이트**(무채색 기반 + 포인트 컬러 1개, 카드보다 테이블 중심)로 전환(D19, 2026-09-08). 새 화면을 만들 때는 반드시 그 문서를 먼저 참고하세요.
