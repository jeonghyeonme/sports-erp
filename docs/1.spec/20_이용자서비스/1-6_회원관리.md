# 05. 회원관리 (Member Management) — 핵심 기능

## 1. 개요 및 조정사항

원본 요구사항: 지점별 회원 인적사항/수강내역/예약·결제내역/PT잔여세션 기록, 지점 관리자는 본인 지점 회원만 조회 가능.

**조정 없음** — 이 기능이 시스템의 핵심(원본 산출물의 본질)이므로 단순화하지 않고 가장 공들여 구현합니다. 다만 "회원 등급제(VIP/일반 등 마케팅성 세그먼트)"처럼 원본에 없는 기능은 추가하지 않습니다(범위 확장 금지).

## 2. 사용자 스토리

- 회원으로서, 앱에서 회원가입 후 내가 다니는 지점을 선택하고 이용을 시작하고 싶다.
- 지점 관리자로서, 신규 방문 회원을 현장에서 직접 등록(오프라인 등록)할 수도 있어야 한다.
- 지점 관리자로서, 회원의 수강/예약/PT 잔여 세션을 한 화면에서 확인하고 싶다.
- 회원으로서, 내 PT 잔여 세션이 몇 회 남았는지 앱에서 확인하고 싶다.

## 3. 데이터 모델

### Member
| 필드 | 설명 |
|---|---|
| id | UUID |
| accountId | FK → Account, nullable (오프라인 등록 시 앱 미가입 상태로 먼저 생성 가능 → 이후 회원이 앱 가입 시 연결) |
| branchId | FK → Branch (주 소속 지점) — `Branch`는 단순 매장이 아니라 위탁계약 현장입니다. 계약 필드(계약기간·계약상대방·계약상태)는 [1-1문서 §2-1](../00_공통/1-1_공통설계서.md#2-1-branch지점-데이터-모델--위탁계약-필드) 참고 |
| assignedStaffId | FK → Staff, nullable — 담당 직원(트레이너 등). 없으면 회원권만 등록되고 담당 직원이 없는 회원(2-1문서 D16) |
| memberNo | string, unique — `{지점코드}{연도}{순번}` |
| name, phone, birthDate, gender | |
| joinedAt | date — 최초 등록일 |
| status | enum(ACTIVE/활성, DORMANT/휴면, WITHDRAWN/탈퇴) — `MemberStatus`(schema.prisma), `MockMember.status`와 동일 값 |
| guardianConsent | boolean, default false — 미성년(유아동/청소년, [1-8문서](1-8_강사프로그램게시.md) `ageGroup`) 회원의 법정대리인 동의 여부. 민법상 미성년자 단독 계약은 법정대리인이 취소할 수 있어 실무 체육시설은 보호자 동의를 표준으로 받음 — 실제 서명·증빙 첨부 워크플로는 범위 밖이며 체크박스 수준으로만 기록 |
| memo | text, nullable — 관리자 메모(특이사항) |

### CourseEnrollment (수강내역 — 원본 "프로그램 수강 내역")
| 필드 | 설명 |
|---|---|
| id, memberId(FK), programId(FK), enrolledAt, expiresAt, status(수강중/종료) | |

### PTSession (PT 잔여세션)
| 필드 | 설명 |
|---|---|
| id, memberId, programId(PT 유형 프로그램), totalSessions, usedSessions, remainingSessions(computed), purchasedAt | |
| PTSessionLog | id, ptSessionId, usedAt, note — 세션 1회 사용시마다 로그(관리자가 "차감" 처리) |

> 예약(Reservation)·결제(Payment) 엔티티는 1-7문서에서 상세 정의하며, 회원 상세 화면에서는 이 두 엔티티를 memberId로 조회해 "수강내역/예약·결제 내역"을 한 화면에 통합 표시합니다(원본 요건 그대로). **PT 패키지 구매 시점에도 [1-7문서](1-7_예약및결제.md#3-데이터-모델)의 `Payment(ptSessionId=이 PTSession.id)`가 함께 생성되어 매출로 기록됩니다**(2026-09-15 — 예전엔 "PT는 Payment 없이 세션 차감만"으로만 다뤘던 누락을 여기서도 반영).

인덱스: `Member.branchId`, `Member.memberNo` unique, `Member.phone`(중복 가입 확인용), `Member.assignedStaffId`

## 4. 화면 목록

| 화면 | 대상 | 설명 |
|---|---|---|
| 회원 목록 | BRANCH_ADMIN(본인 지점), SUPER_ADMIN(전체+지점필터) | 검색(이름/전화번호/회원번호), 상태 필터, 담당 직원 컬럼 표시(assignedStaffId 조인, 없으면 "회원권만(미배정)") |
| 지점 상세(드릴다운) | SUPER_ADMIN | 지점 → 직원(펼치면 담당 회원) → 담당 직원 없음 회원 → 프로그램 순으로 조회(2-1문서 D16) |
| 회원 상세 | BRANCH_ADMIN | 인적사항 + 수강내역 + 예약/결제내역 + PT잔여세션 탭 구성 |
| 회원 등록(현장 등록) | BRANCH_ADMIN | 오프라인 신규회원 등록 |
| 회원가입 | Member(앱) | 지점 선택 → 정보 입력 → 가입 |
| 내 정보 | Member(앱) | 인적사항 조회/수정, PT 잔여세션 표시 |

## 5. API 명세

| Method | Endpoint | 권한 | 설명 |
|---|---|---|---|
| POST | /api/v1/members/register | 공개(앱 회원가입) | Account+Member 동시 생성 |
| POST | /api/v1/members/link | 공개(앱 회원가입 대체 플로우) | 오프라인 등록 Member와 신규 Account 연결 — `memberNo`+`phone`이 **둘 다** 기존 `Member`와 일치해야 함(§6), 이미 `accountId`가 있으면 409(`ALREADY_LINKED`), 불일치 시 401(횟수 제한 적용) |
| POST | /api/v1/members | BRANCH_ADMIN | 현장 오프라인 등록(Account 없이 Member만 생성 가능) |

| GET | /api/v1/members/:id | BRANCH_ADMIN(본인 지점)/SUPER_ADMIN/Member(본인) | 상세(수강+예약+PT 요약 포함) |
| PATCH | /api/v1/members/:id | BRANCH_ADMIN/Member(본인 일부 필드만) | 수정 |
| PATCH | /api/v1/members/:id/status | BRANCH_ADMIN | ACTIVE/DORMANT/WITHDRAWN 전환 처리 |
| GET | /api/v1/members/:id/enrollments | 권한자 | 수강내역 |
| GET | /api/v1/members/:id/pt-sessions | 권한자 | PT 세션 현황 |
| POST | /api/v1/members/:id/pt-sessions/:sessionId/use | BRANCH_ADMIN | 세션 1회 차감(PT 진행 체크) |

## 6. 비즈니스 로직 & 엣지케이스

- **전화번호 중복 체크**: 같은 지점 내 활성 회원 전화번호 중복 시 경고(완전 차단은 아님 — 가족 공유폰 등 현실적 케이스 고려), 앱 회원가입 시에는 Account.email/phone 유니크로 원천 차단
- **미성년 회원 가입**: `birthDate` 기준 만 19세 미만이면 등록/가입 API에서 `guardianConsent=true`를 요구(false 또는 미전달 시 400) — 실제 서명·증빙 첨부 없이 체크박스 동의로만 처리하는 포트폴리오 범위의 단순화입니다
- **오프라인 등록 → 앱 연동 — 연결 조건 정정(2026-09-15)**: `accountId=null`로 생성된 Member를 회원 본인이 앱에서 연결할 때, 원래 Phase 1 권장안이던 "**회원번호만 입력하면 연결**"은 `memberNo`가 `{지점코드}{연도}{순번}`로 **순차 생성되는 예측 가능한 값**이라는 걸 놓친 설계였습니다 — 몇 번만 시도하면 타인의 회원번호를 맞혀 그 사람의 PT 세션·수강내역·연락처에 접근할 수 있습니다("동일 전화번호 자동 매칭은 개인정보 리스크가 있다"고 인지했으면서, 대안으로 제시한 회원번호 단독 방식도 같은 리스크 범주였다는 걸 놓쳤습니다).
  - **정정된 방식**: **회원번호 + 전화번호를 함께 입력**받아 **둘 다 같은 Member 레코드와 일치할 때만** 연결합니다. 회원번호(추측 가능)와 전화번호(추측 불가능한 개인정보) 중 하나만으로는 안 되고 반드시 둘 다 맞아야 하므로, 이미 그 사람의 전화번호를 알고 있는 게 아닌 이상 회원번호를 브루트포스해도 뚫리지 않습니다. SMS 인증(Phase 2, 실제 소유권 증명)까지는 아니지만 회원번호 단독보다 훨씬 안전하고 관리자 승인 워크플로 없이 Phase 1 그대로 유지됩니다.
  - 연결 시도 실패는 계정 잠금(1-2문서 §6)과 같은 이유로 **횟수 제한**(예: 계정당 시간당 5회)을 둬 대입 공격을 늦춥니다.
- **PT 세션 차감**: `remainingSessions = totalSessions - usedSessions`는 항상 서버에서 계산(클라이언트 신뢰 안 함), 0 이하로 차감 시도하면 400 에러
- **타 지점 회원 조회 차단**: BranchScopeGuard로 BRANCH_ADMIN의 모든 회원 API에 `branchId` 강제 필터(원본 요구사항 5번 핵심 — "타현장 정보 조회 불가능하게 할 수 있는 권한 필요"를 기본 동작으로 강제 구현, 선택 옵션이 아니라 항상 적용)
- **회원 탈퇴**: 소프트 삭제(`status=WITHDRAWN`) + Account.isActive=false, 결제/예약 이력은 보존
- **담당 직원 배정(`assignedStaffId`)**: 회원의 `branchId`와 배정하려는 Staff의 `branchId`가 반드시 일치해야 함(1인 담당 모델, N:M 아님). 다른 지점 소속 staffId를 배정하는 것을 막는 서버측 검증은 아직 미구현 — 실제 회원 등록/수정 쓰기 API 구현 시 반드시 추가(2-1문서 D16)
- **위탁계약 종료 지점 등록 차단**: 회원 등록(현장 등록·앱 가입 모두)은 대상 `Branch.contractStatus`가 `TERMINATED`면 409(`BRANCH_TERMINATED`)로 거부합니다 — [1-1문서 §2-1](../00_공통/1-1_공통설계서.md#2-1-branch지점-데이터-모델--위탁계약-필드)의 "신규 회원 등록 차단" 원칙의 실제 구현 지점입니다

## 7. 권한/보안 규칙

- BRANCH_ADMIN: 본인 지점 회원 CRUD, 타 지점 불가(하드 룰)
- SUPER_ADMIN: 전체 조회(통계/분석 목적), 개별 회원 수정은 원칙적으로 지점 관리자 권한이나 예외 상황 대응을 위해 기술적으로는 허용
- Member 본인: 자신의 레코드만 조회/일부 수정(이름·전화번호 변경은 본인 인증 절차 필요 — Phase 2에서 SMS 인증 등 고려, Phase 1은 단순 수정 허용)
- 회원 목록 화면에서 전화번호는 기본 마스킹, 상세 진입 시 전체 노출 + AuditLog 기록(1-1문서 §5 원칙 적용)

## 8. 구현 우선순위

**Phase 1(필수, 가장 먼저 만들 기능)**: 회원 CRUD(가입/등록/조회/수정), 지점별 격리, 수강내역·PT세션 조회, PT 세션 차감 — **현장 등록·조회·수정·상태전환·미성년 동의 검증(§6)까지는 API 완료(2026-09-18), 앱 회원가입·오프라인↔앱 연동·수강내역·PT세션은 여전히 미구현. 화면(admin-web)도 등록/수정 폼이 없어 API만으로는 실사용 불가**
**Phase 2(선택)**: 오프라인↔앱 계정 연동 승인 플로우, 회원 상태 자동 휴면 전환(예: 6개월 미방문 시 배치로 휴면 처리), 전화번호 마스킹 UI

## 9. 테스트 체크리스트

- [ ] BRANCH_ADMIN이 타 지점 회원 상세 조회 시 403
- [ ] PT 세션 잔여 0 이하로 차감 시도 시 거부
- [ ] 회원 탈퇴 처리 후 앱 로그인 차단, 기존 결제 이력은 조회 가능
- [ ] 회원 상세 화면에서 수강/예약/PT 정보가 정확히 집계되어 표시
- [ ] `memberNo`는 맞지만 `phone`이 다르면 연결 실패(회원번호 단독으로는 연결 안 됨)
- [ ] 이미 `accountId`가 연결된 Member에 재연결 시도 시 409(ALREADY_LINKED)
- [ ] 연결 실패가 반복되면(시간당 5회 등) 추가 시도 차단
- [ ] 만 19세 미만 회원이 `guardianConsent=false`(또는 미전달)로 등록/가입 시도 시 400
