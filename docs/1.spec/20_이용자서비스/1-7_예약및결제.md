# 06. 예약 및 결제 (Reservation & Payment)

## 1. 개요 및 조정사항

원본 요구사항: 무/유료 프로그램 게시 후 프로그램별 예약, 모바일 결제(결제 처리방법은 원본에서도 "추후 논의"로 명시되어 있어 조정 여지가 큼).

**조정**: 실제 PG(이니시스/토스페이먼츠 등) 연동은 사업자 등록·심사가 필요해 개인 포트폴리오로는 불가능하므로 **Mock Payment(모의결제) 모듈**로 대체합니다. 단, 결제 상태 전이(대기→승인→실패/환불)와 예약 상태 연동 로직은 실제 서비스와 동일하게 완전히 구현해 "결제 도메인을 이해하고 있다"를 보여줍니다. (선택: 토스페이먼츠 테스트 API 키를 이용하면 실제 연동 흐름까지 무료로 시연 가능 — Phase 2 스트레치 목표로 제안)

**추가 반영(2026-09-15)**: §6에서 한때 "부가가치세는 의도적 범위 외"로 뺐던 결정을 번복하고, **매출 인식·부가세 구분·강사 정산까지 실제로 설계에 포함**합니다. 이유는 두 가지입니다 — ① 이 결정을 다시 검토하며 `PT_PACKAGE`(개인 PT) 구매 시점에 실제로는 결제가 발생하는데도 지금까지 `Payment` 레코드가 전혀 생기지 않아 **PT 매출 자체가 시스템 어디에도 기록되지 않는** 근본적 누락을 발견했습니다(§3 `Payment.ptSessionId` 참고). ② "ERP"를 표방하는 시스템에서 결제→매출→정산으로 이어지는 다리가 없으면 회원관리·예약 도메인이 아무리 정교해도 재무 데이터로 전혀 연결되지 않는다는 지적을 반영했습니다. 대신 국세청 홈택스 연동이 필요한 **전자세금계산서·원천징수영수증의 실제 "발행"은 Mock Payment와 동일한 논리로 상태값만 시뮬레이션**합니다(사업자 인증이 필요해 실제 발행 자체는 불가능).

## 2. 사용자 스토리

- 회원으로서, 앱에서 다니는 지점의 프로그램 목록을 보고 원하는 시간대에 예약하고 싶다.
- 회원으로서, 유료 프로그램은 예약과 동시에 결제하고 싶다.
- 회원으로서, 예약을 취소하면 결제된 금액이 환불 처리되길 원한다(정책에 따라 부분/전액).
- 지점 관리자로서, 오늘 예약 현황과 노쇼(No-show) 여부를 체크하고 싶다.

### Reservation

|---|---|

| createdAt, cancelledAt, cancelReason | |

### Payment (매출 인식의 원천 — 예약 결제 + PT 패키지 구매 결제 통합)
| 필드 | 설명 |
|---|---|
| id | UUID |
| reservationId | FK → Reservation, nullable, unique — `PAID_SESSION` 예약 결제인 경우만 값이 있음 |
| ptSessionId | FK → PTSession, nullable — `PT_PACKAGE` 패키지 **구매 시점**의 결제인 경우만 값이 있음(아래 비고 참고) |
| memberId | FK |
| amount | int — 실 결제금액(공급가액+부가세 합계, 회원이 실제로 지불한 금액) |
| supplyAmount | int — 공급가액(부가세 제외). `supplyAmount = round(amount / 1.1)`(부가가치세율 10%, 부가가치세법 제30조 — 공급대가에서 역산하는 실무 관행) |
| vat | int — 부가세. `vat = amount - supplyAmount` |
| method | enum(MOCK_CARD, FREE) |
| status | enum(PENDING/대기, APPROVED/승인, FAILED/실패, REFUNDED/환불) — `PaymentStatus`(schema.prisma) |
| mockApprovalNo | string — 모의 승인번호(실제 결제인 것처럼 시연용) |
| approvedAt, refundedAt | |

> **비고 — PT 매출 누락 수정**: 기존 설계는 `PT_PACKAGE`(개인 PT 패키지) 구매를 "Payment 없이 `PTSession.usedSessions` 차감만으로 처리"한다고 되어 있었는데, 이건 **PT를 다 쓰는(소진하는) 과정**만 다룬 것이지 **PT 패키지를 처음 사는(결제하는) 순간**이 시스템 어디에도 기록되지 않는 누락이었습니다. `PTSession` 생성(=패키지 구매) 시점에 `Payment(ptSessionId=해당 세션, reservationId=null)`를 함께 생성해 매출로 잡습니다. 세션을 실제로 쓸 때마다(`usedSessions` 차감)는 여전히 결제가 발생하지 않습니다(이미 선불로 다 낸 것이므로) — "구매 시 1회 결제 + 소진은 차감만"이 맞는 흐름입니다.

`Payment`는 `reservationId`·`ptSessionId` 중 **정확히 하나만** 값을 가져야 합니다(DB 레벨 CHECK 제약 또는 애플리케이션 검증).

인덱스: `ScheduleSlot(programId, date)`, `Reservation(memberId, status)`, `Payment(status, approvedAt)`(매출 집계 조회용)

**중복예약 방지 제약 — 조건부 unique로 정정(2026-09-15)**: `(memberId, scheduleSlotId)`에 **무조건적인** unique 제약을 걸면 안 됩니다 — 회원이 한 번 취소(`CANCELLED`)한 회차는 그 조합이 이미 테이블에 남아있어, 같은 회원이 같은 회차를 다시는 예약할 수 없게 막혀버립니다(§6 "REQUESTED/CONFIRMED 상태일 때만 재예약 차단"이라는 의도와 어긋남). PostgreSQL의 **부분 unique 인덱스(partial unique index)**로 정정합니다: `CREATE UNIQUE INDEX ON "Reservation" (memberId, scheduleSlotId) WHERE status IN ('REQUESTED','CONFIRMED')` — Prisma 스키마는 조건부 unique를 선언적으로 표현하지 못하므로 마이그레이션에 raw SQL로 추가해야 합니다. 이렇게 하면 "활성 예약은 회원당 회차당 1건"만 강제되고, 취소된 이력은 몇 건이 쌓여도 재예약을 막지 않습니다.

| confirmedAt, paidAt | datetime, nullable | |

## 6. 비즈니스 로직 & 엣지케이스 (이 기능이 가장 까다로운 영역 — 상세 기술)

- **동시 예약(정원 초과) 방지 — 락 대상 정정(2026-09-15)**: 기존 설계(`SELECT COUNT(*) FROM Reservation WHERE scheduleSlotId=? ... FOR UPDATE`)는 **기존에 이미 존재하는 Reservation 행에만** 락을 겁니다. 정원이 비어있거나(기존 예약 0건) 여유가 있을 때 두 트랜잭션이 동시에 이 쿼리를 실행하면 **둘 다 잠글 대상이 없어 그대로 통과**하고 둘 다 `INSERT`할 수 있습니다(팬텀 삽입 — `FOR UPDATE`는 존재하는 행의 수정·삭제만 막지, 새 행이 끼어드는 것은 막지 못함). 이러면 이 로직이 막으려던 정원 초과가 그대로 발생합니다.
  - **정정된 방식**: `bookedCount`를 별도 캐시 필드로 두지 않는 원칙은 유지하되, 잠그는 대상을 "카운트할 테이블"이 아니라 **"정원이 걸려있는 리소스 자체"**로 바꿉니다 — 트랜잭션 시작 시 먼저 `SELECT * FROM ScheduleSlot WHERE id=? FOR UPDATE`로 회차 행을 잠급니다(회차 행은 예약이 0건이어도 항상 존재하므로 반드시 잠금 대상이 있고, 두 번째 트랜잭션은 첫 번째가 커밋할 때까지 이 시점에서 대기하게 됨). 그 다음에야 `SELECT COUNT(*) FROM Reservation WHERE scheduleSlotId=? AND status IN ('REQUESTED','CONFIRMED')`로 현재 인원을 세고 `capacity`와 비교 → 초과 시 409(`SLOT_FULL`), 아니면 `INSERT`. `ScheduleSlot` 락이 이미 두 트랜잭션을 순서대로 직렬화하므로 이 두 번째 `SELECT`엔 `FOR UPDATE`가 필요 없습니다.
  - 포트폴리오에서 "동시성 처리를 고려했다"를 보여줄 수 있는 포인트라는 원래 취지는 그대로 유지되고, 오히려 "왜 카운트 대상이 아니라 리소스 자체를 잠가야 하는지"까지 설명할 수 있어 더 설득력 있는 포인트가 됩니다.
- **중복 예약 방지**: 동일 회원이 동일 회차에 이미 `REQUESTED`/`CONFIRMED` 상태 예약이 있으면 재예약 차단 — 애플리케이션 레벨 체크뿐 아니라 §3의 부분 unique 인덱스가 DB 레벨에서도 강제합니다(둘 중 하나만 있으면 동시 요청 경합 시 애플리케이션 체크를 우회할 수 있음). `CANCELLED`/`COMPLETED`/`NO_SHOW` 이력은 몇 건이 쌓여도 재예약을 막지 않습니다
- **진행중이 아닌 프로그램**: `Program.status`가 `PREPARING`/`PAUSED`/`ENDED`인 프로그램에는 예약 자체가 불가합니다(409 `PROGRAM_NOT_RUNNING`) — 1-8문서 §3-2
- **자유이용형(`FREE_ACCESS`) 프로그램**: 애초에 이 API의 대상이 아닙니다. 예약이라는 개념 자체가 없고, 이용 기록은 1-9문서의 `FacilityCheckIn`(QR 체크인)만으로 남습니다 — `Reservation`/`Payment` 어느 쪽에도 row가 생기지 않음
- **무료 회차(`PAID_SESSION`, price=0)**: 정원 관리는 필요하지만 결제는 없는 경우 — Payment 레코드 없이 즉시 `Reservation.status=CONFIRMED`
- **유료 회차(`PAID_SESSION`, price>0) 결제 흐름**: `예약 생성(status=REQUESTED, Payment.status=PENDING)` → `모의결제 승인 API 호출` → 성공 시 `Payment.status=APPROVED` + `Reservation.status=CONFIRMED`. 5분 내 결제 미완료 시 예약 자동 취소(배치 or TTL) — 좌석 선점 방지
- **취소/환불 정책**: 회차 시작 `Branch.cancellationDeadlineHours`시간 전(기본 24시간) 취소는 전액 환불, 그 이내는 환불 불가(01문서 §2-1 참고 — 하드코딩 금지, Program 단위 override 필요 시 Program에도 nullable로 추가). 모의결제이므로 실제 환불 처리는 상태값만 변경(`Payment.status=REFUNDED`)
- **부가세 분리는 이제 구현**: `Payment` 생성 시 `amount`(회원이 실제로 낸 금액)만 입력받고, 서버가 `supplyAmount = round(amount / 1.1)`, `vat = amount - supplyAmount`를 자동 계산해 저장합니다. 환불(`REFUNDED`) 시에도 두 값을 그대로 보존해(0으로 리셋하지 않음) 환불 전 매출 이력이 감사 목적으로 남도록 합니다.
- **청약철회권은 여전히 의도적 범위 외**: 전자상거래법상 소비자 청약철회권과 "24시간 전 취소" 정책의 정합성은 실서비스라면 약관에 명시해야 하지만, Mock Payment로 실제 법적 분쟁 리스크가 없는 이 프로젝트에서는 다루지 않습니다(D14와 동일한 판단 — 부가세와 달리 이건 "돈이 실제로 오가지 않으므로" 시스템에 배관을 놓을 유인 자체가 없는 항목이라 구분했습니다).
- **매출 집계(`/revenue/summary`)**: `Payment.status=APPROVED`인 건만 집계 대상(PENDING/FAILED는 매출 아님, REFUNDED는 환불 시점 이후 매출에서 제외 — 즉 `status=APPROVED`인 것만 더하고 `REFUNDED`로 전환된 건은 자동으로 집계에서 빠짐). 지점 매출은 `Payment.memberId`가 속한 회원의 `branchId`가 아니라 **결제 대상 프로그램의 `branchId`**로 집계합니다(회원이 타 지점 프로그램을 이용하는 경우는 없지만, 향후 확장을 대비해 명시).
- **강사 정산 생성(`/settlements/instructors/generate`)**: 지정 월의 `Program.instructorId`가 있는 모든 프로그램의 `Payment(status=APPROVED, approvedAt이 해당 월)`을 강사별로 그룹핑해 `supplyAmount` 합계를 `grossRevenue`로, 그 시점 `Instructor.commissionRate`를 스냅샷으로 `InstructorSettlement`를 일괄 생성합니다. `commissionRate`가 `null`인 강사(본사 직속 등 별도 급여 체계)는 정산 생성 대상에서 제외합니다.
- **원천징수 계산**: `withholdingTax = round(commissionAmount * 0.033)`(사업소득세 3% + 지방소득세 0.3%, 국세청 기준 표준 세율). 이 금액은 실제 홈택스 신고·지급명세서 제출로 이어져야 하지만, 그 연동은 사업자 인증이 필요해 범위 밖 — 화면에는 "원천징수영수증 발급 대상"이라는 안내만 노출합니다(Mock).
- **정산 확정 후 불변**: `CONFIRMED` 이후에는 `grossRevenue`가 재계산되지 않습니다(예: 확정 후 환불이 발생해도 해당 월 정산은 소급 변경하지 않고 다음 달 정산에서 마이너스로 조정) — 급여성 지급의 소급 변경은 실무에서도 지양되는 방식입니다.
- **위탁계약 종료 지점 차단**: 예약 생성 API는 예약 대상 프로그램의 `Branch.contractStatus`가 `TERMINATED`면 409(`BRANCH_TERMINATED`)로 거부합니다 — [1-1문서 §2-1](../00_공통/1-1_공통설계서.md#2-1-branch지점-데이터-모델--위탁계약-필드)의 "신규 예약 차단" 원칙의 실제 구현 지점입니다
- **노쇼 처리**: 회차 종료 후 체크인 안 된 `CONFIRMED` 예약은 배치로 `NO_SHOW` 처리(환불 대상 아님)
- **PT세션형(`PT_PACKAGE`) 프로그램과의 관계**: 1-6문서의 `PTSession`으로 별도 관리하며, `Program.pricingType=PT_PACKAGE`로 어느 트랙을 탈지 판별. **패키지 구매(`PTSession` 생성) 시점에 `Payment(ptSessionId=...)`를 함께 생성해 매출로 기록**하고, 이후 세션을 실제로 쓸 때(`usedSessions` 차감)는 이미 선불 결제된 것이므로 추가 Payment 없이 차감만 처리합니다 — Reservation/Payment 트랙과는 여전히 분리되지만, PT 매출 자체는 Payment를 통해 매출 집계·정산에 반영됩니다(위 비고 참고)

## 7. 권한/보안 규칙

- 회원은 본인 예약만 생성/취소/조회
- BRANCH_ADMIN은 본인 지점 프로그램에 연결된 예약만 조회/체크인/취소 처리 가능
- 결제 금액은 서버에서 Program 가격을 재조회해 검증(클라이언트가 보낸 금액 신뢰 안 함) — 기본적인 결제 보안 원칙
- **강사 정산 생성·확정·지급은 SUPER_ADMIN 전용** — 재물조사([1-10문서](../40_자원문서관리/1-10_기업구조및자원관리분석.md) §4)와 같은 이유로, 급여성 지급은 본사가 개시·확정하는 행위이지 지점이 스스로 처리할 사안이 아님. BRANCH_ADMIN은 본인 지점 강사의 정산 내역을 조회만 할 수 있음
- 정산 관련 금액(`grossRevenue`, `commissionAmount`, `withholdingTax`)은 급여 정보에 준하는 민감 정보로 취급 — 목록 화면에서는 강사 본인 행만 기본 노출, 타 강사 정산 내역은 SUPER_ADMIN만 전체 비교 조회 가능

## 8. 구현 우선순위

**Phase 1(필수)**: 회차 조회, 예약 생성/취소, 무료 회차(PAID_SESSION price=0) 흐름, 정원 초과 방지(동시성 처리) — **완료(2026-09-18, API+화면)**. 동시성 처리는 §6이 Postgres 대상으로 설명한 `ScheduleSlot` 행 락 대신, MockDataService가 단일 Node 프로세스에서 동기 실행되는 인메모리 배열이라는 점을 활용해 별도 락 코드 없이 팬텀 삽입을 막는다(실DB 전환 시 문서의 락 방식을 그대로 적용해야 함)
**Phase 2(선택, 스트레치)**: 모의결제 승인/환불 플로우, 취소 정책(24시간 규정) — **완료(2026-09-18)**. 노쇼 자동 처리 배치, 토스페이먼츠 테스트 연동은 스케줄러·PG 인증이 필요해 **미구현**
**Phase 6(확장)**: `Payment` 부가세 분리(구현 난이도가 낮아 Phase 1과 함께 **완료**로 앞당김) — PT 패키지 구매 Payment 생성(PTSession 엔티티 자체가 없어 보류, 05문서와 동일한 판단), 매출 집계 API, 강사 정산(`InstructorSettlement`) 생성/확정/지급은 [1-10문서](../40_자원문서관리/1-10_기업구조및자원관리분석.md)와 같은 확장 트랙으로 **미구현**

## 9. 테스트 체크리스트

- [ ] 정원이 1자리 남은 회차에 2명이 동시에 예약 요청 → 1명만 성공
- [ ] **기존 예약이 0건인(방금 개설된) 회차에 정원만큼(또는 그 이상) 동시 예약 요청 → 정확히 `capacity`만큼만 성공**(팬텀 삽입 시나리오 — `ScheduleSlot` 락 없이는 이 케이스에서만 뚫림)
- [ ] 동일 회원이 같은 회차 중복 예약 시도 시 차단
- [ ] **회원이 예약을 취소(`CANCELLED`)한 뒤 같은 회차를 다시 예약 시도 → 정상 성공**(부분 unique 인덱스가 활성 상태만 막는지 확인 — 무조건적 unique였다면 여기서 실패했을 것)
- [ ] 유료 예약 후 결제 미완료 상태에서 취소 시 정상 롤백
- [ ] 취소 정책 시간(24시간) 기준 환불 여부 분기 정확히 동작
- [ ] BRANCH_ADMIN이 타 지점 예약을 체크인 처리 시도 시 403
- [ ] `FREE_ACCESS`/`PT_PACKAGE` 프로그램에 예약 생성 시도 시 400(NOT_RESERVABLE)
- [ ] `PAUSED`/`ENDED` 상태 프로그램에 예약 생성 시도 시 409(PROGRAM_NOT_RUNNING)
- [ ] 결제 승인 시 `supplyAmount + vat = amount`가 항상 성립(반올림 오차 없이 합산 일치)
- [ ] PT 패키지 구매(`PTSession` 생성) 시 `Payment(ptSessionId=...)`가 함께 생성되고 매출 집계에 반영됨
- [ ] `reservationId`·`ptSessionId`가 둘 다 null이거나 둘 다 값이 있는 Payment 생성 시도 시 거부
- [ ] 정산 생성 시 `commissionRate=null`인 강사는 대상에서 제외됨
- [ ] 원천징수액이 `commissionAmount * 3.3%`로 정확히 계산됨
- [ ] BRANCH_ADMIN이 정산 확정/지급 API 호출 시도 시 403(SUPER_ADMIN 전용)
- [ ] 같은 강사·같은 월에 정산 중복 생성 시도 시 409
