# D39. 브랜치 전략 — `dev`를 주 개발 브랜치로, `main`은 완성본으로 둔다 (2026-10-06)

> 결정 기록 [인덱스](README.md) · 경위는 [log/066](../log/066.md)

**컨텍스트(Driver)**:
- 실제 개발·배포 기준 브랜치는 `main-5x9td9`였다. 클라우드 세션이 자동으로 만든 이름이 그대로 굳은 것이라, 이름만 보고는 이것이 주 개발 브랜치인지 알 수 없었다.
- 2026-10-04에 기본 브랜치를 `main-5x9td9`로 바꿨지만(Run workflow 버튼 때문, [log/056](../log/056.md)) `main`도 남아 있었다. 어느 쪽이 기준인지가 CLAUDE.md 한 줄에만 있었다.
- CI(`ci.yml`)의 push 트리거는 `main`에만 걸려 있었다. 그래서 기준 브랜치에 병합된 뒤에는 CI가 돌지 않았다(D37 "감수하는 것").
- 세션마다 임시 브랜치(`claude/*`)를 만들어 PR을 올리는 흐름은 유지하고 싶다. 사용자 요청은 "적어도 주 개발이 이뤄지는 메인 브랜치는 명시돼 있으면 좋겠다"였다.

## 결정

| 브랜치 | 역할 | 규칙 |
|---|---|---|
| `dev` | **주 개발 브랜치**, Lambda 배포 대상, 저장소 기본 브랜치 | 모든 PR의 대상. rebase 병합 |
| `main` | 완성본 | 프로젝트 완료 시 `dev`를 병합한다. 그 전에는 직접 push·PR 하지 않는다 |
| 작업 브랜치(`claude/*` 등) | 세션·작업 단위 임시 브랜치 | `dev` 대상 PR → CI → 병합 → 삭제 |

- `main-5x9td9`는 GitHub의 브랜치 이름 변경 기능으로 `dev`가 된다. 새로 만드는 것이 아니라서 이력·기본 브랜치 설정·열린 PR이 그대로 따라간다.
- CI push 트리거는 `[main, dev]`로 바꾼다. 배포 워크플로 트리거와 `render.yaml`은 `dev`로 바꾼다.

**대안**:
- `main-5x9td9`를 `main`으로 바꾸고 기존 `main`을 지운다 — 이름은 가장 단순하다. 하지만 사용자가 `main`을 완성본 자리로 남기길 원했다.
- 이름은 두고 문서에만 명시한다 — 바꿀 것이 없다. 하지만 이름이 역할을 말해 주지 않는 문제가 그대로 남는다.

**감수하는 것**:
- AWS 배포 역할의 OIDC 신뢰 정책 `sub`에 브랜치 이름이 들어 있다. 이름을 바꾸면 신뢰 정책도 바꿔야 하고, 안 바꾸면 배포가 인증 단계에서 실패한다. 전환하는 동안에는 두 이름을 모두 허용한다([aws-lambda/README.md](../../aws-lambda/README.md)).
- 이 결정을 담은 PR은 이름을 바꾸기 전의 `main-5x9td9`에 병합된다. 이름을 바꿀 때까지는 배포 워크플로의 push 트리거(`dev`)가 걸리지 않는다. 그 사이 api 변경은 병합하지 않는다.
- 사용자 로컬 저장소와 GitHub Desktop은 브랜치 이름을 직접 바꿔야 한다.
- 이전 결정·로그에 적힌 `main-5x9td9`는 그때의 기록이라 고치지 않는다.

**재고 트리거**: 프로젝트를 완료해 `dev`를 `main`에 병합할 때. 그때 `main`을 기본 브랜치로 되돌릴지 정한다.
