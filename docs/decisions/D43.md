# D43. 쌓이는 목록은 서버 페이지네이션(offset)을 기본으로 한다 — 회원·예약·결제·자산

> 결정 기록 [인덱스](README.md) · 경위는 [log/081](../log/081.md) · 분류 근거는 [traffic-infra-review](../architecture/traffic-infra-review.md) "B4 분류 결과" · [D37](D37.md) R4(회원 목록 페이지네이션 "후속")를 이어받는다
> 번호: 이 결정은 처음 D42로 작성됐으나, 병합 순서상 D41(회원 모바일 웹)·D42(k6 실측)가 먼저 들어가 D43이 됐다.

**상태**: 결정(2026-10-07), 구현 전 — [작업 브리프](../process/04_작업_브리프.md) B8.

## 컨텍스트

traffic-infra-review의 후보 이슈를 실DB 코드 기준으로 다시 확인했다(2026-10-07). N+1과 전체 배열 스캔은 D31~D36 이관 때 대부분 사라졌다. **페이지네이션이 없어 응답 크기와 조회량이 데이터 누적에 비례하는 목록 4개**가 남았다.

| 목록 | 코드 | 누적 속도 | 본사(필터 없음) 호출 시 |
|---|---|---|---|
| `GET /members` | `member.service.ts` `list` | 지점당 약 280명, 3년 후 약 3만 명(design-constants ②⑥) | 전 지점 회원 전체 |
| `GET /reservations` | `reservation.service.ts` `list` | 하루 약 1,700건(⑮, 가정) | 예약 이력 전체 |
| `GET /payments` | `payment.service.ts` `list` | 예약과 같은 수준(⑮) | 결제 이력 전체 + 날짜 필터는 메모리에서(ADR-RSV-04) |
| `GET /assets` | `asset.service.ts` `list` | 폐기(`DISPOSED`) 자산이 빠지지 않음(D35에서 보류) | 전 지점 자산 전체 |

이 문제는 D24의 공유 CPU 경합과 성격이 다르다. 요청 하나의 비용이 데이터 크기에 비례한다. 그래서 Lambda(D37)로 옮겨도 사라지지 않는다. 처리 시간 W가 늘면 상한 10의 실질 처리량(약 50 rps, ⑫)이 그만큼 준다.

## 검토한 대안

| 안 | 내용 | 장점 | 비용·위험 |
|---|---|---|---|
| **A. offset 페이지네이션** | 게시판 ADR-BRD-02 패턴(`count` + `skip/take`)을 재사용 | 이미 검증된 패턴이고, admin-web 표에 쪽 번호만 붙이면 된다. 3만 행 규모에서 offset 비용은 무시할 수준이다 | 4개 화면의 admin-web 변경. 쪽을 넘기는 사이에 새 행이 끼면 항목이 밀린다(관리 화면이라 감수) |
| B. 커서(keyset) 페이지네이션 | `id`·`createdAt` 기준 "다음" 커서 | 규모가 커져도 비용이 일정하다 | 쪽 번호 UI를 쓸 수 없고 게시판과 패턴이 갈린다. 이 프로젝트 규모에는 과하다 |
| C. 지점 필터 필수화 | SUPER_ADMIN도 지점을 골라야 조회 | 코드 변경이 가장 적다 | 한 지점 안의 예약·결제 이력 누적은 그대로 남는다 |

## 결정

**A.** 쌓이는 목록 4개에 offset 페이지네이션을 넣는다.

1. **요청·응답 형식**: 게시판(`posts.controller.ts`)과 같다. 쿼리는 `page`·`limit`(기본 20), 응답은 `ok(items, { page, pageSize, total })`. 게시판에는 `limit` 상한이 없다. 이 4개 목록에는 상한을 두고 값은 B8에서 정한다.
2. **정렬**: 지금 정렬(회원 `memberNo`, 예약·결제 `createdAt, id`, 자산 `assetCode`)을 유지한다. 예약·결제는 최근 것부터 보는 쪽(`desc`)으로 바꿀지 B8에서 화면과 함께 정한다.
3. **필터는 where로 내린다**: 메모리에서 거른 뒤 자르면 total과 쪽이 틀린다. 결제 날짜 필터가 그렇다(ADR-RSV-04).
4. **자산의 폐기 누적**은 별도 아카이빙 없이 이 페이지네이션과 기존 `status` 필터로 해결한다. 기본 목록에서 `DISPOSED`를 뺄지는 B8에서 화면과 함께 정한다.
5. **회원 모바일 웹(B1)의 본인 조회**(`GET /reservations` MEMBER 본인)도 같은 형식을 받는다. 범위가 본인으로 좁아 페이지가 하나로 끝나는 경우가 대부분이다.

## 결과

- 좋아지는 것: 목록 응답 크기와 W가 데이터 누적과 분리된다. D37 R4가 닫힌다.
- 감수하는 것: admin-web 화면 4개와 api 응답 형식이 바뀐다. 응답이 배열에서 meta 포함으로 바뀌므로, 기존 클라이언트(admin-web)를 같은 PR에서 함께 고쳐야 한다.
- 범위 제외: 회원 이름·전화번호 `contains` 검색의 인덱스(pg_trgm)는 넣지 않는다. 지점 범위에서는 약 280행이라 의미가 없다. 재고 트리거: 본사 전체 검색이 느려질 때.
- 범위 제외: 예약·결제 이력 아카이빙. DB 무료 용량(⑮)에는 1~1.5년 뒤에 닿아 프로젝트 기간 밖이다. 재고 트리거: DB 사용량이 300MB를 넘을 때.

**재고 트리거**: 한 목록의 행 수가 수십만을 넘어 offset 비용이 보일 때 → B(커서)로 바꾼다.
