# D56. 업무지원 요청 — 지점 관리자가 요청하고 본사가 처리하는 새 테이블(SupportRequest), 4상태 (2026-10-17)

> 결정 기록 [인덱스](README.md) · 경위는 [log/121](../log/121.md) · RFP 개념도(p.4) 현장→본사(D51 M9). 엔티티 정의는 [entities.md](../architecture/entities.md) §2-4

**컨텍스트(Driver)**: 개념도의 현장→본사 두 흐름(업무일지·업무지원 요청) 중 업무지원 요청이 코드·설계 어디에도 없었다(2026-10-11 원본 재대조). 기존 테이블로는 "요청 → 처리 → 결과"를 추적할 곳이 없다.

**상위 목표(D53)**: 노하우 습득 — 서비스데스크형 요청 흐름(상태 전이·책임자·종결)을 도메인에 맞게 설계해 본다. **핵심 변수**: 요청에서 처리까지의 흐름을 추적하고 책임자를 남기는 것, 현장 창구 일원화(인사 권한 분리와 같은 결). **답안지**: 서비스데스크 티켓(Jira Service Management 등)의 "요청 → 처리중 → 완료" + "반려".

## 결정 (사용자 승인 2026-10-17 — 스키마 변경, 사용자 설명: 없음 — 추천안 선택)

1. **새 테이블 `SupportRequest`** + enum 2개(분류 FACILITY·STAFFING·SUPPLIES·IT·OTHER, 상태 REQUESTED·IN_PROGRESS·DONE·REJECTED). 마이그레이션 `20261017031420_d56_support_request`.
2. **상태 흐름**: 요청 → 처리중 → 완료, 요청·처리중에서 반려. 완료·반려는 종결. 반려는 답변 필수. 앱은 "읽은 상태 그대로일 때만" 바꾸고(동시 처리 중 하나만 반영, 나머지 409), DB는 CHECK 두 개로 받친다(반려 답변 필수, 종결 상태 ⇔ `resolvedAt`).
3. **권한**: 요청은 지점 관리자(자기 지점, 서버가 지점을 정함), 처리는 본사만. 지점 관리자는 자기 지점 요청만 본다(전역 가드 D46, 리소스 종류 `supportRequest`). 직원 요청은 지점 관리자를 거친다.
4. **계약 종료 지점**은 새 요청 409 `BRANCH_TERMINATED`, 지난 요청 조회는 유지(CLAUDE.md 계약 종료 차단 — 신규 활동).
5. 변경 이력(AuditLog)에는 남기지 않는다 — 요청 행 자체에 처리자·처리 시각·답변이 있다.

## 대안 → 트레이드오프

| 대안 | 얻는 것 | 비용·위험 | 판단 |
|---|---|---|---|
| **새 테이블, 반려 포함 4상태(선택)** | 처리 불가 건을 사유와 함께 닫을 수 있다, 책임자·시각 추적 | 스키마 변경(승인), 화면 1개 | 선택 |
| 새 테이블, 3상태 | 단순 | 처리 불가를 "완료"로 닫아 통계가 흐려진다 | 기각 |
| 게시판 재사용(지점→본사 범위 추가) | 화면 재사용 | 그것도 enum 변경(스키마)이고 상태 추적이 없다 | 기각 |

**재고 트리거**: 처리 담당자 배정·기한(SLA)이 필요할 때, 요청에 첨부가 필요할 때(D57 저장소 재사용), 직원이 직접 요청해야 할 때.
