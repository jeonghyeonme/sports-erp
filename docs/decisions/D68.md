# D68. 위탁계약 갱신·정정·신규 지점 등록 — 계약 이력은 기존 변경 이력(AuditLog)에, 스키마 변경 없이 (2026-10-26, 계획)

> 결정 기록 [인덱스](README.md) · 경위는 [log/185](../log/185.md)

**상태**: 설계 확정, **구현 미착수**(사용자: "이 설계로 진행하겠다고 계획만 세워둬"). 착수는 사용자가 정한다.

**컨텍스트**: 지점(Branch)은 위탁운영 계약 현장인데([entities.md](../architecture/entities.md) §2-1), 지금 앱에서 바꿀 수 있는 계약 데이터는 **상태 하나**뿐이다(`PATCH /branches/:branchId/contract-status`). 계약 상대방·시작일·종료일을 입력·수정하는 API와 화면이 없고(값은 시드 데이터), 새 지점(새 계약)을 만드는 기능도 없다. 그래서 갱신하면 새 종료일을 넣을 곳이 없고, 상태 변경조차 변경 이력(D44)에 남지 않는다. 지점 상세의 안내 문구 "지금은 본사가 입력한 계약 정보를 보여 줍니다"(D22)는 사실과 다르다. [차별화전략](../reference/차별화전략.md) §1은 `PATCH /branches/:id/contract`(갱신 시 새 종료일 입력)를 초안으로만 두었다.

**결정**(사용자, 2026-10-26) — OCR·AI(차별화전략 §1-1)는 제외하고, 그 토대인 수기 입력부터:
1. **계약 갱신**(본사만) — 새 종료일(지금 종료일보다 뒤) 입력, 필요하면 상대방 변경 → 상태를 정상(ACTIVE)으로. **종료(TERMINATED) 지점은 409** — 끝난 계약이다. 같은 단지와 다시 계약하면 본사가 상태를 먼저 되돌린 뒤 갱신한다(끝난 파견은 복구하지 않는다 — ADR-STF-07과 같은 태도).
2. **계약 정보 정정**(본사만) — 상대방·시작일·종료일의 오타 수정. 갱신으로 세지 않고 상태도 바꾸지 않는다.
3. **계약 이력** — 갱신·정정·상태 변경을 변경 이력(`AuditLog`, entity `Branch`)에 **같은 트랜잭션에서** 남기고(D44의 원칙), 지점 상세에 "계약 이력"으로 보인다. 지금 상태 변경이 이력에 남지 않는 빈틈도 함께 메운다.
4. **종료 임박 표시** — 스케줄러 없이 조회 때 계산: 대시보드·지점 상세에 종료일까지 남은 일수, 종료 60일 이내(entities.md §2-1의 `renewalNoticeAt` 정책값)인데 상태가 정상이면 표시만 한다. **자동 상태 전환은 여전히 하지 않는다**(본사가 판단).
5. **신규 지점 등록**(본사만) — 새 위탁계약 = 새 지점. 이름·지점 코드(유일, 회원번호·직원코드 생성에 쓰임)·지역·주소·전화·출근 기준 시각 + 계약 상대방·시작일·종료일. 시설·프로그램·직원 파견은 기존 화면에서 이어서 한다.
6. **화면** — 지점 상세 계약 정보 카드에 [계약 갱신]·[정보 수정], 대시보드에 [지점 등록]. 잘못된 안내 문구를 고친다.
7. **검증** — 지점 관리자 403, 지점 격리 공격 표(`branch-isolation.spec.ts`)에 새 라우트, 날짜 규칙(종료 ≥ 시작, 갱신 종료일 > 기존), 종료 지점 갱신 409, 이력이 변경과 같은 트랜잭션에 남는지(롤백 시 함께 사라짐), 지점 코드 중복 409.

**대안 및 미채택 사유**: 계약 이력 전용 테이블(예: `ContractRenewal` — 회차·기간·계약서 파일 연결)은 갱신 회차와 계약서 문서를 깔끔하게 묶지만 Prisma 스키마 변경(승인 필요)·마이그레이션·배포 DB 반영이 붙는다. 지금 필요한 것은 "누가 언제 무엇을 바꿨나"이고 `AuditLog`(entity·before·after JSON)로 충분하다. 계약서 OCR을 붙일 때(검토 후 반영) 계약서 파일과 회차를 묶을 필요가 생기면 다시 판단한다.

**타당성·리스크**: 스키마 변경이 없어 배포 DB 쓰기는 앱을 통한 정상 사용뿐이다. 신규 지점 등록은 지점 코드·지역 같은 입력 칸이 늘어 범위가 가장 크다 — 착수 때 갱신·정정·이력·임박 표시와 나눠 두 번에 할 수 있다. 계약 상태 판정(`BranchService.loadGate()`)은 그대로라 계약 종료 차단 규칙은 바뀌지 않는다.

**재검토 조건**: 계약서 OCR·AI 착수 때, 갱신 회차별 조회(몇 번째 갱신인가)가 필요해질 때, 자동 상태 전환을 위한 스케줄러가 생길 때.
