# D52. 변경 이력 범위를 근태 정정·회원 상태·자산 상태로 넓힌다 (2026-10-15)

> 결정 기록 [인덱스](README.md) · 경위는 [log/117](../log/117.md) · [D44](D44.md)(변경 이력 도입)·[D47](D47.md)(열람 기록) 위에 얹는다. D44를 대체하지 않는다 — 기록 대상만 늘린다

**컨텍스트(Driver)**: RFP 1-2 #3 데이터관리방안(변경이력). D44는 인사 변경 4종(권한·퇴사·파견·파견 종료)만, D47은 전화번호 열람만 남겼다. 요구사항추적표 §2-3에 "회원·자산 상태 변경, 근태 정정은 기록하지 않는다"가 남아 있었다(D51 M7). 근태 정정(근태관리 ADR-ATT-04)이 새로 생기며 그 흔적이 필요해졌다.

## 결정

1. **기록 대상 3개를 더한다**(사용자 선택 2026-10-15). 스키마 변경 없음 — `AuditLog.action`·`entity`가 문자열이다.
   | action | entity / entityId | before → after |
   |---|---|---|
   | `ATTENDANCE_CORRECTED` | `Staff` / 직원 id | `{date, status, checkInAt, checkOutAt}`(없던 날은 `{date, status: null}`) → 같은 필드 + `reason`, `branchId` |
   | `MEMBER_STATUS_CHANGED` | `Member` / 회원 id | `{status}` → `{status, branchId}` |
   | `ASSET_STATUS_CHANGED` | `Asset` / 자산 id | `{status}` → `{status, branchId}` |
2. **근태 정정은 직원 기준(`entity=Staff`)으로 쌓는다** — 기록 단위(`AttendanceRecord`)보다 "이 직원에게 무슨 일이 있었나"를 한 줄로 모아 보는 쪽(인사 변경과 같은 대상)이 본사가 쓰는 방식에 맞다.
3. **D44 규칙을 그대로 따른다**: 변경과 같은 트랜잭션에서 쓰고(실패한 변경은 남지 않음), 바뀐 필드만 넣고 개인정보(연락처)는 넣지 않는다. 값이 실제로 바뀌지 않은 요청(같은 상태로 재전송)은 남기지 않는다. 자산은 조건부 갱신이 0건(동시 전이 패배)이면 남기지 않는다.
4. 본사 "변경 이력" 화면에 이벤트 3종과 대상 "자산"(이름(자산코드))을 더한다. 열람 권한은 D44대로 본사만.

## 대안 → 트레이드오프

| 대안 | 얻는 것 | 비용·위험 | 판단 |
|---|---|---|---|
| **3개 모두(선택)** | 추적표 §2-3 변경 이력 행을 닫음 | 쓰기 경로 3곳에 기록 호출 | 선택 |
| 근태 정정만 | 가장 작음 | 회원 탈퇴·자산 폐기 같은 되돌리기 어려운 변경의 흔적이 없음 | 기각 |
| 요청 단위 자동 기록(인터셉터) | 기록 누락이 없음 | 트랜잭션 밖이라 실패한 변경도 남거나 성공이 빠질 수 있음, 바뀐 필드만 담기 어려움 | 기각(D44 재고 트리거 — 기록 대상이 더 늘면 다시 본다) |

**재고 트리거**: 기록 대상이 더 늘어 쓰기마다 붙이기 번거로워질 때(D44와 같음), AuditLog가 50MB를 넘을 때(D47 보존 규칙).
