# D25. admin-web을 Cloudflare Worker 정적 자산으로 통합(Render Static Site 폐기)

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: D24 1단계(Worker 엣지 프록시) 배포 직후 사용자가 두 가지를 보고했다 — ① 로그인이 안 됨, ② 화면 새로고침 시 NotFound. 원인으로 짚이는 것: admin-web(Render, `sports-erp-web`)과 api 게이트웨이(Cloudflare Worker, `workers.dev`)가 서로 다른 오리진이 되면서 ①은 새로 생긴 크로스오리진 문제일 가능성이 높고, ②는 D23에서 이미 "미검증"으로 표시해뒀던 Render Static Site의 `_redirects`(Netlify 문법) 동작이 실제로 안 먹혔을 가능성이 높다. 사용자가 "아예 Cloudflare로 admin-web도 이관하자"고 제안했고, 이건 두 버그를 각각 땜질하는 것보다 **구조적으로** 낫다고 판단했다 — 같은 오리진이 되면 CORS라는 변수 자체가 사라지고, `not_found_handling: single-page-application`은 Cloudflare 1급 기능(공식 문서에 명시된 라우팅 옵션)이라 `_redirects` 파일이 Render에서 실제로 해석되는지 추측할 필요가 없어진다.

**설계 질문**: 로그인 실패·새로고침 404를 각각 디버깅할 것인가, 아니면 애초에 두 버그의 공통 원인(오리진 분리)을 없앨 것인가?

**대안 → 트레이드오프**

| # | 대안 | 무엇을 해결하나 | 한계 |
|---|---|---|---|
| A | 현 구조(Render admin-web + Cloudflare Worker api) 유지하고 점 단위로 디버깅 | 최소 변경 | 이 세션은 `onrender.com`/`workers.dev`에 직접 접근할 수 없어(egress 정책) 브라우저 DevTools 없이는 원인을 추측만 할 수 있다 — 근본 원인(오리진 분리) 자체는 그대로 남아 다른 크로스오리진 문제가 또 생길 수 있음 |
| B | Worker api 게이트웨이를 걷어내고 admin-web·api 둘 다 Render로 되돌림(D23 원안) | 오리진 통일(둘 다 Render) | D24가 얻은 엣지 rate limit(로그인 CPU 스로틀링 방어)을 포기하게 됨 — 원인은 해결해도 다른 문제를 되살림 |
| **C(채택)** | admin-web을 Cloudflare Worker의 정적 자산(`assets`)으로 흡수 — UI+API+rate limit 전부 한 Worker | UI/API 오리진 통일(CORS 소거) + Cloudflare의 1급 SPA 라우팅으로 새로고침 404 해결 + D24의 rate limit도 유지 | Cloudflare Workers Builds(git 연동) 없이는 `wrangler deploy`를 수동으로 다시 돌려야 배포됨(Render의 git push 자동배포보다 DX 후퇘) — 아래 "감수하는 것" 참고 |

**결정**: C. `cloudflare-worker/wrangler.jsonc`에 `assets.directory: "../apps/admin-web/dist"`, `not_found_handling: "single-page-application"`, `run_worker_first: ["/api/*"]`를 추가했다. `run_worker_first`를 `/api/*`로 한정한 덕분에 `src/index.ts`(프록시+rate limit 로직)는 수정 없이 그대로 두면 된다 — UI 요청은 이 스크립트를 아예 거치지 않고 Cloudflare 라우팅 계층에서 바로 정적 자산으로 서빙된다. `apps/admin-web/src/lib/api.ts`의 `baseURL` 폴백을 `http://localhost:3000/api/v1`(잘못된 프로덕션 기본값이었음)에서 `/api/v1`(상대경로)로 바꿔, 프로덕션 빌드 시 `VITE_API_BASE_URL`을 아예 지정하지 않아도 같은 오리진의 `/api/v1`을 그대로 호출하게 했다.

**타당성**: 높음 — 두 버그의 재현·디버깅 없이도(이 세션은 어차피 재현 불가능한 환경이었다) 원인 구조 자체를 없애는 접근이라, "왜 고쳐졌는지"를 브라우저 확인 없이도 논리적으로 설명할 수 있다. 다만 실제로 두 버그가 사라졌는지는 사용자의 `wrangler deploy` 재실행과 브라우저 확인이 있어야 최종 확정된다(아래 "다음 작업").

**감수하는 것**: ① Worker가 UI+API+rate limit을 전부 지는 단일 실패 지점이 됨(D24가 이미 인지한 리스크가 커짐 — Worker 장애 시 화면 자체가 안 뜸). ② admin-web 코드를 바꿀 때마다 `npm run build --workspace=apps/admin-web` → `wrangler deploy`를 수동으로 다시 돌려야 한다 — Render Static Site가 가졌던 "git push하면 자동 재배포" 경험을 잃는다. 이건 실질적인 DX 후퇴이고, 필요해지면 Cloudflare Workers Builds(GitHub 연동)로 되찾을 수 있지만 지금은 범위 밖으로 남겨둔다. ③ Render `sports-erp-web` Static Site는 이제 쓰지 않지만, 이 서비스를 실제로 삭제하는 것은 Render MCP 툴셋에 삭제 기능이 없어(조회·생성·갱신만 가능) 사용자가 Render 대시보드에서 직접 해야 한다 — Cloudflare 쪽 동작이 확인된 뒤에 진행 권장(확인 전에 지우면 롤백 수단이 없어짐).

**배포 시도 1 실패 — `_redirects` 무한루프(같은 날)**: 사용자가 위 절차대로 `wrangler deploy`를 실행하자 자산 업로드·바인딩 등록까지는 성공했지만, Cloudflare API가 마지막 게시 단계에서 거부했다 — `Invalid _redirects configuration: Line 1: Infinite loop detected... would cause a redirect to strip .html or /index and end up triggering this rule again`. 원인은 `apps/admin-web/public/_redirects`(Render/Netlify용으로 남겨뒀던 `/* /index.html 200` 규칙)였다 — Cloudflare 공식 문서로 확인해보니 `_redirects`는 Netlify 전용 문법이 아니라 **Cloudflare Workers 정적 자산이 자체적으로 파싱하는 1급 기능**이고, 기본 `html_handling`(`auto-trailing-slash`)이 `/index.html`을 다시 `/`로 정규화해 `/*` 규칙에 재매칭시키면서 무한루프가 된다. 이미 `not_found_handling: single-page-application`이 같은 역할(어떤 자산에도 안 걸리는 요청에 `index.html`을 200으로 서빙)을 충돌 없이 수행하므로, `_redirects` 파일은 이제 불필요할 뿐 아니라 **적극적으로 배포를 막는 존재**였다. `apps/admin-web/public/_redirects`를 삭제해 해결했다 — Render Static Site를 쓰던 시절엔 필요했던 파일이 D25로 오리진이 바뀌면서 의미를 잃고 충돌로 전환된 사례.

**배포 시도 2 성공(같은 날)**: `_redirects` 삭제 + `@cloudflare/workers-types` 버전 정정을 반영해 재실행하자 `npm install`도 에러 없이 끝났고(버전 핀 수정이 실제로 클린 설치 문제를 없앴다는 뜻), `wrangler deploy`가 게시까지 완주했다(`https://sports-erp-api-gateway.01-beauty-minimal.workers.dev`, Version ID `307222a2-d754-4d4d-9c99-797ce7582fe6`). **아직 남은 것**: 브라우저로 이 URL을 열어 UI 로딩·로그인·새로고침(임의 경로) 실동작 확인 — 배포 성공이 곧 "설정이 유효하다"는 뜻이지 "런타임 동작이 의도대로다"까지 보장하진 않는다(D24 완료 문단에서도 같은 구분을 했었음).

**브라우저 확인 결과(같은 날) — 새로고침은 해결, 로그인은 별개 버그로 남음**: 사용자가 "새로고침은 돼, 로그인 안돼"라고 보고했다. D25의 원래 목적(SPA 라우팅)은 달성됐지만, 로그인 실패는 다른 원인이었다 — **이 결정 자체의 `baseURL` 폴백 설계에 있던 오류**다. "프로덕션 빌드는 `VITE_API_BASE_URL`을 비워두면 상대경로로 폴백한다"고 판단했을 때, `apps/admin-web/.env`(로컬 API 서버를 가리킴, gitignore돼 저장소엔 안 보임)가 **`vite build`(프로덕션 빌드)에도 그대로 로드된다는 걸 확인하지 않고 가정으로 넘어갔다** — Vite는 `.env`를 dev/build/preview 전 모드에서 동일하게 읽고, 모드별 분리는 `.env.development`/`.env.production` 같은 접미사 파일만 담당한다. 그 결과 배포된 번들에 `http://localhost:3000/api/v1`이 문자열 그대로 박혀, 브라우저가 자기 자신의 로컬호스트를 호출하려 시도해 로그인이 실패했다(실제로 `dist/assets/*.js`를 grep해서 확인). `apps/admin-web/.env`를 `.env.development`로 이름을 바꿔 모드 한정으로 만들어 해결했다 — 자세한 진단·수정 과정은 `docs/log/` §36 참고.

**최종 확인(2026-09-28)**: 사용자가 재배포 후 "로그인 됐어"로 확인했다. D25가 잡으려던 두 버그(새로고침 404, 로그인 실패) 모두 실제로 해소됐고, admin-web+api 게이트웨이+rate limit이 `sports-erp-api-gateway` Worker 하나에서 정상 동작하는 게 브라우저 기준으로 확정됐다.

**다음 작업**: Render `sports-erp-web` 수동 삭제(대시보드에서 사용자가 직접 — 이제 안 쓰는 게 확정됨) → `cloudflare-worker/README.md`의 rate limit curl 테스트(§33부터 미확인)까지 마무리.
