# D27. Lambda 이관 전제의 스키마 보강 — 부분 unique 3종 · 날짜 컬럼 KST 정합 · 무상태화 테이블

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: D26이 스키마를 mock과 필드 단위로 맞췄지만, "필드가 있는가"만 대조해서 **제약·기본값·상태 위치**는 옛 스키마 그대로였다. 사용자가 "Render에 힘을 싣지 않고 추후 Lambda로 API를 호출할 것"이라고 방향을 확정하면서(2026-09-29), 도메인 이관을 계속하기 전에 스키마가 Lambda(병렬 인스턴스, 무상태) 전제와 이미 결정된 ADR들을 실제로 만족하는지 다시 봤다. 세 가지 틈이 있었다.

1. **ADR이 "활성 상태만 유일"로 결정한 것이 전역 unique로 들어가 있었다.** `Account.email @unique`는 ADR-MEM-02(탈퇴 회원 이메일 재사용), `Reservation @@unique([memberId, scheduleSlotId])`는 ADR-RSV-02(취소 후 재예약 허용)와 정면으로 모순이다 — mock에선 앱 로직으로 흉내 내서 테스트가 통과하지만, 회원관리·예약을 Prisma로 옮기는 순간 DB가 탈퇴 후 재가입·취소 후 재예약을 unique 위반으로 막는다. ADR-STF-03(활성 파견 1건)은 아예 DB 제약이 없었다.
2. **날짜 의미 필드에 `@default(now())`가 걸려 있었다.** `Member.joinedAt`·`Post.publishedAt`·`CourseEnrollment.enrolledAt`·`PTSession.purchasedAt`. DB의 `now()`는 UTC라 00:00~08:59 KST에 하루 전 날짜가 된다 — 2026-09-23에 5개 도메인 10곳에서 고친 버그([architecture/date-time-handling.md](../architecture/date-time-handling.md))가 DB 계층에서 재발하는 경로다. 계약일·입사일·취득일·보존기한도 날짜인데 timestamp였다.
3. **인스턴스 메모리에 있던 상태의 자리가 없었다.** 회원 연동 실패 횟수(ADR-MEM-01, `Map<memberNo, timestamp[]>`)는 Lambda 인스턴스마다 따로 쌓여 "5회 제한"이 인스턴스 수만큼 느슨해진다. 채번(`staffCode`·`memberNo`·`assetCode`)은 mock이 "기존 개수+1"이라 병렬 요청에서 같은 번호가 나오는데, ADR-STF-02가 결정한 "지점별 시퀀스 행 + `FOR UPDATE`"의 테이블이 없었다. D26 "다음 작업" ②④(커넥션 풀링, 콜드스타트)의 스키마 쪽 준비(`directUrl`, `binaryTargets`)도 없었다.

| 대안 | 장점 | 한계 |
|---|---|---|
| A. 도메인을 이관할 때마다 그 도메인의 제약만 고친다 | 이번 작업량 최소 | 이관 순서상 회원관리가 다음이라 곧바로 1번에 부딪힌다. 날짜 기본값처럼 여러 도메인에 걸친 규칙이 도메인마다 따로 결정돼 어긋날 위험 |
| B. 앱 레벨 검사만으로 유일성 보장(mock과 동일) | 스키마 변경 없음 | Lambda 병렬 인스턴스에서 "검사 후 삽입" 사이 경합을 못 막는다 — ADR-RSV-02·STF-03이 "애플리케이션 체크 + 부분 unique 이중화"를 택한 이유 그 자체 |
| **C. 이관을 이어가기 전에 스키마 쪽 틈만 한 번에 메운다 (채택)** | ADR을 DB가 강제, 이후 도메인 이관이 스키마 변경 없이 코드만 옮기면 됨 | Prisma 5 스키마 문법으로 부분 인덱스를 표현할 수 없어 마이그레이션 SQL에만 존재 — `schema.prisma` 상단 주석으로 보완 |

**결정**: C. 판단 기준: 세 틈 모두 "이미 내린 결정(ADR-MEM-02·RSV-02·STF-03, 날짜 규칙, D26 다음 작업)"을 스키마가 못 따라간 것이지 새 설계 판단이 아니다 — 도메인마다 흩어 고치면 같은 규칙을 여러 번 다르게 구현하게 된다.

**한 일**: `main-5x9td9`의 두 마이그레이션 위에 세 번째 마이그레이션 `20260929002914_d27_lambda_readiness`를 얹었다 — 부분 unique 3종(SQL), 날짜 의미 컬럼 11개를 `@db.Date`로 바꾸고 날짜 필드의 DB 기본값 제거, `CodeSequence`·`MemberLinkAttempt` 신설, `directUrl`·`binaryTargets`(`rhel-openssl-3.0.x`) 추가. 이메일이 unique 키가 아니게 되면서 `AuthService.login`의 `findUnique({ email })`는 **타입 오류로 컴파일이 안 됐다** — `findFirst`로 바꾸되 활성 계정을 먼저 고르고, 비활성뿐이면 그 계정을 돌려 `ACCOUNT_INACTIVE`로 거부하게 했다(비활성 계정을 걸러버리면 mock 폴백으로 새서 `INVALID_CREDENTIALS`라는 다른 에러가 나는 것을 막음). `seed.ts`의 `upsert` 키도 이메일에서 고정 id로 바꿨다.

**검증**: 로컬 Postgres 16에 CI 절차(`migrate deploy` → `seed` → 테스트)를 새 DB로 재현 — 테스트 18/19 스위트, 251 통과(기존 248 + 신규 `auth-email-reuse.spec.ts` 3건, D26의 skip 3건은 그대로). 테스트는 `DIRECT_URL` 없이 돌려 런타임(Render/Lambda)엔 이 값이 필요 없음을 확인했다. 시드된 DB에서 세 부분 인덱스가 중복을 거부하고 대조군(탈퇴 후 재가입, 종료된 파견 이력, 취소 후 재예약)은 통과하는 것을 SQL로 확인했다. `prisma migrate dev`가 부분 인덱스를 지우려 하지 않는 것(빈 마이그레이션 생성)도 확인했다. Supabase는 적용 **전** 컬럼·인덱스·enum·제약 지문 4종이 로컬(앞 두 마이그레이션 적용분)과 일치하고 데이터 0행임을 확인한 뒤 MCP `apply_migration`으로 적용했고, 적용 **후** 지문도 로컬과 다시 일치했다. 신규 테이블 2개도 RLS를 켜 전 테이블 RLS 활성 상태를 유지했다.

**감수하는 것**: ① 부분 인덱스가 `schema.prisma`에 안 보인다 — Prisma 버전을 올릴 때 `migrate dev`가 이를 DROP하려 하는지 다시 확인해야 한다(상단 주석에 명시). ② Supabase `_prisma_migrations`는 여전히 비어 있다(D26 감수 사항 ③ 그대로) — 이번엔 지문 비교로 로컬 이력과 같은 상태임을 증명해 두었다. ③ `CodeSequence`·`MemberLinkAttempt`는 테이블만 있고 아직 아무 코드도 안 쓴다 — 인사정보관리·회원관리를 Prisma로 옮길 때 사용 시작.

**다음 작업**: D26 순서대로 회원관리 도메인 이관. 그때 `memberNo` 채번을 `CodeSequence` + `FOR UPDATE`로, 연동 실패 제한을 `MemberLinkAttempt`로 옮긴다.
