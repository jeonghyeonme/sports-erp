# D78. 공유 패키지는 두 웹앱이 같이 쓰는 코드만 담는다 — `packages/types` → `packages/web-shared` (2026-11-12)

> 결정 기록 [인덱스](README.md) · 경위는 [log/223](../log/223.md) · [D13](D13.md)의 "`packages/types`로 클라이언트-서버 타입 공유" 계획을 대체한다

**컨텍스트**: D13은 `packages/types`로 api·admin-web·회원 앱이 DTO 타입을 공유한다고 계획했지만, 실제로는 어느 앱도 그 패키지를 import하지 않았다(36줄, 처음 만든 뒤 그대로). 두 웹앱은 "Vite 워크스페이스 심볼릭 링크 해석 이슈"를 이유로 타입을 각자 두었고, 그 사이 두 앱에 **똑같은 파일**이 쌓였다 — 비밀번호 규칙(`password-rule`), 느린 요청 알림(`slow-requests`·`SlowRequestNotice`, 파일 머리에 "고치면 둘 다 고친다"), 본문 2차 필터(`rich-content`), 값 타입 5개. 리팩토링 요청(log/222~)에서 이 중복을 줄이기로 했다.

**검토한 대안**
- (a) **api까지 포함해 응답 타입을 한 곳에서 공유**(D13 원안): api는 Nest 빌드(`declaration`, rootDir)와 Lambda 번들로 나가서 워크스페이스 TS 원본을 끌어오려면 빌드 설정을 바꿔야 한다. 그리고 응답 타입은 이미 앱마다 모양이 다르다(admin 556줄·member 159줄 — 화면이 쓰는 필드만). 바꾸는 범위에 비해 줄어드는 것이 적다.
- (b) **패키지를 지우고 지금처럼 각자 둔다**: 중복 그대로. "둘 다 고친다" 주석에 기대는 상태가 남는다.
- (c) **두 웹앱만 공유하는 원본 패키지**(채택): 빌드 단계 없이 TS 원본을 두고, 두 앱의 Vite·tsc가 자기 소스처럼 컴파일한다. 이전에 걱정한 심볼릭 링크 문제는 지금 구성(npm workspaces, 의존성 루트 호이스팅)에서 재현되지 않았다 — 두 앱 lint·빌드, 화면 자동 테스트 24건 통과.

**결정**
1. `packages/types`(`@sports-erp/types`) → `packages/web-shared`(`@sports-erp/web-shared`). 이름이 내용(타입만이 아님)과 쓰는 쪽(웹앱만)을 말하게 한다.
2. 담는 것: **두 웹앱에 같은 내용으로 있던 것만** — 값 타입(Role·PricingType·AgeGroup·PaymentStatus·ReservationStatus), `password-rule`, `slow-requests`, `SlowRequestNotice`, `rich-content`. 한 앱만 쓰거나 앱마다 다른 것은 옮기지 않는다.
3. 빌드 단계를 두지 않는다(`main`이 `src/index.ts`). react·dompurify는 peerDependencies — 앱이 가진 것을 쓴다(두 벌이 되면 React 훅이 깨진다).
4. api는 쓰지 않는다. 서버와 화면이 같아야 하는 값(비밀번호 규칙·허용 태그)은 지금처럼 주석으로 서로를 가리키고 api 테스트가 서버 쪽을 본다.

**결과**: 중복 파일 4쌍과 값 타입 5개가 한 벌이 됐다. 앱 `lib/types.ts`는 공유 값 타입을 다시 내보내(re-export) 기존 import는 그대로다.

**다시 볼 때**: api 응답 타입과 화면 타입이 어긋나 버그가 실제로 나면 (a)를 다시 본다(OpenAPI 생성 등).
