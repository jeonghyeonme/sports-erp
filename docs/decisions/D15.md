# D15. admin-web 디자인 토큰화 (Rounded Rectangle 기준)

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: 별도 UI 프레임워크(Tailwind, MUI 등) 도입 없이 순수 CSS 커스텀 프로퍼티(`--radius-sm/md/lg/xl/pill`, `--color-*`, `--shadow-*`)로 디자인 토큰을 정의하고, 대시보드를 포함한 admin-web 전체 도형(카드/버튼/입력/뱃지/사이드바/네비게이션)을 Rounded Rectangle 계열로 통일했다. 대시보드는 KPI 요약 스트립(SUPER_ADMIN이 2개 지점 이상을 볼 때만 노출) + 지점별 통계 카드(아이콘 칩) 구조로 재작성했다.

**쉽게 말하면**: 화면 곳곳에 흩어져 있던 "둥근 정도·색깔·그림자" 값을 한 군데(디자인 변수)에 모아두고, 모든 버튼과 카드가 그 값을 그대로 따라 쓰게 만들어서 마치 한 사람이 한 번에 그린 것처럼 통일된 느낌을 냈습니다.

**근거**: 사용자가 "모던하고 깔끔한 디자인, 도형은 Rounded Rectangle 기준"이라고 방향을 명시했다(2026-09-05). 이미 순수 CSS(`styles.css` 단일 파일) 구조로 시작된 작은 프로젝트에 Tailwind 같은 빌드 의존성을 새로 얹는 것은 이 시점 규모에 비해 과한 비용이고, CSS 변수만으로도 전역 일관성이라는 목표를 충분히 달성할 수 있다고 판단했다.

**타당성**: 높음. 기존 `.card`, `.card-grid`, `table`, `.badge` 등 클래스를 그대로 재사용하면서 토큰(값)만 바꿨기 때문에, 회원/직원/프로그램/게시판/시설 페이지는 코드 수정 없이 새 톤을 자동으로 물려받았다(브라우저로 각 페이지 확인 완료).

**장점**
- 새 디자인을 적용하기 위해 손댄 페이지는 대시보드뿐이지만, 변수를 참조하는 다른 모든 페이지가 함께 갱신됨(변경 지점 최소화)
- 라이브러리 학습·의존성 비용 없이 "일관된 디자인 시스템이 있다"는 인상을 심사에서 어필 가능

**단점·리스크**
- 정식 디자인 시스템(컴포넌트 라이브러리)이 아니라 CSS 클래스 집합이므로, 페이지 수가 크게 늘어나면 클래스명 중복·불일치가 생길 위험이 있음
- 다크 모드는 고려하지 않음(라이트 전용 토큰) — 이 프로젝트 스코프상 우선순위는 낮다고 판단

**대안 및 미채택 사유**: Tailwind CSS 도입도 검토했으나, 이미 순수 CSS로 시작된 작은 코드베이스에 새 빌드 파이프라인을 추가하는 비용이 이 시점의 이득(유틸리티 클래스 생산성)보다 크다고 보아 채택하지 않음.
