# D49. Lambda의 DB 접속을 Supavisor Session pooler(5432)로 바꾼다 — `pgbouncer=true`의 작업당 왕복 3번을 없앤다 (2026-10-11)

> 결정 기록 [인덱스](README.md) · 경위·측정은 [log/105](../log/105.md) · [D37](D37.md) 결정 1의 `DATABASE_URL` 행(Transaction pooler 6543 + `pgbouncer=true`)을 대체한다. 동시 실행 상한 10·`connection_limit=1`·`pool_timeout=5`는 그대로다 · [D48](D48.md)의 A안을 승인(사용자, 2026-10-11)한 것이다

**컨텍스트(Driver)**:
- D48 측정: `pgbouncer=true`에서 Prisma 5.22는 작업마다 BEGIN·DEALLOCATE ALL·COMMIT 왕복을 더한다. 처리 시간(W 약 110ms)의 가장 큰 몫이다.
- Supabase 문서: Supavisor 트랜잭션 모드는 prepared statement를 지원하지 않는다. 그래서 6543에서 플래그만 빼는 안(A2)은 안 된다(log/056의 42P05 장애와 같은 원인). 세션 모드(5432)는 클라이언트 하나가 실제 연결 하나를 세션 내내 쓰고 prepared statement를 지원한다.
- 세션 모드의 동시 클라이언트 수는 대시보드 Pool Size로 제한된다(역할 + DB 조합 기준). 이 풀은 두 모드가 함께 쓴다.

## 결정

1. Lambda `DATABASE_URL` = **Session pooler(`<ref>.pooler.supabase.com:5432`) + `?connection_limit=1&pool_timeout=5`**, `pgbouncer=true` 없음.
2. `set-lambda-env.sh`가 이 형식 또는 이전 형식(6543 + `pgbouncer=true`, 되돌리기용)만 받는다. 6543에서 플래그 누락, 5432에서 `connection_limit`이 1이 아닌 값, 직접 연결은 중단한다.
3. D48 B2(목록 count + findMany 일괄 트랜잭션)는 `Promise.all`로 되돌린다. 플래그가 없으면 일괄 트랜잭션이 BEGIN·COMMIT 2왕복을 더하기 때문이다. B1(인증 조회 합치기)은 유지한다.

## 대안 → 트레이드오프

| 대안 | 얻는 것 | 비용·위험 | 판단 |
|---|---|---|---|
| **A1 Session pooler(선택)** | 순차 왕복 S2 평균 16.8 → 5.9(로컬 실측). W 약 50~60ms·처리 한계 약 100 rps 안팎(추정) | Lambda 실행 환경 수(최대 10)만큼 실제 연결을 상시 점유한다. Pool Size(약 15, 대시보드 확인 필요) 여유가 약 5로 준다 | 선택 |
| A2 6543에서 `pgbouncer=true`만 제거 | A1과 같은 왕복 | Supavisor 트랜잭션 모드는 prepared statement 미지원(문서) → 42P05 | 기각 |
| A3 Prisma driver adapter(`pg`) | 트랜잭션 모드를 유지하며 왕복 감소(예상) | Prisma 5 미리보기 기능, `schema.prisma` 변경, 미측정 | 보류 — 상한 10을 올려야 할 때 다시 본다 |
| 유지(D48 B1+B2까지만) | 변경 없음 | 처리 한계 약 60 rps(추정) | 기각(사용자 결정) |

## 결과

- 좋아지는 것: 요청당 순차 왕복이 약 1/3이 된다. prepared statement를 재사용해 해석 비용도 준다.
- 감수하는 것:
  - **상한 10을 올리기 어려워진다.** 세션 모드에서는 실행 환경 하나 = 실제 연결 하나라, 상한을 올리면 Pool Size를 먼저 올려야 한다(D42 대안 A와 묶인다).
  - 쉬고 있는(얼어 있는) 실행 환경도 연결을 쥐고 있다. 풀러가 끊으면 깨어난 뒤 첫 쿼리가 실패할 수 있다(D37 R2와 같은 위험, Prisma 재연결로 처리).
  - 운영 효과는 k6 재측정 전까지 추정이다.

## 재고 트리거

- 운영 k6 S2에서 W가 약 70ms보다 크게 나올 때 → 역산한 풀러 왕복 가정을 다시 본다.
- "Max client connections reached"·P2024(연결 대기 초과)가 CloudWatch에 나타날 때 → Pool Size 확인·상향 또는 A3.
- 동시 실행 상한을 10보다 올려야 할 때 → A3 또는 Pool Size 상향을 먼저.
