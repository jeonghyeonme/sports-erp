# D61. 처리 대기함 — 대시보드 첫 카드에 역할별 "지금 처리할 일" 건수 (2026-10-21)

> 결정 기록 [인덱스](README.md) · 경위는 [log/149](../log/149.md)

**컨텍스트(Driver)**: 사용자가 "ERP가 게시판 형태로만 있는 게 일반적인가"를 물었다(2026-10-20). 화면이 모두 메뉴로 찾아 들어가는 목록·상세라, 승인할 휴가·처리할 업무지원 요청을 메뉴마다 들어가서 찾아야 했다. 실무 ERP는 첫 화면에 결재함·할 일 목록을 둔다. RFP 조항은 아니고 완성도 작업이다.

**상위 목표(D53)**: 노하우 습득 — 실무 ERP가 왜 대기함을 첫 화면에 두는지(현장 관리자는 메뉴를 돌아다닐 시간이 없다) 만들어 보며 익힌다. **핵심 변수**: 요청 수(대시보드는 가장 자주 열린다, D37·D50), 지점 격리(D46), 세부 권한(D60). **답안지**: 건수만 한 번에 모아 보여 주고 누르면 처리 화면으로 보낸다.

## 결정 (사용자 요청 2026-10-21 "처리 대기함 진행해줘" — 항목은 추천안)

1. **API 하나** `GET /inbox`(본사·지점 관리자·직원) — 항목별 `{ key, label, count, link }`. 범위는 요청자 본인·본인 지점으로 고정(파라미터 없음). 건수만 센다(목록은 각 화면). count 쿼리 2~4개를 병렬로 — 추가 왕복 1회.
2. **항목**: 본사 — 처리할 업무지원 요청(요청·처리중), 계약 갱신 임박·만료 지점, 재배치 대기 직원(ADR-STF-08), 보존기한 30일 이내 문서. 지점 관리자 — 승인 대기 휴가, 승인 대기 인사 변경 신청, 오늘 체크인 대기 예약, 혼잡도 30분 넘게 미갱신 운영 시설(RFP 30분 반영). 직원 — 오늘 출근 체크 전(근무일·승인 휴가 아님·기록 없음), 처리 대기 중인 내 휴가 신청.
3. **세부 권한(D60)**: 지점 관리자 항목은 그 기능의 조회 권한이 꺼지면 뺀다.
4. **화면**: 대시보드 맨 위 "처리 대기" 카드 — 0건이 아닌 항목만 칩으로, 누르면 그 화면. 0건이면 "지금 처리할 일이 없습니다". 실패하면 카드를 숨기고 대시보드는 그대로.

## 대안 → 트레이드오프

| 대안 | 얻는 것 | 비용·위험 | 판단 |
|---|---|---|---|
| 화면이 기존 목록 API 여러 개로 센다 | api 변경 없음 | 대시보드 왕복 4~5회, 목록 전체를 받아 센다 | 기각 |
| **건수 전용 API 1개(선택)** | 왕복 1회, 범위·권한을 서버가 한 곳에서 | 항목을 늘릴 때 api도 고친다 | 선택 |
| 알림(벨)·푸시까지 | 실시간에 가깝다 | 구독·저장 구조가 새로 필요 | 보류 — 대기함 건수를 배지로 쓰는 정도면 충분 |
