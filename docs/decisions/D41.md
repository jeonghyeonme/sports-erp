# D41. 회원 모바일 웹 — `apps/member-web` 별도 앱을 같은 Worker의 `/m/`에 붙인다 (2026-10-07)

> 결정 기록 [인덱스](README.md) · 경위는 [log/077](../log/077.md) · [D40](D40.md) 결정 2(모바일 웹, 같은 스택·같은 Worker)를 구체화한다

**컨텍스트(Driver)**:
- D40은 회원 기능을 admin-web과 같은 React+Vite로 만들고 같은 Cloudflare Worker로 배포하기로 했다. 앱을 어떻게 나누고 Worker에 어떻게 붙일지는 정하지 않았다.
- Worker(`cloudflare-worker/wrangler.jsonc`)는 `apps/admin-web/dist`만 정적 자산으로 서빙한다. 없는 경로는 SPA 폴백으로 **루트** `index.html`(관리자 웹)을 준다. 그래서 회원 화면을 새로고침하면 관리자 화면이 뜰 수 있다.
- Workers 무료 한도는 하루 10만 건이고, [design-constants](../architecture/design-constants.md) ⑬은 하루 약 9.3만 건(93%)이다. 정적 자산 요청은 세지 않는다. 회원 웹에 들어올 때마다 Worker를 1회씩 거치면(83곳 × 100명) 하루 약 0.8만 건이 늘어 한도를 넘는다.
- 회원은 휴대폰 브라우저를 쓴다. 새로고침하거나 탭을 닫는 일이 잦다. admin-web처럼 토큰을 메모리에만 두면 그때마다 다시 로그인해야 한다.

## 결정

1. **앱 형태: B안 — `apps/member-web` 별도 Vite 앱**(`base: '/m/'`). 빌드 결과는 `apps/admin-web/dist/m/`에 쓴다. admin-web 빌드가 `dist`를 비우므로 admin-web을 먼저 빌드한다. 루트 `npm run build:web`이 이 순서로 빌드한다.
2. **Worker 라우팅**: `run_worker_first`를 `["/api/*", "/m/*", "!/m/", "!/m/assets/*"]`로 바꾼다. `/m/*` 화면 경로는 Worker가 받아 `/m/index.html`을 준다. 확장자가 있는 경로는 자산을 그대로 준다. 진입 경로 `/m/`와 빌드 산출물 `/m/assets/*`는 자산 계층이 바로 처리한다. 그래서 Worker 호출은 깊은 경로를 새로고침할 때만 생긴다. `wrangler dev`로 확인했다(log/077).
   - 회원 웹에는 `public/` 파일을 두지 않는다. `/m/` 바로 아래 파일은 요청마다 Worker를 거친다.
3. **토큰 보관**: access token은 메모리에만 둔다. refresh token은 `localStorage`에 둔다. 앱을 시작하면 `POST /auth/refresh` → `GET /auth/me`로 세션을 되살린다. 401이 나면 refresh를 한 번 하고 원래 요청을 다시 보낸다. refresh는 1회용(rotate, 권한관리 A-6)이라, 동시에 여러 요청이 401을 받아도 refresh 요청은 하나만 보낸다.
4. **화면 기준 폭은 360px**이다. 디자인시스템 토큰(색·radius·무그림자)을 그대로 쓴다. 모바일이라 본문은 14px, 누르는 요소는 높이 44px 이상으로 한다.
5. **MEMBER가 아닌 계정은 회원 웹 로그인을 화면에서 거부한다.** 관리자는 admin-web을 쓴다. 권한 판정은 어차피 API가 한다.

**대안**:
- A안: admin-web 안에 `/m/*` 레이아웃을 둔다. 빌드·배포를 바꾸지 않아도 된다. 하지만 관리자 번들에 회원 화면이 섞이고 앱 경계가 흐려진다.
- C안: 회원 웹 전용 Worker를 하나 더 둔다. 하지만 오리진이 둘이 되어 D25가 없앤 CORS가 돌아오고, 무료 한도를 두 Worker가 나눠 쓴다.
- refresh token을 메모리에만 둔다. 가장 보수적이지만 모바일에서는 새로고침할 때마다 로그아웃된다.
- refresh token을 httpOnly 쿠키에 둔다([system-overview](../architecture/system-overview.md) §3.2의 원안). XSS에 강하다. 하지만 인증 방식 변경(api 컨트롤러·쿠키·CSRF·테스트, admin-web 영향)이라 별도 승인 작업이다.

**감수하는 것**:
- `localStorage`의 refresh token은 XSS가 있으면 탈취될 수 있다. rotate라 탈취한 쪽과 정상 사용자 중 먼저 쓴 쪽만 살아남는다. 수명은 14일이다.
- system-overview §3.2는 httpOnly 쿠키라고 적었지만 실제 API는 refresh token을 본문으로 주고받는다. 이 차이는 이 결정 전부터 있었다.
- 배포 순서가 생긴다: admin-web 빌드 → member-web 빌드 → `wrangler deploy`. member-web을 빌드한 뒤 admin-web만 다시 빌드하면 `dist/m`이 지워진다.
- 깊은 경로를 새로고침하면 Worker 호출이 1회 생긴다. 실제 방문당 호출 수는 B1-4에서 세어 ⑩·⑬에 반영한다.

**재고 트리거**: 사용자 HTML 렌더링처럼 XSS 위험이 있는 기능이 회원 웹에 들어오면 httpOnly 쿠키로 바꾼다. Workers 유료로 전환하면 `!/m/` 예외는 필요 없다.
