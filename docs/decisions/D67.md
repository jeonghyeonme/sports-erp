# D67. 중간 제출물 구성과 이후 방향 — 실운영은 하지 않고, 다음은 사용감·계약서 OCR·회원 앱 형태 (2026-10-22)

> 결정 기록 [인덱스](README.md) · 경위는 [log/175](../log/175.md)

**컨텍스트**: 중간고사 대체 제출 요구가 "프로젝트 중간보고서 · 각 주차별 발표자료 및 증빙자료를 압축해 업로드"로 두루뭉술하다. 독자는 지도교수이고 관심은 전체 맥락 파악이다 — ERP라 기능이 많고 맞물려, 설명을 듣는 쪽이 피곤하다(사용자). 동시에 RFP를 충실히 이행했다는 증빙이 필요하다.

**결정**(사용자, 2026-10-22):
1. **제출물** — 한 폴더에 모아 사용자가 압축한다(학번·이름·마감은 사용자 몫).
   - **중간보고서**: 슬라이드 아티팩트(파워포인트 형식, 혼자 읽는 덱) → PDF. 구성은 [4-7](../presentation/4-7_중간발표_슬라이드구성.md) — 맥락 → 설계 → RFP 이행 → 확인 → 진행 경과 → 마무리, 분량은 맞추지 않고 어려운 곳은 장을 늘린다. 시연 접속(URL + 역할별 가이드)은 마지막 장.
   - **RFP 이행 증빙**: HTML 아티팩트 → PDF. 조항마다 "구현한 것"을 **쉬운 말 한 줄로 교체**(기술 근거는 남기지 않음) + 화면 캡처 + 결정 기록. GitHub CI 링크는 넣지 않는다.
   - **주차별 발표자료**: 발표에 쓴 아티팩트를 사용자가 직접 내보낸다. 주차별 이행 증빙은 따로 만들지 않는다.
   - **산출물**: 전부 다시 생성해 최신화한다.
2. **실운영은 하지 않는다.** RFP 부분 3조항(PG 실제 호출·업무위탁 계약서·발주기관 검수·도입)은 "실운영을 하지 않아 범위 밖"으로 정리하고, 실운영 전 조치·순간 몰림 거절 원인 확인은 계획에서 뺀다. 혼잡도 키오스크 입장(혼잡도관리 ADR-FAC-05 대안 C)은 계획에도 넣지 않는다.
3. **다음 계획은 세 갈래**(계획 수준으로만 보고): ① 사용감 확보 — 등록·조회·처리 위주의 기능을 직접 쓰는 사람이 편하도록(목록 쪽 나누기·검색·정렬 일관화, 수치 시각화, 작업 단계 줄이기) ② 계약서 OCR·AI 분석 적용 검토(차별화전략 §1-1, D22 — 검토 후 반영 구조) ③ 회원 앱 형태 재검토 — PWA(D45)의 접근성 한계로 하이브리드·네이티브 앱을 비교(D40 재검토).

**결과**: 좋아진 것 — 제출물마다 역할이 하나다(보고서 = 맥락, 증빙 = 조항별 근거, 주차별 자료 = 경과, 산출물 = RFP 산출물). 감수하는 것 — 요구 목록 해석이 교수의 의도와 다를 수 있다(보고서 안내 장에 해석을 밝힌다). 실운영을 하지 않으므로 S1·S2·S8 수용(security-plan)과 같은 방향.

**재고 트리거**: 지도교수가 제출 형식을 구체적으로 지정할 때, 실운영 계획이 생길 때.
