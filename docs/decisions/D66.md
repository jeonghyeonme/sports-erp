# D66. 관리자 웹은 직원 계정만 — 회원 기능은 회원 웹 한 곳으로 (2026-10-22)

> 결정 기록 [인덱스](README.md) · 경위는 [log/172](../log/172.md) · D41 결정 5(회원 웹은 회원만)의 반대 방향

**컨텍스트**: 관리자 웹은 회원 웹(D41)이 생기기 전 회원 화면 대용으로 회원 로그인을 받았다 — 로그인 화면에 회원 데모 버튼, 회원용 메뉴 5개(대시보드·프로그램·예약·게시판·혼잡도), 예약 화면의 "예약 가능한 프로그램·내 예약" 모드가 남아 있었다. 같은 기능이 회원 웹에 다 있어, 관리자 웹에 회원으로 들어가는 길은 시연 때 "왜 관리 화면에 회원이 들어오나"라는 어색함만 남겼다(사용자 지적, 2026-10-22).

**검토한 대안**
1. 그대로 둔다 — 비용 0, 어색함과 중복 화면(관리자 웹 회원 예약)이 남는다.
2. **화면에서 막는다(채택)** — 관리자 웹 로그인이 회원 계정을 받으면 방금 받은 갱신 토큰을 폐기하고 회원 앱으로 안내한다. 회원 데모 버튼·회원 메뉴·도움말·예약 화면 회원 모드를 지운다.
3. 서버에서 막는다 — 로그인 API는 어느 앱에서 왔는지 모른다. 앱 구분 값(헤더·별도 엔드포인트)을 새로 만들어야 하고, 회원이 쓸 수 있는 API는 어차피 회원 웹이 같은 것을 부르므로 막아도 얻는 보안 이득이 없다(권한 판정은 이미 API의 역할·지점 검사).

**결정**: 2. 관리자 웹은 SUPER_ADMIN·BRANCH_ADMIN·STAFF만 로그인한다. 회원 기능(예약·결제·내 예약·공지·혼잡도)은 회원 웹(`/m/`) 한 곳에서. 로그인 화면 아래 "회원이신가요? 회원 앱에서 로그인" 링크(`/m/`).

**결과**: 좋아진 것 — 앱마다 사용자가 하나(관리자 웹 = 직원, 회원 웹 = 회원)라 시연·매뉴얼 설명이 단순해지고, 관리자 웹의 회원용 코드(예약 화면 회원 모드·회원용 결제 버튼)를 지웠다. 감수하는 것 — 판정이 화면 몫이라 API를 직접 부르면 회원 토큰으로 회원 API를 쓸 수 있다(원래도 같다, 회원 웹이 쓰는 API). 로컬 개발에서는 `/m/` 링크가 관리자 웹 dev 서버로 가므로 회원 웹은 5174에서 따로 연다.

**재고 트리거**: 직원이면서 회원인 사람이 한 계정으로 두 앱을 써야 할 때(지금은 계정 하나에 역할 하나).
