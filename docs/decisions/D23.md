# D23. 배포 인프라 — Render(admin-web + api) + Supabase(스키마 배포 완료, 앱 연결은 미착수)

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정(2026-09-27 확정, 아래 "변경 이력" 참고)**: 두 서비스를 GitHub 연동(push 시 자동배포)으로 조합한다. ① `admin-web`(정적 SPA 빌드 결과물)과 ② `api`(NestJS 서버 프로세스) **둘 다 Render**에 올린다(`sports-erp-web` Static Site, `sports-erp-api` Web Service, 리전 Singapore, 둘 다 무료 티어). ③ PostgreSQL은 **Supabase**에 신규 프로젝트(`sports-erp`)를 만들어 Prisma 스키마(27개 테이블)를 배포해뒀지만, `apps/api`는 여전히 `MockDataService`로 동작 중이라 **아직 이 DB를 실제로 쓰지는 않는다**(`docs/log/` §29).

**쉽게 말하면**: 화면(admin-web)과 서버(api) 둘 다 Render 한 곳에 올리고, DB는 Supabase에 그릇만 미리 만들어뒀습니다(아직 요리는 안 담았습니다). 셋 다 GitHub 저장소만 연결해두면 `git push` 할 때마다 알아서 다시 배포되고, 지금은 아무것도 결제하지 않아도 됩니다.

**변경 이력 — 원래 계획(Cloudflare Pages + Render)에서 왜 바뀌었나**: 이 결정은 원래 "admin-web은 Cloudflare Pages, api는 Render"로 계획됐었다(계획 당시 근거는 아래 "근거"에 그대로 남겨둠). 그런데 2026-09-27 실제 배포 작업 중 **Claude에 연결된 "Cloudflare Developer Platform" MCP 커넥터가 Workers/KV/D1/R2/Hyperdrive용이고 Pages를 만들거나 관리하는 툴 자체가 없다**는 걸 실행 단계에서 발견했다(`migrate_pages_to_workers_guide`만 있음 — 오히려 Pages에서 Workers로 "떠나는" 법 안내뿐이었고, 이는 Cloudflare 자체가 Pages를 단종 방향으로 가져가고 있다는 신호로 보인다). Render의 `create_static_site` 툴은 실제로 서비스를 만들 수 있어서, 계획을 수정해 admin-web도 Render로 통합했다 — **"어느 게 이론적으로 더 나은가"가 아니라 "지금 가진 도구로 실제로 무엇을 만들 수 있는가"를 기준으로 계획을 현장에서 조정한 사례**로 남겨둔다.

**두 번째 변경(2026-09-27, 같은 날)**: 그런데 D24로 api 앞에 Cloudflare Worker(엣지 게이트웨이)가 새로 생기면서 admin-web(Render)·api 게이트웨이(Cloudflare)가 서로 다른 오리진이 됐고, 이게 로그인 실패·새로고침 404 버그로 이어졌다. **[D25](#d25-admin-web을-cloudflare-worker-정적-자산으로-통합render-static-site-폐기)에서 admin-web을 그 Worker의 정적 자산으로 다시 이관**해 이 문단을 사실상 대체한다 — 이 절의 "Render(admin-web+api)"는 역사적 기록으로 남겨두고, 현재 구성은 D25를 볼 것.

**근거(원 계획 당시)**: 현재 `apps/api`는 [app.module.ts](../../apps/api/src/app.module.ts) 주석대로 `PrismaModule` 대신 `MockDataModule`로 동작 중이라 부팅에 실제 DB 연결이 필요 없다 — 그래서 지금은 Render에 `DATABASE_URL` 없이도 그대로 띄울 수 있고, Supabase는 "나중에 실 DB로 이전"할 때를 위해 미리 정해만 두는 것이다. `main.ts`가 이미 `enableCors({ credentials: true })`로 열려 있고 인증은 쿠키가 아니라 `Authorization` 헤더 기반(`apps/admin-web/src/lib/api.ts`에 `withCredentials` 없음)이라, 웹과 API가 서로 다른 서브도메인이어도 추가 설정 없이 붙는다.

**타당성**: 중간 — 무료 티어 특유의 제약을 감수하는 선택이다. Render 무료 웹 서비스는 15분 미사용 시 슬립되고 재요청 시 약 1분 콜드스타트가 발생하며 월 750시간 한도가 있다([Render 문서](https://render.com/docs/free)). Supabase 무료 프로젝트는 7일간 활동이 없으면 자동 일시정지되어 수동으로 재개해야 한다. 포트폴리오 시연처럼 트래픽이 간헐적인 용도에는 이 제약이 큰 문제가 아니지만, **2026-09-27 k6 실측(`docs/log/` §31, [D24](#d24-인증-경로-확장성-대응--부하테스트-실측-기반-단계적-로드맵) 참고)에서 이 제약이 "느리다" 수준을 넘어 "40명 동시 로그인에 응답 15초"까지 악화되는 걸 직접 확인했다** — 타당성 평가를 "중간"으로 유지하되, 실측 전까지는 추측이었던 리스크가 지금은 계량화된 사실이 됐다.

**장점**
- 두 서비스 모두 카드 등록 없이 무료로 시작 가능해 "유지비용 없음" 조건을 만족한다
- 둘 다 GitHub 저장소 연결만으로 push 시 자동 재배포된다
- npm workspaces 구조를 그대로 활용해 두 서비스 모두 리포 루트에서 `npm install && npm run build --workspace=apps/<앱>` 패턴으로 빌드하므로 워크스페이스 호이스팅 문제 없이 별도 빌드 스크립트가 필요 없다
- 하나의 플랫폼(Render)으로 통합돼 대시보드·로그·환경변수 관리가 한 곳에서 끝난다(원 계획의 "두 플랫폼 오가기"보다 운영 부담이 낮음)

**단점·리스크**
- Render 무료 웹 서비스의 슬립/콜드스타트와 Supabase 무료 프로젝트의 7일 일시정지는 "상시 대기" 서비스가 아니라는 뜻이다 — 실제 스포이즘 운영이라면 D18(자체 인프라 운영)이 전제하는 안정성 요구를 만족 못 한다는 점을 인지해야 한다(포트폴리오 시연용으로만 타당)
- **Render 무료 웹 서비스는 공유·스로틀링되는 CPU를 쓴다 — 이게 단순 "느림"이 아니라 D24가 다루는 자기강화형 지연 폭증의 근본 원인이다.**
- `apps/admin-web`이 `BrowserRouter`(히스토리 모드)를 쓰므로 `apps/admin-web/public/_redirects`(`/* /index.html 200`)가 없으면 새로고침 시 404가 난다 — Cloudflare Pages/Netlify 문법이지만 Render Static Site도 같은 `_redirects` 문법을 지원한다고 알려져 있어 파일은 그대로 재사용했다(실제 새로고침 동작은 아직 브라우저로 재확인 안 함 — 다음 확인 대상)
- 첫 배포에서 `NODE_ENV=production`이 `npm install`의 devDependencies 설치를 건너뛰게 만들어 `nest: not found`로 빌드가 실패했었다 — `NPM_CONFIG_PRODUCTION=false`로 수정(`docs/log/` §30)
- Render 대시보드에서의 빌드 커맨드·환경변수 설정은 리포 안의 파일([render.yaml](../../render.yaml))만으로 전부 재현되지 않는다 — Render는 Blueprint(`render.yaml`) 동기화 기능이 있지만, 이번 배포는 MCP 툴로 직접 만들어서 `render.yaml`은 "재현용 기록"으로만 맞춰뒀고 실제 서비스는 Blueprint sync로 연결돼 있지 않다 — 계정 접근 권한이 있는 사람만 대시보드에서 재현/변경 가능하다는 한계가 있다

**대안 및 미채택 사유**: API를 Vercel/Cloudflare Workers 같은 서버리스 플랫폼에 올리는 안도 검토했으나, NestJS는 데코레이터·`reflect-metadata` 기반의 상시 구동 서버 모델이라 서버리스 어댑터(`serverless-http` 등)를 추가로 감싸야 해서 "가장 가볍게"라는 기준에 안 맞았다(Vercel MCP 커넥터도 `list_projects`/`get_deployment` 같은 조회·디버깅 툴뿐이라 애초에 생성 자체가 안 됐다). Railway는 이전엔 무료였지만 지금은 가입 시 1회성 크레딧만 주고 이후 과금되어 "유지비용 없음" 조건에서 탈락시켰다. Fly.io는 Dockerfile과 `fly.toml`/flyctl CLI를 직접 다뤄야 해서 Render 대비 설정 부담이 컸다. DB는 Neon도 후보였으나 사용자가 Supabase를 지정해 그대로 따랐다. Cloudflare Pages는 위 "변경 이력"대로 도구 한계로 이번엔 미채택 — 커넥터가 아니라 CLI(`wrangler`)나 대시보드 수작업으로 접근하면 여전히 유효한 대안이라, 나중에 재검토 대상으로 남겨둔다.
