# D50. 설계 계산의 요청당 처리 시간 W를 약 40ms(운영 실측)로 바꾼다 — Session pooler 전환 뒤 k6·CloudWatch 재측정 (2026-10-12)

> 결정 기록 [인덱스](README.md) · 측정 경위는 [log/109](../log/109.md) · [D42](D42.md) 결정 4("설계 계산에는 W = 110ms, 처리 한계 약 50 rps")를 대체한다. D42의 설정(상한 10·1,024MB)은 그대로다 · [D49](D49.md)의 운영 효과를 확인한 기록이다

**컨텍스트(Driver)**:
- D49(Session pooler 5432, `pgbouncer=true` 제거)가 운영 Lambda에 적용돼 있음을 확인했다(log/108).
- 2026-10-12 06:02~06:11 UTC, 사용자 PC → Function URL 직접으로 `loadtest/k6-lambda.js` S1~S3를 돌리고 CloudWatch Logs Insights(REPORT 줄)로 서버 처리 시간을 1분 단위로 봤다.

## 결정

1. **설계 계산의 W = 약 40ms**(운영 CloudWatch p50, S2·S3 구간 36.8~41.0ms, p95 약 51ms). design-constants ⑫를 이 값으로 고친다.
2. **처리 한계는 "과부하에서 실제 처리 약 80~90 rps(실측 하한)"로 적는다.** 이론값(상한 10 ÷ 40ms ≈ 250 rps)은 쓰지 않는다. 이번 S3에서 k6가 2,169건을 보내지 못해(가상 사용자 400 소진) 측정 PC가 먼저 막혔으므로, 실제 한계는 이보다 클 수 있지만 확인하지 않았다.
3. **로그인은 W가 아니라 약 140ms(p50)로 따로 본다.** 암호 해싱이 대부분이라 접속 방식과 무관하다.

## 결과

- 좋아지는 것: 몰림 시 필요한 동시 실행 칸이 약 1/2.7로 준다(⑫). 세션 모드의 연결 점유(D49 감수)는 실측에서 P2024·5xx 없이 동작했다.
- 감수하는 것:
  - **콜드 스타트가 약 0.36초 길어졌다**(D37 §4 기준 1.5초 안, 여유 감소). 새 실행 환경이 세션 연결을 여는 시간으로 추정 — 확인하지 않았다.
  - **순간 몰림의 거절이 늘었다.** S1 38건은 로그인 증가 중 새 실행 환경 9개가 각 약 1.4초씩 뜨며 자리를 잡은 것으로 설명된다(추정). S2 47건은 그 구간 콜드 스타트가 없어 **원인 미확인** — Throttles·ConcurrentExecutions 그래프로 시점을 봐야 한다.
