# D64. 개발 도구 취약점 — 같은 메이저 고정·vite 6으로 뿌리 10 → 2, 고친 판이 없는 2건은 수용 (2026-10-22)

> 결정 기록 [인덱스](README.md) · 경위는 [log/159](../log/159.md) · 운영 의존성은 [D63](D63.md)

**컨텍스트(Driver)**: D63 뒤 남은 `npm audit` 55건(운영 4 제외 51)을 사용자가 정리하라고 했다(2026-10-22). 줄 수는 많지만 뿌리 패키지는 10여 개다 — 나머지는 jest 29·`@nestjs/cli` 10의 의존성 사슬이 같은 뿌리를 물려받아 줄마다 표시된 것. 개발 도구라 Lambda 묶음·배포 화면에는 들어가지 않는다. 다만 사용자는 Windows에서 vite 개발 서버를 쓴다(vite 권고 다수가 Windows 개발 서버 건).

**상위 목표(D53)**: 노하우 습득 — audit 줄 수가 아니라 "뿌리 패키지 + 도달 경로"로 읽는 법, 고친 판이 아예 없는 경고를 근거와 함께 수용하는 법. **핵심 변수**: 고친 판의 존재·메이저 여부, 공격자 입력이 닿는지(개발 도구는 우리 설정·코드만 읽는다). **답안지**: D63과 같은 순서 — 같은 메이저 고정 → 메이저가 필요하면 비용·효과를 실측 → 남는 것은 수용과 재고 트리거.

## 결정

1. **루트 `overrides`(같은 메이저)**: `picomatch@4` → 4.0.7(ReDoS·메서드 주입), `glob@10` → 10.5.0(CLI 명령 주입), `ajv@8` → 8.20.0(ReDoS), webpack 5.112.0(buildHttp 우회), tmp 0.2.7(경로 탈출 — `external-editor`가 쓰는 `fileSync`는 0.2에도 같다). 잠금 파일은 `@nestjs/cli`를 같은 범위로 다시 깔아 풀었다(`^10.4.9`).
2. **vite 5 → 6.4.5**(두 웹, `@vitejs/plugin-react` 4.7.0 — vite 6 지원): 개발 서버 경로 탈출·`server.fs` 우회·launch-editor(Windows) 9건과 esbuild 0.21(개발 서버 요청 읽기)이 풀린다. 설정 변경 없음, 빌드·개발 서버·화면 자동 테스트 확인.
3. **수용 2건 — 고친 판이 없다**: braces ≤3.0.3(최신 3.0.3, 깊게 중첩된 패턴 스택 고갈 — jest의 micromatch·nest cli의 chokidar가 우리 설정의 glob을 읽을 때만), sprintf-js ≤1.1.3(최신 1.1.3, 큰 정밀도 서식 — jest 커버리지 설정 YAML을 읽는 argparse 사슬). 둘 다 우리 저장소의 설정·코드만 입력으로 받아 공격자가 닿지 않는다. jest 30으로 올려 보았으나 같은 사슬(istanbul → js-yaml → argparse → sprintf-js)이 남아 되돌렸다(실측).

**결과(실측)**: 전체 55 → 46줄, 뿌리는 4개(운영 D63의 2 + 여기 수용 2), 심각 0. 운영 의존성 4건(중간)은 그대로.

**재고 트리거**: braces·sprintf-js에 고친 판이 나올 때(그때 `npm audit fix`), jest·nest cli를 다른 이유로 메이저 업그레이드할 때, vite 6 지원 종료.
