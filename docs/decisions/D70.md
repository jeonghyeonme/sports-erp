# D70. 동시성 빈틈 세 곳 — 종료 지점 판정은 쓰기 트랜잭션 안 지점 행 공유 락, 계약 정정·파일은 회차 번호 확인, 퇴사·발령은 직원 행 락 (2026-11-01)

> 결정 기록 [인덱스](README.md) · 경위는 [log/194](../log/194.md)

**대체**: [D29](D29.md) 결정 2의 `BranchService.loadGate()`(종료 지점 집합을 트랜잭션 밖에서 읽어 넘기는 판정기)를 대체한다. D29가 "도메인이 Prisma로 옮겨지면 트랜잭션 안에서 직접 읽는 방식으로 바뀐다"고 미뤄 둔 일을 끝낸 것이다 — `loadGate()`와 `branch-gate.ts`는 삭제(사용자 확인).

**컨텍스트**: 사용자가 중간 발표 자료에서 결제·예약·취소의 동시성·멱등성 문제를 고쳤던 것을 보고, 기능별로 DB 락이 더 필요한 곳이 있는지 점검을 요청했다(2026-11-01). 모든 쓰기 경로를 훑은 결과 예약·결제·취소·근태·휴가·채번·갱신 토큰·PT 차감·D69 계약 쓰기는 이미 락·조건부 갱신·유일 제약으로 막혀 있었고, 빈틈이 세 곳 나왔다(멱등 키 없는 "두 번 누르면 두 번"은 락으로 풀리지 않아 이번 범위 밖).

**결정**(사용자 "1~3번 고쳐", 2026-11-01):
1. **종료 지점 차단 판정은 쓰기 트랜잭션 안에서 지점 행 공유 락(`lockBranchForShare`)으로 읽는다.** 회원 등록·앱 가입, 예약, 수강·PT 등록, 게시글, 시설 등록, 혼잡도 보정, 자산, 문서, 업무지원 요청 — 채용·발령(ADR-STF-07)과 같은 방식. 종료 확정(`FOR UPDATE`)이 진행 중이면 기다렸다가 커밋된 TERMINATED를 보고 409를 낸다. 공유 락끼리는 막지 않아 평소 쓰기 속도는 그대로다. 예전 방식은 진행 중인 종료를 ACTIVE로 읽고 종료 뒤에 커밋돼 종료 지점에 새 행이 남았다(실DB로 재현, 10개 경로 모두 201).
2. **계약 정정(`PATCH .../contract`)과 계약 파일 올리기(`POST .../contract/files`)는 요청에 회차 번호(`roundNo`, 필수)를 싣는다.** 지점 행 락 뒤에 읽은 진행 중 회차와 다르면 409 `CONTRACT_ROUND_CHANGED`. 화면을 1회차로 띄워 둔 사이 갱신으로 2회차가 생기면, 1회차를 고친다고 생각한 정정·교체가 2회차에 들어가던 것을 막는다(D69 계약 쓰기는 이미 직렬화돼 있었고, 문제는 "어느 회차에 적용되느냐"였다 — 낙관적 확인).
3. **퇴사와 파견 발령은 트랜잭션 처음에 직원 행을 잠근다(`lockStaff`).** 발령이 커밋 전 퇴사를 ACTIVE로 읽고 발령해 퇴사자에게 진행 중 파견이 남던 것(재현: 201), 같은 직원 동시 발령이 진행 중 파견 유일 제약에 걸려 500이 나던 것을 막는다. 잠금 순서(직원 → 지점 공유)는 종료 전이(지점 → 파견 행)와 교착하지 않는다 — 종료 전이는 직원 행을 바꾸지 않는다.

**하지 않은 것**: 요청 단위 멱등 키(PT 1회 사용 두 번 차감, 수강·PT·회차 중복 등록 등 — engineering-risks "멱등성·재시도"), 회원 상태·프로그램·시설 수정의 마지막 저장 우선(이력의 이전 값이 낡을 수 있음), 세부 권한 같은 칸 동시 변경의 500, 전역 P2002→409 변환. 모두 데이터 정합성은 깨지지 않아 영향이 작다고 판단.

**타당성·리스크**: 스키마 변경 없음 — 배포 DB 작업 없음. 2번은 API 요청 본문이 바뀐다(관리자 웹을 같이 고침, 다른 클라이언트 없음). 공유 락은 종료 확정이 진행 중일 때만 쓰기를 잠깐 세운다. 트랜잭션 안에서는 그 트랜잭션 연결만 쓴다(운영 풀 `connection_limit=1`, D37 — 다른 연결을 기다리면 멈춘다).

**검증**: `test/concurrency-gaps.spec.ts`(행 락으로 순서를 결정적으로 만든 실DB 재현 13건 — 고치기 전 코드에서 12건 실패·대조군 1건 통과를 확인), `contract-renewal.spec`(회차 번호 409·400, 대조군 포함). api jest 55개 파일 600건·화면 테스트 16건 통과(로컬).

**다시 볼 때**: 요청 단위 멱등 키를 도입할 때, 계약 화면이 여러 회차를 동시에 고치게 될 때, 지점 행을 배타 락으로 잡는 경로가 늘 때(공유 락 대기 시간).
