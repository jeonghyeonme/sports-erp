# D37. API 호스팅을 Render 무료 티어에서 AWS Lambda(서울)로 옮긴다 — 요청량을 "용량"이 아니라 "입장 제어 + DB 커넥션 상한"으로 푼다

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: 2026-09-30 배포 사이트 점검에서 세 가지가 드러났다(docs/log/051).
- Render `sports-erp-api`는 **9/28의 D26 커밋(`d5e43da`)에 멈춰 있다.** 자동배포 설정은 켜져 있는데 PR #5~#10이 병합된 뒤에도 빌드가 한 번도 시작되지 않았다. D27~D36(실DB 전환 전체)은 배포되지 않았다.
- **API는 싱가포르, DB(Supabase)는 서울(ap-northeast-2)에 있다.** 로컬 실측으로 요청 하나가 쿼리 4~8개를 순차로 보낸다(아래 표). 리전 간 왕복을 70ms 안팎으로 잡으면(추정, 미측정) 요청마다 네트워크 대기만 300~550ms다. Render에는 서울 리전이 없어서 유료 플랜으로 올려도 이 거리는 줄지 않는다.
- D24의 k6 실측(로그인 p95 15.16초)은 공유 CPU 인스턴스 1대에서 요청들이 CPU를 나눠 쓰며 생긴 **"동시 진행 수 L이 늘면 처리시간 W가 늘고, W가 늘면 L이 더 는다"** 자기강화 루프였다(design-constants ⑨).

사용자는 Render 무료 티어의 콜드 스타트·동시 요청 취약성을 이유로 Lambda 이전을 결정했다. **가장 큰 질문은 "요청 수를 감당할 수 있는가"다.** D26 "다음 작업"과 docs/log/038이 남긴 네 가지(메모리=CPU, DB 커넥션 풀링, 동시 실행 한도, 콜드 스타트)도 이 결정에서 답한다.

**전제 — 코드는 이미 무상태다**:
- D36으로 프로세스 메모리 저장소가 없다. 코드 전체를 검색해도 타이머·`@Cron`·인메모리 캐시가 없다. 채번(`CodeSequence`)과 연동 실패 제한(`MemberLinkAttempt`)은 DB에 있다(D27).
- 풀러와 충돌할 기능을 쓰지 않는다. advisory lock은 트랜잭션 범위(`pg_advisory_xact_lock`)만 쓰고, 세션 범위 락·`SET`·`LISTEN`은 없다.
- **Lambda의 커넥션 설정(`connection_limit=1`)으로 전체 테스트를 돌렸다(2026-09-30).** 308건이 통과했고 풀 대기 타임아웃(P2024)은 0건이었다. 트랜잭션 안에서 커넥션을 하나 더 잡다가 스스로 막히는 경로가 없다는 뜻이다. 실패한 1건은 `integrity-helpers`의 대조군("락이 없으면 정원을 넘는다")이다. 커넥션이 1개라 트랜잭션이 직렬화돼 경합 자체가 재현되지 않았다. 코드 결함이 아니라 예상된 결과다.

## 1. 요청량 모델 — 얼마나 들어오고, 요청 하나가 얼마나 걸리나

**요청 하나의 비용(W)** — 2026-09-30 로컬 실측이다. PG16과 API가 같은 머신(4코어)에 있고, 복제 DB를 썼다. 쿼리 수는 `log_statement=all`로 셌다. p50/p95는 순차 30회(로그인은 15회) 기준이다.

| 요청 | 쿼리 수 | p50 | p95 |
|---|---|---|---|
| `POST /auth/login` (bcrypt cost 10) | 5 | 73ms | 84ms |
| `GET /auth/me` | 4 | 7ms | 8ms |
| `GET /branches` (본사, 98개) | 7 | 13ms | 16ms |
| `GET /members` (본사, 전체 — 페이지네이션 없음) | 6 | 16ms | 19ms |
| `GET /programs` (본사) | 6 | 16ms | 19ms |
| `GET /staff` (본사, 195명) | 5 | 14ms | 18ms |
| `GET /posts` (회원) | 8 | 9ms | 12ms |
| 그 외 지점 범위 조회 5종 | 4~7 | 4~9ms | 6~10ms |

`bcrypt.compare`만 따로 재면 1회 63ms다(같은 머신).

**Lambda에서의 W 추정**:

`W(Lambda) ≈ W(로컬) ÷ CPU 비율 + 쿼리 수 × 풀러 왕복시간`

- CPU는 메모리에 비례한다. 1,769MB가 vCPU 1개이고, 1,024MB는 약 0.58개다. 로컬 머신의 코어 1개와 같다고 가정한다(가정).
- 같은 리전의 풀러 왕복은 1~3ms로 잡는다(추정, 배포 후 실측 대상).
- 결과: 일반 조회 **W ≈ 25~50ms**, 로그인 **W ≈ 130ms(1,024MB) / 80ms(1,769MB)**. 기준값은 보수적으로 **50ms**(일반)·**150ms**(로그인)로 쓴다.

**들어오는 요청(λ)** — design-constants ⑩~⑬(이번에 추가)에서 가져온다.

| 시점 | 피크 도착률 | 근거 |
|---|---|---|
| 지금(admin-web만) | 수 rps 이하 | 계정 197개, 관리자·직원만 쓴다 |
| member-app 출시 후(98개 지점) | **≈19 rps** | 로그인 피크 1.9/s(⑧) × 세션당 요청 10건(⑩, 가정 — 약함) |
| 3년 후(130개 지점) | **≈26 rps** | 2.56/s × 10 |
| 민감도: 세션당 30건 | ≈77 rps | 혼잡도 폴링이 붙는 경우 |

**동시 진행 수(Little's Law, L = λW)**:
- 3년 후 기준: 26 × 0.05 = **1.3건**
- 세션당 30건 기준: 77 × 0.05 = **3.9건**
- 로그인: 2.56 × 0.15 = 0.4건

**정리하면, 정상 상태의 처리량은 문제가 아니다.** 필요한 동시 실행은 2~5개다. Lambda 동시 실행 상한을 10으로 두면 처리 한계는 10 ÷ 0.05s = **200 rps**다. 3년 후 피크의 약 8배, 민감도 최악치의 약 2.6배다.

**진짜 제약은 세 가지다**:
1. **W가 늘어날 때의 루프**
2. **DB 커넥션 수**
3. **무료 티어의 "요청 개수" 한도**

아래 결정 1~3이 각각에 답한다.

## 2. 결정

**결정 1 — 자기강화 루프의 고리를 끊는다: 요청마다 CPU를 격리하고, 동시 실행 수를 DB가 감당하는 만큼으로 묶는다(입장 제어)**

D24의 루프는 "L↑ → W↑" 고리에서 생겼다. 요청들이 CPU 하나를 나눠 썼기 때문이다. Lambda는 실행 환경 하나가 한 번에 요청 하나만 처리한다. 그래서 **CPU 몫은 L과 무관하다.** 이 고리는 구조적으로 사라진다.

하지만 공유 자원이 하나 남는다. **DB 커넥션이다.** Lambda를 무제한으로 늘리면, 풀러의 DB 쪽 풀보다 많은 요청이 풀러 안에서 커넥션을 기다린다. 기다리는 만큼 W가 늘고, 같은 루프가 DB 앞에서 다시 생긴다. 그래서 과부하는 **안에서 줄 세우지 않고 입구에서 빠르게 거절한다**(bounded queue, fail fast).

| 설정 | 값 | 이유 |
|---|---|---|
| `DATABASE_URL` | Supavisor 트랜잭션 풀러 `:6543`, `?pgbouncer=true&connection_limit=1&pool_timeout=5` | 실행 환경 하나 = 요청 하나라 커넥션은 1개로 충분하다(위 테스트로 교착 없음을 확인). `pgbouncer=true`는 풀러 모드에서 prepared statement를 끈다. `pool_timeout`은 커넥션 대기의 상한이다 |
| Lambda 동시 실행 상한 | **10** | 풀러의 DB 쪽 풀 크기(무료 플랜 약 15, 대시보드에서 확인 필요)보다 작게 잡는다. `max_connections`=60(2026-09-30 확인)에서 마이그레이션·대시보드·MCP용 직접 연결 여유를 남긴다. 처리 한계는 200 rps다 |
| 상한 초과 시 | Lambda가 429로 즉시 거절 → Worker가 공통 에러 형식의 **503 `SERVER_BUSY`** + `Retry-After: 2`로 바꿔 응답(구현 시 확정 — IP별 제한인 `RATE_LIMITED` 429와 구분한다. 앱이 스스로 내는 429(`LINK_ATTEMPTS_EXCEEDED`)는 공통 포맷이라 그대로 통과) | 대기열이 생기지 않아 나머지 요청의 W가 지켜진다. admin-web에는 자동 재시도가 없어서(2026-09-30 확인) 재시도 폭주도 없다 |
| 쿼리 상한 | `statement_timeout` 5초 | 느린 쿼리 하나가 커넥션을 오래 붙잡지 못하게 한다. 풀러의 트랜잭션 모드는 접속 옵션을 무시할 수 있어서 역할(role) 단위로 건다(DB 설정 변경 — 적용 전 사용자 승인) |
| Lambda 타임아웃 | 10초 | Worker와 브라우저가 무한정 기다리지 않게 한다 |

**동시 실행 상한을 거는 방법은 계정 한도에 달렸다(배포 전 확인)**:
- 신규 AWS 계정은 계정 전체 동시 실행 한도가 10으로 시작하는 경우가 있다. 이때는 그 한도 자체가 상한이 된다. 예약 동시성(reserved concurrency)은 계정에 예약하지 않은 몫을 일정량 남겨야 해서 설정할 수 없을 수도 있다.
- 한도가 1,000이면 함수에 reserved concurrency 10을 건다.
- 어느 쪽이든 목표값은 10이다. Service Quotas에서 확인해 둘 중 하나로 건다.

**결정 2 — 무료 티어의 "요청 개수" 한도를 먼저 계산하고, 넘는 시점과 비용을 정해 둔다**

처리량보다 먼저 닿는 한계는 **하루·한 달 요청 개수 한도**다.

| 한도 | 무료 | 지금(admin-web) | member-app(98개 지점) |
|---|---|---|---|
| Cloudflare Workers 요청 | **10만/일** | 하루 1만 건 수준(추정) — 여유 | 98 × 200명(③) × 10건 = **19.6만/일 — 초과** |
| Lambda 요청 | 100만/월 | 여유 | 약 590만/월 — 초과 |
| Lambda 컴퓨트 | 40만 GB-초/월 | 여유 | 590만 × 0.05s × 1GB ≈ 29.5만 — 무료 안 |

- 정적 자산(UI)은 `run_worker_first`가 `/api/*`만이라 Worker 요청으로 세지 않는다(D25). 세는 것은 API 요청뿐이다.
- **Workers 무료 한도를 넘으면 그날 나머지 요청이 실패한다.** 느려지는 게 아니라 끊긴다. 그래서 member-app 출시(Phase 3) 전에 **Workers Paid(월 $5, 1,000만 요청/월)로 올린다.** Lambda 초과분은 요청 100만 건당 $0.20이라 월 $1 수준이다.
- 지금 단계에서는 무료로 충분하다. 넘는 시점은 "member-app 출시"로 못박아 둔다.
- 비용 사고(공격 등)는 결정 1의 상한 10이 Lambda 비용의 상한도 된다. AWS Budgets 알람($1)을 함께 건다.

**결정 3 — 콜드 스타트는 "없애기"가 아니라 "작게, 드물게"**
- Provisioned Concurrency는 무료가 아니라 쓰지 않는다.
- ⓐ **EventBridge Scheduler로 5분마다 워밍 호출**을 한다. Worker를 거치지 않고 Lambda를 직접 부르므로 Workers 한도에 안 잡힌다(월 8,640회). 핸들러는 HTTP 처리 없이 바로 끝낸다. 1시간에 한 번은 `SELECT 1`까지 실행한다. Supabase 무료 프로젝트는 7일간 활동이 없으면 일시정지되는데, 이것도 같이 막는다.
- ⓑ 배포 묶음을 줄인다. 1단계는 번들링 없이 `npm ci --omit=dev`로 정리한 zip을 쓴다. esbuild 번들은 Nest의 선택적 의존성 때문에 깨질 위험이 있다. 그래서 측정한 Init Duration이 목표(1.5초)를 넘을 때만 2단계로 한다.
- 워밍 1개로는 동시에 새로 뜨는 환경을 막지 못한다. 하지만 Lambda는 콜드 스타트가 **그 요청 하나만** 느리게 만든다. 환경마다 CPU가 따로라 다른 요청으로 번지지 않는다. 동시에 떠도 상한 10에 묶인다.

**결정 4 — 진입 구조: Function URL + 기존 Worker를 그대로 쓴다**
- API Gateway HTTP API는 무료 한도가 12개월뿐이다. **Lambda Function URL**은 추가 요금이 없다.
- Worker의 `API_ORIGIN`만 Function URL로 바꾼다. UI·API 같은 오리진(D25)과 로그인·가입 rate limit이 그대로 유지된다.
- **Worker 우회를 막는다.** Function URL은 공개 주소라 Worker의 rate limit을 건너뛰고 직접 부를 수 있다(지금 Render 주소도 같은 상태다). Worker가 비밀 헤더(`X-Origin-Secret`, Worker secret)를 붙이고, Lambda 앞단 미들웨어가 헤더가 없으면 403을 준다.
- 리전은 **ap-northeast-2(서울)**, 아키텍처는 **x86_64**다. `bcrypt`는 네이티브 모듈이다. Prisma 엔진은 이미 `rhel-openssl-3.0.x`를 포함한다(D27). arm64는 엔진·빌드를 둘 다 바꿔야 해서 뒤로 미룬다.
- 메모리는 **1,024MB로 시작한다.** 로그인 W가 목표를 넘으면 1,769MB로 올린다(아래 검증 기준).

**결정 5 — 코드 변경은 진입점만 추가한다(도메인 로직 무변경)**
- `configureApp(app)`: prefix·ValidationPipe·필터를 한 함수로 모은다. `main.ts`·새 `lambda.ts`·`test/helpers/app.ts`가 같이 쓴다. CLAUDE.md의 "main.ts를 바꾸면 헬퍼도 같이"를 코드로 강제한다.
- `lambda.ts`: `@codegenie/serverless-express`로 Express 앱을 감싼다. Nest 앱은 모듈 전역에 한 번만 만들어 따뜻한 호출에서 재사용한다. 워밍 이벤트는 앞에서 걸러 낸다.
- **JWT 비밀키 즉시 실패 처리.** 지금은 환경변수가 없으면 `'change-me'`로 조용히 동작한다. `NODE_ENV=production`에서 비밀키가 없으면 부팅을 실패시킨다. Lambda 환경변수를 빠뜨리면 누구나 토큰을 위조할 수 있는 구조를 막는다.
- 배포는 GitHub Actions로 한다. `main-5x9td9`에 push되면 x86_64 ubuntu에서 빌드한다. AWS 인증은 OIDC로 하고 액세스 키를 저장하지 않는다. `update-function-code` 후 새 버전을 발행하고, 별칭 `live`를 옮긴다. **롤백은 별칭을 이전 버전으로 되돌리는 것**이다. Render 자동배포가 조용히 멈췄던 일을 반복하지 않도록, 배포 후 `/health`를 확인하는 단계를 워크플로 안에 둔다.

## 3. Lambda로 옮겨도 남는 문제와 대응

| # | 문제 | 대응 | 상태 |
|---|---|---|---|
| R1 | 한 프로세스 안의 동시성 테스트는 `connection_limit=1`에서 직렬화된다 | 운영의 병렬성은 여러 실행 환경에서 나오고, 정합성은 DB 락·조건부 갱신이 지킨다(D28~D36). 테스트는 기본 풀로 계속 병렬 경합을 재현한다. 1 커넥션 실행은 "교착 없음" 확인용으로 남긴다 | 확인 완료(308/309) |
| R2 | 실행 환경이 얼어 있는 동안 풀러가 유휴 연결을 끊으면, 깨어난 뒤 첫 쿼리가 실패할 수 있다 | Prisma가 재연결한다. 스테이징에서 10분 이상 유휴 후 요청으로 확인한다. 실패하면 P1017 1회 재시도를 넣는다 | 배포 후 검증 |
| R3 | 한 회차에 예약이 몰리면 `lockScheduleSlot`이 직렬화한다 | 트랜잭션 1건이 약 10~20ms라 30건이 몰려도 마지막이 약 0.6초다. 행 락 대기는 `statement_timeout`이 상한을 둔다 | 설계상 허용 |
| R4 | 페이지네이션 없는 목록(`GET /members` 본사 전체 — traffic-infra-review 회원관리) | 지금 193명은 16ms다. 7만 명 규모에서는 W가 커진다. Lambda와 무관하게 남는 문제라, member-app 출시 전 페이지네이션을 따로 결정한다 | 후속 |
| R5 | 요청당 쿼리 4~8개(Prisma 5의 include는 별도 쿼리) | 같은 리전이라 왕복당 수 ms다. W가 목표를 넘으면 `relationJoins` 등을 검토한다 | 측정 후 판단 |
| R6 | 마이그레이션 이력: Supabase에는 MCP로 SQL을 적용해 `_prisma_migrations`가 없다 | 배포 파이프라인에 `migrate deploy`를 넣지 않는다. 기준선 맞추기(`migrate resolve --applied`)는 별도 작업이고, 그 전까지 마이그레이션은 지금처럼 수동으로 적용한다 | 후속 |
| R7 | 응답 크기 6MB 한도 | 파일 업로드는 범위 밖이다(1-10). 도입하면 S3 presigned URL로 한다 | 해당 없음 |
| R8 | 실제 클라이언트 IP | Lambda가 보는 IP는 Cloudflare다. rate limit은 Worker가 `CF-Connecting-IP`로 하고, 로그도 이 헤더를 쓴다 | 구현 시 반영 |
| R9 | 시간대 | Lambda도 UTC다. 날짜 계산은 이미 `kst-date.ts`로 통일돼 있다 | 영향 없음 |
| R10 | 관측 | CloudWatch Logs 보존 14일. Throttles>0·Errors·Duration p95 알람과 AWS Budgets 알람을 건다 | 구현 시 반영 |
| R11 | Render 정리 | 전환 후 `sports-erp-api`를 일시정지한다. 롤백은 Render가 아니라 Lambda 별칭으로 한다. Render는 D26 코드라 되돌릴 대상이 못 된다 | 전환 후 |

## 4. 검증 기준 — "감당한다"를 무엇으로 판정하나

D24와 같은 k6로 **Worker 주소에 대해** 측정한다. 결과는 design-constants ⑨의 장애 상황 값(15.16초)과 나란히 기록한다.

| 시나리오 | 부하 | 통과 기준 |
|---|---|---|
| S1 로그인 램핑(D24 재현) | 0→40 VU | 로그인 p95 < 500ms, 에러 0 |
| S2 혼합 조회 | 50 rps × 5분(3년 후 피크의 약 2배) | p95 < 300ms, 429 = 0 |
| S3 과부하 | 300 rps × 1분(처리 한계 200 rps 초과) | 429가 빠르게 나온다(429 응답 p95 < 100ms). 성공한 요청은 p95 < 500ms를 유지한다. DB 연결 수 ≤ 상한 + 여유 |
| S4 콜드 스타트 | 30분 유휴 후 동시 5요청 | Init Duration < 1.5초(CloudWatch REPORT) |

S3이 이 결정의 핵심 검증이다. 과부하에서 **"모두가 느려지는가, 넘친 요청만 거절되는가"**를 가른다. 앞의 것이면 D24의 루프가 DB 앞에서 다시 생긴 것이다. S1·S3에서 로그인 기준을 못 맞추면 메모리를 1,769MB로 올리고 다시 잰다.

## 대안 → 트레이드오프

| # | 대안 | 요청량 관점 | 한계 |
|---|---|---|---|
| A | Render 유지(무료) | 공유 CPU 1대라 루프가 그대로다. 15분 유휴 후 잠든다 | 서울 리전이 없어 DB 왕복 거리도 그대로다. 자동배포도 멈춰 있다 |
| B | Render 유료(상시 구동) | 잠들지 않는다. 단일 인스턴스 CPU는 전용이 된다 | 여전히 1대라 L↑→W↑ 고리가 남는다. 서울 리전 없음. 월 비용 |
| C | **Lambda(서울) + Function URL + 상한 10 (선택)** | 요청별 CPU 격리로 고리를 끊는다. 상한으로 DB 앞 대기열을 막는다. 같은 리전 | 콜드 스타트(결정 3). 무료 요청 개수 한도는 member-app 시점에 초과(결정 2) |
| D | Lambda + API Gateway | C와 같다 | 무료 12개월 후 과금. Worker가 이미 게이트웨이 역할을 한다 |
| E | Lambda + 상한 없음 | 가장 많이 받는다 | 풀 초과분이 풀러 안에서 대기해 W가 늘고, 루프가 DB로 옮겨 간다. 비용 상한도 없다 |

## 5. 범위 변경(2026-09-30, 같은 날) — 회원 앱을 빼고, DB 이전은 조건으로 남긴다

**회원 앱을 개발 범위에서 뺀다(사용자 결정).** 웹(admin-web)에 집중한다. 위 요청량 모델의 "member-app 출시 후" 행은 이제 범위 밖 시나리오다.
- 범위 안 규모는 관리자·직원 약 200명이다. 하루 API 요청은 1만 건 수준(추정)이다. Workers(10만/일)·Lambda(100만/월)·Supabase 무료 한도 안에 여유 있게 든다.
- **결정 2(Workers 유료 전환)는 보류한다.** 회원 앱을 다시 넣을 때 다시 연다.
- 결정 1·3·4·5는 그대로다. 요청량이 작아도 "넘치면 입구에서 거절"과 "동시 실행 상한 10"은 비용·DB 보호 장치로 필요하다.

**DB를 AWS(RDS)로 옮길지 검토했고, 지금은 옮기지 않는다.**

| 관점 | Supabase(서울) 유지 | RDS PostgreSQL(서울)로 이전 |
|---|---|---|
| 지연 | Supabase 서울 리전도 AWS 서울 위에 있다. Lambda와 같은 리전 안 통신이다 | 쿼리당 1~2ms 정도 준다. 병목이던 리전 차이(싱가포르↔서울)는 Lambda 전환으로 이미 사라진다 |
| 커넥션 상한 | `max_connections` 60 + Supavisor 풀러 | 최소 인스턴스(`db.t4g.micro`)도 약 100 안팎이다. Lambda용 풀러(RDS Proxy)는 별도 요금이다 |
| 비용 | 무료(500MB, 7일 비활성 시 일시정지 — 결정 3의 워밍이 막는다) | 무료 혜택은 기간 한정(계정 조건 확인 필요). 이후 월 $15 안팎 |
| 네트워크 | 공개 엔드포인트 + 비밀번호·TLS | 비공개로 두려면 Lambda를 VPC에 넣어야 한다. 외부 호출이 생기면 NAT(월 $30대)가 붙는다. 공개로 열면 Lambda IP가 고정되지 않아 5432를 전체에 연다 |
| 운영 도구 | Supabase MCP로 SQL 적용·시드 지문 확인(D29~D36 절차) | 절차를 새로 만들어야 한다 |
| 되돌리기 비용 | — | 낮다. 저장소 마이그레이션 6개는 순수 Postgres이고, Supabase 전용 설정(RLS)은 저장소 밖에만 있다. `pg_dump`/`pg_restore` + 연결 문자열 교체로 끝나고 코드는 바뀌지 않는다 |

되돌리기 비용이 낮으니 미리 정할 이유가 없다. **아래 중 하나가 생기면 RDS PostgreSQL 이전을 다시 검토한다**(DynamoDB·Aurora Serverless는 D26 판단대로 대상에서 뺀다):
1. DB 용량이 무료 한도(500MB)의 80%(약 400MB)에 닿을 때
2. 특정 시점 복구(PITR) 같은 백업·복구 요구가 생길 때
3. Supavisor 풀 대기가 S2·S3 측정이나 운영 알람에서 반복될 때
4. 회원 앱을 다시 범위에 넣을 때(결정 2와 함께)

결정 5를 구현했다. 도메인 로직은 바꾸지 않았다.

**런타임은 Node.js 22.x로 정했다.** 저장소의 `.nvmrc`는 20이다. 하지만 Lambda의 nodejs20.x는 Node 20 지원 종료(2026-04)에 따라 폐기 대상이라 새 함수에 쓰지 않는다. 배포 워크플로도 22로 빌드한다. CI 테스트는 여전히 20에서 돈다(아래 "감수하는 것").

**검증**:
- **jest:** 전체 309 통과, todo 1. 격리·계약 종료·인사 권한 테스트는 기대값 변경 없이 통과했다. `test/helpers/app.ts`가 `configureApp()`을 쓰게 바뀌면서 테스트 앱에도 CORS 설정이 들어갔다. 동작 차이는 없다.
- **lint·빌드:** api lint 에러 0(경고 1건은 기존 `main.ts`), api 빌드 성공. admin-web lint·빌드 성공.
- **패키징된 zip을 Amazon Linux 2023 컨테이너에서 실행했다.** Lambda 공식 이미지는 이 세션의 네트워크 정책으로 받을 수 없어서, 같은 OS(glibc·OpenSSL 3)인 `amazonlinux:2023`에 Node 22를 얹었다. Function URL 형식(페이로드 2.0)의 합성 이벤트로 직접 호출했다.
  - rhel Prisma 엔진과 bcrypt가 로드됐고, 로그인 200, `/branches` 98건, 쿼리스트링 전달, 400·401 공통 포맷이 나왔다.
  - 비밀 헤더 없음·틀림은 403이었다.
  - 워밍은 첫 호출에 DB 핑, 두 번째는 생략했다.
  - JWT·ORIGIN 비밀값을 빼면 부팅이 실패하고, 어떤 변수가 없는지 메시지가 나왔다.
  - cold init **1.2초**, 따뜻한 `/branches` p50 23ms·p95 30ms(`connection_limit=1`).
- **Worker는 가짜 fetch로 확인했다.**
  - Lambda 스로틀 429는 503 `SERVER_BUSY`(+`Retry-After`)로 바뀐다.
  - 앱 자체 429는 그대로 나간다.
  - 위조한 `X-Origin-Secret`은 Worker 값으로 덮어쓴다.
  - origin 다운은 502 `UPSTREAM_UNAVAILABLE`이다.
- **검증되지 않음:** 실제 AWS(Lambda 런타임·Function URL·풀러 연결·동시성 상한·스로틀 응답 형식), 배포 워크플로 실행, §4 k6 S1~S4. AWS 설정 후 `aws-lambda/README.md` 7번으로 잰다.

**감수하는 것**:
- W와 풀러 왕복은 **로컬 실측에 가정을 얹은 추정**이다. 결정 1의 상한 10과 결정 3의 1,024MB는 §4 측정 결과로 다시 조정한다.
- "세션당 요청 10건"(⑩)은 근거가 약하다. member-app 로그가 쌓이면 갱신한다.
- AWS 계정·함수·OIDC 역할·환경변수는 이 세션에서 만들 수 없다(AWS 연동 도구 없음). 사용자가 콘솔에서 만든다. 체크리스트는 구현 커밋의 `docs`에 둔다.
- 배포 경로가 Cloudflare(UI, 수동 `wrangler deploy`) + AWS(API, 자동)로 둘이 된다. UI 배포 자동화는 이번 범위가 아니다.
- CI 테스트는 Node 20(`.nvmrc`), Lambda·배포 빌드는 Node 22다. `.nvmrc`를 22로 올리는 건 admin-web까지 영향이 있어 별도로 정한다.
- CI(`ci.yml`)는 `main`과 PR에서만 돈다. `main-5x9td9`에 직접 push하면 테스트 없이 배포 워크플로가 먼저 돈다. PR로 병합하는 지금 흐름에서는 PR에서 테스트가 돈다.
