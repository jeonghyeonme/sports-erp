# D20. 대시보드 우선순위 재편 + 위탁계약 필드 도입 + 지점 기준 정보구조(IA)

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: 세 가지를 한 번에 바꿨다. ① 대시보드 최상단 KPI를 "전체 회원/전체 직원/진행중 프로그램"에서 "전체 지점 수/전체 직원 수/계약 갱신 임박 지점"으로 교체하고, ② architecture/entities.md §2-1에 스펙으로만 있던 `Branch` 위탁계약 필드(`contractPartner`, `contractStartAt`, `contractEndAt`, `contractStatus`)를 mock 데이터로 처음 구현해 지점 카드에 계약 상태 뱃지로 노출했다. ③ `BranchDetailPage`의 드릴다운에 혼잡도 섹션을 추가해 "지점 → 직원/회원/프로그램/혼잡도" 4단 구조를 완성하고, 회원/직원/프로그램/시설·혼잡도 최상위 메뉴는 flat 목록 대신 지점별 섹션으로 묶어서 보여주도록 바꿨다(`groupByBranch` 헬퍼, `apps/admin-web/src/lib/group-by-branch.ts`).

**쉽게 말하면**: 지금까지 대시보드 맨 위에는 "회원 몇 명, 직원 몇 명, 프로그램 몇 개"가 떠 있었는데, 이걸 본사가 실제로 매일 신경 써야 할 숫자인 "몇 개 지점과 계약 중인지, 계약이 곧 끝나가는 지점이 있는지"로 바꿨습니다. 회원/프로그램 개수는 없앤 게 아니라 지점 카드 안으로 내려갔습니다. 그리고 회원/직원/프로그램/시설 메뉴를 눌렀을 때 모든 지점이 뒤섞인 표 하나가 아니라, "서초점" "강남점"처럼 지점별로 나뉜 섹션으로 보이게 만들었습니다.

**근거**: CLAUDE.md/architecture/entities.md가 이미 규정한 사업 구조 — `Branch`는 매장이 아니라 위탁운영 계약 현장이고, "시스템 불안정 → 민원 → 계약 해지"가 이 프로젝트의 핵심 리스크 — 를 사용자가 다시 직접 짚으며 "대시보드 메인 카드는 전체 지점 수·전체 직원 수 두 개, 계약 만료 임박한 지점도 따로 띄워야 한다"고 요구했다(2026-09-08~09). 본사 관심사는 회원·프로그램 개수가 아니라 "몇 개 계약을 유지 중이고 어느 계약이 위험한가"라는 것이 이 요구의 실질적 의도다. 동시에 "회원/직원/프로그램은 다 지점보다 하위 단계"라는 정보 구조 원칙과 "최상위 메뉴로 봐도 지점별로 구분돼야 한다"는 요구가 함께 나와, KPI 재편과 IA 재구성을 한 세트로 처리했다.

**타당성**: 높음 — 코드를 짜기 전에 Plan 모드로 범위(계약 필드 4계층 반영 방식, `renewalNoticeAt`/`cancellationPolicy` 등 근태·예약 도메인 필드는 이번 범위 밖으로 명시적으로 제외)를 먼저 정리해 사용자 승인을 받고 진행했다. `contractStatus`는 스펙상 크론으로 전이되는 필드지만 크론이 없는 현재는 mock 시드에 지점별로 직접 값을 넣어(서초점 `ACTIVE`, 강남점 `RENEWAL_DUE`) 대시보드 경고 카드가 실제로 동작하는 것까지 브라우저로 확인했다.

**장점**
- `assignedStaffName`([D16](#d16-지점직원회원프로그램-드릴다운--memberassignedstaffid-추가))과 동일한 "컨트롤러에서 인라인 조인" 패턴을 그대로 재사용해 `branchName`을 4개 컨트롤러(members/staff/programs/facilities)에 일관되게 추가했다 — 새 패턴을 만들지 않고 기존 관례를 확장만 함
- `groupByBranch` 제네릭 헬퍼 하나로 4개 페이지의 그룹핑 로직을 공유해, BRANCH_ADMIN/STAFF처럼 API가 이미 한 지점으로 필터링된 경우 섹션이 자연히 1개로 축소되는 것까지 별도 분기 없이 처리됨
- Prisma 스키마도 mock 데이터와 함께 갱신해([D16](#d16-지점직원회원프로그램-드릴다운--memberassignedstaffid-추가)와 같은 관례) architecture/entities.md·스키마·mock·admin-web 타입이 어긋나지 않게 유지함

**단점·리스크**
- `contractStatus` 전이를 담당할 배치(크론)가 없으므로, 지금 뜨는 "계약 갱신 임박" 숫자는 실제 날짜 계산이 아니라 시드에 박아둔 값이다 — 실 데이터가 들어가는 시점에 크론 또는 API 계층에서 `contractEndAt` 기준 자동 계산 로직이 반드시 필요함
- `renewalNoticeAt`(갱신 알림 발송 기준일)은 스펙에 있지만 이번 구현에서 의도적으로 뺐다 — 지금 화면에 소비하는 곳이 없어 미사용 필드를 미리 만들지 않기 위함이지만, 나중에 알림 기능을 붙일 때 이 결정을 다시 열어봐야 함
- `groupByBranch`는 클라이언트에서 지점별로 묶을 뿐, 서버 API 자체는 여전히 flat 배열을 내려준다 — 지점 수·행 수가 커지면(포트폴리오 규모에서는 무관하지만) 페이지네이션이 지점 경계와 맞물리는 문제를 나중에 고려해야 함

**대안 및 미채택 사유**: "계약 만료 임박" 카드를 배치(크론) 없이 만들려면 `renewalNoticeAt`을 아예 안 만들고 `contractEndAt`에서 매번 60일 임박 여부를 실시간 계산하는 방법도 있었으나, 스펙(architecture/entities.md §2-1)이 `contractStatus`를 "배치로 전이되는 별도 저장 필드"로 명시하고 있어 실제 운영 시나리오(계약 담당자가 수동으로 갱신 처리 완료 표시를 하는 경우 등)와 더 맞는 저장 필드 모델을 그대로 따랐다. 최상위 메뉴 자체를 없애고 지점 드릴다운으로만 접근하게 하는 방안도 검토했지만, 사용자가 "회원/프로그램/시설혼잡도만 따로 봐도"라고 명시해 최상위 메뉴 유지를 전제로 요구했으므로 채택하지 않았다.
