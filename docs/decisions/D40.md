# D40. 범위 재설정 — 지점을 수도권 83곳으로 줄이고, 회원 기능을 모바일 웹으로 만든다 (2026-10-06)

> 결정 기록 [인덱스](README.md) · 경위는 [log/068](../log/068.md) · [D37](D37.md) §5(회원 앱 범위 제외)와 결정 2 보류를 대체한다

**컨텍스트(Driver)**:
- D37 §5는 회원 앱을 범위에서 뺐다. 근거는 [design-constants](../architecture/design-constants.md) ⑬의 "회원 앱 포함 하루 19.6만 건 → Cloudflare Workers 무료 한도(10만/일)의 두 배"였다.
- 그 값은 ③ "지점당 하루 방문 200명"(등록률 25% × 방문율 36%, 둘 다 약한 가정)에서 나왔다. 사용자는 아파트 커뮤니티 시설이 하루 100명을 넘기 어렵다고 봤다.
- 100명으로 다시 계산하면 98곳 전체는 하루 약 10.8만 건(관리자 웹 약 1만 포함)이다. 한도를 두 배가 아니라 조금 넘는다.
- 처리량은 막는 이유가 아니다. 피크는 약 8 rps이고, 10/4 k6 실측 한계는 약 50 rps다([log/056](../log/056.md)).
- 회원용 API(MEMBER 권한 라우트)는 이미 있다. 남은 것은 화면이다.

## 결정

1. **지점 범위를 수도권(서울·경기·인천) 83곳으로 줄인다.** 시드의 지방 지점 15곳을 뺀다. 하루 요청은 약 9.3만 건이 돼 무료 한도 안이다.
2. **회원 기능은 모바일 웹으로 만든다.** 네이티브(Expo) 앱은 만들지 않는다.
   - admin-web과 같은 React+Vite·공유 타입을 쓰고, 같은 Cloudflare Worker로 배포한다. 인프라를 더 붙이지 않는다.
   - 같은 화면을 지점 태블릿에 띄우면 키오스크로도 쓸 수 있다.
3. **산정 가정을 바꾼다.** design-constants ③을 "지점당 하루 100명(사용자 추정)"으로 바꾸고, ④~⑬을 다시 계산한다.
4. 발표 덱(4-5)은 이 계산을 처음부터 쓴 것으로 정리한다(사용자 결정). 저장소의 결정·로그는 실제 경위대로 남긴다.

**대안**:
- 98곳 유지 + 회원 앱은 수도권 지점에만 연다. RFP의 "전국 98개 업장"과 맞고 데이터 변경이 없다. 하지만 사용자가 더 간단한 쪽(지점 축소)을 골랐다.
- 98곳 유지 + Workers 유료(월 $5). 한도 문제가 사라진다. 하지만 무료 범위 운영이라는 지금 원칙을 바꾼다.
- 회원 앱 보류 유지(D37 §5). 계산을 바로잡은 뒤에는 근거가 약하다.

**감수하는 것**:
- RFP의 "전국 98개 업장"과 시스템 지점 수(83)가 달라진다. 발표에서는 "RFP 98곳 중 수도권 83곳을 대상으로 했다"로 설명한다.
- 하루 9.3만 건은 한도의 93%다. 지점당 사용자나 방문당 호출(⑩, 약한 가정)이 늘면 넘는다. 넘으면 Workers 유료로 전환하고 그때 지방 현장을 다시 연다.
- Lambda 요청은 월 약 280만 건으로 무료 100만 건을 넘는다. 요청 요금은 월 1달러 미만으로 추정한다.
- 지점 축소는 시드·테스트(`branch-parity` 98개)·관리자 웹 안내 문구에 닿는다. **배포 DB(Supabase)에서 지점 15곳과 딸린 데이터를 지우는 일은 사용자 승인 후** 별도로 한다.

**재고 트리거**: 하루 요청이 9만 건을 넘기 시작할 때, 또는 지방 현장을 다시 열 때.
