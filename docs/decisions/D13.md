# D13. 모노레포 + 기술 스택 선택 (NestJS/Prisma/PostgreSQL/React+Vite/Expo)

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: npm workspaces 기반 모노레포(`apps/*`, `packages/*`)로 admin-web/api/member-app/types를 한 저장소에서 관리하고, 백엔드는 NestJS+Prisma+PostgreSQL, 관리자 웹은 React+Vite, 회원 앱은 React Native(Expo)를 사용한다. (README, [architecture/entities.md](../architecture/system-overview.md) §6)

**쉽게 말하면**: 관리자 웹, 회원 앱, 백엔드 서버, 공용 타입 정의를 각각 따로 관리하지 않고 한 저장소(모노레포) 안에 모아서, 서로 같은 타입을 공유하며 개발합니다.

**근거**: `packages/types`로 클라이언트-서버 간 DTO 타입을 공유하려면 모노레포가 사실상 필수 전제 조건이다(별도 리포로 쪼개면 타입 동기화를 위해 npm 패키지 배포/버전관리가 추가로 필요해짐). NestJS는 데코레이터 기반 구조(Guard/Interceptor)가 이 프로젝트의 RBAC·BranchScope 요구사항과 잘 맞고, Prisma는 스키마 우선 설계와 타입 안전 쿼리를 제공해 1인 개발의 생산성을 높인다.

**타당성**: 높음. 모든 선택이 서로 시너지를 내도록 구성되어 있다 — 모노레포(공유 타입) + NestJS(데코레이터 기반 인가) + Prisma(스키마=단일 진실 공급원)가 D1(RBAC), D2(branchId 격리)를 구현하는 데 필요한 인프라를 정확히 제공한다.

**장점**
- `packages/types`를 통해 프론트/백엔드 타입 불일치로 인한 런타임 버그를 컴파일 타임에 차단 가능
- Prisma의 마이그레이션 이력이 그 자체로 스키마 변경의 감사 기록이 됨(D7 같은 구조 변경의 근거 추적 가능)
- npm workspaces는 별도 도구(Nx, Turborepo 등) 없이 표준 npm만으로 충분히 굴러가, 1인 개발의 도구 학습 비용을 최소화

**단점·리스크**
- npm workspaces는 Nx/Turborepo 대비 빌드 캐싱·태스크 그래프 최적화가 없어, 프로젝트가 커지면 `npm run build` 등이 매번 전체를 다시 빌드함 — 다만 이 프로젝트 규모(앱 3개)에서는 아직 체감될 문제는 아님
- Expo(React Native)는 Phase 3부터 착수 예정이라 아직 실제 통합 검증이 안 된 상태 — `packages/types`가 Expo 환경에서도 문제없이 import되는지(메트로 번들러 호환성 등)는 Phase 3 착수 시점에 처음 확인하게 됨
