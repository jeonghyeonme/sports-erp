# D44. 변경 이력(AuditLog) — 인사 변경 3종을 같은 트랜잭션에서 기록하고, 본사만 조회한다

> 결정 기록 [인덱스](README.md) · 경위는 [log/086](../log/086.md) · RFP 1-2 #3 데이터관리방안(변경이력), [D17](D17.md) 숙제("누가 언제 승진시켰는지")

**상태**: 결정·구현(2026-10-08, 브리프 B5-2).

## 컨텍스트

- 스키마에 `AuditLog`(actorId·entity·entityId·action·before·after·createdAt)가 있지만 기록하는 코드가 없었다([요구사항추적표](../reference/요구사항추적표.md) §2-3).
- [entities.md](../architecture/entities.md)는 "모든 주요 엔티티를 기록"한다고 적었다. 하지만 모든 쓰기에 붙이면 범위가 크다. 예약·근태처럼 자주 쓰는 쓰기를 기록하면 DB 무료 용량(design-constants ⑮)도 빨리 쓴다.
- 지금 "누가 했는지"를 남기지 않아 추적이 안 되는 것은 인사다. 이 프로젝트의 불변식(인사 권한 분리)과 직접 닿는다.
  - 역할 전환(D17): 승진·강등을 누가 했는지 남지 않는다.
  - 퇴사: 상태만 바뀌고 처리자가 남지 않는다.
  - 파견: `StaffAssignment.assignedBy`가 있다. 다만 이력 화면과 분리돼 있다.
- 지점 계약 상태는 바꾸는 API가 없다(시드로만 정한다). 그래서 지금 기록할 대상이 아니다.

## 결정

1. **기록하는 이벤트(사용자 결정 2026-10-08)**: `entity = 'Staff'`, `entityId = staffId`.

   | action | 라우트 | 할 수 있는 역할 | before → after |
   |---|---|---|---|
   | `ROLE_CHANGED` | `PATCH /permissions/staff/:staffId/role` | SUPER_ADMIN | `{ role }` → `{ role }` |
   | `RESIGNED` | `PATCH /staff/:id/resign` | BRANCH_ADMIN(자기 지점) | `{ status, branchId }` → `{ status, resignDate }` |
   | `ASSIGNED` | `POST /staff/:id/assignments` | SUPER_ADMIN | `{ branchId }` → `{ branchId, note, releasedMemberCount }` |

   - 역할을 같은 값으로 "바꾸는" 요청은 기록하지 않는다. 바뀐 것이 없기 때문이다.
2. **같은 트랜잭션 안에서 쓴다**([data-integrity](../architecture/data-integrity.md) 체크리스트). 변경이 롤백되면 이력도 남지 않고, 이력 쓰기가 실패하면 변경도 롤백된다. `updateRole`은 이 결정으로 트랜잭션 안으로 옮긴다.
3. **actor**는 요청한 계정(`RequestUser.accountId`)이다. 계정이 지워지면 `actorId`는 NULL이 되고 이력은 남는다(스키마의 SET NULL).
4. **before/after에는 바뀐 필드만 넣는다.** 전화번호 같은 개인정보는 넣지 않는다. 이력 자체가 개인정보 저장소가 되지 않게 하기 위해서다.
5. **조회는 SUPER_ADMIN만**: `GET /audit-logs?entity=&entityId=&action=&page=&limit=`.
   - 최신순으로 준다.
   - 페이지 형식은 D43과 같다: `ok(items, { page, pageSize, total })`, 기본 20, 상한 100.
   - 응답에 처리자 이름과 대상 직원 이름을 붙인다. 쪽 단위로 한 번씩 더 조회한다.
   - admin-web에 SUPER_ADMIN 메뉴 "변경 이력"을 둔다.
   - 지점 단위 데이터가 아니라 본사 감사 기록이다. 그래서 BRANCH_ADMIN에게도 열지 않는다. 지점 격리 공격 표에 다른 역할의 403을 추가한다.

## 대안

- **모든 쓰기를 기록**(entities.md 원문): 범위·용량이 크다. 예약·근태는 각 테이블이 이미 이력이다(취소 시각·상태).
- **상세 전화번호 열람 기록**(ADR-MEM-04 숙제): 조회마다 쓰기가 1회 늘어난다. 이번에는 사용자가 고르지 않았다. 남은 숙제로 둔다.
- **Prisma 미들웨어로 자동 기록**: 누가(actor)를 미들웨어가 알 수 없다(요청 컨텍스트 전파 필요). 바뀐 필드만 고르기도 어렵다.
- **지점 관리자에게 자기 지점 이력 공개**: 퇴사 처리는 지점 관리자도 한다. 하지만 감사 기록은 감사 대상에게 열지 않는 쪽이 기본이다. 필요해지면 branchId 범위 필터를 붙인다.

## 결과

- 좋아지는 것: RFP 1-2 #3 "변경이력 관리"에 실제 기록과 화면으로 답한다. D17의 "누가 언제 승진시켰는지"가 닫힌다.
- 감수하는 것: 인사 쓰기 3종에 INSERT가 1회씩 는다. 건수가 적어 용량 영향은 무시할 수준이다.
- 남은 것: 회원·직원 상세 전화번호 열람 기록(ADR-MEM-04), 회원 상태·자산 상태 변경, 근태 정정 이력은 기록하지 않는다.

**재고 트리거**: 개인정보 열람 감사를 요구받을 때 → 상세 열람 기록을 더한다. 기록 대상이 늘어 쓰기마다 붙이기 번거로워질 때 → 요청 컨텍스트(AsyncLocalStorage) 기반 공통 기록을 검토한다.
