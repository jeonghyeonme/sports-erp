# D4. JWT Access(30분)/Refresh(14일, rotate) + 저장소 분리

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: Access Token은 30분 수명으로 클라이언트 메모리/헤더에, Refresh Token은 14일 수명으로 admin-web은 httpOnly Cookie, member-app은 SecureStore에 저장한다. Refresh는 1회용(rotate) 방식을 권장한다. ([권한관리 문서](../domains/권한관리.md) §3.2, §6)

**쉽게 말하면**: 한 번 로그인하면 30분짜리 "임시 출입증"을 주고, 만료되면 뒤에 있는 14일짜리 "재발급 카드"로 조용히 새 임시 출입증을 받게 합니다. 임시 출입증을 도둑맞아도 피해가 30분 안에서 끝나도록 일부러 짧게 잡은 것입니다.

**근거**: Access Token을 길게 잡으면 탈취 시 피해 window가 커지고, 너무 짧으면 갱신 요청이 잦아져 UX와 서버 부하 모두 손해다. 30분/14일은 업계에서 흔히 쓰이는 중간값이다. httpOnly Cookie는 admin-web(브라우저)에서 XSS로 인한 토큰 탈취를 막는 표준 방어이고, SecureStore는 React Native의 표준 안전 저장소다.

**타당성**: 높음, 업계 표준을 그대로 따른 선택. 클라이언트 유형별로 적절한 저장소를 다르게 지정한 것도 정확하다.

**장점**
- httpOnly Cookie + SecureStore 조합은 각 플랫폼에서 검증된 최선의 선택지에 가까움
- Refresh Token을 원문이 아닌 해시로 저장(권한관리 A-3)해 DB 유출 시에도 토큰 자체는 즉시 악용 불가

**단점·리스크**
- httpOnly Cookie 사용 시 CSRF 방어(SameSite 속성, CSRF 토큰 등)가 별도로 필요한데, 문서에 명시적으로 다뤄지지 않음 — 실제 구현 시 반드시 챙겨야 할 항목
- Refresh Token rotate가 "권장"으로만 적혀 있고 Phase 1 필수 항목이 아님(권한관리 A-8 Phase 2로 분류) → Phase 1까지만 구현하고 멈추면 탈취된 Refresh Token이 만료 전까지 계속 유효한 상태로 남음

**How to apply (구현 시 주의)**: admin-web의 Cookie 발급 시 `SameSite=Strict` 또는 `Lax` + `Secure` 플래그를 반드시 설정할 것. CSRF 방어를 Phase 1 체크리스트에 암묵적으로라도 포함시키는 것을 권장.
