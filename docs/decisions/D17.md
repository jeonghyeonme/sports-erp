# D17. 본사 전용 "권한 관리"(Role 전환) 기능 추가

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: SUPER_ADMIN 전용 `/permissions` 화면과 `GET/PATCH /api/v1/permissions/staff` API를 신설해, 지점 직원의 `Account.role`을 `STAFF` ↔ `BRANCH_ADMIN`으로 전환할 수 있게 했다. Mock 데이터 계층에서는 in-memory `accounts` 배열의 객체 프로퍼티를 직접 mutate하는 방식으로 구현했다.

**쉽게 말하면**: 본사 관리자가 화면 하나에서 "이 지점 직원을 지점 관리자로 승진시킬지, 다시 일반 직원으로 되돌릴지"를 드롭다운으로 바로 바꿀 수 있게 만들었습니다.

**근거**: [권한관리 문서](../domains/권한관리.md) §4/§5의 원래 설계는 "계정 생성/비활성화"만 SUPER_ADMIN 화면·API로 명시했을 뿐, "이미 만들어진 직원 계정의 Role을 나중에 바꾸는" 기능은 없었다. 그런데 사용자가 "본사 직원들은 지점별 직원들의 권한 제어가 가능해야 한다"고 명시적으로 요구했고(2026-09-05), 이는 계정 자체의 CRUD가 아니라 이미 있는 계정의 role 필드만 바꾸는 더 좁고 구체적인 요구라 별도의 작은 엔드포인트로 최소 구현했다.

**타당성**: 높음. `RolesGuard`(`@Roles('SUPER_ADMIN')`)로 서버단 강제까지 확인했고, `STAFF`/`BRANCH_ADMIN` 두 값만 `@IsIn`으로 화이트리스트 검증해 `SUPER_ADMIN` 승격 같은 위험한 값 주입을 원천 차단했다. 다만 이 기능은 권한관리 문서에 아직 문서화되지 않은 "사실상의 스펙 확장"이라는 점은 명확히 인지해야 한다.

**장점**
- ~~JWT가 로그인 시점 role을 그대로 서명해 담는 기존 설계와 상호작용하는 지점을 놓치지 않고, "role 변경이 즉시 전역 반영되지 않고 재로그인이 필요하다"는 한계를 화면 문구로 명시해 사용자 혼란을 방지함~~ **정정(2026-09-18)**: 이 "한계"는 애초에 권한관리 A-6이 요구하지 않는, JWT 설계상의 실제 버그였다 — access token엔 이제 role을 담지 않고 `sub`(accountId)만 담아, 매 요청 최신 Account 조회 결과로 role/branchId를 새로 구성하도록 고쳤다. 그 결과 재로그인 없이 다음 요청부터 즉시 반영되며, admin-web 안내 문구도 함께 정정했다.
- BRANCH_ADMIN 계정으로 로그인하면 이 메뉴 자체가 사이드바에서 사라지는 것까지 브라우저로 검증함

**단점·리스크**
- (2026-09-06 해소) 권한관리 A-4(화면 목록)·§5(API 명세)·§7(권한 매트릭스)에 이 화면/API/권한행이 반영됨
- mock 데이터 mutate는 서버 프로세스 재시작 시 원상복구되는 휘발성 상태라, 실제 DB 연동 전까지는 "영구 변경"이 아님 — 데모 중 API 서버를 재기동하면 권한 변경 내역이 사라진다는 것을 시연자가 인지하고 있어야 함
- `AuditLog`([architecture/entities.md](../architecture/system-overview.md) §5) 연동 없이 role을 바꿀 수 있어 "누가 언제 이 직원을 승진시켰는지" 추적이 안 됨 — [D9](#d9-소프트-삭제-원칙-전반)·[D12](#d12-staff-role-분리-branch_admin과-구분)에서 강조한 감사 가능성 원칙과 어긋나는 지점이라, 실제 쓰기 로직 단계에서 AuditLog 연동을 권장

**대안 및 미채택 사유**: Account 전체를 관리하는 범용 CRUD(`GET/POST/PATCH/DELETE /accounts`)를 먼저 구현하고 그 일부로 role 변경을 포함하는 방법도 있었으나, 사용자가 요청한 범위(권한 제어)만 최소로 구현하는 것이 현재 단계(Phase 1 스캐폴딩)에 맞다고 판단해 별도의 작은 엔드포인트로 분리했다.
