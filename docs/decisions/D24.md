# D24. 인증 경로 확장성 대응 — 부하테스트 실측 기반 단계적 로드맵

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: D23 배포 직후 k6로 부하테스트를 진행한 결과(`docs/log/` §31), 로그인(`bcrypt.compare`, cost=10)에 동시 요청이 몰리자 응답시간이 로컬 대비 100배 이상(p95 15.16초) 치솟았다. 조회(MockDataService 인메모리 스캔, 원래 매우 빠름)까지 함께 느려진 것으로 보아 코드 문제가 아니라 **Render 무료 티어의 공유 CPU 스로틀링**이 원인이다. `design-constants.md` ⑦~⑨에서 Little's Law로 다시 계산해보니, 평소 트래픽(초당 2명 미만)은 전혀 문제가 안 되지만 **일단 처리 지연이 발생하는 순간 "동시 진행 건수 = 도착률×처리시간" 공식에 따라 지연이 지연을 부르는 자기강화 루프**에 빠진다는 게 드러났다(정상 처리 시 동시 진행 ≈0.12건 → 15초 지연 시 ≈28.5건). 이건 "인증 방식이 안전한가"(D4가 이미 다룸)와는 다른 질문 — **"이 인증 경로가 실제 성장 목표(98→130개 지점) 규모의 동시 요청을 구조적으로 버틸 수 있는가"**다. 이 시스템이 무엇을 짓는 프로젝트인지(위탁계약 98개, 회원 수만 명 규모를 전제로 한 ERP)를 감안하면 이건 Driver로 승격할 만한 무게가 있다.

**설계 질문**: 로그인 경로의 CPU 스로틀링을 어떻게 해소할까 — 그리고 이건 "코드를 고치는" 문제인가 "인프라를 바꾸는" 문제인가?

**대안 → 트레이드오프**

| # | 대안 | 무엇을 해결하나 | 한계 |
|---|---|---|---|
| A | 로그인 rate limit (AUTH-T01 실구현) | **악의적/과도한 요청**을 걷어내 CPU를 정상 사용자에게 남겨둔다 | **정상적인 동시 로그인 폭주(예: 퇴근 후 동시 접속)는 못 막는다** — 오히려 정상 사용자를 튕겨낼 위험. 보안 대책이지 용량 대책이 아니다 |
| B | bcrypt cost 하향(10→8) | CPU 비용 자체를 줄여 임계점을 뒤로 미룸 | 보안 여유를 대가로 냄. 근본 해결이 아니라 "더 버티는" 것뿐 — 성장하면 다시 부딪힘 |
| C | 수직 확장(Render 유료 플랜, 전용 CPU) | 스로틀링 원인을 직접 제거 | 비용 발생. 단일 인스턴스라 그 인스턴스가 감당 못 할 정도로 크면(3년 후 130개 지점) 결국 다시 한계 |
| D | 수평 확장(다중 인스턴스 + 로드밸런서) | 트래픽을 여러 인스턴스로 분산 — 성장에 맞춰 인스턴스를 늘리면 되는 구조 | **현재 아키텍처로는 불가능하다** — `MockDataService`가 인스턴스별 인메모리 상태라, 여러 인스턴스를 띄우면 각자 다른 데이터를 들고 있게 됨. 실DB(Supabase Prisma) 전환으로 API 서버를 무상태(stateless)로 만드는 게 **전제조건**이다 |
| E | 인증 경로 큐잉/백프레셔 | 서버가 죽는 대신 "잠시 후 재시도"로 우아하게 저하 | 사용자 경험은 나빠짐. 근본 용량 문제는 그대로 남음 — 임시방편 |
| F | Cloudflare 앞단 rate limiting/WAF | 앱 코드 변경 없이 방어선을 한 겹 더 둠 | ~~커스텀 도메인이 있어야 성립~~ → **정정(같은 날 재검토)**: `workers.dev` 서브도메인은 도메인 구매 없이 Cloudflare 계정만 있으면 바로 쓸 수 있고(Cloudflare 공식 문서로 확인), Workers Rate Limiting 바인딩(`ratelimit`, 2025-09-19 GA)도 Zone(=도메인) 없이 Worker 단독으로 동작한다. 진짜 한계는 도메인이 아니라 **배포 도구** — Cloudflare MCP 커넥터엔 Worker를 만드는 툴이 없고(조회만 가능), 이 세션 자체도 egress 정책상 Cloudflare API에 직접 못 붙는다. 로컬에서 `wrangler deploy`로 사용자가 직접 배포해야 한다(§32 후속) |

**결정**: 단일 대안이 아니라 **단계적으로 쌓는다** — 각 대안이 서로 다른 문제(보안 vs 용량)를 풀기 때문에 하나만 골라서는 안 된다고 판단했다.

- **1단계(즉시, 코드 레벨)**: A(로그인 rate limit)를 **F의 정정된 형태로 구현** — NestJS 안이 아니라 **Cloudflare Worker를 api 앞단 엣지 프록시로 세워 거기서** 막는다(`cloudflare-worker/`). 이게 순수 A(앱 레벨 rate limit)보다 나은 이유: 스로틀링되고 있는 건 Render 컨테이너의 CPU인데, 앱 레벨에서 막으면 요청이 **이미 그 CPU를 조금이라도 쓴 뒤에** 거부된다 — 엣지에서 막으면 Render에 닿기도 전에 걸러진다. B(bcrypt cost)는 트레이드오프가 명확하지 않아 지금은 보류 — 필요해지면 재검토.
- **2단계(실DB 전환 시, 아키텍처 레벨)**: 이미 미뤄뒀던 "MockDataService → PrismaService 전환"(`log/` §29 "다음에 추가할 것")이 **이제 단순 영속성 문제가 아니라 D(수평 확장)의 전제조건이라는 새 근거를 얻었다.** 이 전환이 끝나야 Render 다중 인스턴스를 켜는 게 의미가 생긴다.
- **3단계(성장 시점, 인프라 레벨)**: 2단계가 끝난 뒤 C(유료 플랜)+D(다중 인스턴스)를 실제로 켠다. `design-constants.md` ⑨의 3년 후 추정(동시 진행 ≈38.4건, 장애 상황 기준)이 이 시점 판단의 근거가 된다.
- ~~선택(도메인 확보 시)~~ → 1단계로 앞당겨짐. 커스텀 도메인을 실제로 확보하면 Worker를 Zone Rate Limiting Rules(대시보드 WAF 규칙)로 한 단계 더 강화할 수 있다는 점만 향후 옵션으로 남겨둔다.

**타당성**: 높음 — 실측(k6) 없이는 "언젠가 문제가 될 수도" 수준의 막연한 우려였을 것을, Little's Law 재계산(⑦~⑨)으로 "왜 지연이 눈덩이처럼 불어나는가"까지 정량 설명했고, 대안을 "보안 문제"와 "용량 문제"로 명확히 분리해 뒤섞이지 않게 했다. 특히 D(수평 확장)이 현재 아키텍처(MockDataService)로는 애초에 불가능하다는 걸 짚어, 이미 미뤄뒀던 실DB 전환 결정에 "왜 지금 이게 중요한가"라는 새로운 근거를 부여했다 — 서로 다른 시점에 내려진 결정들이 이번 일로 연결된 사례다. F를 "도메인 필요"로 잘못 판단했던 것도 같은 날 바로 잡혔다 — 사용자가 "Cloudflare Pages로 넘기면 도메인 문제도 해결되지 않나"라고 되물은 게 계기였다(§32 후속).

**감수하는 것**: Worker 프록시가 실제로 배포되기 전까지는 "결정만 나고 구현 전" 상태다. 또한 Worker 자체가 하나의 새 실패 지점(single point of failure)이 된다 — Worker가 장애나면 api 전체가 막힌다. 2·3단계(무상태화·수평확장)가 실제로 구현되기 전까지는 §31/D14의 "위험 확인됨" 상태를 유지한다.

**완료(2026-09-27)**: 사용자가 로컬에서 `wrangler deploy`로 배포 성공(`https://sports-erp-api-gateway.01-beauty-minimal.workers.dev`) — `unsafe.bindings` 문법이 실제로 맞았다(에러 없이 한 번에 배포됨). admin-web의 `VITE_API_BASE_URL`을 이 URL로 갱신해 Render 재배포까지 완료(`status: live`). **문제 발견**: 이 상태에서 사용자가 로그인 실패·새로고침 404를 보고했다 — admin-web(Render)과 Worker(workers.dev)가 서로 다른 오리진이 되면서 생긴 문제로 추정됐고, 이게 [D25](#d25-admin-web을-cloudflare-worker-정적-자산으로-통합render-static-site-폐기)로 이어졌다.
