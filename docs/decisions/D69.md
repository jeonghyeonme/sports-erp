# D69. 위탁계약 회차와 계약서 파일 — OCR·AI 없이 본사가 계약서를 보고 직접 입력, 종료 확정은 해지 합의서로 (2026-10-31)

> 결정 기록 [인덱스](README.md) · 경위는 [log/191](../log/191.md)

**대체**: [D67](D67.md) 결정 3의 ②(계약서 OCR·AI 분석 적용 검토)를 "적용하지 않음"으로 대체하고, [D68](D68.md)의 "계약 이력은 AuditLog로, 스키마 변경 없이"를 계약 회차 테이블로 대체한다(갱신·정정·상태 변경을 변경 이력에 같은 트랜잭션으로 남기는 원칙은 유지). [차별화전략](../reference/차별화전략.md) §1-1은 기각.

**컨텍스트**: D68로 계약 갱신·정정·지점 등록은 생겼지만 계약서 원본이 시스템에 없고, 계약 정보는 지점 행에 한 벌뿐이라 지난 계약이 무엇이었는지는 이력 JSON으로만 짐작한다. 문서 관리의 `CONTRACT` 분류는 파일 주소 문자열만 받았다(자원문서관리 A-8 — 실제 업로드 범위 제외).

**목표**(사용자, 2026-10-31): 운영 확실성과 효율. 계약서는 지점당 하나, 몇 년에 한 번 갱신, 입력 칸은 셋이라 OCR·AI로 줄일 입력 부담이 작고, 자동 추출은 검토를 대충 하게 만드는 위험과 외부 전송 문제를 더한다.

**결정**(사용자, 2026-10-31):
1. **OCR·AI는 넣지 않는다.** 본사가 계약서를 올리고, 그것을 보면서 계약 정보를 직접 입력한다.
2. **계약 회차** — 지점마다 회차 번호(1, 2, 3…)를 매기고 회차마다 상대방·시작일·종료일·계약서를 따로 저장한다. 지점에 보이는 계약 정보는 가장 최근 회차다. 지점(Branch) 행의 계약 칸(상대방·시작일·종료일)은 없앤다 — 데이터 중복을 피한다. 계약 상태는 지점에 남는다.
3. **갱신은 새 계약서가 있어야** 새 회차로 생긴다. 기간은 계약서를 보고 직접 넣는다. **종료일은 필수**(상시 계약 없음).
4. **정정·파일 교체는 진행 중인 회차만.** 지난 회차는 읽기만 한다. 계약 파일을 지우는 경로는 없다(교체만).
5. **종료 확정은 해지 합의서가 있어야** 한다(중도 해지 포함, 기간 경과 여부는 보지 않는다). 해지 합의서는 확정 전에 올린다 — 확정 뒤에는 그 지점에 올리지 못한다(ADR-RES-01과 같은 태도). 종료일이 지나도 상태를 자동으로 바꾸지 않고 "기간 종료(N일 경과)"로 표시만 한다.
6. **권한·노출** — 올리기·교체·정정·갱신·종료 확정은 본사만. 지점 관리자는 자기 지점 계약서 열람만. 계약 파일은 계약 화면에서만 다룬다 — 문서 관리에서 계약서 분류를 없앤다.
7. **보존** — 회차가 끝난 날(종료일, 해지로 끝나면 해지 확정일)부터 시스템에 3년, 그 뒤 실물로 7년. 본사가 알림을 받고 [실물 이관 완료]를 누르면 시스템 파일을 지우고 회차에 이관 기록을 남긴다(교체된 옛 파일도 같은 규칙). 사람이 지우는 경로는 이것뿐이다. — **2차 구현**
8. **보안 추가** — 계약서 열람 기록(누가 언제 열었나, D47 방식). 저장 경로는 계약 전용으로 분리, 다운로드 URL은 60초.
9. **문서 관리 실제 파일 업로드**(인사서류·매뉴얼·기타, A-8 범위 제외 해제) — **2차 구현**.

**구조**(결정 2·4·7에서 따라 나옴): `ContractRound`(지점·회차 번호 유일, 상대방·시작일·종료일 필수, 해지 확정일) + `ContractFile`(회차·종류 = 계약서/해지 합의서, 교체되면 교체 시각을 남기고 새 행). 파일을 문서(Document) 테이블에 두는 안은 접근 경로를 최소로 하라는 결정 6과 맞지 않아 택하지 않았다(문서 목록·조회·삭제 API마다 계약 분류를 빼는 조건을 지켜야 한다).

**결과**: 좋아진 것 — 회차별 계약 원본과 값이 한 곳에 남고, 지난 회차가 바뀌지 않는다. 종료 확정에 근거 문서가 붙는다. 감수하는 것 — 지점의 계약 칸을 읽던 곳(대시보드·지점 상세·시드·테스트)이 모두 회차를 읽도록 바뀐다. 기존 지점은 1회차에 계약서가 없어 "계약서 미등록"으로 보이고, 본사가 화면에서 올려 채운다(시드 저장소가 로컬에선 메모리라 샘플 파일을 미리 넣을 수 없다). 배포 DB는 마이그레이션(계약 칸 이전·삭제, 계약서 문서 행 삭제)을 따로 적용해야 하고, 이는 실행 전에 승인받는다.

**재고 트리거**: 계약서 외 문서도 상태 전이의 근거가 될 때, 실운영 계획이 생겨 계약서 입력량이 크게 늘 때(OCR 재검토), 보존기한 자동 처리용 스케줄러가 생길 때.
