# D35. 남은 mock 도메인 3번째 — 자산(자원문서관리의 나머지 절반)을 DB로 옮긴다

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: 문서(D34) 다음은 자산이다. 자산을 옮기면 게시판 하나만 mock에 남는다. 자산에는 다른 도메인이 읽는 데이터가 없어서 미러를 둘 곳이 없다. 옮길 데이터는 서초점 시드 자산 3건이다. 이 도메인에서 단일 스레드 가정에 기대던 규칙은 두 가지다.
- **자산번호 채번**: `{지점코드}-A{순번}`을 "같은 prefix 자산 수 + 1"로 뽑는다(RES-T04). 이 문제는 이미 "실DB 전환 시 트랜잭션+락"으로 결론이 나 있었다.
- **상태 전이 검사**: 읽은 상태로 전이를 검사한 뒤 쓴다. 두 요청이 같은 이전 상태를 읽으면 둘 다 통과한다.

**결정 1 — 자산 원천을 DB로 옮기고, 채번은 D28 헬퍼로(RES-T04, data-integrity §6 체크리스트 첫 줄)**:
- 채번: `allocateBranchCode(ASSET)`가 `CodeSequence`의 `{지점코드}-A` 행을 원자적으로 올린다. 폐기된 자산도 순번을 계속 차지한다는 규칙("재사용 안 함")은 시퀀스가 증가만 하므로 그대로 성립한다. 시드는 그 prefix의 최대 순번으로 시퀀스를 초기화한다. D28 §5가 발견한 "시드 번호와 첫 채번 충돌"을 막기 위해서다.
- 그대로 두는 규칙: 자동 판정(100만원 초과는 고정자산, 자원문서관리 A-6, RES-T01), 고정자산 수량 1(RES-T03, D28 CHECK로 이중화), 상태 전이표(§4-4·§4-8, RES-T02), 검사 순서(지점 없음 → 계약 종료, ADR-RES-01).
- 지점 이름은 조인으로 가져와 목록 N+1을 없앤다(traffic-infra-review 자원문서관리 항목의 자산 절반).

**결정 2 — 상태 전이는 "읽은 상태 그대로일 때만" 갱신한다(D31 프로그램 상태 전이와 같은 방식)**: 전이표 검사는 앱에서 한다. 쓰기는 `updateMany where { id, status: 읽은 상태 }`로 해서, 그 사이 다른 요청이 상태를 바꿨으면 0건이 된다. 이 경우 `INVALID_STATUS_TRANSITION` 409로 돌려준다. 폐기됨(DISPOSED)은 종결 상태라, 동시에 두 전이가 와도 폐기된 자산이 되살아나지 않는다.

**감수하는 것**:
- 폐기 자산이 목록에 계속 쌓이는 문제(traffic-infra-review "무한 누적")는 이번에 다루지 않는다. 페이지네이션이나 보관(아카이빙)은 화면 설계와 함께 정할 일이다. 지금 규모(지점당 수 건)에서는 급하지 않다.
- 기본 정보 수정(`PATCH /assets/:id`)은 여전히 "읽고 검사한 뒤 쓴다". 고정자산 수량이 1이 아니게 되는 경합은 D28 CHECK가 최종 방어선이다. 위반하면 앱 검사가 먼저 막아야 정상이고, 경합일 때만 DB가 거부한다.
- 시드 자산 3건과 ASSET 시퀀스는 사용자 승인 후 머지 전에 Supabase에 함께 적용했다(2026-09-29, 지문 로컬과 동일 — docs/log/049). 둘은 반드시 함께 넣는다.
