# D26. MockDataService→PrismaService 전환 1단계 — 스키마 동기화 + 인증 모듈 이관

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: 사용자가 "API도 깔끔하게 관리하고 싶다, 굳이 Render에 둘 이유 없다, 서로 다른 인프라에 분산할 필요 없다"며 api를 AWS로 옮기고 싶어 했다. AWS의 영구 무료(Always Free) 컴퓨트는 사실상 Lambda뿐인데(EC2는 12개월만, App Runner는 애초에 무료 티어 없음), Lambda는 요청마다 여러 실행 인스턴스가 병렬로 뜰 수 있어 지금의 인메모리 `MockDataService`와 근본적으로 안 맞는다 — 동시 인스턴스마다 서로 다른 mock 데이터를 들고 있게 돼, "방금 등록한 회원으로 로그인하면 안 보임" 같은 데이터 정합성 버그가 난다(D24의 대안 D가 이미 짚었던 문제의 재현). 사용자가 DynamoDB(진짜 Always Free)로 이 문제를 풀 수 있는지 물었고, 맞는 방향이지만 이미 27개 모델·관계형 설계(D2 branchId 격리, D6 `FOR UPDATE` 트랜잭션 락, D9 소프트 삭제)로 Supabase에 배포까지 끝난 Prisma 스키마를 버리는 더 큰 결정이라 판단해, "Postgres/Prisma는 그대로 쓰고 Lambda로 호스팅만 옮기자"로 합의했다. 그러려면 먼저 상태가 외부 공유 저장소(Postgres)에 있어야 하므로 — 이게 D24가 이미 "2단계"로 예고해뒀던 MockDataService→PrismaService 전환이다.

**이번 범위를 왜 좁혔나**: 조사해보니 17개 컨트롤러가 `MockDataService`를 직접 주입(서비스 레이어 없음)하고, 비즈니스 로직이 컨트롤러가 아니라 2,288줄 `mock-data.service.ts` 메서드 안에 있으며, 테스트 18개 파일 전부가 인메모리 배열을 직접 조작해 픽스처를 만든다 — 한 세션에 전부 옮기면 검증 없이 너무 많은 게 바뀐다. 그래서 **기반 공사(스키마 동기화 + 가장 트래픽이 높고 위험한 인증 모듈)까지만** 이번에 하고, 나머지 16개 도메인은 도메인 사이클 방식으로 하나씩 옮기기로 했다(플랜은 `/root/.claude/plans/polymorphic-juggling-parnas.md`에 남아 있음 — 대화 중 조사·설계·승인 과정을 그대로 기록).

**한 일 — 스키마 동기화**: `schema.prisma`를 mock 실제 동작과 맞췄다 — `EnrollmentStatus` enum 값 교체(`EXPIRED`→`COMPLETED`/`CANCELLED`, mock이 진짜 동작이므로), `Staff.offDays`·`AttendanceRecord.branchId`·`Member.guardianConsent`·`Payment.supplyAmount/vat`·`Facility.currentCount/level/lastUpdatedAt` 추가, `Asset`/`Document` 모델 신설(1-10 자원문서관리, 스키마에 아예 없었음). 구현 도중 스키마 조사에서도 놓쳤던 진짜 갭을 하나 더 발견했다 — `Account.name`이 스키마에 없는데 SUPER_ADMIN은 Staff/Member 프로필이 없어 이름을 저장할 곳이 없었다(auth 포팅 중 `toRequestUser`를 구현하다가 발견). 바로 추가해 고쳤다. 마이그레이션은 로컬 Postgres에 `prisma migrate dev`로 만들고(`apps/api/prisma/migrations/`, 이제 저장소에 정식 이력으로 남는다), Supabase에는 이 세션이 Postgres 포트에 직접 못 붙는 제약(D23/§29와 동일) 때문에 SQL diff를 뽑아 Supabase MCP `apply_migration`으로 적용했다 — Asset/Document 신규 테이블에 RLS도 나머지 27개와 같은 기준(정책 없이 RLS만 켜서 PostgREST 차단)으로 맞췄다.

**한 일 — 인증 모듈 이관, 그리고 "과도기 이중 경로"라는 진짜 설계 결정**: `AuthService`(login/refresh/logout/changePassword)와 `JwtStrategy`를 `PrismaService` 기반으로 다시 짰다. 처음엔 순수하게 Prisma만 보게 만들었는데, 실제 테스트 스위트(18개 파일)를 돌려보니 **116개 테스트가 한꺼번에 깨졌다** — `/auth/login`이 모든 도메인이 공유하는 단일 진입점인데, 아직 mock인 16개 도메인의 테스트들도 전부 이 엔드포인트로 로그인하기 때문이다. 그래서 `login`/`refresh`/`logout`/`changePassword`/`JwtStrategy.validate`를 전부 **"Prisma에서 먼저 찾고, 없으면 mock으로 폴백"하는 이중 경로**로 다시 설계했다 — 두 저장소는 ID 체계가 겹치지 않아(Prisma UUID vs mock의 `'account-xxx'` 문자열) 폴백이 안전하다. 이 폴백 덕분에 아직 이관 안 된 도메인들의 테스트가 전부 그대로 통과했다(248/252, 아래 "감수하는 것" 참고). 도메인이 하나씩 이관될 때마다 그 도메인의 mock 폴백을 지워나가고, 전부 끝나면 이 파일에서 mockData 의존성 자체를 없앤다 — 이 계획을 코드 주석에도 명시해뒀다.

**한 일 — 두 저장소에 걸친 "같은 사람" ID를 맞춤**: 정하늘·김민수·박서연·이수진 4명은 mock 시드에도, 새 Prisma 시드에도 같은 이메일로 존재하는 "과도기 공유 계정"이다. 처음엔 Prisma 쪽에 무작위 UUID로 시드했는데, 이러면 Prisma로 로그인한 요청의 `req.user.staffId`가 mock 컨트롤러 입장에선 존재하지 않는 ID라 `STAFF_NOT_FOUND` 같은 에러가 났다(branch-isolation.spec.ts 전체가 이렇게 깨지는 걸 실제로 겪었다). `mock-data.service.ts`의 정확한 ID(`account-minsu`, `staff-seoyeon` 등)를 그대로 Prisma 시드에도 써서 해결 — 이제 Prisma가 로그인을 처리해도 `req.user`의 값이 mock 컨트롤러가 기대하는 ID와 일치한다.

**한 일 — CI가 조용히 깨질 뻔한 것을 미리 잡음**: `PrismaModule`이 앱 부팅 시 `$connect()`를 시도하게 되면서, `.github/workflows/ci.yml`에 Postgres 서비스가 전혀 없다는 게 드러났다(지금까지 api 테스트는 DB 없이 돌아간다고 CLAUDE.md에도 적혀 있었다 — 이제 틀린 설명이라 같이 고쳤다). CI job에 `postgres:16-alpine` 서비스 컨테이너(docker-compose.yml과 동일 이미지·자격증명)를 추가하고, `prisma migrate deploy`(비대화형, 이미 만든 migrations/ 그대로 적용) → `prisma:seed` → 테스트 순서로 스텝을 넣었다. 실제로 로컬에 완전히 새 DB를 만들어 이 순서(`migrate deploy` → `seed` → `jest`)를 그대로 재현해보고 통과를 확인한 뒤에 커밋했다 — 이 부분을 검증 없이 넘겼으면 이 커밋이 푸시되는 순간 CI 전체가 빨간불이 됐을 것이다.

**타당성**: 높음 — 계획(스키마 조사 2개 서브에이전트 병렬 조사 → Plan 파일 작성 → 사용자 승인)부터 구현까지 architecture-driver 방법론을 그대로 따랐고, 무엇보다 **실제로 로컬 Postgres를 띄워 진짜 DB 위에서 로그인·토큰갱신(1회용 rotate)·비밀번호변경·§6의 "역할변경 즉시반영" 불변식까지 수동 curl로 하나하나 확인했다** — 타입만 맞춰놓고 "될 것 같다"로 끝내지 않았다. 과정에서 나온 진짜 발견 3개(Account.name 스키마 갭, ID 불일치로 인한 mock 도메인 붕괴, CI Postgres 부재)를 전부 사전에 잡아낸 것 자체가, "빌드만 통과하면 끝"이 아니라 "실행해서 확인한다"는 이 프로젝트 검증 원칙이 실제로 작동했다는 증거다.

**감수하는 것**: ① 이중 경로(Prisma-우선/mock-폴백)는 명백히 임시 설계다 — 코드에 mock 의존성이 여전히 남아 있고, 도메인이 하나씩 이관되기 전까지는 지워지지 않는다. ② `auth-lifecycle.spec.ts` 2건·`staff-assignment.spec.ts` 1건을 `it.skip`으로 남겼다 — 퇴사·Role전환이 아직 mock 도메인이라 Prisma Account에 반영 안 되는, 정확히 진단되고 문서화된 과도기 한계다(기대값을 바꾼 게 아니라 도메인 이관 전까지 "검증 보류"로만 남김, `docs/domains/권한관리.md` §11 갱신). ③ Supabase 쪽은 `prisma migrate deploy`가 아니라 MCP `apply_migration`(원본 SQL)으로 적용했다 — Supabase의 `_prisma_migrations` 이력 테이블엔 이번 마이그레이션들이 기록되지 않는다(이 세션이 Postgres 포트에 직접 못 붙는 구조적 제약, D23부터 있던 문제). 로컬 migrations/ 폴더가 감사·재현용 단일 진실 공급원이고, Supabase는 "같은 DDL을 다른 경로로 적용받은 거울"이라는 걸 다음에 이 프로젝트를 만지는 사람이 알아야 한다. ④ CI에 Postgres 서비스 컨테이너가 추가돼 빌드 시간이 조금 늘었다(허용 범위).

**다음 작업**: 회원관리 도메인부터 순서대로 이관(컨트롤러 인라인 `mockData.filter()` 패턴과 `createReservation`류의 `SELECT ... FOR UPDATE` 동시성 코드를 처음 겪게 될 도메인). 전 도메인 이관이 끝나면 AWS Lambda 호스팅 논의를 재개(D24 3단계와 자연스럽게 연결) — **재개할 때 반드시 설계해야 할 것(2026-09-28, 4주차 발표 준비 중 대화에서 드러난 문서화 공백)**: 이전까지는 "무상태화만 되면 Lambda로 옮긴다"로만 적혀 있었는데, 실제로는 인프라 부하 관점에서 최소 4가지를 더 설계해야 한다 — ① **Lambda 메모리(=CPU) 사이징**: `bcrypt.compare`가 CPU 바운드라 메모리를 너무 적게 주면 스로틀링 대신 "그냥 CPU가 적어서" 느려진다. ② **DB 커넥션 풀링**: 동시 Lambda 실행 환경마다 Postgres 커넥션을 열면 커넥션이 고갈될 수 있어, Supabase Supavisor(세션/트랜잭션 풀러, `pgbouncer=true`)를 반드시 붙여야 한다 — 안 붙이면 병목이 "CPU 경합"에서 "DB 커넥션 경합"으로 옮겨갈 뿐 사라지지 않는다. ③ **Lambda 동시 실행 한도**: 계정 리전별 concurrency 한도가 있어 순간 피크 시 처리량 상한이 된다. ④ **콜드스타트**: Prisma 쿼리 엔진 바이너리 로딩 때문에 유휴 후 첫 요청이 1~3초 걸릴 수 있어 `binaryTargets` 설정과 Provisioned Concurrency 필요 여부를 판단해야 한다. 이 네 가지가 빠진 채로 "Lambda로 옮기면 끝"이라고 설계하면 스로틀링 문제가 다른 형태로 재발한다.
