## D1. RBAC 4-Role 고정 (개별 권한 커스터마이징 미지원)

> **지난 결정** — D60(세부 권한)이 대체.

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: 원본 요구사항의 "사용자별·프로그램별 세부 권한(입력/수정/삭제/조회/출력)"을 개별 ACL로 구현하지 않고, `SUPER_ADMIN / BRANCH_ADMIN / STAFF / MEMBER` 4개 고정 Role 기반 RBAC로 단순화했다. ([권한관리 문서](../domains/권한관리.md) §1)

**쉽게 말하면**: 직원 개개인한테 맞춤 권한을 하나하나 설정해주는 대신, "본사 관리자/지점 관리자/일반 직원/회원" 4개짜리 완성된 직급표를 만들어두고 그중 하나를 배정하는 방식입니다.

**근거**: 세밀한 개별 권한 부여(ACL) 시스템은 권한 관리 UI, 권한-리소스 매트릭스 저장 구조, 권한 변경 이력까지 요구하는 별도의 서브시스템이다. 1인 개발 리소스로는 이걸 만드는 데 들이는 공수가 실제 심사/시연 가치에 비해 과도하다. 반면 원본 요구사항의 실질적 핵심(요구사항 5번 "타현장 정보 조회 불가능")은 지점 간 격리이지, 개인별 세부 CRUD 권한이 아니다.

**타당성**: 높음. 대부분의 실서비스 ERP도 초기 단계에서는 Role 기반으로 시작해 필요할 때 ACL로 확장한다. 요구사항의 "본질"과 "표면 형태"를 구분해 본질(지점 격리, 퇴사 즉시 차단, 관리자/일반직원 분리)에 공수를 집중한 것은 합리적인 스코프 조정이다.

**장점**
- 구현·테스트가 단순해 Phase 1 내에 완성 가능(4개 Role × Guard 데코레이터 조합만 검증하면 됨)
- 문서화가 쉬워 심사 발표에서 권한 매트릭스 표 하나로 전체를 설명 가능
- Guard 로직이 예측 가능해 보안 버그 표면적이 작음

**단점·리스크**
- 실제 조직에는 "이 지점 관리자에게는 결제 조회만 주고 회원 수정은 막고 싶다" 같은 요구가 생길 수 있는데, 이 구조로는 Role을 새로 만들거나 예외 로직을 하드코딩해야 함
- Role이 늘어날수록(이미 4→ 늘리기 어려운 게 아니라, STAFF 추가 사례(D12)처럼 실제로 한 번 늘어났음) 권한 매트릭스 표가 커지고 Guard 조건 분기가 늘어남

**대안 및 미채택 사유**: 리소스별 Permission 테이블 + Role-Permission 매핑(RBAC2)은 이론적으로 더 유연하지만, 이 프로젝트 규모에서는 오버엔지니어링이라고 판단해 채택하지 않음.

## D6. 예약 동시성 제어: 트랜잭션 내 `SELECT ... FOR UPDATE`

> **지난 결정** — 예약및결제 ADR-RSV-01(회차 행 락)이 대체.

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: `ScheduleSlot.bookedCount`를 캐시 필드로 별도 관리하지 않고, 예약 생성 시 트랜잭션 내에서 락을 건 뒤 `capacity`와 비교해 정원 초과를 막는다. ([예약및결제 문서](../domains/예약및결제.md) §6)

**쉽게 말하면**: 마지막 한 자리를 두 사람이 동시에 예약하려 하면, 한 명씩 차례로 확인하게 만들어서 정원이 초과되는 사고를 막습니다 — 좁은 문에 한 번에 한 명씩만 들어가게 하는 것과 같습니다.

**근거**: 캐시 카운터(`bookedCount` 컬럼을 두고 예약/취소마다 증감) 방식은 갱신 순서가 꼬이면(예: 동시 취소+예약) 실제 예약 건수와 캐시 값이 어긋날 위험이 있다. 실제 테이블을 매번 세는 방식이 정합성 면에서 더 안전하다.

**타당성 — 2026-09-15 정정**: 원래 여기 "실제로 정합성이 보장되는 올바른 구현이라 어필이 과장이 아니다"라고 적었는데, **이 자평 자체가 틀렸었습니다.** 원래 설계인 `SELECT COUNT(*) FROM Reservation ... FOR UPDATE`는 **기존에 존재하는 Reservation 행에만** 락을 겁니다 — 정원에 여유가 있어 기존 예약이 적거나 0건일 때는 잠글 대상이 없어, 두 트랜잭션이 동시에 통과해 정원을 초과하는 팬텀 삽입이 그대로 발생할 수 있었습니다. `FOR UPDATE`라는 키워드를 썼다는 사실과 "실제로 동시성이 안전하다"는 것은 다른 문제인데, 이 둘을 구분하지 못하고 "키워드가 있으니 안전하다"고 self-assess한 것이 이 항목의 실수였습니다. 수정된 설계는 `ScheduleSlot` 행 자체를 먼저 `SELECT ... FOR UPDATE`로 잠급니다(회차 행은 예약 건수와 무관하게 항상 존재하므로 반드시 잠금 대상이 있음) — 이렇게 "카운트할 대상"이 아니라 "정원이 걸려있는 리소스 자체"를 잠가야 동시성이 실제로 안전해집니다. 지금은 이 정정된 설계 기준으로 타당성이 높다고 평가합니다.

**장점**
- 캐시 필드를 두지 않아 "캐시와 실제 값의 불일치"라는 클래스의 버그가 원천적으로 발생하지 않음
- Postgres의 행 락 메커니즘을 그대로 활용해 애플리케이션 레벨의 분산 락(Redis 등) 같은 추가 인프라 없이 구현 가능

**단점·리스크**
- 트랜잭션이 길어지거나(예: 결제 승인까지 한 트랜잭션에 묶으면) 락 보유 시간이 늘어나 데드락/타임아웃 위험이 커짐 — 예약및결제 문서의 흐름(예약 생성 → 별도 API로 결제 승인)처럼 트랜잭션을 짧게 끊어가는 설계가 유지되어야 함
- 트래픽이 실제로 매우 커지는 상황(다지점 대규모 서비스)에서는 특정 인기 슬롯에 요청이 몰릴 때 락 대기열이 병목이 될 수 있음 — 다만 이는 이 프로젝트의 스코프를 벗어나는 가정임

**대안 및 미채택 사유**: 낙관적 락(버전 컬럼 + 재시도)도 검토 가능했으나, 재시도 로직이 클라이언트/서버 양쪽에 필요해 구현 복잡도가 늘고, 예약처럼 "실패 시 즉시 사용자에게 정원마감을 알려도 되는" 도메인에서는 비관적 락(FOR UPDATE)이 더 단순하고 적합하다고 판단.

**구현 메모(2026-09-18)**: 현재 `MockDataService`는 Postgres가 아니라 단일 Node 프로세스에서 동기적으로 실행되는 인메모리 배열이다. `createReservation` 메서드 안에는 정원 체크(`bookedCount` 계산)와 `INSERT`(배열 push) 사이에 `await`가 전혀 없으므로, 자바스크립트 이벤트 루프의 단일 스레드 특성이 사실상 `ScheduleSlot` 행 락과 동일한 효과를 낸다 — 두 요청이 동시에 도착해도 한쪽이 메서드 전체를 끝마칠 때까지 다른 쪽은 실행될 수 없다. 그래서 위에서 설명한 팬텀 삽입 시나리오가 지금 구조에서는 원천적으로 발생하지 않는다. 다만 이는 "우연히 안전한" 것이 아니라 "동기 코드라 안전한"것이므로, 실DB(Prisma/PostgreSQL) 전환 시에는 이 가정이 깨진다 — 그때는 위에서 정정한 대로 `ScheduleSlot` 행에 `SELECT ... FOR UPDATE`를 실제로 걸어야 한다.

## D14. 비기능요구사항(가용성/성능 수치)을 설계 원칙으로 대체

> **지난 결정** — 실측(D42·D50)으로 대체된 초기 원칙.

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: 원본 요구사항의 "CPU 90% 이하", "메모리 85% 이하" 같은 인프라 실측 목표를 포트폴리오 규모에서는 의미가 없다고 보고, 페이지네이션/인덱싱/AuditLog/입력 검증 같은 설계 원칙으로 대체했다. ([architecture/entities.md](../architecture/system-overview.md) §5)

**쉽게 말하면**: "서버가 초당 몇 명을 버텨야 한다" 같은 실측 수치 목표 대신, "목록을 나눠서 보여주기", "검색 속도를 높이는 색인 만들기", "누가 뭘 바꿨는지 기록 남기기"처럼 실제로 지킬 수 있고 확인 가능한 설계 원칙으로 목표를 바꿔치기했습니다.

**근거**: 실측 인프라 지표는 실제 트래픽과 모니터링 인프라(Prometheus/Grafana 등)가 있어야 의미를 갖는데, 로컬 Docker Compose 환경의 1인 개발 프로젝트에서 이런 수치를 재현하는 것 자체가 목적을 상실한 형식적 작업이 된다.

**타당성**: 높음. "원본 요구사항의 정신(안정적으로 동작하는 시스템을 설계할 줄 아는가)"을 "표면적 형태(수치 재현)"보다 우선시한 합리적 판단이며, 문서에 "발표에서는 확장을 고려한 설계로 어필"이라고 명시해 이 조정이 회피가 아니라 대체 전략임을 분명히 했다.

**장점**
- 페이지네이션 필수화, DB 인덱스 명시, AuditLog 등은 실제로 구현 가능하고 코드 리뷰에서 검증 가능한 항목들이라 "말로만 어필"이 아니라 "코드로 증명"할 수 있음

**단점·리스크**
- 이 대체표(architecture/system-overview.md §5)에 언급된 항목 중 일부(Redis 캐싱, 온라인 도움말 Toast/Modal 등)는 아직 각 기능 문서의 Phase 1/2 우선순위에 명시적으로 배치되지 않아, 실제 구현 단계에서 빠뜨리기 쉬움 — Phase별 체크리스트를 작성할 때 이 표의 항목들이 어느 Phase에 들어가는지 명시적으로 매핑해두는 것을 권장

**재검토(2026-09-27)**: "로컬 환경에서는 실측이 무의미하다"는 이 결정의 전제가 실제 배포(Render, `docs/log/` §30) 이후로는 더 이상 성립하지 않는다고 판단해, k6로 실측을 진행했다(`loadtest/k6-scenarios.js`). 결과는 이 결정을 뒤집을 만큼 흥미로운 걸 보여줬다 — 자세한 내용과 대응 방안은 `docs/log/` §31 참고. 요약: 로그인(bcrypt) 동시 요청이 Render 무료 티어의 공유 CPU에서 심각하게 스로틀링되어(p95 15초, 최대 17초) 사실상 손쉬운 DoS 벡터가 된다는 걸 실측으로 확인했다 — 이건 "설계 원칙으로 대체" 대상이 아니라 원본 요구사항 AUTH-T01(로그인 5회 실패 잠금, `docs/domains/권한관리.md`가 이미 Phase2로 분류해뒀던 것)이 실제로 필요한 이유를 실측이 뒷받침해준 사례다. 이 문서의 결론(가용성 수치를 설계 원칙으로 대체)은 "발표용 수치 재현"에는 여전히 유효하지만, "로그인 엔드포인트 남용 방지"는 수치 재현이 아니라 실제 보안 기능이 필요한 영역이라는 게 이번에 드러났다. 이 문제를 "보안 문제(rate limit)"와 "용량 문제(인프라 확장)"로 나눠 단계적으로 대응하기로 한 결정은 [D24](#d24-인증-경로-확장성-대응--부하테스트-실측-기반-단계적-로드맵)에 별도로 기록했다.

## D15. admin-web 디자인 토큰화 (Rounded Rectangle 기준)

> **지난 결정** — D19(고밀도 엔터프라이즈 톤)가 대체.

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: 별도 UI 프레임워크(Tailwind, MUI 등) 도입 없이 순수 CSS 커스텀 프로퍼티(`--radius-sm/md/lg/xl/pill`, `--color-*`, `--shadow-*`)로 디자인 토큰을 정의하고, 대시보드를 포함한 admin-web 전체 도형(카드/버튼/입력/뱃지/사이드바/네비게이션)을 Rounded Rectangle 계열로 통일했다. 대시보드는 KPI 요약 스트립(SUPER_ADMIN이 2개 지점 이상을 볼 때만 노출) + 지점별 통계 카드(아이콘 칩) 구조로 재작성했다.

**쉽게 말하면**: 화면 곳곳에 흩어져 있던 "둥근 정도·색깔·그림자" 값을 한 군데(디자인 변수)에 모아두고, 모든 버튼과 카드가 그 값을 그대로 따라 쓰게 만들어서 마치 한 사람이 한 번에 그린 것처럼 통일된 느낌을 냈습니다.

**근거**: 사용자가 "모던하고 깔끔한 디자인, 도형은 Rounded Rectangle 기준"이라고 방향을 명시했다(2026-09-05). 이미 순수 CSS(`styles.css` 단일 파일) 구조로 시작된 작은 프로젝트에 Tailwind 같은 빌드 의존성을 새로 얹는 것은 이 시점 규모에 비해 과한 비용이고, CSS 변수만으로도 전역 일관성이라는 목표를 충분히 달성할 수 있다고 판단했다.

**타당성**: 높음. 기존 `.card`, `.card-grid`, `table`, `.badge` 등 클래스를 그대로 재사용하면서 토큰(값)만 바꿨기 때문에, 회원/직원/프로그램/게시판/시설 페이지는 코드 수정 없이 새 톤을 자동으로 물려받았다(브라우저로 각 페이지 확인 완료).

**장점**
- 새 디자인을 적용하기 위해 손댄 페이지는 대시보드뿐이지만, 변수를 참조하는 다른 모든 페이지가 함께 갱신됨(변경 지점 최소화)
- 라이브러리 학습·의존성 비용 없이 "일관된 디자인 시스템이 있다"는 인상을 심사에서 어필 가능

**단점·리스크**
- 정식 디자인 시스템(컴포넌트 라이브러리)이 아니라 CSS 클래스 집합이므로, 페이지 수가 크게 늘어나면 클래스명 중복·불일치가 생길 위험이 있음
- 다크 모드는 고려하지 않음(라이트 전용 토큰) — 이 프로젝트 스코프상 우선순위는 낮다고 판단

**대안 및 미채택 사유**: Tailwind CSS 도입도 검토했으나, 이미 순수 CSS로 시작된 작은 코드베이스에 새 빌드 파이프라인을 추가하는 비용이 이 시점의 이득(유틸리티 클래스 생산성)보다 크다고 보아 채택하지 않음.

## D21. 98개 지점 규모 mock 데이터 + 대시보드 테이블화·검색/필터·접이식 그룹핑

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: architecture/system-overview.md §1-1이 인용하는 원본 RFP 수치("전국 98개 업장")를 실제로 mock 데이터에 반영했다 — 서초점·강남점(히어로 지점, 데모 로그인 계정이 물려 있음) 외에 96개 지점을 `apps/api/src/mock-data/branch-generator.ts`가 인덱스 기반으로 결정적으로 생성한다(계약상태 분포는 ACTIVE 81/RENEWAL_DUE 10/EXPIRED 4/TERMINATED 3, 합계 98). 이 규모에서 실제로 스캔 가능한지 검증하기 위해 화면 3곳을 같이 바꿨다: ① 대시보드의 지점 카드 그리드 → 검색·상태필터·위험도 우선 정렬이 있는 테이블(SUPER_ADMIN만, BRANCH_ADMIN 단일 지점 뷰는 기존 카드 유지), ② 회원/직원/프로그램/시설·혼잡도 4개 지점 횡단 페이지 → 지점명 검색 + 기본 접힘 아코디언(`CollapsibleBranchSection`, 검색 결과 3개 이하면 자동 펼침), ③ 권한 관리 → 아코디언 대신 통합검색만 추가(이 화면은 "지점별로 훑어보기"가 아니라 "직원 한 명을 찾아 권한을 바꾸는" 단발 작업이라 목적이 다름).

**쉽게 말하면**: 지금까지는 지점이 2개뿐이라 카드 나열이나 표를 쭉 펼쳐두는 방식이 자연스러웠는데, 실제 스포이즘 규모(98개 업장)로 채워보니 그 방식이 그대로는 무너집니다. 그래서 대시보드는 카드 대신 검색·필터·정렬되는 표로, 나머지 목록 화면들은 지점명을 검색해야 펼쳐지는 접이식 목록으로 바꿨습니다 — "조치가 필요한 지점"(계약 만료·갱신임박)이 항상 표 맨 위에 뜨는 것도 이번에 추가됐습니다.

**근거**: 밀도 레퍼런스(Mindbody Business 등)를 확정한 직후, 사용자가 "원본 RFP 98개 지점 규모를 고려해서 많은 양의 데이터를 접근하기 쉽게 정리해달라"고 명시적으로 요구했다(2026-09-09). 지점이 2개일 때 통했던 카드 그리드·flat 아코디언 나열은 98개에서는 "카드 98장 무한 스크롤"·"펼쳐진 표 98개가 한 페이지에 쌓임"이 되어 오히려 밀도/스캔성 요구와 정반대 결과를 낳는다 — 즉 이번 결정은 D19(밀도)·D20(IA)의 연장선에서, "실제 데이터 규모"라는 세 번째 축을 반영한 것이다.

**타당성**: 높음 — mock 데이터를 `Math.random` 없이 인덱스 기반으로 결정적 생성해 서버를 재기동해도 계약상태 분포·지점 수가 항상 동일하게 재현되는 것을 API 응답(`curl`)과 브라우저 양쪽에서 확인했다. 대시보드 위험도 우선 정렬(만료→갱신임박→정상→종료), 상태필터 4종, "계약 갱신 임박" KPI 클릭 시 필터 자동 적용, 지점 검색 3개 이하 자동 펼침까지 Claude-in-Chrome으로 실제 클릭해 동작을 검증했다.

**장점**
- `groupByBranch`([D20](#d20-대시보드-우선순위-재편--위탁계약-필드-도입--지점-기준-정보구조ia))와 `BranchDetailPage`의 기존 아코디언 패턴(`staff-row`/`chevron`)을 그대로 재사용해(`CollapsibleBranchSection`) 새 CSS·새 상호작용 패턴을 거의 안 만듦

**대안 및 미채택 사유**: `contractStatus`를 배치(크론)로 매일 재계산하는 방식도 검토했으나, 아직 크론 자체가 없는 단계라 mock 시드에 인덱스 기준으로 직접 배정하는 쪽이 훨씬 단순하면서도 화면 검증 목적(분포가 실제로 보이는가)은 동일하게 달성한다고 판단했다. 지점 횡단 4개 페이지도 대시보드처럼 전부 테이블+필터로 바꾸는 방안이 있었으나, "지점별 구성을 훑어본다"는 그 페이지들의 원래 목적(D20)에는 접이식 그룹핑이 더 맞다고 보아 대시보드만 테이블화했다.

## D22. `Branch.region` 필드 도입(대시보드 지역별 그룹핑) + 지점 상세 "계약 정보" 섹션(OCR 전제 명시)

> **지난 결정** — 계약 정보는 D69(계약 회차), OCR은 제외(D69).

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: 두 가지를 이어서 추가했다. ① `Branch`에 `region`(광역 단위, 예: "서울"·"경기") 필드를 신설해 대시보드 지점 테이블을 지역별 접이식 섹션(서울/경기/부산/대구/인천/광주/대전/울산)으로 다시 묶었다 — `address`(상세 주소, 자유 텍스트)와 별개로 그룹핑 전용 정규화 필드다. ② `BranchDetailPage`에 그동안 비어 있던 "계약 정보" 섹션(계약 상대방·계약 기간·계약 상태·잔여일수)을 추가하고, 이 필드들이 궁극적으로는 계약서 스캔본 OCR·AI 자동 추출([차별화전략 §1-1](../reference/차별화전략.md#1-1-계약서-ocrai-분석-2026-09-08-추가-스코프를-계약서-1종으로-한정))로 채워질 것을 전제로 설계됐다는 캡션을 명시적으로 붙였다(실제 OCR 기능 자체는 이번에 구현하지 않음 — 그 문서가 이미 Phase 2~3 스트레치로 분류해둔 범위 그대로).

**쉽게 말하면**: 대시보드에서 98개 지점을 볼 때 "서울/경기/부산..."처럼 지역으로 한 번 더 접어서 보여주고, 지점 상세 페이지에는 그동안 안 보이던 계약 정보(누구랑, 언제부터 언제까지, 며칠 남았는지)를 카드로 추가했습니다. 이 계약 정보는 나중에 계약서를 스캔해서 자동으로 채워 넣는 기능(OCR)을 이미 설계해둔 것을 전제로 만든 것이라, 그 사실을 화면에 짧은 문구로 남겨서 나중에 실제 OCR 기능을 붙일 때 "이 화면은 수기 입력용이 아니라 OCR 결과를 보여주는 화면"이라는 걸 잊지 않게 했습니다.

**근거**: 사용자가 지역별 그룹핑을 직접 요구했고(2026-09-09), 동시에 "계약 관련 내용은 계약서 OCR로 긁어온다는 걸 잊지 말라"고 명시적으로 짚었다. 차별화전략 §1-1은 이미 이 기능을 "위탁계약 필드는 지금 설계상 관리자가 수기로 입력하는 것을 전제로 한다"는 갭을 인지하고 그 보완책으로 설계돼 있었는데, 정작 그 전제가 되는 "지점 상세 화면에 계약 정보 탭"(§1 본문)이 아직 구현 안 된 상태였다 — 이번 기회에 그 선행 조건을 채워 넣으면서, 화면 자체가 "OCR로 채워질 데이터를 보여주는 화면"이라는 맥락을 잃지 않도록 캡션을 남겼다.

**타당성**: 높음 — `region`은 D16·D20·D21과 같은 관례(Prisma 스키마 + mock 타입/서비스 + admin-web 타입 4계층 동시 갱신, architecture/entities.md §2-1 표에도 반영)를 그대로 따랐다. 지역 그룹핑은 대시보드에서 실제로 서울(71개)·경기(9개)·나머지 6개 광역시(각 3개)로 정확히 나뉘어 접히고, 검색·상태필터가 걸리면 해당 지역이 자동으로 펼쳐지는 것까지 브라우저로 확인했다. 계약 정보 섹션도 RENEWAL_DUE 지점에서 "17일 남음"처럼 잔여일수가 정확히 계산되는 것을 확인했다.

**장점**
- `CollapsibleBranchSection`(D21)을 그대로 재사용해 지역 그룹핑에도 새 컴포넌트를 안 만듦 — "지점명" 대신 "지역명"을 넘기는 것만으로 동작함
- `CONTRACT_STATUS_LABEL`/`CONTRACT_STATUS_RANK`를 `DashboardPage.tsx`에서 `apps/admin-web/src/lib/contract-status.ts`로 뽑아 `BranchDetailPage.tsx`와 공유하게 됨 — D20에서 대시보드에만 있던 로직이 두 화면에서 쓰이게 되며 자연스럽게 중복을 없앰

**단점·리스크**
- `region`을 96개 생성 지점의 `area`(구/시) 단위 배열에서 정적으로 매핑했다 — 서울이 21/30 지역을 차지해 지역별 분포가 고르지 않다(서울 71 vs 나머지 각 3~9). 실제 스포이즘 지점 분포와는 무관한 mock 편향이라, 나중에 실 데이터로 바뀌면 이 쏠림은 사라짐
- "계약 정보" 캡션은 OCR 기능이 실제로 없다는 것을 문구로만 알릴 뿐, 업로드 버튼 등 시각적 placeholder는 의도적으로 안 넣었다(동작 안 하는 버튼이 "고장난 UI"처럼 보이는 것을 피하기 위해) — Phase 2~3에서 실제 업로드 기능을 붙일 때 이 섹션을 다시 손봐야 함

**대안 및 미채택 사유**: 지역 코드를 시/도 표준 코드(예: 통계청 행정구역코드)로 정규화하는 방안도 있었으나, mock 데이터 단계에서는 과한 정확도라 사람이 읽는 한글 지역명 문자열로 충분하다고 판단했다. 계약 정보 섹션에 "계약서 업로드" 버튼을 비활성 상태로라도 넣는 안도 검토했으나, 클릭해도 아무 일도 안 일어나는 버튼은 오히려 완성도가 낮아 보인다고 판단해 텍스트 캡션으로만 의도를 남겼다.

## D23. 배포 인프라 — Render(admin-web + api) + Supabase(스키마 배포 완료, 앱 연결은 미착수)

> **지난 결정** — Render 배포 — D25·D37(Worker·Lambda)이 대체.

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정(2026-09-27 확정, 아래 "변경 이력" 참고)**: 두 서비스를 GitHub 연동(push 시 자동배포)으로 조합한다. ① `admin-web`(정적 SPA 빌드 결과물)과 ② `api`(NestJS 서버 프로세스) **둘 다 Render**에 올린다(`sports-erp-web` Static Site, `sports-erp-api` Web Service, 리전 Singapore, 둘 다 무료 티어). ③ PostgreSQL은 **Supabase**에 신규 프로젝트(`sports-erp`)를 만들어 Prisma 스키마(27개 테이블)를 배포해뒀지만, `apps/api`는 여전히 `MockDataService`로 동작 중이라 **아직 이 DB를 실제로 쓰지는 않는다**(`docs/log/` §29).

**쉽게 말하면**: 화면(admin-web)과 서버(api) 둘 다 Render 한 곳에 올리고, DB는 Supabase에 그릇만 미리 만들어뒀습니다(아직 요리는 안 담았습니다). 셋 다 GitHub 저장소만 연결해두면 `git push` 할 때마다 알아서 다시 배포되고, 지금은 아무것도 결제하지 않아도 됩니다.

**변경 이력 — 원래 계획(Cloudflare Pages + Render)에서 왜 바뀌었나**: 이 결정은 원래 "admin-web은 Cloudflare Pages, api는 Render"로 계획됐었다(계획 당시 근거는 아래 "근거"에 그대로 남겨둠). 그런데 2026-09-27 실제 배포 작업 중 **Claude에 연결된 "Cloudflare Developer Platform" MCP 커넥터가 Workers/KV/D1/R2/Hyperdrive용이고 Pages를 만들거나 관리하는 툴 자체가 없다**는 걸 실행 단계에서 발견했다(`migrate_pages_to_workers_guide`만 있음 — 오히려 Pages에서 Workers로 "떠나는" 법 안내뿐이었고, 이는 Cloudflare 자체가 Pages를 단종 방향으로 가져가고 있다는 신호로 보인다). Render의 `create_static_site` 툴은 실제로 서비스를 만들 수 있어서, 계획을 수정해 admin-web도 Render로 통합했다 — **"어느 게 이론적으로 더 나은가"가 아니라 "지금 가진 도구로 실제로 무엇을 만들 수 있는가"를 기준으로 계획을 현장에서 조정한 사례**로 남겨둔다.

**두 번째 변경(2026-09-27, 같은 날)**: 그런데 D24로 api 앞에 Cloudflare Worker(엣지 게이트웨이)가 새로 생기면서 admin-web(Render)·api 게이트웨이(Cloudflare)가 서로 다른 오리진이 됐고, 이게 로그인 실패·새로고침 404 버그로 이어졌다. **[D25](#d25-admin-web을-cloudflare-worker-정적-자산으로-통합render-static-site-폐기)에서 admin-web을 그 Worker의 정적 자산으로 다시 이관**해 이 문단을 사실상 대체한다 — 이 절의 "Render(admin-web+api)"는 역사적 기록으로 남겨두고, 현재 구성은 D25를 볼 것.

**근거(원 계획 당시)**: 현재 `apps/api`는 [app.module.ts](../../apps/api/src/app.module.ts) 주석대로 `PrismaModule` 대신 `MockDataModule`로 동작 중이라 부팅에 실제 DB 연결이 필요 없다 — 그래서 지금은 Render에 `DATABASE_URL` 없이도 그대로 띄울 수 있고, Supabase는 "나중에 실 DB로 이전"할 때를 위해 미리 정해만 두는 것이다. `main.ts`가 이미 `enableCors({ credentials: true })`로 열려 있고 인증은 쿠키가 아니라 `Authorization` 헤더 기반(`apps/admin-web/src/lib/api.ts`에 `withCredentials` 없음)이라, 웹과 API가 서로 다른 서브도메인이어도 추가 설정 없이 붙는다.

**타당성**: 중간 — 무료 티어 특유의 제약을 감수하는 선택이다. Render 무료 웹 서비스는 15분 미사용 시 슬립되고 재요청 시 약 1분 콜드스타트가 발생하며 월 750시간 한도가 있다([Render 문서](https://render.com/docs/free)). Supabase 무료 프로젝트는 7일간 활동이 없으면 자동 일시정지되어 수동으로 재개해야 한다. 포트폴리오 시연처럼 트래픽이 간헐적인 용도에는 이 제약이 큰 문제가 아니지만, **2026-09-27 k6 실측(`docs/log/` §31, [D24](#d24-인증-경로-확장성-대응--부하테스트-실측-기반-단계적-로드맵) 참고)에서 이 제약이 "느리다" 수준을 넘어 "40명 동시 로그인에 응답 15초"까지 악화되는 걸 직접 확인했다** — 타당성 평가를 "중간"으로 유지하되, 실측 전까지는 추측이었던 리스크가 지금은 계량화된 사실이 됐다.

**장점**
- 두 서비스 모두 카드 등록 없이 무료로 시작 가능해 "유지비용 없음" 조건을 만족한다
- 둘 다 GitHub 저장소 연결만으로 push 시 자동 재배포된다
- npm workspaces 구조를 그대로 활용해 두 서비스 모두 리포 루트에서 `npm install && npm run build --workspace=apps/<앱>` 패턴으로 빌드하므로 워크스페이스 호이스팅 문제 없이 별도 빌드 스크립트가 필요 없다
- 하나의 플랫폼(Render)으로 통합돼 대시보드·로그·환경변수 관리가 한 곳에서 끝난다(원 계획의 "두 플랫폼 오가기"보다 운영 부담이 낮음)

**단점·리스크**
- Render 무료 웹 서비스의 슬립/콜드스타트와 Supabase 무료 프로젝트의 7일 일시정지는 "상시 대기" 서비스가 아니라는 뜻이다 — 실제 스포이즘 운영이라면 D18(자체 인프라 운영)이 전제하는 안정성 요구를 만족 못 한다는 점을 인지해야 한다(포트폴리오 시연용으로만 타당)
- **Render 무료 웹 서비스는 공유·스로틀링되는 CPU를 쓴다 — 이게 단순 "느림"이 아니라 D24가 다루는 자기강화형 지연 폭증의 근본 원인이다.**
- `apps/admin-web`이 `BrowserRouter`(히스토리 모드)를 쓰므로 `apps/admin-web/public/_redirects`(`/* /index.html 200`)가 없으면 새로고침 시 404가 난다 — Cloudflare Pages/Netlify 문법이지만 Render Static Site도 같은 `_redirects` 문법을 지원한다고 알려져 있어 파일은 그대로 재사용했다(실제 새로고침 동작은 아직 브라우저로 재확인 안 함 — 다음 확인 대상)
- 첫 배포에서 `NODE_ENV=production`이 `npm install`의 devDependencies 설치를 건너뛰게 만들어 `nest: not found`로 빌드가 실패했었다 — `NPM_CONFIG_PRODUCTION=false`로 수정(`docs/log/` §30)
- Render 대시보드에서의 빌드 커맨드·환경변수 설정은 리포 안의 파일([render.yaml](../../render.yaml))만으로 전부 재현되지 않는다 — Render는 Blueprint(`render.yaml`) 동기화 기능이 있지만, 이번 배포는 MCP 툴로 직접 만들어서 `render.yaml`은 "재현용 기록"으로만 맞춰뒀고 실제 서비스는 Blueprint sync로 연결돼 있지 않다 — 계정 접근 권한이 있는 사람만 대시보드에서 재현/변경 가능하다는 한계가 있다

**대안 및 미채택 사유**: API를 Vercel/Cloudflare Workers 같은 서버리스 플랫폼에 올리는 안도 검토했으나, NestJS는 데코레이터·`reflect-metadata` 기반의 상시 구동 서버 모델이라 서버리스 어댑터(`serverless-http` 등)를 추가로 감싸야 해서 "가장 가볍게"라는 기준에 안 맞았다(Vercel MCP 커넥터도 `list_projects`/`get_deployment` 같은 조회·디버깅 툴뿐이라 애초에 생성 자체가 안 됐다). Railway는 이전엔 무료였지만 지금은 가입 시 1회성 크레딧만 주고 이후 과금되어 "유지비용 없음" 조건에서 탈락시켰다. Fly.io는 Dockerfile과 `fly.toml`/flyctl CLI를 직접 다뤄야 해서 Render 대비 설정 부담이 컸다. DB는 Neon도 후보였으나 사용자가 Supabase를 지정해 그대로 따랐다. Cloudflare Pages는 위 "변경 이력"대로 도구 한계로 이번엔 미채택 — 커넥터가 아니라 CLI(`wrangler`)나 대시보드 수작업으로 접근하면 여전히 유효한 대안이라, 나중에 재검토 대상으로 남겨둔다.

## D26. MockDataService→PrismaService 전환 1단계 — 스키마 동기화 + 인증 모듈 이관

> **지난 결정** — 실DB 전환 1단계(끝남, D36에서 완료).

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: 사용자가 "API도 깔끔하게 관리하고 싶다, 굳이 Render에 둘 이유 없다, 서로 다른 인프라에 분산할 필요 없다"며 api를 AWS로 옮기고 싶어 했다. AWS의 영구 무료(Always Free) 컴퓨트는 사실상 Lambda뿐인데(EC2는 12개월만, App Runner는 애초에 무료 티어 없음), Lambda는 요청마다 여러 실행 인스턴스가 병렬로 뜰 수 있어 지금의 인메모리 `MockDataService`와 근본적으로 안 맞는다 — 동시 인스턴스마다 서로 다른 mock 데이터를 들고 있게 돼, "방금 등록한 회원으로 로그인하면 안 보임" 같은 데이터 정합성 버그가 난다(D24의 대안 D가 이미 짚었던 문제의 재현). 사용자가 DynamoDB(진짜 Always Free)로 이 문제를 풀 수 있는지 물었고, 맞는 방향이지만 이미 27개 모델·관계형 설계(D2 branchId 격리, D6 `FOR UPDATE` 트랜잭션 락, D9 소프트 삭제)로 Supabase에 배포까지 끝난 Prisma 스키마를 버리는 더 큰 결정이라 판단해, "Postgres/Prisma는 그대로 쓰고 Lambda로 호스팅만 옮기자"로 합의했다. 그러려면 먼저 상태가 외부 공유 저장소(Postgres)에 있어야 하므로 — 이게 D24가 이미 "2단계"로 예고해뒀던 MockDataService→PrismaService 전환이다.

**이번 범위를 왜 좁혔나**: 조사해보니 17개 컨트롤러가 `MockDataService`를 직접 주입(서비스 레이어 없음)하고, 비즈니스 로직이 컨트롤러가 아니라 2,288줄 `mock-data.service.ts` 메서드 안에 있으며, 테스트 18개 파일 전부가 인메모리 배열을 직접 조작해 픽스처를 만든다 — 한 세션에 전부 옮기면 검증 없이 너무 많은 게 바뀐다. 그래서 **기반 공사(스키마 동기화 + 가장 트래픽이 높고 위험한 인증 모듈)까지만** 이번에 하고, 나머지 16개 도메인은 도메인 사이클 방식으로 하나씩 옮기기로 했다(플랜은 `/root/.claude/plans/polymorphic-juggling-parnas.md`에 남아 있음 — 대화 중 조사·설계·승인 과정을 그대로 기록).

**한 일 — 스키마 동기화**: `schema.prisma`를 mock 실제 동작과 맞췄다 — `EnrollmentStatus` enum 값 교체(`EXPIRED`→`COMPLETED`/`CANCELLED`, mock이 진짜 동작이므로), `Staff.offDays`·`AttendanceRecord.branchId`·`Member.guardianConsent`·`Payment.supplyAmount/vat`·`Facility.currentCount/level/lastUpdatedAt` 추가, `Asset`/`Document` 모델 신설(1-10 자원문서관리, 스키마에 아예 없었음). 구현 도중 스키마 조사에서도 놓쳤던 진짜 갭을 하나 더 발견했다 — `Account.name`이 스키마에 없는데 SUPER_ADMIN은 Staff/Member 프로필이 없어 이름을 저장할 곳이 없었다(auth 포팅 중 `toRequestUser`를 구현하다가 발견). 바로 추가해 고쳤다. 마이그레이션은 로컬 Postgres에 `prisma migrate dev`로 만들고(`apps/api/prisma/migrations/`, 이제 저장소에 정식 이력으로 남는다), Supabase에는 이 세션이 Postgres 포트에 직접 못 붙는 제약(D23/§29와 동일) 때문에 SQL diff를 뽑아 Supabase MCP `apply_migration`으로 적용했다 — Asset/Document 신규 테이블에 RLS도 나머지 27개와 같은 기준(정책 없이 RLS만 켜서 PostgREST 차단)으로 맞췄다.

**한 일 — 인증 모듈 이관, 그리고 "과도기 이중 경로"라는 진짜 설계 결정**: `AuthService`(login/refresh/logout/changePassword)와 `JwtStrategy`를 `PrismaService` 기반으로 다시 짰다. 처음엔 순수하게 Prisma만 보게 만들었는데, 실제 테스트 스위트(18개 파일)를 돌려보니 **116개 테스트가 한꺼번에 깨졌다** — `/auth/login`이 모든 도메인이 공유하는 단일 진입점인데, 아직 mock인 16개 도메인의 테스트들도 전부 이 엔드포인트로 로그인하기 때문이다. 그래서 `login`/`refresh`/`logout`/`changePassword`/`JwtStrategy.validate`를 전부 **"Prisma에서 먼저 찾고, 없으면 mock으로 폴백"하는 이중 경로**로 다시 설계했다 — 두 저장소는 ID 체계가 겹치지 않아(Prisma UUID vs mock의 `'account-xxx'` 문자열) 폴백이 안전하다. 이 폴백 덕분에 아직 이관 안 된 도메인들의 테스트가 전부 그대로 통과했다(248/252, 아래 "감수하는 것" 참고). 도메인이 하나씩 이관될 때마다 그 도메인의 mock 폴백을 지워나가고, 전부 끝나면 이 파일에서 mockData 의존성 자체를 없앤다 — 이 계획을 코드 주석에도 명시해뒀다.

**한 일 — 두 저장소에 걸친 "같은 사람" ID를 맞춤**: 정하늘·김민수·박서연·이수진 4명은 mock 시드에도, 새 Prisma 시드에도 같은 이메일로 존재하는 "과도기 공유 계정"이다. 처음엔 Prisma 쪽에 무작위 UUID로 시드했는데, 이러면 Prisma로 로그인한 요청의 `req.user.staffId`가 mock 컨트롤러 입장에선 존재하지 않는 ID라 `STAFF_NOT_FOUND` 같은 에러가 났다(branch-isolation.spec.ts 전체가 이렇게 깨지는 걸 실제로 겪었다). `mock-data.service.ts`의 정확한 ID(`account-minsu`, `staff-seoyeon` 등)를 그대로 Prisma 시드에도 써서 해결 — 이제 Prisma가 로그인을 처리해도 `req.user`의 값이 mock 컨트롤러가 기대하는 ID와 일치한다.

**한 일 — CI가 조용히 깨질 뻔한 것을 미리 잡음**: `PrismaModule`이 앱 부팅 시 `$connect()`를 시도하게 되면서, `.github/workflows/ci.yml`에 Postgres 서비스가 전혀 없다는 게 드러났다(지금까지 api 테스트는 DB 없이 돌아간다고 CLAUDE.md에도 적혀 있었다 — 이제 틀린 설명이라 같이 고쳤다). CI job에 `postgres:16-alpine` 서비스 컨테이너(docker-compose.yml과 동일 이미지·자격증명)를 추가하고, `prisma migrate deploy`(비대화형, 이미 만든 migrations/ 그대로 적용) → `prisma:seed` → 테스트 순서로 스텝을 넣었다. 실제로 로컬에 완전히 새 DB를 만들어 이 순서(`migrate deploy` → `seed` → `jest`)를 그대로 재현해보고 통과를 확인한 뒤에 커밋했다 — 이 부분을 검증 없이 넘겼으면 이 커밋이 푸시되는 순간 CI 전체가 빨간불이 됐을 것이다.

**타당성**: 높음 — 계획(스키마 조사 2개 서브에이전트 병렬 조사 → Plan 파일 작성 → 사용자 승인)부터 구현까지 architecture-driver 방법론을 그대로 따랐고, 무엇보다 **실제로 로컬 Postgres를 띄워 진짜 DB 위에서 로그인·토큰갱신(1회용 rotate)·비밀번호변경·§6의 "역할변경 즉시반영" 불변식까지 수동 curl로 하나하나 확인했다** — 타입만 맞춰놓고 "될 것 같다"로 끝내지 않았다. 과정에서 나온 진짜 발견 3개(Account.name 스키마 갭, ID 불일치로 인한 mock 도메인 붕괴, CI Postgres 부재)를 전부 사전에 잡아낸 것 자체가, "빌드만 통과하면 끝"이 아니라 "실행해서 확인한다"는 이 프로젝트 검증 원칙이 실제로 작동했다는 증거다.

**감수하는 것**: ① 이중 경로(Prisma-우선/mock-폴백)는 명백히 임시 설계다 — 코드에 mock 의존성이 여전히 남아 있고, 도메인이 하나씩 이관되기 전까지는 지워지지 않는다. ② `auth-lifecycle.spec.ts` 2건·`staff-assignment.spec.ts` 1건을 `it.skip`으로 남겼다 — 퇴사·Role전환이 아직 mock 도메인이라 Prisma Account에 반영 안 되는, 정확히 진단되고 문서화된 과도기 한계다(기대값을 바꾼 게 아니라 도메인 이관 전까지 "검증 보류"로만 남김, `docs/domains/권한관리.md` §11 갱신). ③ Supabase 쪽은 `prisma migrate deploy`가 아니라 MCP `apply_migration`(원본 SQL)으로 적용했다 — Supabase의 `_prisma_migrations` 이력 테이블엔 이번 마이그레이션들이 기록되지 않는다(이 세션이 Postgres 포트에 직접 못 붙는 구조적 제약, D23부터 있던 문제). 로컬 migrations/ 폴더가 감사·재현용 단일 진실 공급원이고, Supabase는 "같은 DDL을 다른 경로로 적용받은 거울"이라는 걸 다음에 이 프로젝트를 만지는 사람이 알아야 한다. ④ CI에 Postgres 서비스 컨테이너가 추가돼 빌드 시간이 조금 늘었다(허용 범위).

**다음 작업**: 회원관리 도메인부터 순서대로 이관(컨트롤러 인라인 `mockData.filter()` 패턴과 `createReservation`류의 `SELECT ... FOR UPDATE` 동시성 코드를 처음 겪게 될 도메인). 전 도메인 이관이 끝나면 AWS Lambda 호스팅 논의를 재개(D24 3단계와 자연스럽게 연결) — **재개할 때 반드시 설계해야 할 것(2026-09-28, 4주차 발표 준비 중 대화에서 드러난 문서화 공백)**: 이전까지는 "무상태화만 되면 Lambda로 옮긴다"로만 적혀 있었는데, 실제로는 인프라 부하 관점에서 최소 4가지를 더 설계해야 한다 — ① **Lambda 메모리(=CPU) 사이징**: `bcrypt.compare`가 CPU 바운드라 메모리를 너무 적게 주면 스로틀링 대신 "그냥 CPU가 적어서" 느려진다. ② **DB 커넥션 풀링**: 동시 Lambda 실행 환경마다 Postgres 커넥션을 열면 커넥션이 고갈될 수 있어, Supabase Supavisor(세션/트랜잭션 풀러, `pgbouncer=true`)를 반드시 붙여야 한다 — 안 붙이면 병목이 "CPU 경합"에서 "DB 커넥션 경합"으로 옮겨갈 뿐 사라지지 않는다. ③ **Lambda 동시 실행 한도**: 계정 리전별 concurrency 한도가 있어 순간 피크 시 처리량 상한이 된다. ④ **콜드스타트**: Prisma 쿼리 엔진 바이너리 로딩 때문에 유휴 후 첫 요청이 1~3초 걸릴 수 있어 `binaryTargets` 설정과 Provisioned Concurrency 필요 여부를 판단해야 한다. 이 네 가지가 빠진 채로 "Lambda로 옮기면 끝"이라고 설계하면 스로틀링 문제가 다른 형태로 재발한다.

## D29. 도메인 이관 순서를 "참조되는 쪽부터"로 바꾸고, 첫 단계로 지점(Branch)을 옮긴다

> **지난 결정** — 실DB 전환 순서(끝남) — 종료 판정 gate는 D70이 대체.

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: D26은 "다음은 회원관리"로 예고했다. 그런데 회원을 옮기려고 조사해 보니 회원은 지점·직원·프로그램을 참조하고, 이 셋은 mock에만 실데이터가 있었다(mock 98/195/149건, DB 2/3/4건). 회원만 DB로 옮기면 D27·D28의 FK·트리거가 96개 지점의 회원 등록과 담당 직원·수강·PT 등록을 막는다. 아직 mock인 예약·결제·현황판과 두 저장소를 오가는 동기화 코드도 필요해진다. 대안은 A 참조되는 쪽부터(지점 → 직원·파견 → 프로그램·시설·강사·회차 → 회원), B 회원 먼저 + 참조 데이터 DB 복사본 동기화, C 회원과 지점만 함께였다. **사용자가 A를 택했다(2026-09-29).** B·C는 결국 버릴 동기화 코드가 필요하고, 복사본이 늦으면 D28 트리거가 오래된 지점 정보로 잘못 판정한다.

**1단계 지점의 성격**: 지점에는 **쓰기 API가 없다**. 조회만 되는 기준 데이터다. 역할은 둘이다. ① 모든 도메인의 "계약 종료(TERMINATED) 지점 신규 활동 차단" 판정 — mock 서비스 안 9곳에서 동기적으로 한다. ② 지점 목록 화면(`GET /branches`).

**결정 1 — 원천은 DB, mock에는 이름표만 남긴다**: 시드가 98개 지점 전체를 mock과 **같은 원천**(히어로 2개 상수 + `generateLightBranches`)에서 넣는다. 지금 `seed.ts`의 서초·강남은 mock과 값이 다르다(계약 종료일 누락 등). mock 사본은 아직 mock인 도메인이 동기적으로 쓰는 이름·코드·지역·존재 확인·체크인 기준 시각·취소 기준 시간만 남기고, **계약 필드(`contractStatus` 등)는 타입에서 지운다**. 그러면 계약 상태를 mock에서 읽는 코드가 남아 있으면 컴파일이 실패한다. 계약 상태의 사본이 두 개 생기는 것 자체를 막는 장치다. 남은 필드는 "사본 일치 테스트"가 DB와 같음을 검증한다.

**결정 2 — 계약 종료 판정은 요청마다 DB에서 읽어 mock에 넘긴다(gate)**:
| 대안 | 장점 | 한계 |
|---|---|---|
| A. 컨트롤러에서 `await assertNotTerminated(branchId)` 후 mock 호출 | 가장 단순 | 예약처럼 판정 대상 지점이 mock 내부에서 결정되는 경로가 있다(회차 → 프로그램 → 지점). 에러 판정 순서도 바뀐다(예: 진행중 아님 409와 계약종료 409의 우선순위) |
| **B. `BranchService.loadGate()`가 종료 지점 id 집합을 한 번 읽어 mock 메서드에 인자로 넘긴다 (채택)** | 기존 판정 위치·순서를 그대로 유지한다. 인자가 필수라 넘기지 않으면 컴파일 에러다. 쿼리는 요청당 한 번이고 종료 지점은 소수라 가볍다 | 읽은 뒤 쓰기 전 사이에 상태가 바뀌는 경합은 막지 못한다. 계약 상태 변경은 본사의 드문 수동 조치라 감수한다. 각 도메인이 Prisma로 옮겨지면 트랜잭션 안에서 직접 읽는 방식으로 바뀐다 |
| C. mock 사본의 계약 상태를 DB와 동기화 | mock 코드 무변경 | 계약 상태 원천이 두 개가 된다(결정 1이 막으려는 것) |

`CLAUDE.md`가 "실DB 전환 이후"로 미뤄둔 공통 검사 중앙화의 첫 조각이기도 하다. 계약 종료 규칙이 `BranchService` 한 곳으로 모인다.

**결정 3 — 테스트는 워커별 DB에서 돈다**: 지금까지 테스트는 "스위트마다 새 앱 = 새 mock 상태"로 격리됐다. 계약 상태가 DB로 가면 한 테스트가 서초를 TERMINATED로 바꾸는 순간, 병렬로 도는 다른 스위트가 그 상태를 본다. 대안은 A 직렬 실행(`--runInBand`) + 복원, B **jest 워커마다 별도 DB**(마이그레이션·시드가 끝난 DB를 `CREATE DATABASE … TEMPLATE`로 복제)였다. B를 택했다. 도메인이 옮겨질수록 DB 상태를 바꾸는 테스트가 늘어나는데, A는 매번 느려지고 복원을 빠뜨리면 연쇄 실패한다. 워커 안에서는 스위트가 순서대로 돌므로, 테스트가 바꾼 지점 상태는 공용 헬퍼가 매 테스트 뒤에 자동으로 복원한다.

**검증(2026-09-29)**: 로컬 PG16에서 새 기준 DB(마이그레이션 → 시드 98개) → 워커 4개 DB 복제 → 전체 테스트 **264 passed**(261 + `branch-parity.spec.ts` 3건). 사본 일치 테스트는 98개 지점의 이름표 필드가 DB와 같은지 본다. `/branches`는 DB만 바꿔도 계약 상태가 바뀌어 보이고, 이관 전과 같은 응답 형식(날짜 `YYYY-MM-DD` + 건수)을 유지한다. **gate를 일부러 비우면 계약 종료 테스트 8건이 실패함**을 확인해, 판정이 실제로 DB에서 온다는 것도 증명했다. 테스트 뒤 워커 DB는 모두 삭제되고 기준 DB의 서초 상태는 ACTIVE 그대로다(테스트가 기준 DB를 오염시키지 않음). lint 0 에러, api·admin-web 빌드 성공.

**Supabase 시드(2026-09-29, 사용자 승인)**: 배포된 앱은 Supabase에 지점 데이터가 있어야 동작한다(시드 전 0행). `branch-fixtures.ts`에서 만든 upsert SQL을 먼저 로컬의 빈 DB에 두 번 실행해 멱등성과 시드 결과 일치(날짜 외 전 필드 해시)를 확인한 뒤 적용했다. 적용 후 Supabase 해시가 로컬과 같고 98개(종료 3)다. 계약 날짜는 생성기 규칙대로 적용 시점 기준 상대값이다.

**감수하는 것**: 지점명 표시(10개 컨트롤러)는 아직 mock 사본을 읽는다. 해당 도메인이 옮겨질 때 조인으로 바뀐다.

## D30. D29 2단계 — 직원·파견·관리자 계정을 DB로 옮기고, mock에는 DB에서 채우는 미러를 둔다

> **지난 결정** — 실DB 전환 2단계(끝남).

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: 지점(D29)은 쓰기 API가 없어 "mock과 DB를 같은 목록에서 만들고 일치 테스트로 확인"하면 충분했다. 직원은 다르다. ① 채용·수정·퇴사·파견·권한 전환 **쓰기가 있고**, 생성 직원의 입사일은 실행 시각 기준 상대값이라 같은 생성기를 써도 mock과 DB가 날마다 달라진다. ② 아직 mock인 근태·휴가·업무일지·문서·회원(담당 직원)·작성자 이름·지점 건수가 **직원·계정을 동기적으로 읽는다.** ③ 생성 직원 192명은 mock에서 계정 id만 있고 계정 레코드가 없다. DB에서는 `Staff.accountId`가 필수 FK다. 강남 관리자 계정도 mock에만 있다.

**결정 1 — 원천은 DB, mock에는 "DB에서 채우는 미러"**:
| 대안 | 장점 | 한계 |
|---|---|---|
| A. 지점처럼 같은 생성기 + 일치 테스트 | 단순 | 쓰기가 생기는 순간 어긋나고, 날짜가 실행 시각 기준이라 일치 자체가 성립하지 않는다 |
| **B. 앱이 뜰 때 DB에서 mock 미러를 채우고, 직원 쓰기는 DB 커밋 뒤 미러에도 반영 (채택)** | mock 독자(근태 등)는 코드 변경 없이 DB와 같은 값을 본다. 원천은 DB 하나다 | 인스턴스가 여러 개면(Lambda) 다른 인스턴스의 미러는 낡는다. 다만 mock 전체가 원래 다중 인스턴스를 못 버티므로 새로 생기는 한계는 아니다. 근태 등이 옮겨지면 미러도 사라진다 |
| C. mock 독자를 전부 비동기로 바꿔 DB에서 직접 읽기 | 미러 불필요 | 근태·문서·회원 등 아직 옮기지 않은 도메인까지 한꺼번에 고치게 돼 단계가 무의미해진다 |

미러 범위: `Staff` 전체, `StaffAssignment` 전체, 관리자·직원 계정(역할 SUPER_ADMIN·BRANCH_ADMIN·STAFF). 회원 계정은 회원 도메인이 옮겨질 때까지 mock이 그대로 가진다.

**결정 2 — 쓰기는 DB 트랜잭션, 이미 정한 규칙을 그대로 코드로**:
- 퇴사: 직원 상태·퇴사일 + 계정 비활성화 + 진행 중 파견 종료를 한 트랜잭션으로 묶는다(ADR-STF-01).
- 파견: 옛 파견 종료 + 새 파견 + DB 회원 담당 해제 + 강사 연결 해제 + `Staff.branchId` 갱신을 이 순서로 한 트랜잭션에 넣는다(ADR-STF-04, D28 트리거가 순서를 강제).
- 채용: 계정 + 직원 + 최초 파견을 한 트랜잭션으로 만들고, 직원번호는 `allocateBranchCode`로 채번한다(ADR-STF-02). 이메일 중복은 부분 unique 위반(P2002)을 409로 바꿔 알린다.
- 권한 전환: `Account.role`을 바꾼다. JWT 전략이 매 요청 DB를 다시 읽으므로 재로그인 없이 바로 반영된다(ADR-AUTH-01). **D26에서 skip한 테스트 3건이 여기서 다시 살아난다.**

**결정 3 — 아직 mock인 도메인에 대한 부수효과는 DB 커밋 뒤 mock에 적용한다**: 파견의 mock 회원 담당 해제(ADR-STF-04)와 퇴사의 mock 인사서류 보존기한 재계산(ADR-RES-02)이 여기에 해당한다. 두 저장소를 한 트랜잭션으로 묶을 수 없어 원자적이지 않다. DB가 성공한 뒤 mock에서 실패할 경로는 없지만(메모리 갱신), 해당 도메인이 옮겨지면 같은 트랜잭션 안으로 들어간다.

**결정 4 — 계정이 두 저장소로 나뉜 동안 이메일 유일성은 양쪽을 본다**: 직원 계정은 DB, 회원 계정은 mock에 있다. 다만 미러(결정 1)가 직원·관리자 계정을 mock `accounts`에도 넣으므로, 회원 등록·연동이 쓰는 mock의 `isEmailTakenByActiveAccount`는 코드 변경 없이 DB 직원 이메일까지 본다. 채용은 반대 방향으로, DB 트랜잭션 전에 같은 mock 검사로 회원 계정 이메일을 먼저 확인하고(→ 409 `EMAIL_ALREADY_EXISTS`), DB 부분 unique 위반(P2002)도 409로 바꾼다. 두 검사 사이의 경합은 막지 못하지만, 회원 도메인이 옮겨지면 DB 부분 unique 하나로 합쳐진다.

**데이터 신설**: 생성 직원 192명에 계정을 만든다(이메일 `gen-001-1@staff.spoism.example` 형식, 역할 STAFF, 데모 비밀번호). mock에는 계정 레코드 자체가 없었으므로 새 데모 데이터다.

## D31. D29 3단계 — 시설·강사·프로그램·회차를 DB로 옮기고, D30의 미러 패턴을 그대로 쓴다

> **지난 결정** — 실DB 전환 3단계(끝남).

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: D29 순서의 3단계. 네 엔티티는 모두 쓰기 API가 있다(시설 등록·수정·혼잡도 수동 보정, 강사 등록·수정·비활성화, 프로그램 등록·수정·상태 전이·종료, 회차 등록). 아직 mock인 **예약·결제**(회차·프로그램 가격·상태·지점), **회원**(수강·PT의 프로그램 지점 검사, 요약), **지점 건수**(진행중 프로그램 수)가 이것들을 동기적으로 읽는다. D30 직원과 같은 상황이다. 하나 다른 점이 있다. **예약 정원 검사(ADR-RSV-01)가 회차를 읽는 가장 민감한 경로**인데, 예약은 회원 단계(4단계)까지 mock에 남는다.

**결정 1 — D30 결정 1(원천은 DB, mock은 DB에서 채우는 미러)을 그대로 적용**: 대안은 D30 때와 같다(같은 생성기+일치 테스트 / mock 독자 전부 비동기화). 기각 이유도 같다. 새로 따져 본 대안은 **"예약까지 같이 옮기기"**다. 예약은 회원을 참조하고, 회원은 4단계다. 예약만 옮기면 D29에서 막았던 "참조되는 쪽이 아직 mock"인 상태가 반대 방향으로 생긴다. 그래서 기각한다. 정원 검사는 mock 예약 + 미러 회차로 계속 돈다. 단일 프로세스라 이벤트 루프가 락 역할을 하는 기존 가정(예약및결제 A-6 주석)이 유지된다. 회차 행 락(`lockScheduleSlot`, D28)은 예약이 옮겨질 때 쓴다.

미러 범위: `Facility`, `Instructor`, `Program`, `ScheduleSlot` 전체. 이 네 모듈의 자기 조회 API(목록·단건)는 미러가 아니라 DB에서 읽는다(D30과 같다 — 다중 인스턴스로 가도 자기 API는 맞는다).

**결정 2 — 검증 규칙은 위치만 옮기고 그대로 둔다**: 강사·시설 같은 지점 검사(ADR-PRG-03, D28 트리거가 뒤를 받침), PAID_SESSION 정원 필수(ADR-PRG-01), FREE_ACCESS 가격·정원 비우기(강사프로그램게시 A-6), 상태 전이표(강사프로그램게시 A-3), 시설 정원 1 이상·혼잡도 5단계 재계산(혼잡도관리 A-6), 계약 종료 지점의 시설 등록·보정 차단(ADR-FAC-03, `BranchService`로 DB 판정). 수정은 "검증을 모두 끝낸 뒤 한 번에 반영"하던 mock 방식이 DB `update` 한 번으로 자연히 성립한다.

**결정 3 — 강사↔직원 연결을 미러까지 잇는다(ADR-STF-04 숙제 해소)**: DB `Instructor.staffId`는 있었지만 mock 강사 타입엔 없었다. 그래서 D30의 파견 트랜잭션은 DB 강사만 정리하고 mock 강사는 그대로 두었다. 이제 강사 원천이 DB이므로 파견 커밋 뒤 그 직원의 강사 행을 미러에 다시 반영한다. 서초 박서연 강사는 mock에서 `staffId`가 없었는데, 시드에서 `staff-seoyeon`과 연결한다(seed.ts가 원래 그렇게 만들었다. id만 mock 값 `instructor-seoyeon`으로 맞춘다).

**결정 4 — 데이터 원천 통일**: seed.ts의 서초 시설·프로그램 값이 mock과 달랐다(요가 설명 없음, 헬스장 현재 인원 0 등, D29 지점 때와 같은 종류). 강사 id도 uuid였다. mock 값을 기준으로 `catalog-fixtures.ts` 한 곳에서 만든다. 생성 프로그램의 개강일은 생성기 실행 시각 기준 상대값이라 시드한 날 날짜로 고정된다(D30과 같다).

**감수하는 것**: 회차·프로그램을 바꾸는 쓰기와 그걸 읽는 예약 쓰기가 서로 다른 저장소라 원자적이지 않다. 예를 들어 프로그램을 PAUSED로 바꾼 커밋과 예약 생성이 경합하면, 미러 반영 전 짧은 틈에 예약이 들어갈 수 있다. 단일 프로세스에서는 커밋 뒤 미러 반영이 같은 요청 안에서 이어지므로 실제 틈은 await 한 번이다. 예약이 옮겨지면 같은 트랜잭션·회차 락으로 닫힌다.

## D32. D29 4단계 — 회원·예약·결제·수강·PT를 DB로 옮기고, 미러 없이 끝낸다. 인증의 mock 폴백도 여기서 없앤다

> **지난 결정** — 실DB 전환 4단계(끝남).

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: D29 순서의 마지막 참조 단계다. 회원·회원 계정·수강·PT(+사용 기록)·예약·결제가 대상이다. D30·D31과 다른 점이 셋 있다. ① 이 데이터를 동기적으로 읽는 **아직 mock인 도메인이 없다.** 근태·게시판·자산·문서는 회원·예약·결제를 읽지 않는다. 지점 건수와 프로그램의 예약 집계만 읽는데, 둘 다 이미 DB로 옮긴 모듈 안에 있다. ② 이 단계가 끝나면 **모든 계정이 DB에 있다.** D26이 만든 인증의 "Prisma 먼저, 없으면 mock" 이중 경로가 존재할 이유가 사라진다. ③ 예약 생성에서 mock의 단일 스레드 가정이 끝난다. 정원 검사(ADR-RSV-01)가 처음으로 진짜 동시성 아래에 놓인다.

**결정 1 — 미러를 두지 않는다**: D30·D31 미러는 "아직 mock인 독자"를 위한 것이었다. 여기엔 그런 독자가 없다. 미러를 두면 쓰는 사람 없는 복사본만 늘어난다. mock의 해당 배열·메서드를 지우고, 지점 건수(`branchCounts`)와 프로그램의 예약 집계(`bookedCount`·`futureActiveReservationsForProgram`)는 DB 조회로 바꾼다. 대안은 "테스트가 읽으니 미러를 남기자"였다. 테스트를 위해 운영 코드에 복사본을 두는 것은 거꾸로라서 기각했다. 테스트는 Prisma로 읽게 바꾼다. **같은 이유로 D31의 시설·강사·프로그램·회차 미러도 없앤다.** 그 미러의 독자는 예약·회원·지점 건수·프로그램 현황판이었는데, 전부 이번에 DB 조회로 바뀌어 읽는 코드가 남지 않는다. 남는 미러는 D30 직원 미러뿐이다. 근태·문서·게시판이 아직 mock이기 때문이다.

**결정 2 — 인증 mock 폴백 제거(D26 과도기 종료)**: 회원 계정까지 DB로 오면 mock 계정은 하나도 남지 않는다. `AuthService`의 login·refresh·logout·changePassword와 `JwtStrategy`에서 mock 경로를 지운다. 회원가입·연동 직후 로그인(`issueSession`)도 DB 계정으로 발급한다. 이메일 유일성 검사도 D30 결정 4의 "양쪽 저장소 보기"에서 DB 부분 unique(ADR-MEM-02) 하나로 합쳐진다. 다만 채용·가입·연동 모두 앱이 먼저 409를 내고, 경합은 P2002를 409로 바꿔 받는다. mock의 `accounts`에는 D30 미러(직원·관리자 계정)만 남는다. 게시판·문서가 작성자 이름을 읽는 용도다.

**결정 3 — 예약 생성은 D28 헬퍼로 직렬화한다(ADR-RSV-01·02)**: 트랜잭션 안에서 `lockScheduleSlot`으로 회차 행을 잠근 뒤 활성 예약을 센다. 중복 예약은 앱 검사 + 부분 unique 인덱스 이중화(ADR-RSV-02)다. 인덱스 위반(P2002)은 `ALREADY_RESERVED` 409로 바꾼다. 결제(PENDING)는 같은 트랜잭션에서 만든다. 검사 순서(회차 없음 → 프로그램 → 예약 불가 → 진행중 아님 → 회원 지점 불일치 → 계약 종료 → 중복 → 정원)는 mock 그대로 둔다. 에러 코드 우선순위가 테스트로 고정돼 있기 때문이다.

**결정 4 — 채번과 연동 실패 제한은 D27·D28이 마련한 자리로**: 회원번호는 `allocateBranchCode(MEMBER)`로 뽑는다. mock은 "같은 prefix 회원 수 + 1"(동시 등록 시 중복)이고 연도를 호스트 시간대로 구했는데, 이제 KST 연도로 바뀐다. 연동 실패 제한(ADR-MEM-01, 시간당 5회)은 mock의 프로세스 메모리 `Map`에서 `MemberLinkAttempt` 테이블로 옮긴다. 인스턴스가 여럿이거나 재시작돼도 제한이 유지된다. Lambda 전제(D26)에서는 메모리 제한이 사실상 무력했다.

**결정 5 — 옮기면서 드러난 시간대 결함 두 건은 고친다(date-time-handling.md 규칙)**: ① 취소 환불 마감 판정이 회차 시작을 `new Date("YYYY-MM-DDTHH:mm:00")`(호스트 시간대)로 만들었다. 서버가 UTC면 KST 회차 시각이 9시간 늦게 해석돼, 마감이 지난 취소도 환불됐다. 회차 날짜·시각은 KST이므로 `+09:00`을 붙인다. ② 결제 목록의 날짜 필터가 `approvedAt.slice(0,10)`(UTC 날짜)로 비교했다. KST 날짜(`toKstDateString`)로 바꾼다. 둘 다 이 프로젝트가 이미 정한 규칙(CLAUDE.md "날짜 계산") 위반이라 별도 결정 없이 고친다.

**데이터**: 히어로 회원 3명(이수진·오영희·한지민)과 생성 회원, 이수진 계정·수강 1건·PT 1건(사용 기록 3건)을 `member-fixtures.ts` 한 곳에서 만든다. seed.ts가 로컬에만 만들던 예약·결제 데모 행과 그 회차는 mock에 없던 데이터라 지운다(D29 이후 "시드와 mock은 같은 원천" 원칙). MEMBER 채번값은 시드한 회원번호의 prefix별 최댓값으로 맞춘다.

**감수하는 것**: 게시판·문서의 작성자 이름은 여전히 D30 미러(직원·관리자 계정)에서 읽는다. 회원이 작성자인 게시글·문서가 생기면 이름이 비어 보인다. 현재 API는 회원 작성을 허용하지 않으므로 해당 없음을 확인하고 넘어간다.

## D33. 남은 mock 도메인 1번째 — 근태(체크인·결근 확정·휴가·연차 잔여·업무일지)를 DB로 옮긴다

> **지난 결정** — 남은 mock 도메인 1(끝남).

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: D32로 참조 순서가 끝났고, mock으로 남은 도메인은 근태·게시판·자산·문서 넷이다. 근태를 먼저 옮기는 이유는 D30 직원 미러를 가장 많이 읽는 곳이기 때문이다. 결근 판정은 직원의 근무 형태·휴무 요일·파견 이력을 모두 읽는다. 근태 데이터는 시드가 없어서(mock도 빈 배열로 시작) 옮길 데이터가 없다. 그래서 이관 범위는 데이터가 아니라 **로직**이다. 이번에 처음으로 규칙들이 단일 스레드 가정 없이 동시 요청 아래 놓인다. 해당 규칙은 하루 1건 체크인(불변규칙 1), 승인 시 1회 차감(ADR-ATT-01), 결근 확정 멱등(ADR-ATT-02)이다.

**결정 1 — 동시성은 이미 있는 DB 제약 위에 조건부 갱신으로 얹는다(스키마 변경 없음)**:
- **체크인**: `AttendanceRecord(staffId, date)` unique(D26 이전부터)가 최종 방어선이다. 같은 날 동시 체크인이 겹치면 P2002가 나는데, 이를 `ALREADY_CHECKED_IN` 409로 바꾼다. 기록은 있고 `checkInAt`만 비어 있는 행은 "`checkInAt IS NULL`일 때만" 채운다.
- **체크아웃**: "`checkInAt` 있음 ∧ `checkOutAt` 없음"일 때만 갱신한다.
- **휴가 승인·반려**: "PENDING일 때만" 상태를 바꾼다. 승인이면 같은 `$transaction`에서 연차 잔여를 원자적으로 증가시킨다(`usedDays = usedDays + days`, data-integrity §6 체크리스트).
- **연차 잔여 행 지연 생성**: `skipDuplicates`로 넣어, 동시 생성 경합에서도 한 행만 남는다.
- **결근 확정**: `createManyAndReturn(skipDuplicates)`를 쓴다. 두 관리자가 동시에 확정해도 unique가 중복을 막고, 각 호출은 자기가 실제로 만든 행만 돌려받는다.
- **업무일지**: 하루 1건(근태관리 A-3 "권장")은 unique 제약이 없다. 트랜잭션 안에서 `pg_advisory_xact_lock(직원+날짜)`로 직렬화한 뒤 upsert한다.
  - 대안은 `WorkLog(staffId, date)` unique를 추가하는 것이었다. 이는 스키마 변경이라 사용자 승인 대상이고(CLAUDE.md), 기존 Supabase 데이터 점검도 필요하다. 그래서 이번에는 앱 수준 잠금으로 막고, unique 추가는 후속 제안으로 남긴다.

**결정 2 — D30 파견 이력 미러를 없앤다(직원·계정 미러는 유지)**: 파견 이력 미러(`staffAssignments`)의 유일한 독자는 근태의 `branchIdForStaffOnDate`(ADR-ATT-03)였다. 이것이 DB 조회로 바뀌면 읽는 코드가 남지 않으므로 D32 결정 1과 같은 이유로 지운다. 직원 미러는 문서(관련 직원 이름·존재 검사)가, 계정 미러는 게시판·문서(작성자 이름)가 아직 읽으므로 남긴다.

**결정 3 — 결근 미리보기는 "해당 월·해당 직원"으로 범위를 좁혀 한 번에 읽는다(traffic-infra-review 근태 항목의 첫 대응)**: mock은 직원×날짜 이중 루프마다 전체 근태·휴가 기록을 `.some()`으로 다시 스캔했다. 비용이 O(직원×일수×누적기록)이다. DB로 옮기면서 쿼리 4개로 바꾼다. 후보 직원, 그 직원들의 파견 이력, 그 달의 근태 기록(`staffId, date` 인덱스), 그 달과 겹치는 승인 휴가를 한 번씩 읽는다. 판정 규칙과 순서는 ADR-ATT-02·03 그대로 두고, 판정은 메모리의 Set 조회로 한다. 누적 기록이 늘어도 비용은 "그 달" 크기에 묶인다.
- 리뷰 문서가 적어 둔 두 번째 대안인 "월별 집계 사전 계산·캐싱"은 쓰기 경로마다 무효화가 필요하다. 지금 규모에서는 범위 제한만으로 충분하다고 보고 보류한다.
- 확정 API가 미리보기를 쓰기 경로 안에서 다시 계산하는 구조는 유지한다. 확정 대상이 "지금 이 순간의 후보"여야 하므로(멱등 보장) 캐시를 쓸 수 없다.

**결정 4 — 옮기면서 드러난 시간대 결함은 고친다(date-time-handling.md 규칙)**: 연차 잔여의 기준 연도를 `new Date().getFullYear()`(호스트 시간대)로 구했다. 입사 연도도 `new Date(hireDate).getFullYear()`로 구했다. 서버가 UTC면 매년 1월 1일 00:00~08:59 KST 사이 요청이 **전년도 잔여**를 읽거나 만든다. "올해"는 `todayKst()`의 연도로, 입사 연도는 날짜 문자열의 연도로 구한다. D32 결정 5와 같이 이미 정해진 규칙 위반이라 별도 결정 없이 고친다.

**감수하는 것**:
- 업무일지 하루 1건은 DB 제약이 아니라 앱 잠금이다. SQL로 직접 넣는 경로는 막지 못한다(unique 추가는 승인 후 후속 작업).
- 결근 확정과 같은 과거 날짜에 대한 휴가 승인이 동시에 일어나면, 방금 승인된 휴가일이 결근으로 확정될 수 있다. 과거 날짜 휴가를 사후 승인하는 드문 경로이고, 결근 기록은 관리자가 정정할 수 있어 감수한다(근태관리 A-7 정정 API는 아직 미구현, ADR-ATT-02 숙제 그대로).

## D34. 남은 mock 도메인 2번째 — 문서(자원문서관리의 문서 절반)를 DB로 옮기고, 직원 미러를 없앤다

> **지난 결정** — 남은 mock 도메인 2(끝남).

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: 근태(D33) 뒤 mock에 남은 것은 게시판·자산·문서다. 이 가운데 D30 직원 미러(`staff`)를 읽는 곳은 문서뿐이다. 문서는 인사서류 대상 직원의 존재·소속 확인, 관련 직원 이름, 보존기한 기산일(퇴사일)을 직원에게서 읽는다. 문서를 옮기면 직원 미러의 독자가 사라진다. 또 직원 퇴사가 인사서류 보존기한을 다시 계산하는데(ADR-RES-02), 이는 D30 결정 3이 "커밋 뒤 mock에 적용"으로 남겨 둔 **마지막 교차 저장소 부수효과**다. 옮길 데이터는 시드 문서 2건(전사 매뉴얼, 서초 위탁계약서)이다.

**결정 1 — 문서 원천을 DB로 옮긴다(규칙은 그대로)**: 규칙은 mock 구현을 그대로 옮긴다.
- 보존기한 계산(자원문서관리 A-6): HR_RECORD는 퇴사일(없으면 오늘 KST)+3년, CONTRACT는 직접 입력, 나머지는 영구 보관.
- 검사 순서: 지점 없음 → 계약 종료 → HR 대상 직원 필수·존재 → CONTRACT 보존기한 필수. 이 순서는 ADR-RES-01·RES-03, 에러 코드 우선순위 테스트로 고정돼 있어 바꾸지 않는다.
- 소프트 삭제는 D9를 따른다.
- 시드 문서 2건은 `document-fixtures.ts` 한 곳에서 만들어 시드한다(D29 "시드와 mock은 같은 원천"). mock에는 더 두지 않는다.
- 지점 이름은 DB 조인으로 가져오고, 관련 직원·업로더 이름은 id 묶음 조회 한 번으로 붙인다. 이렇게 traffic-infra-review 자원문서관리 항목의 "문서 목록 N+1"도 함께 없앤다.
- 보존기한 임박 목록은 `retentionUntil` 조건 쿼리로 바꾼다. 전체 스캔·정렬이 필요 없다.

**결정 2 — 퇴사 시 인사서류 보존기한 재계산을 퇴사 트랜잭션 안으로(ADR-STF-01·RES-02, data-integrity §6 퇴사 체크리스트)**: 문서가 DB로 오면 두 저장소를 따로 쓸 이유가 없다. `StaffService.resign`의 트랜잭션에서 직원 상태, 계정 비활성화, 파견 종료와 함께 그 직원의 미삭제 HR_RECORD 보존기한을 `퇴사일+3년`으로 갱신한다. 이로써 D30 결정 3의 "커밋 뒤 mock 적용"은 모두 끝난다.

**결정 3 — 직원 미러를 없애고, 계정 미러만 남긴다**: 문서 이관 뒤 `mockData.staff`·`findStaffById`를 읽는 코드가 남지 않는다. D32·D33과 같은 논리로 지운다. 게시판이 작성자 이름(`findAccountById`)을 아직 읽으므로 관리자·직원 계정 미러는 남기고, 게시판을 옮길 때 함께 없앤다.

**감수하는 것**:
- `Document.relatedStaffId`·`uploadedBy`에는 DB 외래키가 없다(스키마 주석은 "FK → Account"지만 관계가 선언돼 있지 않다). 그래서 대상 직원의 존재는 앱이 확인하고, 업로더는 인증된 계정 id라 존재가 보장된다. 외래키 추가는 스키마 변경이라 사용자 승인이 필요해 후속 제안으로 남긴다.
- 관련 직원이나 업로더가 나중에 사라지면 이름이 비어 보인다. 직원·계정은 삭제하지 않고 비활성화하는 구조라 실제로 일어날 경로는 없다.
- 시드 문서 2건은 사용자 승인 후 Supabase에 먼저 적용했다(2026-09-29). 적용 후 지문이 로컬 시드와 같다(docs/log/048).

## D35. 남은 mock 도메인 3번째 — 자산(자원문서관리의 나머지 절반)을 DB로 옮긴다

> **지난 결정** — 남은 mock 도메인 3(끝남).

> 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**컨텍스트(Driver)**: 문서(D34) 다음은 자산이다. 자산을 옮기면 게시판 하나만 mock에 남는다. 자산에는 다른 도메인이 읽는 데이터가 없어서 미러를 둘 곳이 없다. 옮길 데이터는 서초점 시드 자산 3건이다. 이 도메인에서 단일 스레드 가정에 기대던 규칙은 두 가지다.
- **자산번호 채번**: `{지점코드}-A{순번}`을 "같은 prefix 자산 수 + 1"로 뽑는다(RES-T04). 이 문제는 이미 "실DB 전환 시 트랜잭션+락"으로 결론이 나 있었다.
- **상태 전이 검사**: 읽은 상태로 전이를 검사한 뒤 쓴다. 두 요청이 같은 이전 상태를 읽으면 둘 다 통과한다.

**결정 1 — 자산 원천을 DB로 옮기고, 채번은 D28 헬퍼로(RES-T04, data-integrity §6 체크리스트 첫 줄)**:
- 채번: `allocateBranchCode(ASSET)`가 `CodeSequence`의 `{지점코드}-A` 행을 원자적으로 올린다. 폐기된 자산도 순번을 계속 차지한다는 규칙("재사용 안 함")은 시퀀스가 증가만 하므로 그대로 성립한다. 시드는 그 prefix의 최대 순번으로 시퀀스를 초기화한다. D28 §5가 발견한 "시드 번호와 첫 채번 충돌"을 막기 위해서다.
- 그대로 두는 규칙: 자동 판정(100만원 초과는 고정자산, 자원문서관리 A-6, RES-T01), 고정자산 수량 1(RES-T03, D28 CHECK로 이중화), 상태 전이표(§4-4·§4-8, RES-T02), 검사 순서(지점 없음 → 계약 종료, ADR-RES-01).
- 지점 이름은 조인으로 가져와 목록 N+1을 없앤다(traffic-infra-review 자원문서관리 항목의 자산 절반).

**결정 2 — 상태 전이는 "읽은 상태 그대로일 때만" 갱신한다(D31 프로그램 상태 전이와 같은 방식)**: 전이표 검사는 앱에서 한다. 쓰기는 `updateMany where { id, status: 읽은 상태 }`로 해서, 그 사이 다른 요청이 상태를 바꿨으면 0건이 된다. 이 경우 `INVALID_STATUS_TRANSITION` 409로 돌려준다. 폐기됨(DISPOSED)은 종결 상태라, 동시에 두 전이가 와도 폐기된 자산이 되살아나지 않는다.

**감수하는 것**:
- 폐기 자산이 목록에 계속 쌓이는 문제(traffic-infra-review "무한 누적")는 이번에 다루지 않는다. 페이지네이션이나 보관(아카이빙)은 화면 설계와 함께 정할 일이다. 지금 규모(지점당 수 건)에서는 급하지 않다.
- 기본 정보 수정(`PATCH /assets/:id`)은 여전히 "읽고 검사한 뒤 쓴다". 고정자산 수량이 1이 아니게 되는 경합은 D28 CHECK가 최종 방어선이다. 위반하면 앱 검사가 먼저 막아야 정상이고, 경합일 때만 DB가 거부한다.
- 시드 자산 3건과 ASSET 시퀀스는 사용자 승인 후 머지 전에 Supabase에 함께 적용했다(2026-09-29, 지문 로컬과 동일 — docs/log/049). 둘은 반드시 함께 넣는다.

## D48. 처리 한계의 원인은 풀러 모드의 작업당 왕복이다 — 1단계로 Prisma 작업 수를 줄이고, `pgbouncer=true` 제거는 승인 뒤로 미룬다 (2026-10-10)

> **지난 결정** — D49(Session pooler)가 대체.

> 경위·측정표는 [log/102](../log/2026-W41.md#102) · [D42](D42.md) 결정 3("요청당 쿼리 수 줄이기도 지금은 하지 않는다")을 대체한다. D42의 설정(상한 10·1,024MB)은 그대로다

**컨텍스트(Driver)**:
- D42는 요청당 처리 시간 W(p50 약 110ms)가 가정(50ms)의 2.2배인 원인을 "풀러 왕복 × 쿼리 수"로 추정만 했다(D37 R5).
- 로컬 실측(log/102): `pgbouncer=true`에서 Prisma 5.22는 작업마다 BEGIN·DEALLOCATE ALL·COMMIT을 보낸다. 요청당 순차 왕복이 9~45회다(k6 S2 평균 20.8). 플래그를 빼면 같은 라우트가 평균 5.9회다.
- 인증된 모든 요청이 계정 조회와 지점 조회를 따로 해 인증에만 왕복 약 11회를 썼다.

### 결정

1. **원인을 "작업당 왕복"으로 기록한다.** 쿼리 수보다 Prisma 작업 수가 W를 정한다. `connection_limit=1`에서는 작업을 병렬로 바꿔도 효과가 없다.
2. **1단계(구현, 사용자 선택 B1+B2)**: 인증 조회를 작업 하나로 합치고(ADR-AUTH-01의 매 요청 재조회 유지), 목록 count + findMany를 일괄 트랜잭션 하나로, 공지 작성자 이름을 include로 읽는다.
3. **`pgbouncer=true` 제거(A안)는 하지 않는다 — 사용자 승인 대기.** 효과는 가장 크지만(S2 왕복 약 1/3.5) D37 결정 1의 접속 설정을 바꾸고, Supavisor에서 prepared statement가 어떻게 동작하는지 확인해야 하며 운영 재측정이 필요하다.

### 대안 → 트레이드오프

## D63. 운영 의존성 취약점 — 같은 메이저 안에서 고정해 없애고, 도달 불가한 2건은 메이저 업그레이드를 미룬다 (2026-10-22)

> **지난 결정** — 미룬 부분은 D65에서 끝남.

> 경위는 [log/158](../log/2026-W43.md#158)

**컨텍스트(Driver)**: 사용자가 `npm install` 끝의 "71 vulnerabilities"를 보고 운영 의존성부터 처리하라고 했다(2026-10-22). `npm audit --omit=dev` 기준 운영 의존성 18건(심각 2·높음 8·중간 7·낮음 1). 대부분 NestJS 10·bcrypt 5가 하위 패키지 버전을 고정해 두어 생긴 것이고, `npm audit fix --force`는 NestJS 12·bcrypt 6·react-router 7 메이저 업그레이드를 한꺼번에 요구한다. [개발보안 점검표](../architecture/secure-coding-checklist.md)에도 "`npm audit` 결과 대조"가 할 일로 남아 있었다.

**상위 목표(D53)**: 노하우 습득 — 실무에서 audit 경고를 "전부 강제 업그레이드"도 "무시"도 아닌, 경로별 도달 가능성으로 나눠 처리하는 방법을 익힌다. **핵심 변수**: 실제로 닿는 코드 경로, 메이저 업그레이드 비용(NestJS 11은 Express 5 — 라우트 문법·Lambda 어댑터 영향), Lambda 묶음(루트 `node_modules`만 복사, log/155). **답안지**: 같은 메이저 안의 고친 판으로 고정(override) → 남는 것은 권고문의 전제 조건으로 도달 여부를 판정하고 근거와 재고 트리거를 남긴다.

### 결정

1. **잠금 파일 갱신**(`npm audit fix`, 강제 없이): proxy-addr 2.0.8(IP 위조, 심각)·follow-redirects 1.16.1·source-map-js 1.2.2·brace-expansion 1.1.21.

4. **미루는 2건(중간 4줄)** — 메이저 업그레이드가 필요하고 우리 코드에서 닿지 않는다:

   - `react-router` GHSA-wrjc-x8rr-h8h6(공격자 경로를 `<Link>`·`navigate`에 넘길 때 역슬래시 외부 이동, 7.18.0에서 고침)·GHSA-337j-9hxr-rhxg(SSR 하이드레이션 — 우리는 SPA) — 두 웹의 이동 대상은 코드 상수이거나 서버 코드가 정한 링크(처리 대기함)이고, `redirect`·`returnTo` 같은 사용자 경로 쿼리가 없다.
