# D47. 상세 전화번호 열람 기록 — 관리자가 회원·직원 상세를 열 때마다 AuditLog에 `PHONE_VIEWED`를 남기고, 본사만 본다

> 결정 기록 [인덱스](README.md) · 경위는 [log/100](../log/100.md) · RFP 1-2 #7 사용자인터페이스보안, 회원관리 ADR-MEM-04 숙제, [D44](D44.md) 범위 밖으로 남긴 항목

**상태**: 결정·구현(2026-10-10). 스키마 변경 없음.

## 컨텍스트

- 목록은 전화번호를 마스킹하고 상세는 원문을 준다(ADR-MEM-04, 인사정보관리 STF-T03). 상세로 들어가는 동작을 "별도 절차"로 봤지만, 누가 언제 원문을 봤는지는 남지 않았다([요구사항추적표](../reference/요구사항추적표.md) §2-3).
- D44가 AuditLog(actorId·entity·entityId·action·before·after·createdAt)에 인사 변경 기록을 쓰기 시작했고, 열람 기록은 "조회마다 쓰기 1회"라 범위 밖으로 두었다.
- 원문을 주는 곳: `GET /members/:id`(SUPER_ADMIN·BRANCH_ADMIN·회원 본인), `GET /staff/:id`(SUPER_ADMIN·BRANCH_ADMIN·직원 본인), `GET /staff/me`. admin-web 수정 폼은 상세 응답(원문)으로 채운다.

## 결정 (사용자 결정 4건, 2026-10-10)

1. **AuditLog를 재사용한다.** `entity = 'Member' | 'Staff'`, `action = 'PHONE_VIEWED'`, `before = null`, `after = { branchId }`(열람 당시 대상의 지점). 번호 자체는 넣지 않는다(D44 결정 4).
2. **상세를 열 때마다 기록한다.** ADR-MEM-04(상세 = 원문)는 그대로 둔다. 기록 조건:
   - 열람자가 SUPER_ADMIN·BRANCH_ADMIN일 때만. 본인 조회(회원 웹 내 정보, 직원 본인 상세·`me`)는 남기지 않는다.
   - 대상의 번호가 비어 있으면 드러난 원문이 없어 남기지 않는다.
   - 목록(마스킹)·거부된 요청(403/404)은 남지 않는다 — 가드가 핸들러 전에 막는다.
   - 응답 전에 쓴다. 기록이 실패하면 상세도 500으로 실패한다(기록 없이 원문을 내보내지 않는다).
3. **조회는 SUPER_ADMIN만** — D44의 `GET /audit-logs?action=PHONE_VIEWED`와 admin-web "변경 이력" 화면(이벤트 "전화번호 열람")을 그대로 쓴다. 응답의 대상 이름(`entityName`)은 직원·회원 모두 쪽 단위 한 번씩 조회한다.
4. **보존 1년을 규칙으로 적고, 자동 삭제는 만들지 않는다.** 삭제 배치는 노쇼 배치처럼 자동 배치를 범위 밖에 둔 원칙을 따른다. 1년 지난 기록은 운영자가 수동으로 지운다(배포 DB 쓰기라 승인 대상).

구현: `src/prisma/audit.ts`의 `recordPhoneView` — `MemberService`·`StaffService`의 `recordPhoneView`가 이를 부르고, 두 상세 컨트롤러가 응답 직전에 호출한다.

## 대안

- **새 테이블(AccessLog)**: 변경 이력과 열람 기록이 분리되고 `branchId` 컬럼·보존 삭제용 인덱스를 둘 수 있다. Prisma 스키마 변경·배포 DB 마이그레이션이 필요하다. 지금 조회 요구(본사가 대상·처리자로 보기)는 AuditLog로 충분해 고르지 않았다.
- **"번호 보기" 버튼을 눌렀을 때만 원문을 주고 기록**: 기록이 정확하다(수강 내역만 보러 들어와도 열람으로 남는 문제가 없다). 대신 상세도 마스킹하고 `GET /members/:id/phone` 같은 라우트를 새로 둬야 해 ADR-MEM-04를 대체하고, 수정 폼이 원문을 따로 받아야 한다. 화면 변경이 커서 고르지 않았다.
- **지점 관리자에게 자기 지점 열람 기록 공개**: D44와 같은 이유(감사 대상에게 감사 기록을 열지 않는다)로 고르지 않았다.
- **보존 2년 / 1년 + 조회 시 삭제**: 2년은 용량을 두 배로 쓴다. 조회 시 삭제는 읽기 경로에 쓰기가 생기고 코드가 는다.

## 결과

- 좋아지는 것: RFP 1-2 #7 "개인정보 무단 노출 금지"에 목록 마스킹 + 상세 열람 기록으로 답한다. ADR-MEM-04·STF-T03의 숙제가 닫힌다.
- 감수하는 것:
  - **요청당 쿼리 +1(D42)**: 관리자 상세 1회에 INSERT 1회. 회원 상세는 조회 4회(본문 1 + 요약 3) → 5회, 직원 상세는 1 → 2회(가드의 소유 조회 별도). 풀러 `connection_limit=1`이라 왕복이 직렬로 하나 는다(약 10~20ms, 추정·미실측). 회원 웹 본인 조회는 늘지 않는다.
  - **수강 내역만 보러 들어와도 열람으로 남는다** — 상세 화면이 번호를 늘 보여 주므로 실제로 "보였다"는 사실과는 맞다.
  - **용량(design-constants ⑮)**: 행당 인덱스 포함 약 320B(계산). 지점당 하루 관리자 상세 10회로 가정(근거 없음)하면 83곳 × 10 × 365 ≈ 30만 행/년 ≈ **연 100MB**. 자동 삭제가 없으므로 1년 뒤부터는 수동 삭제를 하지 않으면 계속 쌓인다.
  - 상세에 쓰기가 생겨 DB 쓰기 장애 시 상세 조회도 실패한다.

**재고 트리거**: AuditLog 테이블이 50MB를 넘을 때 → 보존 삭제를 자동화(배치, 승인 필요)하거나 새 테이블로 분리한다. 실측 몰림이 D42 재고선(약 25 rps)에 가까워질 때 → 기록을 응답 뒤 비동기로 미루거나 "번호 보기" 버튼안을 다시 본다. 지점별 열람 감사를 요구받을 때 → `after.branchId` 필터 또는 새 테이블.
