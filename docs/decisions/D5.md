# D5. Mock Payment 모듈 (실 PG 미연동)

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

**결정**: 이니시스/토스페이먼츠 같은 실제 PG 연동 대신 Mock Payment 모듈로 대체하되, 결제 상태 전이(대기→승인→실패/환불)와 예약 상태 연동 로직은 실제와 동일하게 구현한다. 토스페이먼츠 테스트 API 키 연동은 Phase 2 스트레치 목표로 남겨둔다. ([예약및결제 문서](../domains/예약및결제.md) §1)

**쉽게 말하면**: 진짜 카드사와 연결하는 대신, 결제가 성공한 것처럼 화면과 데이터만 그럴듯하게 흉내 내는 "가짜 결제" 기능을 만들었습니다.

**근거**: 실 PG 연동은 사업자 등록과 가맹점 심사가 필요해 개인 포트폴리오 프로젝트로는 물리적으로 불가능하다. 반면 "결제 도메인 이해"를 보여주는 것이 심사 포인트이므로, 상태 머신 설계와 예외 처리(부분환불, 취소 정책)는 실물처럼 만들어 도메인 지식을 증명한다.

**타당성**: 높음. 불가능한 것(실 PG 가입)을 억지로 하지 않으면서도, 평가받고자 하는 것(결제 상태 전이 설계 능력)은 정확히 겨냥했다. 토스페이먼츠 테스트 키 옵션을 스트레치로 남긴 것도 시간이 남을 때의 확장 경로를 미리 설계해둔 좋은 판단이다.

**장점**
- 결제 상태 전이 로직(대기→승인→환불)을 PG 응답 지연/실패 같은 외부 변수 없이 안정적으로 테스트·시연 가능
- `mockApprovalNo`(모의 승인번호) 필드로 "실제 결제인 것처럼" 시연 완성도를 챙김

**단점·리스크**
- 실 PG 웹훅(비동기 결제 승인 통지) 처리 경험은 이 구조로는 얻을 수 없음 — 만약 토스페이먼츠 테스트 연동까지 간다면 이 부분이 새로운 학습 포인트가 될 것
- 서버에서 Program 가격을 재조회해 검증(예약및결제 A-7)한다는 원칙은 명시했으나, "결제 금액 위변조 방지"라는 보안 관점의 테스트 케이스가 decisions/(현 문서) 이전엔 테스트 체크리스트에 없었음(예약및결제 A-9 참고) — 실제 구현 시 추가 권장
