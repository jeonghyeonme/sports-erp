# D55. 느린 요청은 3초에 "처리 중", 15초에 "응답이 늦다"를 화면 위에 띄운다 (2026-10-16)

> 결정 기록 [인덱스](README.md) · 경위는 [log/120](../log/120.md) · RFP 1-1 #11 시스템성능 "처리속도 느린 작업은 사전 알림"(D51 M8)

**컨텍스트(Driver)**: 운영자용 경보(Lambda·예산)는 있지만 사용자 화면에는 "불러오는 중" 표시뿐이었다. 사용자는 느린 것인지 멈춘 것인지 알 수 없다.

**상위 목표(D53)**: 노하우 습득 — 응답 시간 기준을 실측값과 사람의 인지 한계로 정하는 법을 익힌다. **핵심 변수**: 운영 실측 요청당 처리 약 40ms, 콜드 스타트 약 1.4초([D49](D49.md)·[D50](D50.md)) — 기준이 1.4초보다 짧으면 콜드 스타트마다 안내가 뜬다. **답안지**: Nielsen 응답 한계(1초까지는 흐름 유지, 10초면 주의를 잃는다).

## 결정 (사용자 선택 2026-10-16, 사용자 설명: 없음 — 추천안 선택)

1. 진행 중인 API 요청 중 **가장 오래된 것이 3초**를 넘으면 화면 위 가운데에 "처리 중입니다. 잠시만 기다려 주세요.", **15초**를 넘으면 "응답이 늦어지고 있습니다. 네트워크 연결을 확인하고, 계속되면 잠시 뒤 다시 시도해 주세요."(주황). 요청이 끝나면 사라진다.
2. 두 앱(admin-web·member-web)의 axios 인터셉터 한 곳에서 잰다(`lib/slow-requests.ts` — 공유 UI 패키지가 없어 두 앱에 같은 파일). 화면마다 붙이지 않는다. 회원 웹은 401 재시도 전에 원래 요청의 측정을 끝내고, 재시도는 새로 잰다.
3. 새로고침 버튼은 두지 않는다 — 관리자 웹은 access token을 메모리에 둬 새로고침하면 로그아웃된다.

## 대안 → 트레이드오프

| 대안 | 얻는 것 | 비용·위험 | 판단 |
|---|---|---|---|
| **3초 안내 + 15초 재시도 제안(선택)** | 콜드 스타트(1.4초)에는 안 뜨고, 멈춘 듯한 경우를 구분해 안내 | 3초 안쪽의 느림은 알리지 않는다 | 선택 |
| 2초 안내만 | 더 일찍 알림 | 콜드 스타트가 2초에 가까우면 자주 뜬다, 멈춤 구분 없음 | 기각 |
| 5초 안내만 | 거의 안 뜸 | 3~5초 기다림을 그대로 둔다 | 기각 |

**재고 트리거**: 콜드 스타트가 2초를 넘을 때(D50 재고와 같이 본다), 안내가 자주 뜬다는 사용자 보고가 있을 때.
