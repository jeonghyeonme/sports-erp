# D10. 혼잡도: 체크인 기반 자동계산 + 수동 보정 하이브리드

> 결정 기록 [인덱스](README.md) · 원래 2-1 기술결정사항 문서의 한 절이었다(2026-10-01 분해).

> **2026-09-20 범위 조정**: 이 결정의 "자동 계산" 절반(QR 체크인·5분 크론)은 구현하지 않기로 했다 — 수동 보정만으로 RFP 요건이 충족되고(혼잡도관리 A-8), 회원 앱·스케줄러가 없어서다. 아래 결정 내용은 향후 확장 방향으로 남겨둔다.

**결정**: IoT 센서/CCTV 기반 실측 대신 예약·QR체크인 데이터로 5분 주기 자동 계산하고, 관리자가 필요 시 수동으로 덮어쓸 수 있는 하이브리드 방식을 채택했다. ([혼잡도관리 문서](../domains/혼잡도관리.md) §1, §4)

**쉽게 말하면**: 사람을 직접 세는 장비가 없으니, 회원들이 QR로 체크인/체크아웃한 기록을 세어서 지금 몇 명 있는지 자동으로 추정하고, 이상하면 관리자가 손으로 고칠 수 있게 했습니다.

**근거**: IoT 하드웨어는 개인 포트폴리오로 확보 불가능하다. 대신 이미 시스템에 존재하는 데이터(예약, 체크인)로 근사치를 계산하는 것은 실제 중소 피트니스 업계에서도 쓰이는 현실적 대안이라고 문서 스스로 밝히고 있다(혼잡도관리 §0).

**타당성**: 높음. "왜 이렇게 설계했는지"를 발표에서 논리적으로 방어할 수 있는 지점이라고 문서가 미리 언급한 것 자체가, 이 결정이 타협이 아니라 의도된 설계임을 보여준다. 5분 주기는 원본 요구사항의 "최대 30분 이내 반영"을 상회 달성하는 수치로, 목표 대비 충분한 여유를 뒀다.

**장점**
- 하드웨어 의존성 없이 소프트웨어만으로 실사용 가능한 근사치를 제공
- 자동/수동 값이 충돌할 때의 동작(수동 보정 후 다음 tick에 자동이 override)까지 명시해 "의도한 동작"과 "버그"를 구분해뒀음

**단점·리스크**
- 체크아웃을 깜빡하는 회원이 많으면(문서도 "실무에서 매우 흔함"이라 인정) 혼잡도가 실제보다 부풀어 보이는 근본적 한계가 있음 — 23:00 강제 마감 배치(혼잡도관리 A-6)로 완화하지만 당일 중 누적 오차는 남음
- QR 체크인이라는 행동 자체를 회원이 안 하면(스캔을 안 하고 그냥 이용) 자동계산의 원천 데이터가 애초에 없음 — 관리자 대리 체크인(혼잡도관리 A-6)으로 보완하지만 결국 사람이 챙겨야 하는 운영 부담으로 이전됨
