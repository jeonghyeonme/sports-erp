# D46. 지점 격리 검사를 전역 BranchScopeGuard 한 곳으로 — 라우트는 `@ScopedResource`로 리소스를 선언한다

> 결정 기록 [인덱스](README.md) · 경위는 [log/095](../log/095.md) · [D2](D2.md)(branchId 컬럼 격리) 위에 얹는다. 실DB 전환(D26~D36)을 전제로 미뤄 둔 "공통 검사 중앙화"를 마무리한다(D29가 계약 종료 판정을 먼저 모았다).

**상태**: 결정·구현(2026-10-10, 사용자 승인).

## 컨텍스트

- 지점 격리는 두 겹이었다.
  - `BranchScopeGuard`: `branchId` 파라미터·쿼리만 봤고, 컨트롤러 6곳에만 `@UseGuards`로 붙어 있었다.
  - 컨트롤러별 `findXOrThrow` + `assert*`: `:id` 라우트를 맡았다. 같은 규칙이 10개 컨트롤러에 조금씩 다르게 복사돼 있었다(회원·직원 "본인", 문서 "전사 공개", 근태 "직원의 현재 지점").
- 가드가 없는 컨트롤러(자산·결제·근태·문서)는 남의 `branchId`를 손으로 본인 지점으로 바꿨다. 새 `:id` 라우트가 검사를 빠뜨려도 잡아 줄 장치는 사람이 기억해 공격 표에 넣는 것뿐이었다.
- 인메모리 시절에는 리소스 주인을 읽는 공통 방법이 없어 중앙화를 미뤘다. 이제 모든 리소스가 DB에 있어 id 하나로 소유 지점을 읽을 수 있다.

## 결정

1. **전역 가드**: `BranchScopeGuard`를 `APP_GUARD`로 등록한다(JwtAuthGuard → RolesGuard 다음). 모든 인증 라우트가 지난다. `@Public`은 건너뛴다.
2. **1단계 — branchId 파라미터·쿼리**: 지금까지와 같다. SUPER_ADMIN 외에는 다른 지점을 지정하면 403 `BRANCH_SCOPE_VIOLATION`, 지정하지 않으면 본인 지점을 주입한다.
   - 전역이 되면서 자산·결제·근태 요약·결근 미리보기·문서 목록에서 BRANCH_ADMIN이 남의 `branchId`를 주면 **조용히 바꾸지 않고 403**이다.
3. **2단계 — 리소스 소유**: 라우트에 `@ScopedResource(kind, { param | query | body, code?, skipFor? })`를 붙이면 가드가 주인을 읽는다(`ScopeOwners`, 필요한 열만 select). 없으면 404(도메인 고유 코드), 남의 것이면 403.
   - 판정 순서:
     1. SUPER_ADMIN은 모두 통과한다.
     2. MEMBER는 회원·예약을 본인 것만 다룬다.
     3. STAFF는 직원·휴가를 본인 것만 다룬다.
     4. 그 밖에는 소유 지점이 일치해야 한다.
     5. 전사 문서(branchId null)는 모든 지점에 공개한다.
   - 거부 코드는 이관 전 값을 그대로 쓴다(`MEMBER_SCOPE_VIOLATION` 등). admin-web 오류 해결 문구가 이 코드를 보기 때문이다.
4. **선언 누락은 테스트가 잡는다**(`branch-scope-coverage.spec.ts`): 실제 앱의 라우트 표를 훑어, 경로 파라미터나 `staffId`·`memberId` 쿼리를 받는 라우트가 선언이나 `@BranchScopeExempt(이유)`를 갖는지 확인한다. 면제는 다음 세 경우다.
   - `@Public`, SUPER_ADMIN 전용 라우트, 경로 파라미터가 `branchId`뿐인 라우트는 테스트가 자동으로 면제한다.
   - 게시글은 지점 소유가 아니라 가시성 규칙(PostService)이라 `@BranchScopeExempt`로 이유를 남겨 면제한다.
5. **컨트롤러에 남는 것**: 지점이 아닌 규칙뿐이다 — 작성자 본인(게시글), 필드별 권한(회원이 담당 직원·메모 수정 불가), PT 세션이 그 회원 것인지.

## 대안

- **서비스 레이어 assert 공통 함수**: 호출을 잊는 문제가 그대로 남는다. 누락 검사도 할 수 없다.
- **Prisma 확장으로 모든 쿼리에 branchId 조건 자동 추가**: 조인·집계·본인(회원·직원) 규칙을 표현하기 어렵다. 숨김(404)과 거부(403)를 구분할 수 없다. 전사 문서 같은 예외가 쿼리마다 흩어진다.
- **Postgres 행 수준 보안(RLS)**: 가장 강하지만 Lambda가 `postgres` 역할 하나로 연결한다(D37). 요청마다 세션 변수를 설정해야 하고 풀러(`connection_limit=1`)와 충돌한다. 다음 단계 후보로 남긴다.

## 결과

- 요청당 쿼리 수:
  - 대부분의 `:id` 라우트는 그대로다. 컨트롤러가 하던 조회를 가드의 가벼운 select가 대신한다.
  - 직원 상세·문서 상세는 응답용 조회가 따로 있어 PK 조회가 1번 늘었다.
- 가드가 파이프보다 먼저 돌아서, 남의 리소스에 잘못된 본문을 보내면 이제 400이 아니라 403·404가 먼저 난다.

## 재고 트리거

- 지점 소유가 아닌 범위 규칙(예: 담당 직원만 보는 회원)이 생기면 `ScopeOwners`의 판정을 넓힐지, 그 라우트만 면제하고 서비스에서 볼지 정한다.
- RLS를 도입하면 1단계 주입과 2단계 판정 중 DB가 대신하는 부분을 걷어낸다.
