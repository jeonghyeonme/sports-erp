## 종합 평가

지금까지의 결정들은 하나의 일관된 원칙을 따른다: **"원본 요구사항의 표면적 형태가 아니라 실질적 의도를 파악해, 1인 개발이 가능한 범위 안에서 그 의도를 가장 잘 구현하는 방식을 선택한다."** RBAC 단순화(D1), 결재 단계 축소(D11), Mock Payment(D5), 혼잡도 하이브리드 계산(D10)이 모두 이 원칙의 적용 사례다.

동시에 이 프로젝트는 스코프를 줄인 영역에서도 **핵심 안전장치는 타협하지 않았다** — 지점 격리(D2)를 전역 가드 한 곳으로 강제하고(D46, 처음엔 가드+서비스 이중 적용), 예약 동시성(D6)을 트랜잭션 락으로 정합성 보장하며, STAFF Role 분리(D12)로 최소 권한 원칙을 뒤늦게라도 바로잡은 것이 그 증거다.

가장 반복적으로 나타나는 리스크 패턴은 **"애플리케이션 레벨의 수동 필터에 의존하는 안전장치"**다 — branchId 필터(D2), 소프트 삭제 필터(D9)가 대표적이며, 둘 다 "새 쿼리를 짤 때마다 사람이 기억해서 조건을 넣어야 한다"는 공통 약점을 가진다. Phase 1 구현을 시작할 때 Prisma 미들웨어로 이 두 필터를 전역화하는 것을 최우선으로 검토할 가치가 있다. → (2026-10-14 덧붙임) branchId 필터는 D46으로 전역 `BranchScopeGuard` + `@ScopedResource` 선언 + 선언 누락 테스트로 풀었다(Prisma 미들웨어가 아니라 가드). 소프트 삭제 필터는 여전히 쿼리마다 조건을 넣는다.
