# D58. 시연 데이터 고밀도화 — 클라이언트는 현장 사용자, 지점 5곳, 시드 실행일 기준 상대 날짜, 테스트 템플릿 둘 (2026-10-18)

> 결정 기록 [인덱스](README.md) · 경위는 [log/122](../log/122.md) · [D40](D40.md)의 데이터 부분(시드 83곳)을 대체한다. 설계 규모(요청량·처리 한계의 83곳 기준, design-constants)는 그대로다

**컨텍스트(Driver)**: 시드 83곳은 대부분 직원 1~3명·회원 0~4명에 이력이 없어 화면이 비어 보였고, 목록·집계·조회 속도를 실제 양에서 볼 수 없었다([log/106](../log/106.md) 계획, D51에서 5곳 방향). [D53](D53.md)은 "클라이언트가 누구이고 무엇을 중시하나"를 이 작업에서 정하기로 미뤄 두었다.

**상위 목표(D53)**: 노하우 습득 — 시드·테스트 데이터를 "실제 쓰는 양"으로 만들고, 그 위에서 성능을 숫자로 확인하는 실무 방식을 익힌다. **핵심 변수**: 현장 사용자가 매일 여는 화면의 밀도와 응답 속도. **답안지**: RFP의 "시스템 불안정 → 민원 → 계약 해지"(현장 체감이 계약을 좌우), 테스트 픽스처와 시연용 시드를 분리하는 일반적인 방식(작은 고정 픽스처 + 별도 대량 데이터).

## 결정 (사용자 결정 2026-10-18 — 사용자 설명: 없음)

1. **클라이언트 = 현장 사용자(지점 관리자·회원), 중시하는 것 = 사용성·속도**(D53 결정 3의 미정 사항을 닫는다). 추천안(RFP 발주처·본사)이 아닌 선택이다.
2. **지점은 5곳만** — 서초(정상, 히어로)·강남(정상, 히어로 — 고정 종료일 2026-10-15가 지나 상태와 어긋나 2027-09-30으로)·마포(갱신 임박)·송파(만료)·노원(계약 종료). 나머지 78곳은 시드에서 뺀다(`branch-generator.ts` 삭제, 대조군 3곳은 `side-branch-fixtures.ts`). 대조군 지점장은 BRANCH_ADMIN 계정이다. 추천안(83곳 유지 + 5곳만 고밀도)이 아닌 선택이다.
3. **날짜는 시드 실행일(KST) 기준 상대값** — 지난 90일 이력 + 앞으로 3주 회차. 고정 씨앗 PRNG만 써서 같은 날 돌리면 같은 데이터다(두 번 실행 지문 비교로 확인).
4. **기준 시드와 시연 데이터 층을 나눈다** — `prisma/seed.ts`(5곳 최소 데이터, 대부분의 테스트가 쓴다) 위에 `prisma/demo-layer.ts`(직원 지점당 4~6명·파견 이력, 회원 30~60명, 예약·결제 약 5,700건, 근태·휴가·업무일지, 게시글, 자산, 문서, 업무지원 요청, 혼잡도 스냅샷)를 얹는다. 실행은 `npm run seed:demo --workspace=apps/api`. 로컬이 아닌 DB에는 막아 두었다(배포 DB 쓰기는 승인 — CLAUDE.md).
5. **jest 템플릿 둘** — globalSetup이 `<기준>_dense`를 한 번 만들고, 파일 맨 위에서 `useDenseTemplate()`을 부른 파일만 그 템플릿으로 워커 DB를 만든다. 고밀도 파일은 사용자가 고른 7개(`list-pagination`·`branch-isolation`·`list-filters`·`attendance-absence`·`catalog-flow`·`posts-member-visibility`·`reservation-capacity`)와 새 `performance`. 성능은 데이터 양 위에서 재야 한다(사용자 판단).
6. 이번 범위는 시드 재작성만 — R1·R2 결함 수정, 지점별 시나리오 실행([engineering-risks](../architecture/engineering-risks.md) §4)은 하지 않았다.

## 대안 → 트레이드오프

| 대안 | 얻는 것 | 비용·위험 | 판단 |
|---|---|---|---|
| **5곳 + 시연 층 분리(선택)** | 화면 밀도, 성능을 실제 양에서 잰다, 대부분 테스트는 작은 데이터라 기대값이 단단하다 | 템플릿 하나 더(전체 jest +약 3초), 고밀도 파일은 개수를 박지 않고 DB에서 센다 | 선택 |
| 83곳 유지 + 5곳만 고밀도 | 지점 목록 규모 화면을 계속 시연 | 빈 지점 78곳이 그대로, 시드가 무거움 | 기각(사용자) |
| 모든 테스트를 고밀도 위에서 | 템플릿 하나 | 시드 개수에 묶인 기대값 수십 곳이 흔들린다, 테스트가 무엇을 보는지 흐려진다 | 기각 |
| 날짜 고정(예: 2026-09) | 완전한 재현 | 날짜가 지나면 "앞으로의 회차"·"이번 달 결근"이 사라진다(히어로 회차가 이미 겪음, ADR-RSV-05) | 기각 |

**결과**: 고밀도 데이터에서 현장 화면 14개 경로의 응답 중앙값이 로컬 6~17ms(한도 1,500ms — CI 편차 감안, 데이터 양에 비례해 느려지는 회귀를 잡는 용도). 배포 DB는 아직 83곳이다 — 줄이고 시연 층을 얹는 것은 배포 DB 쓰기라 승인 대상이고 SQL·절차는 아직 없다.

**재고 트리거**: 지점 목록 규모(수십 곳) 화면을 다시 시연해야 할 때, 고밀도 템플릿 생성이 10초를 넘을 때, 성능 한도에 실제로 걸리는 경로가 생길 때.
