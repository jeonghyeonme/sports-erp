# 02. 인사정보관리 (Staff Management)

## 1. 개요 및 조정사항

원본 요구사항: "현장별 인사관리 탭/코드 생성", "모든 인사기록정보 통합 조회", "권한/승인 시 수정 가능".

**조정**: "승인 기반 수정"의 복잡한 결재라인(다단계 결재)은 1인 개발 범위를 넘어서므로, **본인 신청 → 관리자 승인(1단계)** 구조로 단순화합니다. 대신 인사기록 자체(이력, 재직상태, 부서/직급)는 실사용 가능한 수준으로 충실히 구현합니다.

**추가 반영(2026-09-08, 원본 재확인)**: 원본 RFP(Ⅳ.과업내용 1.과업 목적, p.3~4)는 "당사의 조직 구조는 각 지사 개념으로 퍼져있는 형태이기 때문에 **행정 및 트레이너들 역시** 해당 지역 또는 본사 파견 형태로 직원이 투입되고 있는 상황"이라고 명시합니다. "행정"(관리자급)과 "트레이너"를 나란히 언급하므로, **BRANCH_ADMIN·STAFF 모두 특정 지점에 고정 고용된 게 아니라 스포이즘(본사) 소속으로 현장에 파견되는 구조**입니다. 이는 [13_차별화전략](../decisions/13_차별화전략.md)에서 한때 "확인 전 보류"로 다뤘던 항목이었으나, 원본에 직접 명시된 기본 고용구조임이 확인되어 **핵심 데이터 모델(§3)로 승격**합니다 — Staff의 `branchId`를 "고정 소속"이 아니라 "현재 파견 지점"으로 재정의하고, 파견 이력을 `StaffAssignment`로 관리합니다.

## 2. 사용자 스토리

- 본사 관리자로서, 신규 채용한 직원을 특정 지점에 배치(최초 파견)하고 싶다.
- 본사 관리자로서, 직원을 다른 지점으로 재배치(파견 전환)하고 그 이력을 남기고 싶다.
- 지점 관리자로서, 현재 우리 지점에 파견된 직원들의 직급/연락처 등 일상적인 인사정보를 관리하고 싶다.
- 본사 관리자로서, 전 지점 직원 현황을 하나의 화면에서 조회하고 싶다(원본 "한 화면 조회" 요건).
- 직원으로서, 내 인적사항 변경(연락처 등)을 신청하면 관리자 승인 후 반영되길 원한다.
- 지점 관리자로서, 퇴사 처리 시 퇴사일을 기록하고 계정을 자동으로 비활성화하고 싶다.

## 5. API 명세

| Method | Endpoint | 권한 | 설명 |
|---|---|---|---|
| GET | /api/v1/staff | SUPER_ADMIN(전체), BRANCH_ADMIN(현재 파견 지점) | 목록, `?branchId=&status=&position=` |
| POST | /api/v1/staff | **SUPER_ADMIN** | 신규 채용 등록 — `branchId`(최초 파견 지점) 필수, staffCode 자동 생성 + 최초 `StaffAssignment` 자동 생성 |
| GET | /api/v1/staff/:id | 해당 지점 권한자 | 상세 |
| PATCH | /api/v1/staff/:id | BRANCH_ADMIN(현재 파견 지점) | 인적사항 직접 수정(관리자는 승인절차 없이 즉시 수정 가능) — `branchId`는 이 API로 변경 불가(아래 파견 발령 API 전용) |
| PATCH | /api/v1/staff/:id/resign | BRANCH_ADMIN | 퇴사 처리 → resignDate 기록 + status=퇴사 + **연결된 Account.isActive=false 자동 처리** + 활성 `StaffAssignment.endDate` 마감 |

| GET | /api/v1/staff/:id/assignments | 해당 지점 권한자 또는 SUPER_ADMIN | 파견 이력 전체 조회 |

| PATCH | /api/v1/staff/change-requests/:id/approve | BRANCH_ADMIN | 승인 → Staff 필드 반영 |
| PATCH | /api/v1/staff/change-requests/:id/reject | BRANCH_ADMIN | 반려 |

## 6. 비즈니스 로직 & 엣지케이스

- `staffCode` 생성 규칙: **최초 배치 지점** 코드 + 해당 지점 내 순번(zero-padded 3자리). 동시 등록 race condition 방지를 위해 DB 트랜잭션 + 지점별 시퀀스 테이블 또는 `SELECT ... FOR UPDATE` 사용. 이후 파견 전환이 일어나도 재생성하지 않음(§3 참고)
- 퇴사 처리(`/resign`)는 **트랜잭션으로 Staff.status 변경 + Account.isActive=false + 활성 StaffAssignment.endDate 마감을 원자적으로 처리**(01문서 §6과 연결되는 핵심 지점 — 이 API가 "퇴사 즉시 접근차단"의 실제 트리거)
- **파견 발령(`/assignments`)**: 한 직원은 항상 `endDate=null`인 `StaffAssignment`가 최대 1건이어야 함(불변식) — 새 파견 생성 시 기존 활성 레코드를 먼저 마감하고 `Staff.branchId`를 새 지점으로 갱신하는 것까지 하나의 트랜잭션으로 묶음. 이 API는 SUPER_ADMIN 전용(§7) — 지점 관리자가 임의로 소속 직원을 다른 지점으로 보낼 수 없음(파견은 본사의 인력 배치 결정)
- 변경 신청은 필드 단위로 diff 저장(전체 프로필 재제출이 아님) → 승인자가 무엇이 바뀌는지 명확히 확인 가능
- 퇴사한 직원은 목록에서 기본적으로 숨기되(`status != 퇴사`), 필터로 조회 가능하게 유지(이력 보존)

## 7. 권한/보안 규칙

- BRANCH_ADMIN은 **현재 파견되어 있는 지점**의 직원만 CRUD(퇴사 처리 포함), 타 지점 staffId 접근 시 403(00문서 BranchScopeGuard) — 파견 이동 즉시 예전 지점 관리자는 접근 권한을 잃고 새 지점 관리자가 얻음
- **신규 등록·파견 발령은 SUPER_ADMIN 전용**(§1, §5) — 본사가 채용·배치의 주체라는 원본 RFP 구조를 그대로 반영. BRANCH_ADMIN은 "현재 배정된 인력의 일상 관리"만 담당
- Staff 본인(Role=STAFF)은 자신의 레코드 조회 + 변경 신청만 가능(직접 수정 불가). 01문서의 STAFF 권한 매트릭스와 동일하게 타 직원 레코드는 조회조차 불가
- 전화번호 등 연락처는 목록 화면에서는 뒷자리 마스킹(`010-****-1234`), 상세 화면 진입 시 전체 노출(접근 로그 AuditLog 기록)

## 8. 구현 우선순위

**Phase 1(필수)**: 직원 CRUD, `StaffAssignment` 기반 파견 모델(최초 등록 시 자동 생성 포함), 지점별 목록/필터, 퇴사 처리(+계정 비활성화 연동) — 파견이 원본이 명시한 기본 고용구조이므로 스텁이 아니라 Phase 1에 포함
**Phase 2(선택)**: 파견 발령 화면·이력 UI, 변경 신청/승인 워크플로우, 통합조회 화면의 고급 필터, 연락처 마스킹 UI

## 9. 테스트 체크리스트

- [ ] 신규 직원 등록 시 staffCode 자동 생성 및 중복 없음, 최초 StaffAssignment 동시 생성
- [ ] 파견 발령 시 기존 StaffAssignment.endDate 마감 + 신규 생성 + Staff.branchId 갱신이 원자적으로 처리됨(중간 실패 시 롤백)
- [ ] 파견 발령 후 예전 지점 BRANCH_ADMIN이 해당 staffId 조회 시 403, 새 지점 BRANCH_ADMIN은 조회 가능
- [ ] BRANCH_ADMIN이 파견 발령 API 호출 시도 시 403(SUPER_ADMIN 전용)
- [ ] 퇴사 처리 후 해당 계정으로 로그인 즉시 실패, 활성 StaffAssignment도 함께 마감됨
- [ ] BRANCH_ADMIN이 타 지점 직원 상세 조회 시 403
- [ ] 변경 신청 승인 시 Staff 레코드에 실제 반영, 반려 시 미반영
