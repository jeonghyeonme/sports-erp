# 도메인별 요구사항 매핑과 우선순위 (Step 1 보강)

> **상태**: 초안 (2026-09-22). [01_RFP_분류와_되묻기.md](./01_RFP_분류와_되묻기.md)의 결과물을 도메인(코드 모듈) 단위로 재배치한다.
> **목적**: 9개 도메인을 동시에 붙잡지 않기 위해, 어디부터 손댈지와 어느 도메인끼리 기준이 겹치는지를 먼저 본다.

## 우선순위 기준

- **상**: ① RFP 원문이 괄호·별도 문구로 명시적으로 강조 **또는** ② CLAUDE.md 4대 도메인 불변식(지점 데이터 격리·계약 종료 지점 차단·인사 권한 분리·Branch≠매장)에 직결 **또는** ③ 사업 존속 리스크(B01: 시스템 불안정 → 민원 → 계약 해지)와 직결
- **중**: 기능 요구가 명확하고 구현 가치가 있으나 위 세 조건에 해당하지 않음
- **하**: RFP에 없는 신규 제안 기능이거나, 사업 리스크와 무관한 게시성·부가 기능

우선순위는 **스킵 여부가 아니라 착수 순서**다. "하"도 산출물(§Ⅳ-3)이 요구하는 완결 시스템의 일부이므로 결국 다 다룬다.

## 도메인에 종속되지 않는 것 (횡단 관심사)

이 항목들은 특정 도메인 사이클 안에서 "완료"되지 않는다. 각 도메인이 하나씩 알아서 처리하게 두면 도메인마다 다른 기준이 생긴다. **별도로 한 번만 정하고 전 도메인이 재사용**해야 한다.

| 구분 | RFP 항목 | 왜 횡단인가 | 둘 곳 (제안) |
|---|---|---|---|
| 성능·가용성 | Q01~Q07 (CPU 90%·메모리 85%·성능시험·과부하 점검) | 시스템 전체 인프라 차원, 특정 도메인의 기능이 아님 | `architecture/` — Tier1 딥다이브 대상(이미 Q-01 산정 진행 중) |
| 보안(개인정보 비노출·접근통제) | Q10, Q11, Q12 | 개인정보를 다루는 모든 도메인(회원·인사·결제·문서)에 동일 규칙 적용 | `architecture/` — 권한관리 도메인의 구현물을 규칙으로 승격 |
| UI/UX 일관성 | Q13, Q14, Q16, Q17, Q18 | 모든 화면에 적용되는 디자인 시스템 영역 | `docs/3.design/` (이미 존재) |
| 데이터 관리(표준·이력·오류진단) | Q08, Q09 | 전 엔티티 대상 | `architecture/` |
| 법규 | C03(개인정보보호법 §26 — 본사-지점 위탁관계 자체가 이 조문의 적용 대상), C04(저작권) | 특정 기능이 아니라 사업 구조 전체에 적용 | `architecture/` 또는 컴플라이언스 체크리스트 |
| 사업 배경 | B01~B09 | Driver의 "왜"에 해당 — 이미 별도 분류돼 있음 | `overview/` |
| 수행 절차 | P01~P09 | 시스템 요구가 아니라 수행 방식 | 발표·보고 관련 문서(4.presentation 등) |

## 착수 순서 제안

**상 4개 → 중 3개 → 하 2개**. 상 안에서의 순서는 의존관계로 정한다: **권한관리**(다른 모든 도메인이 이걸 통해 인증·인가를 받음, 가장 먼저) → **회원관리**(지점 격리 테스트가 이미 있어 재료가 준비됨) → **예약및결제**(이미 Tier1 파일럿 확정) → **인사정보관리**(화면 격차가 있어 작업량이 더 필요).

## 이 문서의 한계

- F01(권한관리)은 도메인이면서 동시에 다른 도메인에 침투하는 **메커니즘**이기도 하다. 권한관리 사이클에서 만든 게이트가 나머지 8개 도메인의 API에 그대로 적용되므로, 사실상 권한관리 사이클의 산출물 일부가 횡단 관심사(위 표의 "보안" 행)로 승격된다.
- 우선순위는 1회성 판단이다. 도메인 사이클을 돌다가 근거가 바뀌면(예: 게시판에서 개인정보 이슈 발견) 재조정할 수 있다.
