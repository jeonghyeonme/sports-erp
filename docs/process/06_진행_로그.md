# 진행 로그

> **상태**: 진행 중. 이 문서는 "무엇을 만들었나"가 아니라 **"왜 이렇게 일하게 됐고, 무엇을 근거로 정했으며, 어떻게 검증했는가"**를 시간 순서로 남긴다.
> ADR([domains/*.md](../domains/))이 "이 결정 하나"를 기록한다면, 이 문서는 **결정들 사이의 인과관계와 이 프로젝트의 작업 방식 자체가 바뀐 지점**을 기록한다. 도메인 사이클을 하나 끝낼 때마다 여기에 한 단락을 추가한다([03_도메인_사이클_템플릿.md](./03_도메인_사이클_템플릿.md) §12에 반영).
> **읽는 법**: 각 단락은 "계기 → 한 일 → 근거/수치 → 결과" 순서다. 수치는 출처를 반드시 표시한다(실측/계산/가정).

## 1. 왜 "기능 구현"에서 "요구사항→Driver→검증"으로 방향을 틀었나

처음 요청은 "도메인별로 엣지케이스를 최대한 뽑아서 완성하자"였다. 실행해 보니(예약및결제 도메인 시범) 엣지케이스 목록 자체는 얼마든지 늘릴 수 있지만, **어떤 엣지케이스가 중요한지 판단할 기준이 없었다** — 그냥 감으로 "이것도 있고 저것도 있고"를 나열하는 상태였다.

사용자가 유튜브 영상 두 개를 제시했다:
- [AI에게 검증가능한 목표 제시하기](https://www.youtube.com/watch?v=OTttvhEHncQ) — 핵심 문장: "표준(ISO/IEC 25010·25023)은 무엇을 잴지 정의하지만, **목표값은 표준이 아니라 우리가 정한다.**"
- [티켓 예매 시스템 — 고객 요구에서 설계로](https://www.youtube.com/watch?v=7excI-0n2xk) — 핵심 흐름: 요구사항 분류(기능/품질/제약/**불변규칙**) → 모호함 되묻기 → 검증 가능한 형태로 구체화 → **Architecture Driver 식별(소수로 제한)** → 우선순위 → 설계 질문 → 대안·트레이드오프 → 결정(ADR) → 검증.

두 영상 다 자막을 전문 확인했다(YouTube 자동 자막 API로 직접 추출 — 처음엔 캡션 URL 서명이 만료돼 실패했고, 페이지를 다시 받아 재시도해 성공했다). **이게 이 프로젝트 전체 방법론의 출처다.** "엣지케이스를 많이 뽑는다"가 아니라 "요구사항을 분류하고, 그중 구조를 바꾸는 소수(Driver)만 골라 수치 근거로 대안을 비교한다"로 바뀌었다.

## 2. RFP를 다시 읽고 분류했다 (01번 문서)

`docs/제안요청서 원본.pdf` 11쪽을 pypdf로 전문 추출해 **문장 65개**를 기능(F)/품질(Q)/제약(C)/프로세스(P)/배경(B)으로 분류했다.

**핵심 수치**: 품질(Q) 20개 중 **14개가 판정 불가**(×), 수치가 있는 문장은 CPU 90%·메모리 85%·혼잡도 30분 셋뿐이고 그마저 측정 조건이 빠져 있었다. → "이 RFP는 기능은 명확하고 품질 목표는 비어 있다"는 결론. 이게 영상의 "목표값은 우리가 정한다"는 문장과 정확히 들어맞아, 이후 작업의 정당성 근거가 됐다.

## 3. 규모를 산정했다 (Q-01, 공용 산정 상수)

발주처에 다시 물을 수 없어 "임시 가정 + 확정 근거"로 진행하기로 했다(RFP §Ⅴ-7 "불분명한 사항은 협의해 결정"을 근거로 삼음). 사용자가 확정한 3가지: ①실측 데이터 없음(전부 산정) ②3년 후 목표치 기준 ③대표 업장 1,000세대.

산정 체인(**출처 유형을 매 단계 표시**):
1,000세대 × 2.2명/가구(**실측**: 2023 인구주택총조사 가구원수 분포 가중평균) = 2,200명 → × 25% 등록률(**가정, 약함**) = 550명 → × 36% 일일방문율(**가정**) = 200명/일 → Little's Law(L=λW, **계산**) + 피크계수 2.5배(**가정**) = 피크 동시 재실자 33명/지점 → 98개 업장(현재) 3,200명 → 130개 업장(3년 후, 연 10% 성장 **가정**) 4,300명.

이 값은 [architecture/design-constants.md](../architecture/design-constants.md)에 딱 한 번 만들어 두고, 이후 모든 도메인이 재사용한다(도메인마다 새로 산정하지 않는다는 원칙).

## 4. "9개 도메인, 감당이 안 된다" — 부담을 어떻게 줄였나

Q-01 하나에서 약한 가정이 3개(등록률·방문율·성장률) 나온 걸 보고, 사용자가 "9개 도메인에 이 깊이를 다 적용할 자신이 없다"고 했다. 대응은 두 가지:

1. **Tier1(정밀, 2~5개)/Tier2(경량, 규칙표)로 깊이를 나눈다.** 영상 자체가 이 원칙을 증명한다 — 티켓 시스템 예시도 Driver 5개, 설계 질문 3개로 끝났다(전체 요구사항을 다 이 무게로 다루지 않음).
2. **RFP 65개 문장을 9개 도메인에 매핑하고 상/중/하로 우선순위를 매겼다(02번 문서).** 기준: ①RFP 원문이 명시적으로 강조 ②CLAUDE.md 4대 불변식과 직결 ③사업 존속 리스크(B01: 불안정→민원→계약해지)와 직결. **결과: 상 4개(권한관리·인사정보관리·회원관리·예약및결제), 중 3개, 하 2개.** 상위 4개가 CLAUDE.md의 4대 불변식과 정확히 겹쳤다 — 기준이 이미 프로젝트가 암묵적으로 합의해 온 것과 일치한다는 신호로 받아들였다.

## 5. 도메인 사이클 템플릿을 확정했다 (03번 문서)

영상의 11단계를 도메인 하나에 반복 적용하는 틀을 만들었다. 두 가지를 도중에 고쳤다(둘 다 사용자 피드백):
- **레퍼런스(데이터모델·API·화면)는 결정의 결과물이라 문서 맨 아래(부록)에 둔다** — 위에 두면 "옛 스펙이 고정 사실이고 그 위에 결정을 얹는다"는 인상을 줘서, 실제로는 반대(Driver 분석이 스펙을 바꿀 수 있어야 함)라는 사용자 지적을 반영.
- **단, 사용자 스토리는 예외로 맨 앞에 둔다** — 스토리는 결정으로 바뀌지 않는 원본 입력값이라, 3자가 F01a 같은 ID를 만나기 전에 먼저 맥락을 잡게 하기 위함(영상도 고객의 원문 요구사항을 먼저 나열한 뒤 분류로 들어감).

## 6. 문서 구조를 실제로 재편했다

콘텐츠 3종류(도메인 지식/횡단 지식/과정 기록)를 3개 폴더(`domains/`/`architecture/`/`process/`)로 나누고, "병합 후 원본 유지"가 아니라 **"병합 후 원본 삭제(단, inbound 링크 정리 후)"**를 기본값으로 삼았다(사용자가 "유지는 최대한 피하라"고 명시). `docs/requirements/`(임시 작업 폴더)를 폐지하고 파일 6개를 이동, 상호 참조를 전부 고쳐 **링크 검증 스크립트로 0건 깨짐을 확인**했다(이후 매 사이클마다 재확인).

## 7. 4개 상위 도메인 사이클을 실행했다

권한관리 → 회원관리 → 인사정보관리 → 예약및결제 순서(의존관계 기준: 권한관리가 다른 모든 도메인의 게이트).

**사이클마다 코드를 실제로 열어봐서 발견한 문서-코드 괴리 3건**(감이 아니라 코드 대조로 확인):
- 회원관리: 옛 스펙이 "담당 직원 지점 검증 미구현"이라 적어 뒀지만 실제로는 구현돼 있었다(`assertStaffInBranch`).
- 인사정보관리: 코드 주석이 "파견발령 후 재로그인 필요"라고 적어 뒀지만, 실제 `JwtStrategy`는 매 요청 재조회라 재로그인 불필요했다(**코드 주석도 코드 자체보다 낡을 수 있다**는 사례).
- 인사정보관리(01번 문서 정정): Q-20의 임시 가정("본사 승인 필요")이 실제 1-3문서 결정("BRANCH_ADMIN 1단계 승인")과 달라 정정.

**도메인 간 패턴 재사용도 확인됐다**: "부분 unique 인덱스로 활성 상태만 유일성 강제"가 예약및결제(중복예약 방지, 원조) → 회원관리(ADR-MEM-02, 탈퇴 이메일 재사용) → 인사정보관리(ADR-STF-03, 활성 파견 유일성)로 **세 번 재사용**됐다. 우연이 아니라, 같은 문제 유형(활성 상태만 유일해야 함)을 도메인마다 다른 방식으로 풀지 않겠다는 원칙이 실제로 지켜진 것.

**가장 큰 발견**: 예약및결제는 이 프로젝트에서 가장 정교하게 설계된 도메인(1-7문서 §6의 "락 대상 정정" 논의)인데, **자동 테스트가 0건**이었다. 설계 품질과 검증 수준이 반비례하는 상태였다.

## 8. 발견한 구현 공백을 실제로 메웠다 (2026-09-22)

사용자가 "상인 것들까지만 문서 뽑고 구현 진행하자"고 정한 뒤, 4개 도메인 문서의 "다음 행동 제안" 중 **이미 구현된 로직에 테스트만 없는 항목**(저비용·고가치)을 우선 처리했다.

**테스트 파일 4개, 140개 테스트 전부 통과**:
- `auth-lifecycle.spec.ts`(권한관리): 퇴사 즉시 401, Role 전환 즉시 반영 — 2건
- `staff-assignment.spec.ts`(인사정보관리): 파견 발령 접근권 전환, 활성 파견 1건 유지, 퇴사 후 로그인 차단 — 4건
- `members-validation.spec.ts`(회원관리): 미성년 동의, 담당직원 지점일치, 전화번호 중복 경고 — 10건
- `reservation-capacity.spec.ts`(예약및결제): **정원 초과 방지**, 중복예약 방지, 모의결제 흐름, 취소 24시간 분기, VAT 계산 — 7건

**정원 초과 방지 테스트의 구체적 수치**: 신규 개설(예약 0건) capacity=2 회차에 서로 다른 회원 3명이 `Promise.all`로 동시 요청 → **정확히 2건 성공(201), 1건 409 SLOT_FULL**. 이 시나리오용 슬롯(`slot-seocho-yoga-2`, capacity=2)은 코드에 "SLOT_FULL 케이스를 바로 테스트할 수 있게" 라는 주석과 함께 이미 시드돼 있었는데, 그동안 쓰는 테스트가 없었다 — 이번에 처음 사용했다.

**VAT 계산 검증**: price 30000원 → `supplyAmount = round(30000/1.1) = 27273`, `vat = 30000-27273 = 2727`. 코드 그대로 재현되는지 확인.

**작업 중 발견한 환경 문제**: `apps/api/node_modules`가 아예 없고 `supertest`가 미설치 상태라 8개 테스트 스위트 전부가 실행 전에 실패했다 — `npm install`로 해결(제 코드 문제가 아니라 환경의 부분 설치 상태였음).

**검증 결과**: `npm run test`(8 suites, 140 passed) / `npm exec -- eslint .`(0 errors) / `npm run build`(성공). 4개 도메인 문서의 §11(검증 현황) 표를 "검증되지 않음"에서 "검증됨(2026-09-22) — 파일명"으로 갱신했다.
