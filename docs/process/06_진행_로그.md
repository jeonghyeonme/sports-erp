# 진행 로그

> **상태**: 진행 중. 이 문서는 "무엇을 만들었나"가 아니라 **"왜 이렇게 일하게 됐고, 무엇을 근거로 정했으며, 어떻게 검증했는가"**를 시간 순서로 남긴다.
> ADR([domains/*.md](../domains/))이 "이 결정 하나"를 기록한다면, 이 문서는 **결정들 사이의 인과관계와 이 프로젝트의 작업 방식 자체가 바뀐 지점**을 기록한다. 도메인 사이클을 하나 끝낼 때마다 여기에 한 단락을 추가한다([03_도메인_사이클_템플릿.md](./03_도메인_사이클_템플릿.md) §12에 반영).
> **읽는 법**: 각 단락은 "계기 → 한 일 → 근거/수치 → 결과" 순서다. 수치는 출처를 반드시 표시한다(실측/계산/가정).

## 1. 왜 "기능 구현"에서 "요구사항→Driver→검증"으로 방향을 틀었나

처음 요청은 "도메인별로 엣지케이스를 최대한 뽑아서 완성하자"였다. 실행해 보니(예약및결제 도메인 시범) 엣지케이스 목록 자체는 얼마든지 늘릴 수 있지만, **어떤 엣지케이스가 중요한지 판단할 기준이 없었다** — 그냥 감으로 "이것도 있고 저것도 있고"를 나열하는 상태였다.

사용자가 유튜브 영상 두 개를 제시했다:
- [AI에게 검증가능한 목표 제시하기](https://www.youtube.com/watch?v=OTttvhEHncQ) — 핵심 문장: "표준(ISO/IEC 25010·25023)은 무엇을 잴지 정의하지만, **목표값은 표준이 아니라 우리가 정한다.**"
- [티켓 예매 시스템 — 고객 요구에서 설계로](https://www.youtube.com/watch?v=7excI-0n2xk) — 핵심 흐름: 요구사항 분류(기능/품질/제약/**불변규칙**) → 모호함 되묻기 → 검증 가능한 형태로 구체화 → **Architecture Driver 식별(소수로 제한)** → 우선순위 → 설계 질문 → 대안·트레이드오프 → 결정(ADR) → 검증.

두 영상 다 자막을 전문 확인했다(YouTube 자동 자막 API로 직접 추출 — 처음엔 캡션 URL 서명이 만료돼 실패했고, 페이지를 다시 받아 재시도해 성공했다). **이게 이 프로젝트 전체 방법론의 출처다.** "엣지케이스를 많이 뽑는다"가 아니라 "요구사항을 분류하고, 그중 구조를 바꾸는 소수(Driver)만 골라 수치 근거로 대안을 비교한다"로 바뀌었다.

## 2. RFP를 다시 읽고 분류했다 (01번 문서)

`docs/제안요청서 원본.pdf` 11쪽을 pypdf로 전문 추출해 **문장 65개**를 기능(F)/품질(Q)/제약(C)/프로세스(P)/배경(B)으로 분류했다.

**핵심 수치**: 품질(Q) 20개 중 **14개가 판정 불가**(×), 수치가 있는 문장은 CPU 90%·메모리 85%·혼잡도 30분 셋뿐이고 그마저 측정 조건이 빠져 있었다. → "이 RFP는 기능은 명확하고 품질 목표는 비어 있다"는 결론. 이게 영상의 "목표값은 우리가 정한다"는 문장과 정확히 들어맞아, 이후 작업의 정당성 근거가 됐다.

## 3. 규모를 산정했다 (Q-01, 공용 산정 상수)

발주처에 다시 물을 수 없어 "임시 가정 + 확정 근거"로 진행하기로 했다(RFP §Ⅴ-7 "불분명한 사항은 협의해 결정"을 근거로 삼음). 사용자가 확정한 3가지: ①실측 데이터 없음(전부 산정) ②3년 후 목표치 기준 ③대표 업장 1,000세대.

산정 체인(**출처 유형을 매 단계 표시**):
1,000세대 × 2.2명/가구(**실측**: 2023 인구주택총조사 가구원수 분포 가중평균) = 2,200명 → × 25% 등록률(**가정, 약함**) = 550명 → × 36% 일일방문율(**가정**) = 200명/일 → Little's Law(L=λW, **계산**) + 피크계수 2.5배(**가정**) = 피크 동시 재실자 33명/지점 → 98개 업장(현재) 3,200명 → 130개 업장(3년 후, 연 10% 성장 **가정**) 4,300명.

이 값은 [architecture/design-constants.md](../architecture/design-constants.md)에 딱 한 번 만들어 두고, 이후 모든 도메인이 재사용한다(도메인마다 새로 산정하지 않는다는 원칙).

## 4. "9개 도메인, 감당이 안 된다" — 부담을 어떻게 줄였나

Q-01 하나에서 약한 가정이 3개(등록률·방문율·성장률) 나온 걸 보고, 사용자가 "9개 도메인에 이 깊이를 다 적용할 자신이 없다"고 했다. 대응은 두 가지:

1. **Tier1(정밀, 2~5개)/Tier2(경량, 규칙표)로 깊이를 나눈다.** 영상 자체가 이 원칙을 증명한다 — 티켓 시스템 예시도 Driver 5개, 설계 질문 3개로 끝났다(전체 요구사항을 다 이 무게로 다루지 않음).
2. **RFP 65개 문장을 9개 도메인에 매핑하고 상/중/하로 우선순위를 매겼다(02번 문서).** 기준: ①RFP 원문이 명시적으로 강조 ②CLAUDE.md 4대 불변식과 직결 ③사업 존속 리스크(B01: 불안정→민원→계약해지)와 직결. **결과: 상 4개(권한관리·인사정보관리·회원관리·예약및결제), 중 3개, 하 2개.** 상위 4개가 CLAUDE.md의 4대 불변식과 정확히 겹쳤다 — 기준이 이미 프로젝트가 암묵적으로 합의해 온 것과 일치한다는 신호로 받아들였다.

## 5. 도메인 사이클 템플릿을 확정했다 (03번 문서)

영상의 11단계를 도메인 하나에 반복 적용하는 틀을 만들었다. 두 가지를 도중에 고쳤다(둘 다 사용자 피드백):
- **레퍼런스(데이터모델·API·화면)는 결정의 결과물이라 문서 맨 아래(부록)에 둔다** — 위에 두면 "옛 스펙이 고정 사실이고 그 위에 결정을 얹는다"는 인상을 줘서, 실제로는 반대(Driver 분석이 스펙을 바꿀 수 있어야 함)라는 사용자 지적을 반영.
- **단, 사용자 스토리는 예외로 맨 앞에 둔다** — 스토리는 결정으로 바뀌지 않는 원본 입력값이라, 3자가 F01a 같은 ID를 만나기 전에 먼저 맥락을 잡게 하기 위함(영상도 고객의 원문 요구사항을 먼저 나열한 뒤 분류로 들어감).

## 6. 문서 구조를 실제로 재편했다

콘텐츠 3종류(도메인 지식/횡단 지식/과정 기록)를 3개 폴더(`domains/`/`architecture/`/`process/`)로 나누고, "병합 후 원본 유지"가 아니라 **"병합 후 원본 삭제(단, inbound 링크 정리 후)"**를 기본값으로 삼았다(사용자가 "유지는 최대한 피하라"고 명시). `docs/requirements/`(임시 작업 폴더)를 폐지하고 파일 6개를 이동, 상호 참조를 전부 고쳐 **링크 검증 스크립트로 0건 깨짐을 확인**했다(이후 매 사이클마다 재확인).

## 7. 4개 상위 도메인 사이클을 실행했다

권한관리 → 회원관리 → 인사정보관리 → 예약및결제 순서(의존관계 기준: 권한관리가 다른 모든 도메인의 게이트).

**사이클마다 코드를 실제로 열어봐서 발견한 문서-코드 괴리 3건**(감이 아니라 코드 대조로 확인):
- 회원관리: 옛 스펙이 "담당 직원 지점 검증 미구현"이라 적어 뒀지만 실제로는 구현돼 있었다(`assertStaffInBranch`).
- 인사정보관리: 코드 주석이 "파견발령 후 재로그인 필요"라고 적어 뒀지만, 실제 `JwtStrategy`는 매 요청 재조회라 재로그인 불필요했다(**코드 주석도 코드 자체보다 낡을 수 있다**는 사례).
- 인사정보관리(01번 문서 정정): Q-20의 임시 가정("본사 승인 필요")이 실제 1-3문서 결정("BRANCH_ADMIN 1단계 승인")과 달라 정정.

**도메인 간 패턴 재사용도 확인됐다**: "부분 unique 인덱스로 활성 상태만 유일성 강제"가 예약및결제(중복예약 방지, 원조) → 회원관리(ADR-MEM-02, 탈퇴 이메일 재사용) → 인사정보관리(ADR-STF-03, 활성 파견 유일성)로 **세 번 재사용**됐다. 우연이 아니라, 같은 문제 유형(활성 상태만 유일해야 함)을 도메인마다 다른 방식으로 풀지 않겠다는 원칙이 실제로 지켜진 것.

**가장 큰 발견**: 예약및결제는 이 프로젝트에서 가장 정교하게 설계된 도메인(1-7문서 §6의 "락 대상 정정" 논의)인데, **자동 테스트가 0건**이었다. 설계 품질과 검증 수준이 반비례하는 상태였다.

## 8. 발견한 구현 공백을 실제로 메웠다 (2026-09-22)

사용자가 "상인 것들까지만 문서 뽑고 구현 진행하자"고 정한 뒤, 4개 도메인 문서의 "다음 행동 제안" 중 **이미 구현된 로직에 테스트만 없는 항목**(저비용·고가치)을 우선 처리했다.

**테스트 파일 4개, 140개 테스트 전부 통과**:
- `auth-lifecycle.spec.ts`(권한관리): 퇴사 즉시 401, Role 전환 즉시 반영 — 2건
- `staff-assignment.spec.ts`(인사정보관리): 파견 발령 접근권 전환, 활성 파견 1건 유지, 퇴사 후 로그인 차단 — 4건
- `members-validation.spec.ts`(회원관리): 미성년 동의, 담당직원 지점일치, 전화번호 중복 경고 — 10건
- `reservation-capacity.spec.ts`(예약및결제): **정원 초과 방지**, 중복예약 방지, 모의결제 흐름, 취소 24시간 분기, VAT 계산 — 7건

**정원 초과 방지 테스트의 구체적 수치**: 신규 개설(예약 0건) capacity=2 회차에 서로 다른 회원 3명이 `Promise.all`로 동시 요청 → **정확히 2건 성공(201), 1건 409 SLOT_FULL**. 이 시나리오용 슬롯(`slot-seocho-yoga-2`, capacity=2)은 코드에 "SLOT_FULL 케이스를 바로 테스트할 수 있게" 라는 주석과 함께 이미 시드돼 있었는데, 그동안 쓰는 테스트가 없었다 — 이번에 처음 사용했다.

**VAT 계산 검증**: price 30000원 → `supplyAmount = round(30000/1.1) = 27273`, `vat = 30000-27273 = 2727`. 코드 그대로 재현되는지 확인.

**작업 중 발견한 환경 문제**: `apps/api/node_modules`가 아예 없고 `supertest`가 미설치 상태라 8개 테스트 스위트 전부가 실행 전에 실패했다 — `npm install`로 해결(제 코드 문제가 아니라 환경의 부분 설치 상태였음).

**검증 결과**: `npm run test`(8 suites, 140 passed) / `npm exec -- eslint .`(0 errors) / `npm run build`(성공). 4개 도메인 문서의 §11(검증 현황) 표를 "검증되지 않음"에서 "검증됨(2026-09-22) — 파일명"으로 갱신했다.

## 44. D30 — 직원·파견 이관: 쓰기가 있는 첫 도메인이라 "같은 생성기"가 아니라 "DB에서 채우는 미러"를 택했다 (2026-09-29)

**계기**: D29 순서(A안)의 2단계. 지점과 달리 직원은 채용·수정·퇴사·파견·권한 전환 쓰기가 있고, 아직 mock인 근태·문서·회원·게시판이 직원·계정을 **동기적으로** 읽는다. D29처럼 "mock과 DB를 같은 목록에서 만들고 일치 테스트"를 하면, 첫 쓰기에서 바로 어긋난다. 게다가 생성 직원 입사일이 실행 시각 기준 상대값이라 날마다 어긋난다.

**설계 판단**(상세: 2-1 D30):
- **원천은 DB, mock은 미러.** 앱이 뜰 때 `StaffService.onModuleInit`이 DB의 직원·파견·관리자 계정 전체로 mock 배열을 채우고, 직원 쓰기는 DB 커밋 뒤 해당 행을 다시 읽어 미러에 반영한다. 대안인 "mock 독자 전부를 비동기 DB 읽기로" 바꾸는 방식은 근태·문서·회원까지 한 번에 고치게 돼 단계를 나눈 의미가 사라진다. 미러는 다중 인스턴스(Lambda)에서 낡는다. 하지만 mock 전체가 이미 그 한계를 가지므로 새 한계는 아니다. 근태 등이 옮겨지면 미러도 사라진다.
- **이미 정한 ADR을 트랜잭션으로.** 퇴사 = 상태 + 계정 비활성화 + 파견 종료(ADR-STF-01). 채용 = 계정 + 직원(`allocateBranchCode`, ADR-STF-02) + 최초 파견. 파견 = 옛 파견 종료 → 새 파견 → DB 회원 담당 해제 → DB 강사 연결 해제 → 지점 이동(ADR-STF-04). 이 순서는 D28 트리거가 강제한다. §42에서 "강사 도메인 이관 때"로 미뤘던 강사 연결 해제도 DB 쪽은 이 트랜잭션에 들어갔다.
- **mock 쪽 부수효과는 커밋 뒤에.** mock 회원 담당 해제(ADR-STF-04)와 인사서류 보존기한 재계산(ADR-RES-02)은 두 저장소라 원자적이지 않다. 메모리 갱신이라 실패 경로가 없고, 해당 도메인이 옮겨지면 트랜잭션 안으로 들어간다.
- **이메일 유일성.** 미러가 직원 계정을 mock `accounts`에도 넣기 때문에, 회원 등록·연동의 기존 mock 검사가 코드 변경 없이 DB 직원 이메일까지 본다. 채용은 트랜잭션 전에 같은 검사로 mock 회원 이메일을 확인한다.

**데이터 신설**: mock의 생성 직원 192명에는 계정 id만 있고 계정 레코드가 없었다. DB에서는 `Staff.accountId`가 필수 FK라 계정을 만들었다(`gen-001-1@staff.spoism.example`, STAFF, 데모 비밀번호). 강남 관리자(최강남)도 mock에만 있었는데 DB로 옮겼다. `CodeSequence`의 STAFF 값은 시드한 직원번호의 지점별 최댓값으로 맞췄다. 안 맞추면 첫 채용이 `SEOCHO-001` 중복으로 P2002가 난다.

**테스트 인프라**: 직원 쓰기가 DB에 남으면서 같은 파일의 테스트끼리 상태가 샌다. `staff-assignment`에서 퇴사시킨 직원이 다음 테스트에서 퇴사 상태로 보였다. `test/helpers/worker-db.ts`의 `resetWorkerDb()`가 워커 DB를 기준 템플릿에서 다시 만든다. 모든 파일 시작 시(after-env `beforeAll`) 실행하고, 쓰기를 많이 하는 2개 스위트는 매 테스트마다 실행한다. D29의 "바꾼 상태 되돌리기"는 지점 상태처럼 좁은 경우에만 통하고, 쓰기 도메인에는 통째로 되돌리는 쪽이 맞다.

**D26 skip 3건 재활성화**: `auth-lifecycle` 2건(퇴사 → 로그인 불가, Role 전환 → 즉시 반영)과 `staff-assignment` 1건. D26에서 "직원 쓰기가 Prisma 계정에 반영되지 않는" 과도기 한계로 skip했던 것들이다. 이제 계정과 직원이 같은 DB 트랜잭션에 있어 기대값 변경 없이 통과한다.

**검증**: 전체 271 통과, skip 0(264 + skip 3건 재활성화 + `staff-mirror.spec.ts` 4건). 이 신규 스위트는 미러-DB 행 수·필드 일치, 채용 채번(SEOCHO-003)과 즉시 로그인, 양 저장소 이메일 충돌 409, 파견 시 DB·미러·mock 회원·DB 회원 동시 반영을 본다. api lint 0 에러(경고 1건은 기존 `main.ts`), api·admin-web 빌드 성공. **한 번 설명되지 않은 실패가 있었다**: 개발 중 전체 실행 1회에서 `smoke.spec.ts` 3건이 모두 실패했다. PG 로그에 FATAL은 없었고, 콜드 캐시를 포함한 이후 10여 회 실행에서 재현되지 않았다. 원인을 모르므로 "플레이크"로 분류하지 않고 기록만 남긴다. CI에서 다시 보이면 워커 DB 재생성(`DROP/CREATE DATABASE`)과 앱 부팅 사이의 연결 타이밍을 먼저 의심할 것.

**남은 한계**: 권한관리 화면의 Role 전환, 인사 화면의 채용·파견은 API만 있고(§ 2-3문서) 화면은 여전히 조회 위주다. **배포 반영**: 배포된 앱은 Supabase를 본다. mock에서 관리자·직원 계정이 빠졌으므로, Supabase에 직원·계정·파견·채번 시드를 넣기 전에 머지하면 정하늘 외 관리자·직원 로그인과 직원 목록이 사라진다. 외부 DB 쓰기라 사용자 승인을 받은 뒤 적용했다. 적용 전 조회하면서 **Supabase에는 계정·직원이 한 건도 없었다**는 걸 확인했다(D26 시드는 로컬에만 돌았고, 배포 앱의 로그인은 그동안 mock 폴백이 받아 주고 있었다). 정하늘을 포함한 관리자 계정 전체가 이번 시드에 들어갔다. 방법은 D29와 같다. `staffSeed()`로 upsert SQL을 만들고, 마이그레이션만 적용한 빈 로컬 DB에서 두 번 돌려 멱등성을 확인했다. 그 결과가 `prisma db seed` 결과와 지문(행 수 + 필드 md5)까지 같은지도 확인했다. 계정·직원은 JSON 배열 upsert로 넣었다. 파견·채번 순번은 규칙(`assignment-{staffId}`, 시작일=입사일 / 지점별 최대 순번)대로 SQL에서 직원 행으로 만들었다. 적용 후 Supabase 지문이 로컬과 4개 테이블 모두 같다(계정 196, 직원 195, 파견 195, STAFF 순번 98).
- **입사일 주의**: 생성 직원의 입사일은 생성기 실행 시각 기준 상대값이라 오늘(2026-09-29) 날짜로 고정돼 들어갔다. 이후 로컬에서 시드를 다시 돌리면 로컬 값만 날짜가 밀린다. DB가 원천이 된 지금은 의도된 동작이다.

## 45. D31 — 시설·강사·프로그램·회차 이관: 같은 미러 패턴, 그리고 D28 CHECK가 잡아낸 생성 데이터 결함 (2026-09-29)

**계기**: D29 순서의 3단계. 네 엔티티 모두 쓰기 API가 있고, 아직 mock인 예약·결제·회원·지점 건수가 동기적으로 읽는다. D30 직원과 같은 조건이라, 새 패턴을 만들지 않고 **D30 결정 1(DB 원천 + mock 미러)을 그대로 재사용**했다(상세: 2-1 D31). 새로 검토한 대안은 "예약까지 같이 옮기기"였다. 예약은 회원(4단계)을 참조하므로, 예약만 옮기면 D29가 막으려던 "참조되는 쪽이 아직 mock" 상태가 반대 방향으로 생긴다. 그래서 기각했다.

**구현**: `FacilityService`·`InstructorService`·`ProgramService`(회차 포함)를 만들고 세 컨트롤러를 옮겼다. 자기 조회 API는 DB에서 읽는다. mock의 해당 쓰기 메서드는 지웠고, 검증 규칙(ADR-PRG-01~03, ADR-FAC-01~03, 07문서 §3-2 전이표·§6 가격 정규화, 08문서 §4 5단계)은 문구·순서 그대로 옮겼다. 미러 갱신 헬퍼(`src/mock-data/mirror.ts`)는 배열 참조를 유지한다. mock 독자가 `mockData.programs` 배열을 그대로 들고 읽기 때문이다.

- **ADR-STF-04 숙제 해소**: D30 파견 트랜잭션은 DB 강사만 정리하고 mock 강사는 못 건드렸다. mock 강사 타입에 직원 연결 필드가 없었기 때문이다. 이제 강사 원천이 DB라, 연결을 푼 강사 id를 트랜잭션에서 돌려받아 커밋 뒤 미러에 반영한다.

## 21. 자원문서관리 3개 ADR(RES-01~03)을 전부 구현했다 (2026-09-25)

**RES-02(퇴사 시 보존기한 재계산)**: `resignStaff`가 계정 비활성화·파견 종료를 처리하는 자리에 HR_RECORD 문서 재계산을 추가했다. 테스트에서 "오늘 날짜 기준 계산이라 재직 중 값과 퇴사 후 값이 같은 날엔 구분이 안 된다"는 문제를 미리 피하려고, 실제 시나리오(같은 날 업로드→퇴사) 대신 일부러 틀린 값으로 시드한 문서가 올바른 값으로 고쳐지는지 확인하는 방식을 썼다 — 대조군(타 직원의 HR_RECORD, 타 카테고리, 소프트 삭제된 문서)이 안 바뀌는 것도 같이 확인했다.

## 26. 회원관리 D1(ADR-MEM-01, 오프라인↔앱 연동)을 구현했다 (2026-09-26)

**계기**: §25에 이어 "D3 진행하고 이후 작업들 전부 진행해달라"는 사용자 지시를 그대로 따라 D1으로 넘어왔다.

**한 일**: `POST /members/link`(공개 라우트)를 추가했다. `mock-data.service.ts`의 `linkMemberAccount()`가 memberNo+phone 동시 일치를 확인하고, 새 `Account`(role=MEMBER)를 만들어 기존 offline `Member` 레코드에 연결한다. 불일치 원인(회원번호가 틀렸는지 전화번호가 틀렸는지)은 구분해 알려주지 않고 동일하게 `MEMBER_LINK_MISMATCH`(400)로 묶었다 — §8 질문1이 이미 "부분 정보 노출 금지"를 판단 기준으로 짚어뒀던 것을 그대로 따른 것이다. 실패 횟수는 공격 대상이 되는 memberNo 기준으로 추적(1시간 슬라이딩 윈도, 5회 초과 시 429 `LINK_ATTEMPTS_EXCEEDED`) — `Map<memberNo, timestamp[]>`으로 충분해 새 mock 엔티티를 만들지 않았다. WITHDRAWN 회원은 연동 대상에서 제외했다(도메인 문서가 명시하진 않았지만, 이미 로그인이 막힌 탈퇴 회원에게 새 앱 계정을 붙여주는 건 다른 불변식과 어긋난다고 판단해 여기서 결정). 연동 성공 시 로그인과 동일한 토큰 발급 경로(`AuthService.issueSession()` — 기존 `login()`을 리팩터링해 뽑아냄)로 바로 로그인시킨다.

**부수 발견**: 구현 중 `BranchScopeGuard`가 `@Public()` 메타데이터를 전혀 보지 않고 `if (!user) return false`로 인증 없는 요청을 전부 403 처리하고 있다는 걸 발견했다 — `MembersController`가 컨트롤러 레벨로 이 가드를 걸고 있어 `/members/link`도 그대로 막혔다. `JwtAuthGuard`가 이미 쓰고 있던 `Reflector.getAllAndOverride(IS_PUBLIC_KEY, ...)` 패턴을 그대로 가져와 고쳤다 — 같은 문제를 다음 작업인 D2(`/members/register`)도 똑같이 겪었을 것이므로, 지금 고쳐서 두 번 겪지 않게 했다.

**검증**: `apps/api/test/member-link.spec.ts`(신규 10건) — 성공+즉시로그인, 회원번호/전화번호 불일치 동일취급, 이미 연동된 회원 409, 이메일 중복 409, WITHDRAWN 차단(대조군: DORMANT는 허용), 5회 초과 429(대조군: 다른 memberNo는 서로 영향 없음)까지 커버. `npm run test`(17 suites, **242 passed**), `eslint`(내 변경분 0 문제 — main.ts의 기존 무관 경고 1건만 유지), `nest build` 클린.

## 27. 회원관리 D2(ADR-MEM-02, 앱 회원가입 — 탈퇴 회원 이메일 재사용)를 구현했다 (2026-09-26)

**계기**: §26(D1)에 이어 같은 사용자 지시("전부 진행해달라")를 계속 따랐다. 이 사이클의 마지막 ADR.

**한 일**: `POST /members/register`(공개 라우트)를 추가했다. 핵심은 §8 질문2가 이미 결정해둔 "부분 unique 인덱스(활성 계정끼리만 유일)"를 실제로 구현하는 것이었다 — `mock-data.service.ts`에 `isEmailTakenByActiveAccount()`(`isActive !== false`인 계정끼리만 이메일 중복을 검사)를 신설했다. 이걸 만들면서 D1(§26)에서 이미 짠 `linkMemberAccount()`의 이메일 중복 검사(`findAccountByEmail()` 그대로 사용 — 활성 여부를 안 가림)가 이 ADR의 원칙과 어긋난다는 걸 발견해 **같은 메서드를 쓰도록 함께 고쳤다** — 도메인 문서 §8이 "같은 문제를 도메인마다 다르게 풀지 않는다"고 적어둔 원칙이 도메인 하나 안에서도 그대로 적용돼야 한다고 판단했다. `registerMember()`는 이메일 중복 검사를 가장 먼저 하고 나서 기존 `createMember()`(계약종료 409·미성년 무동의 400·전화번호 중복 경고를 이미 갖추고 있음)를 그대로 호출해 재사용했다 — 인메모리 배열이라 트랜잭션이 없으니, "실패 가능성이 있는 검사를 먼저 해서 부분 생성을 막는" 순서로 롤백을 대신한 것이다(중복 로직을 새로 안 짜도 됨은 덤). 가입 성공 시 D1과 동일하게 `AuthService.issueSession()`으로 즉시 로그인시킨다.

**검증**: `apps/api/test/member-register.spec.ts`(신규 9건) — 가입+즉시로그인, 계약종료 409(불변규칙 2), 미성년 무동의 400(불변규칙 3, 대조군: 동의 시 성공), 활성 계정 이메일 중복 409, **이 ADR의 핵심 시나리오(회원을 탈퇴시켜 계정을 비활성화한 뒤 같은 이메일로 재가입 → 성공, 원래 계정의 이메일은 변형 없이 그대로 보존됨을 확인)**, 실패 시 Member가 생성되지 않음(순서로 롤백을 대신한다는 주장의 검증), 존재하지 않는 지점 404까지 커버. `npm run test`(18 suites, **251 passed**), `eslint`·`nest build` 클린.

**커밋**: 이 절을 포함한 커밋. 이걸로 회원관리 도메인 D1·D2·D3(ADR-MEM-01~03) 전부 구현·검증 완료됐다 — §11 "다음 행동 제안"에 남은 건 AUTH-T05 문서 동기화(§12)뿐이다.

## 28. AUTH-T05를 권한관리 문서에 동기화했다 — 회원관리 도메인 사이클 마무리 (2026-09-26)

## 29. Supabase에 스키마만 우선 배포했다 — 실DB 전환의 첫 단계 (2026-09-27)

**계기**: 사용자가 "인프라에 올리는 것부터 하고 싶다"며 이미 연결해둔 Supabase MCP 커넥터로 DB를 시도해보고 싶다고 요청. CLAUDE.md가 "MockDataService→실DB 전환은 사용자 승인 필요(ADR 대상)"로 명시해둔 결정이라, 범위부터 사용자에게 확인했다 — **API를 지금 바로 Prisma로 전환**할지, **스키마만 먼저 배포**해서 인프라를 준비만 해둘지. 사용자가 후자를 선택했다("오늘 안에 끝남, 지금 도는 앱을 안 건드림" 쪽).

**한 일**: 기존 Supabase 프로젝트 3개(`Portfolio Website Structure`·`Portfolio Site V2`·`Kmong_Dev`)는 전부 이 앱과 무관한 다른 용도라 재사용하지 않고, `sports-erp` 신규 프로젝트를 만들었다(조직 `jeonghyeonme's Org`, free 플랜, 리전 `ap-northeast-2`/서울, 프로젝트 ref `blbjnozojvromktprqhv`). `apps/api/prisma/schema.prisma`에서 `npx prisma migrate diff --from-empty --to-schema-datamodel schema.prisma --script`로 SQL을 뽑아(이 컨테이너에서 DATABASE_URL로 직접 Postgres에 붙는 것보다, Supabase MCP의 `apply_migration`으로 관리 API를 통해 적용하는 쪽이 네트워크 정책상 더 안정적이라 이 경로를 택함) 27개 테이블을 전부 생성했다.

**스키마 드리프트 발견**: 이 과정에서 `schema.prisma`가 실제 `MockDataService` 현실보다 낡아 있다는 걸 확인했다 — **자원문서관리 도메인의 `Asset`·`Document` 모델이 Prisma 스키마에 아예 없다**(2026-09-19에 mock에만 추가되고 스키마엔 반영 안 됨). `CourseEnrollment.status` enum도 스키마는 `ACTIVE`/`EXPIRED` 2종인데 mock은 `ACTIVE`/`COMPLETED`/`CANCELLED` 3종으로 다르다(2026-09-26 D3 작업 때 스키마 갱신을 빠뜨림). 지금은 "스키마만 배포"가 범위라 스키마 자체를 고치지 않고 있는 그대로 배포했다 — 실제 전환 작업 시작 전에 스키마를 mock과 다시 맞추는 게 먼저 할 일로 남는다.

**보안 확인**: 테이블 생성 직후 Supabase 자체 어드바이저리가 27개 테이블 전부 RLS(Row Level Security) 비활성 상태라고 경고했다. 이 프로젝트는 Supabase 클라이언트 라이브러리(anon key)를 전혀 쓰지 않고 NestJS가 `DATABASE_URL`로 Postgres에 직접 붙는 구조라 당장 기능은 안 깨지지만, anon key가 어디선가 실수로 노출되면 PostgREST를 통해 27개 테이블이 전부 읽기/쓰기 가능해진다 — 애초에 이 프로젝트가 PostgREST 경로 자체를 쓸 계획이 없으므로 정책 없이 RLS만 켜는(=REST 경로를 통째로 막는) 게 안전한 기본값이라고 판단했지만, 이건 사용자 승인 없이 자동 적용하지 않고 SQL만 제시했다(Supabase MCP 자체 가이드라인이기도 함).

**검증**: `list_tables`로 27개 테이블·컬럼·FK가 스키마 그대로 반영된 것 확인. 아직 `apps/api`는 이 DB를 전혀 쓰지 않는다 — "연결은 됐지만 사용 중은 아님" 상태이며, 이 사실을 사용자에게 명시적으로 전달했다. **추가(같은 날)**: 사용자가 "정책 없이 RLS만 켜기"를 선택해 27개 테이블 전부 `ENABLE ROW LEVEL SECURITY` 적용, `list_tables`로 전 테이블 `rls_enabled: true` 재확인.

**커밋**: 코드 변경 없음(원격 Supabase 프로젝트에만 DDL 적용). 이 로그 절 자체가 이번 변경의 유일한 저장소 기록이라, 다음에 실제 Prisma 전환에 착수할 때 이 절부터 읽을 것.

## 30. Render에 admin-web·api를 배포했다 (2026-09-27)

**계기**: §29(Supabase 스키마 배포)에 이어 "인프라에 올리는 것" 두 번째 단계. Vercel도 커넥터로 연결돼 있었지만 툴 목록이 조회/디버깅용(`list_projects`, `get_deployment` 등)뿐이라 새 배포를 만들 수 없었다 — Render는 `create_web_service`·`create_static_site`가 있어 실제로 생성까지 가능해서 admin-web·api 둘 다 Render 하나로 몰았다.

**한 일**: Render 워크스페이스(`Jeonghyeonme's workspace`)에 두 서비스를 만들었다 — `sports-erp-api`(Web Service, Node, Singapore, free)와 `sports-erp-web`(Static Site). 모노레포라 MCP `create_*` 툴에 root-directory 옵션이 없어서, buildCommand 자체를 `npm install && npm run build --workspace=apps/api`처럼 워크스페이스 플래그로 해결했다. admin-web이 API URL을 빌드 타임에 굳히는 구조(Vite)라, **api를 먼저 만들어 URL(`https://sports-erp-api.onrender.com`)을 확정한 뒤 그 값을 admin-web의 `VITE_API_BASE_URL`에 넣어 만드는 순서**로 진행했다.

**버그 발견·수정**: api 첫 빌드가 16초 만에 `sh: 1: nest: not found`로 실패했다. 원인은 내가 넣은 `NODE_ENV=production` 환경변수 — npm이 이걸 보고 `npm install`을 devDependencies 제외 모드로 돌려서 `@nestjs/cli`(devDependency, `nest` 바이너리 제공)가 설치 안 됐다. `NPM_CONFIG_PRODUCTION=false`를 추가해 npm이 NODE_ENV와 무관하게 devDependencies를 설치하도록 강제해 해결했다. admin-web(Static Site)은 애초에 NODE_ENV를 안 건드려서 같은 문제 없이 첫 시도에 성공했다.

**JWT 시크릿**: `.env.example`의 `change-me` 계열 기본값 대신 `crypto.randomBytes(32).toString('hex')`로 실제 프로덕션용 시크릿을 생성해 `JWT_ACCESS_SECRET`·`JWT_REFRESH_SECRET`으로 넣었다(레포에는 커밋 안 함 — Render 환경변수로만 존재).

**검증**: Render `get_deploy`로 두 서비스 다 `status: live` 확인. 이 컨테이너 자체의 네트워크 정책이 `onrender.com`을 막고 있어서(egress policy — curl이 `CONNECT tunnel failed, response 403`) 내가 직접 curl로 확인할 수는 없었지만, Render `list_logs`(type=app)로 Nest 부팅 로그(`AppModule dependencies initialized`, `/api/v1/health` 라우트 매핑까지)를 확인해 실제 기동을 검증했다.

**Cloudflare는 이번엔 보류**: DDoS/WAF는 사용자 소유 도메인을 Cloudflare가 DNS 서빙하면서 붙는 기능이라, 지금처럼 Render의 `*.onrender.com` 무료 서브도메인만 있는 상태에선 성립하지 않는다(Render가 소유한 존이라 Cloudflare 앞에 못 세움). 연결해둔 "Cloudflare Developer Platform" 커넥터도 Workers/KV/D1/R2용이라 DNS/Zone/방화벽 툴 자체가 없다. 사용자가 "도메인 확보 전까지 보류"를 선택 — 부하테스트(k6)는 도메인과 무관하니 다음 단계로 그대로 진행.

**커밋**: 코드 변경 없음(Render 서비스 생성은 원격 인프라 작업). 이 로그 절이 유일한 기록.

## 31. k6 실측으로 로그인 CPU 스로틀링을 발견했다 — D14 재검토 (2026-09-27)

**계기**: §30(Render 배포)에 이어, §29~30에서 미뤄뒀던 부하테스트를 사용자가 직접 로컬 Windows 환경에서 실행했다(이 세션 컨테이너는 `onrender.com` 접근이 막혀 있어 대신 실행할 수 없었음 — §30 참고). `loadtest/k6-scenarios.js`(login_ramp 0→40 VU 3분, browse_ramp 0→100 VU 3분, 순서대로 실행해 서로 안 겹치게 설계)를 그대로 돌린 결과를 사용자가 붙여줬다.

**실측 결과**:
- **login_ramp**: `login_duration` avg **7.4초**, p90 **14.48초**, p95 **15.16초**, max 17.11초. 로컬(같은 코드, 같은 bcrypt cost=10)에서는 스모크 테스트 시 평균 60ms였던 것과 비교하면 **100배 이상** 느려졌다.
- **browse_ramp**: 에러는 0건이지만 `http_req_duration` 중앙값 307ms·p95 1.18초·max 33초. 로컬 스모크 테스트에서 각 GET이 수 ms였던 것과 비교하면 이쪽도 심각하게 느려졌다.
- **연결 실패 1건**: `login_ramp` 진행 중(t=2분39초, 아직 login_ramp 구간 — browse_ramp는 3분30초부터 시작이라 겹치지 않음) TCP 연결 자체가 타임아웃(`connectex: ... did not properly respond`)됐다. HTTP 에러가 아니라 서버가 새 연결을 받을 여력 자체가 없었다는 뜻.
- 이 연결 실패로 `res.json()`이 빈 body에서 예외를 던져 스크립트가 죽는 부수적 버그도 같이 발견했다 — `loadtest/k6-scenarios.js`의 `토큰 발급됨` 체크에 `r.body` 존재 확인 + try/catch를 추가해 고쳤다(다음부터는 이런 실패도 예외 없이 "체크 실패"로 정상 기록됨).

**해석**: browse 쪽(MockDataService 인메모리 배열 스캔)도 느려졌다는 게 핵심 단서다 — 조회 로직 자체는 원래도 빨라야 하므로, 이건 "코드가 느리다"가 아니라 **Render 무료 티어의 공유 CPU가 스로틀링되고 있다**는 뜻이다. login_ramp가 40 VU까지 올라가며 `bcrypt.compare`(CPU 바운드, cost=10)를 동시다발적으로 돌리는 동안 컨테이너의 CPU 쿼터를 다 써버렸고, 이후 요청들이 남은 쿼터를 기다리며 순차적으로 밀린 것으로 보인다(cgroup CFS 스로틀링의 전형적인 패턴 — 실제 연산량은 그대로인데 스케줄링 자체가 지연됨).

**이게 왜 중요한가 — D14 재검토**: `2-1_기술결정사항.md` D14는 "포트폴리오 규모에서 실측 인프라 수치는 무의미하다"며 가용성 목표를 설계 원칙으로 대체했었다. 그 판단(로컬 1인 개발 환경에서 수치 재현은 형식적 작업)은 배포 전까지는 맞았지만, **로그인처럼 인증 없이 누구나 호출 가능한 CPU 바운드 엔드포인트는 사실상 무료로 쓸 수 있는 DoS 벡터라는 게 이번 실측으로 드러났다** — 40명이 동시에 로그인만 시도해도 서비스 전체가 15초씩 느려진다. 이건 "발표용 수치를 재현하느냐 마느냐"의 문제가 아니라, `docs/domains/권한관리.md`가 AUTH-T01(로그인 5회 실패 시 잠금)을 "RFP 비요구라 Phase2로 분류, 미구현"이라고 적어뒀던 그 항목이 **실제로 막아야 하는 실제 문제**라는 뜻이다. D14 문서와 요약표에 이 재검토 내용을 반영했다.

**대응 방안(우선순위순, 아직 미구현 — 다음 작업으로 남김)**:
1. **로그인 rate limit(AUTH-T01 실구현)** — IP 또는 이메일 기준 시간당/분당 시도 횟수 제한. 이 문제의 근본 원인(무제한 CPU 바운드 요청)을 직접 막는 유일한 방법. `apps/api`에 `@nestjs/throttler` 같은 미들웨어 도입이 가장 간단한 경로.
2. **Cloudflare rate limiting** — §30에서 "도메인 없어서 보류"했던 결정과 정확히 맞닿는다. 커스텀 도메인을 확보하면 앱 코드 변경 없이 앞단에서 로그인 경로만 막는 규칙을 걸 수 있다 — 도메인 확보 우선순위가 이번 실측으로 더 높아졌다.
3. **bcrypt cost 하향 검토(10→8 등)** — 보안 여유를 조금 내주고 CPU 비용을 줄이는 트레이드오프. 무료 티어처럼 컴퓨팅 자원이 진짜 희소한 환경에서는 현실적인 선택지지만, 이것만으로는 "무제한 요청" 자체를 막지 못해 1번을 대체할 수 없다.
4. **유료 플랜 전환** — 가장 직접적이지만 비용 발생, 포트폴리오 단계에서는 후순위.

**검증**: 사용자가 직접 실행한 실측 결과(위 수치) — 이 세션이 재현한 게 아니라 사용자 실행 결과를 그대로 분석한 것임을 명확히 해둔다. 스크립트 버그 수정 후 재실행은 아직 안 함.

**커밋**: `2-1_기술결정사항.md` D14 재검토 추가, `loadtest/k6-scenarios.js` 버그 수정, 이 로그 절.

## 32. Little's Law로 "동시 로그인" 배율을 산정하고, D24(인증 경로 확장성 로드맵)로 정리했다 (2026-09-27)

**계기**: §31에서 로그인 CPU 스로틀링을 발견한 뒤, 사용자가 정확한 질문을 던졌다 — "지금 이 문제는 로그인 기능에 한해서고, 무료 인프라라 50명도 안 되는 동시 로그인에 문제가 생기는 건데, 이미 위탁계약이 98개인데 접속 인원이 꽤 많지 않겠냐"는 것. 이건 "테스트에서 발견한 버그를 고쳐라"가 아니라 "이 발견이 이 프로젝트가 원래 노리는 규모(98→130개 지점)에서 실제로 문제가 되는가"를 수치로 검증하라는 요구였다.

**한 일 — 정량화**: `design-constants.md`가 이미 산정해둔 ④(피크 동시 재실자 33명/지점, Little's Law)와 ⑤(전사 동시 재실 3,200명)를 그대로 재사용하되, **Little's Law를 반대 방향으로 적용**했다 — 기존엔 "도착률×체류시간=동시 인원"으로 동시 재실자 수를 구했다면, 이번엔 그 동시 재실자 수에서 거꾸로 "도착률"(⑦, ≈45.7명/분)을 역산하고, 이걸 다시 "로그인 처리시간"에 곱해(Little's Law를 정방향으로 한 번 더 적용) "동시 진행 중인 로그인 건수"(⑨)를 구했다. 결과가 핵심을 정확히 짚었다 — **정상 처리(65ms) 시 동시 진행 로그인은 0.12건에 불과해 평소엔 전혀 문제가 안 되지만, 처리시간이 늘어나는 순간(§31의 15초) 같은 공식이 동시 진행 건수를 28.5건으로 밀어올린다.** 즉 "지연이 지연을 부르는" 자기강화 루프라는 걸 계산으로 보여준 것이다 — §31에서 40 VU 램핑 중 응답시간이 완만히 늘지 않고 급격히 무너진 관찰과 정확히 들어맞는다.

**부수 발견 — D23이 실제와 어긋나 있었다**: D24를 쓰려고 기존 배포 결정(D23)을 다시 읽다가, D23이 "admin-web은 Cloudflare Pages"라고 적혀 있는데 §30에서 실제로는 Cloudflare Pages 커넥터에 생성 툴이 없어 **admin-web도 Render로 통합했다**는 사실이 반영이 안 돼 있는 걸 발견했다. 계획(D23 원문)과 실행(§30)이 각각 다른 시점에 기록되면서 어긋난 전형적인 사례라, D23을 실제 배포 상태로 정정하고 "변경 이력" 절로 왜 계획이 바뀌었는지(도구 한계를 실행 단계에서 발견)를 남겼다. 겸사겸사 D20~D23이 요약표에 빠져 있던 것도 이번에 채웠다(문서 자체가 이번 세션 이전부터 그 누락을 갖고 있었음).

**D24 결정 — 왜 "하나 고르기"가 아니라 "단계적으로 쌓기"인가**: 대안을 비교하면서 가장 중요하게 짚은 건, §31에서 1순위로 꼽았던 "로그인 rate limit"이 **이 문제를 안 푼다는 것**이다. Rate limit은 "악의적으로 무제한 요청을 퍼붓는 것"을 막는 보안 대책이지, "진짜 회원 수백 명이 퇴근 후 동시에 정상적으로 로그인하려는" 용량 문제는 못 막는다 — 오히려 너무 빡빡하게 걸면 정상 사용자를 튕겨낸다. 이 둘을 뒤섞지 않고 분리한 게 이번 결정의 핵심이다. 그리고 "수평 확장"(여러 인스턴스로 트래픽 분산) 대안을 검토하다가, **지금 아키텍처(MockDataService, 인스턴스별 인메모리 상태)로는 애초에 수평 확장이 불가능하다**는 걸 짚었다 — 여러 인스턴스를 띄우면 각자 다른 mock 데이터를 들고 있게 되기 때문이다. 그래서 `06_진행_로그.md` §29에서 이미 "다음 할 일"로 미뤄뒀던 "MockDataService → PrismaService 전환"이, 이번 일로 "단순 데이터 영속성 문제"에서 "수평 확장의 전제조건"이라는 새로운 무게를 얻었다 — 서로 다른 시점에 내려진 결정 두 개가 이번 계산으로 연결된 사례다.

**결정**: 1단계(즉시, 코드 레벨) = 로그인 rate limit 구현(보안). 2단계(실DB 전환 시, 아키텍처 레벨) = MockDataService→PrismaService 전환(수평 확장의 전제조건). 3단계(성장 시점, 인프라 레벨) = Render 유료 플랜+다중 인스턴스 실제 가동. 선택(도메인 확보 시) = Cloudflare rate limiting을 1단계 위에 얹기. 자세한 대안 비교표와 각 단계의 근거는 `2-1_기술결정사항.md` D24 참고.

**검증**: 계산 자체(Little's Law 역산·정산)이며 코드 변경은 없다. `design-constants.md`에 ⑦~⑨ 계산 과정과 "약한 고리"(로그인=시설도착 1:1 가정) 명시, `2-1_기술결정사항.md`에 D23 정정 + D24 신설, 이 로그 절로 기록했다.

**다음 작업**: D24의 1단계(로그인 rate limit) 구현부터 시작.

**커밋**: `design-constants.md`, `2-1_기술결정사항.md`, 이 로그 절을 묶은 커밋.

## 33. D24 1단계를 "NestJS rate limit"에서 "Cloudflare Worker 엣지 프록시"로 바꿨다 — 사용자의 반문이 계기 (2026-09-27)

**계기**: §32에서 D24를 정리하며 Cloudflare 관련 대안(F)을 "커스텀 도메인이 있어야 성립"이라고 적어뒀는데, 사용자가 "도메인을 사야 하는 문제도 Cloudflare Pages로 넘기면 바로 해결되지 않냐"고 되물었다. 처음엔 "Pages는 정적 프론트만 담당해서 api(진짜 병목)엔 무관하다"고 답했지만, 이어서 "그럼 Cloudflare Pages 커넥터는 없냐"는 질문에 답하려고 확인하다가 **더 나은 방향**을 발견했다 — Pages가 아니라 **Workers**를 쓰면, `workers.dev` 무료 서브도메인으로 도메인 없이 api 앞에 엣지 프록시를 세울 수 있고, 마침 Workers Rate Limiting 바인딩이 2025-09-19에 정식 출시(GA)돼 있었다. Cloudflare 공식 문서(`search_cloudflare_documentation`)로 두 사실 다 확인했다.

**정정**: D24의 F(Cloudflare 대안)이 "도메인 필요"라고 적어뒀던 게 **틀렸다는 걸 인정하고 바로잡았다.** 대신 진짜 제약은 도구였다 — Cloudflare MCP 커넥터("Cloudflare Developer Platform")에 Worker를 만드는 툴 자체가 없고(`workers_list`/`workers_get_worker`만 있음, 배포 툴 없음), 이 세션도 `api.cloudflare.com`을 egress 정책으로 못 붙는다(직접 curl로 재확인). k6 때와 똑같이 **로컬에서 `wrangler deploy`로 사용자가 직접 배포**해야 하는 구조다.

**한 일**: `cloudflare-worker/`(`src/index.ts`, `wrangler.jsonc`, `package.json`, `tsconfig.json`, `README.md`)를 신설했다. Worker는 `/api/v1/*` 전체를 Render api로 프록시하되, bcrypt가 걸리는 3개 경로(`/auth/login`, `/members/register`, `/members/link`)에만 `ratelimit` 바인딩(IP+경로 기준, 60초당 10회)을 적용한다. 이게 NestJS 안에서 막는 것보다 나은 이유를 D24에 명시했다 — **스로틀링되고 있는 건 Render 컨테이너의 CPU인데, 앱 레벨 rate limit은 요청이 그 CPU를 이미 조금이라도 쓴 뒤에야 거부한다. 엣지(Worker)에서 막으면 Render에 닿기도 전에 걸러진다.**

**정직하게 밝혀둔 것**: rate limit 바인딩의 정확한 `wrangler.jsonc` 문법(`unsafe.bindings` 형태)을 Cloudflare 공식 문서에서 시맨틱 검색으로 재확인하지 못했다 — GA 공지 페이지와 훈련 지식에 근거해 작성했고, `README.md`에 "배포 시 문법 에러가 나면 에러 메시지를 붙여달라"고 명시해뒀다. 코드가 "확실히 맞다"가 아니라 "확인 가능한 한 근거를 남기고, 틀리면 바로 고칠 수 있게 해뒀다"는 상태다.

**검증**: 이 세션에서는 배포·실행 검증이 불가능하다(위 제약). 사용자가 로컬에서 `wrangler deploy`를 실행하고 결과(URL 또는 에러)를 알려주면, 성공 시 admin-web의 `VITE_API_BASE_URL`을 그 URL로 갱신해 Render에서 재배포하고, 실패 시 에러를 보고 코드를 고친다.

**D24 갱신**: F(Cloudflare) 대안의 "한계" 칸을 정정하고, 1단계를 "NestJS rate limit"에서 "Worker 엣지 rate limit"로 교체했다. "선택(도메인 확보 시)" 단계는 삭제하고 1단계로 앞당겼다 — 도메인은 이미 있던 문제가 아니었다.

**커밋**: `cloudflare-worker/` 신설 + `2-1_기술결정사항.md` D24 정정 + 이 로그 절.

**후속(같은 날)**: 사용자가 로컬에서 `wrangler deploy` 실행 → **한 번에 성공**(`https://sports-erp-api-gateway.01-beauty-minimal.workers.dev`) — `unsafe.bindings` 문법에 대한 불확실성이 기우로 끝났다. 곧바로 Render `sports-erp-web`의 `VITE_API_BASE_URL`을 이 URL(`/api/v1` 포함)로 갱신하고 재배포까지 완료(`status: live`). admin-web은 이제 Render api에 직접 붙지 않고 이 Worker를 거친다. **아직 안 한 것**: 브라우저로 실제 로그인이 여전히 되는지(프록시 경유가 정상 동작하는지), `cloudflare-worker/README.md`의 rate limit curl 테스트(11번째 요청부터 429)로 바인딩이 실제로 작동하는지 — 둘 다 다음에 확인할 것.

## 34. D25 — admin-web을 Cloudflare Worker 정적 자산으로 통합, Render Static Site 폐기 (2026-09-27)

**계기**: §33 후속에서 admin-web(Render)을 Worker 경유 api로 재연결한 뒤, 사용자가 "로그인 안되고, 새로고침 하면 Notfound 떠. 그리고 왜 onrender 도메인임? CloudflarePage로 완전히 이적된게 아닌거임?"이라고 보고했다. 이 세션은 `onrender.com`/`workers.dev`에 직접 접근할 수 없어 브라우저로 재현할 수 없었다 — DevTools 정보를 요청하려던 참에, 사용자가 점 단위 디버깅 대신 "아예 클라우드플레어페이지로 이관할거야. AWS 인프라도 붙여서 무료 범위 내에서 인프라 형성할거고. 어때. 이게 낫지 않아?"라고 더 큰 방향 전환을 제안했다.

**판단**: 두 버그 모두 admin-web(Render)과 api 게이트웨이(Cloudflare Worker)가 서로 다른 오리진이 된 게 공통 원인일 가능성이 높다고 봤다 — 로그인 실패는 새로 생긴 크로스오리진 문제, 새로고침 404는 D23에서 이미 "미검증"으로 남겨뒀던 Render Static Site의 `_redirects` 동작이 실제로 안 먹혔을 가능성. 그래서 admin-web을 Cloudflare Worker의 정적 자산으로 흡수하면 **두 버그를 각각 디버깅하지 않고도 구조적으로 없앨 수 있다**고 판단해 동의했다. AWS는 별도로 — 지금 핵심 문제(오리진 분리)와 무관하고, 전체 호스팅을 AWS로 옮기는 건 과잉이라 판단해 "Lambda+EventBridge를 근태관리 자동 결근 배치·혼잡도 자동계산 등 이미 여러 도메인 문서에 스케줄러 부재로 남아있던 gap을 메울 때"로 범위를 좁혀 역제안했고, 사용자가 승인했다(AWS는 이번 작업 범위 밖).

**한 일**: Cloudflare 공식 문서(`search_cloudflare_documentation`)로 Workers 정적 자산 설정 문법을 확인 — `assets.directory` + `assets.not_found_handling: "single-page-application"` + `assets.run_worker_first`(배열로 경로 한정 가능)가 핵심이었다. `run_worker_first`를 `["/api/*"]`로 한정한 게 이번 구현을 단순하게 만든 열쇠 — UI 요청은 `src/index.ts`(프록시+rate limit 로직)를 아예 거치지 않고 Cloudflare 라우팅 계층에서 바로 정적 자산으로 서빙되므로, Worker 스크립트 자체는 수정할 필요가 없었다(주석만 보강).
- `cloudflare-worker/wrangler.jsonc`: `assets: { directory: "../apps/admin-web/dist", binding: "ASSETS", not_found_handling: "single-page-application", run_worker_first: ["/api/*"] }` 추가.
- `apps/admin-web/src/lib/api.ts`: `baseURL` 폴백을 `http://localhost:3000/api/v1`(프로덕션에선 틀린 값이었음)에서 `/api/v1`(상대경로)로 변경 — 로컬 개발은 `.env`가 우선 적용돼 영향 없고, 프로덕션은 이제 같은 오리진이라 상대경로만으로 충분해졌다(CORS 자체가 성립 안 함).
- `render.yaml`: `sports-erp-web` 서비스 블록 삭제, 대체 위치(Cloudflare) 안내 주석으로 교체.
- `cloudflare-worker/README.md`: 배포 순서에 "admin-web 먼저 빌드" 단계 추가, git push 자동배포를 잃는다는 점을 정직하게 명시.
- `2-1_기술결정사항.md`: D25 신설(대안 A/B/C 비교, C 채택), D23에 "두 번째 변경" 절 추가, 요약표·하단 각주 갱신.

**감수하는 것(정직하게)**: Worker가 UI+API+rate limit을 다 지는 단일 실패 지점이 됨(D24가 이미 인지한 리스크가 커짐). admin-web 배포가 Render의 "git push 자동배포"에서 "로컬에서 빌드 후 `wrangler deploy`" 수동 절차로 후퇴함 — DX 저하를 감춘 것 없이 README·ADR에 그대로 남겼다. Render `sports-erp-web`은 Render MCP 툴셋에 삭제 기능이 없어(조회·생성·갱신만 가능) 사용자가 대시보드에서 직접 지워야 한다.

**검증**: 코드·설정 변경뿐, 이 세션에서 배포·브라우저 확인은 불가능하다(egress 정책). 사용자가 admin-web 빌드 후 `wrangler deploy`를 다시 실행하고, 같은 URL(`sports-erp-api-gateway.01-beauty-minimal.workers.dev`)에서 로그인·새로고침을 확인해야 최종 검증된다.

**다음 작업**: 사용자의 `wrangler deploy` 재실행 결과 대기 → 확인되면 Render `sports-erp-web` 수동 삭제 안내 → rate limit curl 테스트(§33부터 미확인 상태로 남아있던 항목)까지 같이 확인 권장.

**커밋**: `cloudflare-worker/wrangler.jsonc`·`src/index.ts`·`README.md`, `apps/admin-web/src/lib/api.ts`, `render.yaml`, `2-1_기술결정사항.md`, 이 로그 절을 묶은 커밋.

## 35. D25 배포 시도 1 실패 — `_redirects` 무한루프를 Cloudflare가 거부, 파일 삭제로 해결 (2026-09-27)

**계기**: §34에서 안내한 대로 사용자가 admin-web 빌드 → `wrangler deploy`를 실행했다. `wrangler`(`^4.0.0`)와 devDependency로 박아둔 `@cloudflare/workers-types@^4.20250927.0` 사이에 peer dependency 충돌이 있어 `npm install`이 `ERESOLVE`로 실패했지만(최신 wrangler 4.142.0이 workers-types v5를 요구), 사용자 로컬엔 이미 v4.20260702.1이 설치돼 있어 npm이 알아서 넘어갔고 `npx wrangler`는 정상 실행됐다 — 이 버전 핀은 정확한 최신 버전을 몰라 넉넉히 잡아둔 것이라 지금 당장 고칠 필요는 없다고 판단해 보류. 자산 업로드(3개 파일)와 바인딩 등록(`ASSETS`/`LOGIN_RATE_LIMITER`/`API_ORIGIN`)까지는 전부 성공했는데, 마지막 게시 단계에서 Cloudflare API가 거부했다: `Invalid _redirects configuration: Line 1: Infinite loop detected... would cause a redirect to strip .html or /index and end up triggering this rule again`.

**원인 진단**: Cloudflare 공식 문서(`search_cloudflare_documentation`)로 확인해보니 `_redirects`는 Netlify 전용 호환 문법이 아니라 **Workers 정적 자산이 자체 파싱하는 1급 기능**이었다. `apps/admin-web/public/_redirects`에 남아있던 `/* /index.html 200`(원래 Render Static Site를 위해 만들어둔 SPA 폴백 규칙, D23 시절)이, D25에서 새로 켠 `not_found_handling: single-page-application`과 **같은 일을 다르게 하면서 충돌**했다 — 기본 `html_handling`(`auto-trailing-slash`)이 `/index.html`을 `/`로 정규화하고, 그 `/`가 다시 `/*` 규칙에 매칭돼 `/index.html`로 리다이렉트되는 걸 Cloudflare가 무한루프로 감지해 배포 자체를 막은 것이다.

**해결**: `apps/admin-web/public/_redirects` 삭제. `not_found_handling: single-page-application`이 이미 같은 역할(자산에 안 걸리는 요청에 `index.html`을 200으로 서빙)을 충돌 없이 수행하므로 이 파일은 더 이상 필요 없다 — Render 시절엔 필수였던 파일이 오리진이 바뀌면서(D25) 의미를 잃고 오히려 적극적으로 배포를 막는 존재로 바뀐 사례다. 삭제 후 이 세션에서 재빌드해 `dist/`에 `_redirects`가 더 이상 나오지 않는 것까지 확인했다(실제 `wrangler deploy` 재실행은 사용자 몫).

**겸사겸사 고친 것**: `npm install`이 `ERESOLVE`로 실패했던 것도 방치하지 않았다 — `cloudflare-worker/package.json`의 `@cloudflare/workers-types` 핀(`^4.20250927.0`)이 실제 설치된 `wrangler@4.142.0`이 요구하는 peer(`^5.20260926.1`)보다 낮아서 생긴 문제였다. 사용자 로컬은 이미 호환 버전이 깔려 있어 `npx wrangler`가 우연히 넘어갔지만, 클린 설치(이 세션 같은 새 환경 포함) 환경에선 그대로 막힐 수 있는 잠재 버그라 판단해 "급하지 않음"으로 미루지 않고 바로 `^5.20260926.1`로 올렸다(에러 메시지가 정확한 요구 버전을 알려줘 추측 없이 고칠 수 있었다).

**검증**: `npm run build --workspace=apps/admin-web`로 재빌드해 `dist/`에 `assets/`·`index.html`만 남고 `_redirects`가 사라진 것 확인(이 세션에서 가능한 범위). 실제 배포 성공 여부·로그인/새로고침 동작은 여전히 사용자의 `wrangler deploy` 재실행이 있어야 확정된다.

**다음 작업**: 사용자가 `_redirects` 삭제 반영 후(git pull) admin-web 재빌드 → `wrangler deploy` 재실행 → 이번엔 게시까지 성공하는지, 배포된 URL에서 로그인·새로고침이 실제로 되는지 확인.

**커밋**: `apps/admin-web/public/_redirects` 삭제, `cloudflare-worker/package.json` workers-types 버전 정정, `2-1_기술결정사항.md` D25에 "배포 시도 1 실패" 절 추가, 이 로그 절.

**후속(같은 날) — 배포 시도 2 성공**: 사용자가 `git pull` → 재빌드 → `wrangler deploy` 재실행. `npm install`이 이번엔 에러 없이 끝났다(`added 39 packages`, 0 vulnerabilities) — workers-types 버전 정정이 실제로 클린 설치 문제를 없앴다는 걸 확인. `wrangler deploy`도 게시까지 완주했다(`https://sports-erp-api-gateway.01-beauty-minimal.workers.dev`, Version ID `307222a2-d754-4d4d-9c99-797ce7582fe6`). `_redirects` 파일이 더 이상 없어 "No updated asset files to upload"로 나온 것도 기존 3개 자산 해시가 그대로 유지됐다는 뜻이라 예상과 일치한다. **아직 안 한 것**: 브라우저로 실제 UI 로딩·로그인·새로고침 확인 — 배포 성공은 설정이 유효하다는 뜻이지 런타임 동작을 보장하진 않는다(D24 완료 때와 같은 구분).

## 36. D25 배포 후 로그인 여전히 실패 — `.env`가 프로덕션 빌드에도 로드된다는 걸 놓쳤다 (2026-09-27)

**계기**: 사용자가 브라우저로 확인한 결과 — "새로고침은 돼, 로그인 안돼". 새로고침(SPA 라우팅)은 고쳐졌으니 D25의 핵심 목적은 달성했는데, 로그인이 여전히 안 된다는 건 별개의 버그가 남아있다는 뜻이었다.

**진단**: 이 세션에서 브라우저 접근은 안 되지만, 로컬에 남아있던 `apps/admin-web/dist/assets/*.js`(직전 빌드 결과물)를 `grep`으로 직접 뒤져봤다 — `localhost:3000/api/v1`이 번들에 문자열 그대로 박혀 있었다. §34에서 "프로덕션 빌드는 `VITE_API_BASE_URL`을 비워서 상대경로 폴백을 쓴다"고 판단하고 `api.ts` 주석에도 "로컬 개발은 .env가 우선 적용된다"고 적어뒀는데, **이게 틀린 전제였다** — Vite는 일반 `.env` 파일을 `dev`/`build`/`preview` **모든 모드**에서 똑같이 읽는다. 모드별로 분리되는 건 `.env.development`/`.env.production` 같은 접미사 파일뿐이다. `apps/admin-web/.env`(gitignore돼 있어 저장소엔 안 보이지만 로컬엔 있음, 로컬 API 서버를 가리키는 `http://localhost:3000/api/v1`)가 `wrangler deploy` 전 `npm run build`에도 그대로 적용돼, 배포된 페이지가 사용자 브라우저에서 자기 자신의 `localhost:3000`을 호출하려 한 것 — 당연히 아무것도 없으니 로그인이 실패했다.

**판단**: 이건 §34에서 내가 직접 낸 판단 오류다 — Vite의 env 로딩 규칙을 정확히 확인하지 않고 "로컬 개발용 `.env`는 프로덕션엔 안 섞인다"고 가정했었다. 고백하고 바로 고쳤다.

**해결**: `apps/admin-web/.env`(로컬 API 서버 URL)를 `apps/admin-web/.env.development`로 이름을 바꿨다 — 이러면 `vite dev`(모드=development)에서만 로드되고 `vite build`(모드=production, `wrangler deploy` 직전 빌드)에는 전혀 관여하지 않는다. `.env.development`는 시크릿이 아니라 로컬 기본값(`.env.example`과 같은 값)이라 gitignore 대상이 아니고, 그대로 커밋해 저장소에 남겨뒀다 — 새로 clone하는 사람도 별도 설정 없이 `npm run dev:web`이 바로 동작한다. `api.ts` 주석도 정확한 설명으로 고쳤다.

**검증**: 재빌드 후 `dist/assets/*.js`를 다시 grep — `localhost:3000` 문자열이 사라지고 `/api/v1`(상대경로)만 남은 것 확인. 실제 로그인 성공 여부는 사용자가 재배포 후 브라우저로 재확인해야 최종 검증된다.

**다음 작업**: 사용자가 `git pull` → **로컬 `.env` 파일이 남아있다면 삭제**(gitignore돼 있어 git pull로는 안 지워짐 — `.env.development`가 대신 그 역할을 하므로 `.env`는 이제 불필요) → admin-web 재빌드 → `wrangler deploy` 재실행 → 로그인 재확인.

**커밋**: `apps/admin-web/.env` → `.env.development` 이름 변경(신규 커밋), `apps/admin-web/src/lib/api.ts` 주석 정정, 이 로그 절.

**후속(2026-09-28) — 로그인 확인됨, D25 완전히 마무리**: 사용자가 로컬 `.env` 정리 후 재빌드·재배포하고 "로그인 됐어"로 확인해줬다. 이로써 D25가 원래 잡으려던 두 버그(새로고침 404, 로그인 실패) 모두 실제로 해소됐다 — 새로고침은 `not_found_handling: single-page-application`으로, 로그인은 `.env`→`.env.development` 정정으로. admin-web+api 게이트웨이+rate limit이 모두 `sports-erp-api-gateway` Worker 하나에서 정상 동작하는 게 브라우저 기준으로 확정됐다.

## 37. D26 — MockDataService→PrismaService 전환 1단계(스키마 동기화 + 인증 모듈 이관), Render sports-erp-web 삭제 직후 (2026-09-28)

**계기**: Render `sports-erp-web`을 사용자가 대시보드에서 직접 삭제한 직후, "API도 깔끔하게 관리하고 싶다, 굳이 Render에 둘 이유 없다"며 api도 AWS로 옮기고 싶다고 했다. 처음엔 "Wrangler CLI 있으면 편하지 않냐"고 물었는데, Wrangler는 Cloudflare 전용이라 AWS와 무관하다는 걸 먼저 정정했다. 그다음 AWS 무료 티어를 짚었다 — Lambda+EventBridge만 영구 무료(Always Free)이고, Lambda는 요청마다 여러 인스턴스가 병렬로 뜰 수 있어 지금의 인메모리 `MockDataService`와 근본적으로 안 맞는다(동시 인스턴스마다 다른 mock 데이터를 들고 있게 됨 — D24가 이미 "여러 Render 인스턴스"에서 짚었던 문제의 재현)는 걸 설명하고 AWS 이전을 잠시 보류시켰다.

**DynamoDB 질문과 그걸 받아들이지 않은 이유**: 사용자가 "DynamoDB는 무료 범위인가? 그걸로 동시성 문제를 풀 수 있지 않나"라고 되물었다 — 정확한 지적이었다(DynamoDB도 Always Free, 공유 외부 저장소로 쓰면 Lambda 동시 인스턴스 문제가 실제로 사라진다). 하지만 이미 27개 모델·관계형 설계(D2 branchId, D6 `FOR UPDATE` 락, D9 소프트 삭제)로 Supabase에 배포까지 끝난 Prisma 스키마를 통째로 버리고 NoSQL로 다시 모델링하는 건 "API 호스팅 위치"보다 훨씬 큰 결정이라고 판단해, "Postgres/Prisma는 유지하고 그 위에서 도는 앱만 Lambda로 옮기자"로 역제안했다. 사용자가 동의했다 — "그럼 그렇게 진행하자."

**플랜 모드로 전환한 이유**: 이 작업의 진짜 착수점은 AWS가 아니라 "MockDataService→PrismaService 전환"(D24가 이미 2단계로 예고해뒀던 것)이라는 게 명확해졌는데, 조사해보니 17개 컨트롤러가 `MockDataService`를 직접 물고 있고 테스트 18개 파일이 전부 인메모리 배열을 직접 조작하는 큰 작업이었다. 플랜 모드로 전환해 Explore 에이전트 2개를 병렬로 돌렸다 — 하나는 마이그레이션 표면(컨트롤러 패턴·도메인 불변식 코드 위치·auth 모듈 세부·기존 Prisma 배선·테스트 인프라), 하나는 스키마 드리프트 전수조사(27개 모델을 mock 타입과 일일이 대조). 두 조사 결과를 바탕으로 "Phase 0(스키마 동기화) + Phase 1(Prisma 배선 + 인증 모듈만 이관)"으로 범위를 좁힌 계획을 세워 승인받았다 — 나머지 16개 도메인은 이번에 안 건드리기로 명시.

**Phase 0 — 스키마 동기화**: `EnrollmentStatus` enum 값 교체, `Staff.offDays`·`AttendanceRecord.branchId`·`Member.guardianConsent`·`Payment.supplyAmount/vat`·`Facility.currentCount/level/lastUpdatedAt` 추가, `Asset`/`Document` 신규 모델(+enum 4개). 로컬 Postgres(이 세션에 `apt`로 이미 설치돼 있던 PostgreSQL 16을 그대로 씀 — Docker 데몬은 이 컨테이너에서 접근 불가)에 `prisma migrate dev`로 적용해 `apps/api/prisma/migrations/`를 처음으로 만들었고, Supabase에는 이 세션이 Postgres 포트에 직접 못 붙는 제약(D23/§29와 동일 — `db.blbjnozojvromktprqhv.supabase.co:5432`, pooler 6543 둘 다 타임아웃 확인) 때문에 SQL diff를 뽑아 MCP `apply_migration`으로 적용했다. 신규 테이블(Asset/Document)에 RLS가 빠져 있던 걸 advisor가 잡아줘서 나머지 27개와 같은 기준으로 맞췄다.

**Phase 1 — 인증 모듈, 그리고 처음 설계가 실제로 깨졌던 지점**: `AuthService`/`JwtStrategy`를 Prisma로 포팅하고 로컬 Postgres 위에서 로그인·`/auth/me`·refresh rotate(재사용 거부까지)·logout(idempotent)·SUPER_ADMIN(프로필 없는 계정)·changePassword·**§6의 핵심 불변식("role 변경이 재로그인 없이 다음 요청부터 반영")**까지 curl로 하나하나 수동 검증했다 — 전부 통과. 여기서 멈추지 않고 `npm run test`(기존 18개 스펙 파일)를 돌려본 게 결정적이었다 — **116개 테스트가 한꺼번에 깨졌다.** 원인: `/auth/login`이 모든 도메인이 공유하는 단일 진입점인데, 순수 Prisma 전용으로 만들면 아직 mock인 16개 도메인의 테스트들도 전부 로그인 자체가 안 된다. `login`/`refresh`/`logout`/`changePassword`/`JwtStrategy.validate`를 "Prisma에서 먼저 찾고 없으면 mock으로 폴백"하는 이중 경로로 다시 설계했다(두 ID 체계가 안 겹쳐서 안전). 이후 248/252까지 회복됐다.

**남은 2개 파일 실패 — ID 불일치를 realize한 계기**: 재실행해보니 `branch-isolation.spec.ts` 전체(50여 건)가 `STAFF_NOT_FOUND`로 깨졌다. 원인: Prisma 시드에 정하늘·김민수·박서연·이수진을 무작위 UUID로 만들었는데, mock 컨트롤러는 `req.user.staffId`가 mock 고유 ID(`'staff-seoyeon'` 등)일 거라고 가정한다 — Prisma로 로그인하면 그 가정이 깨진다. `mock-data.service.ts`의 정확한 ID 값을 그대로 Prisma 시드에도 써서 해결(이제 "같은 사람"이 두 저장소에서 같은 ID를 쓴다). 이후 16/18 통과, 남은 2개 파일(`auth-lifecycle.spec.ts` 2건, `staff-assignment.spec.ts` 1건)은 진짜 남은 과도기 한계였다 — 퇴사·Role전환이 아직 mock 도메인이라 Prisma Account엔 반영 안 됨. 기대값을 안 바꾸고 `it.skip`+사유 주석으로 남겼다(도메인 이관 시 재활성화 대상, `docs/domains/권한관리.md` §11도 이 상태를 정직하게 반영해 갱신).

**CI가 조용히 깨질 뻔한 것**: `PrismaModule`이 부팅 시 DB 연결을 시도하게 되면서 `.github/workflows/ci.yml`에 Postgres 서비스가 전혀 없다는 걸 뒤늦게 깨달았다(CLAUDE.md에도 "DB 불필요"라고 잘못 적혀 있었다 — 같이 고침). `postgres:16-alpine` 서비스 컨테이너를 CI job에 추가하고 `migrate deploy → seed → test` 순서를 넣은 뒤, **이걸 그냥 믿지 않고** 로컬에 완전히 새 DB(`sports_erp_ci_check`)를 만들어 정확히 이 순서를 재현해 통과를 확인하고서야 커밋했다 — 검증 없이 넘겼으면 이 커밋이 푸시되는 순간 CI가 통째로 빨간불이 됐을 것이다.

**정직하게 남겨둔 것**: 이중 경로(Prisma-우선/mock-폴백)는 명백한 임시 설계이고, mock 의존성은 도메인이 하나씩 이관되기 전까지 안 지워진다. Supabase는 `_prisma_migrations` 이력 테이블에 이번 마이그레이션이 기록 안 돼 있다(MCP로 원본 SQL만 적용했으므로) — 로컬 `migrations/` 폴더가 감사용 단일 진실 공급원이라는 걸 다음에 이 프로젝트를 만지는 사람이 알아야 한다.

**검증**: `npm run build`/`npm exec -- eslint .`(에러 0) 통과. `npm run test` 로컬 Postgres 기준 17/18 스위트·248/252 테스트 통과(3건 skip, 사유 문서화). CI와 동일한 절차(`migrate deploy`→`seed`→`test`)를 완전히 새 DB에 재현해 통과 확인. curl로 로그인/refresh rotate/logout/changePassword/§6 즉시반영 전부 실동작 확인.

**다음 작업**: 회원관리 도메인부터 순서대로 이관(컨트롤러 인라인 mock 배열 접근과 `createReservation`의 `FOR UPDATE` 동시성 코드를 처음 겪는 도메인). 전 도메인 이관이 끝나면 AWS Lambda 호스팅 논의 재개.

**커밋**: `apps/api/prisma/schema.prisma`+`migrations/`(신규), `apps/api/src/app.module.ts`·`mock-data/mock-data.module.ts`·`modules/auth/**`, `apps/api/prisma/seed.ts`, `apps/api/test/auth-lifecycle.spec.ts`·`staff-assignment.spec.ts`(skip), `.github/workflows/ci.yml`, `render.yaml`, `CLAUDE.md`, `docs/domains/권한관리.md`, `2-1_기술결정사항.md` D26, 이 로그 절.

## 38. D26 "다음 작업"의 문서화 공백 발견 — Lambda 재개 전 설계해야 할 인프라 부하 4가지 (2026-09-28)

**계기**: 4주차 발표자료 준비 중 사용자가 덱의 로드맵 슬라이드를 보며 "DB 이전하고 Lambda로 옮기면 스로틀링 문제가 어느 정도 해소되나?"라고 물었다. 답하면서 ① Lambda가 근본 원인(공유 CPU 경합)은 없애지만 ② bcrypt CPU 비용 자체는 그대로고 ③ 동시 Lambda 실행 환경이 늘면 이번엔 DB 커넥션이 고갈될 수 있어 Supavisor 풀링이 필요하며 ④ 콜드스타트라는 다른 지연이 생긴다고 설명했다. 그러자 사용자가 정확한 질문을 던졌다 — "이런 거 문서에 명시돼 있음? 없으니까 이런 문제가 생기는 거 같은데."

**확인**: `2-1_기술결정사항.md`·`docs/architecture/`·`CLAUDE.md`를 grep해봤는데 실제로 "커넥션 풀링"·"Supavisor"·"콜드스타트"·"동시 실행 한도" 중 어느 것도 D23~D26 어디에도 없었다. D26의 "다음 작업"은 "전 도메인 이관이 끝나면 AWS Lambda 호스팅 논의를 재개"라는 한 줄이 전부였다 — 이 대화에서 나온 네 가지 고려사항은 순전히 대화 안에만 있었고 기록으로 남지 않은 상태였다.

**바로잡은 것**: D26의 "다음 작업"을 확장해 Lambda 논의를 재개할 때 반드시 설계해야 할 4가지(Lambda 메모리=CPU 사이징, DB 커넥션 풀링, 동시 실행 한도, 콜드스타트)를 명시했다 — 이걸 빠뜨리고 "Lambda로 옮기면 끝"이라고 설계하면 스로틀링 문제가 형태만 바뀌어(CPU 경합 → DB 커넥션 경합) 재발한다는 것도 같이 적었다.

**타당성**: 이 자체는 계산이나 실측이 아니라 "지금까지의 대화에서 나온 설계 판단을 실제 결정 기록으로 옮겨 적은 것"이다 — 프로젝트 원칙(CLAUDE.md "구현 작업 원칙" ②: 구현 후에는 근거를 기록에 남긴다)이 코드뿐 아니라 문서 자체의 공백에도 그대로 적용된 사례. 사용자가 직접 "문서화가 안 돼서 이런 문제가 생기는 것 같다"고 짚어준 게 계기였다는 것도 남겨둔다 — 이후 Lambda 이관 착수 시 이 네 가지를 재발견하지 않고 바로 설계에 반영할 수 있게 됐다.

**검증**: 문서 편집만이라 코드 검증 대상 없음. `2-1_기술결정사항.md` D26과 이 로그 절을 함께 커밋.

## 39. 도메인 사이클 재검토 관점 전환 — 기능 구현에서 트래픽·인프라·아키텍처 흐름으로 (2026-09-28)

**계기**: 4주차 발표자료 준비 중 발표자가 Part A(이번 주 6개 도메인 재검토)를 보고 "기능 구현적인 측면에 집중한 거네, 내 방향성에 안 맞는다 — 어제 오늘 다룬 트래픽·인프라 관점에 집중해야 하는데"라고 지적했다. 지금까지의 도메인 사이클(근태·혼잡도·프로그램·게시판·자원문서관리·회원관리)이 찾은 ADR 16건은 전부 "RFP 요구 대비 지점 격리·계약종료 차단 같은 불변식이 새 라우트에서 빠졌는가"라는 **기능 구현 렌즈**였다 — 같은 주 Part B/C가 다루는 "Render 무료 티어 CPU 스로틀링·k6 부하테스트·Lambda 이관 계획"이라는 **인프라 렌즈**와 관점이 달랐다는 지적은 정확했다.

**한 일**: 6개 도메인 각각의 목록/조회 엔드포인트와 쓰기 경로 코드를 다시 읽어(Explore 에이전트로 위임, 코드만 읽는 조사) N+1 조회·캐싱 없는 폴링 대상·경계 없이 누적되는 전체 스캔·동시 쓰기 경합 패턴을 찾았다. 전부 실제 코드에 있는 패턴이고(예: 강사·프로그램 도메인의 `bookedCount()`는 코드 주석에 이미 "no cache, computed every time"이라고 적혀 있었다), 6개 중 4개(근태관리·혼잡도관리·강사·프로그램·회원관리)를 "심각도 높음"으로 판단했다. 특히 혼잡도관리(`GET /facilities`, 캐싱 없음 + N+1)는 회원 앱 출시 후 가장 자주 폴링될 후보라 이번 주 실측한 로그인 CPU 스로틀링(D24)과 같은 패턴이 다른 엔드포인트에서 재현될 위험으로 짚었다.

**중요한 구분**: 이 문제들은 D24가 실측한 "공유 CPU 경합"(여러 요청이 하나의 CPU를 다투는 문제)과 **다른 클래스**다 — 이건 요청 하나의 계산량 자체가 크거나 데이터 규모에 비례해 계속 나빠지는 문제라, D26의 Lambda 이관 계획으로도 저절로 안 없어진다. 오히려 Lambda 동시성이 늘면 이런 무거운 스캔이 더 많이 동시에 돌아 "DB 용량"이라는 이미 인지한 한계(migration 슬라이드)를 더 빨리 만나게 된다는 것도 짚었다.

**기록한 곳**: 새 횡단 문서 [architecture/traffic-infra-review.md](../architecture/traffic-infra-review.md)에 도메인별 근거(파일:줄)·심각도·검토 방향을 전부 남겼고, 6개 도메인 문서 각각의 §12(이월 사항)에 교차 참조 + 요약을 한 줄씩 추가했다. **아직 ADR이 아니다** — Driver(왜 문제인가)만 찾았고 대안 비교·결정은 안 했다는 걸 문서에 명시했다. 발표 슬라이드(4주차 덱, `dom-attendance`~`dom-member` 6장)도 이번 주 ADR 체크리스트 대신 이 트래픽/인프라 후보 이슈 + "해결방안 검토 중" 상태로 교체했다.

**타당성**: 높음 — 코드를 직접 읽고 찾은 실제 패턴이라(추측이 아니라 파일:줄 근거), 그리고 이번 주 인프라 서사(D23~D26)와 방향이 맞는 관점이다. 다만 아직 부하테스트로 검증된 건 아니다 — "감수하는 것"에 정직하게 남긴다.

**감수하는 것**: 이 목록은 코드를 읽고 추론한 후보일 뿐, 실제로 병목이 되는지는 각 도메인이 Prisma로 이관돼 실제 DB 쿼리 패턴 위에서 부하테스트로 재검증해야 확정된다. 권한관리·인사정보관리·예약및결제(원래 상 우선순위 도메인 중 회원관리를 제외한 나머지)는 이번 스캔에 포함되지 않았다 — 다음 순번.

**검증**: 코드 읽기 기반 조사이며 이번엔 실행 검증 대상 없음(Explore 에이전트가 컨트롤러·`mock-data.service.ts`를 직접 읽고 인용).

## 40. D27 — Lambda 이관 전제로 스키마를 한 번 더 보강했다: ADR과 모순되던 전역 unique, UTC now() 기본값, 메모리 상태 (2026-09-29)

**계기**: 사용자가 "배포보다 실DB 전환이 먼저고, 추후 AWS Lambda로 API를 호출할 거라 Render에 힘을 실을 필요는 없다"고 방향을 확정했다. 착수 전에 한 가지 실수가 있었다 — 최근 7일 현황을 `main`만 보고 분석해서 "실DB 전환은 착수 전"이라고 보고했고, 그 전제로 스키마 재동기화를 처음부터 다시 만들다가 Supabase에 기록되지 않은 마이그레이션 3건(09-28)을 보고서야 실제 작업 브랜치가 `main-5x9td9`(D26, §37~39)라는 걸 알았다. Supabase 적용 직전에 멈추고 사용자에게 알렸고, 사용자가 `main-5x9td9` 기준으로 이어가기로 정했다. `main` 기준으로 만든 초안은 버리고, 그 초안에만 있던 차이분을 D26 위의 세 번째 마이그레이션으로 다시 만들었다. **교훈**: 현황 분석은 기본 브랜치만이 아니라 원격 브랜치 전체의 최근 커밋부터 봐야 한다 — 이 저장소는 `render.yaml`이 가리키는 배포 브랜치가 `main`과 다르다.

**D26 스키마에 남아 있던 틈**: D26은 "mock에 있는 필드가 스키마에 있는가"를 대조했고 그건 정확했다. 하지만 **제약·기본값·상태의 위치**는 대조 대상이 아니었다. ① `Account.email @unique`와 `Reservation @@unique([memberId, scheduleSlotId])`는 ADR-MEM-02(탈퇴 이메일 재사용)·ADR-RSV-02(취소 후 재예약)와 정면으로 모순이다 — mock은 앱 로직으로 흉내 내서 테스트가 통과했지만, 다음 이관 대상인 회원관리를 옮기는 순간 DB가 막는다. ADR-STF-03(활성 파견 1건)은 DB 제약이 아예 없었다. ② 날짜 의미 필드 4개에 `@default(now())` — DB의 `now()`는 UTC라 §11에서 고친 KST 날짜 버그가 DB 계층에서 재발하는 경로였다. ③ 연동 실패 횟수(인스턴스 메모리 `Map`)와 채번(개수+1)은 Lambda 병렬 인스턴스에서 깨지는데 옮길 테이블이 없었다.

**한 일**: 세 번째 마이그레이션 `20260929002914_d27_lambda_readiness` — 부분 unique 인덱스 3종(Prisma 5 문법으로 표현 불가라 SQL로만 두고 `schema.prisma` 상단에 주석으로 명시), 날짜 의미 컬럼 11개를 `@db.Date`로 바꾸고 날짜 필드의 DB 기본값 제거, `CodeSequence`(ADR-STF-02)·`MemberLinkAttempt`(ADR-MEM-01) 신설, `directUrl`·`binaryTargets`(D26 "다음 작업" ②④의 스키마 쪽 준비). 이메일이 unique 키가 아니게 되면서 `AuthService.login`의 `findUnique({ email })`가 **컴파일 단계에서 막혔다** — 스키마 제약 변경이 타입 오류로 바로 드러난 것은 이 전환 방식(Prisma 타입 생성)의 이점이다. `findFirst`로 바꾸되 활성 계정을 우선하고, 비활성뿐이면 그 계정을 돌려 `ACCOUNT_INACTIVE`로 거부하게 했다(비활성을 걸러버리면 mock 폴백으로 새서 에러 종류가 바뀐다). `seed.ts` upsert 키를 이메일에서 고정 id로, CI·`.env.example`에 `DIRECT_URL`을 추가했다.

**검증**: 로컬 Postgres 16 새 DB에 CI 절차(`migrate deploy` → `seed` → 테스트) 재현 — 18/19 스위트, 251 통과(D26의 248 + 신규 `auth-email-reuse.spec.ts` 3건, D26 skip 3건 그대로). 테스트는 `DIRECT_URL` 없이 돌려 런타임엔 필요 없음을 확인. 시드된 DB에서 부분 인덱스 3종이 중복을 거부하고 대조군(탈퇴 후 재가입, 종료된 파견, 취소 후 재예약)은 통과하는 것을 SQL로 확인. `prisma migrate dev`가 부분 인덱스를 지우지 않는 것(빈 마이그레이션)도 확인. Supabase는 적용 전후 모두 컬럼·인덱스·enum·제약 지문 4종을 로컬과 비교해 일치를 확인했고(적용 전 데이터 0행), 신규 테이블 2개 RLS도 켰다. lint 0 에러(기존 `main.ts` 경고 1건), api·admin-web 빌드 성공.

**감수하는 것**: Supabase `_prisma_migrations`는 여전히 비어 있다(D26 감수 ③) — 대신 이번엔 지문 비교로 "로컬 이력 = Supabase 상태"를 증명해 두었다. `CodeSequence`·`MemberLinkAttempt`는 아직 쓰는 코드가 없다.

**커밋**: `apps/api/prisma/schema.prisma`·`migrations/20260929002914_d27_lambda_readiness/`, `apps/api/src/modules/auth/auth.service.ts`, `apps/api/prisma/seed.ts`, `apps/api/test/auth-email-reuse.spec.ts`(신규), `apps/api/.env.example`, `.github/workflows/ci.yml`, `CLAUDE.md`, `2-1_기술결정사항.md` D27, 이 로그 절.

## 41. D28 — 정합성 ADR을 모아 "DB가 강제할 수 있는 것"부터 실DB 전환 전에 적용했다 (2026-09-29)

**계기**: 사용자가 "데이터 정합성 측면의 ADR을 뽑아 실DB로 전환하기 전에 적용하고 싶다"고 요청했다. 9개 도메인 문서의 ADR 22개와 Tier2 규칙표를 훑어 정합성 규칙 27개를 [architecture/data-integrity.md](../architecture/data-integrity.md) 인벤토리로 모았다. D27과 기존 unique가 막는 5개를 빼면 전부 `MockDataService` 앱 로직 한 겹이었다.

**분류 기준 — "무엇이 강제할 수 있나"**: 규칙을 ① 한 행 안에서 판정(CHECK 가능) ② 두 테이블의 지점 일치(복합 FK·트리거 필요) ③ 여러 행을 함께 바꾸거나 동시 요청을 직렬화(트랜잭션·락 — 코드 규칙)로 나눴다. ②·③은 설계 판단이 걸려 있어 사용자에게 물었고, ②는 "파견 정책 먼저 결정", ③은 "공용 헬퍼만 지금"으로 정했다.

**①에서 세운 원칙 — 앱이 검증하는 것만 DB로**: 처음엔 눈에 띄는 규칙을 전부 CHECK로 옮기려 했다. 하나씩 앱 코드와 대조해 보니 프로그램 기간·수강 만료일·회차 시각 3개는 앱에 검증이 아예 없었다. 이런 규칙을 DB에만 걸면 사용자 입력 실수가 400이 아니라 500으로 터진다. 그래서 CHECK는 앱 검증의 거울로만 두고(18개), 그 3개는 "앱 검증부터" 공백으로 문서에 남겼다. 18개 전부 시드된 DB에서 위반 거부·정상 경계값 통과를 SQL로 확인했다. 처음 보고할 때 19개라고 셌는데 실제로는 18개여서 바로잡았다.

**②에서 발견한 공백**: "회원↔담당 직원 같은 지점" 규칙을 트리거로 옮기려고 파견 발령 코드를 보니, `assignStaff`가 담당 회원(`assignedStaffId`)과 강사 프로필을 정리하지 않는다. 직원이 이동하는 순간 규칙이 조용히 깨지는 구조라, 트리거를 먼저 걸면 파견 자체가 막힌다. 정책을 먼저 정하기로 했다(DI-02, 권장 A: 파견 트랜잭션에서 담당 관계 정리). 수단도 확인했다 — SQL로만 넣은 복합 FK는 `prisma migrate diff`가 DROP을 생성해 지워지므로 트리거만 현실적이다.

**③에서 바뀐 설계와 발견**: 채번 헬퍼를 ADR-STF-02 문구대로("시퀀스 행 `FOR UPDATE`") 만들려다가, prefix의 **첫 채번**(새 지점·새해 memberNo)에는 잠글 행이 없어 ADR-RSV-01이 논파한 팬텀 삽입과 똑같이 뚫린다는 걸 알아챘다. `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 한 문장으로 바꿔 동시 20건 채번을 1~20 무중복으로 확인했다. 테스트를 쓰다가 시드가 `SEOCHO-001/002`를 번호째 넣어 헬퍼의 첫 번호와 충돌한다는 것도 발견해 시드에 시퀀스 초기화를 넣었다. 시퀀스 행을 지우면 테스트가 실패하는 것까지 확인했다. 실데이터 이관 때도 같은 초기화가 필요하다고 체크리스트에 적었다. 회차 행 락은 정원 2 신규 회차에 5명 동시 요청으로 검증했다(락 있음 → 정확히 2건, 대조군 락 없음 → 초과).

**검증**: `integrity-helpers.spec.ts` 5건 신규, 전체 256 통과(251 + 5, D26 skip 3건 유지), lint 0 에러, 빌드 성공. `migrate dev`가 CHECK를 지우지 않는 것(빈 마이그레이션) 확인. Supabase는 적용 전 지문 일치(데이터 0행)를 확인하고 적용했다. 적용 후 제약 지문이 어긋나 당황했는데, md5 하나만 보고 판단하지 않고 91개 제약을 이름별 해시로 뽑아 대조하니 차이는 로컬 비교 DB에만 있는 `_prisma_migrations_pkey`뿐이었다. 지문 쿼리의 결함이었지 스키마 차이가 아니었다.

**커밋**: `apps/api/prisma/migrations/20260929004339_d28_integrity_checks/`, `apps/api/prisma/schema.prisma`(주석), `apps/api/src/prisma/integrity.ts`, `apps/api/prisma/seed.ts`, `apps/api/test/integrity-helpers.spec.ts`, `docs/architecture/data-integrity.md`(신규), `2-1_기술결정사항.md` D28, 도메인 문서(인사정보관리·예약및결제), 이 로그 절.

## 42. DI-02 A안 — 파견 시 담당 관계 정리 + 지점 일치 트리거, 그리고 타 지점 예약 결함 (2026-09-29)

**계기**: §41에서 결정 대기로 남긴 DI-02에 대해 사용자가 A안(파견 트랜잭션에서 담당 관계 정리)을 택했다. [인사정보관리 ADR-STF-04](../domains/인사정보관리.md)로 먼저 기록하고 구현했다.

**구현**: 앱의 `assignStaff`는 옛 지점 담당 회원의 `assignedStaffId`를 해제하고, 해제한 회원을 파견 응답 `unassignedMembers`로 돌려준다. mock 강사에는 직원 연결 필드가 없어서, 강사 프로필 정리는 강사 도메인 이관 때 추가하도록 남겼다. ## 43. D29 — "회원관리 이관"을 조사하다 순서를 바꿨다: 참조되는 쪽부터, 1단계 지점 (2026-09-29)

**계기**: 사용자가 D26 순서대로 회원관리 Prisma 이관을 요청했다. 착수 전 조사에서 회원이 지점·직원·프로그램을 참조하는데 셋 다 mock에만 실데이터가 있다는 걸 확인했다(mock 98/195/149 vs DB 2/3/4). 회원만 옮기면 D27·D28의 FK·트리거가 96개 지점의 회원 등록을 막고, 두 저장소를 오가는 동기화 코드가 필요해진다. 구현 전에 멈추고 A(참조되는 쪽부터)·B(회원 먼저 + 복사본 동기화)·C(회원+지점)를 제시했고, 사용자가 A를 택했다. **D28까지 쌓은 DB 제약이 "순서를 잘못 잡으면 바로 막힌다"는 형태로 설계 오류를 드러낸 사례다.** 제약이 없었다면 회원을 먼저 옮기고 나중에 FK를 붙이며 데이터를 고쳤을 것이다.

**지점이 특이했던 점**: 쓰기 API가 없는 기준 데이터다. 그래서 "이관"의 실체는 ① 계약 상태의 원천을 DB 하나로 만드는 것과 ② 아직 mock인 9개 쓰기 경로가 동기적으로 하던 계약 종료 판정을 DB 기반으로 바꾸는 것이었다.

**설계 판단 세 가지**(상세: 2-1 D29):
- **mock 사본에서 계약 필드를 타입째 지웠다.** "계약 상태를 mock에서 읽지 않는다"를 규칙으로 두는 대신, 읽는 코드가 남아 있으면 컴파일이 실패하게 했다. 실제로 테스트 5곳과 `branchSummary`가 컴파일 단계에서 잡혔다.
- **계약 종료 판정은 gate 인자로 넘긴다.** 컨트롤러에서 미리 검사하는 방식은 예약처럼 판정 대상 지점이 mock 내부에서 정해지는 경로가 있고 에러 순서도 바뀐다. 그래서 종료 지점 집합을 한 번 읽어 mock 메서드에 필수 인자로 넘겼다. 기존 판정 자리·순서가 그대로이고, 넘기지 않은 호출부 10곳을 컴파일러가 전부 찾아줬다.
- **테스트를 워커별 DB로 바꿨다.** 계약 상태가 DB로 가는 순간 "스위트마다 새 앱 = 새 상태"라는 기존 격리가 깨진다. 한 스위트가 서초를 TERMINATED로 바꾸면 병렬로 도는 다른 스위트가 그걸 본다. 기준 DB를 템플릿으로 워커 수만큼 복제하고, 바꾼 상태는 공용 헬퍼가 매 테스트 뒤 되돌린다. 앞으로 옮겨질 모든 도메인이 이 인프라를 쓴다.

**발견**: `seed.ts`의 서초·강남 값이 mock과 달랐다(계약 종료일·취소 기준 시간 누락). 두 곳이 같은 목록(`branch-fixtures.ts`)에서 만들어지게 바꾸고, 어긋남을 잡는 사본 일치 테스트를 넣었다.

**검증**: 전체 264 통과. gate를 일부러 비우면 계약 종료 테스트 8건이 실패함을 확인했다(판정이 실제로 DB에서 온다는 증거). 워커 DB 정리·기준 DB 무오염도 확인했다. **Supabase 시드**: 배포된 앱은 Supabase를 보므로 시드 없이 머지하면 지점 목록이 비어 보인다. 외부 DB 쓰기라 사용자 확인을 받은 뒤 적용했다. 같은 원천에서 만든 upsert SQL을 로컬의 빈 DB에 두 번 돌려 멱등성과 시드 결과 일치를 먼저 확인했고, 적용 후 Supabase 해시가 로컬과 같다(98개, 종료 3).

## 46. D32 — 회원·예약·결제 이관으로 D29 순서를 끝냈다: 미러 없이, 인증 폴백까지 걷어냈다 (2026-09-29)

**계기**: D29 순서의 마지막 참조 단계(사용자 요청 "회원 이관 진행해줘"). 착수 전 조사에서 두 가지를 확인했다. ① 회원·예약·결제·수강·PT를 동기적으로 읽는 mock 도메인이 **하나도 남지 않는다**(근태·게시판·자산·문서는 회원을 읽지 않는다). ② 이 단계가 끝나면 모든 계정이 DB에 있다. 그래서 D30·D31의 "미러" 패턴을 여기서는 쓰지 않았다. 오히려 D31 미러의 마지막 독자(예약·지점 건수·프로그램 현황판)가 사라져 D31 미러도 함께 지웠다(상세: 2-1 D32).

**설계 판단**:
- **미러 없음 + D31 미러 제거.** 독자가 없는 복사본은 비용만 남는다. "테스트가 읽으니 남기자"는 테스트를 위해 운영 코드를 늘리는 역방향이라 기각했다. 테스트는 `db(app)`(Prisma) 헬퍼로 읽게 바꿨다. 남는 미러는 근태·문서·게시판이 읽는 D30 직원 미러 하나다.
- **인증 mock 폴백 종료.** D26부터 "Prisma 먼저, 없으면 mock"이던 login·refresh·logout·changePassword·JwtStrategy의 mock 경로와 mock refresh token 저장소를 지웠다. 가입·연동 직후 로그인도 DB 계정으로 발급한다(`issueSessionFor`). D30 결정 4(이메일 유일성을 두 저장소에서 보기)도 DB 하나로 합쳐졌다.
- **예약 생성은 회차 행 락 위에서.** `lockScheduleSlot`(D28) → 검사(순서는 mock 그대로) → 활성 예약 COUNT → 생성. 부분 unique 위반은 `ALREADY_RESERVED`로 받는다(ADR-RSV-01·02). 정원 경합 테스트는 mock 시절엔 단일 스레드라 "락 없이도" 통과했다. 이제는 락이 있어야 통과한다.
- **채번·연동 제한은 D27·D28이 마련한 자리로.** 회원번호는 `allocateBranchCode(MEMBER)`로 뽑고 KST 연도를 쓴다. 연동 실패 제한은 프로세스 메모리 `Map`에서 `MemberLinkAttempt` 테이블로 옮겼다. 앱을 다시 띄워도 제한이 유지된다는 테스트를 추가했다. Lambda 전제에서 메모리 제한은 사실상 무력했다.

**발견 — 옮기면서 드러난 결함 셋**:
1. **환불 마감 시간대**: 취소 환불 판정이 회차 시작을 `new Date("YYYY-MM-DDTHH:mm:00")`(호스트 시간대)로 만들었다. UTC 서버에서는 KST 회차를 9시간 늦게 봐서, 마감 이내 취소도 환불됐다. `+09:00`을 붙였다. 20시간 뒤 회차(환불 안 됨)와 30시간 뒤 회차(환불)를 대조하는 회귀 테스트를 추가했다.
2. **결제 목록 날짜 필터**: `approvedAt.slice(0,10)`(UTC 날짜)로 비교하던 것을 KST 날짜로 바꿨다.
3. **이중 승인·이중 연동·PT 초과 차감**: mock은 단일 스레드라 드러나지 않았다. 결제 승인은 "PENDING일 때만", 연동은 "아직 계정이 없을 때만", PT 차감은 "남아 있을 때만"으로 조건부 갱신해 동시 요청에도 한 번만 성립하게 했다. 세 가지 모두 동시 요청 테스트로 확인했다(잔여 7회 PT에 9회 동시 차감 → 7회만 성공).

**발견 — 검증 단계에서 드러난 것 둘**:
4. **결제 금액 분할 CHECK(세 번째 "DB 제약이 mock 결함을 드러낸" 사례)**: 첫 전체 실행에서 예약 생성이 전부 500이었다. mock은 PENDING 결제를 `supplyAmount=0, vat=0`으로 만들고 승인 때 나눴다. 그런데 D28 `Payment_amount_split_ck`(공급가액+부가세=금액)가 이 상태를 거부했다. 결제 생성 시점에 나누도록 고쳤고, 승인은 같은 계산(`splitVat`)으로 다시 확정한다. §43(FK·트리거), §45(PAID_SESSION 정원 CHECK)에 이어 세 번째다. 모두 "API로는 막았다고 생각했지만 mock 데이터·경로가 규칙을 어기던" 경우다.
5. **테스트 DB 삭제의 간헐 실패 — D30 "설명 안 된 smoke 실패"의 원인 후보를 찾았다**: `contract-termination`이 세 번에 한 번꼴로, 매번 다른 테스트에서 실패했다. 한 번은 `시설 신규 등록`, 한 번은 `자산 신규 등록`, 한 번은 `기존 자산 정정`이었다. 원인은 앱 코드가 아니라 `resetWorkerDb`의 `DROP DATABASE … WITH (FORCE)`가 42501(`permission denied to terminate process`)로 실패한 것이었다. PostgreSQL 로그에서 같은 오류를 확인했다. FORCE는 그 DB에 붙은 모든 프로세스를 호출자 권한으로 종료하려 한다. 테스트가 쓴 직후 autovacuum이 그 DB에서 돌면, 비superuser인 테스트 계정은 그 프로세스를 종료할 수 없다. FORCE 없는 DROP은 서버가 autovacuum을 직접 멈추고 기다린다. 그래서 공용 `dropDatabase`(`test/setup/test-db.ts`)를 만들었다. FORCE를 먼저 쓰고, 42501이면 FORCE 없이, 55006이면 잠깐 기다렸다 다시 시도한다. D32로 테스트마다 DB를 다시 만드는 스위트가 늘어 빈도가 올라갔을 뿐, D29부터 있던 결함이다. **autovacuum이 원인이라는 것은 PostgreSQL 동작에 근거한 추론이다.** 실행 중 연결 목록을 표본으로 떠서 직접 잡아 보려 했지만, 그 실행에서는 실패가 나지 않아 확인하지 못했다. 수정 후 같은 스위트 8회 연속 통과를 확인했고, 그동안 서버 로그의 42501이 1건 늘었다. 오류가 실제로 났지만 대체 경로로 처리됐다는 뜻이다.

**데이터**: 히어로 회원 3명·생성 회원·이수진 계정·수강·PT(+사용 기록)를 `member-fixtures.ts` 한 곳에서 만든다. seed.ts가 로컬에만 만들던 예약·결제 데모 행과 그 회차는 mock에 없던 데이터라 지웠다(D29 "시드와 mock은 같은 원천"). MEMBER 채번값은 회원번호 prefix별 최댓값으로 맞췄다(SEOCHO2025·SEOCHO2026·GANGNAM2026·생성 지점들).

**검증**: 전체 284 통과, skip 0. 전체 실행 2회 연속 통과(271 → 284: 신규 동시성·시간대·연동 지속성 테스트, `catalog-flow` 재작성). 격리·계약 종료·인사 권한 테스트는 기대값 변경 없이 통과했다. api lint 에러 0(경고 1건은 기존 `main.ts`), api·admin-web 빌드 성공. `catalog-mirror.spec.ts`는 미러가 없어져 `catalog-flow.spec.ts`로 이름을 바꿨다(§45의 옛 이름은 기록이라 그대로 둔다). 응답 형태는 유지했지만 admin-web 화면에서 직접 확인하지 않았다(**검증되지 않음**). 목록 정렬은 회원이 회원번호순, 예약·결제가 생성순으로 바뀌었다.

D30·D31과 같은 방식이다. `memberSeed()`로 upsert SQL을 만들고, 마이그레이션만 한 빈 로컬 DB에 지점·직원·카탈로그를 먼저 넣은 뒤 두 번 돌려 멱등성을 확인했다. `prisma db seed` 결과와 지문이 같은지도 확인했다. MEMBER 채번값은 SQL에서 회원번호로 계산했는데, 시드(JS 계산)와 같은 결과가 나왔다. 회원 계정 비밀번호 해시는 Supabase에 이미 있는 데모 계정 해시를 그대로 써서 데모 비밀번호가 같다. 적용 후 6개 테이블 지문이 로컬과 같다(회원 계정 1, 회원 193, 수강 1, PT 1, 사용 기록 3, MEMBER 순번 79).

## 47. D33 — 근태를 DB로 옮겼다: 옮길 데이터는 없고, 옮길 건 "단일 스레드라서 맞았던" 규칙들이었다 (2026-09-29)

**계기**: D32로 참조 순서가 끝난 뒤 남은 mock 도메인 넷(근태·게시판·자산·문서) 중 첫 번째다(사용자 요청 "근태 이관 진행해줘"). 근태를 먼저 고른 이유는 D30 직원 미러를 가장 많이 읽는 곳이어서다. 결근 판정이 근무 형태·휴무 요일·파견 이력을 전부 읽는다. 착수 전 조사로 두 가지를 확인했다. ① 근태·휴가·잔여·업무일지는 mock에서도 빈 배열로 시작한다. **옮길 데이터가 없고, Supabase 해당 4개 테이블도 0행이다.** 그래서 시드가 필요 없다. ② 대신 mock이 단일 스레드라 저절로 지켜지던 규칙이 셋 있다. 하루 1건 체크인, 승인 시 1회 차감, 결근 확정 멱등이다. 이번 이관의 실제 내용은 이 셋을 동시 요청 아래에서도 지키게 만드는 것이었다(상세: 2-1 D33).

**설계 판단**:
- **스키마를 바꾸지 않고 이미 있는 제약 위에 얹었다.** 체크인은 `(staffId, date)` unique의 P2002를 409로 바꾼다. 휴가 승인·반려와 체크아웃은 조건부 갱신("PENDING일 때만", "체크아웃 없을 때만")으로 처리한다. 연차 잔여 증가는 승인과 같은 트랜잭션에서 원자적 증가로 한다(data-integrity §6 체크리스트). 결근 확정은 `createManyAndReturn(skipDuplicates)`라서, 동시 호출이 겹쳐도 각자 자기가 만든 행만 돌려받는다.
- **업무일지만 앱 잠금이다.** 하루 1건 규칙에 DB unique가 없다. unique를 추가하는 것은 스키마 변경이라 사용자 승인 대상이다(CLAUDE.md). 그래서 `pg_advisory_xact_lock`으로 같은 직원·날짜의 upsert를 직렬화했다. unique 추가는 후속 제안으로 남긴다.
- **파견 이력 미러를 지웠다.** 유일한 독자가 근태(`branchIdForStaffOnDate`, ADR-ATT-03)였기 때문이다. D32가 D31 카탈로그 미러를 지운 것과 같은 논리다. 직원·계정 미러는 문서·게시판이 아직 읽어서 남긴다.
- **결근 미리보기의 전체 스캔을 없앴다(traffic-infra-review 근태 항목의 첫 대응).** mock은 직원×날짜 루프마다 전체 근태·휴가 기록을 다시 훑었다. 이제는 쿼리 4개로 후보 직원·파견 이력·그 달 근태·그 달과 겹치는 승인 휴가를 한 번씩 읽고 Set으로 판정한다. 판정 규칙과 순서는 그대로다.

**발견**:
1. **연차 잔여의 "올해"가 호스트 시간대였다.** 연도를 `new Date().getFullYear()`로 구해서, UTC 서버에서는 1월 1일 00:00~08:59 KST 요청이 전년도 잔여를 읽거나 만든다. 입사 연도도 같은 방식이었다. 둘 다 `todayKst()`와 날짜 문자열의 연도로 고쳤다. D32의 환불 마감에 이어 date-time-handling.md의 전수 교체(10곳)가 놓친 호출부다. 그 교체는 `toISOString().slice`를 찾았고, `getFullYear()` 같은 로컬 getter는 검색 대상이 아니었다. 이번에 `apps/api/src`를 grep해서 로컬 getter(`getFullYear`·`getMonth`·`getDate`·`getHours`·`setHours`)가 더는 남아 있지 않음을 확인했다.
2. **UI 확인이 테스트 기준 DB를 오염시켰다.** D32 화면 확인 때 로컬 API를 테스트 기준 DB(`sports_erp`)에 붙여 띄워서, 화면에서 한 쓰기(UI테스트회원, 예약·결제, PT 차감)가 기준 DB에 남았다. 이번 전체 테스트에서 회원번호·지점 건수 기대값 7건이 실패하면서 드러났다(`SEOCHO2026-002` 기대, `-003` 수신). 코드 문제가 아니라 기준 DB 문제라서 `prisma migrate reset`으로 되돌렸다. 이번 근태 화면 확인은 기준 DB를 복제한 별도 DB(`sports_erp_ui`)에 API를 붙여서 했다. **로컬 화면 확인은 기준 DB가 아니라 복제본에서 할 것.**
3. **STAFF가 근태 화면을 열면 지점 요약 API가 403이다.** 화면이 역할과 무관하게 요약을 조회하고 표시만 숨기기 때문이다. 이관 전부터 있던 문제다(문서함 보존기한 알림 403과 같은 형태). 이번 범위 밖이라 별도 작업으로 제안했다.

**검증**:
- **전체 테스트**: 292 통과, todo 1(기존). 2회 연속 통과했다. 격리·계약 종료·인사 권한 테스트는 기대값을 바꾸지 않고 통과했다.
- **신규 `attendance-rules.spec.ts`(8건)**: 동시 체크인, 체크아웃 중복, 지각 판정(가짜 시각), KST 연차 연도, 동시 승인 1회 차감, 병가·반려 미차감, 동시 결근 확정, 업무일지 동시 작성을 확인한다. 도메인 문서가 "검증되지 않음"으로 남겨 둔 4개 항목이 여기서 해소됐다.
- **음성 대조군**: 보호 장치 5개(P2002 변환, PENDING 조건, advisory lock, KST 연도, skipDuplicates)를 하나씩 빼면 해당 테스트가 실패함을 확인했다.
- **lint·빌드**: api lint 에러 0(경고 1건은 기존 `main.ts`), api 빌드 성공.
- **화면 확인(복제 DB, admin-web)**: 직원으로 체크인(지각 판정)·체크아웃·휴가 신청·업무일지를 하고, 지점장으로 요약 조회와 승인을 했다. 승인 뒤 잔여가 16일에서 13일로 줄었다.

**커밋**: `src/modules/attendance/attendance.service.ts`(신규)·`attendance.controller.ts`·`attendance.module.ts`, `mock-data.service.ts`(근태 로직·파견 이력 미러 제거), `staff.service.ts`, 테스트(`attendance-rules` 신규, `attendance-absence`·`attendance-branch-snapshot`·`staff-mirror`를 DB 기반으로), 2-1 D33, 이 로그 절, 근태관리 도메인 문서, traffic-infra-review, 2-3, CLAUDE.md.

## 48. D34 — 문서를 DB로 옮기며 직원 미러를 없앴다: D30의 "커밋 뒤 mock 적용"이 이걸로 끝났다 (2026-09-29)

**계기**: 근태(D33) 다음 순서다(사용자 요청 "문서 이관 진행해줘"). 남은 mock 도메인 셋(게시판·자산·문서) 가운데 문서만 D30 직원 미러를 읽는다. 문서를 옮기면 직원 미러를 읽는 곳이 없어진다. 퇴사 → 인사서류 보존기한 재계산(ADR-RES-02)은 D30 결정 3이 "커밋 뒤 mock에 적용"으로 미뤄 둔 **마지막 교차 저장소 부수효과**였다. 문서를 옮기면서 이것도 퇴사 트랜잭션 안으로 넣었다(상세: 2-1 D34).

**설계 판단**:
- **규칙과 검사 순서는 그대로다.** 순서는 지점 없음 → 계약 종료 → 인사서류 대상 직원 → 계약서 보존기한 필수다. 에러 코드 우선순위가 격리·계약 종료 테스트로 고정돼 있어서다. 보존기한 기산(§5-6)과 소프트 삭제(D9)도 mock 구현 그대로다.
- **퇴사 트랜잭션에 보존기한 재계산을 넣었다.** 퇴사 트랜잭션은 이미 직원 상태, 계정 비활성화, 파견 종료를 묶고 있었다. 여기에 `recalculateHrRetention(tx, …)`을 더했다(data-integrity §6 퇴사 체크리스트). 이로써 D30 결정 3의 비원자 구간이 모두 없어졌다.
- **직원 미러를 없애고 계정 미러만 남겼다.** 게시판이 작성자 이름을 계정에서 읽기 때문이다. `replaceAccountMirror`·`upsertAccountMirror`로 좁혔다. 테스트 `staff-mirror.spec.ts`는 `account-mirror.spec.ts`로 바꿨다.
- **목록 N+1과 임박 목록 전체 스캔을 함께 없앴다**(traffic-infra-review 자원문서관리 항목의 문서 절반). 지점 이름은 조인으로 가져온다. 관련 직원과 업로더 이름은 id를 모아 한 번에 조회한다. 임박 목록은 `retentionUntil <= 기준일` 조건 쿼리로 바꿨다. `Document`에는 두 id 컬럼의 외래키가 없어서 조인 대신 묶음 조회를 썼다. 외래키 추가는 스키마 변경이라 사용자 승인 대상이고 후속으로 남겼다.

**발견**:
- **보호 테스트 두 개(격리·인사 권한)가 미러를 직접 읽고 있었다.** `hr-authority`·`branch-isolation`이 직원·문서 상태를 `mockData(app).staff`·`.documents`에서 읽었다. 미러가 사라지면서 읽는 곳만 `db(app)`으로 바꿨고, **기대값은 하나도 바꾸지 않았다**(CLAUDE.md 가드레일). `branch-isolation`의 직원 픽스처 선택 순서도 미러를 채우던 조회(`staff.findMany()`, 정렬 없음)와 같게 두어, 공격 대상 직원이 바뀌지 않게 했다.
- **목록 정렬이 바뀌었다.** mock은 배열에 넣은 순서(매뉴얼 → 계약서)였고, 이제는 `createdAt` 순(계약서 2026-01 → 매뉴얼 2026-08)이다. 화면에 영향이 없는 것을 확인했다.

**검증**:
- **자동 테스트**: 전체 298 통과, todo 1(기존). 격리·계약 종료·인사 권한 테스트는 기대값 변경 없이 통과했다.
- **새 `document-rules.spec.ts`(6건)**:
  - 인사서류 대상 직원: 필수(400), 존재(404), 타 지점 403
  - 보존기한: 재직자는 오늘 KST+3년, 퇴사자는 퇴사일+3년
  - 삭제: 본사 전용이고 소프트 삭제다. 행은 남고 상세·목록에서 빠지며, 두 번째 삭제는 404
  - 임박 목록: 기준일 이하만, 보존기한 순, 영구 보관·삭제 문서 제외
  - 목록 범위와 이름 필드
  - 도메인 문서가 "검증되지 않음"으로 남긴 두 항목(인사서류 필수, 삭제 권한)이 여기서 해소됐다.
- **음성 대조군**: 네 가지를 하나씩 빼 보면 매번 해당 테스트가 실패했다. 뺀 것은 퇴사 트랜잭션의 재계산, 목록의 소프트 삭제 필터, 지점 관리자 목록 범위, 퇴사일 기산이다. 목록 범위를 빼면 격리 테스트도 함께 실패했다.
- **lint·빌드**: api lint 에러 0(경고 1건은 기존 `main.ts`), api 빌드 성공.
- **화면**: 복제 DB(`sports_erp_ui`, §47 교훈)에서 admin-web으로 확인했다.
  - 지점장: 인사서류를 등록했다. 대상 직원 목록은 DB에서 오고, 보존기한은 오늘+3년이었다.
  - 본사: 임박 목록 1건을 확인하고 소프트 삭제했다.
  - 403 1건은 이전부터 있던 문서함 알림 문제(§47 발견 3과 같은 형태, 별도 작업으로 제안됨)다.

## 49. D35 — 자산을 DB로 옮겼다: 채번 헬퍼의 세 번째 사용처, 그리고 mock의 부분 수정 결함 하나 (2026-09-29)

## 50. D36 — 게시판을 옮기고 `MockDataService`를 지웠다: D26에서 시작한 실DB 전환이 끝났다 (2026-09-29)

**계기**: 자산(D35) 다음 순서다(사용자 요청 "게시판 이관 진행해줘"). 착수 전에 `MockDataService`를 누가 쓰는지 grep했다. 남아 있던 것은 전부 게시판 때문이었다. 게시글 배열, 작성자 이름용 계정 미러(D30), 지점 이름용 이름표 사본(D29), 데모 비밀번호 상수다. 그래서 이번 단계는 "게시판 이관"과 "mock 저장소 삭제"가 한 번에 끝나는 마지막 단계였다(상세: 2-1 D36).

**설계 판단**:
- **가시성과 페이지네이션을 쿼리로 내렸다**(ADR-BRD-01·02, traffic-infra-review 게시판 항목). mock은 전체 배열을 거른 뒤 잘랐다. 이제는 같은 규칙을 where 조건으로 옮기고 `count` + `skip/take`로 자른다. 규칙은 이렇다: 본사는 전부, 그 외에는 전사 공지와 자기 지점 글, 회원은 비노출 본사 공지를 뺀다. 작성자 이름은 id 묶음 조회, 지점 이름은 조인으로 가져온다.
- **조회수를 원자적으로 증가시켰다.** mock의 `viewCount += 1`은 읽은 값에 더하는 방식이라 동시 조회에서 증가분을 잃는다. 수정과 삭제는 "삭제되지 않았을 때만" 반영되는 조건부 갱신으로 바꿨다.
- **`MockDataService`·`MockDataModule`·계정 미러를 삭제했다.** D32~D35에서 미러를 하나씩 지운 것과 같은 논리의 마지막 단계다. `StaffService`의 미러 갱신을 뺐고, 데모 비밀번호는 `mock-data/demo-password.ts`로 옮겼다. 응답 형식 타입과 시드 원천은 남겼다. 폴더 이름 `mock-data/`는 역할과 맞지 않지만 이름 변경은 후속으로 기록만 했다.
- **시드 id를 고쳤다.** `seed.ts`는 게시글 2건을 무작위 uuid로 `create`하고 있었다. 그래서 mock id와 달랐고, 시드를 다시 돌리면 두 벌이 생겼다. 픽스처 id(`post-hq-manual` 등)로 upsert하도록 바꿨다.

**발견**:
1. **mock이 가려 주던 테스트 간 누수.** `posts-member-visibility.spec.ts`의 페이지네이션 테스트 3건이 전체 실행에서 실패했다. 앞 테스트가 만든 25건이 다음 테스트 DB에 남았기 때문이다. mock 시절에는 새 앱만 띄우면 게시글이 초기화돼서 드러나지 않았다. 코드 문제가 아니므로 기대값은 그대로 두고, CLAUDE.md 규칙대로 `beforeEach`에서 `resetWorkerDb()`를 부르게 했다. 이 교훈은 CLAUDE.md 테스트 작성 규칙에 남겼다.
2. **이름만 남은 검증들.** `branch-parity`의 첫 케이스("mock 사본 = DB")와 계정 미러 테스트는 대상이 사라졌다. 앞의 것은 "시드 원천(`branch-fixtures.ts`) = DB"로 바꿔 시드 정합성 검증으로 살렸다. 계정 미러 테스트는 `staff-write.spec.ts`로 이름을 바꾸고 채용·파견의 DB 검증만 남겼다.

- 1.spec/2.decisions 옛 문서 삭제 실행(inbound 링크 정리) 시점 — 9개 도메인 전체가 문서화·핵심 ADR 구현까지 끝났으니 이제 본격적으로 할 만한 시점.
