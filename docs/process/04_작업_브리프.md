# 04. 작업 브리프 — 남은 일을 세션 하나씩으로 나눈 계획 (2026-10-07)

> [문서 지도](../README.md) · 우선순위와 진행 상태는 [STATUS](../STATUS.md)가 기준이다. 이 문서는 "그 일을 새 세션에서 어떻게 시작하나"만 담는다.
> 끝난 브리프는 지우고 경위는 `log/`로 보낸다(STATUS와 같은 방식).

## 공통 — 모든 세션

1. **시작**: `CLAUDE.md`(자동) → [STATUS](../STATUS.md) → 이 문서의 해당 브리프 → 관련 도메인 요약 카드.
2. **브랜치**: `dev`에서 새 작업 브랜치를 딴다(D39). 끝나면 `dev` 대상 PR → CI 통과 → rebase 병합. `main`에는 손대지 않는다.
3. **근거 먼저**: 구현 전에 근거 ID(ADR·D)를 밝힌다. 결정이 없으면 대안·트레이드오프를 먼저 적고 사용자에게 고르게 한다.
4. **로컬 테스트 DB**: PG16 클러스터. `pg_ctlcluster 16 main start` → `apps/api/.env`(gitignore, `.env.example` 참고) → `npx prisma migrate deploy --schema=apps/api/prisma/schema.prisma` → `npm run prisma:seed --workspace=apps/api`. 새 clone이면 `npm ci`와 `npm run prisma:generate`를 먼저 실행한다.
5. **커밋**: `git add`와 `git commit`을 따로 실행한다. 한 명령으로 묶으면 커밋 전 hook이 막는다. 메시지는 한국어로 쓰고 근거 ID를 넣는다.
6. **마무리**: `wrap-up` 스킬(STATUS + `log/NNN.md`).
7. **사용자 승인 대상**: 배포 DB(Supabase) 쓰기, 스키마 변경, 범위 제외 항목 구현. 배포 DB 쓰기는 Supabase 커넥터 인증이 필요하다. 2026-10-06에 인증 오류가 나서 사용자가 SQL Editor에서 직접 실행했다(log/074).

## B1. 회원 모바일 웹 — D40 (가장 큼, 세션 3~4개)

**목표**: 회원이 휴대폰 브라우저로 로그인 → 프로그램·회차 조회 → 예약·취소 → 모의 결제 → 공지·혼잡도 조회를 하게 한다. 대상은 수도권 83곳이다. 발표 시연 전에 끝내는 것이 목표다.

**이미 있는 것(새 API는 거의 필요 없다)**
- 인증: `POST /auth/login`·`/auth/refresh`·`/auth/logout`, `GET /auth/me`, `PATCH /auth/password`
- 회원 가입·연동(공개 라우트): `POST /members/register`, `POST /members/link`(시간당 5회 제한, ADR-MEM-01·02)
- 조회: `GET /programs`, `GET /programs/:id/slots`, `GET /facilities`(혼잡도 포함), `GET /posts`, `GET /posts/:id`
- 예약·결제: `POST /reservations`(MEMBER), `GET /reservations`, `PATCH /reservations/:id/cancel`, `POST /payments/:reservationId/mock-pay`(MEMBER)
- 내 정보: `GET·PATCH /members/:id`, `GET /members/:id/enrollments`, `GET /members/:id/pt-sessions`. 수정은 MEMBER 본인만 하고, 담당 직원·메모는 바꿀 수 없다.
- 관리자 웹에는 이미 MEMBER 메뉴가 있다(대시보드·프로그램·예약·게시판·시설). 데스크톱 레이아웃이고, 데모 계정은 `lee.sujin@example.com`(서초점 회원)이다.

**첫 세션에서 정할 것(사용자에게 묻기) — 앱 형태와 배포 경로**

현재 Worker(`cloudflare-worker/wrangler.jsonc`)는 `apps/admin-web/dist`만 정적 자산으로 서빙한다. 없는 경로는 `single-page-application` 설정에 따라 **관리자 웹 `index.html`로 넘어간다**. 그래서 회원 웹을 붙이는 방식이 이 구조를 결정한다.

| 안 | 내용 | 장점 | 비용·위험 |
|---|---|---|---|
| A | admin-web 안에 `/m/*` 회원 전용 모바일 레이아웃을 둔다 | 빌드·배포 무변경, API 클라이언트·인증·타입 재사용 | 관리자 번들에 회원 화면이 섞인다(크기 증가), 앱 경계가 흐려진다 |
| B | `apps/member-web` 별도 Vite 앱(`base: '/m/'`), 빌드 결과를 Worker 자산 폴더에 합친다 | D40·STATUS가 예정한 형태, 번들 분리 | `/m/*` 새로고침이 관리자 `index.html`로 가지 않게 해야 한다(Worker가 `/m/*`를 먼저 처리하거나 자산 구성 변경). 배포 스크립트·CI 변경 |
| C | 회원 웹 전용 Worker를 하나 더 둔다 | 완전 분리 | 오리진이 둘이라 D25가 없앤 CORS 문제가 돌아온다. Workers 무료 한도(⑬, 하루 9.3만 건 가정)를 두 Worker가 나눠 쓴다 |

권장은 **B**다(D40 결정 2의 "같은 스택·같은 Worker"와 맞는다). 다만 `/m/*` SPA 폴백을 먼저 시험해 보고, 막히면 A로 간다. 결정은 `decisions/D41.md`로 남긴다.

**세션 나누기**
1. **B1-1 결정 + 뼈대**: D41 작성 → `apps/member-web` 생성(또는 A안이면 `/m` 레이아웃) → 로그인·토큰 갱신 → Worker 배포 경로 확인(로컬 `wrangler dev`).
2. **B1-2 조회·예약**: 프로그램 목록 → 회차 → 예약 생성·취소 → 모의 결제. 오류 코드 처리를 포함한다(`BRANCH_TERMINATED` 409, 정원 초과, 취소 마감).
3. **B1-3 공지·혼잡도·내 정보**: 게시판(회원 공개 범위는 `posts-member-visibility.spec.ts` 기준), 혼잡도 5단계, 내 예약·수강·PT 잔여.
4. **B1-4 배포·기록**: CI(`.github/workflows/ci.yml`)에 lint·빌드 추가, Worker 배포, 덱의 `req-shot-member` 캡처 갱신은 사용자 요청이 있을 때만(보호 영역), 문서(회원관리·예약및결제 요약 카드, 요구사항추적표 §3, D40 재고 메모)를 정리한다. 배포 후 방문당 실제 호출 수를 세서 design-constants ⑩(가정 10건)을 실측값으로 바꾼다.

**주의**
- 화면 작업 전 [디자인시스템](../design/디자인시스템.md)을 읽는다. 모바일 웹이라 기준 폭을 360px로 정하고 시작한다.
- 새 API 라우트를 만들면 `apps/api/test/branch-isolation.spec.ts` 공격 케이스 표에 추가한다(CLAUDE.md 불변식).
- 웹앱은 자동 테스트가 없다. Playwright(크로미움 설치됨, `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`)로 로컬에서 스크린샷을 찍어 확인하고, 그래도 보고는 "자동 테스트 없음"으로 한다.
- 요청량: 회원 기능은 방문당 약 10회 호출을 가정했다(design-constants ⑩). 화면 하나가 API를 여러 번 부르면 이 가정이 깨진다. 목록과 상세를 한 번에 받는 쪽을 우선한다.
- 혼잡도 화면(B1-3)은 **자동 폴링하지 않는다**(ADR-FAC-04). 화면 진입과 수동 새로고침(최소 간격)만 허용하고, `lastUpdatedAt`으로 "N분 전 갱신"을 보여 준다.

[요구사항추적표](../reference/요구사항추적표.md) §2-3·§3 기준. 2026-10-07에 확인했을 때 api 코드에는 `auditLog` 쓰기가 없었다(마스킹은 B5-1로 구현, ADR-MEM-04).
- **B5-2 AuditLog 기록**: 스키마(`AuditLog`, actorId SET NULL)는 이미 있다. 어떤 이벤트를 남길지(권한 변경·퇴사·계약 상태 변경, 그리고 회원·직원 상세의 전화번호 원문 열람 — ADR-MEM-04 숙제) 먼저 정한다. 쓰기는 같은 트랜잭션 안에서 한다(data-integrity 체크리스트).
- **B5-3 공통 Toast**(admin-web): 화면마다 다른 성공·오류 알림을 하나로 모은다. 디자인시스템 먼저.

## B8. 쌓이는 목록 페이지네이션 — D43·ADR-RSV-04 (중간, 세션 1~2개, 옛 B6 흡수)

**목표**: `GET /members`·`/reservations`·`/payments`·`/assets`에 게시판(ADR-BRD-02)과 같은 offset 페이지네이션을 넣는다. 결제 목록의 날짜 필터는 DB 조건으로 내린다(ADR-RSV-04).

**할 일**
1. api: 4개 서비스의 `list`를 `{ items, total }`로 바꾸고 `count` + `skip/take`를 넣는다. 컨트롤러는 `page`·`limit`을 받아 `ok(items, { page, pageSize, total })`로 내린다(`posts.controller.ts`를 그대로 따른다). `limit` 상한(예: 100)을 정한다.
2. 결제: `dateFrom`·`dateTo`를 KST 날짜 경계(`kst-date.ts`)의 `approvedAt` 범위로 바꿔 where에 넣는다. 미승인 건(`approvedAt` 없음)은 지금처럼 날짜 필터에서 빠지지 않게 `OR`로 둔다.
3. admin-web: 회원·예약·결제(매출)·자산 화면에 쪽 넘김을 붙인다. 화면이 지금 받는 배열 응답이 meta 포함으로 바뀌므로 같은 PR에서 함께 고친다. 디자인시스템 먼저 읽는다.
4. 화면과 함께 정할 것(사용자에게 묻기): 예약·결제를 최근 것부터(`desc`) 보일지, 자산 기본 목록에서 `DISPOSED`를 뺄지.

**주의**
- 응답 형식이 바뀌는 외부 인터페이스 변경이다. 회원 모바일 웹(B1)이 먼저 나와 있으면 그쪽 호출도 함께 고친다.
- 테스트: 쪽 크기·total·마지막 쪽, 결제 KST 날짜 경계(00:00~08:59 KST 승인 건), 미승인 건 포함 여부를 추가한다. 지점 범위가 바뀌지 않으므로 `branch-isolation.spec.ts`는 기존 케이스가 그대로 통과하는지만 본다.
- `Payment(approvedAt)` 인덱스 추가는 스키마 변경이라 사용자 승인 대상이다. 필요한지는 먼저 재 보고 판단한다.
- `contains` 검색 인덱스와 이력 아카이빙은 범위 제외다(D43 결과).
