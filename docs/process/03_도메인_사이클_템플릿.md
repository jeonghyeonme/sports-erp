# 도메인 사이클 템플릿 (Architecture Driver 방법론)

> **상태**: 초안 (2026-09-22)
> **출처**: [티켓 예매 시스템 | 고객 요구에서 설계로 가는 접근법](https://www.youtube.com/watch?v=7excI-0n2xk) (코딩하는기술사) — 자막 전문 확인. 아래 타임스탬프는 이 영상 기준.
> **목적**: 이 흐름을 도메인 9개 각각에 반복 적용해 "도메인별로 확정"한다. 영상은 시스템 하나에 이 과정을 1번 돌렸지만, 우리는 도메인마다 1번씩 돌린다.

## 원칙: Driver는 소수만 남긴다

영상은 요구사항 전부를 Driver로 승격시키지 않는다. 콘서트 티켓 시스템 예시에서도 **Driver 5개, 설계 질문 3개**로 끝난다(재사용성 같은 하위 우선순위 Driver는 목록엔 있지만 별도 설계 질문·대안비교까지 가지 않음). **이 제한 자체가 방법론의 일부**다 — 한 도메인에서 실제로 구조를 바꾸는 결정은 보통 몇 개 안 된다. 나머지 요구사항은 4단계(수치화)까지만 하고 Driver로 승격시키지 않은 채 규칙표로만 남긴다.

## 문서 순서 원칙: 입력은 앞, 결정 과정은 가운데, 산출물은 맨 뒤

옛 스펙 문서(1-2~1-10)를 병합할 때 내용을 성격별로 구분해서 배치한다. 셋을 섞지 않는다.

1. **§0. 도메인 개요 (사용자 스토리)** — 맨 앞. 이건 우리 결정으로 바뀌지 않는 **원본 입력값**(만족시켜야 할 대상)이라, 독자가 F01a 같은 요구사항 ID를 만나기 전에 먼저 맥락을 잡게 해 준다. 영상도 고객의 원문 요구사항을 먼저 쭉 나열한 뒤에 분류로 들어간다 — 같은 순서.
2. **§1~12. 요구사항 분류 → Driver → 대안 비교 → 결정 (ADR)** — 이 문서의 본체. 3자가 "왜 이렇게 설계했는가"를 읽어나가는 부분.
3. **부록 A. 레퍼런스 스펙 (데이터모델·화면·API·권한매트릭스·구현우선순위)** — 맨 뒤. §1~12(원인)의 **결과 스냅샷**이라 뒤에 둔다. 레퍼런스를 위에 두면 "옛 스펙이 고정 사실이고 그 위에 결정을 얹는다"는 인상을 주는데 실제로는 반대다 — 분석 결과 스펙이 바뀌어야 한다고 나오면 부록 쪽을 고친다. 이 부분은 서사가 아니라 조회용이므로 "부록"으로 표시해 3자가 훑고 지나가도 되는 부분임을 신호한다.

[domains/권한관리.md](../domains/권한관리.md)가 이 순서의 예시다.

## 단계 (도메인 하나당)

### 0. 입력 (이미 준비됨)
- [01_RFP_분류와_되묻기.md](./01_RFP_분류와_되묻기.md)에서 이 도메인에 해당하는 항목
- [02_도메인별_우선순위.md](./02_도메인별_우선순위.md)의 도메인 우선순위(상/중/하)와 근거

### 1. 요구사항 재분류 — 기능 / 품질 / 제약 / **불변규칙**
영상의 4분류를 그대로 쓴다. "불변규칙"은 **협의가 불가능한 것**(트레이드오프 대상이 아닌 것)만 넣는다. 이 프로젝트에서는 CLAUDE.md의 "도메인 불변식"(지점 데이터 격리·계약 종료 지점 차단·인사 권한 분리)이 대부분의 불변규칙에 해당한다 — 도메인별로 이 불변식이 어떻게 구체화되는지 여기서 적는다.

### 2. 모호한 표현 구체화 (되묻기)
01번 문서의 되묻기(Q-nn) 중 이 도메인 것을 확정한다. 실제 되물을 대상이 없으므로 "임시 가정 + 확정 근거"로 남긴다(01번 문서 §0 원칙과 동일).

### 3. 검증 가능한 형태로 — 수치화
가능한 건 수치로 만든다. 여기서 **공용 산정 상수**(`architecture/design-constants.md` — Q-01에서 낸 값)를 재사용한다. 새로 리서치하지 않는다.

### 4. Architecture Driver 식별 (소수로 제한)
3단계 산출물 중 **구조를 바꾸는 것만** 골라 2~5개로 제한한다. 판단 기준: 이걸 어떻게 정하느냐에 따라 데이터 모델·API 형태·동시성 처리 방식이 달라지는가? 아니면 구현 디테일일 뿐인가? 후자는 Driver가 아니라 그냥 엣지케이스 규칙표(Tier2)로 남긴다.
영상처럼 **RFP에 명시 안 됐지만 경험상 필요한 Driver**(예: 외부 결제 장애 격리)를 추가할 수 있다 — 근거를 반드시 적는다.

### 5. Driver 우선순위
불변규칙이 항상 최우선. 나머지는 이 도메인의 리스크·사업 영향으로 순서를 매긴다.

### 6. 현행 구조 진단 (Baseline)
지금 구조(MockDataService 인메모리, 특정 컨트롤러 로직) 그대로면 이 Driver들에서 뭐가 터지는지 먼저 짚는다. 영상이 "기존 구조로 30만 명 오면 DB가 병목"이라고 먼저 진단한 것과 같다. 이 프로젝트는 실DB가 아직 없으므로, "실DB 전환 시 이 지점이 병목이 된다"는 형태로 적어도 된다(전환 자체는 별도 승인 사안 — CLAUDE.md).

### 7. 설계 질문 도출 (Driver당 최대 1개, 전체 도메인당 1~3개로 제한)
"~하면 어떻게 해야 하는가?" 형태의 질문으로 바꾼다.

### 8. 대안 → 트레이드오프 → 결정
질문마다 대안 2~4개를 나열하고, 각각의 장단점을 비교한 뒤 **5단계에서 정한 우선순위**를 판단 기준으로 결정한다. 선택 안 된 대안도 "부가적으로 결합 가능"하면 명시한다.

### 9. 감수하는 것 정리
이 결정으로 얻는 것과 감수하는 것(비용·제약·후속 숙제)을 명시적으로 적는다. "완벽한 무결점 구조"를 찾는 게 아니라 트레이드오프를 알고 선택했다는 걸 남기는 것.

### 10. ADR 기록
포맷(영상 기준, MADR보다 단순화):
```
## 컨텍스트
(이 결정이 필요해진 상황 — Driver·수치)

## 검토한 대안
1. ...
2. ...

## 결정
(무엇을 선택했는지 + 왜)

## 결과
- 좋아진 것: ...
- 감수하는 것: ...
- 남은 숙제: ...
```

### 11. 검증 (가설 인정)
"여기까지는 가설"(영상 10:339~1370s)이라는 태도를 그대로 가져온다. 이 프로젝트에서 검증은:
- **Tier1 Driver**: 가능하면 실측(부하·동시성 테스트). 단, 현재 MockDataService 환경의 한계를 명시(예: 정원 동시성은 Node 단일 프로세스 특성상 팬텀 삽입 자체가 안 일어남 — 1-7문서 §8 기존 서술과 동일 태도).
- **Tier2 규칙**: `apps/api/test/`에 케이스 추가, 없으면 "검증되지 않음"으로 명시(CLAUDE.md 보고 원칙과 동일).
- 검증에 실패하면 4~10단계로 돌아간다.

## 이 템플릿이 부담을 줄이는 이유

- 도메인 하나에서 실제로 정밀 비교가 필요한 Driver는 보통 **2~5개**뿐이다(영상 예시와 동일 규모).
- 3단계(수치화)의 재료는 대부분 이미 만든 공용 상수를 재사용하는 것이라, 도메인마다 새로 리서치하지 않는다.
- Driver로 승격되지 않은 나머지 요구사항은 정량 비교 없이 규칙표(Tier2)로 끝난다 — "모든 것을 이 무게로 다뤄야 한다"는 전제 자체가 틀렸다.

### 12. 이월 사항 + 문서 마이그레이션 메모
- 이 사이클에서 나왔지만 다른 도메인 소관인 발견(되묻기·엣지케이스)을 적어 다음 사이클로 넘긴다.
- 이 도메인의 옛 스펙 문서(`1.spec/`)·관련 있으면 `2-1_기술결정사항.md` 조각을 [05_문서_마이그레이션_추적.md](./05_문서_마이그레이션_추적.md) 기준(유지/병합후축약/폐기후보)으로 판정해 그 표에 행을 추가한다. **지금 실제로 옛 문서를 고치지 않는다** — 표에 기록만 하고, 실행은 전체 사이클이 끝난 뒤 한 번에 한다.
- **[06_진행_로그.md](./06_진행_로그.md)에 한 단락을 추가한다** — "무엇을 결정했나"(ADR)가 아니라 "이 사이클에서 왜 이런 판단을 했고 무엇을 근거로 삼았는지, 무엇을 발견했는지, 어떻게 검증했는지(수치 포함)"를 남긴다. 도메인 문서 자체와 다른 관전 포인트다 — 도메인 문서는 결과, 로그는 과정.
